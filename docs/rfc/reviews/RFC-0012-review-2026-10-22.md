## Findings, most serious first

### 1. F219's deviation rests on a false premise: the reference never answers `found=false`

R:409-412 says `graph.path`'s crash is "deliberately changed to
`found=false` (F219, D193 §5)". F219's disposition gives the reason:
"`{ found=false }`, what `graph.path` already answers for a node it cannot
reach (`getpath.rs:76`)" (`docs/registers/defects.md`, F219, the
**Disposition** paragraph). D193 §5 repeats it. **That branch never runs in
the reference:**

- `fast_paths::calc_path` (`lib.rs:81-84`) is
  `calc_path_multiple_sources_and_targets` (`path_calculator.rs:55-62`).
- When no meeting node is found it answers `None`
  (`path_calculator.rs:198-199`).
- Otherwise it asserts `best_weight < WEIGHT_MAX` (`:201`) and builds the
  `ShortestPath` with that weight (`:204`).
- `is_found` is `self.weight != WEIGHT_MAX` (`shortest_path.rs:84-86`). So
  every `Some` it answers is found, and `getpath.rs:76-77` is dead.
- The reference's answer to "no path" is `None`, which `getpath.rs:93`
  turns into the error **`GRAPH.PATH: can not calculate path`**.

Run in both engines today:

```
:C :A [ [ :A :B 1.0 ] [ :C :B 1.0 ] ] [ :A :B :C ] graph! graph.path println
:A :C [ [ :A :B 1.0 ] [ :C :B 1.0 ] ] [ :A :B :C ] graph! graph.path println
:C :A [ [ :A :B 1.0 ] ]               [ :A :B :C ] graph! graph.path println
```

- First two (C is inside `fast_paths`' size, no path):
  `GRAPH.PATH: can not calculate path` in the oracle **and in Bund2**.
- Third (C is past the size, F219's case): the oracle panics; Bund2
  answers `{ found=false }` (`G:272-274`).

So Bund2 now reports "no path" in two shapes, an error or a MAP. Which one
a program gets depends on whether the unreachable node lies past the
largest endpoint `fast_paths` kept. Adding the unrelated edge `C → B` turns
`found=false` into an error. A program that tests `found` never sees
`false` in the in-size case, and a program that wraps `graph.path` in
`?try` gets no error in the F219 case. This is the same kind of
order-and-shape dependence F220 and D198 were raised for, and the RFC does
not state it anywhere.

D193's options listed "an ordinary error for F219 instead of
`found=false`" (R:471-472), and the owner rejected it. That was decided on
the belief that `found=false` was already the reference's no-path answer.
The second review's finding 5 (`RFC-0012-review-2026-10-18-2.md:184-218`)
never mentions `can not calculate path`. No register records this case.
No golden pins either shape (`grep` of `tests/golden` for both strings is
empty).

- **No criterion reaches it.** Criterion 8's
  `graph_path_answers_no_path_for_a_node_no_kept_edge_reaches` pins
  `found=false` for the five out-of-size graphs. Nothing pairs one with
  the in-size case.
- **Repair: take it to the owner.** This is an approved deviation whose
  grounding was wrong. Options:
  - **A.** F219's case answers `GRAPH.PATH: can not calculate path`, the
    reference's own no-path answer. The panic is still replaced, but by
    behaviour the reference already has, so "no path" has one shape.
  - **B.** Keep `found=false`, and state the two shapes in "Current
    behaviour", the preservation analysis and F219.
  - **C.** `found=false` for every no-path case. That is a deviation in
    a core word (D14), in-size cases included.
- **Whatever the ruling**, F219's disposition paragraph and D193 §5 need
  dated notes correcting "what `graph.path` already answers". R:155-158
  and R:385-387 need correcting too.

### 2. `graph.bellmanford` reports a zero-weight cycle as negative, and misses a negative one, depending on how far the cycle is from the start

S4 (R:248-253) and the preservation analysis (R:438-442) say
`graph.bellmanford` "refuses only a negative cycle the start reaches". S1
(R:178) offers it as `graph.paths`' rows. The cycle test is a floating-point
relaxation (`GA:641-648`, `:765-803`), and rounding at the magnitude of
the distances decides it. Run under `bund2` today:

```
:S [ [ :S :A 1000.0 ] [ :A :B 3.700101551766398 ] [ :B :C 0.699993338763802 ] [ :C :A -4.4000948905302 ] ] [ :S :A :B :C ] graph! graph.bellmanford println
:A [ [ :A :B 3.700101551766398 ] [ :B :C 0.699993338763802 ] [ :C :A -4.4000948905302 ] ] [ :A :B :C ] graph! graph.bellmanford println
```

- The three cycle weights, as the exact values of those `f64`s, sum to
  **exactly zero**. The model found the case and checked the sum with
  `fractions.Fraction`.
- First line: `GRAPH.BELLMANFORD: S reaches a negative cycle through A`.
- Second line: the same cycle entered at distance 0 answers
  `A 0.0, B 3.700101551766398, C 4.4000948905302`.

```
:S [ [ :S :A 1.0e20 ] [ :A :B 1.0 ] [ :B :A -1.0000000000000002 ] ] [ :S :A :B ] graph! graph.bellmanford println
:A [ [ :A :B 1.0 ] [ :B :A -1.0000000000000002 ] ] [ :A :B ] graph! graph.bellmanford println
```

- The cycle `A ↔ B` weighs `-2.2e-16`, a true negative cycle.
- First line: answers `S 0.0, A 1e20, B 1e20`. That is a finite distance
  where the true answer is unbounded, so the cycle is missed.
- Second line: `A reaches a negative cycle through A`.

So whether `graph.bellmanford` answers or refuses depends on the size of
an unrelated weight on the way into the cycle. This is the problem D199
was raised for ("one case was a wrong answer … the negative cycle went
unreported"), at the bottom of the range instead of the top. D193 §1
ruled on rounding for `graph.maxflow`. Nothing rules on it for
Bellman–Ford, and `Wide` does not help: it widens the range, not the
precision (R:330-336). With non-negative weights a spurious cycle cannot
happen, because `fl(d + w) ≥ d`. So "a swap to it works one way"
(R:441-442) holds against `graph.paths`, but not against `graph.allpath`
with negative fractional weights.

- **No criterion reaches it**: finding 3.
- **Repair: take it to the owner.** At minimum, S4 and the preservation
  analysis must say that a cycle is detected in `f64`, so a cycle whose
  weight is below the rounding of the distances around it can be missed,
  and a zero-weight cycle can be reported. Options the owner might be
  shown:
  - state it, as D193 §1 states the rounding-size share;
  - confirm a reported cycle by summing its weights exactly (in `Wide` or
    in exact arithmetic) and treat a non-negative one as no cycle. That
    fixes the false report but not the missed cycle;
  - run the cycle test in exact arithmetic.

  Each has a cost the RFC should name.

### 3. The random cross-checks use small whole-number weights, so no criterion exercises rounding

`random` (`GA:2191-2208`), which `graphs` feeds to every criterion-3
cross-check and to `the_wide_run_scales_with_the_weights`, draws each
weight as an integer from `lo` to `lo + 8`. Sums of those are exact in
`f64`, and stay exact scaled by `2^1020`. So:

- criterion 3 (R:488-500) says "agrees with an independent one over
  seeded random graphs" and does not say the weights are whole. Its
  Bellman–Ford, MST and max-flow checks cannot see finding 2, or a
  rounding-size share (R:354), or a forest's last bits;
- criterion 11's `the_wide_run_scales_with_the_weights` checks `Wide`'s
  range, not its rounding. "Each answer the plain one scaled, to the bit"
  (R:591) is guaranteed for whole weights whatever `Wide` rounds to. The
  rounding claim, "sums round as `f64`'s would with unbounded range"
  (R:331-332), rests on `wide_sums_round_as_unbounded_f64_would`: seven
  values, four in-range pairs and three out-of-range sums, chosen by hand.

**Repair:** criterion 3 should say "whole weights". The RFC should either
add fractional-weight cross-checks against an exact reference (rationals),
or say that rounding behaviour is specified but untested.

### 4. Smaller points

- **R:3-5, the Status line**, says "revised after its second adversarial
  review … and awaiting the next". Three more reviews followed, and the
  line goes on to list them. The opening clause is stale.
- **R:378-388, "Which points are rulings"**, lists the owner's rulings as
  "(D192, D193, D198, D199, D200)". D202 appears later in the same
  sentence; **D203** is missing. Its face, the acyclic refusal, is a
  separate ruling, and the sentence's "`graph.allpath`'s dependence on
  the last node preserved (F220, D200)" does not cover it on its own.
- **S4, the overflow message** (R:254-255): "naming a node whose distance
  cannot be represented". When several cannot be represented, the code
  names the first in node order (`GA:612-616`). That is fixed and
  reproducible, but unstated, which matters because S3 promises an order
  for everything else.
- **S4, the shape checks** (R:268-276): a graph operand that is not a MAP
  is its own `type`, `nodes` and `edges` (`get_or_self`,
  `crates/bund2-value/src/lib.rs:1520-1528`). So `:A "graph" graph.bfs`
  passes the type check and answers `Nodes list must be a list`, and
  `:A 7 graph.bfs` answers `type casting returns: …`, not `MISSED TYPE`.
  This matches the reference for `graph.paths` (run in both engines
  today: identical messages), but the RFC lists the messages without
  saying which operand produces which.

## What the RFC assumes but does not state

- **That `fast_paths` answers `found=false`.** It does not (finding 1).
- **That `f64` relaxation decides "negative cycle".** The RFC writes as if
  the cycle test were exact (finding 2).
- **That each reverse arc in `max_flow` holds at most its edge's
  capacity** (R:323-324, and D199's "Built"). This is the exact-arithmetic
  invariant `r + a = w`. In `f64`, `a - b` and `r + b` each round, so the
  sum can drift. A model of `GA:843-984` over 20,000 random graphs with
  fractional capacities found no reverse residual above its capacity, so
  this is unproven rather than shown false. The RFC should say it rests on
  the drift staying below half an ulp of `f64::MAX`, or argue it.
- **That no program defines a word named like one of the 24.** Nothing in
  `tests/` or `reference/Bund` does (`grep`), and the RFC does not say what
  a user definition of `graph.bfs` would meet.
- **That the overflow node is the first in node order** (finding 4).
