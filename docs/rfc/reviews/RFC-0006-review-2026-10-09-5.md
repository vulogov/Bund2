## Blocking

**B1 — What counts as a response is decided twice, and the RFC says the two
deciders part on two shapes. They part on a quarter of the shapes tried, in
three directions, and D129 approves one.**

§B7: "**Which bytes are a response is `ureq`'s to decide and not
libcurl's**, and for two shapes they decide differently — D129". The table
of parts: "the response | nobody | **all of it is `ureq`'s** (D129)". The
bullet: "**Two responses the reference evaluates fail the fetch**". And the
sentence the section rests on: "In no row does Bund2 ask a listener the
reference does not ask, and in none do the two evaluate different text."

D129's ruling is "Bund2 fails a fetch whose response `ureq` will not
parse", and its reason is in its last line: "Bund2 has asked the listener
the reference asks, and evaluates nothing." That is one direction.

Measured 2026-10-09, directly, no proxy. The origin answers
`"http://127.0.0.1:<port>/<n>" use` with the bytes described; the body is
`"A" println`. Eighty shapes; 60 agree. The 20:

| the response | oracle | Bund2 |
|---|---|---|
| **a `302` with a `Location`, a body and no `Content-Length`** | evaluates the body | **evaluates the empty string; no report** |
| a `101` with a body | evaluates the body | **evaluates the empty string** |
| `Transfer-Encoding: gzip, chunked` over a body that is not gzip | **fetches the chunk framing as text** — `c`, the body, `0` — and fails on `c` | **fetches the body, and evaluates it** |
| `Transfer-Encoding: chunked` given twice | fails | **evaluates the body** |
| a chunk size written `+c` | fails | **evaluates the body** |
| a chunk size with a blank before it | fails | **evaluates the body** |
| an empty line before the status line | fails | **evaluates the body** |
| `Content-Length: +12` | evaluates the body | fails |
| `Content-Length: 12abc` | evaluates the body | fails |
| `Content-Length` past 64 bits | evaluates the body | fails |
| two `Content-Length` lines that differ, 12 and 24 | evaluates 24 bytes | fails |
| `Content-Length: 0x0c` | evaluates the empty string | fails |
| a folded header line | evaluates the body | fails |
| a header whose name holds a blank, or is empty | evaluates the body | fails |
| a bare carriage return in a header's value | evaluates the body | fails |
| one header of 100,000 bytes | evaluates the body | fails |
| a status line that begins `http/1.1` | evaluates the body | fails |
| chunks ended by line feeds alone | evaluates the body | fails |
| a status line and nothing after it | evaluates the empty string | fails |

(Nineteen lines for twenty shapes: the header with a blank in its name and
the one with no name are two.) Twelve of the twenty were run again with
`"[" print "<url>" url print "]" println`, so the text each binary fetched
is on the page: for the redirect the oracle prints `["A" println` and Bund2
prints `[]`.

**Three directions.**

- **Thirteen: Bund2 fails where the reference evaluates** — the last
  thirteen. D129's
  direction, and D129's words reach them: "a fetch whose response `ureq`
  will not parse". The RFC's "two" is short by eleven, as D127's four were
  short at the fourteenth review. Should-fix by themselves.
- **Four: Bund2 evaluates where the reference's fetch fails** — the fourth
  to the seventh line. Bund2 asks the listener the reference asks and then
  runs what the reference will not read. No entry approves it. D127 calls the same
  thing a defect for a URL — "Bund2 fetching where the reference refuses" —
  and D129 opens by saying D127's rule does not reach a response.
- **Three: both fetch, and the text differs** — the first three lines. For
  the redirect and the `101` Bund2's text is empty, so `use` evaluates
  nothing and the program goes on as though a library had loaded. For
  `gzip, chunked` it is the reference whose text is wrong, and under `use`
  that makes a fifth case of Bund2 running a body the reference does not.

**Why it blocks.**

- The sentence "in none do the two evaluate different text" is about 443
  rows and is true of them. Eight rows of the 443 vary the response, and
  six are a header count. It was written of 278 rows once before, was
  true of them, and the RFC's own next sentence says what happened.
- The redirect is not exotic. `use` follows no redirect on either binary,
  so the body of a `301` or `302` is what each evaluates, and a server that
  closes the connection instead of sending a length is an ordinary one.
  The reference then fails loudly on a page of HTML. Bund2 succeeds
  silently on nothing. Only `302` was tried.
- The middle direction is the one every fetch ruling since D124 has kept
  shut: where the two differ, Bund2 fails. Here it does not, and nothing
  says so.
- The RFC's table of parts lists the response as read by "nobody". It is
  the one row of that table with no measurement behind its cell.

**What it needs.** A ruling, and I do not think it is mine to predict.
Refusing in Bund2 what libcurl refuses means reading the head and the
framing before `ureq` does, or instead of it; approving the difference means
a deviation that is not fail-closed, which would be the fetch's second, after
D125. Either way: the shapes in the measurement, where today 8 of 443 rows
have a response that is not the plain one; D129's "two" corrected; and the
sentence about different text either true of the fetch or said of the rows
alone, as the preservation row already says it.

Why `ureq` returns no body for a redirect it was told not to follow was not
traced.

## Should fix

**S1 — A `no_proxy` entry of 128 bytes or more matches nothing in the
reference when the host is an IPv4 address, and matches in Bund2. The two
then ask different listeners.**

| `no_proxy`, host `127.0.0.1`, `http_proxy` set | oracle | Bund2 |
|---|---|---|
| `127.0.0.0/` then 116 zeros and `8` — 127 bytes (control) | direct | direct |
| the same with 117 zeros — 128 bytes | **through the proxy** | **direct** |
| `127.0.0.1/` and 117 `x` — 127 bytes (control) | direct | direct |
| `127.0.0.1/` and 118 `x` — 128 bytes | through the proxy | direct |
| 119 zeros and `127.0.0.1` — 128 bytes | through the proxy | direct |
| a name of 200 bytes, then `,127.0.0.1` (control) | direct | direct |

§B7's row says an entry may carry "any count of zeros" on macOS and that the
bits are "what C's `atoi` reads". Both hold up to 127 bytes. The limit is on
the entry and not the list, and only for a host that is an address; I did
not read libcurl for the reason. The second and fourth rows need no leading
zero, so by reasoning they differ on Linux too, and that was not run.

By D127's words this is a defect "whenever it is found": a different
listener, and Bund2 the one that goes direct. I am not holding the RFC on
it. The fourteenth review said of `/+33` that it would not hold the RFC for
that alone, and nobody writes this entry by accident. It is one comparison
in `bypasses`, a row, and half a sentence.

**S2 — A proxy written with one slash or three is used by the reference and
fails the fetch in Bund2.** `Target::of` takes one to three slashes after
`http:` in a URL, as measured. `proxy_for` splits a proxy at `://` and
nothing else.

| `http_proxy` | oracle | Bund2 |
|---|---|---|
| `http:/127.0.0.1:<p>` | through it | fails; asks nobody |
| `http:///127.0.0.1:<p>` | through it | fails; asks nobody |
| `127.0.0.1:<p>/a://b` | through it | fails; asks nobody |
| `HTTP://127.0.0.1:<p>` (control) | through it | through it |
| `http:127.0.0.1:<p>`, `//127.0.0.1:<p>`, a blank or a line feed at either end (control) | fails | fails |

Each fails closed and D127's rule covers it; they are three more for its
list. The third is `proxy_for` taking a path for a scheme. The first two are
Bund2's two readers disagreeing with each other about one rule, which is
closable where the other was closed.

- D127's bullet, "refused where the reference fetches", lists `[00000::1]`

**S4 — D130 keys on the operating system, and what was measured is two

## What the RFC assumes and does not state

1. **Two clients that send the same request read the same answer.** B1.
   Every row of the parts table but the last is about what is sent.
2. **A response `ureq` accepts is one libcurl accepts.** B1. D129 assumed
   the differences run one way.
3. **A fetch that succeeds fetched something.** B1. An empty body and a
   body `ureq` did not read are the same string to `use`.
4. **A `no_proxy` entry has no length.** S1.
5. **A proxy's scheme ends in exactly two slashes.** S2. A URL's does not,
   three functions away.
6. **The operating system names the C library, and the C library is what
   decides.** S4.
7. **The table at `17e623a` describes `cd10669`.** True: the commit between
   changes no code. Nothing but a reader checks that for the next one, and
   the macOS table is not re-run by the workflow at all.
8. Carried from the fourteenth review and unchanged: a proxy variable that
   is not UTF-8 is unset; both fail, so both did the same thing.
9. Carried from the eleventh to thirteenth reviews and unchanged: the
   sentinel cannot occur in what a build writes; no golden fails to parse;
   `--inspect` reports what a header says and not what the runtime does;
   the executable on disk is the one running when `build` copies it.
10. Carried, and stated in the RFC: the compiler does not fold reads of the
    region; the in-place write works on ELF and PE; `/usr/bin/codesign` is
    present and real; a refusal is text and not an exit status.
