## 1. Blocking

### B1 — compiled code never sees `bund.exit` (D52)

**What D52 decides.** `bund.exit` calls `Vm::request_exit(code)`. "The
interpreter stops at the next word boundary and runs nothing more of the
program" (`docs/registers/decisions.md`, D52 — decided 2026-09-11, the day of
the RFC's last revision). The `Vm` trait carries it
(`crates/bund2-api/src/lib.rs`, `request_exit` and `exit_requested`).

**How Tier 0 honours it.** `bund_exit` records the code and returns `Ok`
(`crates/bund2-stdlib/src/host.rs`, `bund_exit`). Nothing ends at that moment.
The stop is `Interp::exit_gate`, which fails once a code is recorded
(`crates/bund2-interp/src/lib.rs`, `exit_gate`). It is called in two places
only:
- at the top of `Interp::apply_step`, so every value the frame loop,
  `Vm::apply` or the drain steps through is refused;
- at the top of `Vm::eval_lambda`, so no native starts a new body.

`eval_observed` then treats the refusal as the end of the program rather than
as an error. **`Interp::invoke` and `Interp::dispatch` do not check it.** A
native reached other than through `apply_step` still runs after an exit.

**What compiled code reads.** After every call it loads three cells: the
epoch, `autoadd` and the request cell (§S5, lines 714–717; §S6, *Addressing*,
lines 1146–1165). None records an exit. §S8's adapter "calls the native's
`NativeFn` through `bund2_api::catch_panic`" and turns its `Result` into the
status (lines 1546–1550). `bund_exit` returns `Ok`, so the status is success.
Literal pushes and inlined fragments never pass `apply_step`. The spike that
measured criterion 10 reads the same three cells (its commit message,
`3138d3c`), so the lowering that exists already has the gap.

**A golden that moves.** `tests/probes/bund-exit.bund`:

    :f { "inside, before exit" println 3 exit "inside, after exit" println } register
    "before the call" println
    f
    "after the call" println

Its golden (`tests/golden/probes/bund-exit.golden`) records exit **3**, and
output that ends at `inside, before exit`. Bund2 matches it today; I ran it
with exit 3. Under `cargo xtask conform --features jit --jit-threshold 1`,
`f`'s body compiles on its first entry. `exit` is an alias, so the call goes
through the resolving trampoline to `dispatch`, which calls `bund_exit` without
a gate. Control returns `Ok`, and the three cells are unchanged. The compiled
body pushes `"inside, after exit"` and calls `println` through its slot. The
adapter runs it. The line is printed, and the golden fails. Criterion 2 then
moves, which CLAUDE.md calls a bug by definition.

The same holds for a `bund.eval` or `use` whose source calls `bund.exit`.
`eval_source` applies each word through `Vm::apply`
(`crates/bund2-stdlib/src/singles.rs`, `eval_source`). It is refused after the
exit, returns an error, and compiled code takes its error path. So that case is
covered. What is not covered is a direct call.

**Required:**
- Add **D52** to *Decisions consumed*.
- **Specify how compiled code stops.** The smallest rule, with no new cell:
  - the per-native adapter checks `exit_requested()` after the native
    returns, and on `Some` parks `exit_gate`'s error and returns the error
    status;
  - the resolving trampoline does the same after `dispatch`;
  - the entry trampoline refuses to start a body once an exit is recorded, as
    `eval_lambda` does before its cache lookup;
  - the frame loop's compiled entry sits behind `apply_step`'s gate, or checks
    the gate itself.

  Compiled code's existing error path then syncs every promoted value and
  returns (§S5, *What a promoted value must not change*). The status reaches
  the entry in tail position too, because it travels with the return.
  An alternative is an **exit cell** read after every call. That is a fourth
  load under criterion 17. In tail position the entry has to read it instead
  of the body.
- **Add a criterion.** Run `tests/probes/bund-exit.bund` and
  `tests/probes/bund-exit-word.bund` under criterion 2's three
  configurations. Also compile, with promotion on, a body that calls
  `bund.exit` directly, through the alias `exit`, and in tail position, each
  followed by a call and by an inlined `+`. The output, exit code and final
  stacks must match Tier 0's.
- Add a Preservation row, and an assumption: *every way a program stops is
  visible to compiled code at the call that caused it.*
- Consider having `Interp::effect_audit` record a `request_exit` made while a
  fixed-effect native runs, as it records a tail request. Only `bund.exit`
  makes one, and it is opaque. The audit would make that a property rather
  than an observation.

## 2. Significant

### S1 — §S8's list of re-entering paths is enumerated, and already short

§S8 defines the margin over "every way a native re-enters evaluation" and then
lists them (lines 1813–1817). Criterion 11 reports `c_p` and `δ_p` "for each
path §S8 lists" (lines 2468–2470). The following natives landed on 2026-09-11,
and the list names none of them:

- **through `Vm::eval_lambda`:**
  - `for` and `for.` (`crates/bund2-stdlib/src/control.rs`, `for_base`);
  - `*loop` and `*loop.` (`crates/bund2-stdlib/src/seq.rs`, `loop_over_base`);
  - `input` and `input*` (`crates/bund2-stdlib/src/terminal.rs`,
    `input_loop`).
- **through `Vm::apply`, one call per token:** `bund.eval`, `bund.eval.`, `!!`,
  `use` and `use.`, all through `eval_source`. This is a Rust frame, a
  `bund2_syntax::compile` and a loop, per level. Its `c_p` is not
  `Vm::apply`'s alone.

Recursing through `bund.eval` does stop at the floor.
`:f { "f" bund.eval } register f` reports and exits 0. But the report names
the wrong cause: "machine stack exhausted: recursion through a word that runs
a lambda — `times`, `loop`, `map`, `while`, a conditional, `?try` or a method".
§S8 says the error "names the cause" (lines 1890–1893).

**Required:**
- Define the path set so that it cannot go stale. One way is every native that
  enters `eval_lambda`, `apply` or `scoped_call`, collected mechanically. The
  corpus audit and the palette already see those entries through `entry_log`.
- Name `eval_source` as a path of its own for `c_p`.
- Correct the Tier 0 message, or narrow §S8's claim about it. That is a D36
  presentation matter, not meaning.

### S2 — sentences that survived the tenth review's fixes

Each of these contradicts the RFC's current design. A reader who builds from
one of them builds the withdrawn design.

1. **§S6, lines 970–971:** "a compiled word's signature is uniform,
   `fn(&mut dyn Vm)`". §S8 (lines 1523–1545) now says the `NativeFn` shape is
   *not* a boundary compiled code can use. The signature is
   `fn(ctx: i64) -> i32` under `CallConv::Tail`.
2. **§S8, lines 1661–1662:** `Function::stack_limit` "takes its limit only from
   a `VMContext` parameter, which Bund2's uniform `fn(&mut dyn Vm)` does not
   carry". The JIT signature's context pointer could be declared with
   `ArgumentPurpose::VMContext` (`src/machinst/abi.rs`, `generate_gv`). The
   trap argument still rules `stack_limit` out, so the conclusion stands, but
   the second reason no longer holds.
3. **Preservation row, line 2053:** "an `opaque` effect (D12; **none is
   registered today**)". §S6 (lines 1400–1405) says the ten fold words are now
   registered and opaque. Today's corpus has a first stop at `*+`.
4. **Preservation row, line 2080:** "`m ≥ 8 MiB × δ / c`". §S8 (lines
   1818–1819) and row 2087 say `max_p(δ_p / c_p)`.
5. **§S5, lines 731–736:** "Four kinds of call file a request". `if.stack`
   files one too, when its name is the current stack's
   (`crates/bund2-stdlib/src/control.rs`, `if_stack`). The design reads the
   request cell after every call, so it is covered. But the sentence reads as
   complete, and criterion 26 draws its cases from it. (`if.stack` declares
   `opaque(2)`, so it is honest, and it is not in `PROMOTABLE.txt`.)

**Required:** correct all five.

### S4 — smaller items

- **The palette does not run every fixed-effect native.** Criterion 28 (lines
  2756–2766) says it "runs every fixed-effect native". Six are left out:
  `fs.rm`, `sleep.seconds`, `system.setproctitle`, `system.setproctitle.`,
  `password` and `save.model` (`crates/bund2-stdlib/src/lib.rs`,
  `ACTS_ON_HOST`). That is the conservative side, since a native left unrun is
  not listed and not crossed. But the criterion should say so. D48's dated
  note names four of the six. Because the list is kept by hand, the next
  native that acts on the host runs for real under `cargo test` until someone
  adds it. Running the palette in a scratch working directory, or making the
  list opt-in, would close that.
- **`PROMOTABLE.txt` names natives; the options decide what is registered
  under a name.** `register_all_with` registers `--noio` stubs under the same
  names (`crates/bund2-stdlib/src/host.rs`, `stub!`), and `--noeval` replaces
  `bund.eval` and `use` (`register_noeval_stubs`). Every stub fails, so crossing
  one is harmless today. The RFC should state that the list certifies the
  default registration. It should also say that D47's id set comes from the
  registration actually made, or that promotion is off under non-default
  options.
- **Q22.** `docs/registers/open-questions.md` now asks that the cache question
  be cited as "Q22 (cache)", naming this RFC's line 1417. §S7's heading still
  says "Q22".
- **Criterion 10's spike** omits the exit check along with the items it
  already lists (lines 2412–2416). The cost is negligible, but it belongs in
  that list.

## 5. Preservation analysis — what the table does not enumerate

1. **A program that asks to exit mid-body (D52).** Tier 0 runs nothing more.
