## 1. Blocking

### B1 — S1 flattens at registration; S7 and the reference resolve parents at construction

S1:

> Registration additionally computes a **flattened method table** for the
> class: every slot reachable through `.super`, resolved once …

S7, twelve paragraphs later:

> The registry is still consulted for **parents**: `.super` holds parent class
> *names* and construction walks them
> (`reference/rust_multistackvm/src/stdlib/bund_object.rs:44-48`), so a class
> whose parents are unregistered still fails, on the parents.

Both cannot hold. If parents resolve at construction, a class's inherited
slots are not knowable at registration, and there is nothing to flatten.

The reference is unambiguous on which one is the language.
`register_class` validates the CLASS tag and inserts, and does nothing else:

```
reference/rust_multistackvm/src/multistackvm_classes.rs:7-20
    pub fn register_class(&mut self, name: String, bclass: Value) -> Result<&mut VM, Error> {
        if ! bclass.is_type(CLASS) {
            bail!("register: argument #1 is not a CLASS");
        }
        match self.unregister_class(name.clone()) {
            Ok(_) => {
                self.classes.insert(name, bclass);
            }
```

Parents are looked up only inside `make_bund_object`:

```
reference/rust_multistackvm/src/stdlib/bund_object.rs:44-48
                    Ok(class_name) => {
                        if vm.is_class(class_name.clone()) {
                            let parent_value = match vm.get_class(class_name.clone()) {
```

So `:B class ".super" [ :A ] set register` succeeds whether or not `A` exists,
and fails only at `:B object`. Forward references are legal today. Flattening
at registration turns that into an ordering constraint the language does not
have — a narrowing, and one no criterion covers.

This is the first pass's gap 1. It was not addressed, and S7 has made it worse
by stating the construction-time half as settled fact in the same document.

Three ways out, and the RFC has to pick one: re-flatten a class when a parent
later registers (which needs an invalidation edge S5's two generations do not
supply — a *parent's* registration must invalidate the *child's* table);
flatten lazily on first construction, which is where the reference resolves
anyway and costs nothing extra; or accept the narrowing, in which case it is a
deviation and needs a Preservation row and a criterion.

### B2 — a Preservation row says PTR method slots are pushed, which is the opposite of what dispatch does

The table carries:

> | A `LAMBDA` in a method slot is evaluated; anything else is pushed | preserved exactly |

"Anything else" includes `PTR`, and a PTR is not pushed. It is cast to a name,
looked up in `methods_fun`, and **called**:

```
reference/rust_multistackvm/src/multistackvm_object.rs:57-76
        match method_value.type_of() {
            PTR => {
                match method_value.cast_string() {
                    Ok(method_name) => {
                        if self.is_method(method_name.clone()) {
                            match self.get_method(method_name.clone()) {
                                Ok(fun) => {
                                    return fun(self);
```

The RFC's own §4 step 4 gets this right — "The located slot is a `PTR` → look
up `methods_fun` and call it; a `LAMBDA` → `lambda_eval` (`:77-78`); anything
else → push it (`:80-82`)" — so the document contradicts itself, and the row
contradicts the mechanism the whole RFC is built on: §1's table says a method
slot holds "a **PTR** naming a method", and §2 says "a method is reachable only
through a class slot".

`cargo xtask lint` passed over 29 rows without seeing this, which is expected —
it cross-checks rows against *dispositions*, not against the body.

The row should read: a `PTR` resolves through `methods_fun` and is called, a
`LAMBDA` is evaluated, anything else is pushed — three arms, because the
flattened table's contents depend on which of them S1 stores (see §6.2).

### B3 — §3 step 1 and the new `set` row disagree about where an instance's identity comes from

The Preservation table's newest row:

> | `set` on a map returns a **new** value: fresh id, fresh stamp, `q` reset,
> `attr` and `tags` dropped | preserved exactly — **so construction's identity
> comes from the `.class_name` write, not from `dup`** …

§3 step 1, unchanged:

> `dup`s the class … **So every instance gets its own identity** … F13's
> fresh-identity `dup` is exactly right here …

The row is correct and step 1 is not. `set`'s map arm — which covers `CLASS`
and `OBJECT` explicitly — returns a value built by `from_dict`, restoring only
`dt`:

```
reference/rust_dynamic/src/set.rs:14-23
            MAP | INFO | CONFIG | ASSOCIATION | CURRY | MESSAGE | CONDITIONAL | CLASS | OBJECT => {
                let mut res = self.dup().unwrap();
                res.id = nanoid!();
                match &res.data {
                    Val::Map(v) => {
                        let mut m = v.clone();
                        m.insert(key.as_ref().to_string().trim().to_string(), value);
                        let mut raw_value = Value::from_dict(m);
                        raw_value.dt = self.dt;
                        return raw_value;
```

and `from_dict` mints everything fresh:

```
reference/rust_dynamic/src/create_map.rs:31-42
    pub fn from_dict(value: HashMap<String, Value>) -> Self {
        Self {
            id:   nanoid!(),
            stamp:  timestamp_ms(),
            dt:   MAP,
            q:    100.0,
            data: Val::Map(value),
            attr: Vec::new(),
```

The `res.id = nanoid!()` at `set.rs:16` is dead on this path. `dup`'s identity
is overwritten one line after `bund_object.rs:35` by the `.class_name` write at
`:36`, and again by the `.super` write at `:105`. The conclusion the RFC draws
(distinct ids per instance) is right; the mechanism it names is not, and it is
named in the section a reader would trust for it.

**And the row has no citation.** `set.rs` and `create_map.rs` appear nowhere in
the document. This is the RFC's most consequential new row — it is what makes
`.timestamp`, `q` and `attr`/`tags` answerable at all — and it is the one row
`cite` cannot check, because there is nothing there to check.

### B4 — criterion 1's measurement does not work with the tool it names, and the numbers still do not reproduce

The criterion, which explicitly presents itself as the fix for an earlier
unmeasurable wording:

> the criterion is: after this RFC lands, no golden in that set may fail with
> `class not registered` or `object not registered`. Measured by `cargo xtask
> conform -v` and grepping its failure list — which is checkable, unlike the
> earlier wording.

`conform -v` exists (`xtask/src/conform/mod.rs:97`) and widens the listing, but
the per-golden detail it prints is `o.detail` (`:338`), and `o.detail` is
`output differs (N lines vs M)`. Bund2's error text never enters that list.
Grepping it for `class not registered` returns nothing today and would return
nothing after the RFC lands, so the criterion passes vacuously in both
directions. Confirmed by running it.

The split does not reproduce either. Running `bund2 script --file` on each of
the 14 goldens plus the probe and reading the reported reason:

| stops on | goldens |
|---|---|
| `class not registered` (10) | class_display_demo, class_display_demo_2, class_hierarhy_call_method, class_hierarhy_get_values, create_class_demo, create_class_hierarhy_demo, create_object, object_call_method, object_get_value, probes/execute-arm-class |
| `object not registered` (5) | class_constructors_demo, is_demo, object_execute, value_demo, wrap_unwrap_demo |

**10 / 5, not 11 / 4.** The first pass measured 10/5 by first textual
occurrence and the RFC did not move; measuring by what Bund2 actually reports
gives the same answer, so the two measures agree and the RFC disagrees with
both. (Note `class_constructors_demo`, whose first textual `object` is at line
2 but which is nonetheless an `object` stop — the two measures happen to
coincide here, but they are not the same measure and the RFC should say which
it means.)

What would make it checkable: have `conform` carry the failing program's
reason string in `o.detail`, or state the criterion against a direct run of
`bund2` and record the command. Either is work, and RFC-0003's
acceptance-criteria preamble requires saying so.

## 3. Claims that need a citation and lack one

1. **The document contains no `crates/` citation at all.** Verified by grep:
   zero. Three claims about Bund2's own code ride on nothing —
   - S4's `BundValue::id_string` and `BundValue::timestamp` (they exist:
     `crates/bund2-value/src/lib.rs:1176` and `:1152`),
   - S5's "The cache keys on the class's **`Rc` pointer**, as D35 does" (D35
     resolved on option 4, keying on the *payload* `Rc`, `lib.rs:480`), and
   - §3 step 1's "step 2 writes to the copy immediately, so no payload is ever
     shared with the class."

   The last still reads against D35, whose resolution is precisely that a
   `dup`'d value **shares** its payload and that the sharing is what makes the
   cache hit. If construction unshares immediately, that is a cost, and the
   sentence offers it as reassurance. It is also now redundant with B3: `set`
   rebuilds the map wholesale, so nothing is shared for a different and
   better-evidenced reason.

2. **"`.id` returns a 21-character string"** — Preservation row and criterion
   4. Still uncited, as at the first pass. It follows from `id: nanoid!()`
   (`reference/rust_dynamic/src/value.rs:35`) and `nanoid = "0.4.*"`
   (`reference/rust_dynamic/Cargo.toml:19`), whose default alphabet yields 21.
   Criterion 4 turns the number into a test, so cite both.

3. **Four "confirmed against the oracle" claims with nothing recorded.** §1's
   "a class with `".super" [ :Object ]` answers `.id`"; §3's "two objects of
   one class return different ids"; S6's "`:.id :A object !` returns the
   instance's id"; S6's "`# NO LAMBDA or PTR IN #1`". The last I confirmed by
   reading (`object_execute.rs:19`); the other three are behavioural and
   `tests/probes/` has gained nothing since the first pass — still twelve
   probes, none of them OOP beyond `execute-arm-class`. Criterion 4 invokes D21
   for exactly this shape of claim. These belong under it, and until they are
   there the RFC asserts oracle results no later reader can re-run.

4. **`Display` is the root of the base chain.** §1 asserts it. Its evidence is
   that `Display`'s `.super` is built and never pushed to
   (`display_class.rs:100-102`), and that it is registered in
   `display_class.rs:105` — a different file from the `:95,109` the RFC cites,
   which establish only the two edges.

5. **The `set` Preservation row** — see B3. No citation.

## 4. What the Preservation analysis still does not enumerate

Eighteen rows now, up from fourteen, and P1/P2/P3 from the first pass are
covered. These remain, all verified in this session, all inside the ~280 lines
the RFC says it reimplements.

**P4 — `#` swallows errors.** Both applies are discarded:

```
reference/Bund/src/stdlib/functions/oop/object_execute.rs:35-39
    vm.stack.push(obj_val.clone());
    let _ = vm.apply(Value::call("unwrap".to_string(), Vec::new()));
    vm.stack.push(lambda_val.clone());
    let _ = vm.apply(Value::call("!".to_string(), Vec::new()));
    Ok(vm)
```

A failing `unwrap`, or a failing `!` on whatever `unwrap` produced, yields no
diagnostic and `#` returns `Ok`. Under D36 — errors are reported, not
swallowed — this is a decision the RFC must take, not an omission. S6 describes
`#` in full and does not mention it. **Raised at the first pass; unaddressed.**

**P5 — `#.` is counted and never specified.** §6 lists it among the ten words
and the table has a row for `#` alone. It differs in two observable ways: its
depth guard is **1** where `#`'s is **2** (`object_execute.rs:47` vs `:43`),
and it takes the *object* from the workbench while the lambda still comes from
the main stack (`:23-26`). That is exactly RFC-0003 §S4b's receiver convention
and D18's workbench-form rule, and saying so would cost one sentence.
**Unaddressed.**

**P6 — `make_bund_object` on an OBJECT is the identity** (`bund_object.rs:108-110`).
Constructing from an already-constructed value returns it unchanged. No row.
**Unaddressed.**

**P7 — the error texts.** Still one row, for the non-OBJECT receiver. Also in
scope and unrowed: `VM stack is empty` (`multistackvm_object.rs:48`), `VM no
method {} has been registered` (`:53`), `m({}) returned: {}` (`:67`), `VM
Method {} not registered` (`:71`), `VM method name casting error: {}` (`:74`),
`Stack is too shallow for inline EXECUTE.OBJECT` (`execute_object.rs:9`),
`Stack is too shallow for inline object()` (`bund_object.rs:117`), `OBJECT
returns: NO DATA` (`:185`), the `#`/`#.` family (`object_execute.rs:19,21,31,33`),
and the `UNWRAP`/`WRAP`/`IS` family (`value_class.rs:85-144`).

**P8 — `value_locate` is a second public entry point.**
`multistackvm_object.rs:29-42` runs the identical search and returns the value
without dispatching; `rust_multistackvm/tests/vm-test-class.rs` exercises it.
It is the same search S1 replaces and it carries its own error texts. §4
documents `m` only. **Unaddressed.**

**P9 — registration is last-write-wins, in both registries.** `register_method`
unregisters then inserts (`multistackvm_methods.rs:6-13`); `register_class`
does the same (`multistackvm_classes.rs:11-18`). Criterion 5 asks only that two
`Interp`s hold different methods; neither re-registration order is pinned, and
S5's two generation counters are bumped by exactly these two functions.
**Unaddressed.**

New, and not in the first pass:

**P10 — an unregistered PTR `.init` is silently skipped.** Both construction
sites guard with a bare `if` and no `else`:

```
reference/rust_multistackvm/src/stdlib/bund_object.rs:63
                                            if vm.is_method(init_method_name.clone()) {
```

(and `:143` at the top level). A class naming a constructor that was never
registered constructs successfully with no `.init` run and no diagnostic. Under
D36 this is the same decision as P4. The parallel case — an `.init` that is
neither PTR nor LAMBDA — produces a `log::debug!` and nothing (`:81`, `:161`).
The RFC's new PTR row says "both arms exist and the PTR one is the common
case"; there are three arms, and the third is silent.

**P11 — `.init` can replace the object at the *parent* level too.** The new row
covers `if_object_of_class_in_stack` but §3 mentions only the top-level half
(`:163-174`). The same dance runs for every ancestor and decides what goes into
`.super`:

```
reference/rust_multistackvm/src/stdlib/bund_object.rs:83-94
                                    if if_object_of_class_in_stack(vm, class_name.clone()) {
                                        match vm.stack.pull() {
                                            Some(parent_object_in_stack) => {
                                                super_list = super_list.push(parent_object_in_stack);
```

So a parent's constructor can substitute a *different* parent object into the
instance's `.super` — which is precisely the tree S1's flattened table claims
to have precomputed, and precisely why `.class_name` is load-bearing (D25 says
so). It is arguably a second divergence source alongside `set_value_in_object`,
and S1a accounts for only the first.

**P12 — an object's `.id` is not stable across mutation.** The new `set` row
records the mechanism and stops. Every `set` mints a fresh id, so `wrap`
changes an object's `.id`, and D1's equality-is-id-comparison consequence
follows. Whether Bund2 preserves that is a language question and it is unasked.

**P13 — `locate_value_in_object` exists twice, byte for byte.** The private
copy at `multistackvm_object.rs:6-25` and the public one at
`value_class.rs:10-29` in a different crate. S1 cites the export without a line
and never notes the duplication; criterion 2 names "the search implementation"
in the singular as its oracle. Which one, and does the RFC keep both?
**Raised at the first pass; unaddressed.**

## 5. Registers not consulted

CLAUDE.md's rule is to grep the registers for the RFC's *words and files*. Four
things that search returns and the RFC does not carry:

1. **F67 — "a missing parent class is reported under the child's name"**
   (`docs/registers/defects.md:1940`). It was filed as a result of the first
   review *of this RFC*, and it lives at `bund_object.rs:99`, inside the
   function S3 reimplements as a frame loop. The RFC does not name it and
   carries no disposition for it. A defect in the reimplemented path needs a
   Preservation row either way — reproduce the wrong name, or fix it and say
   which golden moves.

2. **F11 — "inverted guard in `register_method_value_init`"**
   (`defects.md:74`), at `value_class.rs:59`, which is the `Value` class's
   `.init` — this RFC's construction path, reached by every built-in class
   through `.super`. **F11's `Disposition:` line is empty.** Under CLAUDE.md an
   RFC may not adopt an undispositioned defect silently; this one should either
   be dispositioned or named as blocking.

3. **D32 — `q` propagation is preserved.** The new `set` row records that `q`
   is reset to `100.0` at construction and never names D32, which is the
   decision that makes `q` load-bearing rather than vestigial. Two `set`s run
   per construction (`bund_object.rs:36`, `:105`), so an object's `q` is
   unconditionally 100.0 regardless of the class's.

4. **`set` calls `self.dup().unwrap()`** (`set.rs:15`, and `:42`, `:75`). A
   `dup` failure inside `set` aborts the interpreter, on the construction path,
   twice per object. Not a Bund2 concern directly — but it is exactly the
   failure mode CLAUDE.md's no-panic rule exists for, it is not in the defects
   register (grep finds nothing), and it was raised at the first pass.

| 6 | **fails as written** | `cite` and `lint` are clean today, verified — 0 defects, 4 benign advisories on this document, no contradictions. But the criterion also requires "the load-bearing citations quoted as fenced blocks so `cite` verifies their content", and **the RFC contains zero fenced blocks**. It also over-reads what `cite` gives: only 11 of the roughly forty line references in this document are fully qualified, so the other three quarters — including every miss in §2 — are outside the tool's reach entirely. |

**Still unchecked by any criterion:** S6's `#`-versus-`!` distinction, which the

## 7. Assumed but not stated

1. **That `.super` is acyclic.** `locate_value_in_object` recurses with no
   visited set (`multistackvm_object.rs:18-23`) and `make_bund_object` likewise
   (`bund_object.rs:42-104`), so a cyclic `.super` is unbounded recursion
   today. S1's registration-time flatten has to terminate on the same input,
   and S3's frame push converts today's stack overflow into a hang or heap
   exhaustion — which interacts directly with criterion 3's 60-second clock.
   Nothing is said. **Raised at the first pass; unaddressed.**

2. **What the flattened table stores.** "Every slot reachable through
   `.super`, resolved once" is still ambiguous between the *slot value*
   (PTR/LAMBDA/other, with `m`'s three-arm dispatch still at call time) and the
   *resolved function*. `m` dispatches on the slot's **type**
   (`multistackvm_object.rs:57-83`), so the difference is observable, and B2's
   wrong Preservation row is a symptom of the ambiguity. **Unaddressed.**

3. **How S5's inline cache interacts with S1a's divergence mark.** S1a sends a
   diverged object's lookups back to the search. S5's cache keys on the class's
   `Rc` and two registry generations — none of which move when
   `set_value_in_object` rewrites one object. As written, the inline cache
   reintroduces exactly the unsoundness S1a was added to fix, one layer up. The
   cache must consult the divergence mark before the key, and S5 does not say
   so.

4. **Which classes core registers.** §6 concludes "with no further decision
   required". D14 partitions **words**, and ten classes register without a
   word: `Object`, `Printable` (`base_classes.rs:100,115`), `Display`
   (`display_class.rs:105`), `Value` (`value_class.rs`), `Integer`, `Float`,
   `Bool`, `List`, `Floats`, `Intervals`. D14 cannot place any of them, and its
   step 3 file completion runs "in `vm/` and `stack/` only, and never in
   `bund/`" — `oop/` is `bund/oop` (`docs/core-words.md:19`), so the one
   mechanism that would have swept them in is explicitly excluded. This is not
   cosmetic: criterion 4 needs `Object` and `Printable` to answer `.id`, and
   `.str`/`.print`/`.println` need `Display`. It decides whether a core-only
   Bund2 can answer criterion 4 at all. **Raised at the first pass;
   unaddressed.**

5. **That method names key on the raw string**, with no normalisation of the
   leading dot. §1 establishes that slot and method names differ and does not
   say what the flattened table keys on.

6. **That construction's `apply` is the ordinary `apply`.** §3 step 6 says
   "`apply`s" without saying what that does to an OBJECT — it falls to the
   push arm, which is the only reason the constructed object ends up on the
   stack at all. One sentence.

7. **That the three RFCs it depends on are unaccepted.** RFC-0001 and RFC-0002
   are **Proposed**, RFC-0003 is **Draft** — verified. The header's "Blocked
   on: nothing" is now correctly qualified to *decisions*, which is an
   improvement, but S3 rests on RFC-0003 §S4, S5 on RFC-0002's registry shape,
   and S4 on RFC-0001's heap header, and the header does not say that none of
   the three is accepted.

## 8. Consistency with accepted RFCs and ERRATA

- **ERRATA** — consistent. The final entry retires the "cannot shrink to 16
  bytes" supersession exactly as the Motivation describes and cites the same
  `base_classes.rs:91-92` and `:16`. No conflict.
- **RFC-0003 §S4** — consistent. §S4 names class-hierarchy depth as the third
  axis and defers it here; S3 picks it up. One small mismatch of attribution:
  §S4 says "Flattening it is RFC-0009's concern (flattened per-class vtables)"
  as the remedy for *depth*, whereas RFC-0009 uses frames for depth (S3) and
  flattening for dispatch cost (S1). Not a contradiction, but §S4's
  parenthetical now points at the wrong mechanism.
- **RFC-0003 §S4b** — consistent and well used. `execute_class` and
  `execute_object` taking `_op` unused is verified, and §5's "which RFC-0003
  §S4b confirms is the convention" is accurate.
- **RFC-0003 §S7** — consistent. The `methods_fun` row's "as RFC-0003 §S7 did
  for the conditional table" is a fair parallel.
- **RFC-0003 §S8** — S5's correction is right. §S8 keys `(Symbol, generation)`
  on the *word* table, and the property that makes it sound is that the thing
  keyed and the thing versioned are the same table. S5 no longer borrows it.
- **RFC-0003 §S3** — the analogy is still overstated. S1 says the flattening is
  a cache over the field tree "in exactly the sense RFC-0003 §S3 makes BundIR a
  cache over a lambda body". §S3's cache needs no invalidation because D5 makes
  lambda bodies write-once. The field tree is writable — which S1a, two
  paragraphs later, is entirely about. The RFC now contains both the analogy
  and its refutation. Drop "exactly", or say what the disanalogy costs.
- **RFC-0000** — §2's "fifth name-keyed table" is better than the first draft's
  (it now separates *word* tables from this one) but the ordinal still does not
  land. `VM` holds seven name-keyed maps — `inline_fun`, `command_fun`,
  `methods_fun`, `lambdas`, `classes`, `vars`, `name_mapping`
  (`multistackvm.rs:21-32`) — and S5 relies on `classes` being one of them
  while §2's list of four omits it. The substantive claim (it is not a word
  table, and RFC-0002's slot table should not absorb it) is right. Drop the
  ordinal.
- **D35** — the Rc-pointer key is now used correctly and the D20
  materialisation argument is correctly inherited. The one place the RFC still
  reads D35 against itself is §3 step 1's "no payload is ever shared" (§3.1).
- **D36** — the RFC no longer calls it "settling"; the Open questions section
  correctly ties the F66 deferral to D36's *error presentation* still moving,
  which matches F66's disposition rather than D36's status. Good.
- **D25** — the Open questions reversal on `execute-arm-class` matches D25's
  follow-on verbatim. Closed.

## 9. Summary

Four blockers, all new or newly sharpened:

- **B1** S1 flattens the method table at registration while S7 and the
  reference resolve parents at construction. The reference tolerates forward
  references (`register_class` validates only the tag); flattening at
  registration narrows the language, and the RFC contradicts itself rather
  than choosing.
- **B2** A Preservation row says a PTR method slot is pushed. PTRs are looked
  up in `methods_fun` and called — the mechanism §1, §2 and §4 are all built
  on. The row contradicts §4 step 4, and `lint` cannot see it.
- **B3** §3 step 1 attributes an instance's identity to `dup`; the new `set`
  row says, correctly, that it comes from the `.class_name` write. The row is
  right and uncited — `set.rs` and `create_map.rs` appear nowhere in the RFC.
- **B4** Criterion 1's grep finds nothing in a failure list that only ever
  prints `output differs`, and its 11/4 split measures 10/5 by both the textual
  and the runtime measure.

Beyond those: six citation ranges that miss (three of them named in the first
review and unchanged — `base_classes.rs:97-98`, `bund_object.rs:36-45`,
`bund_object.rs:162-173`), zero `crates/` citations under three claims about
Bund2's own code, zero fenced blocks under a criterion that requires them, four
oracle results still unpinned by a probe, ten preservation behaviours with no
row — of which P4 and P10 (silent failure, twice, under D36) and P11
(constructors substituting a *parent* object into the tree S1 precomputes) are
the ones that would change an answer — and four register entries the subject
search returns that the RFC does not carry, including F67, which this RFC's own
first review produced, and F11, whose disposition is empty.

What I would keep unchanged: §5 and S7, which now read F16/D23/D25 correctly
and are the best-grounded part of the document; S1a, which is the right
diagnosis even though S5 does not yet honour it; S6; §6's line accounting;
criterion 2's object quantifier; criterion 3's admission that its tool does not
exist; and the Alternatives section, which still rejects the right three things
for the right reasons.
