## B1 — assumption 35 says no wire encoder exists to recurse. One does, it is reachable from `save.model`, and it aborts at 3,400 levels

Assumption 35, as revised today to answer the eighteenth review's S2:

> Of the other walks over a value's members, **only `render` recursed on
> depth**, and assumption 36 carries it: `PartialEq` and `Hash` compare and
> hash a container by `identity()` and never descend into its members
> (`crates/bund2-value/src/lib.rs`), and **no wire encoder exists in the tree
> to recurse.**

The first two clauses are right; I opened both impls and they stop at
`identity()`. **The third is false.** `crates/bund2-value/src/wire.rs` is the
bincode encoder and decoder (D4), and it descends per level in both
directions:

- `val_of` (`crates/bund2-value/src/wire.rs:234`) maps `Payload::List`,
  `Payload::Lambda`, `Payload::Map` and `Payload::ValueMap` through
  `WireValue::from_value`, which calls `val_of` again; `Payload::Scalar` calls
  `val_of` directly;
- `WireValue::into_value` decodes `Val::List` and `Val::Lambda` through
  `decode_all`, which calls `into_value` per item, and `attr` the same way;
- `bincode`'s derived `Serialize`/`Deserialize` on `WireValue`/`Val` recurse on
  top of that.

It is reachable: `save.model` calls `wire::to_binary`
(`crates/bund2-stdlib/src/world.rs:86`), and `load.model` and the sqlite blob
path call `from_binary` (`:138`, `crates/bund2-stdlib/src/data.rs:326`).

Measured here, release binary, 2026-09-11:

    list
    3400 { drop list push } times
    "built" println
    "m" swap "/tmp/w.redb" save.model
    "saved" println

prints `built`, then `thread 'bund2' has overflowed its stack` / `fatal
runtime error: stack overflow, aborting`, exit **134**. Bisected: **3,300 exits
0, 3,400 aborts.** A control that builds the same value and prints `built`
without saving exits 0 at 30,000.

Three things make this worse than the four already filed:

1. **It is the shallowest of the class by an order of magnitude.** F114 needed
   20,000, F115 30,000, F116 16,000, F117 24,000. This one goes at 3,400 — a
   depth a program could plausibly build without meaning to.
2. **No floor is anywhere near it.** `save.model` re-enters no evaluation, so
   it appears in neither `every_reentering_function_is_named`'s set nor §S8's
   `c_p`. Assumption 4 scopes its reserve claim to a *leaf* native, and
   assumption 30 states the rule this breaks: "a new one must not recurse on
   data a program controls."
3. **Criterion 28's palette can never find it.** `save.model` is one of the six
   `ACTS_ON_HOST` natives the palette never runs (assumption 21), so the one
   mechanised audit that touches every fixed-effect native is blind here by
   design.

This needs a defect entry and a disposition, as F114–F117 got, and assumption
35's third clause has to be withdrawn. Until then the RFC asserts a property
the binary contradicts, in the sentence written to stop exactly that.

## B2 — `BundValue::display` recurses too, so `println` on a deep value aborts, and the "set of four" is not closed

The Status line:

> which closes the set of four — F114, F115, F116, F117 — that D39's dated note
> now governs.

And assumption 35 again: "**only `render` recursed on depth**".

`BundValue::display` (`crates/bund2-value/src/lib.rs:865`) is a second
renderer, distinct from `render_into`, and F117 did not touch it. Its `List`
arm calls `v.display()` per member and its `Map` arm the same (`:894`–`:923`).
Measured here, release:

    list
    28000 { drop list push } times
    "built" println
    dup println
    "printed" println

prints `built`, then overflows, exit **134**. Bisected: **27,000 exits 0,
28,000 aborts.** The same control at 30,000 without the `dup println` exits 0,
and `debug.display_stack` at 30,000 now exits 0 — so this is `display`, not the
build and not the path F117 fixed.

`println` is on every conformance path there is, and `display` is what `pull`,
`print`, `println` and the string conversions all reach. F117's own defect
entry says the four "were the same defect in four places"; there are six, and
two of them are open.

The substance of the fix is presumably the same worklist F117 already has. What
the RFC owes is the disposition and, in assumption 35, a claim that survives
being checked: the set of walks over a value's members is `render_into`,
`display`, `summarise` (bounded at `MAX_DEPTH = 2`, verified at
`crates/bund2-value/src/lib.rs:983`), `Drop`, `PartialEq`, `Hash` and the wire
codec — and two of those seven still recurse.

## Significant

### S1 — §S8 still says F116 is open, so the Status line's own correction is untrue

The Status line claims "**S1–S4**: F116's status reads FIXED in all three
places". Two of the three were fixed. §S8, line 2074, still reads:

> Two more paths outside this design recursed the same way, and §S8's floors
> reach neither: dropping a deep value (F115, since fixed the same way) and
> parsing a deep run-time string (**F116, open**), assumptions 34 and 35.

`docs/registers/defects.md` records F116 as FIXED 2026-09-11, the fix is in the
tree (`crates/bund2-syntax`, `MAX_NESTING`), and assumption 34 and the
Preservation row both say so. This is the eighteenth review's S1, re-filed: the
register is the authority, and one of the three places still disagrees with it
— now with a sentence in the Status line asserting that it does not.

### S2 — D33 was resolved during this review, and the RFC consumes it as OPEN in three places

`docs/registers/decisions.md` (working tree, uncommitted) now reads:

> - Status: **RESOLVED — ordering is exact; F47 carries the dated note.**

with "Decided by the repository owner, 2026-09-11: **option 2 — exactness
extends to ordering**", and the resolution names this RFC directly: "This also
unblocks RFC-0005: §S6 forbade lowering a mixed-kind comparison to a machine
compare while D33 stood, and said the lowering becomes available if D33
resolved this way."

The RFC still says, in three places:

- the header — "**D33** (**OPEN**; §S6 states what it withholds rather than
  taking its default)";
- §S6, *Three things bound promotion* — "**D33 is OPEN.** Ordering across int
  and float currently answers **true to all four** of `<`, `>`, `<=`, `>=` at
  once (F47)";
- the Preservation table — "mixed-kind comparison lowered to a machine compare
  | forbidden while D33 is OPEN (§S6)".

The behavioural claim in the second is now false on the binary: `2.0 1 <`
answers true and the other three false (run here, release).

Two things follow beyond the edit. First, this is CLAUDE.md's "never adopt an
OPEN decision's default silently" in its mirror image — the decision moved
under the RFC and the RFC has not noticed. Second, **"the lowering becomes
available" is optimistic and §S6 should not simply invert its sentence.**
`exact_int_float_ord` (`crates/bund2-stdlib/src/logic.rs:197`) is not a machine
compare: NaN returns `None`, ±∞ are special-cased, integers within 2^53 compare
as `f64`, and above 2^53 the comparison goes through the float's floor with a
fractional tie-break. That is a lowerable *fragment* under §S6's constraint 2,
with the generic branch still the word — not a single `fcmp`.

### S3 — the prose that reads the derived re-entry set is stale again, in three more places

The eighteenth review's S3 was that §S8's prose named `execute_reached` where
the derived set names `execute_one`. §S8 and §S5 were corrected. Three places
that say the same thing were not:

- **assumption 28**: "so `execute_value`'s arms that do Rust work before
  re-entering evaluation — CLASS, OBJECT, CONDITIONAL — are not reachable from
  a literal, and neither is its MAP arm. Its other arms are LIST, LAMBDA and
  the name arm." Every one of those arms is in `execute_one`
  (`crates/bund2-stdlib/src/values.rs:372`); `execute_value` is a one-line
  delegation to `execute_reached` (`:334`);
- **assumption 29**: "the one that did, `execute_value`, files only when the
  program executed a lambda itself". The `tail_lambda` call is
  `execute_one`'s `Reach::Top` arm (`:388`);
- **the Preservation row** for F113: "a lambda a container reaches, now run
  inside `execute_reached`". The `vm.eval_lambda(&v)` is `execute_one`'s
  `Reach::Nested` arm (`:395`).

The RFC's stated reason for deriving the set was that a list went stale within
a day. The derivation is sound; the prose around it has now gone stale twice in
two reviews, and the fix each time has been partial. A file-plus-symbol
citation that names the wrong symbol is the failure Q30 exists to prevent.

### S4 — D39's dated note governs three defects, not the four the Status line credits it with

The Status line: "which closes the set of four — F114, F115, F116, F117 — that
D39's dated note now governs."

D39's dated note of 2026-09-11 (`docs/registers/decisions.md`, read in this
session) names **F114, F115 and F116**, and its worked examples are the two
worklists and the parser bound. F117 does not appear in it. The rule it states
— "no Rust recursion may be driven by the depth of a value a program controls"
— does cover F117, and B1 and B2 above, but the register does not say so.
Registers are append-only and a dated note is how this is added; the RFC should
not describe a register entry as saying something it does not.

### S5 — `Registry::follow` is bounded at 64 links, and §S4's new rule calls it a fixed point

§S4, in the paragraph that answers the eighteenth review's B1:

> `Registry::follow` walks the chain to a fixed point

`follow` (`crates/bund2-api/src/lib.rs:1011`, opened) walks the chain with
`guard += 1` and `if guard > 64 { break; }`, returning the last link it
reached. D39's own dated note names "`follow`'s 64" beside `while`'s ten
million as one of its thresholds, and D39's `alias`-cycle warning exists
because "it would otherwise resolve to whichever link the guard stopped on".

So the answer for a chain past 64 links, or a cycle, is *not* a fixed point,
and it is part of Tier 0's meaning under criterion 2's invariant. Nothing in
§S4 breaks: a name reached through an alias points at the resolving trampoline
and runs the full chain through `dispatch`, which is the same `follow`. But
§S4's sentence is the one a lowering author will read, and it describes a
property the function does not have. Either the trampoline rule is stated as
the reason agreement holds regardless, or the bound is named where the
resolution is described.

## Minor

1. **`ValueMap` keys nested in `ValueMap` keys still recurse after F117.**
   `render_payload`'s `ValueMap` arm renders each key with `k.render(true)`,
   which starts a fresh worklist — flat for one key, but a `ValueMap` reached
   *through* a key is a new `render_into` frame per level. F117's defect entry
   says "each of those is a walk the same driver bounds", which is true per key
   and not per nesting. Unreachable today: nothing in `bund2-stdlib`
   constructs a `Payload::ValueMap`, so no word can build one. Worth a
   sentence in the entry rather than a fix.
2. **D33's decision text gives its example in the wrong operand order.** It
   says "`1 2.0 <` is true and the other three are false". Bund compares the
   second operand against the top: `1 2 <` answers false and `1 2 >` true, in
   Bund2 **and in the oracle** (both run here, `target/oracle/release/bund`).
   The program that is true is `2.0 1 <`. The substance is implemented
   correctly; only the example reads backwards. Outside this RFC's scope, but
   §S6 will cite this decision.
3. **Criterion 1's 9.47 ns and §S6's *Measured* tables remain unverifiable
   here**, since `crates/bund2-bench` is not under version control — the same
   note the last four reviews have carried. The `spike/lowering-1` figures in
   criterion 10 do check out against `3138d3c`'s commit message.
4. **The `cranelift-codegen` citations stay invisible to `cite`.** I did not
   re-open all six this time; the eighteenth review opened each and found them
   accurate, and nothing in the pin has moved.

## What the RFC assumes and does not state

- **That the wire codec does not walk a value's depth.** It does, and
  `save.model` aborts at 3,400 levels. B1.
- **That `render_into` is the only renderer.** `display` is a second one and it
  aborts at 28,000. B2.
- **That `Registry::follow` reaches a fixed point.** It stops at 64 links. S5.
- **That a native outside the re-entering set and outside the palette's reach
  is safe.** `save.model` is both — not in `REENTERING` because it evaluates
  nothing, not in the palette because it is `ACTS_ON_HOST`. Nothing in the RFC
  audits that intersection, and B1 lives in it.
- **That `bund2-jit`'s `status_of` and drain helper will call
  `Vm::clear_tail_request`.** Assumption 33 now says this, and says no scan can
  cover it. Unchanged from the eighteenth review, and fair for a design not yet
  built.
- **That the "set of four" is a set the register agrees on.** S4.

## Acceptance criteria — checkability

I re-read all thirty. Each still names a tool and either a threshold or a
boolean; the six carrying numbers (1, 7, 9, 10, 11, 17) still carry them, and
criterion 2's third command still cannot run (`--jit-threshold` is not an
argument `xtask conform` knows, re-confirmed here), which the RFC says. Two
notes:

- **Criterion 14 is where B2 lands, again.** It names `debug.display_stack` as
  the example of a word reading beyond its arity and puts it on the
  conformance path. `display_stack` is now safe at depth; `println`, which
  every golden uses, is not. The criterion is checkable as written and simply
  does not reach this.
- **Criterion 28's palette cannot reach B1.** Assumption 21 already states that
  the six `ACTS_ON_HOST` natives are never run and that this is "the
  conservative side, since an unrun native is not listed and not crossed". That
  reasoning is right for *promotion* and does not extend to D37: an unrun
  native can still abort the process. The assumption is worth one clause saying
  which property the exclusion is conservative for.

## Preservation analysis — completeness
