## Should fix

### S1. §S7's stand-for test is defined by "a scope selecting exactly its uid arguments", which the RFC never defines, and under SMYSL's default plan options it turns some of `smysl.kb`'s own facts into program facts

**Location.** §S7, "What a fact stands for", first bullet (the revision 17
text: "stands for its units when it is a fact `smysl.kb` would load from
the handle's library for a scope selecting exactly its uid arguments").
§S7's opening line: "`smysl.kb` (handle scope → kb) loads the units an
`sq/1` scope selects". §S5, "The environment".

**What the RFC says.**

- The test is a counterfactual: would `smysl.kb` load this fact for some
  scope that selects exactly the fact's uid arguments?
- `smysl.kb`'s scope is "an `sq/1` scope". §S5 names the environment
  (scope, `Env`, `PlanOptions::default()`) only for "a dossier, a measure
  and a query (§S6)", not for `smysl.kb`. No section says how
  `smysl.kb` resolves its scope text: which `PlanOptions`, `run` or
  `scope::resolve`, or what an answer that is not a scope does (a
  `count` names no units; a `ranked` answer is capped by `limit`).

**Evidence.**

- `PlanOptions::default()` sets `all_versions: false`
  (`smysl-query/src/plan.rs:161-175`).
- With `all_versions` false, `run` ends with the supersession pass. It
  replaces each superseded unit in the answer by its newest head, and
  keeps a superseded unit only if a history traversal reached it
  (`smysl-query/src/exec.rs:429-454`; the pass's doc, `:459-461`).
- So under the options §S5 gives every other scope, no plain `sq/1`
  scope selects a superseded unit. A unit's grounds are uids fixed in its
  identity (`smysl-core/src/types/unit.rs:20-22,25-58`), so `U` can still
  ground on `G` after `G` has been superseded by `G'`.

**The consequence.** Take `smysl.kb` over a scope selecting `U`, where
`U` grounds on a superseded `G` that the library holds.

- §S7's table loads `[ grounds U G ]`: "one per ground". Unlike `rel`,
  the grounds row has no "in scope" condition.
- Under the literal rule, the test asks for a scope selecting exactly
  `{U, G}`. The supersession pass replaces `G` with `G'`, so no such
  scope exists without a history traversal. The fact `smysl.kb` itself
  loaded is then a program fact, and `smysl.prove` writes it as a
  `speculative` claim.
- Under the reading the prose after it suggests ("So the units are held,
  and the fact is borne out: … a ground …"), the fact stands for `U`.
- The two readings write different units for one proof. Criterion 12
  does not tell them apart: its "fact standing for a unit" need not name
  a superseded unit. Neither do criterion 18's new `grounds` and `label`
  cases.

**A second, smaller ambiguity.** "Its uid arguments" is not tied to a
position. §S7's gist section defines a uid as "a STRING atom that
`Uid::parse` accepts" (`smysl-core/src/ids.rs:71`). A `[ gist U Text ]`
whose `Text` happens to be a canonical uid would then have two uid
arguments, and the scope test would ask for a unit named `Text`.

**Why this matters now.** Before revision 17, `smysl.kb`'s scope
semantics only decided which facts a KB holds, and criterion 11 tests
that directly. Revision 17 makes the same unstated semantics decide what
`smysl.prove` writes. That is a rule-M-adjacent output that D244 R8
governs.

**Needed.**

- State the test directly, with no scope in it. Name the uid positions:
  `U` in `unit`, `gist`, `grounds`, `deps`, `label` and `effective`; `G`
  and `D`; and `From` and `To`. Then the fact stands for its units when:
  - every uid position names a unit the library holds; and
  - `unit`: the unit's schema and declared status are those given;
  - `gist`: its gist is `Text`;
  - `grounds` / `deps`: `G` is among `U`'s grounds, or `D` among its deps;
  - `label`: the library binds `L` to `U`;
  - `effective`: `effective_status` over the library under the strict
    policy gives `U` that status, and it differs from the declared one;
  - `rel`: the library holds a relation of that kind from `From` to
    `To`, and `is_withdrawn` does not report it.
- Say that a superseded unit the library holds counts as held. The
  revision 16 rule ("whose uid arguments all name units in the handle's
  library") already read it that way.
- Separately, name `smysl.kb`'s scope environment. Presumably it is
  §S5's: `LibraryScope`, `Env` with times and entities, and
  `PlanOptions::default()`. Say what `smysl.kb` does with a `count`
  answer and with a `ranked` answer capped at `limit`. Criterion 11
  should then fix the environment it compares against.
- Add one criterion 18 case in M9: `[ grounds U G ]` from `smysl.kb`,
  with `G` superseded, writes nothing for that fact.

## Notes

- **N1. Criterion 18 tests only three of the seven shapes under the new
  rule.** (Criterion 18's `smysl.prove` bullet; M9.) It covers `rel`
  (withdrawn), `grounds` (not borne out) and `label` (borne out). There is
  no case for `unit` with a status the unit does not declare, `gist`,
  `deps`, or `effective`. `effective` is the one whose truth is not a
  property of `U`'s record. It is derived from the whole library's
  retractions, and a retraction a bridge appends while the proof runs can
  change it before the write (§S7, "judged at write time"). Add a case: a
  hand-built `[ effective U "unfounded" ]` for a unit no retraction
  touches is a program fact. Add another: `[ unit U S "cited" ]` for a
  `speculative` `U` is a program fact.
- **N2. `smysl.parse`'s `SMY-W056` is not quite "as SMYSL's `check`
  does".** (§S4, `smysl.parse`; criterion 18.)
  - `unwithdrawable` raises it only when the store holds the relation the
    withdrawal names (`if let Some(rel) = store.relation_by_id(…)`,
    `smysl-check/src/passes/integrity.rs:46-47`). In a document, a
    withdrawal by rid, or one by edge whose relation the document does not
    declare, yields a `Record::Withdrawal` carrying only a rid
    (`smysl-core/src/surface/parse.rs:2654-2679`). So its kind is
    unknowable, and `smysl.parse` cannot warn on it.
  - The store keeps withdrawals in a `BTreeSet` per rid
    (`smysl-graph/src/store/interp.rs:31-32`), so two identical
    `@withdraw` lines are one withdrawal to `check`, and two records to
    `smysl.parse`.
  - Say "one per distinct withdrawal of a `supersedes` or `retracts`
    relation the document holds". The criterion's two-agent case is
    unaffected.
- **N3. The new stand-for rule has no Preservation row of its own.** It
  is folded into "A withdrawn edge" ("… nor any fact the library does not
  bear out"), which is about edges. Revision 17's change reaches
  `unit`, `gist`, `grounds`, `deps`, `label` and `effective` facts from a
  hand-built KB. Such a fact used to stand for its units whenever its uids
  were held. Now it is written as a claim unless the library bears it
  out. Give it a row, for example "A fact a proof uses: stands for its
  units only when the library bears it out, at write time, else a
  program fact (§S7)". Keep the withdrawn-edge row to edges.
- **N4. D244 R8 carries no note for revision 17's change, although R3
  got one for a smaller one.** "Provenance by shape and library"
  (`docs/registers/decisions.md:16497`) covers revision 17's rule, as the
  answer table says, and no ruling changes. But "library" now means "the
  library bears the fact out", not "its uids are in the library", and the
  caller described this as a change made for the owner's veto. Revision
  15 recorded a dated note on R3 for a clarification of the same size
  (`docs/registers/decisions.md`, the note after R21 A). A dated note on
  R8 would keep the register the shared state CLAUDE.md asks it to be.

## Assumptions the RFC makes but does not state

1. **Any set of held units can be selected exactly by an `sq/1`
   scope** (S1). Under `PlanOptions::default()`, a superseded unit cannot
   be, without a history traversal.
2. **`smysl.kb`'s `effective` facts are computed over the whole library
   and then filtered by the scope.** §S7 points to §S5's `smysl.status`,
   which is library-wide, but does not say so. Revision 17's test, "for a
   scope selecting exactly" `{U}`, gives the intended answer only on that
   reading.
3. **`smysl.kb` resolves its scope in §S5's environment** (S1). §S5 names
   that environment only for dossiers, measures and queries.
4. **Every withdrawal in a document names a relation the document
   declares** (N2). Otherwise `smysl.parse` cannot know the edge's kind,
   and `SMY-W056` cannot be raised for it.
