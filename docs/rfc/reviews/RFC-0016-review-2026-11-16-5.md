## Should fix

### S1. Three of criterion 6's new cases cannot observe the k they assert

**Location.** Criterion 6, lines 759-769:
- "**A large exact case:** a = [1.0 2.0 … 65.0] and b = a + 0.5 … k = 1692, with the fixture's ends. It exercises the descending difference and `u128` near its limit; n = m = 66 is past it and takes the floor."
- "**The floor's documented shortfall:** a = [1.0 … 20.0], b 691 values no two equal and none equal to a's … the floor's k = 5749, where the exact k would be 5746."
- "**Low one-sided levels:** on a = [1.0 2.0 3.0], b = [1.5 2.5 3.5], "greater" at conf 0.3 answers `lower` = D₍₆₎ (k = 6, past ⌊nm/2⌋, read by symmetry)".

**Evidence (`rev6_mw.py`).** A test sees k only through D₍ₖ₎ and D₍ₙₘ₊₁₋ₖ₎. With integer-spaced data, the differences aᵢ − bⱼ = i − j − ½ repeat heavily. So neighbouring k select the same values:

| Case | k asserted | Wrong k it should catch | Ends at the asserted k | Ends at the wrong k |
|---|---|---|---|---|
| n = m = 3, conf 0.3 "greater" | 6 (symmetry read) | 5 (truncated counts, the fourth review's S2) | lower −0.5 | lower **−0.5** (D₍₄₎ = D₍₅₎ = D₍₆₎) |
| n = m = 65, 95% | 1692 (exact) | 1691 (the floor) | −7.5, 6.5 | **−7.5, 6.5** |
| n = 20, m = 691, 80%, b = 0.5, 1.5, … | 5749 (floor) | 5746 (exact) | −393.5 | **−393.5** |

At n = m = 65, every k from 1654 to 1711 (58 values) gives the same two ends. So the case:
- does catch an ascending difference (k = 1535: ends −10.5 and 9.5);
- does not catch an implementation that takes the floor at n = m = 65, or that sets the 2¹²⁸ boundary anywhere near it.

"n = m = 66 is past it" is checked by nothing. The n = 20 case leaves b to the test author. "No two equal and none equal to a's" admits b = 0.5, 1.5, …, under which floor and exact agree. The n = 2, m = 52 case (line 757) names no data at all.

The conf 0.3 data are the fourth review's own suggestion, so this is that review's error, carried into the RFC.

**Problem.** Each of these cases was added to catch a specific wrong implementation:
- the truncated read;
- a wrong branch threshold;
- the floor where exact applies.

As written, each passes that implementation.

**Suggested fix.** Choose data whose differences are all distinct, and state the expected ends (`rev6_data.py`, all checked: no pooled ties, all nm differences distinct):

- **conf 0.3:** a = [1.0 2.0 3.0], b = [1.1 2.3 3.6].
  - `lower` = D₍₆₎ = −0.10000000000000009.
  - The truncated k = 5 gives −0.2999999999999998.
  - The boundary at 0.9 on the same data still gives k = 1, with ends −2.6 and 1.9.
- **n = m = 65:** a = 1 … 65, bⱼ = 1.001·j + 0.5.
  - Exact k = 1692 gives −7.5269999999999975 and 6.461000000000006.
  - The floor's 1691 gives −7.527999999999999 and 6.462000000000003.
  - Ascending gives −10.515999999999998 and 9.450000000000003.
  - A case at n = m = 66 on the same pattern would make the boundary observable.
- **n = 20, m = 691:** a = 1 … 20, bⱼ = 1.001·j + 0.5 for j = 0 … 690.
  - The floor's 5749 gives −393.895 and −276.79499999999996.
  - The exact 5746 gives −393.89799999999997 and −276.792.
- **n = 2, m = 52:** name the data in the same way.
- **Optional:** add the exact branch's k > nm, for example n = m = 3 at one-sided conf 10⁻⁸ → E101. The only E101 case is in the normal branch, so a guard written only there passes.

### S2. Finite operands can overflow a Hodges–Lehmann difference, its median, or an interval end, and the RFC does not say what then

**Location.**
- S1, line 176: "B12 holds: no word answers NaN or ±∞ from finite operands."
- S2's Mann–Whitney bullet, lines 295-298: "the mean of D₍ₙₘ/₂₎ and D₍ₙₘ/₂₊₁₎", and [D₍ₖ₎, D₍ₙₘ₊₁₋ₖ₎].
- S2's t ends: "estimate ± t₁₋α/₂ · se".
- "Infinite ends [A3]", line 347.

E114 for a non-finite result is stated only in S6 (line 523) and for S7's weights (line 584).

**Evidence (`rev6_overflow.py`).**
- **An end.** a = [1e308 1.0 2.0 3.0] and b = [−1e308 1.5 2.5 3.5] are finite, with no ties. At 95% two-sided, k = 1, and D₍₁₆₎ = 1e308 − (−1e308) = **∞**. The plain `stat.test.mannwhitney` answers this pair normally, since it works on ranks.
- **The median.** a = [1.7e308 1.6e308 1.5e308 0.0] and b = [0.0 0.1 0.2 0.3] give D₍₈₎ = 1.5e308 and D₍₉₎ = 1.6e308. Their mean, (D₍₈₎ + D₍₉₎)/2, is **∞** in f64. The true median, 1.55e308, is finite, and D₍₈₎/2 + D₍₉₎/2 gives it.
- **The house rule elsewhere.** RFC-0015's tests refuse a non-finite statistic with E114 (`infer.rs`, `statistic`), and the describe words refuse a non-finite variance or covariance in the same way (`describe.rs`, `finite`).

**Problem.** The RFC leaves three outcomes open:
- answer ∞, which is against B12;
- leave the key out, which is what A3 does for an infinite end;
- refuse.

The second matters most. D251's A2 amendment says "an absent `lower` or `upper` means only an infinite end (A3)", and an implementation that treats an overflowed D₍ₙₘ₊₁₋ₖ₎ as an infinite end breaks that silently. The median's overflow is worse: it refuses or answers ∞ where the true answer is finite. Criterion 2's palette (NaN, ±∞, wrong types, empty, ragged) has no ±f64::MAX, so nothing reaches either case.

**Suggested fix.**
- One sentence in S1: "an estimate, end or statistic that is not finite from finite operands is E114, as RFC-0015's `statistic` and `finite` refuse; an absent end is only ever an infinite one (A3)".
- In S2, form the even-nm median as D₍ₙₘ/₂₎/2 + D₍ₙₘ/₂₊₁₎/2, or as the lower plus half the difference, which cannot overflow when both are finite.
- Add the first pair above to criterion 2 → E114.

The same sentence covers `oddsratio`'s ad/(bc) and the t ends.

**N2. "The count at nm − u − 1" should say "the lower-tail count".** Lines 315-317: "the lower-tail count at u > ⌊nm/2⌋ is C(n + m, n) minus the count at nm − u − 1".
- The identity holds for the cumulative count L(nm − u − 1), not for the coefficient c(nm − u − 1). The sentence's first half uses "lower-tail count", and its second half drops it.
- At u = nm the index is −1, and L(−1) = 0. State it, since a `usize` index cannot be −1.

Verified for every u at n, m ≤ 12 (`rev6_mw.py`).

**N3. "The largest k" has no maximum when the threshold is at least 1.** If (α/2)(1 + 10⁻⁷) ≥ 1, every k past nm satisfies P(U ≤ k − 1) ≤ the threshold. So "the largest k" is unbounded, not nm + 1. E101 at k > nm makes the outcome right. Say "the largest k in 0 … nm + 1", so that the search an implementer writes is bounded by the text.

**N4. "8.2·10⁻⁴ at 90% two-sided" is 8.147·10⁻⁴, which is 8.1 to two figures.** This applies to both S2 (line 331) and D251's table. The fourth review gave "8.15", and rounding that again gives 8.2. Also, "each worst at n = 7, m = 1 080 104" is a plateau: s = 7 gives the same shortfall to four digits from l = 1 080 104 to the cap (`rev6_floor.py`). "At s = 7" would be more accurate.

**N5. S5's lgamma figures are CPython's `lgamma`, not Bund2's.** Bund2's `lgamma` is `statrs` 0.18.0's Lanczos `ln_gamma` (`special.rs`, `lgamma`). With it ported bit for bit (`rev6_J.py`):
- J's relative error is **3.5e-10 at df 400 000** (S5 says 1.2e-10) and 4.6e-10 at 399 998, as S5 says;
- the lgamma side's worst is 3.3e-13, at df 69, not CPython's 1.5e-14.

The switch rule and criterion 9's 1e-12 both still hold. Either say which lgamma was measured, or quote Bund2's figures.

**N6. The count table is largest at nm = 10⁷, not at s = 6.**
- Line 364-365: "⌊nm/2⌋ + 1 `u128`, 80 MB at its largest (s = 6, l = 1 666 666)".
- Sizes with nm exactly 10⁷ are exact and allowed, since only "above 10⁷" is E111. These are s = 1, 2, 4 and 5 against 10⁷/s. Each holds 5 000 001 entries, 16 bytes more than at s = 6.

The figure, 80 MB, is right; the place is not. This is negligible, so drop the parenthesis or name nm = 10⁷.

**N7. "Every n ≤ 6" and "n = 7 from m = 1 080 104" are about min(n, m).** Line 301. The condition C(n + m, n) < 2¹²⁸ is symmetric, so a = 1 080 104 values against b = 7 is past it too. Say "every min(n, m) ≤ 6".

D251's third amendment still says "every n ≤ 5" (`decisions.md:17272`). That is true as a lower bound and is now superseded in the RFC's text. The fourth amendment does not mention it.

**N8. S7's "seeded from entropy, as RFC-0015 §S8 has it".** RFC-0015 §S8 says the fallback is "a thread-local `StdRng`" (`RFC-0015-biomathematics.md:678-679`). The entropy seeding is `with_rng`'s `StdRng::from_entropy`. Cite `rng.rs`, `with_rng`, for that half.

**N9. D251's Status line and the RFC's rulings table do not record the fourth amendment.**
- D251's Status (`decisions.md:17211-17219`) lists the amendments up to "C's exact branch widened" and stops. The third review's N12 had asked for this line to name every amendment, and it is stale again.
- The RFC's A9 row (line 840) says "**A**, then **C** in its k, widened" and does not show the owner's "record A" on the shortfall (options A accept, B conservative).
- The RFC's header (line 14) does mention it.

Add a clause to each, as the earlier amendments did.

## Verdict

**Ready once two should-fixes are answered.** No blocker. Revision 5's mathematics is sound: every k, bound, shortfall and tail it states reproduces.
- **S1:** criterion 6's conf 0.3, n = m = 65 and n = 20, m = 691 cases use data with repeated differences. The k each asserts and the wrong k each was added to catch give the same ends. Replacement data with every difference distinct, and their expected ends, are given above.
- **S2:** a Hodges–Lehmann difference, the even-nm median, or a t end can overflow from finite operands. State E114, which RFC-0015's `statistic` already uses, so that an absent end keeps meaning only "infinite" (A3, A2's amendment). Form the median without overflow.
