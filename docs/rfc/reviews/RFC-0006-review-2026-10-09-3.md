## Blocking

**B1 — A port that is not a number from 1 to 65535 is refused by the
reference and is port 80 in Bund2, for the URL and for the proxy.**

§B7: "All 175 agree on where the request goes but two: a URL with no scheme,
which D54 approves, and a literal space, which D125 does." The preservation
row for `use`, `url`, `url.` says the same. F182's note: "`on_curls_port`
writes 1080 in before `ureq` sees the proxy."

`http_url` copies whatever follows the host's last colon into the URL it
hands `ureq`, and `on_curls_port` returns a proxy that has anything at all
after its colon unchanged (`Some(_) => Some(rest.to_string())`)
(`crates/bund2-stdlib/src/host.rs`). Neither asks whether it is a port.
`http` 1.5.0 then reads a port as `parse::<u16>()` and answers `None` when
that fails (`src/uri/port.rs:37-43`, through `authority.rs:180-185`) — the
authority itself still parses — and `ureq` 3.4.0 fills a missing port with
the default: `unwrap_or(… .default_port().unwrap_or(80))` for the request
(`src/util.rs:353-358`), `unwrap_or_else(|| self.inner.proto.default_port())`
for the proxy (`src/proxy.rs:289-294`), which is 80 for HTTP (`:34-36`). So a
port Bund2 cannot read becomes a port nobody wrote. libcurl refuses the URL.

Measured 2026-10-09, with a listener on port 80 that answers with a program
printing `p80`. "Asks nobody" means no listener received a connection.

| the program, or the one variable set | oracle | Bund2 |
|---|---|---|
| `"http://127.0.0.1:65536/lib.bund" use` | fails; asks nobody | **`GET /lib.bund` to port 80; prints `p80`** |
| the same with `:99999`, `:65616`, `:4294967376`, `:80x` | fails; asks nobody | **port 80, each** |
| `"http://localhost:65536/lib.bund" use` | fails; asks nobody | **port 80** |
| `:65536` with `http_proxy` naming a proxy | fails; asks nobody | **`CONNECT 127.0.0.1:80` to the proxy** |
| `http_proxy=http://127.0.0.1:99999` | fails; asks nobody | **port 80 asked as the proxy: `CONNECT`, then `GET`; prints `p80`** |
| `http_proxy=http://127.0.0.1:<a port>x` | fails; asks nobody | **the same** |
| `http_proxy=127.0.0.1:99999` | fails; asks nobody | **the same** |
| `:0` in either place (control) | fails | fails |
| an empty port in the URL (control) | port 80 | port 80 |

**Rows 91 and 92 of the measurement are the fifth and sixth lines of that
table**, and `docs/measurements/fetch-2026-10-09.md` has both as
`fail | fail`. They agreed because `fetch.py` listens on three ports and
1080, and Bund2 went to a fourth. Run again here with port 80 answering,
they differ.

**Why it blocks.**

- It is the twelfth review's B1 on the same axis: which port. That review's
  summary — "passes the variable's text to a second parser and stops
  looking" — is still true of the text after the colon, in both operands.
- The direction is the one with a consequence. In every difference the RFC
  lists, Bund2 fails where the reference fetches, or reads a file the
  program named. Here **Bund2 evaluates what a listener on port 80 returns
  for a URL the reference refuses**, and the URL named another port. A
  program that builds a port by arithmetic and gets it wrong has a fetch
  that fails in the reference and succeeds in Bund2, from the host's web
  server.
- The RFC states the opposite twice and cites a measurement for it, and the
  measurement contains the case.
- Bund2 chooses the string it hands over, so, like the port-less proxy and
  unlike D124's two, this is closable in `host.rs`.

**What it needs.** No ruling that I can see: the reference refuses, Bund2
does not, and no entry approves it, so it is a defect under F182 or F183.
Then a row in §B7's table, the "but two" sentence, the preservation row,
F182's note, rows 91 and 92 re-measured with port 80 answering, and a test
that names a port over 65535 in the URL and in the proxy. The check wants to
be libcurl's and not `u16`'s alone: `:0` and an empty port are already
right and should stay so.

**B2 — The reference fetches and evaluates schemes Bund2 refuses, and
nothing approves it. D54's scheme set is Bund2's, not the reference's.**

The preservation row: "**Preserved under D54's scheme set (D76)**". §B7: "A
string with no scheme is refused, and `https://` is refused — both approved
deviations under D54." D54 lists those two; D124 adds a third and fourth and
D125 calls itself "the fifth approved deviation for the fetch". D54's own
text on any other scheme is "Anything else fails", which is what Bund2 does.

The reference hands the string to libcurl whole
(`reference/Bund/src/stdlib/helpers/file_helper.rs:45`), and the libcurl it
links on this machine speaks more than two: `curl --version` lists twenty-four
protocols for it. Measured 2026-10-09:

| the program | the one variable set | oracle | Bund2 |
|---|---|---|---|
| `"gopher://127.0.0.1:<port>/0/lib.bund" use` | — | **evaluates what the listener returns**; it received `/lib.bund` | refuses; asks nobody |
| `"dict://127.0.0.1:<port>/d:word" use` | — | **evaluates what the listener returns**; it received `CLIENT libcurl 8.7.1` | refuses |
| `"ftp://127.0.0.1:<port>/lib.bund" use` | `ftp_proxy`, an HTTP proxy | **evaluates what the proxy returns**; it received `GET ftp://…/lib.bund` | refuses |
| the same | `all_proxy` | **the same** | refuses |
| the same | — | connects, waits for an FTP greeting, fails | refuses; asks nobody |
| `"telnet://127.0.0.1:<port>" use` | — | connects, fails | refuses |

`gopher://` with `http_proxy` set went direct, so that variable is not read
for it; `ftp_proxy` is a variable the reference reads that §B3's list of
five does not have, and Bund2, refusing `ftp://`, never needs.

**Why it blocks.**

- It is CLAUDE.md's shape exactly: "a required deviation filed as a
  non-deviation, so no criterion covers it". `https://` refused is on D54's
  list by name. `gopher://` refused is the same deviation and is on no list.
  The twelfth review carried it as an assumption — "`file://` and `http://`
  are the only schemes the reference would have fetched … none was measured
  here" — and D54's note of the same day answers for spellings, not for
  schemes.
- Row 161 of the measurement is `url ftp://127.0.0.1:OPORT/x`,
  `fail | fail`, and is counted among the rows that "agree on where the
  request goes". The oracle's request went to the listener. S1.
- **It is the lighter of the two.** Bund2 fails closed, the owner chose the
  set in D54's first line, and I expect the answer to be one sentence. But
  the sentence is the owner's, the count of approved deviations is stated
  in three entries, and the row says "preserved".

**What it needs.** A ruling: a sixth approved deviation under D54 — every
scheme but `file` and `http` is refused, where the reference fetches
whatever its libcurl speaks — or something narrower. Then the row, §B7's
last bullet, and D54's list.

## Should fix

**S1 — The measurement cannot tell "asked nobody" from "asked and was not
understood", and §B7 reads its `fail` as the first.** `fetch.py` classifies
a run by the last line of standard output and records a listener's request
only when it is an HTTP head (`run`, and `serve`'s wait for `\r\n\r\n`). A
connection that speaks another protocol, or none, leaves no trace and the
cell reads `fail`. Run again with listeners that record every connection:

| row | setting | oracle | Bund2 | covered by |
|---|---|---|---|---|
| 39 | `http_proxy=socks5://p1` | connects; SOCKS5 greeting | asks nobody | D124 |
| 40 | `http_proxy=https://p1` | connects; TLS hello | asks nobody | D124 |
| 93 | `http_proxy=socks5h://127.0.0.1` | connects to 1080; SOCKS5 greeting | asks nobody | D124 |
| 160 | `HTTPS://…` | connects; TLS hello | asks nobody | D54 |
| 161 | `ftp://…` | connects; waits for a greeting | asks nobody | **nothing — B2** |
| 91, 92 | a proxy port over 65535, or not a number | asks nobody | **asks port 80** | **nothing — B1** |

So "All 175 agree on where the request goes but two" is false of seven rows.
Four are approved deviations the sentence forgot it had; three are the two
blockers. The file's own sentence, "Two rows differ in who answers", is true,
and is a weaker claim than the RFC makes from it. Two more things about the
file: row 91 is printed as `proxy http://127.0.0.1:<port>` where `fetch.py`
prints `proxy http://127.0.0.1:99999`, so "`fetch.py`, beside this file,
produced the table" is not quite so; and "Bund2 is the tree that carries
F182's note of the same day and F183" names no commit.

**S2 — A proxy with no scheme and anything after its address fails the
fetch; the reference uses it.** Not one of D124's two.

| `http_proxy` | oracle | Bund2 |
|---|---|---|
| `127.0.0.1/` or `127.0.0.1/x` | through port 1080 | fails; asks nobody |
| `127.0.0.1:<port>/`, `…/x`, `…?q`, `localhost:<port>/x` | through the proxy | fails; asks nobody |
| `http://127.0.0.1:<port>/path` (row 83, control) | through it | through it |

Rows 83 and 86 tried a path and a query after a proxy *with* a scheme, and
row 78 a slash; none without one. `on_curls_port` writes the port in
correctly — `127.0.0.1:1080/x` — and the fetch fails after that, in
`ureq::Proxy::new` or behind it; I measured the outcome and did not trace
which line refuses. It fails closed. A trailing slash on a proxy variable is
an ordinary thing to write.

**S3 — "`a proxy with no port` | port 1080, whatever its scheme" is not
what the oracle does for `https://`.** With a listener on 1080,
`http_proxy=socks5h://127.0.0.1` reached it and
`http_proxy=https://127.0.0.1` reached nothing, where `https://` *with* a
port sent a TLS hello to that port. So libcurl's default for an HTTPS proxy
is not 1080; I did not find which port it is. The column is headed "oracle
and Bund2", and the comment on `on_curls_port` says "whatever the proxy's
kind". Bund2 refuses an HTTPS proxy before the port matters (D124), so
nothing behaves differently; the sentence is measured for `http://`, for no
scheme and for `socks5h://`, and says more.

**S4 — More spellings on which the two differ, all outside the 175.** F183
says "another spelling may differ", and these do:

| the URL, or the proxy | oracle | Bund2 |
|---|---|---|
| `<`, `>` or a backtick in the path; `<` in the query | fetches | refuses |
| a host with `%xx` in it — `127.0.0.%31`, `%6cocalhost` | fetches the decoded host | refuses |
| the same in a proxy, `http://127.0.0.%31:<port>` | through it | refuses |
| a host that is not ASCII, through a proxy | asks the proxy | refuses |
| `http://[::1%25lo0]:<port>/…` | fetches | refuses |
| `http://a@b@127.0.0.1:<port>/…` | **refuses** | **fetches** |

All but the last fail closed, and each is one call past `http_url`: the URL
it builds is parsed again by `http::Uri`, which has its own list of bytes.
`^`, `|`, `{}`, `[]`, `'`, a lone `%` and the sub-delimiters were tried in a
path and agree.

**S5 — A direct request differs on the wire too, and §B7 says only the
proxied one does.** "**The request differs on the wire**" is D124's first
deviation, about a proxy. With no proxy:

| the URL's path | the oracle sends | Bund2 sends |
|---|---|---|
| `/a/../lib.bund` | `GET /lib.bund` | `GET /a/../lib.bund` |
| `/é.bund` | `GET /%c3%a9.bund` | `GET /é.bund`, the two bytes raw |

libcurl removes dot segments and percent-encodes bytes above ASCII in a
path before it asks; `ureq` sends what it was given. (`%2e%2e` is left alone
by both, and a query's high bytes are sent raw by both.) Most servers answer
the two alike. One that does not answers the reference and Bund2 with
different bodies, and §B7's own sentence — "the body of an error status is
still the answer" — means `use` evaluates whichever it got.

**S6 — `a_proxy_that_names_no_port_is_asked_on_1080` does not say when it
did not run.** §B7: "which needs port 1080 free and says so when it is
not". It prints with `eprintln!` and returns, and the test passes, so the
harness discards the line. Run here with port 1080 held: `1 passed`, and
the words "port 1080 is in use" appear nowhere in the output. A run of
`cargo test` cannot tell whether the wire half was checked. The same
question applies to the run recorded above: I do not know whether 1080 was
free at that moment.

**S7 — Small, each one line.**

- §B7: "an absolute path after one slash or three". The code and F183 say
  three or more; rows 164 and a five-slash URL tried here read the file.
- §B7: "`file:` … with `%xx` decoded". `percent_decode` ends in
  `String::from_utf8(out).ok()`, so a path whose decoded bytes are not
  UTF-8 — `%ff` — fails the fetch. Read, not measured against the oracle.
- The closing paragraph's "Eleven reviews of this document … twenty-three"
  was right as of the twelfth. This one makes it twelve and twenty-five.

**S8 — Carried, all stated in the RFC and none changed.** `cargo xtask
bundle` in neither `cargo test` nor CI; `black_box` a hint; ELF and PE
unmeasured in the built form; `/usr/bin/codesign` possibly a stub; no
criterion has run in CI; the recorded version is `0.0.0`; Q42; the three
loose citations.

## Claims that need a citation and lack one

- "**All 175 agree on where the request goes but two.**" Its source is the
  table, and the table does not record where a request went (S1).
- "a proxy with no port | **port 1080, whatever its scheme**". Three kinds
  were measured and one of the others differs (S3).
- "libcurl sends the rewritten form, so the `Host` header is `127.0.0.1`
  for `127.1`" — the comment on `http_url`, and the reason F183 gives for
  rewriting. No row records a `Host` header; `fetch.py` keeps the request
  line only.
- "`file:` follows curl's rules as far as they were measured". Honest, and
  it means the rule is the table. The table has no file in a directory
  whose name needs `%xx` beyond a space, no directory as the target (tried
  here: both fail), and no name with `%` that is not an escape (tried here:
  both read it).
- Carried: "one approved deviation's recorded hash pins a path Bund2
  prints"; both `codesign` tables, criterion 1's size tables and §B2's two
  timings name no command that reproduces them.

## What the RFC assumes and does not state

1. **A `fail` in both columns is the same event.** S1. It is at least three:
   refused before any connection, connected and not understood, and
   connected to a port where nothing was listening that day.
2. **The ports `fetch.py` listens on are the ports a request can go to.**
   B1. Port 80 is where `ureq` goes when it cannot read a port, and nothing
   listened there.
3. **Handing `ureq` a URL libcurl would accept is handing it one `ureq`
   reads the same way.** `http_url` normalises the host and passes the port
   and everything after the authority through. The twelfth review's second
   assumption, moved from the proxy to the URL.
4. **`http` and `file` are the schemes a program in the reference can
   `use`.** B2. They are the schemes Bund2 has.
5. **`u16::parse` failing means "no port was written".** That is `http`'s
   reading and `ureq` builds on it; libcurl's is "not a URL".
6. **A proxy variable that is not UTF-8 is unset.** Carried from the twelfth
   review; `fetch_uri` reads with `std::env::var(..).ok()`. Read, not
   measured.
7. **A passing test ran what it names.** S6.
8. Carried from the eleventh and twelfth reviews and unchanged: the sentinel
   cannot occur in what a build writes; no golden fails to parse;
   `--inspect` reports what a header says and not what the runtime does; the
   executable on disk is the one running when `build` copies it.
9. Carried, and stated in the RFC: the compiler does not fold reads of the
   region; the in-place write works on ELF and PE; `/usr/bin/codesign` is
   present and real; a refusal is text and not an exit status; the rules
   are one libcurl's, 8.7.1, on macOS.
