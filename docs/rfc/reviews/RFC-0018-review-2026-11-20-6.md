## Should fix

### SF1. "As R orders them" holds only when an interaction's members are written in the order their variables first appear

§S2 (463-468) says an interaction's columns vary "the first member varying fastest, as R orders them", citing `addfactor`. D264's premise for its fifth choice says the same: "R varies an interaction's first member fastest (`model.c:263-278`)". `addfactor` fixes how the next variable's columns are placed. It does not decide which variable is next. R's column loop takes a term's variables in variable-index order:
- `for (i = 0; i < nVar; i++)` (`model.c:701`), checking the term's bit for each variable (`:711`);
- the index is the order in which `InstallVar` first meets each variable in the formula (`model.c:1091-1112`);
- the term label is built in the same order (`model.c:2053-2075`).

So R codes `y ~ b + a + a:b` with `b` fastest and labels the term `b:a`. Under K6, an interaction's members are always earlier terms. R's "first" member is therefore the one whose main effect comes first in `terms`. §S2's "first" is the one written first in the interaction. The two agree only when the interaction lists its members in main-effect order. Example: §S2's `[ "b" "a" [ "a" "b" ] ]` varies `a` fastest, and R's equivalent varies `b` fastest. Criterion 1's "codes its columns in R's order, the first member fastest" (1270-1271) has the same ambiguity.

**Fix (plain error in the citation; the remedy is an [author] choice):** either
- (a) qualify the sentence. "The first member as written varies fastest. R's order follows the variables' first appearance in the formula (`model.c:701`, `:1091-1112`), so the two agree when an interaction lists its members in the order of their main effects." Criterion 1 then uses such an interaction. Or
- (b) order an interaction's members by their main effects' positions in `terms`, which is R's order. Names would then follow that order too, as R's labels do (`model.c:2053-2075`).

Either way, D264's fifth premise needs a dated note in the register, as D251's A3 has one ("confirmed on a corrected premise"). The owner ruled on "R's order", and (a) is not quite R's order.

### SF2. The offset has two sources of truth, and a hand-made design can make them disagree

The fifth revision makes `spec.offset` decide two things:
- whether `fit.glm` refits the null model (795-798, "'An offset' is one the design was given (`spec.offset`), zeros included");
- whether `model.predict` reads an offset column (927, "`offset`'s column read when the spec names one").

Everything else reads the `offset` LIST's values:
- the fits themselves;
- `fit.lm`'s closed-form `null.deviance`, Σ wᵢ(yᵢ − offsetᵢ − m)² (§S3);
- the `fit.logistic` path (D263).

The design check (593-605) requires `spec.offset` "when the design was given them". It does not require the `offset` LIST to be all 0.0 when `spec.offset` is absent. A program that writes an offset into a design by hand, which the check's preamble allows ("a design may be made or changed by hand"), therefore gets three wrong results:
- from `fit.glm`, a `null.deviance` at the weighted mean of y that ignores the offset. That is R's `glm.fit` value, which `glm()` replaces because it is wrong (`glm.R:104-107`'s comment);
- from `fit.lm` under the same design, a `null.deviance` that includes it;
- from `model.predict`, predictions without it.

The same applies to `weights` against `spec.weights`, though only `model.predict`'s prediction-interval default reads the latter.

**Fix (plain error):** add to §S2's invariants: "without `spec.offset`, every `offset` is 0.0; without `spec.weights`, every weight is 1.0" (E101 naming the key). The §S8 malformed-design row then covers it. Alternatively, read "an offset" from the values everywhere, and give up the R parity that the fifth review's U4 asked for. The invariant is simpler.

### SF3. Which inverse link `model.predict` maps through, clamped or bare, is unstated

§S4's clamp table (753-763) gives each link a clamped inverse, `log` as μ = max(exp η, ε) among them. §S6 (965-993) maps η̂ and the interval ends "through the inverse link", and scales `se` by |μ′(η̂)|. It does not say whether the clamp applies there. R's `predict.glm` uses the family's own `linkinv` and `mu.eta` (`predict.glm.R:60-61`), which are the clamped ones (`family.R:99-102`; `family.c` for the logit). The difference is visible on criterion 5's new case:
- the zero group's `lower` is 0.0 by the bare inverse and 2.22·10⁻¹⁶ through the clamp (recomputed above);
- the third bullet ("an end outside the family's valid μ … answered as computed", 991-994) makes the bare 0.0, outside the Poisson's μ > 0, a legitimate answer;
- under `logit`, an end beyond `ETA_LIMIT` maps to 1/(1 + e^−36.04) through `fit.logistic`'s clamp and to the exact logistic without it.

The fixture script cannot be written until this is fixed. The same paragraph also leaves a non-finite point prediction or response-scale `se` to the general rule unstated: for example, `log` at η̂ = 800 gives μ = ∞. That is E114 by §S1, and not A3, since `fit` and `se` are not interval ends.

**Fix:** state that `model.predict` maps through §S4's clamped inverse link and μ′, as R's `predict.glm` does. Cite `predict.glm.R:60-61` and `family.R:99-102`. Add a sentence that a non-finite `fit` or `se` is E114 (§S1), A3 applying only to `lower` and `upper`. Criterion 5's zero-group case then states `lower` as ε. If the bare inverse is preferred instead, mark it **[author]**.

### SF4. A fit's lengths, and a spec's agreement with the fit's columns, are not checked

- **The fit check** (1036-1043) asks only that each key be present with its type ("a missing or mistyped key is E101"). The design check states lengths ("the MATRIX n × k, every LIST of its length", 590-591). The fit check does not. A fit is a MAP that a program can edit, so the check also needs:
  - `coef`, `se`, `p` and `names` of length k;
  - `vcov` k × k;
  - `fitted`, `y`, `weights`, `offset` and `hat` of length n, the same n.

  Without these, `model.influence`, `model.residuals` and `model.compare`'s element-wise equality index past an end. `model.predict` forms xᵀVx with x and V of different sizes, which an `nalgebra` product does not refuse.
- **`model.predict` codes a new frame from `spec`** (925-927). Line 607 says it checks `spec`'s shape. It does not check that the spec codes the fit's columns. The RFC invites one way they can differ: "a design whose MATRIX a `linalg.` word has changed passes only if it still meets these" (606-607). Removing one factor contrast column, with `names` and `assign` edited to match, still meets every listed invariant. The fit then has k coefficients, and its `spec` codes k + 1 columns.

**Fix (plain error):** add the lengths to the fit check, each E101 naming the key, as §S2 does for a design. State that `model.predict` refuses when the columns its `spec` codes differ from the fit's `names`, in count or name. Use E101 on `fit`, e.g. `fit is outside model.predict's domain: spec codes 7 columns, names has 6`. Add both to criterion 8's palette.

## What the RFC assumes and does not state

- **U1. The fit words' order of refusals.** `model.matrix` (548-567) and `model.predict` (948-956) state an order. `fit.lm`, `fit.glm`, `model.anova`, `model.compare`, `model.residuals` and `model.influence` do not. For example, a malformed design with an unknown `family` could fail either way, and a malformed fit with an unknown `type` likewise. Criterion 8 does not care which fails first, but each word's per-row tests do. State "operand checks, then `opts`, then the computation", or whichever order is meant.
- **U2. `model.anova`'s suffix for a refusal from the full model.** Line 1059-1061 says the Gaussian perfect-fit refusal comes from the full model "with no row suffix". The general rule (1064-1066) names only the sub-model rows and the null model. Say whether every refusal from the full model's fit has no suffix, or `, fitting the model through term "<last>"`.
- **U3. The cost of dropping a whole interval key.** Under D264's second choice, one infinite end removes `upper` for every row of the prediction. A program that wants the other rows' ends predicts them separately, or reads `type` `"link"`. That is the owner's ruling. The text could say so in one sentence, as D251's note says how a program tests for the key.
