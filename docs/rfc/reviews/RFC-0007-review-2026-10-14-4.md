says.** D166 refuses the value at every writer. For `save` that refusal
lands after two of the word's three families have already committed, so a
refused `save` leaves a world file whose lambdas are newer than its stacks —
new behaviour the reference cannot exhibit, with no row and no sentence in
D166 (B1). Two things about the reference that D166 and F208 describe
incompletely: the oracle's own `dup` refuses the same value through the
same codec, so "every writer accepts it" is not the reference's whole

`save`'s refusal text is one layer short of the reference's shape at that
site, against a row that says "under their own prefixes" (S2). RFC-0001,
which specifies the codec and is Accepted, carries no note that `to_binary`
now refuses two classes of value (S3). Every blocker of the fourth and
fifth reviews is answered where it stands, and I re-checked each answer.

## Blocking

### B1 — A refused `save` under D166 leaves a partially written world, and nothing records it

D166 B: "every writer refuses a JSON value below the top level, under its
own prefix". `save` is not one write. `save_world` for `Family::All` runs
`replace_aliases`, `replace_lambdas` and `replace_stacks` in sequence
(`crates/bund2-stdlib/src/world.rs:612-620`), and each is its own redb
transaction that commits before the next begins (`:349-362`, `:365-388`,
`:394-420`). The codec is called inside the lambdas and stacks transactions
(`:382`, `:413`). So a VM whose stack holds the value gets this far: aliases
committed, lambdas committed, stacks refused and rolled back.

Measured today, release Bund2, one program — a lambda `lam` registered, a
MAP holding a JSON on the stack, `save`:

| step | result |
|---|---|
| `save` | `Aliases SAVE returns: the value holds a JSON value inside a container, …` |
| the world file | written, 1 MiB (redb's preallocation) |
| `load.lambdas` from it, fresh VM, then `lam` | loads; `lam` answers `3` |
| `load.stacks` from it | `Stacks LOAD returns: Error compiling SELECT for stack data: no such table: STACK_DATA` |

So the program was told the save failed and the world file holds its new
lambdas and none of its stacks. The reference's `bund_save` has the same
sequential shape (`bund_save.rs:10-39`, one `conn.execute` per value with
no enclosing transaction), but the reference's `to_binary` does not fail on
this value, so the state is reachable only in Bund2 and only since D166.
The oracle on the same program printed `after save` and wrote a 32 KiB
world holding everything.

What is needed: a row — "a refused `save` has already replaced the aliases
and lambdas" — or a check that runs the walk over every stack value before
the first transaction, which would make the refusal atomic and the row
unnecessary. Either is the owner's: D166's recommendation and risk
sentence speak of "the write" as if it were one, and the register should
say which the ruling meant. `save.model` is one transaction (`world.rs:86-89`,
the codec before `begin_write`) and is clean.

## Significant

### S1 — The oracle's `dup` refuses the same value through the same codec, and Bund2's accepts it

F208: "every writer accepts the value and every reader of the bytes
fails". D166: "a program that wrote such a value and never read it now
fails at the write". Both describe the reference as if the value were
freely usable there until a reader. It is not. `Value::dup` is a
`to_binary`/`from_binary` round trip (`reference/rust_dynamic/src/dup.rs:6-19`),
reached from the `dup` word through `dup_in_current_stack`
(`reference/rust_multistack/src/ts_stack_op.rs:30-49`), and from
`many_in_current_stack`/`many_in_stack` (`:70-90`), which D20 and F13 cite
as the path of `dup` and of `?move`/`?.`. Measured today:

| program | oracle | Bund2 |
|---|---|---|
| `dict "k" '{"k": 1}' json set dup` | `Error duplicating data in current stack: dup() returns: Bincode does not support the serde::Deserializer::deserialize_any method (…)` | `after dup` |
| `… { true } ?.` | `after ?.` | `after ?.` |

So in the reference the value cannot be `dup`ed at all, which narrows
D166's risk considerably — a reference program holding such a value could
never have copied it — and in Bund2 it can, because F13's FIX made `dup` a
structural clone. That second half is a deviation nothing records: F13
records the JSON key-order consequence of the round trip and not that the
round trip *fails* for a nested JSON; F208 says "every writer accepts". It
is outside this RFC's eight words, which is why it is not B-level here, but
D166 is this RFC's decision and its description of the reference is where
the gap is. What is needed: an addendum to F13 or F208 naming `dup` and
the `many` family as reference sites that refuse the value, and one
sentence at the RFC's D166 passage (`:191-199`) so "the reference writes
it" does not read as "the reference handles it". (`?.` succeeded on the
oracle; whichever path it took, it did not reach `Value::dup` for this
operand, and D20's "`?move`/`?.` hit the same code" is not re-checked here.)

### S2 — `save`'s refusal text is one layer short of the reference's, against a row that says "under their own prefixes"

The row at `:662` says the seven writers refuse "under their own
prefixes". For `save` the Bund2 text is `Aliases SAVE returns: the value
holds a JSON value inside a container, …` — `save_world`'s wrapper
(`world.rs:615`, the reference's paste preserved) around the bare codec
string, because `replace_stacks` and `replace_lambdas` map the codec's
error with `.map_err(Error)` and no prefix (`:382`, `:413`). The
reference's shape at those sites is `Aliases SAVE returns: Error
converting data to blob: <reason>` for a stack value (`stacks.rs:110`) and
`Aliases SAVE returns: Error compiling lambda body: <reason>` for a lambda
(`lambdas.rs:92`). `save.model` has its layer (`SAVE.MODEL returns: Error
compiling mode: …`, `world.rs:85-87` against `models.rs:101`, the
reference's own "mode"); `encode.base64` and `debug.dump` have theirs. The
omission predates D166 — D114's depth refusal takes the same path — but
D166 is the first ruling to assert the prefix for `save`, and no test holds
it. One `map_err` at each of the two sites, and a test.

### S3 — RFC-0001 specifies the codec and does not say it refuses anything

RFC-0001 is Accepted (`:3`). It describes the wire format as `to_binary`
serialising the concrete value and `from_binary` restoring it verbatim
(`:290-294`), and the reference's `dup` as the round trip (`:64-69`). It
has no mention of F118, D114, D166 or `MAX_WIRE_DEPTH`. After D114 and
D166 the codec refuses two classes of value the reference writes — past
256 levels, and a JSON inside a container — and the document that owns the
codec says so nowhere, while this RFC says so in three places. RFC-0000
got a dated note when this RFC's third review found its feature table
stale (`:261-266`); RFC-0001 is owed the same for its codec paragraph.

## What the RFC assumes but does not state

1. **A refused write is a write of nothing.** False for `save` (B1).
2. **The reference handles the value everywhere but at a reader.** False:
   its `dup` refuses it (S1).
3. **Each writer's refusal carries the reference's text at that site.**
   One layer short for `save` (S2).
4. **RFC-0001's codec paragraph still describes the codec.** It does not
   mention either refusal (S3).
5. **The fourth `bus_pull` arm cannot fire.** True, because channels are
   never removed and the map holds the sender; that reason is the "channels

## Disposition

Not ready to accept, on one finding: B1 is a behaviour D166 introduced
that D166 did not consider, it loses a program's data consistency rather
than a message, and it needs either a row the owner accepts or a one-walk
check before the first transaction. S1 and S2 are the register's and the
row's descriptions of what was built, both wrong in a sentence each; S3 is
a dated note owed to RFC-0001. Everything the fourth and fifth reviews
blocked on is answered where it stands and each answer checks out; every
test the criteria name passes in both builds; D166's two tests are
load-bearing; conformance is at its ceiling. The oracle was run on every
writer D166 names and on two it does not, and the two it does not are
where the findings came from — which is the fifth review's closing point
restated: run the rest before labelling them.
