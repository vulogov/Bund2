## Blocking

### B1. SMYSL's CLI has no `--break-lock`, so R14 and R20 point operators at nothing

These parts of the RFC send an operator to "SMYSL's `--break-lock`" to
clear a stale lock:

- §S9, which since revision 5 includes the lock Bund2 leaves after a
  panic;
- R14 A;
- R20 A;
- criterion 15;
- Q51's revision-5 note.

At 4f5ecb9, that option is not implemented anywhere:

- `Lock::break_lock` exists (`smysl-graph/src/lock.rs:193`). Its own
  comment says "Nothing in this crate calls it" (`:190-192`).
- `src/main.rs` never mentions `break_lock`, `break-lock` or `Lock::`.
  Its only uses of the lock module are `acquire_all`, at `:8628`,
  `:12656`, `:12790`, `:12914`, `:13033` and `:13104`.
- A search of the whole tree finds `break_lock` only in `lock.rs`, in its
  test, and in `smysl-graph/tests/redb_crash.rs:276`. `--break-lock`
  appears only in prose: `CHANGELOG.md:4101`,
  `SMYSL-2.4_LIBRARY_AND_INGEST.md:1216,1223,1873,3825` and the manual's
  appendices.

So the operator's only remedy is to delete `lock` and `log/*.lock` by
hand. Two consequences:

- **R14 A's reason is gone.** R14 A rejects a `smysl.unlock` word because
  breaking a lock is SMYSL's operator command. No such command exists.
- **R20 A turns every Bund2 panic in a write into a library no tool can
  unlock.** The panic forgets the library lock **and every shard lock**
  `acquire_all` took (`smysl-text/src/lock.rs:30-41`). Criterion 15
  breaks "the lock", in the singular, and would then still meet SM07 on a
  shard lock.

**Needed:**
1. Withdraw the claim that SMYSL offers `--break-lock`, and cite what
   exists. The fourth review's citation list repeated the error, as every
   earlier review did.
2. Re-decide R14 with that fact. The options are:
   - an operator deletes the files by hand, with the RFC naming them;
   - a Bund2 word or CLI subcommand calling `Lock::break_lock` for the
     library lock and each shard lock, after printing each holder;
   - asking SMYSL for the command as U8.
3. Make criterion 15 break every lock left.

## Should fix

### S1. The library a write reads is the one opened before the locks, not one read under them

§S9 takes SMYSL's order: open, read the shard names, then lock
(`smysl:src/main.rs:8618-8628`). Q57 records that a shard may appear in
that window. The window is wider than Q57 says. Everything the write
decides from the open library comes from the state **as of the open**,
not as of the locks, because `Library::open` loads every log into the
in-memory store (`smysl-text/src/library.rs:327-350`), and nothing
reloads it after `acquire_all`.

These claims are therefore false whenever another process writes in the
window:

- §S7: provenance is "judged at write time, against the library as it is
  when the locks are held".
- §S7: the gist profiles "are read under the locks, at write time".
- §S4: the attestation clock's `prev` is "read under the locks", so an
  agent's clocks "never go backwards". Two Bund2 processes writing as one
  agent can each read the same `prev`.
- §S4: "this agent has not attested that uid already". A second process
  may have just attested it, and a duplicate attestation is written.
- §S4: retraction step 1's "already retracted" and step 2's plan.
- `encode_by_shard`'s de-duplication checks `self.store`
  (`smysl-text/src/shards.rs:520`), the stale store. So a record another
  process appended in the window is appended again. The log then holds
  it twice, though a reader de-duplicates it.

**Needed:** either re-open the library after the locks are taken, and
write through the second open, or state these claims as "as of the
open" and widen Q57 to cover them.

### S2. NFC normalisation runs after the gist is fitted, and can lengthen it

§S7 fits the rendering with `fit_gist_with`, and then SMYSL's
`UnitCore::new` NFC-normalises the gist (`smysl-core/src/types/unit.rs:147`,
through `normalise` at `smysl-core/src/types/mod.rs:274-281`). NFC is
not length-preserving:

- A composition exclusion such as U+0958 normalises to two code points,
  U+0915 U+093C. That is 3 UTF-8 bytes becoming 6.
- So a gist fitted exactly to its bound can exceed it once SMYSL
  normalises it, and that is `SMY-E022`.

A Bund STRING atom is not guaranteed to be NFC.

**Needed:** normalise to NFC before fitting. `normalise` is `pub(crate)`,
so Bund2 would use `unicode-normalization` directly; SMYSL already
brings it into the tree. Criterion 12 should add an atom that is not NFC
next to the cut.

### S3. An error part way through an append releases the locks, which R20 does not cover

R20 keeps the lock after a **panic**, so that a library that may be half
written refuses further writes. The same half-written state follows an
**error** part way through `append_records`:

- The shard loop returns on `log.append(bytes)?` after earlier shards
  were written (`smysl-text/src/library.rs:1364-1375`).
- The store append can fail after every log was written (`:1379-1382`).

On an error, the locks drop normally and are removed, as they are in
SMYSL's own commands.

R20's rationale, "the program would write on to a library that may be
half-written", applies equally to that case. State whether R20 covers
errors returned from `append_records`, and if not, why a panic and an
error differ. Q51 should name the error path too.

### S4. Attestation parents feed salience's corroboration, which the RFC does not say

§S4 gives each conclusion an attestation whose parents are its grounds,
so that a `parents` trace walks back to its premises. SMYSL also reads
attestation parents in `salience`:

- It groups each unit's attestations by agent and recipe, and collects
  each group's parents as its ancestry (`smysl-graph/src/salience.rs:353-364`).
- It then keeps only "groups whose ancestry is disjoint from everything
  kept so far" (`:366-367`).

So the parents Bund2 writes decide whether its attestation counts as
independent corroboration when another agent also attests the same
conclusion.

That is probably the intended meaning, since a proof rests on its
premises, but it is a behaviour of `smysl.salience` that §S5 and
Preservation do not mention.

Hop 0 has a similar reading. "A unit's hop is the earliest any agent
attested it", and `hop_diff` partitions units by it
(`smysl-graph/src/lineage.rs:718-736`). Every Bund2 unit is at hop 0.
State both.

## Notes

- **N1.** Cite `smysl:src/main.rs:4484-4505` for the retract sequence,
  not `:4486`.
- **N2. Q58 can be answered.** `SMY-E020` resolves a body token as a
  label only through the `labels` map the caller supplies
  (`smysl-check/src/passes/closure.rs:46-80`, the `else` arm of the token match). Under
  `CheckOptions::default()` that map is empty, so a label reference is
  never reported. Closure reads the body only (`:60`), and Bund2's bodies
  hold no uid. Q58's worry is the reverse of what happens: a library's
  label references go **unchecked**, which is the point to state.
- **N3. `fit_with_suffix` answers 0 in two cases.** It does so when no
  character fits, and also when the suffix alone exceeds the bound
  (`smysl-core/src/types/estimate.rs:189-203`). SM12 should say it covers
  both.
- **N4. The `policy` key's form is unstated.** §S4's table says `policy`
  is optional, but not what a given value looks like. SMYSL's `Policy`
  is a struct, with a `boundary_level` and more
  (`smysl-text/src/part.rs:34`). Either define the MAP, or leave the key
  out of Phase 1 and always use SMYSL's default.
- **N5. `observed` is asymmetric.** It reads back as a STRING above
  `i64::MAX`, but §S2 does not say whether a STRING `observed` is accepted
  when writing. As written, it is SM03.
- **N6. A panic inside `acquire_all` itself** unwinds inside SMYSL,
  before Bund2's guard holds anything. The locks already taken then drop
  and are removed. It is harmless, since nothing has been written, but
  R20's mechanism only begins once `acquire_all` returns. Say so.
- **N7. A forgotten `Lock` leaks its `PathBuf` and `String`**
  (`smysl-graph/src/lock.rs:126-130`). Nothing more is leaked, since a
  `Lock` holds no open file. Worth one sentence, since `mem::forget` reads
  as alarming.
- **N8. Labels within one parse.** The comment the RFC cites at
  `labels.rs:10` goes on to say that "a store built from one parse never
  binds a label twice", and that SMYSL warns `SMY-W054` when it chooses
  (`:10-12`). So criterion 5's constraint is already true of every
  document. The warning should be listed among those §S4 routes through
  D36.
- **N9. "Bund2's lock has `unicode-segmentation` 1.13.3 and `libm`
  0.2.16"** is checked against `Cargo.lock` and holds, but carries no
  citation. Name the file.

## Preservation: what is missing

- **SMYSL has no lock-breaking command** (B1). With R20 A, a library
  Bund2 leaves locked cannot be unlocked by any SMYSL tool. The row
  "SMYSL's lock as a crash notice — Kept" is true of the lock, and silent
  on the remedy.
- **Salience corroboration and hop** (S4).
- **De-duplication in the window** (S1). A record another process
  appended between the open and the locks is appended again.

## Assumptions the RFC makes but does not state

1. **An operator can break a SMYSL lock with a SMYSL tool** (B1).
2. **The library opened before the locks is the library under them**
   (S1).
3. **A Bund STRING is NFC** (S2).
4. **Only a panic leaves a library half-written** (S3).
5. **Attestation parents serve lineage only** (S4).
