## 1. Blocking

### B1 — assumption 33 states the wrong write set for the request cell, and leaves `status_of`'s clear undefined

**What the RFC claims.** Assumption 33, added for the sixteenth review:

> 33. **Only `request_tail` and `take_pending` write the request cell**, which
>     §S6's *Addressing* requires of the compiled mirror. `Interp::request_tail`
>     is the only writer today, and nothing enforces it; an assignment to
>     `pending_tail` that bypassed both would desynchronise compiled code from
>     Tier 0 silently.

§S6's *Addressing* agrees with the first half:

> one **request cell** (§S5, *A call may leave a body to run*), mirroring
> whether a tail request is pending: set by `request_tail`, cleared by
> `take_pending`

**What the RFC says elsewhere.** Three more writers, all in §S5, all
load-bearing and all added by earlier reviews' blockers:

- line 997: "**`status_of` therefore clears the request cell whenever it
  answers an error**" — the answer to the fifteenth review's B1;
- line 1019: "**A refused drain clears the cell.** If the Tier 0 floor refuses
  the drain, the helper clears the request before it returns the exhaustion
  error";
- line 980: "Tier 0 does not leave one behind on a failure, since F96:
  `Interp::invoke` clears a request when the native that filed it fails."

**What the code says.** `Interp` writes `pending_tail` in three places:

- `Interp::request_tail` — `self.pending_tail = Some(body)`
  (`crates/bund2-interp/src/lib.rs`, `request_tail`);
- `Interp::take_pending` — `self.pending_tail.take()` (same file);
- **`Interp::invoke`** — `if r.is_err() { self.pending_tail = None; }` (same
  file, `invoke`), which is F96's fix and which the RFC cites by name.

So "Interp::request_tail is the only writer today" is false on its face, and
false against a line the RFC itself quotes two pages earlier. Assumption 33 is
also internally inconsistent: its heading names two writers and its next
sentence names one.

**Why this is blocking rather than a wording slip.** Assumption 33 exists to
state the invariant that keeps the compiled mirror in step with `pending_tail`.
As written it states an invariant that does not hold, so it cannot catch what it
was added to catch — and the thing it fails to catch is undecided in the RFC:

> **does `status_of`'s clear reach `pending_tail`, or only the mirror?**

Both readings are defensible from the text, and they differ in behaviour:

- **Mirror only.** Then the fifteenth review's B1 is not fixed. The adapter
  calls the native's `NativeFn` directly and never reaches `Interp::invoke`
  (§S8, piece 2; `invoke` is private to `Interp`), so a native that files
  through `Vm::tail_lambda` and then returns `Err` leaves `pending_tail` set.
  Clearing the mirror makes compiled code stop looking, and Tier 0's next
  `take_pending` — inside `Interp::run_to` or `Interp::apply` after the
  compiled body returns — pushes a frame for a body nobody asked for. Under
  `?try` that body runs inside the handler, which is precisely the failure
  criterion 26's second case is written to catch, and the criterion would pass
  while the defect stood.
- **Both.** Then `status_of` is a fourth writer of `pending_tail` and the drain
  helper a fifth, assumption 33 forbids them, and "nothing enforces it" points
  at a rule the design breaks by construction.

The RFC never distinguishes the two. §S5 says only "clears the request cell",
and §S6 defines that cell as a mirror. The one place that could settle it —
the assumption added for exactly this purpose — settles it wrongly.

**What would answer it.** Say, in §S6's *Addressing*, that the cell and
`pending_tail` are written together and name every writer: `request_tail`,
`take_pending`, `Interp::invoke` (F96), `status_of`, and the drain helper's
refusal path. Then restate assumption 33 as the property that actually has to
hold — *no write to `pending_tail` occurs outside that set* — which is the
thing nothing enforces and which a test over `crates/bund2-interp` could
enforce, in the shape `every_reentering_function_is_named` already uses for a
different set. As it stands, assumption 33 asserts a false fact and misses the
true one.

### B2 — §S8's reserve invariant is falsified: `execute_reached`'s data-depth recursion aborts the process from four lines of Bund

**What the RFC claims.** §S8, *The reserve is for the frames between one check
and the next*:

> The Tier 1 floor is one reserve above the bottom of Tier 1's share, so a
> compiled body entered just above it, **and anything it calls without
> re-entering evaluation, stays inside that share**.

and assumption 30, added for the sixteenth review:

> 30. **A native may recurse in Rust between two floor checks.** … A list
>     nested `n` deep therefore spends `n` Rust frames before any floor is
>     asked, and **`STACK_RESERVE` carries them** (§S8). Nothing measures that
>     depth.

**What is true.** `STACK_RESERVE` is 256 KiB (`crates/bund2-interp/src/lib.rs`,
`STACK_RESERVE`). I measured the depth, which assumption 30 says nothing does.
The program builds a nested list with a shallow parse, so nothing here is the
parser's recursion:

```
list
20000 { drop list push } times
"built" println
!
"executed" println
```

Release binary, this machine:

| n | without the `!` | with the `!` |
|---|---|---|
| 15000 | prints `built` | prints `built`, then `executed` |
| 20000 | prints `built`, exits 0 | prints `built`, then **`thread 'bund2' has overflowed its stack` / `fatal runtime error: stack overflow, aborting`, exit 134** |

The `!` is the whole difference at 20000, so the abort is `execute_reached`'s
LIST self-recursion and nothing else. From the 15000/20000 bracket a level
costs roughly 550 bytes, so **`STACK_RESERVE` carries about 470 levels, not
`n`**. Assumption 30's "`STACK_RESERVE` carries them" is not conservative — it
is wrong by whatever margin the program chooses, and the program chooses.

**Why this blocks Tier 1 and not only Tier 0.** The sentence quoted from §S8 is
the argument for why compiled frames never eat Tier 0's part, and criterion 11's
margin `m` rests on it: `m` is computed from `δ_p / c_p` over the re-entering
paths, all of which are measured *per level of evaluation nesting*.
`execute_reached`'s LIST and MAP arms are not evaluation nesting — the RFC's own
assumption 30 says `stack_ok` is consulted only where an arm reaches `Vm::apply`
or `Vm::eval_lambda` — so they are the "anything it calls without re-entering
evaluation" the sentence promises stays inside the reserve, and they do not. A
compiled body entered one byte above the Tier 1 floor that calls `!` on a list
nested 500 deep is already below the floor with no check between.

**And it is a live D37 violation with no defect filed.** §S8's own
*Tier 0 needs the same floor, and needs it now — F85* makes exactly this
argument for `:f { 1 { f } times } register f` — "That is a D37 violation with
no tier involved at all" — and files it as F85. This shape is the same
violation reached a different way, and the RFC files it as an assumption that
"claims nothing about it" instead. CLAUDE.md's disposition rule does not allow
that: an abort is a defect, and D37 is absolute.

**A second and a third path, unnamed anywhere.** Both measured on the same
binary:

- **Teardown.** `list  30000 { drop list push } times  "built" println` prints
  `built` and then aborts with the same stack overflow, exit 134. The program's
  own work has finished; the recursion is the drop of the nested value. The RFC
  names no recursion on that path at all.
- **`bund.eval`.** A 16,000-deep list literal handed to `bund.eval` as a string
  aborts inside evaluation, exit 134. `eval_source` checks `stack_ok` before
  `Vm::apply` (§S8), but the *parse* of the string it was handed happens on the
  same thread with no floor between, and the string is a run-time value.
  RFC-0003 excludes the parser's recursion over a source *file*; this is not
  that. §S8's two floors account for evaluation nesting and for compiled
  entries, and for nothing else, and no assumption names parse depth.

**What would answer it.** File the `execute_reached` case as a defect against
D37, as F85 was, and decide the guarantee: either a floor check inside the
recursion (which is a `stack_ok` in the LIST and MAP arms, cheap and in the
shape `Vm::eval_lambda` already uses), or an explicit depth bound on the
recursion under D39. Then correct assumption 30 to say what the reserve
actually carries — a number, since one is now measured — and either bring
teardown and parse depth into the assumption list or state that §S8's floors
are silent about them, which the Preservation table currently implies but does
not say.

## 2. Significant

### S1 — `reference/.../execute.rs:93-95` is cited for a claim it half refutes, and the Top arm's divergence is unstated

**What the RFC says.** Status line 159–162:

> The fix now turns on **reach**: a lambda the program executes itself is a tail
> position and still files, and a lambda any container reaches runs at once,
> **as the reference does whichever arm reaches it.**

and assumption 29:

> the one that did, `execute_value`, files only when the program executed a
> lambda itself, and runs one at once when a list or a dict reached it (F113,
> completed after the sixteenth review's B1; **the reference does the same at
> `reference/rust_multistackvm/src/stdlib/execute.rs:93-95`**).

**What the cited lines say.** I opened them:

```
93                LAMBDA => {
94                    return vm.lambda_eval(ptr_value);
95                }
```

That is the single LAMBDA arm of `stdlib_execute_base_inline`, reached both from
the top-level pull (`:24-26`) and from the LIST loop's recursion (`:40-48`) and
the dict arm's (`:55-83`). It runs the body **at once in both reaches**. The
reference has no tail-request mechanism to file into.

So the citation grounds the *Nested* half of the sentence and **contradicts the
Top half**: where Bund2 now files, the reference runs at once. Read as written,
"as the reference does whichever arm reaches it" attaches to both halves and is
false of one of them. This is CLAUDE.md's recurring shape — a required
deviation written as a non-deviation, so no criterion covers it.

The divergence is defensible and is almost certainly unobservable in ordering,
because §S5 says "a request means *run this before the next value*". But the
RFC never says that here, and the reason lives only in F113's register entry —
which itself cites **RFC-0003 §S4a** twice for "the body runs after the native
returns, costing no Rust frame". §S4a is *Context depth is represented, so
`endcontext` can refuse*; it is about `endcontext` and F60, not about tail
requests or heap-cost recursion. So the one place that argues the Top arm is
right argues it from the wrong section.

**What would answer it.** Cite `:93-95` for the Nested half only. State the Top
half as what it is — Bund2 files where the reference runs at once, so that a
program's own `{ … } !` costs no Rust frame — and ground it on §S5's
"run this before the next value" plus RFC-0003's frame loop, with the section
that actually says so. Correct F113's `§S4a` citations while you are there.

### S2 — criterion 11's `execute_reached` case is not checkable

§S8 line 2107–2109:

> Its LIST and MAP arms also recurse into themselves on the depth of the value,
> with no floor check between those frames, so **criterion 11 measures its
> deepest shape** (assumption 30).

Assumption 30 closes with "Nothing measures that depth." A criterion that
measures "its deepest shape" over a recursion with no bound names no number and
admits no failing outcome — the deepest shape is whatever the test author
builds, and a deeper one always exists. This is the shape the acceptance-criteria
preamble warns about: "7 read 'shows improvement', and nothing fails that."

Criterion 11 itself (lines 2885–2888) says only that the run reports `c_p` and
`δ_p` per path. For `execute_reached` that is well defined for its two
*evaluation* re-entries, and undefined for the self-recursion, whose cost is
per level of *data* rather than per level of evaluation and so does not enter
`m` at all.

**What would answer it.** Once B2 is decided, criterion 11's case becomes a
number: the depth at which `execute_reached` reaches the Tier 0 floor, reported
in both builds, with the requirement that it reports rather than aborts — the
same shape the `loop` axis already has. As written the case cannot fail.

### S3 — `PROMOTABLE.txt`'s header line, which criterion 28 cites as its authority, mis-states its own arithmetic

Criterion 28:

> **Met**, 2026-09-10, when 178 of 205 fixed-effect natives were listed;
> **218 of 263 after D55 and F111 (the list's own header line)**

The header line reads:

> `# 218 of 263 fixed-effect natives reached; 8 of them observe beyond their operands.`

It is generated at `crates/bund2-stdlib/src/lib.rs` from
`promotable.len()`, `natives.len()` and `reached.len() - promotable.len()`, and
`promotable` is `reached` **filtered to exclude** the observers. So 218 is the
*promotable* count, not the reached count, and the 8 observers are precisely
*not* "of them" — `reached` is 226. The file agrees with that reading: 218 data
lines, and the eight observers appear only as `# observes:` comments.

The RFC's own sentence says "listed", which is right. But it quotes the header
as its authority, and criterion 14's "the flagged natives are listed in
`PROMOTABLE.txt` as comments" sits beside criterion 28's "the natives some run
brought to `Ok` are **exactly those** `PROMOTABLE.txt` lists" — two sentences
that only reconcile if the reader already knows a comment is not a listing. A
reader checking the number against the file gets 218 = 210 + 8 and cannot tell
which.

**What would answer it.** A one-line fix to the generated header
(`218 promotable of 226 reached, of 263 fixed-effect natives; 8 reached natives
observe beyond their operands and are never crossed`), and criterion 28 quoting
the corrected line.

### S4 — D55's recorded status contradicts what criterion 28 claims

`docs/registers/decisions.md`, D55:

> - Status: **RESOLVED — built; `PROMOTABLE.txt` awaits regeneration by the
>   repository owner.**

The list has since been regenerated — its header carries D55's and F111's
figures — and criterion 28 treats it as current and **Met**. The register is
append-only but a status may change, and this one did not. A session reading
D55 first would conclude the list criterion 28 rests on has not been produced.

**What would answer it.** Change D55's status line; nothing else.

## 4. Claims that need a citation and lack one

**4.1 — "`status_of` clears the request cell" has no definition of what the cell
is at Tier 0.** B1. Every other cell in §S6's *Addressing* is defined by the
Tier 0 state it mirrors and by its writers. This one is defined that way too,
and then written by two more things.

**4.2 — assumption 30's "`STACK_RESERVE` carries them" carries no number.** B2.
It is the only quantitative claim in the assumption list with neither a
measurement nor a derivation beside it, and it is false.

**4.3 — "the frames between one check and the next may run up to one reserve
past it"** (§S8, the undeclared-thread arithmetic) is the same claim in the
embedder case, also unmeasured, and B2's measurement contradicts it there too:
an embedder on a default 2 MiB thread has less room, not more.

**4.4 — "An embedder's native can still file twice, and nothing detects it"**
(assumption 29). True as far as I can tell, but the effect audit *does* record a
tail request filed under a fixed effect (`Interp::request_tail`'s
`audit_breach`), so the claim needs to say that the audit catches the
fixed-effect case and not the opaque one.

## 6. Preservation analysis — what it does not enumerate

The table is thorough and each row names a guard. Three behaviours the design
can change are absent:

1. **A lambda reached through a container now runs synchronously inside
   `execute_reached` where it used to be filed** (F113). The consequence is not
   a wrong answer — it is a Rust frame per container level per lambda, on a
   path whose own recursion has no floor check. No row names it, and the row
   for requests still enumerates "`!` on a lambda, `if`, `ifthenelse`, a lambda
   call" as the things that file, which is now true only of a lambda the
   program executes itself.
2. **A value's construction and its teardown recurse on data depth.** B2's
   second measurement: a program that produced correct output aborts during
   drop. No row, and no assumption, names either.
3. **The parse inside `bund.eval` and `use` recurses on the depth of a
   run-time string.** B2's third measurement. The `eval_source` row exists for
   its evaluation cost; its parse cost is named in §S8's `c_p` prose and its
   parse *depth* nowhere.

Rows 1 and 3 are Tier-0-visible today. Row 2 is too. None of them is a tier
divergence, which is why criterion 2 cannot move on them — the same argument

enumerate what the design could change, and §S8's floors are part of this

## 8. What the RFC assumes and does not state

Beyond the thirty-three it lists:

1. **That `status_of`'s clear of "the request cell" reaches `pending_tail`, not
   only the compiled mirror.** B1. This is the one that decides whether the
   fifteenth review's blocker is closed.
2. **That parse depth inside `bund.eval`, `!!` and `use` fits in the thread's
   stack.** Measured false at 16,000. §S8's two floors do not cover it and no
   assumption names it.
3. **That constructing and dropping a value does not recurse past a floor.**
   Measured false at 30,000: the drop of a nested list aborts a program that
   already printed its output.
4. **That `Reach::Top` filing rather than running at once is unobservable.**
   The RFC asserts the reference "does the same" (S1) rather than arguing the
   equivalence, so the assumption is not merely unstated — it is stated as a
   fact about the reference that the reference does not support.
5. **That `debug.display_stack`'s `Debug` rendering of a deep value is
   bounded.** It survived 20,000 levels here, so this one is only unmeasured
   rather than false. The report path's `BundValue::summary` is bounded by
   design (CLAUDE.md, D36); the `--raw-values` and `debug.display_stack` path
   is not, and §S5's "an error's report shows the stack Tier 0 would have
   shown" reaches it.
6. **That the effect audit's record of a tail request under a fixed effect
   does not overlap `status_of`'s clear.** `request_tail` calls `audit_breach`
   before it assigns; nothing says whether a cleared request is also un-recorded,
   which matters for criterion 24's counts if a native files and then fails
   under the audit.
