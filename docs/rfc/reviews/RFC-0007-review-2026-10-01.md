## Blocking

### B1 — `recv` on an empty channel does not error. It pushes NODATA

The RFC says so four times: the table ("**Errors on an empty channel rather
than blocking**"), the second "measured fact" ("an empty channel is an immediate
error (`bus/crossbus.rs:144-147`)"), the Preservation row, and criterion 1.

The cited lines are the word's call to `bus_pull` and its error wrapper. What
`bus_pull` does with an empty channel is one call deeper:

```rust reference/Bund/src/stdlib/functions/bus/mod.rs:129-131
    if r.is_empty() {
        return Ok(Value::nodata());
    }
```

The error is for a channel that **does not exist** (`mod.rs:124-127`,
`bus::internal::pipe no pipe: {k}`). The oracle:

| program | output |
|---|---|
| `"nochan" recv println` | `RECV returns error bus::internal::pipe no pipe: nochan` |
| `"chan" bus.data println "chan" recv println` | `false`, then `NODATA` — exit 0 |
| `"chan" 42 send drop "chan" recv drop "chan" recv println` | `NODATA` |
| `"in" recv println` | `NODATA` |

The last row is a second omission: `pipes_init` creates two channels, `in` and
`out`, before any program runs (`mod.rs:43-49`, called at `:151`). They are part
of the contract and the RFC does not mention them.

So there are three states — absent (error), empty (NODATA), has data — and the
RFC has two. The commonest polling shape, `bus.data` then `recv`, lands in the
state the RFC gets wrong, *because* `bus.data` creates the channel. An
implementation built to criterion 1 errors where the reference pushes a value.

"The local bus is goldenable" survives: `recv` still does not block. The
contract it is goldenable *against* is the wrong one. This is the
"follow the call one level further" failure CLAUDE.md names.

### B2 — A received value has the sender's id and stamp. The RFC asserts the opposite

§C2: "**A sent value is not the value that arrives.** … `recv` yields an *equal*
value with its own identity … A program comparing `.id` across the bus sees two
values." Preservation: "a received value is equal and not identical." Criterion
3: "Its `.id` differs from the sent value's, asserted rather than assumed."

`bus_pull` returns what `Value::from_binary` returns (`mod.rs:134-137`).
`from_binary` returns the deserialised struct unchanged
(`reference/rust_dynamic/src/bincode.rs:52,71`), and `id` and `stamp` are
ordinary serialised fields (`reference/rust_dynamic/src/value.rs:15-18`). The
two paths that *do* mint a new identity say so explicitly — `dup`
(`dup.rs:11`, `res.id = nanoid!()`) and `Value::unwrap` (`bincode.rs:95`). The
bus has no such line. The oracle:

```
$ bund eval --eval '42 debug.display_stack "chan" swap send.quick "chan" recv debug.display_stack drop'
│ Value { id: "5FPG7nkKL1g1qfDtyQJaJ", stamp: 1790836841633.0, dt: 2, … data: I64(42) … }
│ Value { id: "5FPG7nkKL1g1qfDtyQJaJ", stamp: 1790836841633.0, dt: 2, … data: I64(42) … }
```

Same for a STRING and for a LIST, whose elements keep their ids too.

The RFC's own sources say this. D20: "`from_binary` restores them verbatim"
(`decisions.md:952-953`). D77 is cited as "the property that sank the
encoded-stream bundle", and D77's property is the reverse of the one claimed:
serialisation *freezes* identity, so "a literal would arrive at run time
*already stamped*" (`decisions.md:4225`). Materialising an id on `send` and restoring it on `recv`
yields the **same** id.

**JSON is the one exception**, and the RFC does not mention it: `to_binary`
re-wraps a JSON value (`bincode.rs:9-28`) and `from_binary` rebuilds it through
`Value::json` (`:54-69`), so a JSON value does arrive with a fresh identity
(D20's "corrected scope", `decisions.md:982-990`).

Consequences:

- Criterion 3 asserts a behaviour the oracle does not have. Implemented as
  written it is an unapproved deviation that **no golden would catch**, because
  the capture normalises ids (`xtask/src/golden/mod.rs:168`).
- The error is inherited from **D86** — "what comes out of `recv` is an *equal*
  value with its own identity … and that is the reference's behaviour"
  (`decisions.md:3604-3608`). D86 is RESOLVED and the register is append-only,
  so it needs a correcting entry before this RFC can consume it.
- `.id` is not callable on a scalar in the reference (`42 .id` →
  `Inline .id not registered`), so "a program comparing `.id` across the bus"
  is only expressible for an OBJECT. Whatever checks criterion 3 has to say how.

What Bund2 *does* change here, and the RFC should say instead: D1/D2 make
identity lazy, so `send` is where an untouched value's stamp is first sampled.
That is D20's approved deviation, and it is about *when*, not *whether the id
matches*.

### B3 — The eight words are not in scope. D28 defers them, and the RFC does not cite D28

"Eight words, all unimplemented in Bund2, **all in the in-scope set**."

They are not:

- `xtask/src/corpus/classify.rs:476-482` — the whole directory
  `Bund/src/stdlib/functions/bus` is a `Deferral { decision: "D28", reason:
  "zenoh distributed bus — not essential" }`.
- Coverage's `in_scope` is exactly the words with no deferral
  (`xtask/src/corpus/mod.rs:543-549`). The 497 contains no `bund/bus` word; the
  "uncovered by subsystem" list has no `bund/bus` row.
- D28 names `bund/bus` among the subsystems feature-gated **off by default**
  (`decisions.md:1310-1313`), and RFC-0000's feature policy repeats it
  (`RFC-0000-architecture.md:255-259`). RFC-0001 relies on it: "all in `bus`,
  which D28 defers" (`RFC-0001-value.md:245-246`).
- `docs/arity.md:102-103,403-404,425-428` records all eight as "not probed:
  effectful, out of scope, or terminates".

D28 says `Blocks: nothing`. This is the subject-search miss CLAUDE.md warns
about, for the third RFC running.

Consequences:

- **Criterion 5 cannot be met.** "Coverage moves by eight" needs the eight in
  the denominator, which makes it 505. That is a scope change, and the scope is
  D28's.
- **Criteria 1 and 2 need a golden the suite will not admit.** A program is in
  the conformance suite when it is hermetic *and* has no deferred word
  (`xtask/src/corpus/mod.rs:1341`). The bus words fail both tests today:
  deferred under D28, and `Effect::Bus` (`classify.rs:225`). The RFC lists the
  effect classification as an *open question* (its last bullet), so two
  acceptance criteria rest on an item the RFC has not settled.
- D28's recorded reason is wrong for these eight — they are crossbeam, not
  zenoh, which D86 established. That is a good argument for splitting the
  deferral: `crossbus.rs` in, `globals.rs` out. It is still a decision. It adds
  `crossbeam` to the default build, changes RFC-0000's feature list, and moves
  the completeness denominator. D86 says "in scope" in passing
  (`decisions.md:3587`) without amending D28.

This needs an entry in `docs/registers/decisions.md` before the criteria can be
written. The RFC should then say which crate the words land in and under which
feature.

### B4 — Nothing in the RFC, and no criterion, involves a second VM

The title is concurrency. The Motivation says "this RFC is (a) and (b)" —
`run()` as an `async fn`, and many VMs on a thread pool. The Design section
specifies neither:

- no `async fn`, no executor, and no statement that (a) is dropped;
- no API by which an embedder creates a VM on a thread — §C6 says an embedder
  does it and stops there;
- no statement of where the channel map lives, so how two VMs come to share it
  (S10);
- nothing on a VM ending: its channels, its exit code, its `Reporter`.

`crates/bund2-async` exists, described as "Executor integration and async
native words. Feature-gated. See RFC-0007", and RFC-0000's crate table gives it
to this RFC (`RFC-0000-architecture.md:195`). The RFC does not mention the
crate.

**All seven criteria pass with one VM and a `VecDeque` per name.** That is not
an accident of the criteria; it is what the reference is. `BUND` is one global
VM (`RFC-0002-symbols-and-words.md:160-167`), and no reference crate spawns a
thread. In the reference, `send`/`recv` is a queue from a VM to itself.
Crossbeam is unobservable there.

So the "preservation contract" preserves a single-VM queue, and the concurrent
case — the one D84, D85 and D86 are about — has no reference behaviour, no
design text, and no check. The RFC needs either:

1. a design for the multi-VM case and a criterion that runs it (two `Interp`s
   on two threads, one `send`s, the other `recv`s, named test), or
2. an explicit statement that this RFC is the bus-word contract only, with the
   embedding API deferred — and then "(a) and (b)" comes out of the Motivation.

It also weakens "three independent arrivals at one design". The reference did
not arrive at an actor model; it arrived at a named queue. D84, D85 and D86
were taken by one owner on one day and cite each other.

### S2 — The error texts are part of the contract and none is listed

CLAUDE.md's second way out is "write the real error arm". The arms:

- `Stack is too shallow for inline {P}` and
  `Workbench is too shallow for inline {P}` (`crossbus.rs:45,50,53,123,128`).
  In `send.` the stack is checked **before** the workbench (`:49-54`).
- **`{P}` is `SEND` for `send.quick` and `SEND.` for `send.quick.`** — the
  quick forms reuse the plain prefixes (`:177,182`).
- `{P}: No object for sending was provided` (`:63,102`);
  `{P}: No channel name discovered on the stack` (`:67,106,138`).
- **`BUS.DATA: Error name casting: {err}`** — in all five functions, so `send`
  and `recv` report a bad name under `bus.data`'s prefix (`:35,71,110,142`).
  Oracle: `42 "chan" send` → `BUS.DATA: Error name casting: This Dynamic type
  is not string`, **with both operands consumed**.
- `Stack is too shallow for BUS.DATA`,
  `BUS.DATA: No channel name discovered on the stack` (`:27,31`);
  `Can not determine current stack name` (`:19`).
- `{P} returns error {err}` wrapping `bus::internal::pipe no pipe: {k}`,
  `bus::internal::pipe error: {err}`, `Error enveloping data: {err}`,
  `Error converting from binary: {err}`,
  `bus::internal::pipe {k} can not recv: {err}` (`mod.rs:76-146`,
  `crossbus.rs:75,114,146`).

Each is as checkable as the positive paths. Criterion 1 names none.

### S3 — `--noio` disables all eight words

`crossbus.rs:208-216` registers `stdlib_bund_bus_disabled` under each of the
eight names when `cli.noio` is set; it fails with
`bund BUS functions disabled with --noio` (`:197`). Oracle-confirmed for `send`
and `bus.data`.

Bund2 has the mechanism (`crates/bund2-stdlib/src/host.rs:443`) and a bundle
carries the flag (`crates/bund2-cli/src/bundle.rs:277`). The RFC has no row for
it in Current behaviour or Preservation, and no criterion.

### S4 — §C3's second layer does not exist: no Bund word makes an ENVELOPE

"`wrap`/`unwrap` are program-visible words a Bund author may use to hold a
serialised value *as a value*."

The Bund words `wrap` and `unwrap` are registered at
`reference/Bund/src/stdlib/functions/oop/value_class.rs:168-169`. They are OOP
words: `wrap` stores a value in an OBJECT's `.data` field, `unwrap` reads it
back (`value_class.rs:95-123`). Neither serialises. Bund2 already has them, in
`crates/bund2-stdlib/src/oop.rs:733-735`.

`Value::wrap()` — the Rust method at `reference/rust_dynamic/src/bincode.rs:79`
— has **no caller** in `Bund`, `rust_multistackvm`, `rust_multistack` or
`bundcore`. ENVELOPE values are built only by the image words, through
`make_envelope` over raw pixels (`functions/image/image_class.rs:36,48,100`),
and `image` is D28-deferred.

So:

- §C3 describes two layers and there is one.
- The alternative "`send` accepting an ENVELOPE without re-serialising" is
  moot.
- The research's "a mechanism the language already has a word for"
  (`01-extensibility-async.md:284-288`) is false and needs an ERRATA entry.
- D11 carries the same sentence (`decisions.md:490-491`), which is where the
  RFC's "(D11)" comes from. That needs a register note too.

### S5 — Criterion 4 is a deviation, filed as preservation

"A program too deep to serialise is refused at `send`."

The reference refuses nothing: `to_binary` is a bare `bincode2::serialize`
(`bincode.rs:30`). Oracle: a list nested 257 deep, and one 300 deep, both
`send` → `true` and `recv` cleanly.

`MAX_WIRE_DEPTH` is F118's bound, taken for `save.*`/`load.*`, where a value
that cannot be read back is the worse failure. Applying it to `send` is a new
observable difference at depth 257. It may well be the right call. It needs a
row in Preservation marked **Changed**, a disposition (F118 extended, or a
decision), and an entry in `tests/golden/DEVIATIONS.txt` if a probe captures
it. "A program too deep" should read "a value".

### S6 — "It departs nowhere today" is false in five places

The header says the research is followed and ERRATA records any departure.
ERRATA has no entry for `01-extensibility-async.md`. The departures:

1. **§2.1(c), §2.4, §2.7** — "achievable at Tier 0", "Await inside a Tier-0
   word: yes" (`:230,298-300,389`). D84 says no. The RFC states this in its
   Motivation and still claims no departure.
2. **§2.4's `NativeKind`** (`:302-308`) defines all three kinds: `Sync` "runs to
   completion, must not block"; `Blocking` "must be dispatched to
   `spawn_blocking`"; `Async` carries a future. So "this RFC defines their
   meaning for the first time rather than inheriting one" contradicts the
   document it follows. §C5's `Blocking` — parks its own VM's thread, nothing
   dispatched — is a different definition.
3. **§2.3's envelope word** (`:284-288`) — S4.
4. **§2.6, shared compile service** — "required under concurrency"
   (`:376-378,392`); a per-VM `JITModule` is called "Bad" (`:368-370`). Bund2
   built per-`Interp`: "one compiled cache, one `JITModule` … per `Interp`"
   (`RFC-0005-cranelift-tier.md:2492-2494`). The roadmap puts "tier pinning,
   shared compile service" in this RFC's row (`05-rfc-roadmap.md:96`). The RFC
   says nothing about either. Tens of VMs is tens of code-memory caps, and that
   number is not stated.
5. **§2.3's transport** — "tasks on a `LocalSet` … channels carrying envelopes"
   (`:290-292`). The RFC takes a thread per VM and raw bytes. Reasonable, and a
   departure.

### S7 — `Blocking` is defined with no member and no reader, which is what §C5 declines for `Async`

§C5 defines `Blocking` as "the host words, `recv` if it ever gained a blocking
form, a fetch". No word is re-marked: all 25 registrations in
`crates/bund2-stdlib/src/host.rs` are `WordKind::Sync`, and the RFC proposes changing
none. Criterion 7 then requires that nothing read the field. A definition with
no writer and no reader is "a vocabulary with no consumer", the RFC's own
reason for leaving `Async` alone.

Two further problems:

- `WordKind` is in `bund2-api`, "the one crate with a stability guarantee"
  (`RFC-0002-symbols-and-words.md:577`). An embedder can register an `Async`
  word today. "Deliberately left undefined" in a stable enum needs a
  disposition: remove the variant, or document it as reserved and say what the
  runtime does with one (today: runs it as `Sync`).
- Under §C5's definition, a `Sync` word "returns without yielding the thread".
  `input` and `password` are declared `Sync`
  (`crates/bund2-stdlib/src/terminal.rs:202,204`) and park the thread until a
  person types; `sleep.seconds` and the file words likewise. Either they are mis-declared from the moment
  this RFC is accepted, or the definition is not the one in use.

### S9 — The distributed half's contract is not enumerated

§C4 defers zenoh "with its boundary stated", and names "the globals path's
semantics" and `--distributed`. The reference's distributed surface is larger,
and a deferral should list what it defers:

- three words: `global`, `global*`, `?global` (`globals.rs:109-111`), each
  failing without `--distributed` with `BUND must be in distributed mode. You
  shall pass --distributed to CLI` (`helpers/zenoh/putget.rs:45`);
- two CLI subcommands, `bus` and `cluster` (`reference/Bund/src/cmd/mod.rs:96-97,172`),
  with four key-prefix options and their environment variables (`:192-201`);
- `ZENOH`'s initialiser calls `std::process::exit(10)` on a bad config or a
  failed connect (`mod.rs:29,36`) — an exit Bund2's no-panic rule cannot
  reproduce as written;
- `debug.display_distributed_info`, which RFC-0008 owns and which locks the
  same session.

"Zenoh is a large dependency" has no citation; D28 is the ground
(`decisions.md:1304-1309`). D40 is cited as "a transport's dependencies", and
D40 is about `string.grok`'s C dependency — the precedent holds, the paraphrase
does not.

### S10 — Process-global state, once there is more than one VM

The RFC assumes VMs share a channel map and does not say how.

1. **Where the map lives.** The reference's `PIPES` is a process-global
   `lazy_static` (`mod.rs:15-20`). If Bund2's is a `static`, every `Interp` in a
   process shares channels by name — including the `Interp`s `cargo test` runs
   on parallel threads, so two unit tests using `"chan"` interfere. If it is a
   handle, the embedder API has to pass it, and that API is not designed (B4).
2. **The non-blocking guarantee depends on the map lock.** The reference tests
   `is_empty()` and calls the blocking `recv()` under one `PIPES` lock
   (`mod.rs:123-132`), so no other consumer can take the message between the
   two. With one VM that is trivially safe. With two consumers and a receiver
   cloned out of the lock, the second `recv()` blocks forever. "`recv` does not
   block" must be stated as an invariant with its mechanism (`try_recv`, or the
   lock held), and checked.
3. **`PIPES.lock().unwrap()`** — eight sites. Bund2 cannot unwrap. The RFC
   should say what a poisoned bus reports.
4. **State Bund2 already holds per process becomes shared between VMs**:
   `MT`, `CHACHA`, `GENERATORS` (`crates/bund2-stdlib/src/random.rs:41,45,169`)
   and `ARGS` (`host.rs:62`). A seeded random sequence in one VM is perturbed
   by another. In the reference each node is a process and owns its generator.
   That is a behaviour the design changes, and Preservation does not list it.
5. **Per-thread state each VM thread must set up**: the stack region
   (`crates/bund2-interp/src/lib.rs:422`; RFC-0005's embedder rule,
   `RFC-0005-cranelift-tier.md:3426-3430`) and the symbol interner
   (`crates/bund2-value/src/lib.rs:433`). D44 is listed as consumed and the body
   never uses it. Sixty-four VMs at `EVAL_STACK` each
   (`crates/bund2-cli/src/main.rs:88-94`) is a reservation worth one sentence.

## Preservation analysis — what is missing

Rows the table has and gets wrong: `recv` (B1), the payload's identity (B2),
`send.`/`recv.` (S1). Rows it lacks:

1. Three channel states, not two; `recv` on an absent channel versus an empty
   one (B1).
2. The pre-created `in` and `out` channels (B1).
3. Identity and stamp **preserved** across the bus, JSON excepted (B2).
4. The workbench forms' operand sources and `bus.data.current`'s arity (S1).
5. Every error text, the `BUS.DATA` prefix on `send`/`recv` name errors, the
   quick forms' prefixes, and that a failed name cast consumes both operands
   (S2).
6. `--noio` (S3).
7. A value deeper than 256 — **changed** (S5).
8. A LAMBDA can be sent and executed on receipt (oracle:
   `"chan" { 1 2 + } send.quick "chan" recv ! println` → `3`). Code crosses the
   bus. Worth a row now, because under zenoh it is remote code, and `--noeval`
   does not obviously cover it.
9. The received value's `stack` tag is rewritten by the receiving push. With
   one VM this is invisible; with two it is where a value changes owner.
10. Shared random-generator and `ARGS` state between VMs (S10).
11. `WordKind::Async` in a stable API with no meaning (S7).
12. `global`, `global*`, `?global`, the `bus` and `cluster` subcommands — out
    of scope, but named (S9).
13. D28's scope and RFC-0000's feature list — changed, if B3 is resolved the
    way the RFC assumes.
14. Per-`Interp` `JITModule` under tens of VMs (S6, item 4).

## Consistency with accepted RFCs and ERRATA

- **RFC-0000** (Accepted): `bus` is gated and off (`:255-259`); `bund2-async`
  "reconciles with the existing bus layer per RFC-0007" (`:195`). The RFC
  treats the words as in scope and never names the crate (B3, B4).
- **RFC-0001** (Accepted): "all in `bus`, which D28 defers" (`:245-246`); and
  "RFC-0007 inherits the question" of `BundValue` crossing a thread
  (`:825-826`). The second is answered — bytes cross, values do not — and the
  RFC should say it is discharging that hand-off.
- **RFC-0002** (Accepted): "per-stack dispatch, when RFC-0007 needs it, is the
  single order with the stack as a parameter" (`:68-71,255-259`). The RFC does
  not say whether it needs it. It appears not to; say so, so the forward
  constraint is closed rather than left hanging.
- **RFC-0003** (Accepted): "async (RFC-0007) gets a suspendable one"
  (`:519`). D84 declines the suspension. No conflict, but RFC-0003's stated
  benefit is not being taken, and a line would record that.
- **RFC-0005** (Proposed): one `JITModule` per `Interp` (`:2492-2494`) against
  research §2.6 (S6).
- **ERRATA**: no entry for `01-extensibility-async.md`. Five are owed (S6).
- **Registers**: D86 (`:3604-3608`) and D11 (`:490-491`) each carry a claim the
  reference contradicts (B2, S4). Both need appended corrections. D28's reason
  for `bus` is wrong for `crossbus.rs` (B3).

## What the RFC assumes but does not state

1. **The eight words are in scope.** They are D28-deferred (B3).
2. **A program using them can be a golden.** Not while they are `Effect::Bus`
   and deferred (B3).
3. **The reference's bus connects VMs.** It connects one VM to itself (B4).
4. **A channel map shared by every VM in the process**, with no statement of
   where it lives or who can reach it (S10).
5. **`is_empty` then `recv` stays atomic with more than one consumer** (S10).
6. **Serialisation mints identity.** It preserves it (B2).
7. **`wrap` is the ENVELOPE word.** It is an OOP word (S4).
8. **An embedder API exists** to start a VM on a thread, declare its stack
   region, hand it a program, and collect its exit and its diagnostics (B4).
   D36's `Reporter` is per `Interp`; tens of them writing to one stderr is
   unaddressed.
9. **`exit` in one VM** — `request_exit` is per `Interp`. Whether it ends the
   VM or the process is not said.
10. **Channel lifetime.** The reference never removes a channel. With
    long-lived processes and computed names, the map grows without bound —
    a second unbounded quantity beside the one §C2 names.
11. **Channel names are a flat process-wide namespace** shared with
    `bus.data.current`'s stack names, so a stack called `in` collides with the
    default channel.
12. **A received LAMBDA is compiled in the receiver.** D42 keys the cache on
    `Rc` identity, which does not cross.
13. **Probes do not move conformance** (S8, criterion 6).

## Disposition

**Not ready to propose**, and not for the reasons the header gives. §C5 and §C6
are honest open questions. The blocking problems are elsewhere:

- two of the "three measured facts" are contradicted by the oracle (B1, B2),
  and one of them is asserted by a criterion and inherited from a RESOLVED
  decision;
- the RFC's scope rests on D86's "in scope" against D28's deferral, which is an
  unmade decision (B3);
- the document specifies a single-VM queue and calls it concurrency (B4).

B1 and S1–S3 are corrections the bus files settle on a re-read. B2 and S4 need
register corrections first. B3 needs the owner.
