## Findings, most serious first

### 1. Bund2's `graph.path` Title-cases its operands; the reference does not. The RFC builds on the divergence and calls the seven words "preserved exactly"

The reference looks both of `graph.path`'s node operands up exactly as
given: `t.get(&start_node)` after a bare `cast_string`
(`getpath.rs:53-60`), and the same for the end (`getpath.rs:65-71`). No
`make_nodename` is called. Bund2 maps both through `node_name` first
(`crates/bund2-stdlib/src/graph.rs:228`, `:238`).

Run against both engines:

```
:c :a [ [ :a :b 1.0 ] [ :b :c 2.0 ] ] [ :a :b :c ] graph! graph.path println
```

- oracle: `GRAPH.PATH: unknown start node: a`
- bund2: `{ found=true ::  path=[ A ::  B ::  C :: ] ::  weight=3.0 :: }`

No register records this. The only `graph.path` defect is F101, about
node and edge reading, not operands. No golden catches it: the corpus and
the probe use single capital letters, which Title-casing leaves alone.

Three things in the RFC depend on it:

- R:37-38 states "Node names are Title-cased before anything looks them
  up". That is false for the operands of `graph.path` (`getpath.rs:57,69`)
  and of `graph.paths` (`dijkstra.rs:52-58`). The second case is recorded
  in Bund2 (`graph.rs:453-456`, test `the_start_node_is_not_title_cased`)
  and in D192.
- R:44 says "Bund2 reproduces all seven words", and R:105-107 says the
  seven are "preserved exactly, except F17's order". Neither is true while
  this divergence stands.
- R:75 "A node operand is Title-cased" is the new words' rule. D192's
  build note justifies it "as `graph.path`'s are"
  (`docs/registers/decisions.md:3717`). That precedent is Bund2's bug, not
  reference behaviour. The rule can still stand on its own merits, but it
  needs a reason that does not rest on it.

Under CLAUDE.md, this is a Bund2 bug to fix, or an unplanned deviation to
take to `decisions.md`. The RFC cannot be Accepted with "preserved
exactly" over it. The fix also changes the RFC's own family. If
`graph.path` returns to the reference's behaviour, `graph.paths` and
`graph.path` both look up as given, and the twelve new words are the
only graph words that Title-case an operand. If D192 keeps Title-casing,
that inconsistency inside one family needs stating as a deviation from
the family's convention.

### 2. R:39-41 misstates the edge rule. Four or more elements are not refused

R:39-40: "two elements weigh 100.0, exactly three take the third as a
FLOAT, and anything else is refused (`make_graph.rs:125-133`)". The cited
lines say otherwise. `if rel.len() == 3` takes the weight (`:125-130`).
The `else` gives 100.0 (`:131-133`) for **every** length that passed
`rel.len() >= 2` at `:105`, so four or more elements weigh 100.0 and the
extra elements are ignored. Only fewer than two is refused (`:134-135`).
Separately, a non-LIST edge fails its cast at `:137`.

D192 §3 states the rule correctly (`decisions.md:3686-3687`, "100.0 when
an edge has two elements or more than three"), as do F101, the code
comment in `read` (`graph_algorithms.rs:123-124`), and the test
`each_refusal_section_s4_names` ("Four elements weigh 100.0").
The RFC contradicts its own ruling, implementation and test. Since
"Current behaviour" is the preservation contract (template, `0000-template.md:17-20`),
this is the section where the error does most harm.

### 3. "A graph reads the same to every word" is not true of the reference, so criterion 2 cannot check it

R:73-75 says the new words read a graph "as the reference's words read it
… a repeated edge replacing the earlier one as `algos` does". Criterion 2
says "A graph reads the same to every word". The reference's seven words
use two different readers, and they disagree:

| | `graph.path` (`make_fast_graph`) | `graph.paths`, `.allpath`, `.transitiveclosure` (`make_graph`) |
|---|---|---|
| weight | `w as usize`, so 1.9 reads as 1 and −1.0 as 0 (`make_graph.rs:64`) | `f64` as given (`:130`) |
| repeated edge | the **lowest** weight kept: `freeze` sorts by from, to, weight and `dedup_by` keeps the first (`fast_paths-1.0.0/src/input_graph.rs:136-142,148-161`) | the **last** given, replacing the earlier (`algos/src/cs/graph.rs:108-113`) |

The RFC chose the `algos` reader without saying a choice existed.
`the_reader_agrees_with_build_algos` compares against `build_algos` only,
so it checks agreement with three of the four algorithm words, not with
"every word". Either restate criterion 2 as "reads as `graph.paths`
does", and say in "Current behaviour" that `graph.path` reads
differently, or justify the stronger claim.

The criterion's 300 graphs are also narrower than "a graph":
`random()` (`graph_algorithms.rs:~1278-1296`) builds distinct
single-capital node names, integral weights of at least 1, and only
three-element edges. Duplicate nodes, Title-casing that changes a name,
two- and four-element edges, and every refusal path are outside it.

### 4. F17's fix has no criterion for two of its three words, and the one cited does not check order

Criterion 5 (R:136-137) cites
`each_form_of_several_operands_takes_the_operand_d111_names`
(`wb.rs:446-458`). That test compares `graph.paths.` with `graph.paths`
row for row. It establishes that the two forms agree, not that either is
in node order. It catches a missing sort only by chance, when two
`HashMap`s happen to iterate differently. For three nodes they agree one
time in six.

`graph.allpath` and `graph.transitiveclosure` are in F17's disposition
(`defects.md:533-537`, "by the first node and then the second for the
two pair words"), and their sorts exist (`graph.rs:507`, `:538`). No
criterion names a test for either, and no test asserts their row order.
S3 (R:79-83) does not state the pair rule ("first node, then second")
that F17 records.

A checkable criterion: for a graph whose `nodes` list is not alphabetical
(for example `[ :C :A :B ]`), each of the three words answers rows in
exactly that order, the pair words ordered by `from` and then `to`. Run
it more than once in one process.

Side note, outside the RFC: the doc comment on `graph_paths` still says
"The rows come in `HashMap` order, which changes from run to run, as the
reference's do" (`graph.rs:457-458`). Twenty lines below, the code sorts
them (`:476-477`).

### 5. Criterion 1 names checks that do not check effects

"Registered with fixed effects — `bund2 words`". `bund2 words` prints
names only ("every name a program can call, one per line"), not effects.
The honesty test it names
(`no_native_takes_a_stack_name_in_an_operand_the_palette_leaves_at_seven`,
`lib.rs:616-635`) lists `graph.maxflow` in `UNVARIED`. That is an
**exemption**: it says the audit does not vary the third operand. It is
not a check of the declared effect.

The effect audit that does check declared effects,
`every_fixed_effect_native_keeps_its_pair_over_the_promotable_palette`
(RFC-0005 criterion 28, `lib.rs:770-787`), never brings any of the 24 new
names to `Ok`. Every one is `# not reached` in
`tests/golden/PROMOTABLE.txt:398-429`. What does confirm `n → 1` for each
word is `each_form_holds_the_graph_on_the_workbench`. With the stack
beneath at `7`, it requires the plain form to leave exactly one answer
above it. That test, not `bund2 words`, belongs in criterion 1.

The RFC should also state the consequence for RFC-0005: none of the
twelve is promotable, so compiled code syncs before each, as it does for
the seven.

### 6. Criterion 4's count is wrong, and S4's list outruns its tests

"The seven unit tests in `graph_algorithms.rs`" (R:134-135). There are
ten that are not cross-checks: `traversals_answer_in_node_order`,
`a_node_operand_is_title_cased`, `structure_words_answer_lists_of_lists`,
`a_cycle_has_no_topological_order`, `weighted_words_answer_maps`,
`a_repeated_edge_takes_its_last_weight`,
`the_workbench_forms_hold_the_graph`,
`each_form_holds_the_graph_on_the_workbench`,
`each_refusal_section_s4_names`,
`a_deep_graph_does_not_overflow_the_stack`. D192's "Seven unit tests"
(`decisions.md:3752`) carries the same stale count. The criterion should
name the tests.

Gaps against S4 (R:87-92):

- "An unknown or non-STRING node operand is refused naming the word" is
  tested for `graph.bfs`, `graph.degree` and `graph.dfs` only
  (`a_node_operand_is_title_cased`). It is not tested for
  `graph.maxflow`'s source or sink, `graph.bellmanford`,
  `graph.reachable` or `graph.neighbors`.
- "not finite" is tested only by calling `max_flow` directly with
  `f64::INFINITY` (`each_refusal_section_s4_names`), not through the
  word. NaN is not tested at all.
- The graph-shape refusals (`MISSED TYPE`, `unknown data type`,
  `Nodes list must be a list`) come from the reference-worded
  `graph_operand` (`graph.rs:415-451`), not from the new messages. S4 does
  not mention them, though `each_form_holds_the_graph_on_the_workbench`
  pins `MISSED TYPE`.

### 7. Criterion 3 checks the internal functions, not the words, and not S3's order

The eight cross-checks call `bfs`, `scc`, `mst` and the others on a
`Net`. None goes through the interpreter. Each checks a set, a partition
or a total, which is right for correctness. None checks the ordering that
S3 promises:

- `reachable_is_the_transitive_closure_row` sorts BFS and DFS output
  before comparing, so "breadth first" and "depth-first preorder" as
  orders are checked only on the one fixed DAG in
  `traversals_answer_in_node_order`.
- `mst_is_minimal` checks the total weight. The tie rule ("equal weights
  in the order the graph lists them") and "lightest first" are not
  checked. Graphs with more than eight non-loop edges are skipped, and
  the test does not say how many of its 200 survive.
- `bellman_ford_agrees_with_floyd_warshall` accepts any reported node `u`
  with `d[u][u] < 0`. It does not check that `u` is reachable from the
  start, although the message says "A **reaches** a negative cycle through
  B". It does not check D192's "smallest-numbered node on it"
  (`graph_algorithms.rs:556-558`).
- `max_flow_is_the_min_cut` only ever takes node 0 as source and the last
  node as sink.

These are acceptable as cross-checks. Criterion 3 should say "each
algorithm's *answer as a set/value* agrees", and a separate criterion
should cover S3's order through the words.

### 8. Citation of D192 §2 for "one read of the graph"

R:96-97: "over one read of the graph (D192 §2)". D192 §2 rules *whose*
implementation, Bund2's own (`decisions.md:3678-3683`), and says nothing
about reading once. If "one read" is a claim, it is grounded in `operand`
→ `read` (`graph_algorithms.rs:178-181`).

### 9. The Motivation counts wrong

R:23-26: "The reference answers **three** graph questions", followed by a
list of four (`graph.path`, `graph.paths`, `graph.allpath`,
`graph.transitiveclosure`). R:29: "three of the four answers". The second
count is right (`graph.path` answers one ordered path, `getpath.rs:79-89`).
The cited `mod.rs:113-120` registers `graph`, `graph.` and `graph!` and
calls four `init_stdlib`s. It does not name the four algorithm words,
which are registered at `getpath.rs:106`, `dijkstra.rs:95`,
`allshortpath.rs:95` and `transitiveclosure.rs:84`.

## Claims that need a citation and lack one

- R:35-36, "Nothing is cached; every word re-reads it": grounded by each
  word calling its builder at `:44` (`dijkstra.rs`, `allshortpath.rs`,
  `transitiveclosure.rs`, `getpath.rs`).
- R:29-30, "three of the four answers come back in an order that changes":
  needs `algos`' `johnson.rs:25` and `warshall.rs:40` (both return a
  `HashMap`) beside `dijkstra.rs:71`, or F17.
- R:68, `graph.bellmanford`'s rows are `graph.paths`' rows: `dijkstra.rs:69-76`.
  This claim is checkable and true.
- R:99-100, Edmonds–Karp needs at most nodes × edges rounds: a textbook
  bound (Edmonds and Karp, 1972) with no citation. It holds in floating
  point here only because the bottleneck arc's `cap -= b` is exact. `b`
  is the minimum of those same caps (`graph_algorithms.rs:666-676`), so
  the critical arc reaches exactly 0. That argument should be written
  down, because D39 is what it satisfies.
- R:116-117, "`graph` would print it": the probe golden pins
  `{ edges=[] :: nodes=[] :: type=graph }`
  (`tests/golden/probes/graph-algorithms.golden`). Cite it.

## Preservation analysis: what it does not enumerate

R:103-109 has two bullets. The design can also change, or newly fix,
the following:

1. **`graph.path`'s operand casing** (finding 1). This is an existing
   deviation the analysis asserts away.
2. **Which reader the new words copy** (finding 3). A program that moves
   from `graph.path` to `graph.bfs` or `graph.bellmanford` sees duplicate
   edges and fractional weights read differently.
3. **Operand casing across the family.** `graph.paths` refuses `:a`, while
   `graph.bellmanford`, offered as its drop-in ("so a program can swap one
   word for the other", D192), accepts it. The swap works in one direction
   only. Dijkstra also refuses a negative weight it meets
   (`algos/…/dijkstra.rs:103-107`), where Bellman–Ford does not.
4. **Residual stack on refusal.** Every new word pulls the graph, then
   its node operands, then refuses. After a refusal both are gone, so a
   `?try` recovers to a stack without them. That matches the reference's
   pull-then-check shape, but RFC-0004 (`:490-495`) treats the residual
   stack as observable, and the RFC never states it. The same applies to
   the order of refusals: a malformed graph is reported before a bad node
   operand, because the graph is read first.
5. **F17's sort key for the pair words**, by `from` then `to`. F17 records
   it; S3 does not (finding 4).
6. **Position of a replaced edge.** `algos` moves a re-given edge to the
   end; `Net` keeps it at its first position with the last weight
   (`graph_algorithms.rs:51`, `:135-145`). "The order the graph lists
   them", used by `graph.mst`'s tie rule and `graph.maxflow`'s `edges`,
   therefore means *first appearance*. That is a choice, and an
   unstated one.
7. **`graph.mst` reads edges both ways.** D192 §3 says the two words that
   do so "say so". The S1 row for `graph.components` says so; the row for
   `graph.mst` (R:67) does not. A→B and B→A are separate `Net` edges, and
   the lighter wins.
8. **D111's family table is extended.** The 2026-10-07 note's container
   row (`decisions.md:9416`) lists `graph.path` and `graph.paths`, and
   `wb.rs`'s `ADDED` list has 58 names, none of them new. The twelve new
   forms are D192's build choice ("each can be overruled"), not D111's
   ruling. R:53-54 attributes them to D111.

## Consistency with accepted RFCs and ERRATA

- ERRATA has no graph entry; nothing here contradicts it.
- RFC-0002 and RFC-0004 (the declared dependencies) are Accepted. The
  RFC-0004 dependency is real: `bund2 check` reads these effects. But no
  criterion connects the two (finding 5).
- RFC-0005 criterion 28: the twelve are unpromotable (finding 5). That is
  consistent, but unstated.
- The template requires an **Open questions** section
  (`0000-template.md:41-43`). The RFC has none. Findings 1 and 3 belong
  there at least.
- **Subject search of the registers.** The RFC lists D192, D38, D37, D39,
  D111 and F17. It misses F101, which is directly about the four-element
  rule the RFC then misstates (finding 2), and D14, under which the graph
  family is library rather than core. This is the recurring failure
  CLAUDE.md names.

## What the RFC assumes but does not state

- That weights are finite. Only `graph.maxflow` refuses NaN or ±∞.
  `graph.mst` orders NaN by `total_cmp` (`graph_algorithms.rs:492`), and
  `graph.bellmanford` stores NaN for a node first reached over a NaN edge
  (`:512-515`). Neither is specified.
- That `graph.mst` accepts negative weights (D192 says so; the RFC does
  not), and that a self-loop is never in the forest (`:491`).
- That `graph.maxflow` validates the capacity of **every** edge, including
  self-loops and edges unreachable from the source, before running
  (`:583-592`). That `edges` lists only edges that carry flow (D192 says
  so; R:69 does not), in the graph's order. That an unreachable sink
  answers `flow = 0.0` rather than an error.
- That `graph.degree`'s `in` and `out` are INTEGERs, count a repeated edge
  once, and count a self-loop once each way. D192 says this; R:62 says only
  "MAP `in`, `out`".
- Which node the two cycle errors name. For `graph.toposort` it is the
  node where the DFS entered the cycle (`:351-354`). For
  `graph.bellmanford` it is the smallest-numbered node on the cycle
  (`:556-558`). Both are deterministic, by different rules, and S4 names
  neither.
- Which cycle `graph.cycle` answers: the first a DFS in node order closes.
- That `graph.reachable` is reflexive for every node, with or without a
  self-loop, because `algos`' Warshall closure is. The probe shows this
  only for a one-node graph.
- `NO DATA #n` numbering for the operands, which `each_refusal_section_s4_names`
  pins (`#2`, `#3`).
- That the `algos` checkout under `~/.cargo/git/checkouts/` is the
  `4c08437` the oracle links. Only `reference/Bund/Cargo.lock:88` says so,
  and the RFC does not cite it.

## Disposition

**Not ready for Accepted.** Finding 1 is a reference divergence in shipped
Bund2 with no register entry, and the RFC's preservation analysis asserts
it away. Under CLAUDE.md it goes to `defects.md` as a Bund2 defect, or to
`decisions.md` if the owner wants to keep it, before code or this RFC
moves. Finding 2 is a misread of a cited line that D192, F101 and the
code all have right. Findings 3–7 are criteria that name a test which
does not check the claim. Each has a concrete replacement above.
