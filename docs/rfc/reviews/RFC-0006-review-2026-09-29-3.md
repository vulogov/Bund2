## Verdict

**Two blockers and eight significant findings.** The payload and front-end
design is sound, and most citations check. Both blockers share the recurring
shape CLAUDE.md names: a claim about what the code does that stopped one call
short, and a deviation filed as a non-deviation.

- **B1.** `--noeval` does not stop evaluation. `"40 2 +" compile lambda! !`
  prints `42` under `--noeval --noio`, and `url` plus the same three words
  fetches and evaluates remote code under `--noeval` alone. D78 obliges this
  RFC to state what each flag leaves ungated, *by name*. §B3a does that for
  `--noio` and not for `--noeval`, and its sentence on fetching is half wrong.
  Criterion 10 passes on an artefact that evaluates arbitrary source.
- **B2.** D10 describes `--emit=bundle` as "pure interpreter, **no
  Cranelift**" (`decisions.md:443`). Criteria 1, 3 and 6 and §B4's `--features`
  all assume a bundle runtime built *with* `jit`, which contains Cranelift.
  D77 approved a departure from one phrase of that same sentence ("embedded
  IR") and not from this one. The header says nothing awaits a decision, and
  that is not true.

## B1 — `--noeval` leaves evaluation ungated, and §B3a does not say so

§B3a says `--noeval` "does the same [registers stubs that fail] to
`bund.eval`, `use` and `use.`" and cites `host.rs`. That is exactly what it
stubs (`crates/bund2-stdlib/src/host.rs:353-366`), and it matches the
reference, which gates `bund.eval`, `bund.eval.`, `bund.eval-file` and
`bund.eval-file.` (`reference/Bund/src/stdlib/functions/bund/bund_eval.rs:117-121`)
and `use` (`reference/Bund/src/stdlib/functions/bund/bund_use.rs:74`).

**What it does not stub is `compile`**, which the reference registers
unconditionally (`reference/Bund/src/stdlib/functions/bund/bund_interpreter.rs:76`).
`compile` parses a string into a LIST (`:29-43`). `lambda!` retypes that LIST
as a lambda, and `!` or `execute` runs it. Reproduced at `657ac8c`:

```
$ echo '"40 2 +" compile lambda! ! println' > t.bund
$ bund2 script --noeval --noio --file t.bund
42
```

`execute` behaves the same way. `url` fetches text and is gated by `--noio`,
not `--noeval` (`host.rs:464-465`). So `"file://…" url compile lambda! !`
**fetches and evaluates** under `--noeval` alone. The same holds for `http://`,
under D54.

Three consequences:

1. **D78's obligation is unmet.** D78 says "RFC-0006 states what each flag
   leaves ungated, by name" (`decisions.md`, D78, *It is not a sandbox*). §B3a
   names `--noio`'s gaps (`args`, `sleep.seconds`, `io.graph`, and `use`) and
   nothing for `--noeval`. The failure D78 exists to prevent is "a builder who
   believed `--noio` protected that person". A builder who believes a
   `--noeval` artefact cannot evaluate source is making the same mistake.
2. **"Fetching is gated by `--noeval`, not `--noio`" is half wrong**, both in
   §B3a (RFC line 305) and in D78 (`decisions.md:3550`). Fetch-and-evaluate
   (`use`, `use.`) is `--noeval`'s. Fetch-to-string (`url`, `url.`, and `file`)
   is `--noio`'s. The conclusion that follows it, "a `--noio` artefact can
   still pull and evaluate remote code", is still true, because `use` survives
   `--noio`. The sentence as a whole needs both halves.
3. **Criterion 10 checks the stubs, not the property.** "A bundle built
   `--noeval` still refuses `bund.eval`, `use` and `use.`" passes on an
   artefact that evaluates any string it is given. That is acceptable only if
   the RFC says plainly that `--noeval` means "these words are stubs" and
   **not** "this artefact does not evaluate source". The criterion's list also
   omits `bund.eval.`, which Bund2 stubs (`host.rs:354`).

**This is preserved behaviour, not a Bund2 defect.** The reference has the same
gap. Nothing here asks to change `--noeval`, and gating `compile` would be a
deviation that needs its own decision. What is needed:

- §B3a names `compile`, `lambda!`, `!` and `execute` as the route `--noeval`
  leaves open, and says that `url` plus that route fetches and evaluates under
  `--noeval` alone.
- The fetching sentence is corrected here, and D78 gets an amendment, the way
  D77 and D11 were amended.
- Criterion 10 states what it covers and lists `bund.eval.`.
- If the owner wants `--noeval` to mean "evaluates nothing", that is a new
  decision. Do not adopt it here.

## B2 — a `jit` bundle departs from D10's description, and no decision covers it

D10's resolution describes the bundle: "`--emit=bundle` — runtime plus
embedded IR, **pure interpreter, no Cranelift** and no `cc`"
(`docs/registers/decisions.md:443`). The research it cites says the same:
"Product A (runtime + embedded IR, **pure interpreter**)"
(`docs/research/02-native-binaries.md:228-229`). The research's own table
disagrees and marks Cranelift "optional (for JIT tiering)" (`:40`), so the two
sources D10 draws on conflict. D10 took the stricter reading.

The RFC builds on the looser reading and does not say so:

- **Criterion 1** measures "a bundle runtime with and without `jit`".
- **Criterion 3** is restated "against a configuration", *because* another
  configuration of a bundle runtime contains `cranelift-codegen` and
  `cranelift-jit`.
- **Criterion 6** requires "a bundle built with `jit`".
- **§B4** has `--emit=bundle --features` select among runtimes, and `jit` is a
  feature (`crates/bund2-cli/Cargo.toml`, `[features]`).

D77 is an approved deviation from **one phrase** of that sentence: "D10's
parenthetical calls `--emit=bundle` 'runtime plus embedded IR'", and it rules
on that phrase alone. "Pure interpreter, no Cranelift" is not mentioned in
D77, the RFC or the Preservation table. The table's "D10's 'embedded IR'
description" row covers exactly what D77 covers.

This is the same class of departure D77 was filed for. The RFC treated one
half as a decision and missed the other half of the same clause. Carrying
Cranelift does not violate D10's *resolution*, because Cranelift is pure Rust
and needs no `cc`. It is still the owner's call whether a bundle may tier. If
it may not, criteria 1 and 6 go, and §B8's gate needs a different
measurement.

**What is needed.** Either put it to the owner as an amendment to D77, or as a
new entry, or drop `jit` bundles. Add a Preservation row either way.

## Significant

**S1 — "the bytes reach only a Bund string" is false, and D11's amendment
repeats it.** RFC lines 86-88 say the `to_binary` bytes "reach only a Bund
string, read back by `decode.base64`". D11's amendment says "no word writes the
raw format to a file, and no external consumer is implied"
(`decisions.md:509-511`). `reference/Bund` calls `to_binary` in eight places,
and three of them take the bytes out of the process:

- **The world file stores every lambda in exactly `Value::compile`'s format.**
  `for (n,l) in vm.lambdas.iter() { match l.to_binary() … INSERT INTO LAMBDAS
  (name, lambda)`, and the failure message says "Error compiling lambda body"
  (`reference/Bund/src/stdlib/helpers/world/lambdas.rs:80-95`). `compile` on a
  LAMBDA *is* `to_binary` (`bincode.rs:38-50`), so this is the object format,
  on disk, in a user-named file. Stacks and models go the same way
  (`world/stacks.rs:100`, `world/models.rs:90`).
- **Zenoh publishes the raw bytes to other processes**
  (`reference/Bund/src/stdlib/helpers/zenoh/pubsub.rs:22,60`,
  `zenoh/putget.rs:22,61`). A peer is an external consumer by construction.
- `debug_dump` hexdumps them to stdout
  (`reference/Bund/src/stdlib/functions/debug_fun/debug_dump.rs:52`).

D31 already covers the world file ("no external readers", owner, 2026-09-11).
D31's premise is wrong in the same way, though: "The object format has no
producer reachable from Bund, so no file in it exists" (`decisions.md:1507-1508`),
while its own `LAMBDAS` table is that format. **D11's resolution most likely
survives**, on D31 for disk and on zenoh being distributed-mode only
(`putget.rs:15-17` requires `--distributed`). The proof, however, has now been
corrected once and is still incomplete. The disposition belongs to the owner
and should not be carried by the RFC's prose.

Also, "exactly the bytes `compile_to_binary` would write" is not exact. The
`compile` word appends `\n` and stops at `EXIT`
(`bund_interpreter.rs:29,35-36`); `compile_to_binary` does neither
(`compile.rs:14-21`).

The Preservation row still says "nothing can depend on either". The second
review asked for "a bundle reads neither". That is the claim the RFC needs,
and it is true.

**S2 — "Q39" is a duplicate identifier.** `open-questions.md` has two Q39
rows: `:15`, promotion across a producing call, "RESOLVED as D68", which D68
cites ("resolving Q39", `decisions.md:4300`) and so does RFC-0005 (`:1960`);
and `:26`, code signing, added in `2c1e772`. The RFC cites the second (lines
469 and 560). Registers are append-only and "never delete or renumber", so a
reader following "Q39" from D68 now reaches two questions. File the signing
question as **Q40** and annotate `:26` as misnumbered, pointing to Q40. Whether
renumbering a row committed today counts as "renumbering" is the owner's call.

**S3 — criterion 7's reformulation drops the trampoline, which calls a body
directly.** RFC-0005's criterion 4 allowed "exactly two exceptions … a
native's `Tail` thunk calling its Rust adapter, and **the entry trampoline
calling the body it enters**". The lowering quotes that and implements it
(`crates/bund2-jit/src/lower.rs:1150-1163`, and `:3073` for the word body's
trampoline: `module.declare_func_in_func(body_id, f.func)`). Criterion 7 now
says "no relocation names another compiled body", and permits only "imports of
runtime symbols". The trampoline's relocation names a compiled body, and it is
not an import. It is permitted only by reading "reached from inside another
body" as excluding the trampoline, and the criterion never mentions the
trampoline. State both of criterion 4's exceptions. The second half of
criterion 4, "every call slot's target is a `Tail` thunk or a `Tail` body", is
still dropped, as both earlier reviews noted.

§B5 still presents the `cells` comment as the safety argument for
`slots_base`. The comment sits under `iconst(ptr, slots_base)` and above
`iconst(ptr, cells)`, and it names "§S6's cells" (`lower.rs:2549-2553`);
`slots_base` (`:2341`) has none. The conclusion holds for both immediates, but
the quote is attributed to the wrong one.

**S4 — no failure path for the trailer, which is the new way this binary can
fail.** Nothing in the RFC says what the runtime does when its executable has
no trailer (someone runs the prebuilt runtime directly), a truncated one, a
wrong magic, a format version it does not know, or a length past the file's
start. `grep` finds no "corrupt", "truncat", "D37" or "panic" in the document.
This is start-up code that parses bytes out of `current_exe`, which is where
`unwrap` goes when nothing says otherwise, and CLAUDE.md makes the no-panic
rule absolute. The CLI's precedent is a message on stderr and exit **2** for a
failure to start (`crates/bund2-cli/src/main.rs:145-153`). State the path and
add a criterion: a bundle with each of those defects is reported, not
panicked, and exits 2. The second review asked for this criterion. It also
asked for `./app --stats` reaching `args` and `bund.exit 3` exiting 3. None of
the three was added.

**S5 — builder and runtime versions can differ, and the trailer cannot tell.**
§B1 "ships **or locates**" a prebuilt runtime. §B3 parses at build with the
builder's parser, discards the result, and re-parses with the runtime's. The
Preservation row "Program meaning … Preserved exactly, because the artefact
parses and evaluates the same source through the same entry points" holds
only if both are the same Bund2. A located runtime from another version can
reject what the build accepted, or evaluate it differently. The trailer's
"pinned SHAs" (lines 135, 297) are, in this RFC's usage, `reference/`'s
SHAs, which say nothing about Bund2's version. The second review flagged the
ambiguity as Minor. With "locates" and a build-time parse, it is now
load-bearing. The trailer should carry Bund2's own version or commit, and
`bund2 build` should refuse a runtime that does not match. D50 bears on this
directly: `sysinfo.version` answers with the *runtime's* version
(`crates/bund2-stdlib/src/sysinfo.rs:16`), and the RFC still does not mention
D50.

**S6 — criteria 2, 6 and 10 depend on names the RFC never gives.**

- **Criterion 2** needs a runner. `run_once` spawns `exe script --file <path>`
  (second review, `xtask/src/golden/mod.rs:366-371`). Under §B3, a bundle
  hands all of that to `args`. The RFC names no mode.
- **Criterion 6** needs `compiled_entries()` reported from a bundle. The
  channel is "environment variables" (line 257), and none is named.
- **Criterion 10** asks for "every environment variable the start-up path
  reads set to every value that would clear them". That is checkable only
  against an enumerated list, and there is none.
- **`BUND2_JIT_THRESHOLD`** is read by the runtime's constructor
  (`crates/bund2-runtime/src/lib.rs:59`), so every `jit` bundle inherits it
  from whoever runs it. The RFC lists `--jit-threshold` among the flags a
  bundle drops (line 255) and never mentions the variable that still works.
  The Preservation table's diagnostic-flags row omits `--jit-threshold`
  entirely.

**S7 — criterion 3 still passes today, because the RFC never says which
binary the runtime is.** `bund2-cli`'s default features are `[]`, and
`cranelift-*` is optional in `bund2-jit` (`crates/bund2-jit/Cargo.toml:32-36,
54-55`). So `cargo tree` on today's default `bund2` lists no Cranelift, with no
bundle in existence. That is the vacuity the revision says it removed. If the
bundle runtime is a new binary, the criterion cannot run until that binary
exists, which is fine, but the RFC has to say so. The research names
`libbund2_runtime.a` (`02-native-binaries.md:224`). The RFC names no crate,
binary or target. `cargo tree` still checks a graph rather than the shipped
file. Also note that the `aot` feature pulls `cranelift-codegen` and
`cranelift-object` (`bund2-jit/Cargo.toml:54`), so "built without `jit`" is
not sufficient; the configuration must also exclude `aot`.

**S8 — the parse-at-build row is filed as "Deliberately changed" with no
decision.** The rows for diagnostic flags and for a syntax error's timing are
the only "Deliberately changed" rows without a D-number. D78 covers the first,
since it places `--nocolor` in "§B3's environment-variable channel" and so
ratifies that channel. Nothing covers the second. There are two honest
options. If the reference has no build step, there is no behaviour to change:
relabel the row "no reference counterpart" and say why. If it is a change, it
needs a decision. As written, the RFC takes a disposition of its own on a
change it has labelled deliberate.

## Minor

- **`RFC-0005:6556-6562` is short.** The quoted "§S7 compiles a body *on* an
  entry and runs that entry interpreted" is at `:6548-6549`; the trigger
  sentence is at `:6557-6561`. Cite `:6548-6561`. "Closed **this morning**"
  (line 371) is a relative date in a durable document. Use 2026-09-29.
- **Stale sentence, third review running.** "The decode happens on that
  thread, where a depth of 256 is known to be safe" (lines 247-248). Nothing
  is decoded, and 256 is the wire cap criterion 5 says does not apply. It
  should say "the parse" and cite F116 (`crates/bund2-syntax/src/lib.rs:161-174`).
- **Quote trimmed without an ellipsis, third review running.** §B3's quote
  ends "every compiled body declines." The source continues with a colon:
  ": criterion 2 would then pass with no compiled code having run at all"
  (`crates/bund2-cli/src/main.rs:58-62`).
- **"Four things the artefact's front end must settle"** (line 250) is
  followed by six bullets.
- **The header's decision lists still do not match the body.** D44 appears
  only in the header. D45 (line 262) is used and not listed. D52 (the exit
  code) and D50 are absent. D1 is "see the preservation table", and the table
  does not mention it. Q28 is answered in §B5 and never named, although
  RFC-0005 hands it to this RFC by name (`RFC-0005:6589-6591`).
- **The exit code is masked.** `ExitCode::from((code & 0xff) as u8)`
  (`main.rs:163`), per D52. §B3 says only "`vm.exit_requested()`".
- **argv[0].** "All of argv reaches `args`" (line 252). The reference fills
  `args` from the script arguments only, never the program name
  (`reference/Bund/src/cmd/bund_script.rs:13-19`). Say that argv[0] is
  excluded, or preservation breaks for every program that reads `args`.
- **The diagnostic-flag list is incomplete.** The CLI also has
  `--no-dump-stack` and the alias `--debug-values`, and `dump_stack` defaults
  to **on** (`main.rs:209, 219-221`). The environment channel has to express
  "off", not only "on".
- **The trailer is not integrity-protected, and the RFC should say so.** D78's
  floor holds against environment variables. The trailer is appended plain
  bytes, so anyone holding the file can rewrite a restriction out of it. That
  is consistent with "not a sandbox", and one sentence in §B3a would stop a
  reader inferring otherwise.
- **`bund2 build`'s own parse thread is unstated.** §B3 puts the runtime's
  parse on the sized thread. The build-time parse of a 1024-deep program
  (criterion 5) runs wherever `bund2 build` runs it. F116 measured debug
  aborts at 2,000-4,000 levels on a test thread (`bund2-syntax/src/lib.rs:169-171`),
  and a 1 MiB main-thread stack, Windows' default, halves that margin.
- **ERRATA still misses two contradictions.** `02-native-binaries.md:44-45`
  ("Serialise the BundIR object format") and `:40` ("deserialise IR") are
  contradicted by D77. `:46`, "runs anywhere Rust runs", is qualified by §B1,
  and the RFC's Summary (line 36) still repeats it unqualified.
- **Carried over and still open:** "AOT" is a defined term (the
  `cranelift-object` build) used here for a bundle, and the existing `aot`
  feature is not mentioned. The parse figure times `compile`, not
  `parse` + `lower_with_spans`, which is what a bundle runs
  (`crates/bund2-bench/benches/interpret.rs:181-184`).
- **Verified and correct.** `RFC-0003:422`. `bincode.rs:38-50` (refusal at

| 7 | Deferred. | Relocation records of a native object. | The trampoline exception is dropped, and so is the slot-target half (S3). |
| 8 | Once 2's runner exists. | `conform`, per golden, over native images. | Should list RFC-0005's two reopened mirror cases explicitly. §B5 says they are owed, and the criterion does not. |
| 9 | Yes. | Two runs of one bundle, each observing the literal's `.timestamp`, at least 1 ms apart, with the build time recorded. | Under D2 the literal must be *observed*. Say so in the criterion. |
| 10 | Only against an enumerated list. | A test that sets each named variable. | Checks the stubs, not "does not evaluate" (B1). It omits `bund.eval.`, and no variables are enumerated (S6). |
| 11 | Yes. | `conform`. | Restates 2 and 8. Say which run, or drop it. |

**Missing criteria**, each a behaviour the RFC states that nothing checks:

- A missing, truncated or mismatched trailer is reported, not panicked, and
  exits 2 (S4).
- `./app --stats` reaches `args` (§B3's argv rule).
- `bund.exit 3` exits 3, and `bund.exit 256` exits 0 (D52's masking).
- `bund2 build --inspect` prints what the trailer holds, including a
  restriction added at build (D78 promises this; only criterion 10 touches it,
  indirectly).
- `bund2 build` refuses a runtime whose version differs from its own, if S5 is
  adopted.
- A diagnostic from a bundle names the path given to `bund2 build`, verbatim.
  Criterion 2 catches this only for goldens with an approved deviation.

## Preservation analysis — what the table is missing

1. **What `--noeval` leaves reachable**: `compile` / `lambda!` / `!`, and with
   `url`, remote evaluation (B1). The row says "§B3a names what each leaves
   ungated", and §B3a does so for one flag.
2. **Whether a bundle may tier**: D10's "pure interpreter, no Cranelift" (B2).
3. **`sysinfo.version`**: the runtime's version, not the builder's (D50, S5).
4. **Behaviour under a version-skewed runtime** (S5).
5. **`BUND2_JIT_THRESHOLD`**: still read, and so still under the runner's
   control, with speed as the only effect (S6).
6. **`--jit-threshold`**: dropped from argv. It is in §B3's list and missing
   from the table's row.
7. **The exit code on a start-up failure**: exit 2 in the CLI, and unstated
   for a bundle (S4).
8. **`args` and argv[0]** (Minor).
9. **The reference's object bytes in the world file and on zenoh**: not read
   by a bundle, so no change, but the row's reason ("nothing can depend on
   either") is wrong (S1).

## Assumptions the RFC makes and does not state

1. **That `--noeval` means "these words are stubs"**, not "no source is
   evaluated" (B1).
2. **That a bundle runtime may contain Cranelift** (B2).
3. **That the builder and the runtime are the same Bund2**, so a build-time
   parse predicts the run-time one (S5).
4. **Which binary the prebuilt runtime is**, and how many ship: targets times
   feature sets, now multiplied by restriction-free configurations (S7, §B4).
5. **That the runtime can locate and read its own executable**, and what it
   does when the trailer is absent or malformed (S4).
6. **That the trailer is trusted**: a floor against environment variables, not
   against editing the file (Minor).
7. **That argv[0] is excluded from `args`** (Minor).
8. **That `bund2 build` parses on a thread large enough for `MAX_NESTING`**
   (Minor).
9. **That a signed runtime survives an append**: stated, as `[UNGROUNDED]`,
   under an identifier that collides with D68's Q39 (S2).
