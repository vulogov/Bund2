# RFC-0013 review — revision 10 (2026-10-28)

Reviewer's stance: adversarial. The RFC was not edited. This review reads
what revision 10 changed, which is criterion 1b's E40 test. It then
searches the code and registers for every other place the memory guard is
taken, which no earlier review did. Read against `reference/Bund` 21b40b0
and Bund2 at `17a2b7c`.

**Verdict: Not ready for Accepted.** There is no blocking finding and
nothing to rule on. One should-fix: the RFC misses the house precedent for
a native that polls the guard. That precedent also bears on the E40 prefix,
which the seventh review recommended without having seen it. One note.

## Should-fix

### S1. Two shipped natives already poll the guard, and the RFC cites neither

The RFC describes the guard as polled "where a body starts running" (Bund2
behaviour, quoting the `memguard` module header). D171 says the same: "the
one place a body starts running". Neither has been true since F210.

`grep memguard::take` over `crates/` finds three takers:

- `push_frame_once` in `bund2-interp`: the interpreter's poll.
- `seq`'s `build` in `crates/bund2-stdlib/src/seq.rs`: it polls between
  chunks of 4096 values. This is F210's fix, ruled "F210 A plus B" in
  `docs/registers/defects.md`.
- `ascii_plot`'s row loop in `crates/bund2-stdlib/src/host.rs`, which
  `io.graph` reaches through `io_graph`: it polls every
  `ROWS_BETWEEN_CHECKS` (4096) rows. This came with F104's refusal, and
  its doc comment says the guard "is asked every few thousand, as `seq`
  asks it". So the house has already followed F210 once.

RFC-0013's engine poll (S4) would be the third native to poll, and F210 is
its direct precedent. The RFC grounds the engine poll only in D171, and
F210 is not in its register list. That is the "search the registers by
subject" failure CLAUDE.md names: F210 is about the guard, and it doesn't
declare `Blocks:` RFC-0013.

The precedent matters to a text, not only to the citation list. Both
existing natives return **`Trip::error` as it is, with no prefix**:
`build` returns the closure's `Error`, and the closure is
`memguard::take().map(|t| t.error())`. `ascii_plot` does the same.
Revision 9 gave E40 S12's `<W>: ` prefix, as `-7.md` S2 recommended. That
review weighed S5 against S12 and did not know the house already had an
answer.

So the house rule is that a native's own guard poll fails with the
guard's text alone. That is the reading revision 8 had in S5.

**Fix:**

1. Add F210 and F104, with `seq`'s `build` and `ascii_plot`, to the register list
   and to the guard bullet under "Rules of the house". Say the module
   header's "where a body starts running" now covers only the interpreter.
2. Choose E40's text with the precedent in view. To follow it, list E40
   beside E00 as unprefixed in S12, and restore "the guard's text alone"
   in S5. To keep the prefix, say why the engine departs from `seq` and
   `io.graph`. Either is the RFC's to choose, since the error texts are its
   own and no decision is OPEN. This reviewer now recommends the
   precedent: the guard's error is the same event whichever native meets
   it, and a reader should not have to know which one did to match it.
   With the precedent, `seq`, `io.graph` and the `kb.` words all fail the
   same way.
3. Update criterion 1b's substring to match: the guard's text, with
   `KB.QUERY: ` only if the prefix is kept.

## Notes

- **N1. "Fails in under a second" is an estimate.** Criterion 1b's
  account of the cap says a missing poll "fails in under a second as
  E30". No engine exists to measure. Criterion 5 records arena growth
  rather than time for the same reason. The claim is rationale rather
  than a criterion, and harmless, but "quickly" or "after 1,000,000
  inferences" says only what is known.

## Preservation analysis

Unchanged since `-6.md`. Revision 10 changed one criterion.

The memory guard is outside the Preservation analysis's scope, since no
shipped poll changes. The RFC adds a poll, and that changes nothing a
program already sees.

## Consistency

- **D171** describes the guard's taking place as single. F210 and F104
  have since made it three, and RFC-0013 would make it four. D171 is
  RESOLVED and append-only, so it stays as it is. The RFC should say that
  it reads D171 as amended in practice by F210 and F104.
- **D226:** RESOLVED, and the RFC agrees row for row.
- **RFC-0010, RFC-0012 and ERRATA:** as in `-5.md`.

## Assumptions not stated

- That a native polling the guard is acceptable at all. F210's ruling
  already settled that, which is one more reason to cite it.
