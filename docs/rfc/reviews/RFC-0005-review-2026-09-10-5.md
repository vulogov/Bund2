Three blockers are new. Each is a callee capability the design does not yet
account for, which is the pattern the Summary describes. The first is **not
about promotion at all**, and it affects every call compiled code makes.

- **B1.** A native, or a call to a lambda, often does not run its body before
  it returns. It leaves a *request* that the frame loop fulfils afterwards.
  The RFC's call protocol never mentions that request.
- **B2.** `object` is a second `execute.`: it runs a class's `.init` under
  `eff(1, 1)`. Criterion 24 cannot see it, because it only passes lambdas, and
  the eighth review's hand audit missed it.
- **B3.** Criteria 24 and 25 check `bund2-stdlib`, while §S5 promotes across
  *any* native with a fixed effect. `Registry::register_native` is public, and
  D9 hands external crates `Native`.

## 1. Blocking

### B1 — compiled calls ignore the tail-request protocol

**What Tier 0 does.** `Vm::tail_lambda` is `Interp::request_tail`, which sets
`self.pending_tail = Some(body)` and returns. Its doc comment: "Ask the loop to
run `body` **after the current native returns**". The frame is pushed only by
`Interp::take_pending`, which is called in exactly three places: after each
`apply_step` in `Interp::run_to`, inside `Interp::apply`, and in `drain_frames`
(all `crates/bund2-interp/src/lib.rs`). These use the request:

- **`execute`'s LAMBDA arm**, `vm.tail_lambda(body)` (`execute_value`,
  `crates/bund2-stdlib/src/values.rs`). That is `!` on a lambda: the
  corpus's commonest word, and 32 of the 63 opaque stops in §S6's table.
- **`if` and `if.false`**, through the helper they share, and **`ifthenelse`**
  (`crates/bund2-stdlib/src/control.rs`).
- **Every call to a lambda name.** `Interp::dispatch`'s `Resolved::Lambda`
  arm: "Calling a lambda is a tail position … So it becomes a request, and the
  loop pushes a frame".

So the request's semantics are *run the body before the next value*. Run
against Tier 0 on 2026-09-10, `{ 10 } ! 20`, `true { 10 } if 20` and
`:f { 10 } register f 20` each leave `10` beneath `20`.

**What the RFC says.** §S4: "Every inter-word call loads a pointer from a
runtime-owned slot and calls it indirectly." §S4, *Two structures*: an alias's
call slot points at "a resolving trampoline that runs the full chain through
`dispatch`". §S5 lists "three things" that "may have changed" after a call:
the current stack's epoch, name meaning and `autoadd`. `pending_tail`,
`request_tail` and `take_pending` appear nowhere in the document. The only
mentions of `tail_lambda` (lines 1374, 1549 and 1774) are about where a
compiled body is *entered*.

**What follows.**

1. **Order changes.** A compiled body that calls `!`, `if` or a lambda
   through its call slot gets control back with the body not yet run. If it
   continues, even through §S5's runtime helpers, the requested body runs
   later. `Interp::apply` of the *next* value applies that value first and
   only then calls `take_pending`. So `{ 10 } ! 20` compiled that way
   leaves `20` beneath `10`.
2. **A request can be lost.** `request_tail` assigns. A second native call
   that requests a tail before anything takes the first overwrites it, and the
   first body never runs. Tier 0 cannot reach this state, because it takes
   after every step. Compiled code reaches it on the second call.
3. **The trampoline does not do what §S4 needs.** "Runs the full chain through
   `dispatch`" runs nothing when the chain ends at a lambda. It files a
   request.
4. **§S8's tail-call claim inherits it.** A last word lowered as
   `return_call_indirect` to a native that files a request returns to the
   compiled body's caller with the request pending. The frame loop would take
   it only after its *next* `apply_step`. `Vm::eval_lambda`, if a compiled body
   was substituted for its `push_frame`, would return without running it.
5. **§S8's list of entry points is short by one.** "The two places Tier 0
   starts a body" are the frame loop and `eval_lambda`. A compiled body that
   drains a request mid-body starts a Tier 0 body synchronously: a third place,
   and a nested `run_to` with its own Rust frame. Recursion through `!`
   inside compiled code then spends a machine frame per level above the Tier 1
   floor. The floors bound that, but §S8's decline argument and criterion 11
   never mention the path.

This is independent of promotion. D46 syncs before a lambda call, and §S5
syncs before `!`. **After the sync the call still has to run its body in the
right order**, and nothing says how.

**Required:**
- Add the pending request as a fourth piece of state after every call, and say
  what compiled code does with it. For a non-tail call, the body is run to
  completion before the next op, which is `Interp::apply`'s shape. For a tail
  call, the request is handed to the caller, which must take it immediately.
- Specify what each entry point does when a compiled body returns with a
  request pending: the frame loop's entry, and `eval_lambda`'s.
- Add the synchronous drain to §S8's list of places a body starts, and cover
  it in the decline argument.
- **Add a criterion:** `{ 10 } ! 20`, `true { 10 } if 20` and
  `:f { 10 } register f 20`, each compiled with the call in a non-tail and a
  tail position, and each matching Tier 0. Add a second request before the
  first is taken, such as `{ 1 } ! { 2 } !`. Add a Preservation row.

### B2 — `object` runs `.init` under `eff(1, 1)`, and criterion 24 cannot see it

`object` is registered `eff(1, 1)` (`crates/bund2-stdlib/src/oop.rs`, the
`register_native("object", …)` line). `object_word` looks up the class and
calls `make_object`, then `push_and_init`, then `run_init`. `run_init`
evaluates the class's `.init`: a LAMBDA through `vm.eval_lambda`, or a PTR
through `vm.method(&mname)` followed by `f(vm)`. `make_object` does the same
for every parent class. Run 2026-09-10:

    :object ?effect println                        → { consumes=1 :: opaque=false :: produces=1 :: }
    :A class :.init { "init ran" println } set register
    1 2 :A object                                  → prints "init ran"
    :B class :.init { swap drop } set register
    1 2 :B object debug.display_stack              → 1, then the object: the 2 is gone

So `object` runs arbitrary code, and consumes beyond its declared arity, under
a fixed effect. The corpus does this: `class_constructors_demo.bund:31` builds
an object whose construction runs five `.init` lambdas, and Q14's table counts
27 uses of `object` (`docs/registers/open-questions.md:428`).

**Why criterion 24 passes.** It runs each fixed-effect native against stacks
and workbenches of **lambdas**. `object_word` needs a string naming a
*registered class*, so it fails at `as_str()` before any body starts. The RFC
notes that a native handed a *name* would slip through. The operand kinds the
test never tries are wider than that: a class name, a CALL or PTR value naming
a lambda, a CONDITIONAL, a LIST, an OBJECT.

**Why the hand audit passed it too.** The eighth review listed the sixteen
stdlib functions that re-enter evaluation and "checked each one's registered
words". `run_init` is one of the sixteen, but it is not registered: it is
reached one call up, through `push_and_init` from `object_word`. That is
CLAUDE.md's "follow the call one level further", applied to the audit itself.
The claim is repeated in three places that now need correcting: criterion 24
("The eighth review's audit of the sixteen functions that re-enter evaluation
found none"), F87's status paragraph, and the test's doc comment ("the
reviewer's hand audit … found none that is not also reached by a lambda").
The eighth review never made that last claim.

`run_init`'s PTR arm has a second shape. It calls a method native **directly**
(`vm.method`, then `f(vm)`), with no dispatch, no slot and no generation. So a
native runs whose own effect nobody reads. The built-in `.int_init` family
pulls its argument from the stack (`crates/bund2-stdlib/src/oop.rs`,
"Stack is empty for method '.init'"). Only the calling word's opacity protects
this path.

**Required:**
- Have the owner record `object`'s declared effect as a defect in RFC-0004's
  annotation. The number is the owner's. Make it opaque.
- **Widen criterion 24** beyond lambdas: operands that include a registered
  class whose `.init` is a lambda, a CALL and a PTR naming a registered lambda,
  a CONDITIONAL, a LIST of lambdas, and an OBJECT. Mutation-check it against
  `object` before the fix, as this review did for `execute.`.
- Replace "checked mechanically for every native" (§S5, line 568) and
  "found none" (criterion 24) with what the test actually establishes.
- Re-derive *Where promotion stops* once `object` is opaque. Every analysed
  path that reaches `object` before any other stop moves.

### B3 — the checks cover one crate, and §S5 trusts every native

§S5 promotes across any call whose native declares a fixed effect. That is
sound only if the native (a) runs no body (criterion 24), (b) reports nothing
at `Error` (criterion 25) and (c) observes nothing beyond its arity (Q34,
criterion 14). Assumptions 7 and 8 say (a) and (b) are "Enforced by a test".
The tests iterate `bund2_stdlib::register_all` and read
`crates/bund2-stdlib/src/*.rs`.

But `Registry::register_native` is `pub` (`crates/bund2-api/src/lib.rs`).
D9's resolution says "External crates get `Native` with a declared effect",
and §S10 repeats it: "an external package gets `Native` with a declared effect
and no more". §S8's *Embedders* paragraph assumes embedders exist. An
embedder's `eff(1, 0)` native that calls `vm.eval_lambda`, or
`vm.report(Diagnostic::error(…))`, gets wrong results under `jit`, and no
criterion can fail. B2 shows that even the stdlib's own declarations are wrong
without a sufficient check. There is no reason to expect better of code this
repository never sees.

**Required:** state which natives promotion crosses. The cheapest rule uses
machinery the RFC already has: **promote across a call only when the callee's
registration id is one `bund2-stdlib` made** (D43's ids already identify those
registrations for fragments). Every other native syncs, as at an opaque site.
Or state the assumption, with its consequence for embedders, and have the
owner decide it. Correct assumptions 7 and 8, and the Status line's "no native
reports at `Error` severity", to say "no `bund2-stdlib` native".

## 2. Significant

### S1 — `effect_of` answers with the native's effect for a lambda that shadows it

§S5 (lines 541–544): "For a native that is the effect declared in the native's
own slot (`Registry::effect_of`, …) … A lambda has no declared effect:
`effect_of` returns `None` for one". D46's first paragraph says the same.

`Registry::effect_of` follows aliases and then returns
`slot.native.or(slot.command).map(|n| n.effect)`. It never looks at
`slot.lambda`. Its doc comment ("`None` when the name resolves … to something
with no declared effect — a lambda") holds only when no native shares the
slot. `register_lambda` "does not disturb the native binding" by design. Run
2026-09-10:

    :drop { 1 } register  5 drop debug.display_stack   → 5, 1      (the lambda ran)
    :drop { 1 } register  :drop ?effect println        → consumes=1 produces=0
    :dup { drop drop drop } register  1 2 3 dup        → bund2 check: 0 findings, 2 sites analysed

An implementation that decides "native, fixed effect" by asking `effect_of`,
as §S5's citation directs, promotes across a lambda that shadows a native.
That is the case D46 forbids. Neither criterion catches it. Criterion 22's D46
part uses the fresh names `f` and `g`, and criterion 5 shadows `+` only to
test inlining.

**Required:** classify every callee with `Registry::resolve`, and read an
effect only when it answers `Native` (or `Command`). Correct the sentence, and
have the owner add a dated note to D46. Add to criterion 22 a body
`1 2 3 drop` promoted across `drop`, after `:drop { drop drop } register`.
Recommend that the owner record `effect_of`'s doc/code mismatch, and `?effect`'s
answer for a shadowed name, as a Bund2 defect (RFC-0004's).

### S2 — "never lower" fails when compiled frames hold the share

§S8, *A decline is a return*: "A level beneath the floor therefore costs what
it costs with the tier off, **plus whatever the feature adds to
`eval_lambda`'s own frame** (a cache lookup)." Then *Room is bytes*: the
inequality "has close to a factor of two to spare". That spare comes from
Tier 1's share, and it exists only if the nesting being measured can use the
share.

Take a program that recurses **directly** until its compiled frames reach the
Tier 1 floor, and then begins native-mediated nesting (`times`). With the tier
off, the direct recursion is flat on the heap (RFC-0003's frame loop), and the
nesting has Tier 0's whole 8 MiB. With it on, the share is held by compiled
frames, and the nesting has the same 8 MiB at a per-level cost of `c + δ`. For
any δ > 0 it reports at a lower level. D44's requirement 2 is "A program whose
native nesting fits under the default binary fits under the `jit` binary". A
program near the limit fits with the tier off and not with it on.

Criterion 11's `loop` axis begins nesting at the top of the stack, with no
compiled frames above it, so it cannot show this.

**Required:** either require δ = 0 beneath the Tier 1 floor, so that the cache
lookup is done in a callee that returns before `run_to` and leaves no frame
live across the nesting, or state the allowance and take it to the owner
against D44. Add a criterion-11 case: direct recursion deep enough for compiled
frames to pass the Tier 1 floor, followed by the `loop` axis from there, with
on ≥ off.

### S3 — `bund2`'s own thread declares its region, so as written the tier never runs in the CLI

§S8: "A declared region is Tier 0's alone. `set_stack_region` takes a top and a
size … So under `jit`, a region an embedder declares gets no Tier 1 share, …
and compiled code does not run there." `bund2`'s `main` declares its own thread
through the same function:
`bund2_interp::set_stack_region(bund2_interp::stack_marker(), EVAL_STACK)`
(`crates/bund2-cli/src/main.rs`). The text promises a declaration that names a
share "with the tier", and does not say the CLI moves to it. Without that move,
criterion 2 passes with no compiled code running, and so do the parts of
criteria 9, 10 and 22 measured through `bund2`.

**Required:** say that `bund2`'s thread declares its share through the new
declaration. Make criterion 2 fail when no body was compiled, for example by
requiring the lowering's side table (criterion 17) to be non-empty over the
corpus. Criterion 11 already requires "the depth at which compiled bodies begin
declining" to be reported, which catches this there.

### S4 — smaller items

- **§S6 contradicts itself on what it counts.** Line 1168: "`bund2 check`
  reports **every** call site where RFC-0004's analysis stops". The new
  paragraph at 1204–1213: "the first word-named stop on each analysed path,
  not every opaque site", and "a lower bound". §S5 (line 589) builds on it:
  "control flow is 19 of the 63 opaque sites". Make line 1168, the section
  title and line 589 say "first stops".
- **Criterion 25 is textual.** `Diagnostic`'s fields are public
  (`pub severity`, `crates/bund2-api/src/diag.rs`), so
  `Diagnostic::warning(…)` with `severity` assigned from a variable passes the
  scan. B3 is the larger gap. The criterion should say it scans for spellings.
- **Criterion 24 depends on a fresh `Interp` per native** and counts only
  frame pushes. A fixed-effect native that dispatches a name to *another
  native* (through `vm.apply` of a CALL) starts no frame, and so is invisible.
  None exists today; `apply` is `opaque(1)`. The criterion's title, "runs a
  body", is narrower than §S5 needs, which is "reaches anything by name or
  value".
- **The honesty test's doc comment** cites a finding the eighth review did not
  make (B2). This belongs in `crates/`, not the RFC, but criterion 24 repeats
  it.

## 7. What the RFC assumes and does not state

1. **A call from compiled code is complete when the callee returns** (B1).
   In Tier 0 it is complete when `take_pending` has run.
2. **Whether a native runs a body does not depend on its operand's kind**, so
   lambdas are a sufficient probe (B2).
3. **Every native that promotion crosses is `bund2-stdlib`'s** (B3).
4. **A name that resolves to a lambda has no effect in `effect_of`** (S1).
5. **The feature adds nothing to a Tier 0 level beneath the Tier 1 floor**, or
   Tier 1's share is free when native nesting begins (S2).
6. **`bund2`'s thread declares a Tier 1 share**, through a declaration that
   does not exist yet (S3).
