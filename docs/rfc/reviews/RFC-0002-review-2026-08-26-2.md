# RFC-0002 review — second pass, 2026-08-26

Reviewing `docs/rfc/RFC-0002-symbols-and-words.md` at commit `3da06b7`,
revised after review 1 (`RFC-0002-review-2026-08-26.md`).

Method: every `reference/...:N` citation was opened and read in this session.
Counts re-derived from the tree, the goldens and `cargo xtask`. The grammar
(`reference/bund_language_parser/bund.pest`) was read in full, because the
RFC's "interned at parse time" rests on it.

Verdict: **do not accept — and again not because of D14.**

The blocking problem is that **the document contains two Design sections, and
the second one is the design review 1 rejected.** Lines 298-322 duplicate
§"Alias resolution happens twice", §"`$` skips the lambda check" and
§"Registration is last-write-wins" verbatim from lines 160-184, and line 324
opens a second `## Design` whose §"One slot table" (line 338) declares the
single-enum `WordEntry` that review 1 found unable to represent a name bound as
both lambda and native. The revision was inserted ahead of the old text rather
than replacing it. As committed, the RFC specifies both designs and asserts
both "a slot is a set of bindings, not one binding" (line 200) and "a name has
exactly one meaning" (line 356).

Everything below is secondary to that, but none of it is fixed by removing the
stale half.

## What this pass confirms as correct

**The dispatch analysis is exact.** All thirteen allocation rows check out
against `multistackvm_apply.rs:9-62`, `multistackvm_alias.rs:34`,
`multistackvm_inline.rs:25,42,52,71,81` and `ts_inline.rs:33,34`, in the order
given, for `dup` specifically — including the subtlety that row 8 fires because
`i` receives the already-resolved `dup_one`, which is not itself an alias. The
eight hash lookups count out too: `is_command` 1, `get_alias` 2, `is_lambda` 1,
`is_alias` 1, `is_inline` 1, `TS::get_inline` 2.

**Resolution order is right**, including that `is_command` precedes the
`autoadd` branch (`:16` before `:19`) — which the preservation table then
contradicts. See B2.

**The seven tables are seven**, and they are exactly the ones named:
`inline_fun`, `command_fun`, `methods_fun`, `lambdas`, `classes`, `vars`,
`name_mapping` at `reference/rust_multistackvm/src/multistackvm.rs:24-30`, with
`vars` doubly keyed at `:29`.

**The lambda/native independence is real.** `register_lambda` checks
`is_type(LAMBDA)` at `multistackvm_lambdas.rs:8` and inserts into `self.lambdas`
at `:13`, touching nothing else; `call_internal_word` strips the sigil and
calls `i` (`multistackvm_call_internal_word.rs:7-8`).

**F31's mechanism reproduces exactly.** `TS::is_inline` tests the bare name
(`ts_inline.rs:25`) while `register_inline` writes the suffix (`:8`) and
`get_inline` reads it (`:33,34`). I counted the stack-layer registrations
independently: **31** distinct `register_inline` names in `rust_multistack`,
matching F31 and criterion 5.

**The mutex figures reproduce.** 119 `BUND.lock()` sites in `Bund/src`, **110**
of them inside a function named `init_stdlib` — exactly the split the RFC
claims. `run_snippet_for_script` takes the lock at `run_snippet.rs:63` and
drops it at `:95`, after `bc.eval(code)` at `:85`, so "the entire program run"
is right. `bund_eval.rs:31` takes `vm` directly.

**F32 reproduces.** `lambdas/registry.rs:88,89,90` register `register`,
then `unregister` → `stdlib_lambda_unregister`, then `unregister` again →
`stdlib_class_unregister`. The second wins.

**F18 is now 14 and 14.** `cargo xtask arity` prints exactly 14 rows, and the
register's list has 14 entries with `tail` restored.

**The world-file citation is right.** `world/lambdas.rs:81` is the
`l.to_binary()` call inside `for (n,l) in vm.lambdas.iter()`.

## A. Citation defects

**A1. `compile_and_apply.golden` does not contain `"get"` or `"swap"`.**
RFC:279-284 claims that golden "renders `dt: 6, q: 100.0, data:
String("println")`, and the same for `"+"`, `"format"`, `"get"` and
`"swap"`." The file contains three such renderings — `println`, `+`,
`format` — and no `get` or `swap` at any `dt`.

The underlying claim survives, misattributed: suite-wide the `dt: 6` census is
`println`×13, `get`×9, `format`×8, `swap`×7, `!`×4, `get,`×1, `+`×1 = **43**,
matching the RFC's own total. `get` and `swap` are golden-visible, in the
`object_oriented_programming` goldens, not in the one cited.

This is the same failure mode as review 1's A1–A3: the citation resolves, the
sentence around it does not hold. `cargo xtask cite` cannot catch it because
the target is a golden, not a `reference/` line — it is not checked at all.

No other citation in the RFC misstates its target.

## B. Internal contradictions

**B1. Two Design sections, the second one rejected.** Stated above. The
preservation row "A name bound as lambda and native at once — **Preserved
exactly.** Slots carry one `Option` per namespace" (line 424) is true of the
struct at line 203 and false of the enum at line 346, which is 78 lines closer
to it. Line 356-358 — "a name has exactly one meaning and the namespaces that
must stay distinct — commands, methods, vars — keep separate tables" — is the
sentence review 1 rejected, still present, and now also contradicting line 205
and line 210, where `command` and `method` *are* slot fields.

**B2. The `autoadd` preservation row contradicts §Resolution order.** The row
reads "The `autoadd` branch preceding all of it — **Preserved exactly**"
(line 420). It does not precede all of it: `apply` tests `is_command` at
`multistackvm_apply.rs:16` and returns through `c()` at `:17`, and only the
`else` reaches `if self.autoadd` at `:19`. The RFC's own numbered list gets
this right — command is step 2, autoadd is step 3. The observable consequence
is that with `autoadd` set a command still executes rather than being appended,
and the row as written promises the opposite.

**B3. Criterion 6 asks for something the grammar makes impossible.** It
requires that a name resolve "to the lambda by `name` and to the native by
`$name`, **for the same `Symbol`**" (line 480-481). Under
`reference/bund_language_parser/bund.pest`, `$` is not a token: `name` is
`element ~ nelement*` (`:28`) and `element` (`:36`) admits `SYMBOL`, the
Unicode category that contains `$`. So `$println` lexes as one name and interns
to a **different** `Symbol` than `println`. The reference strips the sigil at
run time, in `call_internal_word` (`:7`), not at parse time.

The RFC never says where `$` is handled. That is the one place where "interning
happens at parse time" has a consequence it does not follow through: either the
parser recognises the sigil and flags the `CALL` (in which case `bund.pest` is
being changed, and the RFC says the grammar "is what defines a name"), or the
sigil rides inside the interned string and criterion 6's "same `Symbol`" is
false as written.

**B4. `Arc<Registry>` cannot hold RFC-0001's values.** §"Registry builder"
freezes the builder into "an immutable `Registry` shared by `Arc`" (line 390)
and calls it "the change RFC-0007's actor model needs" (line 394). But `Slot`
holds `lambda: Option<BundValue>` and `class: Option<BundValue>` (lines
207,209), and RFC-0001's `BundValue` is `Heap(Rc<HeapValue>)` with `Cell`
fields — neither `Send` nor `Sync`. An `Arc` around a non-`Sync` type cannot
cross a thread boundary, so the `Arc` buys nothing an `Rc` would not, and the
actor-model claim does not hold. Review 1 of RFC-0001 raised the same
`Send`/`Sync` gap (its E5) and RFC-0001 still does not mention threads. This is
the first place the two RFCs actually collide, and neither cites the other.

**B5. Summary versus Design on how many tables collapse — review 1's D1, not
fixed.** The Summary still says "The seven name-keyed `HashMap<String, _>`
tables in `VM` collapse to one slot table" (line 40-41). The new design
excludes `vars` explicitly (line 241-244); the stale design excludes commands,
methods and vars (line 357). Three different answers in one document.

**B6. Open questions versus Design on methods and vars — review 1's D2, not
fixed.** Line 506-508 still says "Whether `methods_fun` and `vars` become
slot-table discriminants or stay separate tables is left to the
implementation", while `Slot` has a `method: Option<NativeFn>` field (line 210)
and the text settles `vars` (line 241).

**B7. The 498 is asserted, and every tool says 497.** Line 28 and criterion 2
state "the in-scope set goes 497 -> 498" and "D29 has moved the in-scope set to
**498**". `cargo xtask coverage` prints `words in scope 497` and
`COVERAGE 121/497`; `cargo xtask scope` prints 497. D29's own denominator
paragraph is forward-looking and correct — 498 is what the set becomes once
`stacks_left` exists — but the RFC states it in the perfect tense and names
`cargo xtask coverage` as the tool for it. A reader who runs the named tool
gets a different number with nothing explaining why. RFC-0000's B2, an accepted
RFC, pins 121/497.

## C. Behaviours the preservation analysis does not enumerate

**C1. `autoadd` has three branches; the RFC still covers one.** Review 1's C6,
unaddressed. `apply` tests `self.autoadd` at `:19` (CALL), at `:72` (CONTEXT —
where it pushes the context value instead of switching stacks, `:72-81`) and at
`:89` (the default arm, `:89-100`). The CONTEXT branch is a different
behaviour, not a repetition: with `autoadd` set, `@name` stops switching
stacks. RFC-0002 owns dispatch, so it owns this row.

**C2. `PTR` has no row.** Review 1's C3 asked for `CALL` *and* `PTR`; only
`CALL` got one. `PTR` is `Val::String` carrying a resolvable name, it is what
the `resolve` word produces, and it accounts for 30 golden renderings — a
number the RFC itself quotes (line 283-284) in the sentence that then only
disposes of `CALL`. If a `CALL` carries a `Symbol`, does a `PTR`? The RFC does
not say, and `ptr` is a distinct production in the grammar (`bund.pest:29`).

**C3. `unregister` through a per-VM overlay needs a tombstone.** Line 391 says
"Runtime mutation — `register`, `alias` — writes through a per-VM overlay".
`unregister` and `unalias` are also words (`reference/rust_multistackvm/src/stdlib/alias.rs:73`,
`lambdas/registry.rs:89-90`), and the RFC names them as such two lines earlier
at line 320. Removing a binding that lives in the frozen `Registry` cannot be
expressed by an overlay that only overwrites; it needs an explicit absent
marker. Without one, unregistering a builtin silently becomes a no-op — which
is F32's shape, reintroduced by the fix.

**C4. Slot-vector growth is monotonic; the reference's tables are not.** A
`Symbol` is an index into a `Vec<String>` and a `Vec<Slot>`. `unregister`
removes a `HashMap` entry today and the memory is reclaimed; under the slot
table the symbol and its slot persist. For a long-running process driving
`bund.eval` with generated names — which D16 keeps legal — that is unbounded
growth. Probably acceptable; it is a consequence of the design and it is
unstated.

**C5. The CLI tier is still unnamed — review 1's E2, unaddressed, and ERRATA
says it must be.** §"Seven name-keyed tables" describes the VM's tables plus
"the stack layer's own `inline_fun`… reached by fallthrough" (line 122-124),
which is two. `ERRATA.md` records, against
`00-jit-feasibility.md` §2 and `03-metaprogramming-oop-debugger.md` §1, that
there are **three** sources and ends: *"RFC-0002's slot table has to absorb all
three."* I counted them: `register_inline` is called 418 times in `Bund/src`,
160 in `rust_multistackvm`, 31 in `rust_multistack`. The first two land in the
*same* VM table, which is why the fallthrough story reads as two tiers — but
the RFC neither states that nor acknowledges the ERRATA entry that names it.

**C6. `StackEffect` "derived rather than hand-written" overstates the tool.**
Line 381-383 says `cargo xtask arity` "already extracts the reference's guards
mechanically and found 14 under-declared ones (F18), so the initial
declarations are derived". What the tool extracts is the *declared* guard —
the number F18 proves wrong for those 14 words — and its own output warns that
the probed column "needs reading before RFC-0004 trusts either number". So for
14 words the derivation is known-wrong and the RFC does not say which column it
takes. Review 1 asked for that ruling (its item 6); it is still open.

## D. Acceptance criteria, one at a time

1. **`conform` does not fall below the mark.** Checkable, tool exists,
   correctly reasoned — dispatch, not meaning.
2. **`coverage` against D14's partition.** Correctly marked `[BLOCKED: D14]`.
   The embedded 498 is the problem, not the blocking. B7.
3. **Dispatch allocates 0 times.** Honestly labelled as having no tool, and it
   names the future one. Good. Note the figure it answers — 13 — is for `dup`,
   an alias reaching the stack layer, which is the *worst* case; a VM-layer
   non-alias costs fewer. The criterion says "a word", so say which word.
4. **`cargo tree -p bund2-api`.** Labelled near-vacuous, as RFC-0001's
   equivalent is. Fine.
5. **`resolve` succeeds for all 31 stack-layer words.** Checkable, the count
   verified independently, and the reasoning about why it cannot be a golden is
   correct and is the best paragraph in the section.
6. **Lambda/native coexistence.** The behaviour is right and the mechanism is
   right; "for the same `Symbol`" is wrong. B3.
7. **World-file round trip across processes.** Checkable, and it is the
   criterion that catches C4 of review 1. Good.
8. **`cite` reports zero defects.** Passes today, and the RFC's own caveat is
   accurate — A1 is a fresh instance of exactly what it warns about, and
   `cite` does not look at goldens at all.

**Missing criteria.** Three preservation rows still have nothing that runs
them: the `autoadd` row (and it is wrong, B2), the `CALL`-renders-as-text row —
which is the one criterion 1 would catch only by accident, since a wrong
rendering fails a golden for an unrelated-looking reason — and the alias-chain
deviation row, which asserts "none is constructible in the corpus" with no
check named.

**D-1's handoff is premature.** Lines 491-496 hand RFC-0000's deferred
feature-gating criterion to RFC-0003 on the grounds that "this RFC declares no
feature". But the open half of D14 is precisely whether `bund2-api` is one
surface or two (line 406-409), and a separate library surface that out-of-tree
packages compile against is a feature declaration in everything but name. The
handoff is sound only if D14 resolves to one surface. Say so, or hold it.

## F. Assumed but not stated

1. **Where the `$` sigil is stripped**, and therefore whether it survives
   interning. B3.
2. **That `PTR` payloads follow the same rule as `CALL`.** C2.
3. **That the overlay can express deletion.** C3.
4. **That `Symbol` is dense and allocated in first-seen order**, which is what
   makes `Vec<Slot>` indexing valid rather than a sparse map. Never stated.
5. **That the interner is per-run**, so two runs of the same program may assign
   different `Symbol`s to the same name — fine, but load-bearing for the
   world-file rule and only implied.
6. **That a name's identity is its exact bytes**, including the `,` and `.`
   suffix axes (D22, D18): `format` and `format.` are different names, and the
   grammar admits both (`bund.pest:36` includes `,` and `.` in `element`).
   Interning makes that structural rather than conventional, which is an
   improvement worth stating.
7. **That names are whitespace-terminated** (`bund.pest:28,29`), which is why
   `run_snippet_for_script` appends `\n` (`run_snippet.rs:62`). A
   re-implemented `bund2-syntax` that tokenises differently changes what a name
   is.
8. **That the word set is read from compiled code only.**
   `reference/rust_multistackvm/src/stdlib/classes/registry.rs` exists, defines
   `register`/`unregister` words and an `init_stdlib`, and is **not a module** —
   no `mod classes` declaration exists anywhere in the crate, so it is never
   compiled. Any scan that enumerates words by reading the tree will pick up
   phantom registrations from it. Worth one sentence in an RFC whose subject is
   the word table.
