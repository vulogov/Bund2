## Findings, most serious first

### 1. The graph family is **core**, not library: R:97-99 cites a line that says the opposite

R:97-99: "The family is **library**, not core, under D14's partition
(`docs/core-words.md:16`), so it is outside the 100% preservation that
core words carry."

`docs/core-words.md:9` is the heading `## core`. `:16` sits under it:
`- **bund/graph** — graph graph! graph. graph.allpath graph.path graph.paths graph.transitiveclosure`.
The `## library` heading is at `:43`. The file has not changed since D14
resolved (`f62be91`). All seven reference graph words are core. D14 says
"Only the core 286 is a preservation target" (`decisions.md:740-741`).

The same error is in F17's note of 2026-10-18 (`defects.md:568-571`):
"the family is library (`docs/core-words.md:16`)". Both earlier reviews
marked this citation "yes". It has been wrong since the RFC was first
written.

Consequences:

- The RFC's preservation argument goes. F219's `found=false`
  (D193 §5) is a **deviation in a core word**. D193 rules it, so it is
  approved, but the RFC presents it as a change outside the preservation
  guarantee. Under D14 it is a change to a guaranteed word, and the RFC
  should say so.
- F17's sort still deviates from nothing, because the reference's order
  is unspecified. That argument holds whatever the family's scope, and it
  should not rest on R:97-99.
- Findings 2 and 3 below concern core words.
- **Repair:** correct R:97-99. Add a dated note to F17 (append-only)
  saying its 2026-10-18 note misread `core-words.md:16`.

### 2. `graph.allpath` answers `[ ]` when the last listed node has a negative out-edge, in both engines, and no register records it

`algos`' Johnson does not add a new vertex. It takes the **largest
existing vertex** as its source `q` (`johnson.rs:41-44`) and calls
`g.add_edge(q, v, 0)` for every `v` (`:45-47`). `add_edge` first
**removes** any existing `q → v` edge (`graph.rs:108-111`). So the
potentials come from a graph in which the last node's real out-edges have
been replaced by zero-weight ones. When one of those real edges is
negative, the reweighted weight `w + h_q - h_v` is negative (`:61-65`).
Dijkstra then refuses it, and Johnson **skips that source's rows
silently** (`:71-74`: `Err(_) => continue`).

```
[ [ :A :B 1.0 ] [ :B :C 1.0 ] [ :C :A -0.5 ] ] [ :A :B :C ] graph! graph.allpath println
```

oracle: `[]`. bund2: `[]`. The graph has no negative cycle (the cycle
weighs 1.5), and every pair is connected. List the same graph's nodes as
`[ :C :A :B ]` and both engines answer all nine rows, `C → A` at `-0.5`.
With `-5.0` in place of `-0.5`, there is a negative cycle. It is not
reported, and the answer is still `[]`.

- So **the order of the `nodes` list changes `graph.allpath`'s answer**,
  not only the order of its rows. S3 and F17 make node order the one thing
  every answer may depend on. The RFC never mentions that it does so here.
- "Current behaviour" (R:92-96) and Preservation's "negative weights"
  bullet (R:320-322) cover `graph.paths` and `graph.bellmanford` only.
  `graph.allpath` already takes negative weights, sometimes, and answers
  wrongly otherwise.
- `the_algos_words_answer_in_node_order` (`G:719-740`) uses only positive
  weights, so it cannot see this.
- This is an original-implementation defect in a core word (finding 1)
  that "preserved exactly" (R:301) carries without saying so. It belongs
  in `defects.md`. Its disposition (preserve, or not) is the owner's
  decision, not this RFC's to take silently.

### 3. F219's fix answers "no path" from an isolated node **to itself**, where an equivalent node answers a path

`graph_path` answers `{ found=false }` whenever either index is at or past
`fast_paths`' node count (`G:257-260`). D193 §5 and F219 justify this:
"No kept edge reaches such a node, so there is no path." That does not
hold when the start and the end are **one node**, because the empty path
always exists.

```
:C :C [ [ :A :B 1.0 ] ] [ :C :A :B ] graph! graph.path println
:C :C [ [ :A :B 1.0 ] ] [ :A :B :C ] graph! graph.path println
```

- First line, oracle and bund2:
  `{ found=true :: path=[ C ] :: weight=0.0 }`. C is isolated but is
  index 0, inside the size.
- Second line, oracle: panics. bund2: `{ found=false }`.

The two graphs are the same, listed in a different order. The fix makes
the answer depend on where the isolated node is listed, which is exactly
what S3 says must not happen. `:A :A list [ :A ] graph! graph.path` (no
edges) also answers `found=false`. The five graphs in
`graph_path_answers_no_path_for_a_node_no_kept_edge_reaches`
(`G:664-679`) all have start ≠ end. **Repair:** answer
`{ found=true, path=[ X ], weight=0.0 }` when `start_ix == end_ix`, as
`fast_paths` does in range. D193 §5 ruled on "no path", so changing the
same-node case needs that ruling revisited.

### 4. Finite weights still give infinite answers, and one case is a wrong answer: a negative cycle `graph.bellmanford` does not report

D193 §3 refuses non-finite weights because "none of the twelve words'
answers over one means anything". Sums of finite weights overflow just the
same, and nothing guards them:

```
:A [ [ :A :B 1.0e308 ] [ :B :C 1.0e308 ] ] [ :A :B :C ] graph! graph.bellmanford   → C path=inf
[ [ :A :B 1.0e308 ] [ :B :C 1.0e308 ] ] [ :A :B :C ] graph! graph.mst             → weight=inf
:T :S [ [ :S :T 1.0e308 ] [ :S :M 1.0e308 ] [ :M :T 1.0e308 ] ] [ :S :M :T ] graph! graph.maxflow → flow=inf
```

All three were run in bund2. The worst case is a **wrong answer**,
because `-inf` stops relaxation:

```
:A [ [ :A :B -1.0e308 ] [ :B :A -1.0e308 ] ] [ :A :B :C ] graph! graph.bellmanford
```

- bund2: `[ { node=A :: path=-inf } { node=B :: path=-inf } { node=C :: path=NODATA } ]`.
  A negative cycle reachable from A, **not reported**.
- Drop the unrelated node C (`[ :A :B ]`) and bund2 answers
  `GRAPH.BELLMANFORD: A reaches a negative cycle through A`.

Why: once a distance reaches `-inf`, `-inf + w < -inf` is false
(`GA:544`). With three nodes the extra pass finds nothing to relax and
`bellman_ford` returns `Ok` (`GA:558-565`). So S4's promise ("an
impossible question is an error") fails, and an isolated node changes
which answer comes back.

- No criterion reaches this. Every cross-check uses weights from -3 to 8
  (`GA:1666-1683`), or whole capacities up to 9e13 (`GA:2098`).
- S1's `graph.bellmanford` row (R:122) promises `path` or NODATA, never
  `inf`. S5's Edmonds–Karp argument (R:247-257) is sound, but `flow` can
  still be `inf`.
- **Repair:** check each sum for finiteness, which takes a ruling on what
  an overflow answers. One option: refuse it as D193 §3 refuses a weight,
  for example `GRAPH.BELLMANFORD: a distance overflows: A -> C`. Either
  way, this is a design gap D193 did not see, and it goes to
  `decisions.md`.

### 5. `graph.mst` orders `-0.0` before `0.0`, against S3's tie rule

S3 (R:174-175): "equal weights in the order the graph lists its edges".
`mst` sorts with `f64::total_cmp` (`GA:509`), which puts `-0.0` before
`0.0`, although `-0.0 == 0.0`. A Bund literal makes `-0.0` (`-0.0
println` prints `-0.0`).

```
[ [ :A :B 0.0 ] [ :B :C -0.0 ] [ :A :C 0.0 ] ] [ :A :B :C ] graph! graph.mst println
```

bund2: `edges=[ [ B C -0.0 ] [ A B 0.0 ] ]`. B–C is listed second but
comes first. `mst_is_minimal`'s order check (`GA:2044-2049`) compares with
`==`, so it would flag this, but its weights are whole numbers from -2 up
and never `-0.0`. Small, but the RFC states the rule exactly. Either sort
by `partial_cmp` over finite weights (which the reader now guarantees) or
state the rule as "total order".

### 7. Smaller points

- **R:189-190**: "so `B` need not be the smallest node on any cycle". Read
  literally, this contradicts the sentence before it, because `B` *is* the
  smallest node of the cycle found. The meaning is "on every reachable
  cycle" or "of all reachable cycles".
- **R:62-68**, "both readers": the unknown-node refusal cites only
  `make_graph`'s `:114-116`. `make_fast_graph`'s is `:48-50`.
- **Criterion 9** (R:393-396): "read by `read`, open and closed into a
  cycle". The open chain goes through `read` (`GA:1288-1303`). The closed
  one is made by pushing onto `closed.edges` and `closed.out` by hand
  (`GA:1309-1311`), so `read` never sees a 200,000-node cycle. The
  algorithms are called directly, not through the words.
- **Criterion 3**, `bellman_ford_agrees_with_floyd_warshall`
  (`GA:2004-2026`): it checks that `u` is the least node of *some*
  negative cycle, among nodes ≥ `u`. That is consistent with S4 as
  restated by D193 §2, but weaker: it does not check that the cycle is the
  one the walk back found. Fine as a criterion, as long as it is described
  that way.

## Preservation analysis: what it does not enumerate

1. **Scope.** The seven words are core (finding 1). Every "deliberately
   changed" item is a change to a guaranteed word.
2. **`graph.allpath`'s answer depends on node order** with a negative
   out-edge on the last node (finding 2). It is preserved, but not stated.
   A program moving from `graph.allpath` to `graph.bellmanford` sees
   different answers for the same graph.
3. **F219's same-node case** (finding 3): `found=false` where the
   reference's in-range behaviour answers a path of one node.
4. **Overflow** (finding 4): the new words answer `inf`/`-inf`, and in one
   case miss a negative cycle, where D193 §3's reasoning says they should
   refuse.
5. **`-0.0` ordering in `graph.mst`** (finding 5).

## What the RFC assumes but does not state

- That the graph family is outside D14's core (false; finding 1).
- That `graph.allpath`'s set of answers is independent of the order of
  `nodes` (finding 2).
- That a node `fast_paths` did not number has no path to anything,
  itself included (finding 3).
- That sums of finite weights stay finite (finding 4).
- That `total_cmp` and `==` agree on the weights the reader admits
  (finding 5).
- That `conform`'s denominator is fixed while the RFC is in review
  (finding 6).

## Disposition

**Not ready for Accepted.**

- **Finding 1** is a misread citation, but the misreading carries the
  RFC's preservation argument. It needs the text corrected and a note on
  F17.
- **Findings 2 and 3** are behaviour in core words that the RFC calls
  preserved or fixed, and each answer depends on how `nodes` is ordered.
  Finding 2 needs a `defects.md` entry. Finding 3 needs D193 §5 revisited
  for the same-node case.
- **Finding 4** is a wrong answer in a new word (an unreported negative
  cycle), plus infinite answers D193 §3's reasoning excludes. It needs a
  ruling in `decisions.md`.

Findings 5–7 are small repairs to text or tests.
