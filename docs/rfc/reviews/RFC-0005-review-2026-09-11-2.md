## 1. Blocking

### B1 — an exit recorded by a drained body is seen one native too late

**What §S5 now promises.** "A recorded exit becomes the error status at the
call that recorded it" (lines 762–763), through four places: the per-native
adapter, the resolving trampoline, the entry trampoline, and the frame loop's
compiled entry (lines 764–771). "Compiled code's existing error path does the
rest … so no body runs another op after the exit" (lines 773–776).
Assumption 19 says every way a program stops "is visible to compiled code at
the call that caused it" (lines 2049–2053).

**The helper the list leaves out.** After any call that filed a request,
compiled code calls a **drain helper** that does "`take_pending`, then
`run_to`" (§S5, lines 819–825). §S8 counts it as a third place a body starts
(lines 1838–1840). It is not a native, so no adapter wraps it. It does not
run `dispatch`, so it is not the resolving trampoline. When the drained body
is interpreted, no entry trampoline runs either.

**Tier 0 does not gate the end of a body.** `Interp::run_to` pops a finished
frame and carries on, with no gate at the pop (`crates/bund2-interp/src/lib.rs`,
`run_to`, the `Some(None)` arm). `Interp::exit_gate` is called only at the top
of `Interp::apply_step` and of `Vm::eval_lambda` (same file). So when
`bund.exit` is the **last** word of a body, `run_to` returns `Ok`. Tier 0
stops anyway, because the next thing it does is an `apply_step`. The next
thing compiled code does after a drain is its own next op.

**The program.** `bund.exit` as the last word of an `if` branch inside a loop,
which is the ordinary way to quit:

    3 { "tick" println true { "bye" println 7 exit } if "after if" println } times
    "end" println

At Tier 0 it prints `tick` and `bye`, and exits 7 (run in this session).

Take the `times` body compiled and the branch body interpreted:
1. `if` (`opaque(2)`) files a request through `tail_lambda`
   (`crates/bund2-stdlib/src/control.rs`, `if_base`) and returns `Ok`. The
   adapter finds no exit recorded and returns success.
2. The request cell is set, so the drain helper runs `take_pending` and then
   `run_to`. The branch prints `bye`, pushes `7`, and calls `exit`. That goes
   alias → `dispatch` → `bund_exit` → `request_exit(7)`, which returns `Ok`.
   The frame ends, `run_to` returns `Ok`, and the drain returns success.
3. The epoch and `autoadd` are unchanged. The compiled body pushes
   `"after if"` and calls `println` through its slot. The adapter runs
   `println`, which **prints `after if`**, and only then finds
   `exit_requested` and returns the error status.

The output gains a line, so a golden of this shape would move.

**When the branch body is interpreted.** Whenever it has not reached §S7's
64 entries. That is exactly the shape above once the loop is hot, because the
quit branch runs once. It is also interpreted whenever it declines below the
Tier 1 floor (§S8, *A decline is a return*), at any threshold.

**Why no criterion sees it.**
- Criterion 2's threshold-1 run compiles the branch body too. Its tail call to
  `exit` then goes through the resolving trampoline, which does check.
- The corpus probes put `exit` mid-body (`tests/probes/bund-exit.bund`) or at
  top level (`tests/probes/bund-exit-word.bund`).
- Criterion 30's compiled cases put `exit` in the compiled body itself.

None of them has a compiled caller whose interpreted callee ends in `exit`.

**Two more helpers of the same kind.**
- **The tail hand-back into a compiled caller.** A body-to-body slot call
  (line 1628) has no entry between the bodies. A request the callee returns
  pending is therefore drained by the caller, which is the case above.
- **§S5's residual path.** It applies the rest of a body "one at a time
  through the runtime's `apply`" (lines 704–706). `Interp::apply` is
  `apply_step`, then `take_pending`, then `run_to` (same file, `Interp::apply`).
  If the last value applied is `exit`, or a call whose body ends in one,
  `apply` returns `Ok`. The function then returns status 0, and a compiled
  caller runs on.

**Required:**
- **Close the set of helpers, and make it structural.** Every Rust helper that
  runs Bund code on compiled code's behalf and then returns to it must turn a
  recorded exit into the error status: the adapter, the resolving trampoline,
  the drain helper and the residual path's apply. The helper list will go
  stale as a hand-kept list does (S1). The safer form is one function through
  which every helper's `Result` becomes a status and which consults
  `exit_requested`. Then no helper can be added that forgets the check.
- **Or reconsider the exit cell** that lines 777–781 rejected. It costs a load
  per call, and it needs no enumeration. That is the argument §S5 itself makes
  for the epoch ("Rather than enumerate every word … compiled code re-reads
  the state after every call", lines 694–700). Either choice closes B1. The
  status approach is sound only if the set of helpers is closed.
- **Reword assumption 19 and lines 773–776.** An exit is visible at the
  *helper that returns to compiled code*, not "at the call that caused it".
- **Extend criterion 30.** Cover a compiled caller with:
  - a cold lambda callee whose last word is `exit`;
  - the same reached as an `if` branch;
  - a body on the residual path whose last value is `exit`;
  - a callee that declines below the Tier 1 floor.

  Follow each by a `println`. These cases must run with the callee held below
  the threshold, since threshold 1 hides the defect.
- Name the drain and the residual path in Preservation row 2195.

## 2. Significant

### S1 — the re-entering set is derived in prose only, and the day's list is already short

§S8 says the path set is "every `bund2-stdlib` function that calls
`Vm::eval_lambda`, `Vm::apply` or `Vm::scoped_call`, found by a source scan as
criterion 25 finds `Error` reports". It then prints the set "on 2026-09-11"
(lines 1890–1900). **No such scan exists.** `crates/bund2-stdlib/src/lib.rs`
carries criterion 25's scan (`no_native_reports_at_error_severity`) and
nothing for re-entry. So the printed set is still a hand list, and it is
already short.

I ran the scan by hand: the three methods, over `crates/bund2-stdlib/src`,
outside tests. It finds 22 sites. The RFC's list names `times`, `loop`, `map`,
`while`, `for`, `*loop`, `input*`, the conditionals, `?try`, the method paths,
`context` and `eval_source`. It misses:
- **`execute_value`** (`crates/bund2-stdlib/src/values.rs`). `!` and `execute`
  handed a name call `vm.apply(BundValue::call(name))`. `!` is the corpus's
  second commonest first stop (17 of 116).
- **`apply`** (`crates/bund2-stdlib/src/singles.rs`, registered `opaque(1)`),
  through `Vm::apply`.
- **`?.` and `?MOVE`**, through `conditional_move`
  (`crates/bund2-stdlib/src/singles.rs`) → `Vm::eval_lambda`. These are
  natives, not conditional runners, so "the conditionals" does not obviously
  cover them.

(`run_csv` and `run_sqlite` in `data.rs` are registered with
`register_conditional`, so "the conditionals" covers them.)

**Tier 0 blames the wrong words again.** `:f { "f" ! } register f` recurses
through `execute_value` → `Vm::apply` → `run_to`, spending one Rust frame per
level. The floor holds: the program reports and exits 0. But the report says
"recursion through a word that runs a lambda or evaluates source — `times`,
`loop`, `map`, `while`, `for`, `*loop`, a conditional, `?try`, a method,
`bund.eval` or `use`". `!` is not among them. That is the eleventh review's S1
one word over. Line 1974 says the error "names the cause".

**Two places still assume a list.** Criterion 11 reports `c_p` and `δ_p` "for
each path §S8 lists" (lines 2579–2581). Preservation row 2150 names `times`,
`loop`, `map`, a conditional, `?try` or a method.

**Required:**
- **Build the scan as a test**, beside criterion 25's, and let criterion 11
  take its path set from that test's output.
- **Add `!` and `execute` by name, and `apply`, as paths.** For `!` by name,
  `c_p` is `Vm::apply`'s plus `execute_value`'s frame.
- **Fix the message.** Either name `!` or say "a word that runs a lambda,
  evaluates source or calls a name". That is D36 presentation, not meaning.
- **Correct line 2580 and row 2150.**

## 5. Preservation analysis — what the table does not enumerate

1. **An exit recorded by a body the drain ran**, by a declined callee, or by
   the residual path's last value. Tier 0 runs nothing more. Compiled code runs
   every literal and inlined op up to the next native, and runs that native
   too (B1).
2. **Native nesting through `!` by name, `apply`, `?.` or `?MOVE`.** Nothing
   measures its per-level cost, so `m` may be too small for it. The message
   Tier 0 gives there names other words (S1).
3. **A native that observes beyond its operands only when handed a lambda or
   an object**, whose tuples D55's comparison skips (§7, item 5).

Three existing rows contradict the design or the code:
- row 2150 carries the old list of re-entering words (S1);
- row 2173 leaves `swap_in` out of what D55 found (S2);
- row 2182 says fourteen operand kinds (S2).

## 7. What the RFC assumes and does not state

1. **The end of a body is a step at which the gate runs.** It is not.
   `run_to` pops a finished frame without the gate, and Tier 0 is saved only
   because its next action is an `apply_step` (B1).
2. **Only natives under an adapter, and `dispatch` under the resolving
   trampoline, run Bund code on compiled code's behalf.** The drain helper and
   the residual path's `apply` do too (B1).
3. **The set printed in §S8 is a scan's output.** It is a hand list (S1).
4. **The committed `PROMOTABLE.txt` is the one D55 produced.** At `HEAD` it is
   not (S2).
5. **A native that observes beyond its operands shows it on some tuple with no
   lambda or object operand.** D55's comparison skips tuples containing either
   (`f14_kind` in the palette test). The breach, observation and padding
   checks still run on them. `curry`, which takes a lambda, is on the list.
6. **A stack-name operand is always among the top two.** The palette varies
   only the top two operands; deeper ones are always `7`, so a name in third
   place or lower is never `"main"`. That holds today: every fixed-effect
   native in `stack.rs` that takes a name consumes at most two operands. It is
   a property of today's words and nothing enforces it.
