## Verdict

**One blocker, eight significant findings.** The bundle half is close. The
front end has gaps the RFC reports as settled, and two of the claims it
carries into D77 are wrong about the code, although D77's conclusion does not
depend on them.

- **B1.** §B3 lists "four things the artefact's front end must settle". The
  CLI accepts three more flags that change **what words do**: `--noio`,
  `--noeval` and `--nocolor`. It also has a defined path for a program that
  does not parse. The RFC mentions neither. `--noio` is a sandbox the
  reference offers, and whether a bundle can have one is the owner's call, so
  "nothing in this document is open" is not yet true.

## B1 — the front end omits the host flags and the parse-failure path

The CLI's `parse_args` accepts `--noio`, `--nocolor` and `--noeval`
(`crates/bund2-cli/src/main.rs:236-240`), and each is the reference's
(`reference/Bund/src/cmd/mod.rs:139-146`: "Disable I/O group of functions",
"Disable bund.eval group of functions", "Disable colors in output"). They
flow into `HostOptions` (`crates/bund2-stdlib/src/host.rs:32-35`) and from
there into `Runtime::with_options_and_threshold` (`main.rs:436-437`). In
other words, they decide which words fail.

§B3 lists only the diagnostic flags (`--stats`, `--dump-stack`,
`--raw-values`, `--jit-threshold`), says they "move to environment
variables", and puts the diagnostic ones in the Preservation table. The
host flags are in neither place. Under §B3's rule, "all of argv reaches
`args`", a bundle's I/O words are **always enabled and cannot be disabled**,
which is a behaviour the reference's user had and the bundle's user does not.
That may be the right answer. It is still a decision, and the design does not
take it:

1. Always off. A bundle cannot be sandboxed, and the table must say so.
2. Fixed at build time (`bund2 build --noio`), recorded in the trailer.
3. Read from the environment, like the diagnostic flags.

Option 3 lets whoever runs the artefact change what the program's words do.
Option 2 lets whoever builds it make that choice. These are not
interchangeable, and D76 has already given the person running the artefact
responsibility for what it fetches, which bears on the choice.

**The parse-failure path is also unstated.** The CLI parses at run time and,
when that fails, reports through the reporter and exits 0
(`main.rs:446-455`, and D36's "the process exits **0**",
`decisions.md:1939-1945`). Under §B1, `bund2 build` could either:

- **parse at build time and refuse**, which is a deviation from `script`,
  where the same program runs, reports and exits 0; or
- **not parse**, and ship an artefact that reports a syntax error on every run.

Either can be defended. The RFC picks neither.

**What is needed.** Add the three host flags and the parse-failure path to
§B3's list and to the Preservation table, each with a disposition. Put the
host-flag choice to the owner.

## Significant

**S1 — §B2.3 overstates the boxing finding, and D77 repeats the overstatement.**
The RFC says that under the wire codec "no arithmetic fragment would ever
admit: Tier 0's fragment fast path **and all of §S6's inlining** would be dead
… and RFC-0005's **promotion machinery would never fire**". The Tier 0 half is
right: `admits_with` matches `Some(BundValue::Int(_, _))` only
(`crates/bund2-ir/src/fragment.rs:163-167`). The Tier 1 half is wrong:

- Tier 1 classifies a literal by `v.dt() == INTEGER` and then `v.as_int()`
  (`crates/bund2-jit/src/lower.rs:1904-1912`). `as_int` looks through boxing,
  `BundValue::Heap(h) => match &*h.payload { Payload::Scalar(inner) =>
  inner.as_int()` (`crates/bund2-value/src/lib.rs:700-709`), and `dt()` of a
  boxed value is its heap `dt` (`:1182`). A boxed int literal therefore
  becomes `Plan::Literal(n)`, which is promotion.
- A promoted site's `TopAreInt` guard is answered **statically** by the model
  of known int literals, and `jit_admits` is not consulted
  (`lower.rs:478-481`, `takes_registers`). So inlining over promoted literals
  fires as well.

The first review had this right: Tier 1 **accepts** the boxed form and pushes
a fresh unboxed int, so the two tiers disagree about the literal's stamp. The
revision dropped that point and replaced it with a claim the code
contradicts. "A bundle would be slower than the interpreter" was never
measured either.

**D77's conclusion survives**, because stamps, context names and spans are
each sufficient on their own. However, D77's own text says "every scalar
returning boxed, so `Guard::TopAreInt` admits nothing and Tier 0's fragment
path and all of §S6's inlining die" (`decisions.md:3517-3520`). Registers are
append-only, so this needs an amendment note on D77 rather than an edit. The
RFC's §B2.3 should say "Tier 0's fragments decline, and Tier 1 promotes the
same literal, so the two tiers disagree".

**S2 — §B2.1 cites D2 for the opposite of what D2 decided.** The RFC says:
"D2 rules that out in terms: '`stamp` is creation time', and a lazy stamp
'must still answer "when was this value constructed", which rules out
sampling the clock at observation time'". Those words are in D2
(`decisions.md:78-84`). They are the **constraint recorded before the
decision**. The decision itself follows:

> **The clock is not read at construction at all.** The stamp is sampled when
> it is first observed. … This is a **deviation from 100% preservation** …
> `.timestamp` stops meaning "when this value was constructed" and starts
> meaning "when this value was first asked".
> — `docs/registers/decisions.md:92-101`

So D2 is the approved deviation that makes a stamp an observation time. A
build-time stamp is still wrong under D2, because the first observation
happens at run time, and so the conclusion stands. The argument is simply
cited backwards. D77 repeats it: "stamps fixed at build time (against D2's
'stamp is creation time')" (`decisions.md:3515-3516`). The Preservation row's
reason, "literals are constructed at run time", should say "sampled at first
observation, which is at run time (D2)". As written it describes the
construction-time model D2 rejected.

**S3 — §B5 leaves out the helper imports, and those alone make criterion 7
unsatisfiable as written.** §B5 lists two gaps: baked immediates, and planning
against a live VM. There is a third. The word lowering imports eight helpers
as `Linkage::Import` functions: the admits adapter, `jit_residual`,
`jit_stack_moved`, `jit_pop_int`, `jit_push_int`, `jit_dup_top` and
`jit_drop_top` (`lower.rs:2363-2404`). It binds them by address through
`JITBuilder::symbol` (`lower.rs:2250-2260`). In an `ObjectModule`, **each
call to one of them is a relocation targeting a function.**

Criterion 7 inherits RFC-0005 criterion 4's rule, "no relocation targeting a
function beyond §S8's two", with the two being thunk-to-adapter and
trampoline-to-body (`RFC-0005:4196-4200`). The helper calls are neither, so
today's lowering fails criterion 7 even after §B5's (1) and (2) are built.
§B5 needs a point (4): either route helpers through slots the way natives
are routed, or have criterion 7 name the helper relocations as permitted. The
same criterion 4 has a second half, "every call slot's target is a `Tail`
thunk or a `Tail` body" (`RFC-0005:4200-4202`). Criterion 7 still drops it,
as the first review noted.

The first review also asked about the relocation model (PIC) and what the
runtime library exports. §B5 answers neither.

Separately, §B5's block quote ("§S6's cells, addressed as an immediate…") is
presented as the justification for `slots_base`. That comment is about
`cells`: it sits between `iconst(ptr, slots_base)` at `lower.rs:2549` and
`iconst(ptr, cells)` at `:2553`, and it names "§S6's cells". `slots_base`
(`:2341`) has no comment stating why it is safe. The argument's conclusion
holds for both immediates, but it quotes the code as saying something it
does not say.

**S4 — two of RFC-0005's hand-offs to this RFC are unanswered.**

- **Q28, s390x.** "What remains of Q28 is whether s390x is a platform Bund2
  ships for at all, which §S10's portability story answers for the
  interpreter and **RFC-0006 will answer for AOT**" (`RFC-0005:6588-6591`).
  §B6 does not mention s390x.
- **Ahead-of-entry compilation reopens an exclusion.** RFC-0005 excludes two
  of its thirteenth review's mirror cases "only while §S7 compiles on an entry
  rather than ahead of one. **If that changes** — an ahead-of-entry or
  background compile, **which RFC-0006 may want** — the mirrors become
  writable and this row reopens" (`RFC-0005:6555-6562`). §B5(3), "which
  bodies compile at build time", is exactly that change. It should say that it
  reopens RFC-0005's row, and criterion 8 should include those mirror cases.

RFC-0005's other four hand-offs are answered: conformance (`:3917-3921`,
criterion 8), relocations (`:4187`, criterion 7), cells through a data symbol
or helper (`:2488-2490`, §B5(1)), and the audit (`:95`).

**S5 — "no artefact of either shape exists in the wild" is false. The words
that emit the reference's object bytes are reachable.** The RFC is right that
the two *producers*, `Value::compile` and `compile_to_binary`, have no
callers. I re-ran the grep and found one test caller and zero respectively.
The RFC's conclusion is wider: "neither is reachable from a Bund program, so
no artefact of either shape exists", and the Preservation row says "nothing
can depend on either". The shape is reachable by another route:

- The Bund word `compile` parses a string and pushes a LIST of its tokens
  (`reference/Bund/src/stdlib/functions/bund/bund_interpreter.rs:29-43`,
  registered at `:76`). That is `compile_to_binary`'s intermediate
  (`reference/bund_language_parser/src/compile.rs:6-21`), apart from stopping
  at EXIT.
- `encode.base64` calls `to_binary` on any value
  (`reference/Bund/src/stdlib/functions/encoding/base64.rs:33`, registered at
  `:121`). So does the bus (`reference/Bund/src/stdlib/functions/bus/mod.rs:88`),
  and so do zenoh publish (`reference/Bund/src/stdlib/helpers/zenoh/pubsub.rs:22,60`)
  and the world model (`reference/Bund/src/stdlib/helpers/world/models.rs:90`).

`"…" compile encode.base64` is therefore base64 of exactly the bincode
`compile_to_binary` would write, and a Bund program can build it and store it
wherever it likes. The shape exists as text, even though it never exists as a
file.

For this RFC that costs little, because a bundle reads neither format. It does
mean the Preservation row should say "a bundle reads neither", not "nothing
can depend on either". The same gap is in **D11**'s "No other word emits a
compiled object" (`decisions.md:476-485`). That entry is not this RFC's to
edit, but it should get a finding or an amendment. D31 covers the world file.
It does not cover `encode.base64`.

**S6 — "Diagnostic source locations: Preserved" does not say what the
location's file is. A golden pins it, so criterion 2 will see the
difference.** `run` builds each location with `locate(src, file, span)`, where
`file` is the path given to `--file` (`main.rs:430, 453-461`). `Location`
displays as `{file}:{line}:{column}` (`crates/bund2-api/src/diag.rs:68-75`),
and D36 puts it in the report's `Location` row (`decisions.md:1949-1955`).
Goldens capture **stdout and stderr together** (`xtask/src/golden/mod.rs:416-418`),
and an approved deviation pins a **hash of Bund2's exact output**
(`xtask/src/conform/deviations.rs:13-18, 125-130`).

Run from `reference/Bund`, `bund2 script --file
../../tests/probes/execute-arm-not-executable.bund` prints `│ Location ┆
../../tests/probes/execute-arm-not-executable.bund:14:4 │`, and that golden is
an approved deviation under F66 (`tests/golden/DEVIATIONS.txt`). A bundle's
trailer, as §B1 and §B4 list it, holds a magic, a version, SHAs, a length and
features. It has **no file name**. A bundle therefore prints something other
than that path, the hash drifts, and the CEILING moves.

Criterion 2 would catch this, which is to its credit. The design should still
say what the file is. The honest choice is the path as given to
`bund2 build`, stored in the trailer.

Criterion 2 also needs a runner. `run_once` spawns `exe script --file <path>`
(`golden/mod.rs:366-371`), and a bundle, under §B3, passes all of that to
`args`.

**S7 — criterion 3 still passes today, and it now contradicts criterion 6 and
§B4.** "The shipped runtime contains no code generator … listing neither
`cranelift-codegen` nor `cranelift-jit` in a default build". The default build
of `bund2-cli` already lists neither (`crates/bund2-cli/Cargo.toml:29-33`;
`crates/bund2-jit/Cargo.toml:52-55` makes both optional), so the criterion
passes with no bundle in existence, which the revision says it was rewritten
to prevent. Two contradictions:

- **Criterion 6** requires "a bundle built with `jit`", and **§B4** has
  `--features` select among shipped runtimes. A `jit` runtime is a shipped
  runtime and does contain `cranelift-codegen` and `cranelift-jit`. The
  criterion's title is false for the one runtime criterion 6 needs.
- `cargo tree` checks a dependency graph, not a binary. If the claim is about
  the shipped binary, check the binary, for example for Cranelift's symbols.

The first review's other point also still stands: §B5(3) says the **native**
image ships no code generator, and no criterion checks that.

**S8 — ERRATA's RFC-0006 entry names the wrong section, and leaves a
contradiction unrecorded.** ERRATA says "`02-native-binaries.md` §9 ->
superseded by RFC-0006 §B1 and §B5: the `include_bytes!`-and-link
construction it describes…" (`docs/research/ERRATA.md:123-127`). The
`include_bytes!` construction is in **§1**
(`docs/research/02-native-binaries.md:44-46`), and it is what §B1 cites.
§9 (`:245-266`) describes phasing and "the same lowering", which is §B5's
concern. Two more research claims contradict decided design and have no
ERRATA line:

- §1's Product A row gives startup as "**deserialise IR**" (`02-native-binaries.md:40`).
  D77 decides to parse source text instead.
- §1's "runs anywhere Rust runs" (`:46`) became, under §B1, "gated on having
  that runtime". The RFC's own Summary still repeats the unqualified form:
  "Runs on every target Rust runs on" (RFC line 35).

## Minor

- **Stale sentence from the first draft.** §B3 ends with "the decode happens
  **on that thread**, where a depth of 256 is known to be safe" (RFC lines
  228-229). Nothing is decoded under §B2, and 256 is the wire cap that
  criterion 5 says does not apply. It should say "the parse", and cite F116's
  measurement of where the recursive-descent parser aborts
  (`crates/bund2-syntax/src/lib.rs:745-749`).
- **The quote in §B3 is still trimmed without an ellipsis.** The comment
  continues past "every compiled body declines" with ": criterion 2 would
  then pass with no compiled code having run at all"
  (`crates/bund2-cli/src/main.rs:58-62`). The first review raised this.
- **The header's decision lists do not match the body.** D44 is listed as
  consumed and never appears in the body. It belongs in §B3, because D44 is
  why the thread's size is not part of meaning. D45 (§B3) and D52 (the exit
  code) are relied on and not listed. D1 is "touched … see the preservation
  table", and the table never mentions it.
- **The exit code is `vm.exit_requested()` masked to 8 bits** (`main.rs:161-164`,
  and D52: "keeping the low 8 bits as Unix `exit` does",
  `decisions.md:3113-3115`). §B3 should say "as the CLI does, D52". A failure
  to *start* exits 2 in the CLI (`main.rs:145-153`). A bundle's equivalent is
  a missing or corrupt trailer, and its behaviour there is unstated (see
  assumptions).
- **The parse measurement is `compile`, not the path a bundle runs.**
  `startup/parse/mixed` times `bund2_syntax::compile(src)`
  (`crates/bund2-bench/benches/interpret.rs:181-184`), which is
  `lower(&parse(src)?)` (`crates/bund2-syntax/src/lib.rs:678-680`). The bundle
  runs `parse` and then `lower_with_spans` (§B2), which builds a second vector.
  The order-of-magnitude conclusion almost certainly survives, and the same
  file's comment says process spawn dominates end-to-end runs
  (`interpret.rs:168-169`). The figure is still labelled as the thing the
  bundle pays, and it is not. Neither figure has a recorded output in the
  repository, so neither can be re-derived from anything checked in.
- **`MAX_NESTING` and "1024 levels" are right** (`crates/bund2-syntax/src/lib.rs:174`),
  and the interpreter already runs a 1024-deep LIST, lambda and context on
  both build profiles. Criterion 5 is testing the bundle path, not a limit.
- **§B4's trailer record of features has no reader.** The trailer is written
  from the runtime it was copied from, so nothing can disagree with it. Say
  what reads it, or drop it. "The pinned SHAs" is also ambiguous. In this RFC
  the phrase means `reference/`'s SHAs, which mean nothing inside an
  artefact. Bund2's own commit is presumably what is meant.
- **"AOT" is a defined term** — "the `cranelift-object` build"
  (`docs/rfc/RFC-0000-architecture.md:269, 286`; CLAUDE.md) — and the title
  uses it for a bundle, which is not one. An `aot` feature already exists,
  with the comment "Build this before the JIT" (`crates/bund2-jit/Cargo.toml:52-54`),
  and the RFC does not mention it. Both points were carried over from the
  first review.
- **D50.** `sysinfo.version` reports Bund2's own version
  (`decisions.md:3006-3012`). In a bundle, that is the *runtime's* version,
  which may not be the version of the `bund2` that built it. This is a one-line
  Preservation row.
- **Verified and correct:** `RFC-0003:422` (the "cache over a body" sentence);
  `bincode.rs:38-50` (non-LAMBDA refused at `:39-41`, then `to_binary`);
  `bincode-test.rs:103` (the only `.compile()` caller); `compile.rs:6-30`
  (`bund_vec_to_list` at `:6-12`, `compile_to_binary` at `:23-30`, zero
  callers); `02-native-binaries.md:44-49`; `file_helper.rs:42-54` (no
  `follow_location`, no `fail_on_error`, no size cap, transport error to

  `MAX_WIRE_DEPTH` at `wire.rs:140`; `wants_stack` at `report.rs:128-130`;
  `a_tier_with_no_share_compiles_bodies_and_enters_none` at `tier.rs:1367`;

- Whatever B1 decides for `--noio`.

## Preservation analysis — what the table is missing

The table now has fourteen rows and covers the first review's nine. The
design can also change these:

1. **`--noio` / `--noeval` / `--nocolor`**: which words fail, and whether a
   bundle can be sandboxed at all (B1).
2. **A program that does not parse**: refused at build, or reported at every
   run (B1).
3. **The `Location` row's file**: what path a bundle reports, which an
   approved deviation's hash pins (S6).
4. **Tier agreement on a literal's stamp**: preserved, because scalars stay
   unboxed. The row that says so gives the wrong mechanism for the rejected
   design (S1), and its `.timestamp` neighbour gives the wrong reason (S2).
5. **`sysinfo.version`**: the runtime's version, not the builder's (D50).
6. **The exit code when the artefact cannot find its own payload**: exit 2,
   as the CLI does for an unreadable file, or something else.
7. **RFC-0005's mirror-case exclusion under build-time compilation**:
   reopened by §B5(3) (S4).
8. **The `jit` threshold and its environment variable**: `BUND2_JIT_THRESHOLD`
   is read by the runtime, so a bundle's tier behaviour depends on the
   environment of whoever runs it. The effect is on speed only, but it should
   be stated beside the diagnostic flags.

## Assumptions the RFC makes and does not state

1. **What each host flag is in a bundle**, and who chooses it (B1).
2. **Whether `bund2 build` parses the source** (B1).
3. **That the prebuilt runtime can find and read its own executable.**
   `std::env::current_exe` is platform-dependent, and a missing trailer has
   no stated error path.
4. **That appending bytes to a runtime executable leaves it runnable and
   distributable** on each platform. `[UNGROUNDED]` in this repository,
   because the constraint is external. It needs stating because the known
   interactions are with code signing (a signed Mach-O or Authenticode
   signature does not cover appended bytes, and macOS on arm64 requires a
   valid signature to run) and with tools that strip or rewrite binaries.
   This should go to `docs/registers/open-questions.md`. It is the one
   question §B1's construction depends on and nobody has asked it.
5. **How `bund2 build` obtains runtimes**: shipped with `bund2`, downloaded,
   or built by the user. §B1 says "ships or locates", and for a target
   Cranelift does not support this is a distribution decision, not an
   implementation detail. `02-native-binaries.md:212-213` also says
   "pre-linking a template executable and patching code into it is writing a
   linker with extra steps". §B1 appends data, not code, which is why it
   escapes that objection, and it should say so.
6. **What the Location's file is** (S6).
7. **That criterion 2's runner exists** (criteria table).
8. **That the helper functions will be exported by the runtime under stable
   names**, for native (S3).
9. **That s390x is or is not a target**, for native (S4).
