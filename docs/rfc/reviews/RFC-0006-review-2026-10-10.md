## Blocking

### B1 — D133 is an approved deviation with no preservation row, and the row beside it says the opposite

D133 was ruled today: Bund2 reads a response one way on every system, and
where the Linux reference differs "that is an approved deviation there"
(`docs/registers/decisions.md`, D133, "The ruling"). Sixteen rows. The
status header has it, §B7 has it, the open questions have it. The
preservation table does not: `D133` occurs nowhere between "## Preservation
analysis" and "## Alternatives considered".

The row that should carry it is the fetch's, and three of its sentences are
now wrong:

1. **"The Linux measurement is of the tree before D131 and has none of the
   rows about a response."** It is of `6c84d9e`, the commit of D131, and
   has all 741 rows (`docs/measurements/fetch-linux-2026-10-09.md`, first
   paragraph). The status header corrected this sentence where it stood
   there — "*(Until 2026-10-10 this said Linux had not been measured since
   D131.)*" — and §B7 corrected it too. The table was not touched.
2. **"In all of these but D125's Bund2 fails closed, and in no measured row
   does it ask a listener the reference does not or fetch other text."** On
   Linux, measured: in rows 570, 660, 734 and 735 Bund2 fetches where the
   reference fails — the empty string once and a body three times — and in
   621, 622, 655, 658 and 659 the two fetch different text (D133's table;
   the Linux file, "What differs between the two binaries"). The sentence
   cites the macOS file, and of that file it is true. The row does not say
   it is about one system, and its next sentence is about two.
3. **"Preserved per system: … Bund2 follows it where that was found
   (D130)."** D133 is the second place it was found, and there Bund2 does
   not follow. D133 says so of itself: "This is D130's question again", and
   answers it the other way.

And the list of approved differences in that row — D54, D124, D125, D126,
D127, F185 — ends before D133.

Why this blocks and the smaller findings do not. Rows 660, 734 and 735 are
`use` evaluating a body the system's own reference refuses. That is the
shape F187 was ruled a defect for: "in 6 it fetched a body the reference's
fetch refuses". On Linux it is now approved, which is the owner's to do and
is done. But the preservation table is where a reader learns which
behaviours differ, and CLAUDE.md names the failure exactly: "a required
deviation filed as a non-deviation, so no criterion covers it". Here it is
filed in the registers and denied in the table.

**What would answer it:** a row for D133, or the fetch row rewritten — the
16 rows by kind, that four of them are Bund2 running or going on where the
Linux reference stops, and "fails closed" and "no other text" scoped to
macOS and 8.7.1 in so many words.

## Should fix

### S1 — "`--noio` makes its 62 names fail" is four short

§B3a, "So the routes are not a list a search can close": "`--noio` makes
its 62 names fail". The same section counts 66 since D132: "with the three
that exist only under it, 66 names answer with the stub". Sixty-two was the
count before `use`, `use.`, `bund.eval-file` and `bund.eval-file.`.

Measured here, since the RFC says "The 610 were not run again for this":
under `--noio`, **63 of the 610 answer with a stub and one, `fs_is_file.`,
is not registered**, which is the RFC's 63 and 1. The stubs by group: BUS 8,
FS.LS 8, LOAD 7, FS.CP 6, FILE 4, SAVE 4, SYSTEM.SHELL 4, and two each for
the rest, with FILESYSTEM and SQLITE at one. So the count the section gives
in one place is right, and the other place was not updated.

### S2 — `--noeval`'s list is one name short by the document's own way of counting

For `--noio` the RFC counts names, aliases included: `cwd`, `cp`, `ls` and
`sh` are in the 63. For `--noeval` it counts "six words" and Bund2's two.
Measured the same way under `--noeval`: **nine names answer with a stub**.
The ninth is `!!`, an alias of `bund.eval`
(`reference/Bund/src/stdlib/functions/create_aliases.rs:13`;
`crates/bund2-stdlib/src/singles.rs`, `register_alias("!!", "bund.eval")`).

It is refused on both binaries. `"40 2 + println" !!` under `--noeval`
answers `bund EVAL functions disabled with --noeval` on Bund2 and on the
oracle at `21b40b0`, and prints `42` on both without the flag. So nothing
is wrong with the behaviour. What is missing:

- §B3a's "The group is six words" and "How this list was closed" do not
  name `!!`, and a reader auditing a program for the six does not find it.
  D132 knows the name: "`bund.eval` and `!!` evaluate a string the program
  holds".
- Criterion 10 says a bundle "still refuses each of the group's six words".
  `!!` does not occur in `crates/bund2-cli/tests/bundle_build.rs`. The
  floor for the alias rests on alias resolution reaching the stub, which is
  true today and which no test of the floor holds.

### S3 — "the table in the repository is that run" is no longer true

§B7, on D130's fix: "the workflow ran again on the commit that made it, the
seven rows go through the proxy, and no other cell changed; the table in
the repository is that run." That run was 38002480092, of `17e623a`. The
file now holds run 38026701887, of `6c84d9e`, and says of itself "This is
the third version". The second run's table is in history only. The same
paragraph gives the file as "the 443 settings there were then", which is
right about then and reads as a description of the file.

### S4 — the file's name says 2026-10-09 and its measurement is of 2026-10-10

`docs/measurements/fetch-linux-2026-10-09.md` begins "Measured 2026-10-10".
The RFC, D133 and F188 all cite it by the name. Nobody is misled who opens
it. A reader of the RFC who does not open it sees a 2026-10-10 measurement
cited to a file dated the day before, twice in one paragraph.

### S5 — the exit code rests on D52 and the RFC does not cite it

§B3 and the preservation table give the exit code as `vm.exit_requested()`
with no decision. D52, "`bund.exit` is a request the embedder honours", is
resolved and is the ruling that makes that call the exit code. It declares
no dependency on RFC-0006, which is how it is missed: CLAUDE.md's first
recurring failure. It is in neither "Decisions consumed" nor "Touched but
not consumed".

## Acceptance criteria

The table "What runs these" is accurate against
`.github/workflows/ci.yml`, read here. Three things it does not say:

- **Criteria 2 and 13: nothing fails when a golden is lost above the
  baseline.** Criterion 13 says "the CEILING line is what holds the number
  today". It is printed. `cargo xtask conform` returns an error on one
  condition, a pass count below the recorded baseline
  (`xtask/src/conform/mod.rs`, the match on `read_baseline`), and the
  baseline is 106. At 133 that is 27 goldens the job would lose and stay
  green, in source mode and in `--bundles`. So "none failing" in criterion
  2's tables is a line a person read on a date, and the CEILING holds the
  number for a reader and for nothing else. The criterion says the first
  half of this and then claims the second.
- **Criterion 10 does not try `!!`** — S2.
- **No criterion covers the fetch, and the RFC says so.** It is still the
  finding with the most weight here. Ten of the decisions this RFC consumes
  are the fetch (D124 to D133), and so is the longest preservation row.
  What checks them is `fetch.py`, which "gates nothing and uploads the
  table for a person to read". D133's sixteen rows in particular are a
  count nobody is asked to keep: when `ubuntu-latest` moves its libcurl the
  count changes with no commit to this repository, and no job fails. Either
  the fetch is this RFC's — and then it wants a criterion whose check is
  the two tables' cells against a recorded list of rows — or it is the
  interpreter's, as §B7 says, and then the last six reviews of it were of
  the wrong document.

Criteria 3 to 7, 9, 11 and 12 each name a test that exists by that name
where the RFC says it is. Criterion 1 is a dated measurement with nothing
to re-take it, which the table says, and 8 is withdrawn.

## Preservation analysis — what it does not enumerate

- **D133** — B1.
- **`!!` under `--noeval`.** Preserved, measured on both binaries, and not
  named in the row "What `--noeval` stops", which lists six.
- **How long a fetch waits.** `ureq` is gone and Bund2 opens the connection
  itself (`crates/bund2-stdlib/src/http.rs`, `TcpStream::connect`). §B7
  says of the two readers that "neither sets a limit on how long an answer
  takes, which was read and not compared". The preservation row lists what
  is preserved and approved and does not carry that sentence. A bundle that
  hangs on a silent listener is the kind of behaviour a table row is for.
- **The source path is disclosed.** §B3 records the path the build was
  given, "verbatim up to 256 bytes", and every diagnostic and `--inspect`
  prints it. The row "Diagnostic file name" calls that "Preserved". It is
  also new surface: an artefact carries a path from its builder's machine
  to whoever runs it, and two builds of one source from two directories
  are different artefacts. §B2 states the like cost for the source text.
- **A report's wrapping, since F186.** The fix says "No byte of a report
  changes", on a test over 1,932 reports, and gives two limits: below 40
  columns, and a word with characters outside printable ASCII, where
  "nothing proves there is none". Not this RFC's change. It landed in this
  RFC's last revision and the row "Diagnostic source locations" is where
  a bundle's reports are said to match a `script` run's.

## What the RFC assumes and does not state

- **That the 741 rows still hold at `e2fc0b0`.** Both tables are of
  `6c84d9e`. The commit after the measurement changed
  `crates/bund2-stdlib/src/report.rs` and added two dependencies,
  `unicode-width` and `unicode-segmentation`. A cell is "what was printed".
  F186 argues no byte moved; neither table was run again.
- **That `ubuntu-latest` keeps libcurl 8.5.0.** D133 covers a third libcurl
  "in kind" and names no rows for it. The RFC's "16" is a fact about a
  runner image.
- **That alias resolution keeps reaching a stub.** S2. The floor for `!!`,
  and for `cwd`, `ls` and the other aliases under `--noio`, is that an
  alias resolves by name at the call. Nothing in §B3a says so.
- **What "all of argv" is.** §B3 says all of argv reaches `args`. Whether
  that includes the artefact's own name is not said, and it is the first
  thing a wrapper moved from `script` to a bundle would ask after `--`.
- **That a reader has a cargo registry with `ureq` 3.4.0 in it.**
- **That a measurement of one profile is a measurement of the artefact.**
  §B3a does not say which profile its bundles were built in. §B1 says a
  release build once folded the region away and ran a filled bundle as the
  plain interpreter, and that the only check is `cargo xtask bundle`, which
  is in neither `cargo test` nor CI. A restriction is a byte in that
  region.
- **That "one reader on every system" is one behaviour.** D130 chooses a
  `no_proxy` rule when Bund2 is compiled and D133 chooses none. So Bund2
  differs from itself between systems in D130's seven rows and from the
  reference between systems in D133's sixteen. Both are ruled. The RFC
  states each and never puts them side by side.
