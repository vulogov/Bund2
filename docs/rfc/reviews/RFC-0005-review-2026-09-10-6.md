Two blockers are new. The first is the ninth review's B2 one level further, from
*runs a body* to *moves the stack by its pair*. The second is not about
promotion. It concerns what sits between compiled code and a native.

- **B1.** Promotion trusts the declared pair of every `bund2-stdlib` native.
  Only the arms the corpus exercises have been checked. `drop_stack` declares
  `1 -> 0`, empties the current stack whatever it is handed, and no golden
  runs it.
- **B2.** Compiled code cannot call a `NativeFn` as the RFC describes it.
  `fn(&mut dyn Vm) -> Result<(), Error>` is a Rust-ABI function with a
  two-word argument and a `String` in its return, and Cranelift can tail-call
  only `CallConv::Tail`. The shims this forces decide what a panic does, and a
  panic in a native is reachable today.

## 1. Blocking

### B1 — the depth half of criterion 24 covers the corpus's arms, and §S5 trusts every pair

**What §S5 relies on.** After a call to a native with a fixed pair, promotion
"models the depth from the callee's pair" (criterion 24, line 2515–2516), and
keeps values below `consumes` in registers. D47 restricts that to
`bund2-stdlib`'s registrations and says an embedder's native "costs speed,
never meaning" (line 890). That holds only if every `bund2-stdlib` pair is
right on every arm.

**What is checked.** Assumption 7 says it precisely (line 1832–1835): the pair
is "checked by criterion 24's audit over the corpus since F91 and F92, **for the
natives and operands the corpus reaches**". Criterion 24 repeats it (lines
2537–2541): a word the corpus never calls is left to
`no_fixed_effect_native_runs_a_body`, and that test checks **only whether a body
starts** (`crates/bund2-stdlib/src/lib.rs`, `honesty_tests`). It never compares
depth. The Preservation row for miscounted pairs (line 1961) cites the corpus
audit alone.

So a fixed-effect native is checked for depth only on the arms the corpus
happens to reach. F92 is the evidence that this matters: ten of the pairs the
corpus reached were wrong, and `format` was wrong only on the arm with
placeholders.

**A live counterexample.** `drop_stack` is registered `eff(1, 0)`
(`crates/bund2-stdlib/src/stack.rs`, the `w(r, "drop_stack", …)` line). The
function takes no operand. It drops the current stack by name
(`drop_stack`, same file: `let name = vm.current_name(); vm.drop_stack(&name)`).
The reference's takes no operand either: `stdlib_drop_stack` ignores both
`_value1` and `_value2` (`reference/rust_multistack/src/stdlib/drop.rs:54`) and
calls `TS::drop_stack`, which removes the current stack outright
(`reference/rust_multistack/src/ts_drop_stack.rs:10-23`). Bund2's own probed
table already says `0+` (`docs/arity.md:187`). Run 2026-09-10:

    1 2 3 "zz" drop_stack debug.display_stack      → ╭╮ ╰╯   (empty; exit 0)

A body `1 2 drop_stack 3 +` compiled under §S5 keeps `1` in a register across
`drop_stack`, since the pair says it consumes only `2`. The compiled body adds
`1 + 3`. Tier 0 fails with a shallow stack. `cargo xtask coverage` lists
`drop_stack` among the five implemented words that no golden runs, so the
corpus audit cannot see it.

F92's closing paragraph files `drop_stack` among the named-stack words "whose
current-stack effect depends on whether the name *is* the current stack". It
takes no name. It always acts on the current stack.

**How far the gap goes.** `armprobe` runs each of the 206 fixed-effect natives
against three padding values and then every operand tuple drawn from fourteen
kinds: `7`, `2.5`, `true`, two strings, a class name, two LISTs, a DICT, two
lambdas, `nodata`, a PTR and an OBJECT. 13,490 runs were made, with the audit
on. Results:

- The positive controls fire. `object` re-registered `eff(1, 1)` breaches
  ("started a body", "dispatched `drop`"), and `clear` re-registered
  `eff(0, 0)` breaches on depth.
- **`drop_stack` breaches on all fourteen kinds**: "declares (1, 0) and moved
  `main` from 4 to 0". No other stdlib native breaches on this palette.
- **62 fixed-effect natives never returned `Ok` on any tuple**, so the depth
  check never ran for them: every workbench form (`head.`, `car.`, `sort.`,
  `convert.*.`, `string.*.` …), `get`, `get,`, `set,`, `is`, `json`, `unwrap`,
  `wrap`, `take`, `swap_in`, `return_from`, `return_to`, `dup_one_in`,
  `dup_many_in`, `to_current`, `endcontext` and others. The palette never
  touches the workbench. A clean run over those words would say nothing.
- `cargo xtask effects` lists 104 natives it could not measure. It currently
  exits 1, on `format` (F92's open item).

The first review that widened the operands found a defect. That is the pattern
the Summary describes.

**Required:**
- Have the owner record `drop_stack`'s declared effect as a defect in RFC-0004's
  annotation. The number is the owner's; `docs/arity.md:187` reads `0+`. Add a
  dated note to F92, whose "not reached" list misdescribes it.
- **State which pairs promotion trusts, in terms of what has been checked.** Two
  options use machinery the RFC already has. Either promote across a
  `bund2-stdlib` native only if the audit has *reached it with `Ok`* on a
  recorded operand set, kept as a checked-in list the way `EFFECTS.txt` is, so
  a word nothing reached is synced like an embedder's. Or widen criterion 24 to
  a generated-operand audit that includes workbench operands, lists every
  native it could not bring to `Ok`, and withholds promotion from that list.
  Or take the question to the owner. D47 was decided on the premise that
  `bund2-stdlib`'s pairs are checked, and for most arms they are not.
- Correct line 1960's "against lambdas for the words the corpus never calls":
  that test checks body starts, not pairs.
- **Add a criterion:** the audit reaches every fixed-effect native with `Ok`, or
  the native is on the list promotion refuses. Mutation-check it against
  `drop_stack` before its fix.

### B2 — the call boundary is unspecified, and it decides what a panic does

**The claim.** §S8 answers §3.2f: a compiled word's signature is "one pointer
to the VM and one status, uniformly, which is the shape `bund2-api` already has"
(lines 1462–1467), quoting `NativeFn`. "A uniform signature satisfies the real
rule by construction" (line 1474). §S6, *Addressing*: "Compiled code receives
`&mut dyn Vm` (§S8)" (line 1086). §S11: errors "are already `Result`-shaped …
compiled code keeps that convention" (lines 1911–1913).

**What the source says.**
- `NativeFn` is `fn(&mut dyn Vm) -> Result<(), Error>`
  (`crates/bund2-api/src/lib.rs:61`). That is Rust's unspecified ABI.
  `&mut dyn Vm` is two words, a data pointer and a vtable, whose layout is not
  stable. `Error` is `pub struct Error(pub String)` (`crates/bund2-api/src/lib.rs`,
  `Error`), so the return is not a status in any sense Cranelift can express.
- `cranelift-codegen` 0.135.0's `CallConv` has no Rust ABI. Its members are
  `Fast`, `Tail`, `SystemV`, `WindowsFastcall`, `AppleAarch64`, `Probestack`,
  `Winch` and one more (`src/isa/call_conv.rs`, `CallConv`).
- `typecheck_tail_call` requires `cc.supports_tail_calls()` **and** that the
  callee's convention equal the caller's (`src/verifier/mod.rs`,
  `typecheck_tail_call`), and `supports_tail_calls` is true of `CallConv::Tail`
  alone (`src/isa/call_conv.rs`). The eighth review's reading ("compares
  `call_conv` and `returns`, not parameters") was right about parameters, but
  missed that the shared convention must be `Tail`.

**What follows.**
1. **No call slot can hold a `NativeFn`.** Every native reached from compiled
   code needs an adapter with a C convention and a thin pointer: an
   `extern "C"` shim that rebuilds `&mut dyn Vm` and turns the `Result` into a
   status, with the `Error` parked somewhere the caller can read it.
2. **No `return_call_indirect` can reach that shim.** Rust cannot define a
   `Tail`-convention function. A tail call through a slot therefore needs every
   slot target to be `Tail`: a JIT-emitted `Tail` thunk per native (or one
   generic thunk) that makes an ordinary call to the shim. Compiled bodies
   must be `Tail` too. Rust then cannot call them directly, so the frame loop,
   `eval_lambda` and the drain enter through a C-convention trampoline.
3. **The shim decides what a panic does, and a panic is reachable.** D37 bans
   panics in Bund2's code. Its dependencies are not covered.
   `string.distance.jarowinkler` passes its operands straight to
   `natural::distance::jaro_winkler_distance` (`crates/bund2-stdlib/src/singles.rs`,
   the `string.distance.jarowinkler` registration), which slices by byte index
   past the end of the shorter string (`natural` 0.5.0, `src/distance.rs:41`).
   The reference uses the same crate (`reference/Bund/Cargo.toml:58`). Run
   2026-09-10:

       "zz_nofile" "A" string.distance.jarowinkler println
         → thread 'bund2' panicked at …/natural-0.5.0/src/distance.rs:41:28:
           start byte index 2 is out of bounds of `A`      (exit 1)

   Under Tier 0 the panic unwinds out of the evaluation thread, and `main`
   maps the failed join to `ExitCode::FAILURE`
   (`crates/bund2-cli/src/main.rs:47`). Under Tier 1 the same native is
   reached through compiled frames. Since Rust 1.81, a panic unwinding out of an
   `extern "C"` function aborts the process. An `extern "C-unwind"` shim would
   unwind through Cranelift frames, which is sound only if the JIT registers
   unwind tables for every function. So the exit status changes from 1 to an
   abort, or worse. `armprobe` hit it on six operand pairs.

This is not the helper table §S4 says it owes (lines 519–524). That table is
about runtime *helpers*. This is every inter-word call, and the RFC states
the opposite of what the source allows.

**Required:**
- Replace lines 1459–1478's "the shape `bund2-api` already has" with the real
  boundary: the JIT's own signature (a thin context pointer and an integer
  status), where the `Error` of a failed call is kept, the per-native
  adapter, the `Tail` thunk, and the entry trampoline. State which calls can be
  `return_call_indirect` once natives are behind thunks.
- **Decide what a panic in a native does under both tiers, the same way.** The
  cheapest rule that preserves D37: `catch_unwind` at `Interp::call_native`,
  mapping a panic to `Error::internal` naming the native. That changes Tier 0's
  behaviour too, from an exit with a Rust backtrace to a reported internal
  error, so it is the owner's decision. The alternative, identical aborts in
  both tiers, contradicts D37's "every unrecoverable internal error is handled
  with a meaningful explanation".
- Recommend the owner record the `jarowinkler` panic as a Bund2 defect. It is
  a D37 violation with no tier involved, shared with the reference.
- **Add a criterion:** a native that panics, reached from a compiled body in a
  non-tail and a tail position, gives the same observable result as Tier 0.
  Add a Preservation row.

## 2. Significant

### S1 — D47's set of registration ids is not specified

§S5 (lines 884–886): "the callee's registration id (D43) is one `bund2-stdlib`
made, **the same set its fragments are keyed by**". The fragment table is
keyed by the ids of the registrations *that have a fragment*: three today
(`int_add`, `dup`, `drop_top`; `crates/bund2-stdlib/src/fragments.rs`). The set
D47 needs is every `bund2-stdlib` registration, about 270 names. D43 says how a
fragment's id is recorded, and nothing says how the full set reaches
`bund2-jit`.

Two consequences follow:
- D43 assigns ids in `Registry::register_native` only. §S5 (line 568) reads an
  effect when `resolve` answers `Command`, but a command carries no D43 id, so
  under D47 no command is ever crossed. That is safe, but it should be said.
  (`bund2-stdlib` registers no command today.)
- D43 records that F32's replay gives a re-registration a fresh id. The set has
  to follow a replay, or a replayed stdlib native silently stops being crossed.
  That costs speed, not meaning, but criterion 10's figures would then describe
  the wrong configuration.

**Required:** say how the set is published: for example, `register_all`
records the ids it minted, and `bund2-jit` reads that set as it reads the
fragments. Correct "the same set its fragments are keyed by", and give D47 a
dated note.

### S2 — the margin is sized from `loop` alone

§S8 (lines 1721–1727) sets Tier 0's part under `jit` to `8 MiB + m`, with
`m ≥ 8 MiB × δ / c`, where `c` and `δ` are "the bytes one `loop` level
spends", reported by criterion 11. The bound has to hold for **every** path
that re-enters evaluation. That covers `times`, `map`, the conditionals,
`?try`, the method paths, `Vm::apply`, `Vm::scoped_call` and now the drain
helper. Each has its own `c`. If `δ` is roughly a fixed number of bytes, the
worst ratio comes from the native with the smallest `c`, and `loop` need not be
that native.

The rule that "the tier adds nothing to a Tier 0 level" (lines 1715–1720)
names one site, the cache lookup at `Vm::eval_lambda`. But `run_to` is on every
nesting level as well, and under the tier it is an entry point that must test
the cache when it starts a frame (§S8, *A decline is a return*). Its frame can
grow too.

**Required:** define `m` over the maximum `δ / c` across the re-entering
paths, and have criterion 11 report `c` and `δ` for each. Extend the design
rule to `run_to`'s compiled-entry check.

### S3 — four edges of the request protocol

1. **Order of the post-call reads.** Lines 721–727 load the request cell
   "beside the epoch and `autoadd`" and drain if it is set. A drained body can
   switch the current stack, set `autoadd` or `register` a name. Today that is
   harmless, because every request-filing call is opaque or a lambda call, and
   nothing is promoted across either. The RFC should either require that the
   epoch and `autoadd` be read *after* the drain, or state why their order does
   not matter.
2. **A stale request after an error.** Tier 0 never clears `pending_tail` on
   an error: `run_to`'s `Err` arm unwinds frames only, and `eval_observed` and
   `Interp::apply` return early (`crates/bund2-interp/src/lib.rs`). A native
   that files a request and then returns `Err` leaves it set. `?try` catches
   the error, and the next `take_pending` runs the stale body. No
   `bund2-stdlib` native does this: all four sites return `Ok` straight after
   filing. An embedder's native can. Compiled code would then return
   `Error::internal` at its next slot call where Tier 0 runs the body, so
   "Tier 0 cannot reach that state" (line 736) holds only for `bund2-stdlib`.
   Clearing `pending_tail` on every error path in Tier 0 would make it
   structural.
3. **A refused drain.** The drain "checks the Tier 0 floor before it
   re-enters" (line 741). If it refuses, the cell is still set. Say whether it
   is cleared. The case is unreachable while compiled code runs only above the
   Tier 1 floor, but the text should not leave it open.
4. **Where the frame loop enters compiled code.** "Each entry takes it at
   once: the frame loop before its next `apply_step`" (lines 729–731) presumes
   an integration point that is never stated: in `take_pending`, at a frame's
   first step, or in place of `push_frame`. `push_frame` is "the one place a
   body starts running, so the one place its key is observed" (its doc
   comment). A compiled body substituted before it bypasses `entry_log` and the
   place §S7's counter would count. Frames carry an `exit` action as well.

**Required:** settle 1, 3 and 4 in §S5, and take 2 to the owner as a Tier 0
defect or a stated limit. Add to criterion 26: a request filed inside a
drained body, and an embedder native that files then fails, under `?try`.

### S4 — smaller items

- **Stale figures once the working tree lands.** `conform` reads **82/89,
  CEILING 82/89**, with and without `--features jit`, re-run 2026-09-10 on this
  tree. The RFC says 79/86 in §S1 (line 301), §S10 (lines 1893–1894) and
  criterion 2 (lines 2017, 2043). *Where promotion stops* counts 161 programs
  and 122 stops. With the three untracked probes it is 164 programs, 124
  stops and 76 opaque, adding `if.in_workbench` and `execute`. Criterion 12's
  "36 of 86 … 39 carry some" is now 36 of 89 and 40.
- **Criterion 24's dispatch breach sees only `call_native`.** A fixed-effect
  native that reaches a method native through `vm.method` then `f(vm)`
  (`dispatch_method`, `run_init`; `crates/bund2-stdlib/src/oop.rs`), or a
  conditional runner through `vm.conditional` (`display`,
  `execute_conditional`), dispatches nothing the audit can see. Today only
  opaque words do. The criterion should say "through dispatch".
- **`effects` and `arity.md` are a second witness the RFC does not use.**
  `docs/arity.md:187` had `drop_stack` at `0+` before any of this. A criterion
  that compared declared pairs with that table's probed column would have
  flagged it.

4. **`bund2-jit` can obtain the set of registrations `bund2-stdlib` made**

   not matter (S3.1).
7. **No native files a tail request and then fails** (S3.2).

## 8. Recommendation

**Stay Draft.** The answer to the ninth review was complete, and every part of
it I could run behaves as stated. The request protocol matches Tier 0's
programs, F91 and F93 are fixed, and the audit catches the defects it was
written for. Every citation is right.

The next level splits in two directions again. B1 carries the ninth review's B2
from "runs a body" to "moves the stack by its pair", and the answer that worked
there, a wider operand set, is what found `drop_stack`. B2 is new ground. Every
review so far has asked what a callee *does*. This one asks how compiled code
*reaches* it, and the answer decides what happens when the callee panics.

In order:

1. **B1.** Record `drop_stack`. Tie promotion to what the audit has actually
   reached, or widen the audit and exclude what it cannot reach. Correct line
   1960 and F92's note.
2. **B2.** Specify the boundary: signature, status, error slot, adapters,
   thunks, entry trampoline. Take the panic rule to the owner, and have the
   `jarowinkler` panic recorded.
3. **S1–S3.** Publish D47's id set. Size `m` over every re-entering path.
   Close the four request-protocol edges.
4. **S4.** Refresh the figures when the working tree is committed.
