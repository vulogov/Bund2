## 1. Blocking

### B1 — `status_of` reports an exit to Rust callers that Tier 0 answers `Ok`

**What §S5 now promises.** Every helper turns its `Result` into a status
through `status_of`, which answers the error status once an exit is recorded
(lines 777–783). "In tail position the status travels with the return, so no
compiled op runs after the helper that saw the exit returns" (lines 811–813).
Criterion 30 requires that "Output, exit code and **final stacks** must match
Tier 0's" (lines 2998–2999).

**What Tier 0 returns at the end of a body.** `Interp::run_to` pops a finished
frame without the gate (the RFC says so at line 799). So when a body run
synchronously ends in `bund.exit`, `run_to` returns `Ok`, and so does
`Vm::eval_lambda` (`crates/bund2-interp/src/lib.rs`, `eval_lambda`: the gate is
at its top only). The native that called it carries on in Rust. Tier 0 stops
only at the next `apply_step`, and the native may do real work before one
comes.

**What compiled code returns instead.** Take the body `{ 7 exit }`, compiled.
`exit` is its last call, so it is a `return_call_indirect` to the resolving
trampoline, since `exit` is an alias. `dispatch` runs `bund_exit`, which records
7 and returns `Ok`. `status_of` sees the exit and answers the error status.
The status goes back through the tail call to the entry trampoline, which
turns it into `Err`, and `Vm::eval_lambda` returns `Err`.

**Three natives that act on the difference**, all among the 21 the new test
names:

- **`map`** (`map_base`, `crates/bund2-stdlib/src/seq.rs`). After `Ok` it
  pulls the outcome, collects it, and goes on. After `Err` its `?` returns at
  once. Run at Tier 0 in this session:

  | program | Tier 0: result, exit, final stack | compiled body under `status_of` |
  |---|---|---|
  | `[1] { 7 exit } map` | `Ok`, exit 7, one LIST `[1]` | `Err` on the first item; final stack `1` |
  | `[1 2] { 7 exit } map` | `Ok`, exit 7, `2` (the second item pushed, then its `eval_lambda` refused) | `Err` on the first item; final stack `1` |
  | `1 [1] { 7 exit 99 } map` | `Ok`, exit 7, `1 1` | the same: `exit` is not last, so both stop at the next op |

  The last row is the control. Only a body whose **last** action records the
  exit differs.
- **`input*`** (`input_loop`, `crates/bund2-stdlib/src/terminal.rs`). After
  `Ok` it calls `rl.readline` again. Run at Tier 0 with the program
  `"p> " { println 7 exit } input*` and the input `a`, then a 3-second pause,
  then `b`: it prints `a`, **blocks for the second line** (`real 3.01`), and
  exits 7. With `{ println 7 exit 1 drop }` it exits at once (`real 0.00`).
  Compiled under `status_of`, `input_loop` gets `Err` after the first line and
  never reads again. The two tiers differ in what they read from the terminal.
- **`?try`** (`run_tryexcept`, `crates/bund2-stdlib/src/conditional.rs`). Read,
  not run. A `try` body ending in `exit` gives `Ok` at Tier 0, and `?try`
  returns. Compiled, it gives `Err`, and `?try` pushes an `error` CONDITIONAL
  before its `except` body is refused. The final stacks differ by that value.

**Tier 1 also disagrees with itself.** A body ending in a tail call to `exit`
returns `Err` to its entry. A body ending in `true { 7 exit } if` hands the
request back (lines 865–870). The entry drains it through `run_to`, whose pop
does not gate, so it returns `Ok`. The same program shape therefore gets two
answers depending on how its last word reached `exit`.

**Why no criterion sees it.**
- Criterion 2's threshold-1 run compiles the `map` body and would diverge. But
  nothing a golden captures runs after an exit: the probes say "the capture's
  own epilogue never runs" (`tests/probes/bund-exit.bund`). The CLI prints no
  stack after an exit either (`run`, `crates/bund2-cli/src/main.rs`).
- Criterion 30's new cases all put the compiled body on the **caller's** side:
  a compiled caller of an interpreted callee. B1 is the mirror image, a
  compiled callee whose caller is Rust.

**The root is a Tier 0 defect, and the RFC inherits it.** D52 says the
interpreter "stops at the next word boundary and runs nothing more of the
program". `Vm::request_exit`'s documentation says "The interpreter runs nothing
more of the program once it is made" (`crates/bund2-api/src/lib.rs`,
`request_exit`). The reference ends the process inside `bund.exit`. Tier 0's
`input*` runs a `readline` after the exit, and `map` pushes a list. Neither
is in the registers: no entry in `defects.md` or `open-questions.md` mentions
`bund.exit`, `exit_gate` or `request_exit`. `status_of` is in fact closer to
D52 than Tier 0 is. But criterion 2's invariant is agreement with Tier 0, so a
tier that is more faithful here is still a movement.

**Required.** Choose one. The first changes Tier 0, so it needs the owner.
- **(a) Make Tier 0 gate where a synchronous run returns to Rust.**
  `Interp::eval_lambda`, `Interp::apply` and `Vm::scoped_call` would call
  `exit_gate` after `run_to` returns `Ok`. Every native then sees `Err` in both
  tiers. `input*` stops reading and `map` stops collecting, which is what D52
  and `request_exit`'s documentation already promise. `status_of` becomes
  exactly Tier 0, and the tail hand-back agrees with the direct tail call. No
  golden can move, because nothing is captured after an exit. File the defect
  first, and add a dated note on RFC-0003 if its frame-loop contract is read as
  covering `eval_lambda`'s `Ok`.
- **(b) Keep Tier 0, and give the boundary a third status, *exit*.** A
  non-tail call site treats it as an error, since Tier 0 would refuse the next
  op. The entry trampoline returns it as `Ok`, as `run_to` does. This
  reproduces the defect exactly and needs the hand-back path to match it.

Either way:
- **Extend criterion 30 with the mirror cases**, each at threshold 1 and with
  the body hot: `[1] { 7 exit } map` and `[1 2] { 7 exit } map`, compared on
  the final stack; a `?try` whose `try` body ends in `exit`; and `input*` over
  a two-line input, compared on the lines consumed.
- **Say whether the state after an exit is meaning.** Criterion 30 says final
  stacks are. D52 is silent, and a TUI that "might close a session" would
  still show them. If the owner rules that they are not, B1 narrows to the
  `input*` read, which stays.
- **Add a Preservation row** for a compiled body entered from Rust whose last
  action records an exit.

## 2. Significant

### S1 — three sentences in §S5's exit rule do not describe the code

1. **Lines 765–766:** "Every Tier 0 call passes `apply_step`, so the gate sees
   the step after the exit, whatever made the call." It does. But between the
   exit and that step, the Rust code of the native that ran the body may run,
   and B1 is that gap. The sentence reads as though Tier 0 stops at once.
2. **Lines 773–775:** "A `bund.eval` or `use` whose source calls `bund.exit`
   is covered already, since its next `Vm::apply` is refused". `eval_source`
   applies each value and returns `Ok` when the stream ends
   (`crates/bund2-stdlib/src/singles.rs`, `eval_source`). When `exit` is the
   source's last value, no next `Vm::apply` comes. The case is covered now,
   by `status_of` at the adapter that wraps `bund.eval`, and not for the
   reason given.
3. **Line 794:** "the frame loop's compiled entry sits behind `apply_step`'s
   gate". A compiled entry runs a whole frame in place of its steps, so
   `apply_step` is not on the path. What refuses is the entry trampoline
   (lines 792–793), through which the frame loop enters compiled code
   (lines 1672–1675). The sentence is redundant, and it points at the wrong
   mechanism.

**Required:** correct all three. The first depends on how B1 is answered.

### S2 — the re-entry scan is exact only for the spellings it matches, in the crate it reads

§S8 says the test "fails until a new re-entering function is named, so the set
cannot go stale" (lines 1936–1938). What `every_reentering_function_is_named`
does:
- It matches the three calls by their dotted spellings, `.eval_lambda(`,
  `.apply(` and `.scoped_call(`. A call written `Vm::apply(vm, v)` is not
  matched.
- It names the enclosing function only after `pub fn `, `pub(crate) fn ` or
  `fn `. A call inside a `pub(super) fn`, `const fn`, `unsafe fn` or
  `async fn` is filed under the function before it. If that name is already
  listed, nothing fails.
- It reads `src/` with `read_dir`, so a file in a subdirectory is never read.
  It cuts each file at its first `#[cfg(test)]\nmod `, as criterion 25 does.
- It reads `bund2-stdlib` only. `run_init` and `dispatch_method` call a
  method's `NativeFn` directly (`crates/bund2-stdlib/src/oop.rs`). An
  embedder's method native, or an embedder's ordinary native, may call
  `Vm::eval_lambda`. D47 keeps promotion off those, but the margin `m` is a
  property of the stack, not of promotion. An embedder that opts in through
  `set_stack_region_with_share` gets an `m` computed over `bund2-stdlib`'s
  paths only.

**None of these gaps is live today.** No `Vm::…(` call form, no unparsed
function head and no subdirectory exists in `bund2-stdlib/src`, and the
crate's own method natives do not re-enter evaluation (checked with `grep`
this session). The claim is about the future, which is what the sentence
promises.

**Required:** state the limits beside the sentence, and add an assumption:
re-entering paths outside `bund2-stdlib` are not in `m`, and an embedder that
declares a share takes that on.

### S3 — smaller items

- **`status_of` can leave a request pending behind an error.** Line 891–892
  says "No stale request outlives an error". F96 keeps that true for a native
  that *fails*. `status_of` turns a native's `Ok` into an error, so a request
  the native filed stays in the cell. No `bund2-stdlib` native can do this
  today: the four that call `tail_lambda` (`if_stack`, `if_base`,
  `ifthenelse_base` in `control.rs`, and `execute_value`) run no body before
  filing. It needs a body that records an exit followed by a request. Either
  have `status_of` clear the cell when it answers an exit, or say why a stale
  request is harmless: after an exit, every later start is refused.
- **The committed `CONFORMANCE.txt` reads 82/89.** The RFC's 105/113, and
  `cargo xtask conform` this session, agree with the working tree's
  uncommitted copy. That copy predates this review. As with `PROMOTABLE.txt`
  in the twelfth review, the owner commits it.
- **`CollectingReporter` has no location.** Line 945 and criterion 22 name it,
  and it is not in `crates/bund2-api/src/lib.rs`. It is
  `crates/bund2-api/src/diag.rs`, `CollectingReporter`, whose `seen` field
  criterion 22 reads.
- **Row 2239** credits D55's first run with `swap_in`, `rotate_stack_left` and
  `rotate_stack_right` among the named-stack words. `PROMOTABLE.txt` also
  flags `move_from`, which reads from a stack by name. Criterion 14 names all
  eight correctly.

## 5. Preservation analysis — what the table does not enumerate

1. **A compiled body entered from Rust whose last action records an exit.**
   The entry returns `Err` where Tier 0's `run_to` returns `Ok`, and the
   native that ran the body acts on the difference (B1).
2. **A tail hand-back whose drained body ends in an exit.** It returns `Ok`,
   where a direct tail call to `exit` returns `Err`. The tier disagrees with
   itself (B1).
3. **An error `status_of` makes from a native's `Ok` while a request is
   pending.** F96's "no stale request outlives an error" is not kept on this
   path (S3).
4. **Native nesting through a re-entering path outside `bund2-stdlib`**, under
   an embedder's declared share, where `m` was not computed over that path
   (S2).

Row 2261 is accurate as far as it goes. It covers compiled code as the
*caller* of whatever recorded the exit, and it needs a companion for compiled
code as the *callee*.

## 6. Consistency with accepted RFCs, registers and ERRATA

- **D52.** Its text reads "stops at the next word boundary and runs nothing
  more of the program" (`docs/registers/decisions.md`, D52, *Decision*). Tier 0
  runs a native's remaining Rust after an exit: `input*` reads again and
  `map` pushes. So Tier 0 does not keep D52 to the letter, and `status_of`
  would keep it more closely. Criterion 2 measures against Tier 0, so the
  difference is still a movement. No defect records it (B1).
- **`Vm::request_exit`'s documentation** says the same as D52 and is contradicted
  the same way (`crates/bund2-api/src/lib.rs`, `request_exit`).
- **RFC-0003 (Accepted).** Its frame loop and `Vm::eval_lambda` are where B1's
  option (a) lands. If the owner takes (a), RFC-0003 may need a dated note
  saying that `eval_lambda` refuses after `run_to` once an exit is recorded.
- **RFC-0004 (Accepted).** Its 2026-09-09 amendment still matches §S5 ✓.
- **D48, D55, F111.** Consistent with the RFC since the answer ✓.
- **ERRATA.** No new contradiction. The entries from `:89` still describe
  RFC-0005 correctly.

## 7. What the RFC assumes and does not state

1. **A compiled body returns to Rust what Tier 0 would have returned.** It
   does not when the body's last action records an exit (B1).
2. **Tier 0 runs nothing after an exit.** It runs the Rust code of the native
   that ran the body, until the next `apply_step` or `eval_lambda` (B1).
3. **The state after an exit is meaning.** Criterion 30 treats final stacks as
   meaning. D52 does not say, and neither does §S5 (B1).
4. **Every re-entering path is a function in `bund2-stdlib`, spelled with a
   dotted call inside a function head the scan parses** (S2).
5. **A request left pending when `status_of` answers an exit is harmless.**
   It is, because every later start is refused. But the RFC states the
   opposite rule, and not this one (S3).

## 8. Recommendation

**Stay Draft.** The answer to the twelfth review is complete as far as it
goes. `status_of` closes the set of helpers that return to compiled code, the
re-entry set is a test, and every figure and citation is right today.

The blocker is the other side of the same boundary. The twelfth review asked
that a helper never report success to compiled code after an exit. The answer
makes every helper report an error, and in tail position that error reaches
Rust. At the same point Tier 0's `run_to` returns `Ok`, and natives act on
the answer: `map` collects, `?try` recovers, `input*` reads another line.
Whether to change Tier 0 is the owner's call. It is also a Tier 0 defect
against D52 that no register holds yet.

In order:

1. **B1.** File the Tier 0 defect: after an exit, a native's remaining Rust
   still runs. Take it to the owner with options (a) and (b). Extend criterion
   30 with the mirror cases, say whether post-exit state is meaning, and add a
   Preservation row.
2. **S1.** Correct lines 765–766, 773–775 and 794.
3. **S2.** State the scan's limits, and add the assumption that `m` covers
   `bund2-stdlib` only.
4. **S3.** Decide what `status_of` does with a pending request, commit
   `CONFORMANCE.txt`, give `CollectingReporter` its file, and add `move_from`
   to row 2239.
