# RFC-0017 review: revision 11 as implemented, 2026-11-19

**Scope.** This review covers revision 11 of `docs/rfc/RFC-0017-frames-and-missing-values.md`, Accepted on 2026-11-18, together with its two dated notes:
- 2026-11-18, `frame.with` on a frame of no columns;
- 2026-11-19, a frame does not round-trip through JSON.

The RFC is 1189 lines at `development/0.56.0` 9b71007. All four milestones have landed: M1 89ba65a, M2 8ad1fac, M3 672f453 and M4 9b71007.

It is the first review since acceptance, and the first that can read the RFC against the code that implements it. Earlier reviews read it against the reference alone. So besides re-opening every citation, this review asks a second question: where the code had to choose, did the RFC say what to choose?

The RFC was read against:
- the previous review, `docs/rfc/reviews/RFC-0017-review-2026-11-18-4.md`, of revision 10;
- D252 and its three dated notes (`docs/registers/decisions.md:17291-17368`);
- `docs/research/ERRATA.md:249-256`;
- research 07 (`docs/research/07-statistical-research.md:52`, `:85-107`, `:217`);

- the implementation: `crates/bund2-stdlib/src/biomath/frame.rs`, `frame/{check,opts,render,reshape,csv,table,summary}.rs` and their tests, and `biomath/na.rs`.

Only this file was written. `reference/` was not touched, and `git submodule foreach 'git status --short'` prints nothing for any submodule.

## Should fix

### SF1. D252 still says `json` carries a frame unchanged

D252's consequences (`docs/registers/decisions.md:17326-17327`) read: "A frame is a plain MAP and stays one, so `json`, the wire format and `vm.spawn` carry it unchanged."

The 2026-11-19 note corrected RFC-0017 S2 and criterion 7, but not the register. A frame always holds STRINGs in `columns`, and `json.from_value` refuses every STRING. Probe: `[ "x" ] [ [ 1 2 ] ] frame.new json.from_value println` gives `Error casting JSON value: Error casting DICT: Error casting LIST: This Dynamic type is not supported for JSON: 4`.

D252 already carries two dated notes correcting its findings (`:17350-17359`, `:17361-17368`). This is a third of the same kind. The ruling (C1 B) does not rest on the JSON clause and is unchanged. The register is append-only, so the fix is a dated note, not an edit.

The note's own Bund2 citation, "`crates/bund2-stdlib/src/json.rs`, `from_value`", points at the wrapper. The refusal is in `crates/bund2-value/src/lib.rs`, `to_json`, the `_` arm, which `from_value` calls, so cite that.

The `vm.spawn` clause in the same sentence was never probed by RFC-0017 or its reviews (assumption A6).

### SF2. "Every refusal is listed with its text in S8" does not hold for S5

S1 states that every refusal is listed with its text in S8 **[D256 S3]**. M4 had to write texts that no S8 row gives:

| Refusal | Text as built (`frame/summary.rs`) | S8 |
|---|---|---|
| A `stats` entry that is not a two-item LIST of STRINGs | `stats is outside …: item 1 is <value>` | S5 calls it E101; S8's wrong-type row names only `names` and `by` items |
| A `stats` column absent | `stats is outside …: no column "zz"` | S8's absent-name row lists `name`, `names`, `by` and `opts`, not `stats` |
| Two entries with one result name | `result name "x.sum" repeats another` | S8 has only `repeats a by column` |
| A statistic on a string or logical column | `"mean" of column "s", a string column` / `a logical column` | S8 gives only the factor form, `"mean" of column "g", a factor` |
| `frame.matrix` on a string or logical column | `column "s" is string` / `is logical` | S8 gives only `is a factor` |
| The join cap | `the join's row count exceeds its cap of 100000000` | S8 leaves `<what>` open |

Each is a reasonable reading. But S1's sentence, and D256 S3's ruling behind it, promise a table a reader can rely on. Add the rows in a dated note.

### SF3. Refusal order is stated for `frame.aggregate` only

S5 states the order of `frame.aggregate`'s refusals, and the first failure wins. It gives no order for `frame.join` or `frame.matrix`, nor for which NONE `"refuse"` names first. The code chose:
- **`frame.join`:** `left`; `right`; `by`'s item types; `no keys`; then, for each name in turn, absent from `left`, given twice, absent from `right`; then `opts`; then key kinds; then shared non-key names.
- **`frame.matrix`:** the frame; `names`, its kinds included; `opts`; `no rows`; then the cells under `na`; then `no rows` again after `"omit"`.
- **`"refuse"`, in both words:** the first NONE in the order the word reads its columns (`stats` order, deduplicated, or `names` order), each from row 1.

S2's "each rule applied in column then row order" applies to the frame check, not to `na`. A program with two faults sees whichever comes first, so the order is behaviour and belongs in the RFC.

### SF4. "No existing line moves" in `PROMOTABLE.txt` cannot hold literally

Criterion 10 and the Preservation row both say `PROMOTABLE.txt` is regenerated "with no existing line moved". But the file's first line is a count, which changes whenever a name is added:
- 89ba65a removed `# 509 promotable of 518 reached, of 759 fixed-effect natives…`;
- 9b71007 removed `# 520 promotable of 529 reached, of 782…` (`git show <sha> -- tests/golden/PROMOTABLE.txt`).

The intent, that no existing *name* line moves, held in both. Say that.

## Notes

- **N1. Criterion 7 quotes the end of a message.** `This Dynamic type is not supported for JSON: 4` is the end of the full text quoted under SF1, and `value_round_trips` checks it with `contains`. Write "ends with" or quote the whole text.
- **N2. Criterion 5's "a frame of no rows with a factor column under `"mean"`" can be read two ways.**
  - As the `by` column: it answers no rows. `aggregate_edges` tests this reading.
  - As the column `"mean"` reads: the frame of no rows has no cell to read, but the column is still a factor because it is in `levels` (S2), and a factor under `"mean"` is E101 at entry by S5's own rule. S5's "a statistic's column of no kind is accepted" does not cover it.

  Say which reading is meant.
- **N3. S5's rule that a result name may not equal `.dropped` cannot fire.** A result name is `<column>.<statistic>`. A column name is never empty (S8 row 3), and no statistic is called `dropped`, so no result name can be `.dropped`. The reachable case is the other one S5 lists: a `by` column named `.dropped` under `"omit"`, which the code refuses as `result name ".dropped" repeats a by column`. Either drop the clause or say it guards the `by` case only.
- **N4. "What Bund2 does" now describes the tree before the RFC.** Two statements are no longer true of 9b71007, and both changed as designed:
  - `describe.rs`'s module doc no longer says the two means "may differ in the last bit"; M4 corrected it, as S5 requires.
  - "No `frame.` or `na` word exists" is no longer true.

  A dated note marking the section as before-implementation would stop a reader taking either statement as current.
- **N5. M3's commit did not meet criterion 10 on its own.** 672f453 was pushed with `PROMOTABLE.txt` stale: `frame.csv.parse` and `frame.csv.parse.` were reachable and missing. `every_fixed_effect_native_keeps_its_pair_over_the_promotable_palette` failed on that commit until 9b71007 regenerated the list. The RFC says each milestone ends with criteria 9 and 10. For one commit that was not so, and the record should say it.

## What the RFC assumes and does not state

- **A1. A `by` column that a statistic also reads.** S5 puts `by` columns outside `na`. When one is also a statistic's column, the code applies `na` to it as a statistic's column. Probe: a CSV `x,y` with `x` empty at row 2, `[ "x" ] [ [ "x" "mean" ] [ "y" "sum" ] ]`, gives `column "x" row 2 is none (na "refuse")`. The NONE group S5 promises never forms. Defensible, but unstated.
- **A2. Columns of no kind.**
  - `frame.matrix` accepts a column of no kind (all NONE).
  - `frame.aggregate` accepts one for any statistic, not only on a frame of no rows, which is the only case S5 names.
  - With rows, both then refuse under `"refuse"`, or empty out under `"omit"`: `no rows`, or `group [ 2.0 ] has 0 values for "mean"` (probed).
- **A3. BOOL join keys match by value.** S5 names numbers, factor keys and NONE. Probe: two CSV frames keyed on `true` and `false` join row to row.
- **A4. `.dropped` appears whenever `na` is `"omit"`,** even when only `"count"` statistics run and it can only be zeros.
- **A5. A program cannot write NONE inside a LIST literal.**
  - Probe: `[ "x" ] [ [ 1 na ] ] frame.new` is `FRAME.NEW: E101 columns is outside frame.new's domain: column "x" row 2 is a CALL`, because a literal holds `na` as a word, not its value. `true` and `false` behave the same in a literal.
  - The ways in are `na` with `+`, JSON's `null`, and `frame.csv.parse`.
  - S3 introduces `na` without saying this, and anyone who writes examples or documentation will meet it first.
- **A6. `vm.spawn` carrying a frame,** which D252's consequence asserts (SF1), was never probed or tested by RFC-0017. The wire format is exercised only through `encode.base64` and `decode.base64` (criterion 7).

## Verdict

The RFC is sound and its implementation meets it. Every citation re-read holds, and every criterion is checkable and has a named test.

Two problems were missed by the eleven earlier reviews, both now caught:
- the JSON round trip, which turned out to be impossible, and was corrected in the RFC but not in D252 (SF1);
- refusal texts that S5 implies but S8 never wrote down (SF2).

SF1 needs the owner, since `decisions.md` is append-only and its notes are the owner's to record. SF2 to SF4 and the notes are wording, best done in one dated note on the RFC.
