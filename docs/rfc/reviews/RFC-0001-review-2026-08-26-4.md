# RFC-0001 review 4 — 2026-08-26

Adversarial read of `docs/rfc/RFC-0001-value.md` at commit `221926a`, against
`reference/` at the pinned SHAs (`cargo xtask cite`: 5/5 oracle crates
byte-verified, 1221 citations resolve, 0 defects).

**Verdict: do not accept.**

Review 3's ten items are done and hold. Every `reference/...:N` citation in the
RFC was opened and read this pass — all 50 resolve, and with the two exceptions
in C3 and C10 all say what the prose says. `cargo xtask layout` reproduces every figure
(16/8; scalar 0/0; `dup a list 4 649`; `dup a boxed scalar 4 649`; `box a
scalar 5 721`). `cargo xtask corpus` reproduces 132 programs and `dup 55 38`.
The payload↔`dt` table is now complete and correct: I verified all six rows
against their constructors, including the two post-construction assignments
(`create.rs:166`, `:186`) and `CURRY` → `Val::Map`
(`reference/rust_dynamic/src/create_curry.rs:16,18`).

What blocks it is different in kind from reviews 2 and 3. Those found the design
contradicting its own table. This one finds **the design contradicting the
decision it consumes**: D13's explicit instruction — "the lazy identity slot
must be shared across clones and must split at the same points the `Rc` does…
RFC-0001 must show one policy governing both" — is answered for `Clone` and left
unanswered for `Rc::make_mut`, and the gap fires on the hottest path in the
language. Alongside it: criterion 7's "nineteen" is still unsatisfiable for the
same reason "twenty" was, three counts in the scalar argument are wrong, and the
preservation table has no row for the RFC's largest deviation.

## A. Blocking

### A1 — `Rc::make_mut` on an unminted identity breaks D1's clone-equal contract

*Design, "Value semantics", lines 313-329; preservation row `set_tag`, line 546.*

The RFC says:

> Mutations that mint nothing, of which `set_tag` is the only one reachable, are
> split points too, and `make_mut` copying the id is the correct behaviour for
> them, because the reference's in-place write does not change the id either.

and the table row says "**Preserved exactly.** `make_mut` copies the id, which
is what an in-place write does."

`make_mut` does not copy *an id*. It copies **the slot**, and under D1 the slot
is normally empty. Copying an empty slot does not preserve identity — it creates
two independent futures that will mint *different* identities on first
observation. That is precisely the hazard D1 names:

> Under naive deferred generation, an unobserved value and its clone each hold an
> empty slot, materialise independently, and compare **unequal** — a silent
> behaviour change on the most ordinary operation there is.
> (`docs/registers/decisions.md:40-43`)

The RFC answers that hazard for `Clone` only ("`Clone` is an `Rc` bump, so the
identity slot is shared", row at line 544). `make_mut` is the other half, and
D13 asks for both in one policy:

> the lazy identity slot must be shared across clones and must split at the same
> points the `Rc` does. If the two split policies disagree, an unobserved value
> and its clone materialise different ids and `A == A.clone()` silently becomes
> false. RFC-0001 must show one policy governing both.
> (`docs/registers/decisions.md:352-356`)

**The failing sequence, all on live paths.**

1. `A` is a heap value, never observed. `identity` slot is 0.
2. `B = A.clone()` — an `Rc` bump. One `HeapValue`, refcount 2, one slot.
3. `B` is pushed. `TS::push` calls `value.set_tag("stack", …)` unconditionally
   (`reference/rust_multistack/src/ts_push.rs:25`) — a mutation that mints
   nothing, so by the RFC's own rule it is a `make_mut` split.
4. Refcount is 2, so `make_mut` clones the `HeapValue`. Both copies now hold
   `identity: Cell(0)`.
5. `A == B` materialises both. Two different counter values. **False.**

In the reference, `Clone` copies the `String` and `set_tag` mutates in place, so
`A` and `B` still share an id and `A == B` is **true** through
`reference/rust_dynamic/src/eq.rs:53`.

Step 2 is not exotic: `Value::get` returns `d.clone()`
(`reference/rust_dynamic/src/get.rs:11`), `peek` clones, `push` clones every
element (`reference/rust_dynamic/src/push.rs:42,44`). Step 3 is *every push*.
This is the contract review 2 blocked on, broken again by a different mechanism.

The repair is not large — force the identity before `make_mut` clones, or give
`identity` its own `Rc` the way `payload` already has one for exactly this
"shareable on different schedules" reason (line 307-309) — but it is a design
change and the RFC has to state which, and then say it in the table.

**The same defect applies to `stamp`.** `Cell<f64>`, same slot, same split. In
the reference a clone carries the original's `stamp` and `set_tag` does not
touch it, so `A.timestamp` and `B.timestamp` agree. Under this design they
disagree. D2's deviation section (lines 428-433) states only the converse — two
values constructed apart reporting the same stamp — and not this one.

**And `curr` is worse, because it is shared where it should not be.**
`curr: Cell<i32>` sits inside the `Rc`, so a `Cell` write mutates *every clone*
without needing `&mut` and therefore without triggering `make_mut` at all. The
reference's `curr` is per-value: `Clone` is derived, so clones get independent
cursors, and `Iterator::next` takes `&mut self`
(`reference/rust_dynamic/src/iter.rs:6`). Putting the cursor in a shared `Cell`
gives it reference semantics inside a value model D13 exists to keep by-value.
Latent today — `impl Iterator` has no caller, which I re-verified: no `curr`
assignment exists anywhere outside `iter.rs` across all four crates — but the
RFC carries the field precisely so RFC-0003 can drive it, and this is the state
RFC-0003 would inherit.

### A2 — criterion 7's "nineteen" is unsatisfiable for the same reason "twenty" was

*Criterion 7, lines 634-640; F38.*

Review 3 cut criterion 7 from twenty payload arms to nineteen on the ground that
`Val::Token` has no constructor. The criterion's method is "compared against
bytes **captured from the oracle**" — which requires the arm to be **producible
by a running Bund**, not merely to have a Rust constructor. Three more arms fail
that test:

| arm | constructor | callers outside `rust_dynamic` | callers inside |
|---|---|---|---|
| `Val::Exit` | `Value::exit()` (`reference/rust_dynamic/src/create_special.rs:85-91`) | 0 | 0 |
| `Val::Operator` | `Value::operator()` (`reference/rust_dynamic/src/create_special.rs:109-115`) | 0 | 0 |
| `Val::Embedding` | `Value::embedding()` (`reference/rust_dynamic/src/create_special.rs:253-259`) | 0 | 0 |

Verified two ways: no call site for any of the three constructors in
`rust_multistackvm`, `rust_multistack`, `Bund`, `bundcore` or `rust_dynamic`
itself, and no construction of `Val::Exit`, `Val::Operator` or `Val::Embedding`
anywhere outside `create_special.rs`. Contrast `Val::Metrics`, which *is*
reachable — `Value::metrics()` is called by the `metrics` word
(`reference/rust_multistackvm/src/stdlib/artefacts.rs:62`).

So the criterion asks for bytes the oracle cannot emit for at least four of its
nineteen. F38 states "nineteen of the twenty payload arms can be produced by a
running Bund and one cannot"; that is false as written and needs amending
alongside the criterion. The number the criterion can honestly ask for is
**sixteen or fewer**, and the RFC should enumerate the arms rather than quote a
count — which it currently cannot do at all, because of A3.

Note this is a *different* question from F36's, which scanned for a **write** of
each `dt` constant. `Value::exit()` writes `dt: EXIT`, so F36's scan excluded
`EXIT` correctly by its own criterion while the writer is itself dead. Two
distinct properties; the RFC uses the weaker one to certify the stronger claim.

### A3 — `Payload` is used and never defined

*Design, "The heap object", line 251.*

`HeapValue` declares `payload: Rc<Payload>`. `Payload` appears nowhere else in
the RFC. The entire discussion of nineteen/twenty arms, of `Val::Token`'s
omission (F38), of `dt` and payload as independent axes, and of criterion 7
presupposes a `Payload` enum that the RFC never writes down — while it does
write down `BundValue` (line 220) and `HeapValue` (line 244).

The consequence is not cosmetic. Two register entries hand RFC-0001 decisions
that can only be recorded in that type and are therefore unmade:

- **F15** — "Fixing this means choosing a deterministic map for the value
  representation, which is RFC-0001 territory and interacts with D13… Which
  order — insertion or sorted — is a value-representation question for
  RFC-0001" (`docs/registers/defects.md:193-194,201-202`). The RFC picks `BTreeMap` for
  `tags` and says nothing at all about `Val::Map`'s replacement, which is the
  larger half — F15 records that the unordered dict is the cause of 15 of 18
  unreproducible programs and that it reaches output through **two** rendering
  paths. F15 is not mentioned in the RFC, has no preservation row, and no
  criterion.
- **F36** — "Record the omission in RFC-0001's **tag table**, and note that it
  makes the tag count 38 live constants of 42 declared"
  (`docs/registers/defects.md:847-850`). There is no tag table. See B1.

### A4 — three counts in the scalar argument are wrong

*Lines 346-349; criterion 2, lines 598-600; criterion 6, lines 630-633; review
history 3, lines 774-777.*

The RFC states, in four places, that **27** of the 258 renderings have a scalar
payload and **24** of those carry a non-empty `tags`. The goldens say **34** and
**29**:

| payload | renderings | with non-empty `tags` |
|---|---|---|
| `I64` | 17 | 12 |
| `Bool` | 12 | 12 |
| `F64` | 3 | 3 |
| `Null` | 2 | 2 |
| **total** | **34** | **29** |

Reproduce with `grep -o 'data: I64' $(find tests/golden -name '*.golden') | wc -l`
and siblings. The 258 total and the 29-golden figure are correct on the same
basis (every `Value {`, nested included), so the two numbers are not on
different footings — 27 and 24 do not reconcile with any counting rule I could
construct: top-level-only gives 18 and 18, and dropping any one payload kind
gives 22, 31 or 32.

The direction is against the RFC: **more** renderings than claimed are ones an
inline-only scalar arm could not produce. The argument survives and gets
stronger; the figures in it do not. This is the third review to find a count in
this RFC that does not reproduce, and criterion 6 is written *against* these
figures, so it is currently unsatisfiable as stated.

### A5 — the preservation table has no row for the RFC's largest deviation

*Preservation analysis, lines 538-565.*

`42 == 42.5` changes from **true** to **false**. That is the one change in this
RFC that a captured golden already disagrees with — `eq-asymmetry.golden` pins
`true` — and it has no row.

The two equality rows do not cover it:

- Line 547, "Equality: content for four arms, identity for fifteen, mixed for
  `Val::List`" → "**Preserved exactly** for every arm with a heap header". Under
  this design `Int` and `Float` are *scalar* arms, not heap arms, so this row
  explicitly excludes them.
- Line 548, "Equality by identity for `Bool`, `Nodata`, `None`" → covers the
  other three scalars.

So the table says nothing whatever about `Int` and `Float` equality, which is
where F33 lives. The design section (lines 436-468) and criterion 12 are both
correct and I verified them against `tests/golden/probes/eq-asymmetry.golden`
line by line — truncating orientation `false`, widening `true`, both now
labelled the right way round. The Preservation analysis is the contract, and the
deviation is missing from it.

Three more dispositions with no row: **F15** (see A3), **F38** (`Val::Token`
omitted — named in criterion 7, absent from the table), and **F14** (Bund2's
error text drops `Debug`, which interacts directly with criterion 6's "the
`Debug` rendering reproduces the reference's text").

Note `cargo xtask lint` cannot catch any of these: it cross-checks *rows that
name a defect* against that defect's disposition (10 rows across both RFCs). A
missing row is invisible to it, and criterion 14 leans on it as if it were not.

## B. Must fix before acceptance

### B1 — the `dt` row contradicts the F36 row, and the count is wrong

Line 540: "`dt` carried verbatim as a `u16` over **the same 42 constants**."
Line 551: "`ASSOCIATION` … **Deliberately omitted.**"
Line 805 (review history): "**F36** is extended … to all four `dt` constants
with no writer: `LITERAL`, `LARGE_FLOAT`, `ASSOCIATION`, `TOKEN`, leaving **38
live of 42** declared."

Three statements, two of them incompatible with the first. The RFC knows the
answer is 38 and its table still says 42, and names only one of the four
omissions. F36 asks for a tag table; there is none (A3).

Verified: `types.rs:15-56` is exactly 42 constants, and I re-ran F36's scan —
`LITERAL`, `LARGE_FLOAT`, `ASSOCIATION` and `TOKEN` have neither a `dt:` field
initialiser nor a `dt = ` assignment. `Value::association()` sets `dt: CONFIG`
(`reference/rust_dynamic/src/create_map.rs:85`), which is why `ASSOCIATION` has
no writer; the RFC's payload table is right to omit it from the `Val::Map` row.

### B2 — F35's row claims a symmetry with `set` that does not hold for lists

Line 550: "`push` on a `RESULT` yielding a `LIST` (F35) — **Deliberately
fixed.** The `dt` is preserved, **as `set` already does for maps.**"

True for maps (`reference/rust_dynamic/src/set.rs:21-22` rebuilds through
`from_dict` and then restores `raw_value.dt = self.dt`). But `set` has the
identical `dt`-loss on the arm above it:

```rust reference/rust_dynamic/src/set.rs:8-10
    LIST | RESULT => {
        return Value::from_list(vec![value]);
    }
```

`from_list` writes `dt: LIST` (`reference/rust_dynamic/src/create_list.rs:23`),
so `set` on a `RESULT` yields a `LIST` exactly as `push` does — and, separately,
discards the receiver's entire contents. F35 is dispositioned as a `push`-only
fix, the RFC's row cites `set` as the model to follow, and the model has the same
bug in a second place. Either F35 extends to `set.rs:8-10` or the row must stop
claiming `set` gets it right.

### B3 — the ordering analysis covers the unreachable path and not the reachable one

*Lines 131-137; preservation row, line 553.*

Both citations check out — `cmp`'s four `id.cmp` fallbacks are at `ord.rs:175,
183,191,199`, and `lt`'s `_ => return true` at `:16,24`. What is missing is that
**`lt` is not alone**. `impl PartialOrd for Value` overrides four methods, not
one:

    reference/rust_dynamic/src/ord.rs:9    fn lt
    reference/rust_dynamic/src/ord.rs:48   fn le
    reference/rust_dynamic/src/ord.rs:87   fn gt
    reference/rust_dynamic/src/ord.rs:126  fn ge

Each has `Val::I64`, `Val::F64`, `Val::Time`, `CINTEGER` and `CFLOAT` arms and a
`_ => return true` fallback, and **none of them reads `id`**. Only
`partial_cmp` (`:6-8`) delegates to `cmp`.

That is the ordering the language actually reaches, and it is covered by a
golden. `algos::sort::quicksort::sort::<Value>`
(`reference/Bund/src/stdlib/functions/values/sort_lists.rs:36`) compares with
`>` and `<=`, which land on the overridden `gt`/`le`;
`reference/Bund/tests/testing_sorting_numbers_in_list.bund:7` sorts 15 **floats**
— `seq_descending` pushes `Value::from_float`
(`reference/Bund/src/stdlib/functions/math/seq.rs:29-38`) — and
`tests/golden/tests/testing_sorting_numbers_in_list.golden` records `Bool(true)`.
That golden passes *because* `gt` has an `F64` arm; had `>` reached `cmp` it
would sort by nanoid and fail 14 times in 15.

Consequences the RFC does not state:

- The **observable** ordering surface is four identity-free methods with a
  `true`-on-mismatch fallback. There is no preservation row for it, and no
  statement of what Bund2's `lt`/`le`/`gt`/`ge` do — including whether Bund2
  reproduces "`a < b` and `a > b` both true for a kind mismatch", which `sort`
  on a heterogeneous list exposes.
- Fixing `cmp`'s `F64` arm per F12 does **not** reconcile `cmp` with
  `lt`/`le`/`gt`/`ge`, which still disagree on every kind mismatch (`cmp` →
  `id.cmp`, the four → `true`). The row reads as though F12's fix closes the
  inconsistency; it closes one arm of it.
- Under this design, `cmp` for two `Bool`s — same kind, both scalar, no `I64`/
  `Time`/`String` arm, `dt` not `CINTEGER` — falls to `id.cmp` in the reference
  and has **no identity to read** in Bund2. The RFC argues scalar
  *equality*-by-identity is an acceptable deviation (lines 380-394); it makes no
  such argument for ordering, and review 2's finding was phrased as
  "identity-equality **or identity-ordering**" (line 723).
- D1's own secondary consequence — "if identity ends up counter-derived, the
  `Ord::cmp` fallback changes from 'lexicographic on a random nanoid' to
  'creation order'… a behaviour change on a path the reference has"
  (`docs/registers/decisions.md:54-56`) — is handed explicitly to RFC-0001 and
  appears nowhere in it.

Related, and a register defect rather than an RFC one: **F12 mis-attributes its
own citation.** It says "`partial_cmp` handles `Val::F64`
(`reference/rust_dynamic/src/ord.rs:19-21`)", but `:19-21` is inside `lt`, and
`partial_cmp` at `:6-8` is `Some(self.cmp(other))` — it delegates to `cmp` and
therefore *cannot* disagree with it. F12's disposition then asks Bund2 to make
`cmp` "consistent with `partial_cmp`", which is circular. `cargo xtask cite`
flags this exact line as an advisory (`defects.md:75 → ord.rs:19,21 —
'partial_cmp' occurs in the file but not within 3 lines`). RFC-0001 line 135
silently restates it in the correct terms ("inconsistent with `PartialOrd`'s
`lt`") without recording the correction, so the register stays wrong and the RFC
rests on a disposition whose stated target is incoherent.

### B4 — F34 is claimed as oracle-confirmed with no captured artefact

Line 405-406:

> Confirmed against the oracle: `dict 99 attribute "b" 2 set` renders
> `attr: []`, while the control `1 2 attribute` renders it populated.

The control is captured — `tests/golden/probes/value-fields.golden`, from
`tests/probes/value-fields.bund:10`. **The `dict 99 attribute "b" 2 set` case is
not.** It appears in no probe under `tests/probes/` and no golden under
`tests/golden/probes/`. F34 makes the same claim
(`docs/registers/defects.md:797-799`) with the same absence.

D21 exists to prevent exactly this: "we never hand-write expected output. A
probe states what to run; the reference states what it does"
(`docs/registers/decisions.md:723-725`). F34's row is marked "**Preserved
exactly**" and the mechanism diverges from the obvious implementation
(`make_mut` copies the header where the reference rebuilds it) — so it is a
preservation claim that nothing in the repository re-checks, and `cargo xtask
conform` will never catch a Bund2 that gets it wrong. Add the probe, or mark the
row "no golden covers it" as the F35 row honestly does.

### B5 — the F34 reset is enumerated short by two fields

Lines 396-412 and the row at 549 say a container mutation "clears `attr`, `curr`
and `tags`". The cited constructor resets **five** fields, not three:

```rust reference/rust_dynamic/src/create_map.rs:33-40
    id:   nanoid!(),
    stamp:  timestamp_ms(),
    dt:   MAP,
    q:    100.0,
    ...
    attr: Vec::new(),
    curr: -1,
    tags:   HashMap::new(),
```

The fresh `id` is covered elsewhere (row at line 543). The **`stamp` is not**.
D2 requires it: "`set` and `push` continue to reset it (`set.rs:32,59,92`,
`push.rs:166`), which under deferred sampling means resetting it back to
unobserved" (`docs/registers/decisions.md:116-117`). The RFC's `stamp` section
(lines 414-434) never mentions mutation, and its preservation row (line 552)
covers construction only. Under this design a container whose stamp was already
observed would keep it across a `set` unless the reset is stated. `q` is
likewise reset to `100.0`, which is harmless only because of the constant-render
decision — worth one clause, since that decision is itself in tension (C1).

## C. Smaller, but they should not survive a fifth review

### C1 — the `q`-is-constant argument and the two-`Null`-arms argument rest on the same function and disagree

Line 189-191 grounds `q` as renderable-constant on "`Value::new` sets `q: 0.0`
(`reference/rust_dynamic/src/value.rs:38`) but **nothing reaches it**".

Line 234-239 then adds a `None` arm to `BundValue` *because* `Value::new` sets
`dt: NONE` (`value.rs:37,39`).

Both are grounded in the same constructor. If `Value::new` is worth a dedicated
scalar arm, its `q: 0.0` is worth a rendering rule — and a Bund2 `None` will
render `q: 100.0` where the reference renders `q: 0.0`. That is an unstated
deviation on the one arm the RFC went out of its way to add.

Also: "nothing reaches it" is slightly overstated. `Value::none()` *is*
`Value::new()` (`reference/rust_dynamic/src/create_special.rs:19-21`) and has one
live caller, `reference/Bund/src/stdlib/functions/debug_fun/debug_debug.rs:20`.
The claim that survives is narrower and sufficient: no reachable path *renders*
a `q: 0.0` value through `Debug`, because that caller passes it to a
`comfy_table` cell. (`Value::map_float`, the other `Value::new()` site at
`reference/rust_dynamic/src/map.rs:108`, has no caller at all.) Q18's grounding
line carries the overstatement too.

### C2 — "29 of the 65 goldens" is stale; the denominator is 66

Line 195 says 65; criterion 5 says 0/66; `tests/golden/CONFORMANCE.txt` says
`0/66`; `find tests/golden -name '*.golden' | wc -l` says 66. RFC-0000's
provenance table records all three moves 63→64→65→66
(`docs/rfc/RFC-0000-architecture.md:466-468`), and criterion 5's account of them
is correct. The "29" and "258" are unaffected — `eq-asymmetry.golden`, the
ninth probe, contains no `Value {` rendering — which is exactly why the stale
denominator was easy to miss.

(`tests/golden/CONFORMANCE.txt`'s own comment still says "59 goldens"; not the
RFC's text, but it is the artefact criterion 5 points at.)

### C3 — `Ord::cmp`'s partition is described with the same looseness the RFC corrected for `eq`

Line 131: "content for `I64`, `Time` and `String`, and `self.id.cmp(&other.id)`
**otherwise**". The catch-all has a `CINTEGER` arm that compares real parts by
content (`reference/rust_dynamic/src/ord.rs:196-198`), so "otherwise" is not
otherwise. The RFC made a point of stating `eq`'s partition precisely after
review 3 ("four arms by content, `Val::List` mixed, fifteen by identity"); the
parallel imprecision survives one paragraph below. Note also that `cmp` handles
`CINTEGER` and **not** `CFLOAT`, where `eq` handles both (`eq.rs:47,50`) — so
the two are not "the same shape".

### C4 — criterion 6's "reproduces the reference's text" is not literally satisfiable

Line 532-534 and criterion 6 both ask the `Debug` rendering to reproduce the
reference's text "exactly". It cannot, by this RFC's own design: `id` is a
counter, not the reference's nanoid, and `stamp` is sampled at a different
moment. Every golden header records the escape — "normalised: id and stamp
(F14), dict member order (F15), ANSI stripped" — so what is checkable is
"reproduces the **normalised** text", and the criterion should say so. As
written it asserts something D1, D2 and F14 have each already contradicted.

### C5 — criteria 2 and 3 are green today and do not bind the implementation

Criterion 1 says "asserted in a unit test in `bund2-value`, **and** `cargo xtask
layout` reports the same" — two checks, one of which binds the real type.
Criteria 2 and 3 name only `cargo xtask layout`, which measures
`CandidateHeader` declared in `xtask/src/layout/mod.rs`. Both pass right now,
against a scaffold whose `bund2` exits 70. They can stay passing while
`bund2-value` allocates differently. Give them the same second clause criterion
1 has.

### C6 — criterion 14 is not scoped to this RFC and currently fails

`cargo xtask lint` reports 1 inconsistency today —
`docs/rfc/RFC-0002-symbols-and-words.md:397`, a duplicate `## Design` heading.
RFC-0001 is clean. As written, criterion 14 makes RFC-0001's acceptance
contingent on a defect in a different document. Scope it, or state that the
whole-tree reading is intended.

### C7 — `Debug` is a sixth materialisation point

Line 276-277: "D1 enumerates the needs: `.id`, equality, ordering, hashing,
serialisation. All five materialise." Two paragraphs above, the RFC establishes
that the `Debug` rendering must print a nanoid-shaped id — a sixth. It should
be named as such, particularly since F14's disposition removes `Debug` from
error text but not from `debug.display_stack`, which is what the 29 goldens
capture.

### C8 — "dup-family" names one word

Line 50: "55 dup-family tokens across 38 of the 132 corpus programs". `cargo
xtask corpus` reports `dup 55 38` for the alias `dup` alone; `dup_one`,
`dup_many`, `dup_in`, `dup_many_in` and `dup_one_in` are separate rows. The
figure is right, the label is not.

### C9 — criterion 12's explanatory clause over-generalises

"the reference already answers false for the truncating one" holds for the
2^53 pair (`eq-asymmetry.golden`: int on top → `false`) and is the opposite of
true for the `42`/`42.5` pair in the same criterion (int on top → `true`). The
sentence was written about the 2^53 case — review 3's finding — and now reads as
covering both examples in the criterion.

### C10 — `eq.rs:59-62` is off by one

The `impl Eq for Value` block is lines **60-62**; `:59` is blank. Cited as
`:59-62` at line 440, and the same range appears in F33 and D30's amendment.
Harmless, and the only citation-range error I found in 50.

## D. Claims that need a citation and lack one

- **"a 21-character string" / "the reference's 21-character nanoid alphabet"**
  (lines 41, 260, 641). Repeated three times, load-bearing for criterion 8, and
  never grounded. It is a property of the `nanoid` crate's default, not of any
  line in `reference/`, and the goldens cannot corroborate it because the
  normaliser replaces every id with `<id>`. Either cite the dependency pin or
  drop the number from the criterion.
- **"`dt: 6` (`CALL`) appears 43 times and `dt: 7` (`PTR`) 30 times"** (line
  91-92). Both reproduce exactly, but no artefact or command is named, unlike
  every layout figure in the RFC.

## E. What the RFC assumes and does not state

1. **Single-threaded values.** `Rc` and `Cell` are `!Send` and `!Sync`. Nothing
   in the RFC says a `BundValue` cannot cross a thread. D6 (async granularity)
   and D7 (tens vs thousands of concurrent VMs) are both **OPEN**, and D7's
   default of "tens" is an actor model — which is compatible, but only if stated.
   If RFC-0007 ever moves a value between VMs, this is an `Arc` rewrite of the
   whole type. One sentence now; a crate-wide change later.
2. **The identity counter has no VM seed.** D1's resolution is "lazy nanoid
   derived from **counter plus VM seed** (preserves format)"
   (`docs/registers/decisions.md:14`). The RFC says only "that counter formatted
   into the reference's 21-character nanoid alphabet" (line 261-262), and
   criterion 8 scopes uniqueness to "two values minted in **one VM**". The seed
   is what makes ids distinguishable *across* VMs, which matters for the world
   file (D27) and for the cross-run contract D20 discusses under Q8. Dropping it
   is a narrowing of the decision, and silent narrowing is what CLAUDE.md's
   "never adopt an OPEN decision's default silently" rule is guarding against in
   the neighbouring case.
3. **What "formatted into the alphabet" means for ordering.** D1 predicts the
   `Ord::cmp` fallback becomes "creation order". That is only true for some
   formattings — a fixed-width big-endian encoding sorts by counter, a
   little-endian or variable-width one does not. The RFC picks neither. See B3.
4. **`BTreeMap` is a choice, not a given.** The `tags` field is `BTreeMap`
   (line 249) where the reference is `HashMap`
   (`reference/rust_dynamic/src/value.rs:24`). That is the F15 fix, silently:
   sorted rather than insertion order, chosen without saying so, for one of the
   two containers F15 covers and not the other. See A3.
5. **That `q` is never written by anything Bund2 will add.** The RFC renders it
   as a constant, which forecloses a future word writing it. Fine, but it is a
   language decision taken as a representation decision.
6. **That criterion 7's oracle byte-capture harness will exist.** No tool
   captures bincode bytes per payload arm today; `cargo xtask cite`'s two
   "exact-match blocks" are something else. Every other criterion names the
   command that checks it — 1/2/3 `layout`, 5 `conform`, 13 `cite`, 14 `lint`.
   Criterion 7 names none, and after A2 it does not even name a satisfiable set.
7. **That Q14 does not bite.** Q14 is OPEN and names RFC-0001 explicitly —
   "does the corpus resolve interpretation well enough to write RFC-0001 and
   RFC-0005 criteria against". The header's "**No OPEN decision or question
   gates this RFC**" is true only because RFC-0001 states no performance
   criterion. Say that, rather than leaving the blanket claim to be checked
   against the register by the next reader.
8. **That `Rc::make_mut`'s split points are the *only* places identity can
   diverge.** They are not, once the slot can be empty — see A1. The RFC's
   narrowed statement (line 321-323) is correct as far as it goes and stops one
   step before the case that matters.
