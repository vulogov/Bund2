## Blocking

### B1 — `recv` has a decode-failure arm a program can reach, both implementations reach it, they disagree on the text, and nothing records it

The reference's `bus_pull` has three arms, not two. After the absent-channel
`bail!` (`mod.rs:126`) and the empty-channel `NODATA` (`:130`), the decode
itself can fail: `Value::from_binary` returns `Err`, and the word bails with
`Error converting from binary: {err}` after logging the same text at
`ERROR` (`mod.rs:139-143`). The RFC describes `bus_pull` as "two arms"
(§C2's correction, criterion 1, the `recv` row) and the Preservation table
has a row for a failed *encode* at `send` (`mod.rs:114`) and none for a
failed *decode* at `recv`.

**It is reachable from Bund, on both sides.** `to_binary` wraps a JSON value
as text only at the top level (`bincode.rs:9`, `:54`); a JSON inside a
container is serialised as a bare `serde_json::Value`, which bincode writes
and cannot read back. Bund2's codec says exactly this of itself —
"a JSON value nested in a list is written as JSON, which then cannot be read
back, in the reference and here alike" (`wire.rs:722-724`) — and that its
failure text "is bincode 2's rather than `bincode2`'s, the one part of the
round trip that is not the reference's" (`:759-760`). The RFC never read
that paragraph. Measured today, release oracle and Bund2, one program:

```
"jm" dict "k" '{"k": 1}' json set send
"jm" recv
```

| | `send` | `recv` |
|---|---|---|
| oracle | `true` | `RECV returns error Error converting from binary: Bincode does not support the serde::Deserializer::deserialize_any method (…/rust_dynamic-0.49.0/src/bincode.rs:75:17)`, plus an `ERROR bund::stdlib::functions::bus` line on stderr |
| Bund2 | `true` | `RECV returns error Error converting from binary: Serde(AnyNotSupported)` |

(A JSON inside a LIST cannot be built this way: `push` refuses a JSON on
both sides with the same text, and a `[ … json ]` literal holds the word
unevaluated. A MAP member is one container that takes it; nothing here says
it is the only one.)

Four things follow, none of them in the document:

1. **A Preservation row is missing** for the arm, and it is not "preserved":
   the prefix is the reference's and the reason after it is Bund2's codec's,
   which is exactly the shape D114 records for `send` — and D114 recorded it
   as an approved deviation with an entry. This one has no entry, no
   decision and no defect. `cargo xtask conform` cannot see it: the error
   renders through the reference's diagnostic table (F66).
2. **`send` accepts what `recv` cannot read, and the value is lost.** The
   sender was told `true`; the receiver dequeued the bytes (`mod.rs:132`,
   `bus.rs:94-96`) before the decode failed, so the message is gone on both
   sides. §C2's "with `MAX_WIRE_DEPTH` at 256 refusing what it could not
   read back" describes the one case F118 bounded; this case is not refused
   at `send`, and whether it should be is the same question D114 answered
   for depth. Under several VMs it is sharper: the sending VM has no way to
   learn that its message was dropped in another thread.
3. **The oracle prints a line Bund2 does not.** `log::error!` at `mod.rs:141`
   writes to stderr before the bail. Bund2 reports through the diagnostic
   (CLAUDE.md, D36) and prints nothing else. That is the policy, and the
   table records the same difference nowhere for this word.
4. **§C2's JSON note is incomplete.** It says "a JSON value is the
   exception" for identity and stamp, citing the top-level wrap. The
   nested case is the other half of the same two citations, and it is not
   an exception to identity but to *delivery*.

What is needed: a row; a decision on whether `send` refuses a value that
cannot be read back (as D114 did for depth) or `recv`'s text is accepted as
Bund2's; and a defect or ERRATA note that §C2 and criterion 1 described
`bus_pull` with one arm too few.

## Significant

### S1 — The `bund.exit` row describes a mechanism that is not what happens; run here

The row (`:585`): "`bund.exit` in a host VM — **Ends that VM, not the
process**: `request_exit` is per `Interp`, and `Host` returns the closure's
answer. Read from the code, not run."

Run, through a host, `Host::with_limit(1)`, one closure:

| step | result |
|---|---|
| `rt.eval_str("7 8 3 bund.exit 9")` | `Ok(())`; stack depth 2 (the `9` did not run) |
| `rt.eval_str("1 2 +")` on the same `Runtime` | `Ok(())`; stack depth still 2 — **nothing ran** |
| process | alive; the host spawns again; `live()` reads 0 |

So "ends that VM" is not the mechanism. `bund.exit` sets `exit_code` on the
`Interp`; the frame loop's `exit_gate` (`bund2-interp/src/lib.rs:563-570`)
refuses every later step with `Error::exited`, and the top level "recognises
it by the request, not by the text, and returns cleanly" (`:560-562`) — so
`eval_str` answers `Ok`, and **every subsequent `eval_str` on that `Runtime`
also answers `Ok` having evaluated nothing.** The code is readable only
through `Vm::exit_requested` (`bund2-api/src/lib.rs:756`,
`bund2-interp/src/lib.rs:2102`), which is what the CLI reads
(`bund2-cli/src/main.rs:1316`) and the host neither reads nor surfaces. An
embedder whose closure runs a script that calls `bund.exit 3` gets `Ok`,
whatever the closure returns, and no code.

The behaviour may be right — it is the CLI's own contract applied inside a
thread — but the row should say what it is: the VM is not ended, it is
switched off, silently, and the code is on `exit_requested()`. "Read from
the code, not run" was the honest label; the reading was wrong.

### S2 — Where a host VM's diagnostics go: a reporter that discards, not stderr

The fourth review's S2 asked for a row and proposed its content: "the
default reporter, stderr, unlabelled". The destination is wrong. `Interp::new`
installs `SilentReporter` (`bund2-interp/src/lib.rs:418`), whose `report`
is empty (`bund2-api/src/diag.rs:215-219`); `Runtime::build` installs
nothing else (`bund2-runtime/src/lib.rs:203-271`, and `:49-50` says the
default "discards"); only the CLI swaps in `TextReporter`
(`bund2-cli/src/main.rs:1253-1255`) and reports an evaluation error itself
(`:1309-1313`). A host VM is built by `Runtime::with_options_and_threshold`
(`host.rs:354`), so:

- an **Error** reaches the closure as `eval_str`'s `Err` and is reported
  nowhere — run here: `"absent" recv` in a host VM returns the full
  `Attempt to evaluate value … returned error: RECV returns error
  bus::internal::pipe no pipe: absent` string, and nothing is printed;
- a **Warning** or **Notice** a word emits through `Vm::report` — the
  startup-defect warning `eval_str` itself emits (`bund2-runtime/src/lib.rs:304-306`)
  among them — goes to `SilentReporter` and **vanishes**.

An embedder can install its own on `rt.interp.reporter` inside the closure
(`Runtime.interp` is public for that reason, `bund2-runtime/src/lib.rs:43-45`);
the RFC does not say so, and the Preservation table has no row. This is the
`Reporter` seam's whole reason for existing per CLAUDE.md, and under tens of
VMs it is the one place a diagnostic has no terminal to fall back to.

### S3 — The dropped-handle row's `Drop`, and the slot that comes back before the word table goes

Unchanged since the fourth review's S1. The row at `:586` names "`Vm`'s
`Drop`"; `Vm<T>` has none. The behaviour — the thread is detached and the
slot returns through `Finish<T>` — is right. And `Host::spawn`'s thread
stores the answer, `drop(finish)`s (slot back, waiter woken), and only then
drops `rt` at the scope's end (`host.rs:354-362`); `live()`'s doc says the
opposite order (`:290-294`). A woken waiter can spawn a 65th VM while the
64th's word table is still allocated. One line, `drop(rt)` before
`drop(finish)`, makes the comment and criterion 14's "VMs that exist at
once" true.

### S4 — Nothing shipped reaches the host, and the RFC does not say how an embedder would

The RFC puts §C8 in `bund2-async` and says what the crate holds
(`:444-453`). It does not say who links it. `bund2-cli` does not (no
`bund2-async` in its manifest; `grep` finds it only in the workspace root,
`crates/bund2/Cargo.toml`, and the crate itself). `crates/bund2`, "Library
facade. The embedding API.", declares `bund2-async` optional behind an
`async` feature (`Cargo.toml:16,22`, default off) — and its `src/lib.rs` is
twelve lines with **no items at all**: no `pub use`, no module. Enabling
the feature links the crate and exposes nothing. RFC-0000's crate table
says "optional; reconciles with the existing bus layer per RFC-0007"
(`:195`).

So today the host and the façade are reachable only by depending on
`bund2-async` directly, which no document says, and every test of criteria
10 to 14 is in-crate. Whether the facade is meant to re-export it, whether
`bund2 script` is ever meant to spawn a VM, and whether `async` stays a
feature at all are questions for RFC-0000 as much as this one; this RFC
should at least state the fact.

### S5 — The §C8 note "the mechanism above is wrong" withdraws more than it means to

The note at `:475-483` follows two bullets. The second ("`recv` has no
fairness … delivers to whichever wakes first") is the one that is wrong,
and the note corrects it. The first ("`bus.data` then `recv` is not atomic
… `ensure_bus` … releases the lock; another VM may consume in between") is
right — `mod.rs:58-70` releases at `:65`/`:68`, and `bus.rs:102-109` says
the same — and it is the mechanism criterion 12's test forces with a
barrier. A reader of "the mechanism above is wrong" cannot tell which
bullet is withdrawn. One word fixes it.

## Preservation analysis — rows the table lacks

Twenty-eight rows now. What the design touches and no row names:

1. **A failed decode at `recv`** (B1): reachable with a JSON inside a MAP;
   `RECV returns error Error converting from binary: ` with the decoder's
   own reason on each side; the message is consumed and lost; the oracle
   also logs an `ERROR` line and Bund2 does not.
2. **Where a host VM's diagnostics go** (S2): an Error to the closure as
   `Err`, a Warning or Notice to `SilentReporter`; an embedder installs its
   own on `rt.interp.reporter`.
3. **What `bund.exit` does in a host VM** (S1): `Ok`, the `Runtime` is then
   switched off, the code is on `exit_requested()` and the host does not
   surface it.
4. **The slot is released before the word table is freed** (S3).
5. **A `Host` dropped with live VMs**: no `Drop`; the threads run on and
   decrement a counter nobody reads. Fourth review's row 3.
6. **Every VM's default stack is `main`.** The "one flat namespace" row
   (`:579`) says a stack and a channel share a name; under N VMs it means
   `bus.data.current` on N default stacks is **one** channel, `main`, and
   `bus.rs:309-318` already works around exactly that in the tests.
7. **A received value's `stack` tag** is the receiving push's (amendment's
   assumption 9; a behaviour, so a row).
8. **`--nocolor` reaches spawned VMs** with D165 (a `HostOptions` field).
9. **How an embedder reaches the host** (S4): no binary links it; the
   facade's `async` feature exposes nothing.

## What the RFC assumes but does not state

1. **A value `send` accepts is a value `recv` can return.** False for a JSON
   inside a container, on both sides (B1). §C2's "refusing what it could
   not read back" is true of depth and of nothing else.
2. **The three decoders' failure texts are Bund2's.** `wire.rs:759-760`
   says so; D88 and F109 speak of the decoded *value*, never of a decode
   that fails. For `sqlite` and the world file F109 noted that any other
   bytes "fail the whole query with the decoder's message"; for the bus the
   RFC says nothing.
3. **`bund.exit` in a host VM is observable by the embedder.** Only through
   `exit_requested()`, which the host does not read (S1).
4. **A host VM's warnings reach somebody.** They reach `SilentReporter` (S2).
5. **An embedder can link the host.** Only by naming `bund2-async` directly
   (S4).
6. **`Host::live()` is exact.** Not during teardown (S3).
7. **Criterion 13's two VMs start within 10,000 `recv` polls of each other.**
   An iteration bound, not a time bound; the executor's timeout does not
   cover it.
8. **Two `Host`s in one process share `PIPES`** — and share `main` as every
   VM's default channel name (row 6 above). Implied by "process-global",
   never stated as a property an embedder with two hosts meets.
9. **`Slot` is still 96 bytes.** §C1's note scales D85's 396 names to 610
   and keeps the slot size; no test in the tree asserts `size_of::<Slot>()`.

## Disposition

Not ready to accept. B1 is new and needs a decision, not a note: `send`
delivers a value that `recv` on either implementation cannot read, the
value is lost, and Bund2's text for the failure is its own — the same shape
D114 took to the owner for depth. B2 and B3 are the fourth review's two
blockers, unchanged because the document is unchanged. S1 and S2 are two
rows the amendment labelled "not run"; running them showed one mechanism
wrong and the other review's proposed row pointing at the wrong place,
which is an argument for running the rest before the next amendment rather
than labelling them. Every test the criteria name exists and passes in both
builds; criterion 8 is now checked for all eight words on both binaries;
nothing in the code blocks, and the code's own comment at `wire.rs:722-724`
knew B1 two weeks before this document did.
