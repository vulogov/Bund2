## Verdict

**Three blockers.**

- **B1.** The RFC never says how the program gets into the artefact. The
  research it builds on says `include_bytes!` into a stub and link it, and
  on Linux and macOS `rustc` links through `cc`. Read that way,
  `--emit=bundle` needs the C toolchain that D10 forbids below `bund2 build`.
  Criterion 4 would catch that only after it was built.
- **B2.** Encoding the program with the wire codec changes what its literals
  are. Stamps are fixed at build time, against D2. The name of every `( … )`
  context is the same on every run. Every scalar literal comes back boxed, and
  that makes Tier 0 and Tier 1 disagree about a literal's `.timestamp` inside
  one bundle. Source locations are also dropped from every diagnostic.
  Criterion 2 cannot see any of this. The Preservation table says "preserved
  exactly".
- **B3.** §B5 says `--emit=native` is "the same lowering, pointed at
  `ObjectModule`". The lowering bakes host-process heap addresses into the
  code as immediates, and it plans against a live `Vm`. The RFC does not say
  which bodies get compiled at build time, when no word is registered yet.
  Criterion 7 is defined against lowering that cannot be emitted into an
  object file as it stands.

## B1 — the bundle's own construction is unstated, and the obvious reading needs `cc`

§B2 says what a bundle contains. §B3 says what its `main` does. Neither says
**how the bytes and the stub become one executable.** The research the RFC
builds on says it outright:

> Serialise the BundIR object format (main study §4.3), `include_bytes!` it
> into a stub `main`, link against the runtime.
> — `docs/research/02-native-binaries.md:44-46`

That is a `rustc` invocation per build. On `*-linux-gnu` and on macOS,
`rustc`'s default linker driver **is `cc`**. D10's resolution
(`docs/registers/decisions.md:450-461`) forbids exactly that for this mode:
"It does not permit … `--emit=bundle` itself to require a C compiler." It also
forbids needing a Rust toolchain in some form, which the RFC does not mention
at all.

Several other passages only make sense under a particular answer to this
question:

- **Criterion 3** asks `cargo tree` "on the bundle stub", which assumes the
  stub is a Cargo package that is built.
- **§B2's case for versioning** is "a bundle is read by a runtime that may be
  newer than the one that wrote it". Under `include_bytes!` that cannot
  happen, because the reader and the writer are the same compilation. It is
  true only if the payload is *attached to a prebuilt stub*, for example by
  appending it to the binary or writing it into a named section.
- **The third open question** asks what a runtime does with a version it does
  not recognise. The answer depends on the same choice.
- **§B6** says a target Cranelift does not support gets `--emit=bundle`. For
  that to be true without a toolchain, `bund2 build` must *ship a prebuilt
  stub for each target*. That is a distribution decision, and nothing states
  it.

**What is needed.** State the construction. A prebuilt stub with the payload
attached is the only option consistent with D10 that I can see. Then make
criterion 4 check the **absence of `rustc` and `cc` during `bund2 build`**, not
only building the stub without `cc`. If a Rust toolchain is required, that is
a decision against D10's wording and it belongs in the register.

## B2 — the wire codec is not neutral about the literals it carries

§B2 adopts `wire::to_binary` per element and §"Preservation analysis" says
"Same IR, same evaluator". The IR that reaches the evaluator is not the same
IR. Four behaviours change, and none of them is listed.

**1. Stamps are fixed at build time — against D2.** `WireValue::from_value`
states "**Serialising materialises the identity and the stamp** (D20)"
(`crates/bund2-value/src/wire.rs:145-147`). `into_value` restores the stamp as
written: `stamp: Cell::new(node.stamp)` (`wire.rs:300-302`). D2 makes a
stamp mean "when this value was first asked", and records that as an approved
deviation (`docs/registers/decisions.md:66-110`). A literal in a bundle gets a
third meaning: *when the artefact was built*. That can be before the program
started, even by years. `.timestamp` reads it directly
(`crates/bund2-stdlib/src/oop.rs:328-339`). No decision covers this, and D20's
list of places where "materialising is correct"
(`decisions.md:919-924`) covers values *meant to be read by another process*,
which a program's own literals are not.

**2. The name of the anonymous `( … )` context is fixed across runs.** Lowering
emits `BundValue::context()` for every `Ctx` term
(`crates/bund2-syntax/src/lib.rs`, `lower_into`'s `Term::Ctx` arm). That mints
a fresh id as the stack's name (`crates/bund2-value/src/lib.rs:600-602`). The
reference also mints one per parse
(`reference/rust_dynamic/src/create_special.rs:28`, `data: Val::String(nanoid!())`, cited at
`lib.rs:595-596`). In the interpreter, every run lowers again and gets a new
name. In a bundle, lowering happened once at build time, so every run of the
artefact shares the same name. A program that `save.stacks` into a world file
and runs twice gets collisions it cannot get today.

**3. Every scalar literal comes back boxed.** `leaf_payload` decodes an
integer as `Payload::Scalar(BundValue::Int(..))` (`wire.rs:326`), and every
node is wrapped as `BundValue::Heap(..)` (`wire.rs:300-309`). D1 settled that
"Scalars therefore carry no identity" and are not heap values
(`decisions.md:58-64`). Two consequences follow, one about speed and one about
meaning:

- Tier 0's fragment guard `TopAreInt` matches only
  `Some(BundValue::Int(_, _))` (`crates/bund2-ir/src/fragment.rs:167`). A
  boxed literal fails it, so every fragment guarded that way **declines on
  bundled literals** that it admits in the interpreter.
- Tier 1 classifies a literal by `dt() == INTEGER` and then `as_int()`
  (`crates/bund2-jit/src/lower.rs:1904-1907`), which accepts the boxed form,
  and emits `Plan::Literal(n)`. It then pushes a **fresh, unboxed** int. So in
  a `jit` bundle the same literal has a build-time stamp when Tier 0 pushes it
  and an observation-time stamp when Tier 1 does. **The tier changes a value a
  program can read.** That is the invariant RFC-0005 and CLAUDE.md hold at
  exactly zero.

**4. Diagnostics lose their source location.** The CLI takes a location from
`lowered.span_of(i)`, the source text and the file name
(`crates/bund2-cli/src/main.rs:457-463`). §B2's container holds a magic, a
version, SHAs and values: **no spans, no source text and no file name.** So
every error a bundle reports has lost the Bund source location that D36
requires. `lower_with_spans` keeps spans *beside* the values, not in them
(`bund2-syntax/src/lib.rs`, `Lowered`), so the wire codec could not carry
them even in principle.

**Why criterion 2 misses all four.** Goldens normalise id and stamp away
(`xtask/src/golden/mod.rs:166-168`, F14). An anonymous context name is random
per run in the oracle too, so no reproducible golden can contain one. Goldens
capture stdout, and diagnostics go to stderr (`bund2-cli/src/main.rs`, the
`--stats` comment: "Every golden captures stdout"). Boxing changes speed, not
output. Criterion 2 would pass on a bundle that has all four problems.

**An alternative the RFC does not consider: embed the source text.** If the
bundle carries source and the stub runs `parse` then `lower_with_spans`, as
the CLI does, all four problems disappear. The same step also removes the
depth-cap mismatch (S2), the JSON-quirk argument, and most of the
container-versioning question. D76 chose the source-text form for embedded
`use` targets for a closely related reason: keeping errors where they are
today. The cost is parse time at startup, and nothing has measured it. The
RFC should either take this route or reject it with a number. It should not
leave it out of "Alternatives considered".

## B3 — §B5's "same lowering" cannot be pointed at an object file as built

§B5 says: "The same lowering, pointed at `ObjectModule` instead of
`JITModule`. … the two differ in which `Module` receives the CLIF." Following
`compile_word` one level down:

- **Host addresses are baked in as immediates.**
  `let slots_base = slots.as_ptr() as i64;` (`lower.rs:2341`), then
  `f.ins().iconst(ptr, slots_base)` (`:2549`). The generation-cell base is
  baked the same way, `f.ins().iconst(ptr, cells)` (`:2553`, and `:3091` for
  the floor). These are heap addresses in the compiling process, and they mean
  nothing in the process that runs a `.o`.
- **The plan is made against a live VM.** `compile_word(&mut self, body, last,
  cells, vm: &mut dyn Vm)` (`lower.rs:1793-1799`) calls `plan_body(body, vm)`,
  and that asks `self.crossable_callee(v, vm)` (`:1909`). The answer depends on
  what is registered *at that moment*.
- **Runtime helpers are bound by address.** `builder.symbol("jit_pop_int",
  jit_pop_int as *const u8)` and its siblings (`lower.rs:997-1000`,
  `:2251-2260`) are `JITBuilder` bindings. In an object file they become
  undefined symbols, which the runtime library must then export under stable,
  unmangled names.

These lead to questions §B5 has to answer, and it answers none of them:

1. **Which bodies are compiled at build time?** Tier 1 compiles a registered
   word's body once it passes a run-time threshold. At build time nothing is
   registered, because `:w { … } register` has not run, and under D16 the name
   may be computed.
2. **How do slot tables and generation cells reach compiled code?** Through the
   context, or through data symbols? If through data symbols, they add
   *relocation records*. Criterion 7 ("no relocation targeting a function
   beyond the two") survives that only if it says data relocations are
   outside its scope. It should say so, because RFC-0005 criterion 4 was
   written about a module where these relocations did not exist.
3. **What does the runtime library export, and in what relocation model?**
   (PIC, symbol names, and the `libbund2_runtime.a` that
   `02-native-binaries.md:224-226` names.)

"Specified to the depth D10 and RFC-0005's criterion 4 require" is not met.
Criterion 7 cannot be built until question 2 is answered.

## Significant

**S1 — Current behaviour omits the reference's whole-program producer, and
§B2 argues against a design the reference already has.** D11 is titled
"external dependents of `compile_to_binary`". That function is
`reference/bund_language_parser/src/compile.rs:23-30`. It parses a program,
**wraps the token vector in one LIST** (`bund_vec_to_list`, `:6-12`) and
calls `to_binary` on it. It has zero callers (grep over `reference/`). The RFC
cites only `Value::compile` (`bincode.rs:38-50`), which refuses anything that
is not a LAMBDA. §B2 then rejects "`wire::to_binary` applied to the program as
a whole" because "that function takes one value, not a vector". The
reference's answer to that objection is one line long. The conclusion (one
value per element) may still be right, since it avoids adding a nesting level,
but the reason given is not. The Current behaviour section should cite
`compile.rs`, because it is the closest thing the reference has to a bundle.

**S2 — `MAX_WIRE_DEPTH` makes `bund2 build` refuse programs the interpreter
runs, and that is a deviation, not preservation.** `MAX_WIRE_DEPTH` is 256
(`wire.rs:140`). The parser's `MAX_NESTING` is **1024**
(`crates/bund2-syntax/src/lib.rs:174`). A program nesting 257–1024 deep parses
and runs under `bund2 script` and cannot be bundled. The Preservation row
reads "**Preserved.**" It should read "deviation: build refuses what `script`
runs", with a register entry, or the RFC should pick the source-text form
(B2), which has no second bound. Separately, `wire.rs:127-133` records that a
decode aborts at depth **512** on a 2 MiB debug thread. The RFC does not say
which thread the stub decodes on. It needs to decode on the thread it spawns
(§B3), or it has to argue why the main thread is safe.

**S3 — Criterion 2 compares totals, and names no mechanism.** "Reports the
same N/M and the same CEILING" is satisfied by one golden newly failing while
another newly passes. The criterion needs **per-golden verdict equality**.
`cargo xtask conform` also has no mode that runs a bundle. The criterion
should name the flag or subcommand that will exist, or it is not yet
checkable. It is also blind to everything in B2 (see "Why criterion 2 misses
all four").

**S4 — There is no criterion for RFC-0005's hand-off on native conformance.**
RFC-0005 states: "the output of `bund2 build --emit=native` must read the same
N/M and CEILING as Tier 0 … Criterion 2 here covers the JIT; RFC-0006 states
the AOT counterpart" (`docs/rfc/RFC-0005-cranelift-tier.md:3917-3921`).
Criterion 2 here is about bundles. Criterion 8 says "conformance moves by
exactly zero" without saying *what is run*: source, bundles, or native
images. The native counterpart is not stated anywhere.

**S5 — §B1's main claim has no criterion, and criterion 3 is vacuous.** §B1
makes "ships no code generator" the gate for native. No criterion checks that
a native image lacks `cranelift-codegen`. Criterion 3 checks the *bundle*,
which §B1 says may contain Cranelift when `jit` is on. In the default build,
criterion 3 passes **today, before any bundle exists**:
`bund2-cli`'s `default = []` (`crates/bund2-cli/Cargo.toml:29-30`) and
`bund2-runtime`'s optional `bund2-jit` (`crates/bund2-runtime/Cargo.toml:23-29`)
already keep Cranelift out. It should check what `bund2 build` *actually
places in the artefact*, under both features, and a separate criterion should
check the native image.

**S6 — §B3 names a test that cannot hold the stub to anything.**
`a_tier_with_no_share_compiles_bodies_and_enters_none`
(`crates/bund2-runtime/src/tier.rs:1367`) builds a `Runtime` in-process, with
no thread and no stub. It shows the failure mode but does not check the stub.
Criterion 6 does, but it does not say how a bundle *reports*
`compiled_entries()`. The CLI does it through `--stats` on stderr
(`bund2-cli/src/main.rs`, `run_cli`), and B1's stub has no stated argument
parsing (see Assumption 4).

**S7 — ERRATA is promised and empty, and the RFC's terminology diverges from
the accepted RFCs.** The header says "where this RFC departs from it, §B8 says
so and `docs/research/ERRATA.md` records it". ERRATA has **no RFC-0006
entry**. Departures that need one:

- `02-native-binaries.md:44` says to serialise "the BundIR object format".
  §B2 serialises neither BundIR nor that format.
- `02-native-binaries.md:252-256` (Phase 5, `ObjectModule` first) is reversed.
  The RFC's Alternatives entry says so, but it is not recorded in ERRATA.

Terminology: the Summary says "the program's **BundIR** embedded". RFC-0000
(`docs/rfc/RFC-0000-architecture.md:225-236`) and RFC-0003
(`docs/rfc/RFC-0003-syntax-ir-and-tier0.md:480-485`) make BundIR the optional
instruction set, distinct from the `Vec<BundValue>` stream. RFC-0003 says
specifically that "if a later RFC serialises it — for AOT (RFC-0006) … D11's
'version freshly' applies". The RFC serialises the stream, not BundIR, and
should say so in those words. CLAUDE.md's terminology also defines "AOT = the
cranelift-object build", so the title "Ahead-of-time output" covers a bundle
that the defined term does not.

The same section omits current behaviour: **an `aot` feature already exists**
and is chained through `bund2-jit`, `bund2-runtime` and `bund2-cli`
(`crates/bund2-jit/Cargo.toml:52-54`, `crates/bund2-runtime/Cargo.toml:28`,
`crates/bund2-cli/Cargo.toml:33`; `docs/registers/defects.md:2613`). Its
comment, "Build this before the JIT: object output can be disassembled…", is
now stale.

**S8 — §B7 cites `:43` for more than `:43` shows.**
`reference/Bund/src/stdlib/helpers/file_helper.rs:43` is `easy.useragent("ZBUS")`,
and it supports the user agent. "No redirect is followed, the body of an error
status is still the answer, the body has no size limit" is shown by what
`:42-54` *does not set*: no `follow_location`, no `fail_on_error` and no size
cap. `get_file_from_uri` also turns a transport error into `None`
(`:46-50`). Cite `:42-54`, and say that these are curl's defaults *by
omission*. The same citation carries the same gap in D54
(`decisions.md:3216-3219`).

## Preservation analysis — what the table is missing

The table has five rows. The design can change at least these as well:

1. **`.timestamp` of a literal**: build time rather than first-observation
   time (B2.1; D2, D20).
2. **The anonymous `( … )` context name**: constant across runs (B2.2).
3. **Scalar representation, and so Tier 0 fragment admission and Tier 1/Tier 0
   agreement on stamps** (B2.3; D1).
4. **Diagnostic source locations**: lost (B2.4; D36).
5. **Programs nesting 257–1024 deep**: runnable under `script`, refused by
   `build` (S2).
6. **`args` / `args.parse`**: what a bundle passes to `script_args`
   (`crates/bund2-stdlib/src/host.rs:74-86`) versus what its runner consumes.
   Unstated (Assumption 4).
7. **The exit code**: the CLI returns `vm.exit_requested()`
   (`bund2-cli/src/main.rs:465`). The stub's behaviour is unstated.
8. **The word set.** D16 means no word can be proven unused. The corollary
   the RFC does not draw is that the *feature set the stub was built with*
   decides which words exist. A program calling `string.grok` works under a
   `grok` build of `bund2` and fails in a default-feature bundle, as an
   unknown word at run time and never at build time. This is D40's feature
   gate observed from the artefact side.
9. **Under `--emit=native`, words registered at run time** (`register`,
   `bund.eval`, `use`) have no code generator to reach in the shipped image.
   That is a change in speed, not meaning, but it should appear as a row so
   nobody later "fixes" it by shipping Cranelift.

## Assumptions the RFC makes and does not state

1. How the payload is joined to the stub, and whether `bund2 build` invokes
   `rustc`, `cargo` or a linker for `--emit=bundle` (B1).
2. That `bund2 build` ships a prebuilt stub for each target it can bundle for,
   including targets Cranelift does not support (§B6's promise).
3. That a program's literals may be fixed at build time without changing
   meaning (B2), which contradicts D2.
4. What the artefact's argv means: all of it goes to `args`, or the runner
   takes `--stats`, `--dump-stack` and `--raw-values` first as the CLI does
   (`main.rs`, `run_cli`). Criterion 6 depends on the answer.
5. Which reporter the stub installs, and what a diagnostic's location reads
   when there is no source (B2.4).
6. Which cargo features the bundled runtime is built with, and whether
   `bund2 build` lets the user choose (Preservation row 8).
7. For native: which bodies are compiled at build time, how slot tables and
   cells are addressed, and what the runtime library exports (B3).
8. That the bundle is decoded on the spawned evaluation thread, where depth
   256 is known to be safe (S2).
9. That one source file is the whole program. `use` is settled by D76, but the
   RFC does not say whether `bund2 build` takes several files, a directory, or
   standard input.
