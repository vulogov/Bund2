## Blocking

**B1 — `decode.base64` turns a string into a lambda and `!` runs it. A bundle
built `--noeval --noio` runs code that arrives on standard input, and the RFC
names the word nowhere.**

`encode.base64` serialises any value with `to_binary`
(`reference/Bund/src/stdlib/functions/encoding/base64.rs:33`), which the RFC
cites. `decode.base64` is its inverse: it pulls a STRING (`:71`),
base64-decodes it (`:77`) and hands the bytes to `Value::from_binary`
(`:83`). Both are registered with no gate (`:121-124`). Bund2 does the same
(`crates/bund2-stdlib/src/encoding.rs`, `decode_base64`). A LAMBDA is a
value, so a string becomes something `!` runs, and no parser is involved.

Measured. The string is what `{ 40 2 + println } encode.base64 println`
prints, 572 characters:

| built or run | program | result |
|---|---|---|
| bundle, `--noeval --noio`, stdin closed | `"<the string>" decode.base64 !` | `42` |
| bundle, `--noeval --noio` | `"> " input decode.base64 !`, the string piped in | `42` |
| `bund2 script --noeval --noio` | the first program | `42` |
| oracle `--noeval --noio`, its own string | the first program | `42` |
| oracle, Bund2's string; Bund2, the oracle's string | the first program | `42` both ways |

`--inspect` on both bundles prints `restrictions   --noio --noeval`.

What the RFC says:

- §B3a: "**no single flag stops a program obtaining text and running it**:
  under `--noeval` alone, `url` fetches and the three words above evaluate
  the result." This needs no fetch, no text, and holds under both flags.
- §B3a, "How this list was closed": "By reading every place outside tests
  where Bund2 parses a string at run time". `decode.base64` parses nothing.
  The search was the right idea aimed at one of two mechanisms.
- D122: the route is "a string a program holds, run with nobody at the
  keyboard, beside `compile lambda! !` and, under `--noeval` alone,
  `bootstrap`." A closed list in a RESOLVED decision, short by this.
- Criterion 10 says of itself that it checks stubs. It cannot see this.

Three things to weigh, the first against the finding.

- **It gives a program nothing `compile lambda! !` does not.**
  `"> " input compile lambda! !` already runs a line from standard input
  under both flags, and the RFC names that route. So the floor is where it
  was. D122's own reasoning — gating one word "would not make the flag mean
  'evaluates nothing' while `compile lambda! !` stands" — applies whole.
- **D78 asks for names, and this is the fifth review in a row to find one.**
  "RFC-0006 states what each flag leaves ungated, by name." The difference
  this time is that the RFC had just written down why the list was
  complete.
- **It is the one route an audit for text would miss.** A reader checking a
  program for `compile`, `debug` and `bootstrap`, as §B3a now teaches, finds
  none of them in `input decode.base64 !`. And the string travels: Bund2
  ran the oracle's and the oracle ran Bund2's.

**What it needs.** Either the owner's word that D122's ruling covers it, or a
ruling that it does not; then a paragraph in §B3a, a row in the preservation
table, a note on D122, and a second sentence in "How this list was closed"
naming the decode sites as well as the parse sites. There are six outside
tests: `encoding.rs` (this word), three in `world.rs` (`load.model`, and
S3's two), `data.rs` (`sqlite`'s BLOB cells) and `bus.rs` (`recv`). Only
the first is ungated under both flags. Gating it would be a deviation, as D119 was.

## Should fix

**S1 — `--output` on a hard link to the building binary is not refused, and
the build destroys the builder while reporting success.** §B3: "`--output`
naming the binary doing the building is refused, compared by canonical
path". The comment at the guard goes further: "Compared by identity rather
than by spelling — canonical paths, so a symlink or a relative path cannot
slip past" (`crates/bund2-cli/src/main.rs`, `build`). A canonical path is a
spelling. Two names for one inode have two.

Measured on a scratch copy, `ln bund2 alias`, then
`./bund2 build --file p.bund --output alias`:

| | before | after |
|---|---|---|
| the build | — | exit 0, "wrote …/alias — 13 of 1048576 bytes used" |
| `alias` | inode 219927895 | a new inode; runs and prints `hi` |
| `bund2` | inode 219927895 | same inode, bytes changed; `./bund2 words` exits 137 |

`build` writes with `std::fs::write`, which truncates and rewrites the
existing inode — the builder's. `codesign` then replaces `alias` with a
signed file of its own, so the builder is left holding the unsigned filled
image, which macOS kills. This is the implementation review's B3 by another
name, and `a_build_refuses_to_overwrite_the_binary_doing_it` cannot see it.

The cause is wider than the guard. Because the write is in place and not a
rename of a finished file:

- a symlink at `--output` is followed, and its target rewritten (read from
  `std::fs::write`'s contract, not measured);
- an artefact that is running while it is rebuilt is rewritten under itself
  (likewise);
- **a failed signing leaves a file at `--output` that cannot run.** `reseal`
  runs after the write and nothing removes the file. §B3 lists "a signing
  failure" among the failures that exit 1 and says of a program over
  capacity that nothing is written; it does not say that this one writes.

A defect for `defects.md`, and one sentence here. §B3's "replaced without a
word" is true and is the mild case.

**S2 — "How this list was closed" claims one search and the routes need
two.** B1's general form. The sentence that ends the paragraph — "A word
added later that parses a string appears in that search and not in this
list" — is true and reads as a guarantee. A word added later that *decodes*
a value appears in neither.

**S3 — Under `--noeval` alone, `load`, `load.lambdas` and `load.stacks` bring
runnable code in from a file. The eighth review's S2 said so in its last
sentence and the answer named `bootstrap` only.** Measured, on bundles built
`--noeval`:

| world file holds | program | result |
|---|---|---|
| the lambda `hidden`, `{ 40 2 + println }` | `"r9" load.lambdas hidden` | `42` |
| a stack whose top is `{ 40 2 + println }` | `"r9s" load.stacks !` | `42` |

With `BUND2_NOIO=1` the first answers
`bund LOAD functions disabled with --noio`. Bund2 decodes both through
`wire::from_binary` (`crates/bund2-stdlib/src/world.rs`); the reference
through `Value::from_binary`
(`reference/Bund/src/stdlib/helpers/world/lambdas.rs:32`, `stacks.rs:29`).
And `bootstrap` itself loads all of it before it evaluates a script
(`reference/Bund/src/stdlib/functions/bund/bund_load.rs:36`), which §B3a's
paragraph, citing `:42-50`, starts six lines too late to say. `sqlite` hands
a decoded BLOB to a lambda the same way
(`reference/Bund/src/stdlib/functions/conditional/conditional_sqlite.rs:170`;
read, not measured). All are `--noio` stubs, so the reference's boundary by
D79 — and names D78 requires.

**S4 — The preservation table says one word writes a file; §B3a says two.**
The `--noio`, `--noeval` row: "for `--noio` that includes one word that
writes a file". §B3a's bullet is headed "**One writes a file**" and goes on
to `debug`, which "keeps one of its own". The row five below it, "The

## What the RFC assumes and does not state

1. **Code a program is handed arrives as text.** It can arrive as a value
   (B1, S3).
2. **A search of parse sites finds every route** (S2).
3. **`--output` is the only name for the file it names**, and nothing is
   running it (S1).
4. **A build that fails leaves nothing.** True of four of the five failures
   §B3 lists (S1).
5. **The base64 form is Bund2's own business.** One string each way ran on
   the other binary, measured here; nothing in the RFC says whether that is
   relied on.
6. Carried, and stated in the RFC: the compiler does not fold reads of the
   region; the in-place write works on ELF and PE; `/usr/bin/codesign` is
   present and real; the builder can read its own executable; a refusal is
   text and not an exit status.

B1 is one word and one sentence of method: is `decode.base64 !` under
`--noeval` the reference's boundary, named, as D122 ruled for `debug`. If it
is, the rest is three names and two rows. S1 is a defect in `bund2 build`
that this RFC's sentence covers and its test does not.

**On the pattern.** This is the fifth review in a row to find a way a
restricted artefact runs code it was handed. The eighth asked how the list
had been closed; the RFC answered, and the answer was checkable, which is
what made this one findable by a single search. The citation table is clean
for the first time. What is left of the pattern is one mechanism wide: code
reaches a program as text or as a value, values are decoded in six places,
and the RFC has searched for the text.
