## Verdict

**Two blockers. One is new and measured; the other is carried unanswered.**

**B1.** F118's bound is on writing, and the new Preservation row says D31 makes
that enough. D31 is about world files. Since D27 a world file is redb, so a
SQLite file is never one. Yet `sqlite` decodes every BLOB in any SQLite file a
program names, through the same `from_binary`. **A 174 KB BLOB nested 3,000 deep
aborts the dev binary** (measured below). The row also gives three reasons no
audit sees the codec, and each is true of `save.model` alone.

**B2** is the twentieth review's B2, which `1326f15` did not touch. §S6 and D43
still say the generation mirror is written "by the same `touch()`". That cannot
be built, because `Slot::touch` has no name and no registry. There is still no
assumption or derivation for the mirror's writer set.

The twentieth review's significant items are also unanswered. The Status line
does not mention that review at all, so a reader cannot tell which of its items
stand (S1 below).

## B1 — the codec still aborts on decode, through a path D31 does not cover and the new Preservation row misdescribes

The row added in `1326f15` (line 2669):

> **the wire codec walking a value's depth**, which `save.model`, `load.model`
> and the sqlite blob path reach — and which no audit sees, since the word
> re-enters no evaluation and is `ACTS_ON_HOST` | an arena for both directions,
> and `MAX_WIRE_DEPTH` refusing to *write* past 256 levels, because bincode's
> derived `Deserialize` builds the tree before a check could run (F118); D31 is
> what makes a write-side bound sufficient

### The guard does not reach the third site it names

The codec has three shipped call sites (grep over `crates/`):

| site | direction | where the bytes come from |
|---|---|---|
| `crates/bund2-stdlib/src/world.rs:86` (`save_model`) | encode, bounded by `to_binary`'s `depth_of` (`crates/bund2-value/src/wire.rs:647-653`) | a value the program built |
| `crates/bund2-stdlib/src/world.rs:138` (`load_model`) | decode | a redb world file |
| `crates/bund2-stdlib/src/data.rs:326` (`sql_cell`) | decode | **a BLOB in any SQLite file whose path the program supplies** |

- **`sqlite_word` accepts any path** that `is_file()`
  (`crates/bund2-stdlib/src/data.rs:285`).
- **`run_sqlite` decodes every BLOB** it reads: it opens the file read-only
  (`:406`), runs the query (`:412-414`) and calls `sql_cell` on every cell
  (`:418`).
- **`sql_cell` sends every BLOB to `from_binary`** (`:326`).
- **`from_binary` has no depth check.** It calls bincode's
  `decode_from_slice` directly (`crates/bund2-value/src/wire.rs:680-682`), and
  `wire.rs:119-122` says a decode cannot be bounded.

**D31 cannot make a write-side bound enough here.** D31 asks whether anything
outside the project reads a Bund **world file**. Its resolution is that nothing
outside Bund opens one (`docs/registers/decisions.md:1478-1530`). D27 made the
world file redb, and `load_model` reads redb (`world.rs:122-140`). A SQLite
database opened through `sqlite` is therefore never a world file, and D31 says
nothing about who wrote its BLOBs. D39's third clause, added in `1326f15`,
says: "where the recursion is a dependency's, bound the side you control, and
say which side that is". On this path Bund2 writes neither the file nor the
BLOB, so the clause has no side to bound.

### Measured, 2026-09-12

The BLOBs were hand-encoded in bincode's legacy layout: `WireValue` field for
field (`wire.rs:37-46`), nested one-element `Val::List`s tagged LIST (9), and an
innermost `Val::Null` tagged NONE (0). That is the shape F118 measured. Each was
inserted with `sqlite3` and read by:

    "before" println
    "<db>" sqlite :sql "select b from t" set :lambda { "row decoded" println drop } set !
    "after" println

run as `target/debug/bund2 script --file …`, the dev binary `conform` had just
built:

| depth | BLOB | exit | output |
|---|---|---|---|
| 10 | 572 B | 0 | `before`, `row decoded`, `after` |
| 256 | 14,840 B | 0 | same |
| 1,000 | 57,992 B | 0 | same |
| **3,000** | **173,992 B** | **SIGABRT** | `thread 'bund2' has overflowed its stack` / `fatal runtime error: stack overflow, aborting` |

The depth-10 control decodes and runs the lambda, so the path is real rather
than an error path. The abort agrees with F118's table, where a debug build on
8 MiB aborts decoding at 2,048. On release the level would be about 6,000,
which was not measured here. Either way the process dies and takes the
program's stacks with it, which D37 forbids and §S8's floors do not reach:
`sql_cell` runs before `run_sqlite`'s `eval_lambda` at `:426`, not inside it.

### The row's other reasons are wrong for two of the three sites

- **"re-enters no evaluation".** `run_sqlite` calls `vm.eval_lambda`
  (`data.rs:426`), and §S8 lists it among the 21 re-entering functions
  `every_reentering_function_is_named` finds (RFC line 2188). The claim is true
  of `save_model` and `load_model` only.
- **"is `ACTS_ON_HOST`".** The list is `fs.rm`, `sleep.seconds`,
  `system.setproctitle`, `system.setproctitle.`, `password` and `save.model`
  (`crates/bund2-stdlib/src/lib.rs:412-419`). The palette skips `load.model`
  because it is registered `StackEffect::opaque(2)` (`world.rs:176`), and the
  palette filters out opaque natives (`lib.rs:424`), not because it acts on the
  host. `sqlite` itself is `eff(1, 1)` and not on the list (`data.rs:436`), so
  the palette does run it. That run only pushes a conditional, and the decode
  lives in the runner.

The conclusion that no audit sees the decode is right. None of the three reasons
given is right for all three sites.

### Why this is a blocker and not a wording fix

This is the twentieth review's B1 pressed one step further. That review named
`sql_cell` as a site whose depth "is not a value the program built but bytes it
read". The answer bounded writing, justified it by D31, and put the sqlite path
into the row's first cell. Its guard cell does not cover that path. The row now
certifies a path that aborts, which is the pattern this RFC's Status line has
recorded nineteen times: a sentence asserting a path safe, falsified by
measurement.

### What would answer it

**The disposition is the owner's.** F118 is marked FIXED on a premise that
holds for `load.model` and not for `sqlite`, and CLAUDE.md forbids adopting a
default silently. Options, none of them verified here:

1. **Bound the decode before bincode sees the bytes.** The legacy layout is
   fixed-width, so a non-recursive scan of the byte structure could, in
   principle, measure nesting and refuse. This is `[UNGROUNDED]` as a claim of
   feasibility: `WireValue` holds `Val::Json(serde_json::Value)`, whose encoding
   is not fixed-shape.
2. **Refuse BLOB decoding past a size or shape limit**, reporting instead of
   decoding. A limit weaker than depth would be heuristic.
3. **Record a stated exception to D37** for bytes a program reads from a file
   Bund did not write, in `decisions.md`, before the RFC rests on it.

Whichever is chosen, the row needs to:

- split `sqlite` from `save.model` and `load.model`;
- correct "re-enters no evaluation" and "`ACTS_ON_HOST`";
- stop citing D31 for a file D31 does not govern.

Assumption 35's codec clause (lines 2528-2531) should name the two decode sites,
which the twentieth review also asked for and which did not land. D39's third
clause should say what applies when Bund2 controls neither side.

## B2 — the generation mirror still has no implementable mechanism, no stated property and no derivation (carried from the twentieth review's B2)

Nothing in `1326f15` or `0d5b828` touches it. Re-verified today:

- **The sentence is unchanged.** RFC line 1467-1469: "a **generation cell per
  name**, mirrored from the registry `Slot`'s counter by the same `touch()` that
  bumps it". D43 repeats it (`docs/registers/decisions.md:2566-2568`).
- **`touch` still cannot do it.** It is `fn touch(&mut self)` on `impl Slot`
  (`crates/bund2-api/src/lib.rs:521`), with no `Symbol` and no `Registry`.
- **The writer set is still the same six.** Shipped `touch()` calls are at
  `:904`, `:915`, `:924`, `:935`, `:987` and `:999`. The seventh grep hit, at
  `:1320`, is `the_generation_saturates`, inside the test module that begins at
  `:1067`.
- **Nothing states or checks the property.** There is no assumption in *What
  this design assumes* and no scan beside
  `every_writer_of_the_request_cell_is_named`.

The twentieth review's argument stands in full. The request cell got assumption
33 and a scan because an enumerated writer set went stale. The generation cells
are the same kind of mirror, and a stale one costs more: an inlined `+` running
a meaning it no longer has moves `conform` under `--features jit`, which §S2
forbids. What would answer it is unchanged: correct the mechanism sentence here
and in D43, preferably by moving `touch` onto `Registry` so one function writes
both; state the property as an assumption; and derive it, or say that the
structural form removes the need.

### S2 — assumption 35's codec clause describes a ceiling no program can reach any more

Line 2528-2531: F118's arena "moved `save.model`'s ceiling from 3,400 levels to
about 39,000, and `MAX_WIRE_DEPTH` refusing to *write* past 256".

The 39,000 held only between `8252ccd` and `1326f15`. `to_binary` now runs
`depth_of` before it encodes anything (`wire.rs:647-653`), so `save.model`
reports at 257 and never gets near bincode's encode recursion. As written, the
clause reads as if `save.model` saves to 39,000 and a separate guard stops
something else at 256.

The assumption's heading adds a second problem: "nothing on that path may
recurse". The codec clause then keeps a recursion, bincode's, bounded rather
than removed. Assumption 35 should say what the codec is now: a bound checked
before encoding, a decode side with no check, and the sites that decode.

### S3 — `depth_of` counts a JSON payload as one level, and bincode does not

`children_of` treats `Payload::Json` as a leaf (`wire.rs:528`). `Val::Json`
carries a whole `serde_json::Value` (`:77`), whose derived `Serialize` recurses
through it. So the depth `to_binary` checks is a lower bound on the recursion
bincode performs whenever a JSON value sits inside a container.

It is safe today only because of a dependency's limit. Shipped code constructs
JSON in two places: `json`'s parse (`crates/bund2-stdlib/src/json.rs:84`) and
`json.path`'s result array (`:63`), which holds subtrees of a parsed value. A
parse is bounded by `serde_json`'s own recursion limit, which is a property of
the dependency that neither the RFC nor F118 states. `wire.rs:641-642` records
that a nested JSON value cannot be read back, so this concerns encoding only.
It is the shape F118 warns about, a bound that belongs to a dependency, and it
belongs beside assumption 35.

## What the RFC assumes but does not state

1. **Every BLOB decoded through `sqlite` is shallow enough for the reading
   thread.** Nothing makes it so; B1 shows a 174 KB counterexample.
2. **`MAX_WIRE_DEPTH`'s margin assumes a thread of at least 2 MiB.** F118's
   debug figures scale with the stack (512 on 2 MiB, 2,048 on 8 MiB). At
   512 levels per 2 MiB, a 1 MiB debug thread would abort near 256 itself. That
   is arithmetic on F118's table, not a measurement. §S8 already considers
   embedders who set `RUST_MIN_STACK` below 1 MiB (lines 2246-2249), so the two
   paragraphs should meet.
3. **JSON depth is bounded by `serde_json`'s parser.** `depth_of` counts a JSON
   payload as one level (S3).
4. **No world file deeper than a reader's limit survives from a build without
   the bound** (Preservation item 2).
5. Carried from the twentieth review, all still unstated:
   - every writer of a `Slot`'s generation writes that name's mirror cell;
   - nothing hands out a `&mut Slot` (`slot_mut` is private at
     `crates/bund2-api/src/lib.rs:875`, and the fields are `pub`);
   - the workbench is never a promotion source;
   - a compiled body carries a resume index per call site, and no folded or
     inlined region spans one;
   - `follow`'s bound is a Bund2 choice with no oracle behind it.
