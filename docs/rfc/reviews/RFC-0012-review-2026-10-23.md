## Verdict

**Not ready for Accepted.** Two findings are behaviour no ruling covers,
and both are in core words the RFC says it preserves:

1. **`graph.allpath`'s answer is not a function of the program.** The
   potentials' Bellman–Ford walks `algos`' edges in `HashMap` order, which
   is seeded afresh per map. Where rounding is in play, the number of passes
   it needs depends on that order. So the same program answers rows on one
   run and `negative cycle detected` on the next, in both engines. That
   holds for a cycle of weight exactly zero as well as for a negative one.
   F225 and D208 describe the faces as fixed per program; F17's fix orders
   the rows but cannot make their existence reproducible.
2. **`graph.path` answers a wrapped weight**, `found=true`, for a path whose
   `usize` sum passes 2^64. In both engines that is release-build
   behaviour. Bund2's debug build panics inside `fast_paths` instead,
   caught as an internal error. The preservation analysis states only the
   `1.0e300` case, which answers "can not calculate path", and so suggests
   that an overflowing sum is refused.

The remaining findings are bookkeeping from the last commit.

## Findings, most serious first

### 1. `graph.allpath` answers differently from run to run: the potentials' Bellman–Ford walks a `HashMap`

`algos` stores a graph as `HashMap<V, Vec<(V, W)>>`
(`algos/src/cs/graph.rs:64-66`), and `edges()` iterates that map
(`:150-154`). Johnson's potentials come from a Bellman–Ford over it
(`johnson.rs:50-53`). That Bellman–Ford makes at most `|V| − 1` passes in
the map's order, stops early when a pass changes nothing, and then refuses
if any edge still relaxes (`bellman_ford.rs:63-101`).

In exact arithmetic, `|V| − 1` passes always suffice when there is no
negative cycle, so the order cannot matter. In `f64` it can. When a cycle
lowers its nodes by rounding a few times before rounding stops it, the
relaxations needed can exceed what `|V| − 1` passes cover in one order and
not in another. The process seeds each map afresh, so the answer changes
between runs.

**A cycle of weight exactly zero, refused on some runs.** The weights sum
to exactly 0, checked in `Fraction`:

```
[ [ :S :A -100.0 ] [ :A :B 4.159226947493753 ] [ :B :C 2.819570687287843 ] [ :C :A -6.978797634781596 ] ] [ :S :A :B :C :Z ] graph! graph.allpath println
```

| engine | runs | rows answered | `GRAPH.ALLPATH: returned: negative cycle detected in graph` |
|---|---|---|---|
| oracle | 150 | 133 | 17 |
| `bund2` | 150 | 144 | 6 |

`:S` and the same graph with `graph.bellmanford` answers distances under
`bund2` (`A` at `-100.0`), as it should.

**A negative cycle, found on a few runs and missed on the rest.** The cycle
`B ↔ C` weighs −0.5:

```
[ [ :A :B -1.0e16 ] [ :B :C 1.0 ] [ :C :B -1.5 ] ] [ :A :B :C :Z ] graph! graph.allpath println
```

- **Oracle, 100 runs:** 97 answer rows and 3 answer `negative cycle
  detected`.
- **`bund2`, 100 runs:** the same, 97 and 3.

A third program, `[ [ :A :B -1.0e20 ] [ :B :C 8192.0 ] [ :C :B
-8192.001 ] ] [ :A :B :C :Z ]`, refused on 6 of 120 oracle runs and 2 of
60 `bund2` runs. Run under every order of the map's four keys, the Python
model refuses it in 1 of the 24.

Only the refusal varies, not the rows. When the relaxation settles, its
result is the greatest fixed point of a monotone map, whatever the order.
The reweighting and Dijkstra (`johnson.rs:61-93`, `dijkstra.rs:102-103`,
which walks a `Vec`) are deterministic. So a run either answers the same
rows or refuses.

Consequences:

- **"Current behaviour" (R:172-195) states F225's three faces as fixed
  per program.** It says "that rounding decides the answer three ways, all
  run in both engines". For some programs the answer is not decided by the
  program at all. The three programs it cites happen to be stable: the
  model gives each the same answer under every key order.
- **D208 was put as "preserve the rounding"**, with faces a test can pin.
  Whether "preserved" covers an answer that changes between runs of one
  program is a different question. The pattern is the one D203 was raised
  for. The presumption is that it does, since the crate and the cause are
  the same, but no ruling says so. A program that wraps `graph.allpath` in
  `?try` can take either branch on any run.
- **Motivation (R:88-92) and F17's disposition** say the three `algos`
  words are made reproducible by fixing their row order. For
  `graph.allpath` that is true of the order and not of the answer.
- **The preservation analysis (R:514-523) says "Bund2 runs the same
  `algos` revision and keeps all of this".** It keeps the variation too,
  but at a different rate: 6 in 150 against the oracle's 17 in 150 on the
  first program. Bund2's `HashMap` is a different hashbrown build from the
  oracle's. That proves only that both vary; it does not mean Bund2
  reproduces the oracle's answer on any given run.
- **No criterion covers it**, and no test could pin one run's answer.

**Repair:**
- A new defect, or a dated note on F225, recording the variation with the
  first program and its counts.
- The owner to rule whether D208 covers an answer that varies between
  runs, as D203 put F220's third face to D200. The alternative is a
  deviation, such as `graph.allpath` running its potentials in a fixed edge
  order, which would make the answer the program's.
- "Current behaviour", the F17 sentence in Motivation, and the
  preservation analysis to say it.
- A test that the three F225 programs are stable under every key order.
  The model above does this in a few lines, and would turn this review's
  "happen to be stable" into a criterion.

### 2. `graph.path` answers a wrapped weight for a path past 2^64; Bund2's debug build panics there

`graph.path` reads each weight `as usize` (`make_graph.rs:64`).
`fast_paths` then sums weights in `usize` with no check, both in
contraction (`node_contractor.rs:75`) and in the query
(`path_calculator.rs:145,153-155`). Release builds wrap.

```
:C :A [ [ :A :B 1.0e19 ] [ :B :C 1.0e19 ] ] [ :A :B :C ] graph! graph.path println
```

- **The oracle** answers `{ weight=1553255926290448500.0 :: found=true ::
  path=[ A :: B :: C :: ] }`. The path weighs 2×10^19; the answer is that
  minus 2^64.
- **`target/release/bund2`** answers the same.
- **`target/debug/bund2`**, built at `e7c7c20`, answers `internal error:
  native graph.path panicked: attempt to add with overflow (at
  …/fast_paths-1.0.0/src/node_contractor.rs:75)`. That is the dev profile
  `cargo xtask conform` measures ("measured: bund2-cli, dev profile").
  D49 catches the panic, but it reports a valid program as "a defect in
  Bund2", the shape F219 was fixed for. `cargo test` and `conform` both
  build with overflow checks on. So a unit test or a golden of this program
  would see the panic, not the answer a release build gives.

A single edge at or above 2^64 saturates to `usize::MAX` = `WEIGHT_MAX`
(`constants.rs:26`). No path through it is ever better than `WEIGHT_MAX`,
so it cannot be used: `:B :A [ [ :A :B 1.0e300 ] ] [ :A :B ] graph!
graph.path` answers `GRAPH.PATH: can not calculate path` in both engines.
That, not a refused sum, is why R:552-554's `1.0e300` program answers as it
does.

Consequences:

- **R:552-554 ("overflow") is incomplete in the direction that
  matters.** It puts `graph.path` beside the two `f64` words as a word
  that does not answer an overflowed sum. It answers one, wrapped and
  marked found.
- **"Current behaviour" (R:105-130)** lists `graph.path`'s reader
  differences: truncation, skipped self-loops and sub-1 edges, the lowest
  repeated weight, and F219. It omits saturation at `usize::MAX` and the
  wrap.
- **F219's lesson recurs here.** Bund2 matches the oracle only in release.
  In a debug build the same program becomes an internal error.

**Repair:**
- A defect for the wrap, with this program.
- The owner to rule: preserve it (release behaviour), or answer it some
  other way, as D193 §5 did for F219's crash. Either way, the debug-build
  panic is a Bund2 defect under D37. Bund2 can check the weights itself
  before calling `fast_paths`: one pass over the kept edges, summing in
  `u128`, decides whether any path could wrap.
- R:552-554 restated, and "Current behaviour" to list saturation and the
  wrap.

## Preservation analysis: what it omits

- **`graph.allpath` varies between runs** (finding 1). This is a fourth
  face of F225, and the only one that makes a reference word's answer
  depend on something other than the program.
- **`graph.path`'s `usize` arithmetic** saturates a weight at 2^64 and
  wraps a sum past it, answering `found=true` with a wrong weight
  (finding 2). Under "overflow", "a program moving between old and new
  words sees" a wrong found path in `graph.path` where the new words refuse
  or answer exactly.
- **Bund2's build profile changes one reference word's answer**
  (finding 2). Nothing in the analysis says Bund2's fidelity to
  `graph.path` holds only in release.

Nothing else found changes behaviour a program can reach. The `.` forms,
the reader, operand casing, edge order and the new words' refusals were
spot-checked and answer as S1, S2 and S4 say.

## What the RFC assumes but does not state

- **That every reference graph word is a function of its program**,
  apart from row order (finding 1). `graph.allpath` is not, wherever its
  potentials need rounding to settle.
- **That `graph.path`'s weights cannot wrap**, or that an over-large
  path is refused (finding 2).
- **That Bund2's fidelity to `fast_paths` is independent of the build
  profile** (finding 2). It holds only where overflow checks are off.
- **That D208, ruled on faces a test can pin, extends to faces that vary
  between runs** (finding 1).
- **That the three F225 programs' answers are stable.** They are, under
  every key order of the model, but the RFC does not say so or check it.
