- Date: 2026-08-30
- Reviewing: `docs/rfc/RFC-0003-syntax-ir-and-tier0.md` (Draft), second pass
- Method: every `path:line` opened against the pinned submodules in this
  session; every empirical claim re-run on `target/oracle/release/bund`;
  the brace count re-measured with a scanner that tracks string state across
  line boundaries.
- Submodule SHAs match the RFC header exactly and all six are clean: `Bund`
  `21b40b0213a7`, `bund_language_parser` `80377728f45b`, `bundcore`
  `3b0b8ba219a6`, `rust_dynamic` `ceb27c96fa10`, `rust_multistack`

- `cargo xtask cite`: 0 defects over 1376 citations, oracle crates
  byte-verified 5/5. `cargo xtask lint`: no contradictions.

The first review's four blockers are all answered, and answered well: D5 is
consumed and D3's mechanism amended in the register, F58 is carried as a
deviation with D34 behind it, the `?`-family gets a resume mechanism instead
of a hand-wave, and the 42 is now correct and measured. The draft argues
against three of its own earlier positions and wins each time. What follows is
what a second adversarial pass found anyway, ordered by cost.

Three of the previous review's citation defects were **not** corrected and are
repeated below, because a repeat defect is worth more than a new one.

## 1. Blocking

### B1 — "Neither re-enters evaluation" is false, and the OOP arms are a fifth re-entrant family

The closing note (RFC:714-720) says `execute_class` and `execute_object` "have
since been read, closing F59's scope … **Neither re-enters evaluation, so D4's
frame model is unaffected by them.**"

Both re-enter evaluation, one call deeper than the files that were read.

- `execute_object` dispatches with `vm.m`
  (`reference/rust_multistackvm/src/stdlib/bund_execute/execute_object.rs:20`),
  and `m` evaluates a LAMBDA method directly:
  `LAMBDA => { return self.lambda_eval(method_value); }`
  (`reference/rust_multistackvm/src/multistackvm_object.rs:77-78`).
- `execute_class` delegates to `stdlib_object_inline`
  (`execute_class.rs:10` → `reference/rust_multistackvm/src/stdlib/bund_object.rs:115`),
  which calls `make_bund_object` (`:125`) — a function that **recurses over the
  superclass list** (`:50`) and `lambda_eval`s each parent's `.init` (`:76`) —
  then `lambda_eval`s the object's own `.init` (`:156`), then **inspects the
  stack** (`if_object_of_class_in_stack`, `:6-25`, called at `:162`), then
  calls `vm.apply` (`:166`, `:169`, `:173`).

That last shape — evaluate, pull and inspect, evaluate again — is exactly the
shape D4 says cannot be expressed as an exit action and needs the
request/resume mechanism ("`conditional_run` … the second evaluation is not in
tail position", RFC:396-403). The OOP constructor path is a second instance of
it and the RFC asserts the opposite.

Two further consequences the note forecloses:

- `make_bund_object`'s recursion is over **class-hierarchy depth**, a third
  depth axis beside call depth and parser nesting depth. D4 excludes the parser
  explicitly and says nothing about this one.
- D23 makes `<class> !` the supported spelling for object creation, so this
  path is reached through the very word D4b re-specifies, and the corpus's
  `object_oriented_programming/` goldens exercise it.

F59's *scope* conclusion is unaffected — neither arm consults `op`, both take
it as `_op`, and I confirmed that reading. It is the frame-model sentence that
has to go, or D4 has to name the OOP path alongside the `?`-family.

### B2 — the interpreter loop exists three times, and the third one is the debugger

F52, D6 and the Preservation table all say "twice" / "the two copies are
currently identical". There is a third, at
`reference/Bund/src/stdlib/functions/debug_fun/debug_debug.rs:52-80`: the same
`format!("{}\n", …)` append (`:52`), the same `bund_parse` (`:53`), the same
`NONE` / `EXIT` / `ERROR` / `apply` arms, and the same two error strings
verbatim — `Detected an Error posted on the stack: {:?}` (`:66`) and `Attempt
to evaluate value {:?} returned error: {}` (`:78`).

It is **not** identical. It interleaves `bund_debug_print_word(&word)` (`:74`)
before each `apply`, and after each `apply` it runs an interactive readline
loop (`:81-95`) that re-enters evaluation through `bund_compile_and_eval`
(`:89`).

Three things follow:

- "the two copies are currently identical" is the sentence that makes D6 "not a
  deviation". With a third, non-identical copy, collapsing to one evaluator is
  a deviation for the debugger unless the single entry point grows the hook
  this copy open-codes.
- D6 names two callers — "`bund.eval` and the top-level script path". There are
  three, and the omitted one is the one whose behaviour differs.
- This is the strongest argument for D4 in the whole reference and the RFC does
  not make it. The debugger exists today only because someone copied the loop
  and inserted a print; a materialised frame stack is what lets RFC-0008 stop
  doing that. D4 already claims the debugger as one of its four payoffs
  (RFC:392-394) without noting that the reference already paid for it by
  duplication.

### B3 — criterion 3 names an artefact that does not exist and a mechanism it does not have

Criterion 3 (RFC:641-649) is the best-intentioned criterion in the document and
is not satisfiable as written.

- **"The 69 golden-backed programs compare against captured streams."** No
  golden captures a stream. Across all 69 files the only section headings that
  occur are `## exit` (69) and `## output` (69). A golden is an exit code and
  rendered stdout; there is no parse-time capture anywhere in `tests/golden/`.
- **"under the golden normaliser, which erases `id` and `stamp` (F14)"** — that
  normaliser is textual, substituting `<id>` and `<stamp>` into *rendered*
  output (visible in `tests/golden/probes/dt-reachable.golden`). It is not a
  comparator over `Vec<Value>`, and a value-stream comparison needs one.
- **Nothing states how the reference's stream is obtained.** The oracle CLI has
  no dump-the-parsed-stream mode (`bund --help`: `script`, `eval`, `shell`,
  `test`, `load`, `wscript`, `bus`, `cluster`, `version`), `reference/` is
  read-only so it cannot be instrumented, and linking
  `bund_language_parser` as a library is either the crates.io copy — F21, the
  thing the RFC's own header caveats — or a build of the submodule for
  something other than golden capture, which CLAUDE.md restricts.

The criterion also carries `cargo xtask parity` as declared new work, which is
right. What is missing is the sentence saying what `parity` can actually read
on the reference side. Without it the criterion cannot be scheduled, and it is
the criterion that decides whether D1's grammar claim is true.

## 3. Internal contradictions

**I1 — three sites or four.** RFC:61 — "The **three** sites that parse all
append `\n` first". RFC:275-276 — "what the reference already achieves by
appending `\n` at all **four** evaluation sites."

Neither number is the count of `bund_parse` callers, which is **five**:

| site | appends `\n`? |
|---|---|
| `reference/bundcore/src/bundcore_eval.rs:9` | yes, `:8` |
| `reference/Bund/src/stdlib/helpers/eval.rs:9` | yes, `:8` |
| `reference/Bund/src/stdlib/functions/bund/bund_interpreter.rs:30` | yes, `:29` |
| `reference/Bund/src/stdlib/functions/debug_fun/debug_debug.rs:53` | yes, `:52` — B2 |
| `reference/bund_language_parser/src/compile.rs:15` | **no** |

The fifth matters to D1's "the set of accepted programs is unchanged", which is
argued only over the appending sites. `compile.rs:14` is called only by
`compile_to_binary` (`:24`), and D11 establishes that nothing reachable from
Bund produces one — so the omission is harmless, but that is an argument the
RFC has to make rather than one it makes by not noticing.

**I2 — restates or refines.** The header (RFC:17-19) says the alternatives
section "restates §1.1's finding rather than refining it"; the alternatives
section (RFC:602-603) says "This refines §1.1 rather than contradicting it."
Having read `docs/research/05-rfc-roadmap.md:30-41`, the header is right: the
paragraph is §1.1 nearly word for word, down to "Literal `if`/`times`/`while`/
`loop` remain statically analysable; the `?`-family does not." Line 603 is the
one to fix, and `docs/research/ERRATA.md:53-57` — which deliberately declines
to supersede §1.1 — is the reason to fix it that way round.

**I3 — "`op` is threaded through every *pull* site and no *push* site"**
(RFC:462) is false inside `execute.rs`. The MAP arm's key pull
(`reference/rust_multistackvm/src/stdlib/execute.rs:56`) is a pull site that
ignores `op` — which the RFC says itself eighteen lines later ("The MAP arm's
key continues to come from the main stack", RFC:479-480) and again in the
retraction paragraph ("takes its key from the main stack (`:56`) whatever the
operand says", RFC:573-574). The accurate statement is the one F59's register
entry makes: `op` is threaded through the **receiver** pull (`:20-23`) and
nothing else. The design conclusion is unaffected; the premise as stated is
not what the file does.

## 5. Acceptance criteria

**1 — checkable, and the number is right.** I re-measured over all 69 golden
sources with a scanner that tracks string and comment state across line
boundaries: **42** carry a brace as code, **49** carry one anywhere, and the
seven-golden gap is exactly the `format`-placeholder set —
`fmt_conditional_demo`, `fmt_conditional_with_display_demo`, `pull_demo`,
`textexpression_demo`, `value_demo`, `class_display_demo`,
`class_display_demo_2`. Both this RFC's 42 and the previous review's 49 are
correct under their own measures, as the parenthetical says.

One caution the parenthetical does not cover: a naive line-based strip of
strings and comments yields **44**, not 42, because two of the seven hold their
braces inside *multi-line* string literals (`pull_demo.bund:26-30` is a
markdown table inside one). The measure — "outside string literals, with string
state tracked across lines" — belongs in the criterion, not only in the
footnote, or the next person to check it will get 44 and file a defect.

`conform --parse-only` is correctly declared as new work; no `parse_only` exists
in `xtask/src/` today. The 4/69 baseline is confirmed in
`tests/golden/CONFORMANCE.txt`, whose stale "59 goldens" comment from the
previous review is now fixed.

**2 — checkable.** Depth, wall clock and scope are all named, which answers the
previous review. One gap: the criteria preamble promises that each "names the
tool that decides it" and this one names none. It cannot be a probe — a probe

**3 — see B3.**

**4 — checkable, and correctly placed under `tests/probes/` per D21.** I ran

## 6. Preservation analysis — behaviours it does not enumerate

Beyond B1 and B2:

**P1 — `endcontext` is a shadowable name, and D2 lowers to a call on it.** D2
and D34 say lowering "emits the CONTEXT marker, the inner terms and the
`endcontext` call together". `endcontext` is a registered inline
(`reference/rust_multistackvm/src/stdlib/ctx.rs:31`) and `apply` resolves alias
→ lambda → inline (`multistackvm_apply.rs:39, 46, 59`), so a program that does
`:endcontext { … } register` today re-points the closing half of every `( … )`
in the file. D4a then makes `endcontext` context-depth-aware. Nothing says
whether Bund2's lowered close is still a call through the word table
(shadowable, and now capable of failing "Context is empty" from inside a
form the parser balanced) or a structural frame exit (not shadowable — a
deviation, and probably the one you want). One sentence settles it; today the
RFC can be read either way.

**P2 — a fourth grammar trap: a comment abutting a word is swallowed into the
name.** `/` is an `element` character (`bund.pest:36`) and `name` is atomic, so
pest applies `COMMENT` (`:54`) only where whitespace separates it. Confirmed on
the oracle:

    1 2 +// add     ->  i(+//) for stack returned: Inline +// not registered
    1 2 + // add    ->  3

This is the same family as F49/F50/F51 — grammar and intent disagreeing on a
form that parses — and D1 names three traps as "preserved and documented". It
also acquires an end-of-input case under D1's widened terminator set, which is
precisely where the RFC is most careful elsewhere.

**P3 — F49 has a twin on floats.** `float` shares the `digits` rule
(`bund.pest:23` against `:49`), so `1.0_5` parses and then fails conversion the
same way: `Error converting FLOAT to VALUE: lexical parse error: 'invalid digit
found'`. D1 and the preservation row name `1_000` only. Same disposition, but a
port that fixes the integer handler alone leaves this one behind, and F49's
register entry is the place it should be recorded.

**P4 — `stack` is `"@" ~ LETTER+`, so `@s1` is a parse error.**
(`bund.pest:27`; confirmed on the oracle, failing at 1:1, while `@s` works.)
The row "`@x` → named context | preserved exactly" hides a rule strictly
narrower than `name`'s — no digits, no `_`, no punctuation. A re-implementation
that reuses the name lexer for stack names widens the accepted language
silently, which is the same class of error D1 spends a page avoiding for the
trailing-whitespace rule.

**P5 — `execute.` on an OBJECT changes which error a program sees.** With the
`:117` guard corrected, `execute.` with an empty main stack reaches
`execute_object`, whose own guard bails `Stack is too shallow for inline
EXECUTE.OBJECT` (`bund_execute/execute_object.rs:8-10`), where today the
wrapper rejects the call earlier with `Stack is too shallow for inline
execute()`. No golden is at risk — no corpus program uses `execute.` or `!.` —
but "F53 … fixed" and "`execute`'s eight arms and their errors | preserved
exactly" are two rows that meet here. F59's "two arms, not four" answers the
`op` question, not this one.

**P6 — F53's other half.** F53's register entry records that the *base*
function's workbench guard (`execute.rs:14-18`) is already correct, which is
what tells an implementer to delete the wrapper's guard rather than rewrite the
base. D4b cites `:117` against `:22` and stops. One clause in D-space, as the
previous review also suggested.

**P7 — `execute`'s CALL arm goes through `vm.call`, not `apply`.** The dispatch
table row says so (`execute.rs:30`), and D8 puts inline caches on "call sites".
Whether the dynamic `!` is a cacheable site is left open — and by D16 it is the
site whose target is least predictable, so it is exactly where a monomorphic
cache thrashes. Not a defect; an unstated boundary on D8.

## 7. Consistency with the registers, the accepted RFCs, and ERRATA

**Clean, checked:** D5 is now consumed and D3's amendment (decisions.md, D3
"Amendment (2026-08-29)") is used faithfully, including the reversal of its
mechanism and the withdrawn `bund.eval-file` argument. D11 is discharged
explicitly and correctly. D34's resolution is reproduced accurately, including
the oracle measurement and the "top-level `( … )` is unchanged, so no golden
moves" conclusion. F59's and F60's register entries and the RFC agree. Q21 and
Q22 now exist in `open-questions.md:987-988`. D16, D21 and D27's use is
faithful; ERRATA's `!` paraphrase (69 invocations across 39 of 132 programs;
`execute` never spelled) is exact. F48's caveat is correctly scoped. `lint`
finds no contradiction across 26 preservation rows.

**7.1 — decisions-D3's Status line still contradicts its own amendment.** The
Status line reads "Eligibility falls out of the **content-hash** compiled
cache"; the amendment below it reverses that to identity keying. RFC-0003 cites
the amendment and is right to. Not this RFC's to fix, but a reader who stops at
the Status line will think the RFC contradicts a RESOLVED decision — which is
how B1 of the last review happened. Worth a status rewrite in the register.

**7.2 — D3's one still-standing consequence has no home.** The amendment
preserves the Tier-0 parse-cache observation: the reference re-parses identical
strings on every call, and keying *parses* by source text is independent of how
compiled code is keyed. RFC-0003 owns the parser and the evaluator, mentions no
parse cache, and hands nothing to RFC-0005. Take it or assign it.

**7.3 — "Blocked on: nothing" versus the RFC's own open questions.** The header
says nothing blocks. The Open questions say D8 keys on `(Symbol, generation)`
and "RFC-0002 records its generation overflow policy as unresolved" — which I
confirmed at RFC-0002:945. Either D8 is scoped so the overflow policy cannot
reach it, or the header is optimistic by one item. RFC-0002 is itself
**Proposed**, not Accepted, which D7 and D8 both build on.

**7.4 — F56's count.** Unchanged from the previous review and still worth
fixing before an implementation copies it: F56 says "45 aliases from this table
minus this one"; `create_aliases.rs:4-45` holds **42**. RFC-0003 wisely does not
repeat the number and does adopt the disposition.

## 8. Assumed but not stated

1. That `execute`'s CLASS and OBJECT arms do not evaluate. Stated, and false —
   B1.
2. That the debugger is not an evaluator — B2.
3. That a value-stream comparator exists, and that the reference's front end can
   be run at all outside the oracle binary — B3.
4. That the fifth `bund_parse` caller (`compile.rs:15`, which does not append)
   is out of scope because D11 found it unreachable from Bund. True; unsaid.
5. That the lowered `( … )` close is or is not a word-table call — P1.
6. That criterion 2's 100,000-deep test is a Rust test rather than a probe.
7. That D3's parse-cache observation belongs to some later RFC — 7.2.
8. That `execute`'s dynamic call site is out of D8's scope — P7.
9. That the seven-golden brace gap is measured with cross-line string tracking,
   without which the number is 44 — §5.1.
10. That `?try`'s handler frame catches failures raised by **native** words as
    well as by lambdas. `raise` bails from a native (`raise.rs:16`), and today
    the Rust `Err` propagates through `lambda_eval`'s `bail!` chain into
    `conditional_tryexcept.rs:32`. In a frame loop a native's failure has to
    reach the marked frame by the same route as a lambda's; D4 describes the
    unwind only for frames.
