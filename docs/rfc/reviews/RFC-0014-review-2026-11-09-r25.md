## Should fix

### S1. Comparing "by code and subject" misses an error the batch adds under a code and subject the library already holds, and `SMY-E060`'s subject is the missing uid

**Location.**
- §P4 step 6, second bullet (lines 2557-2563).
- Criterion 25's R47 case (lines 3656-3660).
- R47 as ruled (`decisions.md:16962`, "compared by code and subject").

**Problem.**
- **`SMY-E060` names the uid that is missing, not the unit that refers to it.**
  - An `Overlay` uses `StoreRead`'s default `report_dangling` (`smysl-graph/src/store/read.rs:368-379`); `Store`'s own is the same (`smysl-graph/src/store/mod.rs:1019-1030`). Each pushes `Diagnostic::new(Code::E060).with_subject(Subject::Unit(*uid))` for each node in `adjacency.dangling()`.
  - `dangling()` is the nodes that are referenced and not present (`smysl-graph/src/adjacency.rs:393-395`).
  - So the report holds one `E060` per missing uid, whatever refers to it.
  - A library holding `U` grounded on a missing `G` reports `(E060, G)`. A batch adding `V`, also grounded on `G`, leaves the merged report's `E060`s unchanged. Step 6 finds nothing added, and `V` is committed with a dangling ground.
  - Criterion 25's "a batch that itself adds a dangling ground is refused (R47)" passes only if the fixture's new ground names a uid other than the library's missing one. The criterion does not say so.
  - (No comparison of reports can catch this case, since the report does not change. It needs saying, not fixing.)
- **Code and subject also loses multiplicity where the subject is the referring unit.**
  - The closure pass pushes one `E020` per offender, each `Diagnostic::on(Code::E020, *uid)` on the *referring* unit, with a message naming the offender (`smysl-check/src/passes/closure.rs:99-106`).
  - A `b3:` token in a body is resolved against the whole store (`:69`), so a batch unit can turn a library unit's latent prose reference into an `E020` on that library unit.
  - If that library unit already had an `E020` for another offender, `(E020, L)` is already present, and the new error is not "added". The ruling chose A over B precisely to catch an error the batch causes on a unit the library already holds (lines 3147-3149).
  - `E072` (ambiguous prefix, `:91`) behaves the same way.
- **"No subject" is not a SMYSL notion.** Every `Diagnostic` has a `subject`. The whole-store case is `Subject::Store` (`smysl-core/src/diag.rs:510-523`), which is also what `Diagnostic::new` defaults to (`:540-548`). Store-subject errors carry specific messages (`smysl-check/src/passes/library.rs:190`, `:372`; `smysl-check/src/passes/time.rs:235`), so comparing their messages works.

**Suggested fix.**
- Compare multisets of `(code, subject, message)`. Each message here is deterministic and names the offender. Or state the gap in the Preservation row "The check at commit".
- Either way:
  - name `Subject::Store` as the "no subject" case;
  - say that a reference to a uid the library already lacks is not an added error;
  - make criterion 25's refused case name a uid that is not already dangling.
- Comparing by message as well goes beyond R47's stated mechanism. Record it as a dated note on D248 for the owner, not silently.

### S2. For an answer, staging's `clean` and step 6 judge different splits under different granularity profiles

**Location.**
- The staged value's `clean` (line 2431): "the staging adds no error to those the store already had, judged as step 6 judges a commit".
- §P4's cap, item 3 (lines 2486-2488).
- Step 6 (lines 2539-2563).

**Problem.**
- **The baseline differs.**
  - At staging, "the store" for an answer is the in-memory copy. SMYSL builds it as the library's store with the dossier appended: the declaration, the units, the relations, the `Thread` and the `View` (`smysl:src/main.rs:6668-6681`). `answer` takes that `&Store` (`smysl-ingest/src/answer.rs:188`). So the dossier's records are in the baseline and are subtracted.
  - At commit, the baseline is the library alone, and the dossier's units and relations are batch (step 6, "the units, relations, labels and schema declarations").
  - So any error a dossier record causes is invisible at staging and refused at commit.
- **A concrete case.**
  - The question unit's gist is the question text (`smysl-query/src/dossier/mod.rs:977-978`). `UnitCoreBuilder::build` does not bound a gist's length. The shape pass reports `E022` when the gist exceeds `l0_max` (`smysl-check/src/passes/shape.rs:45-48`), and `l0_max` is 30 in every built-in profile (`smysl-core/src/types/view.rs:112,126,140`).
  - A question of more than 30 tokens therefore stages `clean` true, then fails step 6 with `staged batch no longer checks clean` over a unit the program never edited.
  - SMYSL refuses the same answer (its `stage_or_commit` sees the whole scratch store), so refusing is faithful. Saying `clean` first is not.
- **The profile differs.**
  - `answer` stages with granularity `None`, so `check` takes `store_granularity(store)` (`smysl-check/src/lib.rs:298-302`). That reads every `View` in the store and, when they differ, takes the widest of them (`:259-290`).
  - The dossier's `View` carries `View::new`'s default profile (`smysl-query/src/dossier/mod.rs:1125-1147`; `smysl-core/src/types/view.rs:236-246`). So the scratch store's profile is the widest of the library's and the default.
  - Step 6's overlay holds no `View` (`smysl-ingest/src/stage.rs:221-224`), so it checks under the library's own profile.
  - On a library whose views are not all the default, the two checks bound `E022`, `E040` and `W041` differently.

**Suggested fix.**
- For an answer, judge `clean` as step 6 will:
  - the baseline is a check of the library alone;
  - the compared report covers the library plus the dossier's records and the answer.
- Either build the in-memory store `answer` reads without the `Thread` and `View`, since `answer` reads only member units (`smysl-ingest/src/answer.rs:97-107`), or pass the library's profile explicitly to the second `prepare_under`.
- Add a criterion 26 case: a question over 30 tokens stages `clean` false.
- The written `View` will also widen the library's profile for every later check. SMYSL's `ask --save` does the same. A Preservation sentence would record it.

### S3. The `held` flag is not said to clear on unwinding, so a panicking writer would leave every later writer in the process waiting for ever

**Location.** §P6 "Who waits" (lines 2659-2681); criterion 28's panic case (lines 3738-3743).

**Problem.**
- **Today a panic cannot strand the root.** `Serial` is a `MutexGuard`, which releases the root's mutex on unwinding (`write.rs`, `Serial` and `serialise`). §S9 relies on that: "a panic in an earlier writer leaves nothing for it to protect … the lock it left … refuses the next write with SM07" (lines 2013-2016).
- **Revision 25 keeps the guard's promise only for the mark.**
  - It says a guard clears the mark "on every exit, unwinding included" (line 2674).
  - For `held` it says only that "releasing a root takes the table's lock, clears `held`, and notifies" (line 2668), with no guard and no unwinding.
- **Two writers can panic while `held` is set.**
  - Phase 1's `panic` probe fires after the mutex and the locks are taken (line 2022).
  - Its `pause` panics after 30 s while the root is held (`probe.rs`, `at_pause`).
  - `smysl.ingest.text` can panic in the model thread (criterion 28).
- **If `held` is cleared only on a normal return,** the next writer finds no mark and `held` set, and waits on the condition variable with no timeout. Criterion 28's expected SM07 "with the lock's text" becomes a hang, and so does Phase 1's panic criterion.

**Suggested fix.**
- Say that `held` is cleared by a guard on every exit, unwinding included, as the mark is. Say it is one guard, or name the order: clear `held` and the run's mark under one acquisition of the table's lock, then notify.
- Taking the table's lock in `Drop` during unwinding is safe for the reason the RFC already gives: the lock is never held while a word runs.

## Notes

**N1. Step 6 checks with labels that step 7 then drops, and the library-alone check's options are not given.**
- `prepare_under` checks under `CheckOptions::default().with_labels(labels)`, using the batch's labels (`smysl-ingest/src/stage.rs:226`).
- The closure pass resolves those labels in *every* body in the store, library units included (`smysl-check/src/passes/closure.rs:39-44,80`).
- Step 6 runs before step 7's R46 drop. So a colliding model label `c/x` resolves to the batch's unit, and a library unit whose body says `c/x`, and grounds on the library's `c/x`, gains an `E020`. The commit is refused for a binding step 7 would have dropped.
- The library-alone check is described only as "with the same granularity" (line 2558). Bund2's `smysl.check` runs `CheckOptions::default()` with no labels (`words.rs`, `smysl.check`). If the library-alone run does the same, every label-resolved `E020` on a library unit counts as added, although no later `smysl.check` would report it.
- **Fix:** run both checks under one `CheckOptions`: the same label map, and the same granularity, `None` in both when the staged value's is NODATA. Pass `prepare_under` only the labels that survive a pre-remap collision test, or accept and state the residue.

**N2. R42's waiters are no longer woken when a mark is set.**
- Revision 24 signalled the condition variable "when a root's mutex is released or a mark is set". Revision 25 notifies only on release (line 2668) and when a guard clears (line 2674).
- So a writer queued behind an earlier write refuses only when that write releases, not "once the mark is set", as criterion 27 says (line 3710). A test that asserts the SM07 while Phase 1's `pause` still holds the earlier write would hang until the 30 s panic.
- **Fix:** notify when a mark is set, or reword criterion 27 to "SM07 when the earlier write releases, without waiting for the run".

**N3. "What a commit takes as given" still omits fields that are written as given** (review r24's N2, partly answered).
- The list does not name:
  - `Thread::id`, `Thread::schema` and `Step::role` (`smysl-core/src/types/thread.rs:375,423-430`);
  - `View::id`, `requires`, `granularity`, `intent`, `lang` and `extra` (`smysl-core/src/types/view.rs:222-232`).
- `View::granularity` has consequences. `store_granularity` takes the widest profile across views (`smysl-check/src/lib.rs:259-290`), so a hand-edited `View` with a wide profile widens every later check of the library.
- **Fix:** name these fields, or have step 7 require the `View`'s profile to be `View::new`'s default.

**N4. Criterion 25's new cases need tighter wording.**
- **The `step` case** (line 3669). When the library lacks `x.query/v1`, an answer's records begin with that `SchemaDecl` (§P4's kinds; `smysl:src/main.rs:6668-6674`). Step 4 refuses it for `ingest` too, so the SM03 may name the declaration rather than the `Thread`. Use a library that declares `x.query/v1`, or assert "naming a record `ingest` does not make".
- **The worked case** (lines 3662-3666): "`G` is then appended at a lower status". Status is hashed, so a unit appended "at a lower status" is not `G`. Say "the unit `G`, whose status is below `U`'s, is then appended".

**N5. Q60 is not in the RFC's own "Open questions" section.** That section (from line 3756) says "Each is in `docs/registers/open-questions.md`" and stops at Q59. Q60 is in the register and marked `[UNGROUNDED: Q60]` at line 2745. Add its bullet.

**N6. The RFC's R47 row and the register differ slightly.**
- The register's option A says "compared by code and subject … the library's own errors counted in one `Warning`". The RFC's row (line 3959) omits both. §P4 adds "by message when it has no subject", which the ruling does not say (S1).
- Staging's `clean` "the same" leaves open whether staging also emits the count `Warning`.
- Align the row with the register, and state the staging case.

**N7. `path` `auto`: the citation and the deviation.**
- `smysl-provider/src/config.rs:95-96` says only that `auto` is one of the values. That `auto` "means no override" is `smysl:src/main.rs:11252`, which review r24 cited.
- SMYSL's `--path auto` is accepted (`:11252-11259`), so SM03 for `opts.path` `auto` refuses where the CLI accepts.
- The reason given, that leaving `path` out means the same, is sound. A clause in the Preservation row would record it.
