## Should fix

### S1. The UNVARIED reasons for `frame.aggregate.` and `frame.join.` name one operand where the palette leaves two

**The RFC says** (S7's table): `frame.aggregate` leaves "`frame` and `by`; `frame.aggregate.` `frame`", and `frame.join` leaves "`left` and `right`; `frame.join.` `left`".

**What the source shows.**
- The audit varies `min(consumes, 1)` operands for a `.` form (`crates/bund2-stdlib/src/lib.rs:934-937`).
- A `.` form declares `consumes − 1` from the stack (`crates/bund2-stdlib/src/wb.rs:188`).
- `frame.aggregate.` therefore declares 3 (`frame by stats`, with `opts` from the workbench). The palette varies `stats` and leaves `frame` and `by` at 7. `frame.join.` declares 3 and leaves `left` and `right`.
- RFC-0016 got the same shape right: `stat.test.binom.opts` and its `.` form both leave "k and n" (`docs/rfc/RFC-0016-statistical-inference.md:636`).

**Why it matters.** The audit's comment block records what each listed native does with *every* operand it leaves at 7 (`lib.rs:803-856`). An implementer who copies this table never reads what `frame.aggregate.` does with `by` or `frame.join.` with `right`. The count, 75, is unaffected.

**Suggested fix.** "`frame.aggregate`, `frame.aggregate.`: `frame` and `by`"; "`frame.join`, `frame.join.`: `left` and `right`".

### S2. The statistics' shared code refuses with its own texts before `frame.aggregate` can check anything

**The RFC says** (S5). Each statistic is "computed by the code of a named word". "Each answer is checked: a non-finite one … is E114 naming the group and the statistic". A group with too few cells is E101 with S8's text `stats is outside <w>'s domain: group [ "a" ] has 1 value for "var"`. "`amean`'s own refusal text and `math.min`'s NaN on an empty series are never reached."

**What the source and probes show.**
- `vec.sum`'s code is `sum(word, xs)`, which refuses inside with `<WORD>: E114 the answer overflows a FLOAT: Σ xᵢ` (`biomath/vector.rs:71-74`). It never hands back a non-finite answer to check.
- `stat.var` and `stat.sd` share `checked_variance`, which refuses too few values with `at_least`'s `series is outside <w>'s domain: a series of 1 value` (`biomath/operand.rs:231-242`). It refuses overflow with `… : the variance` (`biomath/describe.rs:38-41`).
- Probed: `[ 1.0e308 1.0e308 ] stat.sd println` is `STAT.SD: E114 the answer overflows a FLOAT: the variance`. The overflow is in the *mean* (`describe.rs:28-30`), so two equal cells refuse.
- The RFC says only of `amean` and `math.min` that their own failures are never reached.

**Why it matters.** Called as written, `"sum"`, `"var"` and `"sd"` produce `Σ xᵢ`, `the variance` and `a series of 1 value`, not S8's texts. S1 says every refusal's text is in S8 (D256 S3).

**Suggested fix.** State that `frame.aggregate` checks a group's size before calling the shared code. Say also that it calls the arithmetic and not the checking wrappers, either `describe::variance` and `xs.iter().sum()` directly, or the wrappers with their refusals mapped. S8's E101 and E114 texts are then the only ones a program sees. Add a case to criterion 5 for `"var"` of two 1e308 cells (E114, `x.var of group …`).

### S3. D258 S2's i64 refusal has no column scope, so it refuses a string column `csv` reads (probed)

**The RFC says** (S6): "a field that matches the integer pattern but does not fit an i64 (`99999999999999999999`) is E101 naming the field, its row and its column **[D258 S2]**". The non-finite rule just above it is scoped "in a column inferred FLOAT"; this one is not.

**What the source and a probe show.**
- A column holding `A1` and `99999999999999999999` infers `{Str, Int}`, which `column_kind` makes a string column (`data.rs:119-125`). `cell` then never parses an i64 (`:143`).
- Probed, a file `id\nA1\n99999999999999999999\n` read with `:column "id"` prints `[ A1 ::  99999999999999999999 :: ]`.
- The RFC as written refuses that file.
- D258 S2's question was raised from a column inferring INTEGER ("`99999999999999999999` through `csv` is `could not parse … as dtype i64`"). Its ruling says only "E101 naming the field, its row and its column".

**Why it matters.** Accession numbers and barcodes mixed with alphanumeric IDs are the case the third review gave for meeting this rule. As written, the frame reader refuses a file `csv` reads and that holds no number at all. This is the same per-field/per-column question D255's note settled for non-finite fields.

**Suggested fix.** "In a column inferred INTEGER or FLOAT, a field that matches the integer pattern but does not fit an i64 is E101". Record the reading beside D258, as D255's note did, so the owner can overrule it. Add the `A1` column to criterion 6. This is an owner question about the ruling's scope, though one the D255 precedent answers.

### S4. What an empty unquoted field is, when `na` does not list `""`, is unstated

**The RFC says** (S6). "An unquoted field equal to an `na` string is NONE … Every other unquoted field is inferred as `csv` infers it". "In a one-column frame an empty line is one empty field." D258 B1 says that field is "NONE".

**What the source shows.**
- `infer("")` is `Kind::Str`: `is_bool`, `is_float` and `is_int` all refuse an empty string (`data.rs:68-115`).
- `csv` never asks. It filters empty fields out of the evidence (`read_frame`, `.filter(|f| !f.is_empty())`), and `cell` makes an empty field null whatever the kind (`:133-135`).

**Why it matters.** Take `{ na: [ "NA" ] }`, a program asking for empty fields to stay empty. The text "as `csv` infers it" gives NONE for every empty field, which makes the `""` entry in P6's default inert. A literal `infer` makes them `""` STRINGs instead, which turns a numeric column with one gap into a string column with no refusal. D258 B1's "NONE" for an empty line agrees with only the first reading.

**Suggested fix.** State one rule and mark it **[author]**. Either an empty unquoted field not in `na` is an empty STRING that takes part in inference, or it is NONE always and `""` in `na` is redundant. Add a criterion 6 case with `na` `[ "NA" ]` and an empty field.

### S5. The reader's quoting rules stop at the well-formed case

**The RFC says** (S6): "a field is quoted when its first byte is `"`, a doubled `""` inside one is a quote, and a quoted field may hold the separator and line breaks". An unterminated quote is E101.

**Cases with no rule:**
- **Bytes after a closing quote:** `"a"b,1`. Probed through `csv`, which reads it as `[ ab :: ]`. RFC 4180 gives it no meaning. Is it E101, the STRING `ab`, or the STRING `a` with `b` dropped?
- **A quote inside an unquoted field:** `a"b,1`. Probed through `csv`, which reads `[ a"b :: ]`. Is it a literal, or E101?
- **A space before an opening quote:** ` "a"`. By "first byte" it is unquoted, so it is the five-byte field ` "a"`, inferred (a STRING). That is presumably intended, but the RFC does not say it.

**Why it matters.** These are what spreadsheet exports and hand-edited files produce. Without a rule, two implementations of S6 differ, and D254's "a quoted field is text" needs to know where a quoted field ends.

**Suggested fix.** A sentence per case. E101 naming the row for the first two is the choice consistent with the unterminated-quote rule, and should be marked **[author]**. Add one case to criterion 6.

### S6. The round trip fails for a frame whose first column name begins with U+FEFF, and header fields' treatment is unstated

**The RFC says** (S6). "`frame.csv.parse` of `frame.csv.text` of a frame, with an empty options MAP, is `frame_eq` to it, factors aside". The writer quotes "any header name holding the separator, a quote or a line break". The reader removes "a leading UTF-8 byte-order mark".

**A frame that does not round-trip.**
- `columns [ "\u{FEFF}x" ]` is a legal frame: a non-empty, distinct STRING (S2).
- `frame.csv.text` writes its header unquoted, since it holds none of the three, so the text begins with `EF BB BF`.
- The reader strips them, and the column comes back as `x`.
- `file` hands the BOM through: a file of BOM, `x`, `1` has `len` 7 (probed).

**And one rule is missing.** Nothing says whether the `na` strings and inference apply to the header row. With the default `na`, a column named `NA` would read back as a NONE header name if they did, and that is E101 or a different frame.

**Why it matters.** The claim is universal, and criterion 6's frames do not include either case, so the claim is wrong where nothing tests it.

**Suggested fix.**
- Quote every header name. This is simplest, and costs nothing, since a quoted header is text either way. Failing that, also quote a name that begins with U+FEFF.
- State that header fields are never matched against `na` and never inferred.
- The header-quoting rule is the RFC's own (S9).

### S7. `frame.text`'s rules contradict each other on some STRINGs, and leave the width's unit open

**The RFC says** (S6): "No line ends in a space", and "a STRING as it is, neither truncated nor escaped". Also "A column is as wide as its widest cell or its header", and "At most 20 rows print".

**Gaps:**
- **A STRING that ends in a space, or an empty STRING, in the last column.** "As it is" puts a space at the end of the line, or leaves the separator there. "No line ends in a space" forbids both. Which wins is unstated.
- **Width's unit.** `"µg" len` is 3 (probed): Bund's lengths are bytes. A width in bytes misaligns any non-ASCII cell, while one in `char`s differs from `len`.
- **Which rows set the width:** all of them, or the 20 printed?
- **The example's `1`** must be an INTEGER, since a FLOAT 1.0 prints `1.0` and changes the width. S6's description of the frame does not say which.
- **`… 1 more rows`** for 21 rows.
- **The alignment of a column of no kind** (all NONE): numeric or not?

**Why it matters.** Criterion 8 checks only S6's example and the 20-row cut, so it passes either way. A second implementation (a TUI's, D36) would differ on each point.

**Suggested fix.**
- Trim only the padding, and keep a STRING's own trailing spaces. Or state that the line rule wins.
- Say width is in `char`s, or in bytes.
- Say the width is taken over the printed rows.
- Write "INTEGER 1" in the example.
- Say how a column of no kind aligns.
- These choices are the RFC's own (S9).

### S8. `frame.join` with an empty `by`, and a repeated name in `by`, are unstated

**The RFC says** (S5) that an empty `by` for `frame.aggregate` makes one group **[author]**. For `frame.join` it says nothing. S4 refuses a repeated name only in `frame.select` and `frame.sort`.

**Why it matters.**
- An empty `by` read literally matches every left row to every right row: a cross product, which the 10⁸ cap then bounds. That may be intended, or it may be E101. Either way it is a choice.
- `by` given as `[ "id" "id" ]` in `frame.aggregate` or `frame.join` would add a duplicate column to the answer, which the frame check then refuses with a text naming the answer, not the operand. This is the case the third review's S4 fixed for `frame.select`.

**Suggested fix.** State both, with S8 rows, and mark them **[author]**.

### S9. Several rulings are extended or narrowed without an [author] mark, and the list misses them

The RFC marks and lists its own choices well. These are of the same kind and are neither marked nor listed:

- **D252: "A word that accepts NONE takes the `na` option"** (`decisions.md`, D252's "What the rulings fix"). S3 says "The words that only move cells (S4) carry NONE and take no `na` option". `na.count`, `na.omit`, `na.fill`, `frame.join` (NONE keys) and `frame.sort` (NONE last) accept NONE without one. The scoping is sensible, and P8 names only `frame.aggregate` and `frame.matrix`, but it narrows D252's sentence. It needs a mark, or a dated note beside D252: **owner**.
- **D256 S3: "E103 is kept for a numeric column's non-number cell".** A LIST or MAP in a numeric column is such a cell; S2 makes it E101 (the third review's S5 fix). The fix is right, but it narrows the ruling.
- **D257 S9 ("each column as wide as its widest cell; numbers right-aligned, the rest left").** S6 adds that the header counts toward width, that a numeric column's header and NONEs are right-aligned, that no line ends in a space, and that a STRING is neither truncated nor escaped. All sit under the ruling's mark.
- **D257 S10 ("`sep`, one character").** S6 narrows it to "one ASCII byte other than `"`, CR and LF" under **[D257 S10]**. The narrowing is right (the third review's S8), but the ruling says "character".
- **Header quoting under [D254].** D254 rules that "every STRING cell" is quoted. The header-name rule is the RFC's own (and S6 suggests changing it).
- **"An `opts` operand is always required"** (S1). It follows RFC-0016's `.opts` words, but no ruling names it.
- **Empty text is a frame of no columns; a frame of no columns writes and prints the empty STRING** (S6).
- **`frame.join`'s kinds:** "a factor and a string column counting as one kind", and "a `by` column of no kind … agrees with any". D257 S6 rules that factor keys compare by level text, but not that a factor matches a string column.
- **The reader's BOM and terminator rules.** Q65 was answered for `csv-core`. The frame reader is the RFC's own, so "as `csv-core` removes it" is a choice to match, not a fact about the reader.

**Suggested fix.** Mark each **[author]** (D252's with a note for the owner), and add them to §Open questions' list.

## What the RFC assumes and does not state

- **That `file` is the only way in.** `file` also fetches over HTTP (`host.rs:1456-1470`), so `frame.csv.parse` can parse a fetched CSV. "No new I/O" is true, but the reach of the existing I/O is wider than "the file system".
- **That `file`'s lossy decoding is acceptable** (N2): invalid UTF-8 is replaced, not refused.
- **That `file`'s path is absolute** (N2), in the read example.
- **That `column_kind`'s merge is shared or reimplemented identically** (N6).
- **That the shared statistics' code is called below its own checks** (S2).
- **That header fields are never matched against `na` or inferred** (S6).
- **That widths in `frame.text` count something specific** (S7).
- **That a row MAP built per row by `frame.filter` and `frame.rows` is affordable.** Each costs O(ncol) allocation per row, at Tier 0, on top of the O(cells) entry check. The RFC says the work is "bounded by the frame's size", which is true but not the same as cheap.
- **That INTEGER cells above 2⁵³ may lose exactness** where a statistic or `frame.matrix` converts them (N8).
