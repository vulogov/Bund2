## Verdict

**Not ready for Accepted**, on one finding. The owner ruled on D212, and
nothing here argues against the outcome (no cache). But both reasons the
RFC gives for the ruling are false, and one of them contradicts an
accepted RFC and two resolved decisions. The registers search that should
have caught this was not run.

1. **D212's reasons, which S5 restates (R:515-520), are false.**
   - "Every algorithm here is at least linear, so a cache could at most
     halve a call" is false for `graph.neighbors`, whose work after the
     read is the node's out-list (GA:1044-1050). On a 20,000-node chain,
     one call costs about **50 ms**, and nearly all of it is reading the
     graph to answer one name.
   - "Invalidating one on a `set` belongs to the value model (RFC-0001)"
     assumes there would be something to invalidate. There is not. `set`
     builds a new payload, and RFC-0001's 2026-09-13 amendment, D5 and D35
     already give a cache keyed on the payload's `Rc` that can never go
     stale. RFC-0005's compiled cache is built that way.

Then, smaller:

2. The Title-cased form a program now has to write is wider than S2's
   example shows. Digits split as well as underscores, so a graph listed
   `[ :N1 :N2 ]` is named `"N 1"`, and `:N1` names nothing, in both
   engines. That is the reference's behaviour for `graph.paths`, and it
   now applies to all nine words that take a node operand. Neither S2 nor
   D211 states it.
3. The registers search was not brought up to date for D211 and D212
   (R:69-85). This is the recurring failure CLAUDE.md names, and it is
   how finding 1 got through.
4. Smaller points: "all nineteen" words is really nine; the operand
   refusal texts differ across a swap; a wrap claim of "nothing else";
   and one citation's line range.

## Findings, most serious first

### 1. D212's two reasons are false, and S5 states them as the design

R:515-520:

> That is the design, not a gap (**D212**, A): every algorithm here is at
> least linear, so a cache could at most halve a call, and invalidating
> one on a `set` belongs to the value model (RFC-0001).

D212 (`decisions.md:3656-3678`) gives the same two reasons as option A's
case, and opens with the premise (`:3663-3664`): "Caching that form would
need a derived value that any `set` on the MAP invalidates."

**"At least linear" is false.** `graph.neighbors` reads the graph, then
answers `net.out[u]` (GA:1044-1050). That is O(out-degree), not O(nodes +
edges). `graph.bfs`, `graph.dfs` and `graph.reachable` allocate `seen`
over all nodes, but touch only the edges they reach. Even where the
algorithm is linear, "linear" does not mean "as costly as the read". The
read Title-cases every node name and both ends of every edge through
`convert_case` and hashes each, while a traversal does integer work over
`Vec`s. Measured on macOS arm64, release, at `3e399fe`: a chain of 20,000
nodes and 19,999 edges, as a literal followed by `graph!`, then `k`
copies of `dup "N 0" swap graph.neighbors drop`:

| `k` | real, s (two runs) |
|---|---|
| 1 | 1.17, 1.17 |
| 101 | 6.15, 6.17 |

So each `graph.neighbors` call costs about **50 ms** to answer `[ N 1 ]`,
one name. A program that asks each node's neighbours in turn makes 20,000
calls, or about 1,000 s, where a cached read would cost one read plus
20,000 lookups. That is a factor that grows with the graph, not "at most
half".

**"Invalidating one on a `set`" names work that does not exist.** A MAP
is never written through. `set` builds a new payload (`lib.rs:1235-1246`,
`:2971-2974`), and nothing in the workspace mutates a payload in place.
This is the question the registers already answered for lambda bodies:

- **D5** (`decisions.md:298-310`): write-once, so "the compiled cache
  [can] skip invalidation"; "`set` applied to a LAMBDA **replaces** the
  body and returns a *new* value".
- **D35** (`decisions.md:1886-`), option 4, decided: key on the payload's
  `Rc` pointer. A `dup`'d value shares the payload and the entry, and
  nothing is materialised.
- **RFC-0001's amendment of 2026-09-13** (`RFC-0001-value.md:1800-1842`)
  adds `payload_weak` for exactly that kind of cache. An entry holds a
  `Weak` to the payload it was derived from, and stops upgrading when the
  payload goes.

A read `Net` keyed the same way is never stale, and the value model needs
no work for it. The model is done, and RFC-0005's cache already uses it.
So the second reason contradicts an accepted RFC, and D212's premise is
the default D5 explicitly departed from ("assume mutable; invalidate on
write").

**What this does and does not ask.** The outcome is the owner's ruling,
and no cache is a defensible choice: it is what the reference does, and
nothing here is a regression. But the RFC states as fact two reasons that
are not so, and one of them is the reason a future RFC would cite for not
caching. The repair is not to edit D212, which the registers forbid. It
is a dated note on D212 putting the corrected premises to the owner, and
S5 restated to give only what holds. For example: "no cache, as the
reference has none; a read costs O(nodes + edges) on every call, which
dominates `graph.neighbors` and the traversals from a node with small
reach (about 50 ms per call at 20,000 nodes); a cache would key on the
payload as RFC-0005's does (D35, RFC-0001's `payload_weak`) and is not
proposed." Whether the owner still chooses A on those facts is the
owner's call. The RFC should not say "at most halve".

### 2. The Title-cased form is wider than `My Node`

S2 (R:325-333) explains the consequence of D211 with one example:
`[ :my_node ]` lists `My Node`, which `"My Node"` finds and `:my_node`
does not. D211's text adds `:ab` and `:AB`. Neither says that
`convert_case`'s Title case splits at a letter–digit boundary
(`make_graph.rs:9-11`). So the commonest way to name generated nodes no
longer round-trips. Run today, `[ [ :N1 :N2 1.0 ] ] [ :N1 :N2 ] graph!`:

| program | oracle | `bund2` at `3e399fe` |
|---|---|---|
| `dup "nodes" get println` | `[ N1 :: N2 :: ]` | — |
| `:N1 swap graph.paths` | `GRAPH.PATHS: unknown start node: N1` | `GRAPH.PATHS: unknown start node: N1` |
| `"N 1" swap graph.paths` | rows for `N 1` and `N 2` | rows for `N 1` and `N 2` |
| `:N1 swap graph.bfs` | — | `GRAPH.BFS: unknown start node: N1` |
| `"N 1" swap graph.bfs` | — | `[ N 1 :: N 2 :: ]` |

This is the reference's behaviour, preserved, and D211 chose it for the
twelve with the reason stated. Under D192 the new words found `:N1`, so
D211 is what took that away from them. Nothing here argues for reversing
D211. But "a program names a node by its Title-cased form" is only usable
if the RFC says what that form is. S2 should say that digits and case
changes split words too (`:N1` is `N 1`, `:nodeA` is `Node A`), and that
the reliable spelling is a name read back from the graph's own answers.

### 3. The registers search stops at the tenth review

The "Registers searched by subject" bullet (R:69-85) lists its terms up
to "*Since the tenth*". `3e399fe` rewrote S2 and S5 on two new decisions
but added no search for their subjects. A search for "cache" or
"invalidat" finds D5 and D35 at once, and "payload_weak" finds RFC-0001's
amendment. Those are the entries finding 1 rests on, and none is in
"Decisions consumed" (R:65-68). This is the failure CLAUDE.md names under
"Grounding an RFC": entries resolved and directly on the RFC's subject,
missed because none declares `Blocks:` this RFC.

### 4. Smaller points

- **"All nineteen look a node operand up as given"** (R:620-621). Ten of
  the nineteen take no node operand: `graph`, `graph.`, `graph!`,
  `graph.allpath`, `graph.transitiveclosure`, `graph.toposort`,
  `graph.cycle`, `graph.components`, `graph.scc` and `graph.mst`. The
  claim holds for the other nine, so "every word with a node operand"
  would be exact.
- **The swap is one set of refusals, two sets of texts.** S2 (R:331-333)
  says `graph.paths` and `graph.bellmanford` now "refuse the same
  operands". As sets, yes. But `graph.paths` refuses a non-STRING start
  as `casting start node name returns: This Dynamic type is not string`
  (`dijkstra.rs:52-55`, F218). The twelve say `the start node must be a
  STRING, not Integer` (GA:213-218). A program that matches `?try`'s
  text sees the difference. The preservation analysis lists what a
  program moving between old and new words sees (R:613-655), and does
  not list this. `graph.path`'s end-node slips (`getpath.rs:67,71`) are
  stated under "Current behaviour", but not in that list either.
- **"The query compares the sum with `<` and nothing else"** (R:157-160,
  citing `path_calculator.rs:145-146`). The meeting sums are unchecked
  too: `curr.weight + self.get_weight_bwd(…)` (`:153,155`) and
  `curr.weight + self.get_weight_fwd(…)` (`:189,191`). So are the
  backward relaxation (`:181`) and the pruning test `curr.weight >
  best_weight` (`:133,169`). The conclusion stands, since every one of
  these is a plain `usize` add or compare. But the citation covers one
  site of five, and "nothing else" is not quite so.
- **`bellman_ford.rs:91-97`** (R:217-218) is cited for "the potentials'
  Bellman–Ford sums and tests `new_dist < *dist_v` in `f64`". Those lines
  are the cycle test after the passes. The relaxation whose rounding
  F225's three faces turn on is `:69-81` (`new_dist < *current`, `:75`).
  Both round, so both should be cited.

  half", so a program author would expect a cost the measurement does not
  show.
- **Digit and case splits in the names a program must write** (finding

- **Refusal texts across the `graph.paths` → `graph.bellmanford` swap**

the twelve words, and the reference words' lookup was already as given

## What the RFC assumes but does not state

- **That reading costs no more than the algorithm it feeds.** That is
  the premise behind "at most halve". It fails for `graph.neighbors` and
  for traversals from a node with small reach (finding 1).
- **That a MAP can change under a cache.** In Bund2 it cannot: `set`
  rebuilds, and D5 and D35 rest on that (finding 1).
- **That Title case changes only case and underscores.** It also splits
  at digits and inner capitals, so the "Title-cased form" a program must
  write is not always guessable (finding 2).
- **That the four words the test drives stand for all seven.** This is
  true, because they share `node_operand`, but the RFC does not say so
  (Acceptance criteria).
