# RFC-0002 review — first pass, 2026-08-26

Scope: `docs/rfc/RFC-0002-symbols-and-words.md` at `025baf6`, read against the
pinned submodules. Every `path:line` the RFC cites was opened in this session;
the thirteen-allocation trace and the eight-lookup count were re-walked call by
call; the lock split, the stack-layer word count and the arity disagreement
count were re-measured. Consistency checked against RFC-0000, RFC-0001,
`decisions.md`, `defects.md` and `ERRATA.md`.

Verdict: **do not accept** — and not for the three decisions it is already
blocked on. The design has a structural collision the Preservation analysis
does not see: **one slot per name cannot hold a lambda and a native at the
same time, and the reference holds both.** F26's own probe — the one the RFC
cites two sections earlier — is the proof. The preservation row claiming F26 is
"Preserved exactly" is therefore unsatisfiable by the design directly above it.

Two more of the same kind: the `Symbol`-in-`CALL` change is golden-visible in a
live corpus golden and has no preservation row, and it is not serialisable
across processes, which the world file requires.

The grounding work is unusually good. Every one of the thirteen allocation rows
is exactly right, the 119/110 lock split is exact, and "seven tables" is
literally seven. Three citation slips, all off-by-one.

---

## What this pass confirms as correct

**The thirteen-allocation table is right, row by row.** I walked `dup` through
`apply` → `i` → `i_direct` → `TS::get_inline`. Rows 1–13 land on
`apply.rs:11,16,39`, `alias.rs:34`, `apply.rs:46,59`,
`inline.rs:71,81,42,25,52`, `ts_inline.rs:33,34` — all verified, none
duplicated, none missed. The trace also holds only because `dup_one` is
registered *solely* in the stack layer: `grep '"dup_one"'` over
`rust_multistackvm` and `Bund` returns only the alias registration
(`create_aliases.rs:18`), and the word itself is at
`reference/rust_multistack/src/stdlib/dup.rs:87`. Both facts the RFC states.

**"Eight hash lookups" is right too**, though the RFC does not show the work:
`is_command` 1, `get_alias` 2, `is_lambda` 1, `is_alias` 1, `is_inline` 1,
`TS::get_inline` 2 = 8.

**The lock split is exact.** `grep -c 'BUND.lock()'` over `reference/Bund/src`
returns **119**, and partitioning those by enclosing function gives **110**
inside an `init_stdlib` and **9** elsewhere. The RFC's "119 sites. 110 of those
are `init_stdlib` registrations" is precise. `run_snippet.rs:63` takes the lock
at the top of `run_snippet_for_script` (`:61`) and drops it at `:95`, after
`bc.eval(code)` at `:85` — held for the entire run, as claimed.

**"Seven name-keyed tables" is literally seven.** `multistackvm.rs:24-30` —
`inline_fun`, `command_fun`, `methods_fun`, `lambdas`, `classes`, `vars`,
`name_mapping`. Exactly the cited range, exactly seven.

**Every resolution-order line reference is right**: `:13-15` empty name,
`:16-17` command, `:19` and `:20-27` autoadd, `:33-35` `$`, `:39-42` alias,
`:46-54` lambda, `:59` inline. So is the F26 material: the comment is at
`:30-31`, `call_internal_word.rs:7-8` strips the sigil and calls `self.i`, and
`i` resolves aliases at `inline.rs:71`.

**F31's mechanism reproduces.** `TS::register_inline` writes
`format!("{}_inline")` (`ts_inline.rs:8`), `TS::get_inline` reads with the
suffix (`:33,34`), `TS::is_inline` tests the bare name (`:25`) — and
`resolve` consults it third (`resolve.rs:21`) before bailing (`:23`). I counted
the stack layer's `register_inline` names: **31 distinct**, matching.

**"14 under-declared" is right.** `cargo xtask arity` prints "declared and
probed disagree **14**". See B5 for a defect in F18 that this exposes.

## A. Citation defects

Three, all off-by-one, all pointing one line above the line that carries the
claim. `cargo xtask cite` passes all three — see D6.

**A1. `bund_eval.rs:30`.** RFC:101-104 — "`bund.eval` re-enters the interpreter
and takes `vm` directly rather than the lock
(`reference/Bund/src/stdlib/functions/bund/bund_eval.rs:30`)." Line 30 is
`Ok(snippet) => {`. The line that shows `vm` passed through is **`:31`** —
`return helpers::eval::bund_compile_and_eval(vm, snippet);`. The claim is
correct: `bund_eval.rs` imports `BUND` at `:4` and never locks it on this path.

**A2. `ts_inline.rs:24`.** RFC:82-83 — "`TS::is_inline` tests the bare name
(`reference/rust_multistack/src/ts_inline.rs:24`)." Line 24 is the function
signature; the bare-name test is **`:25`**,
`if self.inline_fun.contains_key(&name)`. F31 carries the identical citation,
so this is inherited rather than introduced — worth correcting in both, since
`:24` is exactly the line a reader would check to confirm the defect and it
shows nothing.

**A3. `multistackvm_methods.rs:32`.** RFC:70-74 lists four `contains_key`-then-
`get` sites. Three are cited as `:32-33`, which is right in each case. The
fourth, `get_method`, is cited as `:32` alone — `contains_key` only. The `get`
is at `:33`. Inconsistent with its own three siblings in the same sentence.

## B. Claims that need a citation and lack one

**B1. "the stack layer's dead `functions` table is consulted by nothing"**
(RFC:120-121). True — `TS::functions` is declared at
`reference/rust_multistack/src/ts.rs:21` and initialised at `:33`, and grep
finds no read site — and it is F19. Neither the register entry nor a
`path:line` is given.

**B2. "31 stack-layer words"** (RFC:84). True, and it is F31's figure. No
citation.

**B3. "eight hash lookups"** (RFC:65). Correct, but the RFC tabulates the
thirteen allocations and asserts the eight. The breakdown is short enough to
show.

**B4. "Interned at parse time"** (RFC:172-175) rests on `CALL` values being
built by the parser. Nothing establishes that. `Value::call` lives at
`reference/rust_dynamic/src/create_special.rs:73`, and
`bund_language_parser` — listed in the RFC's own SHA header — is never cited
anywhere in the body. This is the load-bearing premise of the entire Symbol
design and it is the one claim with no source behind it.

**B5. "found 14 under-declared ones (F18)"** (RFC:222). The **number is
correct** — `cargo xtask arity` reports 14. But F18's prose enumerates only
**13**; `tail` (`reference/rust_multistackvm/src/stdlib/values/value_carcdr.rs:201`,
declared 1, probed 2→1) is missing from the list. The register's heading and
its list disagree, and this RFC quotes the heading. Worth a correcting entry in
`defects.md`, which is append-only.

## C. Preservation gaps

### C1. One slot cannot hold a lambda and a native. The reference holds both.

This is the blocker.

`register_lambda` inserts into `vm.lambdas`
(`reference/rust_multistackvm/src/multistackvm_lambdas.rs:7-11`) and checks
only `is_type(LAMBDA)` — nothing consults `inline_fun`. `is_lambda` reads
`vm.lambdas` and nothing else (`:29-33`). So after
`"println" { … } register`, the name `println` is **simultaneously** a lambda
in `lambdas` and a native in `inline_fun`. `apply` reaches the lambda, because
`is_lambda` is tested at `:46` before `i` at `:59`; `$println` reaches the
**native**, because `call_internal_word` goes straight to `i` and skips the
lambda check.

That is not a hypothetical. It is F26's second probe, verbatim:

> `:Hi { … } register "Hi" ptr !` prints `HI`; the same with `"$Hi"` fails
> with "not registered" — the lambda check really is skipped.

F26's probe only discriminates because the two live in **different tables**.
Under `WordEntry` as an enum in a `Vec<Slot>` indexed by `Symbol`, writing
`Lambda(BundValue)` into the slot destroys `Native { … }`. `$name` then has
nothing to fall through to, and the "surprise" the preservation table promises
to keep — "**Preserved exactly**, including the surprise" — cannot be
delivered by the structure defined forty lines above it.

The RFC's own §"Seven name-keyed tables" states the principle it then violates:
"They are distinct namespaces, and conflating them produces false resolutions."
It names commands, methods and vars as the ones that must stay distinct. It
misses that lambdas and natives are a fourth such pair, and that `$` is the
observable that proves it.

### C2. Lambdas and classes are also independent, and also collapsed

`classes` and `lambdas` are separate `HashMap`s
(`multistackvm.rs:27,28`), with independent predicates —
`is_lambda` (`multistackvm_lambdas.rs:29-33`) and `is_class`
(`multistackvm_classes.rs:29-33`). The `register` word dispatches on the
operand's type into one or the other (`stdlib/lambdas/registry.rs:17,20`), with
no collision check. So `"Foo" <lambda> register` followed by
`"Foo" <class> register` leaves both populated in the reference; `Foo`
executes the lambda and `"Foo" resolve.class` finds the class.

`WordEntry` has one arm each for `Lambda(BundValue)` and `Class(BundValue)` in
one slot. The second registration overwrites the first. No preservation row.

### C3. The `CALL` payload is golden-visible, and the RFC changes it

RFC:172 — "A `CALL` value carries a `Symbol`, not a `String`."

`Value::call` builds `data: Val::String(name)` with `dt: CALL`
(`reference/rust_dynamic/src/create_special.rs:73-80`), and that payload is
captured in the goldens through two channels:

- **`debug.display_stack`.** `tests/golden/examples/bund_dynamic_demos/compile_and_apply.golden`
  renders the output of the `compile` word as a LIST containing
  `dt: 6, q: 100.0, data: String("+")`, `String("format")` and
  `String("println")` — three CALL values, spelled out, in a passing corpus
  golden.
- **Error text.** `tests/golden/probes/execute-arm-not-executable.golden`
  renders `dt: 6, … data: String("!")` inside
  `Attempt to evaluate value Value { … } returned error: …`.

Across the suite that is **43** `dt: 6` renderings and **30** `dt: 7` (PTR,
also `Val::String` — `create_special.rs:65`), every one of the 73 with a
`String(…)` payload. RFC-0001's criterion 5 commits to reproducing that text
exactly.

So the design must keep the name recoverable from the `Symbol` *and* render it
in the reference's spelling. That may well be easy. It is not in the
Preservation analysis, and the Summary states the change without qualification.

### C4. `Symbol` is not serialisable across processes, and the world file needs it to be

D8 records that whole `Value`s are persisted as bincode BLOBs —
`for (n,l) in vm.lambdas.iter() { match l.to_binary() … }`
(`reference/Bund/src/stdlib/helpers/world/lambdas.rs:80-84`), written by
`save.lambdas` and read back by `load.lambdas`. A lambda body is a list of
CALL values. A `Symbol(u32)` is an index into a per-run interner, so the blob
means nothing on reload unless names are re-materialised at serialisation
time.

This also collides with **RFC-0001's** preservation row "Binary wire format —
**Preserved exactly**, byte-identical": a `u32` and a length-prefixed `String`
do not serialise to the same bytes. Neither RFC mentions the other on this
point. No golden catches it — `Binary([` appears in zero goldens — which is
exactly why it needs stating rather than discovering.

### C5. Registration order is part of the contract, and the reference depends on it by accident

Reading the mechanism this RFC is about turned up a defect not in the register.

`reference/rust_multistackvm/src/stdlib/lambdas/registry.rs:87-91`:

```
pub fn init_stdlib(vm: &mut VM) {
    let _ = vm.register_inline("register".to_string(), stdlib_lambda_register);
    let _ = vm.register_inline("unregister".to_string(), stdlib_lambda_unregister);
    let _ = vm.register_inline("unregister".to_string(), stdlib_class_unregister);
}
```

`register_inline` is last-write-wins (`multistackvm_inline.rs:6-9`), so line 89
is dead: `unregister` is `stdlib_class_unregister`. **The `unregister` word
unregisters a class; there is no reachable way to unregister a lambda**, even
though `stdlib_lambda_unregister` exists and is what the name says.

(A near-duplicate pair sits at `reference/rust_multistackvm/src/stdlib/classes/registry.rs:60-63`.
That file never runs — `classes/mod.rs` is empty and nothing calls
`classes::init_stdlib` — so it is dead code, not a second overwrite.)

The consequence for the RFC: its preservation row reads "Last-write-wins
registration — **Preserved exactly**, as a generation bump." A generation bump
preserves the *rule*. Reproducing the *outcome* requires replaying the same
order across the ~110 `init_stdlib` calls, because the reference's final table
is order-dependent in at least this one place. The Design says only
"Registration happens against a builder, which freezes into an immutable
`Registry`" — and a builder is precisely where a duplicate registration would
be deduped, rejected, or warned about, any of which changes the word set.

### C6. `autoadd` has three branches; the RFC lists one

`apply` tests `self.autoadd` in the CALL arm (`:19-27`), again in the CONTEXT
arm (`:72-73`, where it pushes the context value instead of switching stacks),
and again in the default arm (`:89-97`). The resolution-order list and the
preservation row ("The `autoadd` branch preceding all of it — **Preserved
exactly**") cover only the first. The CONTEXT one is a different behaviour
entirely — stack switching suppressed — and is part of the same flag's
contract.

## D. Internal inconsistencies

**D1. Seven tables do not collapse into one; four do.** The Summary says "The
seven name-keyed `HashMap` tables in `VM` collapse to one slot table indexed by
`Symbol`." The Design says the opposite two sentences later: "the namespaces
that must stay distinct — commands, methods, vars — keep separate tables."
`WordEntry`'s arms cover `inline_fun`, `lambdas`, `name_mapping` and
`classes` — four. The Summary overstates by three.

**D2. The Design settles what the Open questions say is unsettled.** Design:
"commands, methods, vars — keep separate tables." Open questions: "Whether
`methods_fun` and `vars` become slot-table discriminants or stay separate
tables is left to the implementation." One of these has to go.

**D3. The Design commits the error §"Seven name-keyed tables" warns against** —
C1 and C2.

## E. Consistency with accepted RFCs and ERRATA

**E1. RFC-0000 hands D-1 to this RFC and this RFC does not take it.**
RFC-0000:422-427 — "**D-1.** `cargo tree --no-default-features` pulls in no
`ai`, `image`, `bus`, `forecast`, `statistics`, `internaldb` or `console`
dependency … **D28 is a commitment until RFC-0002 declares the feature set.**"
RFC-0002 declares no feature set, mentions no feature, and has no criterion for
it. Its sibling D-2 was picked up by RFC-0001 ("Real with RFC-0001",
RFC-0000:432); D-1 is dropped. It may be legitimate to defer it behind D14 —
the library/core split is what decides which subsystems are features — but the
RFC has to say that rather than be silent.

**E2. ERRATA's three-tier entry is only half discharged.** It ends "RFC-0002's
slot table has to absorb all three." The RFC accounts for the VM inline table
and the stack layer's, reached by fallthrough. The third tier — the Bund CLI's
registrations, the ones that take the 156 up to 357 — is never named. They
register into the same `VM::inline_fun`, so the design does absorb them; the
errata assigns the RFC the job of saying so.

**E3. Conflicts with RFC-0001** on the wire format and on the `Debug`
rendering — C3, C4.

**E4. Criterion 4 is vacuous, and unlike RFC-0001's it is not labelled so.**
`cargo tree -p bund2-api` prints two lines: `bund2-api` and `bund2-value`.
There is no `bund2-interp` and no `bund2-jit` to find, because there is nothing
in the crate. RFC-0001's parallel criterion says outright "**This criterion is
vacuous until `bund2-value` has dependencies at all**". RFC-0000's fourth
review pass was spent correcting exactly this overclaim. It has come back.

## F. Acceptance criteria, one at a time

**1 — checkable, and the most valuable one here.** `cargo xtask conform`
against `tests/golden/CONFORMANCE.txt` (0/64). Note what it does: it is the
criterion that would catch C3, since `compile_and_apply.golden` renders three
CALL payloads as text. Worth saying so, because the RFC currently reads as if
dispatch changes could not reach a golden.

**2 — honestly blocked.** Correct handling of D14/D29.

**3 — not checkable as written, and no tool exists.** "Dispatching a word
allocates **0** times, measured the way `cargo xtask layout` measures the
value: a counting allocator across a window around one `apply` of a `CALL`."
`cargo xtask layout` measures value shapes and has no VM, no `apply`, and no
dispatch path; I ran it. "The way X measures" names a method, not a command.
Either name the command to be built, or say the harness is part of the work
item.

**4 — checkable, vacuous, unlabelled.** E4.

**5 — checkable and precise, but it has no mechanism.** `"dup_one" resolve`
succeeding is a clean regression test for F31. But **the oracle fails it** —
that *is* F31, confirmed in the register: `"dup_one" resolve` returns
`RESOLVE: function dup_one not found`. So no probe golden can be captured for
it, and D21's governing rule is "we never hand-write expected output." This is
D21's own "fourth situation" — a probe that would encode a reference bug. The
criterion needs one sentence saying the test is a hand-written Rust assertion
and why that is permitted here, or it is a criterion with no way to exist.

**6 — checkable, near-vacuous as evidence about citations.** `cargo xtask cite`
reports 0 defects across 1130 citations today, with A1, A2 and A3 all standing,
because it verifies that a file and line exist and that a quoted token is
within three lines — not that the line means what the prose says. The tool says
so itself.

**Missing criteria.**

- **Nothing checks C1.** A lambda and a native sharing a name, with `$`
  selecting the native, is the design's sharpest risk and F26 already supplies
  the exact program. It should be criterion 0.
- **Nothing checks the world-file round trip** (C4): `save.lambdas` then
  `load.lambdas` in a fresh process.
- **Nothing covers D-1's feature set** (E1).
- **Nothing checks registration order** (C5) — e.g. that `unregister` resolves
  to the class implementation, preserving the reference's accident.

## G. Assumed but not stated

1. **That `u32` cannot run out.** With `bund.eval` and D16's permanently open
   world, names arrive at run time. `Symbol` is `u32` and the RFC gives no
   reclamation policy, no bound, and no behaviour on exhaustion.
2. **That the slot vector never shrinks** — that `unalias` and `unregister`
   leave the slot `Vacant` rather than freeing the index. `Vacant` is in the
   enum, which implies it; nothing says it.
3. **That `Symbol`s from two registries never mix.** The interner is "part of
   the registry, not a global", and RFC-0007's actor model plus per-VM
   overlays means values carrying `Symbol`s may cross VM boundaries. Nothing
   states that they may not, or how a foreign `Symbol` is detected.
4. **That `generation: u32` wraparound is unreachable.** An inline cache that
   compares generations is wrong exactly once per 2^32 redefinitions of a slot.
5. **That registration order is replayed** — C5.
6. **That the parser builds `CALL` values** — B4. `bund_language_parser` is in
   the SHA header and nowhere in the body.
7. **Which arity column `StackEffect` is seeded from.** The RFC says
   "derived rather than hand-written" from `cargo xtask arity`. F18's second
   consequence is explicit that the *declared* column cannot be trusted and
   that the *probed* one must be used where they disagree — for 14 words. The
   RFC cites F18 for the count and not for the ruling.
8. **That `NativeFn` keeps the reference's shape**,
   `fn(&mut VM) -> Result<&mut VM, Error>` (`multistackvm.rs:8`). `NativeFn` is
   named as part of the stable surface and never defined; with `WordKind::Async`
   in the same enum, the signature is plainly not going to be that one for all
   three kinds.
9. **What becomes of the stack layer's own dispatch surface.** `TS::i`
   (`ts_inline.rs:42`) and `TS::functions` (`ts.rs:21`) vanish into "one slot
   table"; the RFC does not say whether `TS` keeps any word table, which
   matters because RFC-0000 keeps the stack as its own crate.
10. **That `WordKind` is observable nowhere.** Declaring `Sync`/`Blocking`/
    `Async` per word is new surface with no reference behaviour behind it —
    the same class of addition D18 flagged for gap-filled `.` forms, where
    nothing in `tests/golden/` can validate it.

## What would make this acceptable

1. Resolve C1. Either `WordEntry` is not one-slot-per-name — natives and
   lambdas coexist, as they do today — or `$` stops working and F26's row is
   rewritten as a deviation. The first is almost certainly right; either way
   the preservation table must stop claiming both.
2. Same for C2: lambdas and classes are independent namespaces in the
   reference.
3. Add preservation rows for the `CALL`/`PTR` payload (C3) and for `Symbol`
   serialisation (C4), and reconcile both with RFC-0001.
4. Record the `lambdas/registry.rs:90` overwrite as a defect, and say whether
   the registry builder replays registration order (C5).
5. Cover all three `autoadd` branches (C6).
6. Fix A1–A3 and give citations for B1–B4; take F18's probed-column ruling,
   and correct F18's short list.
7. Reconcile the Summary with the Design on how many tables collapse (D1), and
   the Design with the Open questions on methods and vars (D2).
8. Take D-1 or say explicitly that it waits on D14 (E1); name the CLI tier
   (E2); label criterion 4 vacuous (E4).
9. Give criterion 3 a command and criterion 5 a mechanism; add a criterion for
   the lambda/native coexistence and one for the world-file round trip.

D9, D14 and D29 are handled correctly. The RFC marks each where it bites and
takes no default, which is what `CLAUDE.md` asks for — the blocking is not the
problem with this draft.
