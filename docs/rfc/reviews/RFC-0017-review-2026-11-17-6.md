## Should fix

### S1. The group in S8's texts is not what `BundValue::summary` renders

**The RFC says** (RFC:671): E114 reads `the answer overflows a FLOAT: x.mean of group [ "a" ]`, "the group being `BundValue::summary` of its key LIST (`[ "a" NONE ]` for two `by` columns, `[ ]` for an empty `by`)". The E101 row above it (RFC:670) renders a group the same way: `group [ "a" ] has 1 value for "var"`.

**What the source shows.** `summarise`'s LIST arm writes `list/<n>`, then ` [`, the items joined by `, `, and `]` (`crates/bund2-value/src/lib.rs:1686-1700`). It writes a STRING in double quotes (`:1667`) and NONE as `none` (`:1654`). An empty LIST is `list/0` with no brackets (`:1688`). Probed through an E101 that summarises its operand:
- `'["a", null]' json json.to_value 0.5 0.5 math.betainc` is `MATH.BETAINC: E101 x is outside math.betainc's domain: list/2 ["a", none]`;
- `'[]' json json.to_value 0.5 0.5 math.betainc` is `… domain: list/0`.

So `summary` would make the text `x.mean of group list/1 ["a"]`, and for an empty `by` `x.mean of group list/0`. It shows at most four items, then `, …` (`:1643`, `:1696-1698`), so a group of five `by` columns is truncated. `[ ]` is not even a Bund LIST literal: `[ ] println` is `empty block: `]` needs a term before it` (probed).

**Why it matters.** Criterion 5 compares the E114 and E101 texts "with S8's text". S8 gives two answers: the example, and the function named to produce it. They disagree on every case, so the test-writer must pick one.

**Suggested fix.** Choose one and make the examples agree:
- keep `summary`, and show `group list/1 ["a"]`, `list/2 ["a", none]` and `list/0`, saying that more than four keys are shown as `, …`; or
- define the group's text directly **[author]**: each key's value as `frame.text` prints a cell (NONE as `NA`), joined by `, ` in `by` order, with the empty `by` named `all rows`. For example, `x.mean of group "a", NA`.

The second reads better in a report and is not bounded at four keys. Either way, say which. The fix is one row's text.

### S2. A column in `levels` with no non-NONE cell is both "a factor" and "of no kind"

**The RFC says.**
- A column's kind "is read from its cells that are not NONE". A column that is "all NONE, or no rows" takes no kind and is "accepted wherever a kind is asked for" **[author]** (RFC:239-248).
- A factor is "STRING, each one of the column's `levels`", and a string column is one "not in `levels`" (RFC:246-247). So membership of `levels` is part of the kind.
- `frame.factor` makes a column of no kind "a factor with no levels" (RFC:362-363). Criterion 4 asks for exactly that (RFC:775-776).

**The overlap.** After `frame.factor` on an all-NONE column, the column is in `levels` with an empty LIST. Is it then a factor or a column of no kind? The same question arises for any factor column of a zero-row frame. The answer decides several words:
- `frame.matrix`: "a … factor column is E101 naming it" (RFC:459-460) against "accepted wherever a kind is asked for". It reaches E101 either way on an all-NONE column (the NONEs, or no rows), but with different texts in S8 (RFC:674).
- `frame.aggregate` on a frame of no rows promises "a statistic's column of no kind is accepted" (RFC:400-402). A zero-row factor column is then accepted, or is `"mean" of column "g", a factor` (RFC:669).
- `frame.join`: "a `by` column of no kind … agrees with any" (RFC:451-452). An all-NONE factor key against a numeric key is then accepted, or is E101 `key "id" is … in left and … in right`.
- `frame.text`'s alignment: a column of no kind is left-aligned (RFC:593). A factor is left-aligned too, so nothing changes here.

**Why it matters.** Each case has two defensible answers, and no criterion picks one. The zero-row aggregate is in criterion 5, and a frame read with `factors` naming an all-empty column is ordinary input.

**Suggested fix.** One sentence in S2, marked **[author]**: "A column named in `levels` is a factor whatever its cells; 'no kind' is a column outside `levels` with no non-NONE cell." Then `frame.matrix` and the statistics refuse it as a factor, and `frame.join` matches it as a string key. If the opposite is wanted, say that instead. Add one case to criterion 5: a zero-row frame with a factor column under `"mean"`.

**N4. `describe.rs` already has `amean`'s arithmetic, and its module doc says otherwise.**
- `describe.rs:28-30` is `pub(crate) fn mean(xs: &[f64]) -> f64 { xs.iter().sum::<f64>() / xs.len() as f64 }`.
- `amean` is `let n = source.len() as f64; let sum: f64 = source.iter().sum(); sum / n` (`series.rs:285-287`).
- The two are the same operations in the same order, so the same bits.

So "`amean`'s sum over count" need not be factored out as a third new function. `amean` can call `describe::mean`, or the RFC can say why it keeps a duplicate. Meanwhile, §Current behaviour repeats `describe.rs`'s module doc, that its mean "may differ in the last bit" from `stat.mean.arithmetic`'s (RFC:167-169, quoting `describe.rs:5-6`). The code contradicts that. The quotation is accurate, but the RFC leans on it to say the statistics "live in three places". Say that the doc's caveat does not hold of the code, or drop the clause.

**N5. The extracted median has a precondition that can panic.**
- Over an empty slice, `s[n / 2 - 1]` underflows `usize` (`describe.rs:66-69`, the even arm at n = 0). Today `at_least(…, 1)` in the same function prevents it.
- `variance` has the same precondition, and states it: "The caller has checked n ≥ 2" (`describe.rs:32`).
- RFC:403-404 has `frame.aggregate` check sizes first, so the design upholds the precondition.
- CLAUDE.md's first preference is a structural invariant. Say in S5 that each extracted function documents its precondition, as `variance` does, or takes a non-empty guarantee.

**N6. Criterion 10 does not check the moved code's tests.** The new Preservation row says the three words' "answers, refusals and tests are unchanged" (RFC:692). Criterion 10 names only "the `csv` tests in `data.rs` pass unchanged" (RFC:852-853). Add `vector.rs`'s, `describe.rs`'s and `series.rs`'s tests to it. Those tests are the check that the move was a move.

**N7. The header-row texts are left to assembly, and one case cannot occur.**
- "A fault in the header row (a quote, the width)" (RFC:518) has no width case with `header` true: the header *is* the width.
- With `header` false, row 1 sets the width, so row 1 cannot be wrong either.
- For the quote faults, substituting `the header` for `row <n>` gives `a quote opened at the header is not closed` and `the header has "b" after a closing quote`.

Drop "the width" from RFC:518, and write the three header texts out in S8 (RFC:678) so criterion 6 compares fixed strings.

**N8. `frame.text`'s end-of-line rule covers only the last cell.** "Padding is never added at a line's end, nor the separator before an empty last cell" (RFC:596-597). Two cases are not reached:
- When the last two cells of a row are empty STRINGs, the second-last cell's padding and separator end the line.
- When an empty last cell follows a left-aligned, padded column, that column's padding now ends the line.

The intent reads as "no line ends in whitespace that is not a STRING's own". Say that, and criterion 8's "an empty last cell" case covers both.

**N9. A repeated name is unstated in four places.**
- `frame.complete`'s `names`, `frame.matrix`'s `names` (a MATRIX with a column twice), `factors`, and `descending`.
- RFC:342-346 lists `frame.select`, `frame.sort`, `frame.aggregate` and `frame.join` only.

Criterion 9 accepts either outcome. Say E101 or allowed for each.

**N10. `.dropped`'s position is unstated.** Result columns come "after the `by` columns" (RFC:426). `.dropped` is "a column" (RFC:435), placed nowhere. Criterion 5 compares whole frames by `frame_eq`, which compares `columns` in order (RFC:280-281), so the test must know. Say "last".

**N11. `frame.factor` on a factor column: say the level order.**
- "Recomputes from its cells, dropping unused ones" (RFC:361-362), with the table's "sorted" (RFC:335), reads as re-sorting by bytes. A custom order from `frame.factor.levels` is then lost.
- R keeps the order. `factor(f)` orders `unique(x)` with `order(y)` (`factor.R:25-27`), and a factor sorts "in the order of their levels" (`sort.Rd:64-65`). So R drops unused levels and keeps the rest in place.

Either reading is fine, but write which one, and if it is re-sorting, add it to §Differences from R.

**N12. A difference from R the section could list, and two uncited claims.**
- R's `read.table` skips blank lines by default: `blank.lines.skip = TRUE` (`readtable.R:71`), "blank lines in the input are ignored" (`read.table.Rd:169-170`). D258 B1 reads them, and refuses a stray one in a wider frame. D258 does not rest on R, but a reader coming from R will meet it first. One bullet in §Differences from R would say so.
- "As polars reads it" (RFC:967) is uncited. `data.rs`'s module doc (`:19-20`, "An empty field is null") is the nearest grounding in this repository.
- "Which RFC-0016 rejected for the same reason" (RFC:209-211) is uncited. It is RFC-0016's alternative at `RFC-0016-statistical-inference.md:670-672`.

**N13. Three unmarked choices, and one ordering left open.**
- `frame.take`'s "repeats allowed" carries **[D257 B3]** (RFC:330), but B3 rules only 1-based counting (`decisions.md:17524`).
- `frame.head` takes `min(n, nrow)` (RFC:331).
- "A frame with no columns has 0 rows" (RFC:325).

Each is the obvious choice, but none is marked **[author]** or listed. Separately, text that is only a UTF-8 byte-order mark is left open. If "a leading … mark is removed" (RFC:514-515) runs before "Empty text is a frame of no columns and no rows" (RFC:516-517), the text is a zero-column frame. Otherwise it is one record. Say the BOM goes first.

## What the RFC assumes and does not state

- **That `file`'s path is absolute.** RFC:476 still writes `"path" file` (carried from the fourth and fifth reviews).
- **That `file` reaches only the file system.** It also fetches over HTTP (`host.rs:1455-1456`, the `Target::Http` arm). "No new I/O" holds, but `frame.csv.parse` can parse fetched text (carried).
- **That `frame.filter` reaches the bridge.** `dynamics.rs`'s `call` is `pub(super)` (`dynamics.rs:53`), private to `biomath`. A `frame` module needs a visibility change, or calls the bridge directly. Neither is named (carried).
- **That a column's membership in `levels` decides whether it is a factor when no cell says a kind** (S2).
- **The order of refusals across checks.** Two orders are unstated:
  - the frame check against other operand checks (carried);
  - inside `frame.csv.parse`, tokenising faults (quotes, width) against inference faults (NaN, beyond i64). For a text with a ragged row 5 and a `NaN` at row 3, which refusal is reported depends on whether the reader tokenises everything before inferring.

  Single-fault criteria do not see either order.
- **That the extracted functions' preconditions hold at every caller** (N5).
- **That `frame.text` of a frame with columns and no rows prints its header row alone.** This follows from the rules but is not said.
- **That a row MAP per row in `frame.filter` and `frame.rows` is affordable at Tier 0** (carried; RFC:368-369 says only "bounded").
