## Blocking

### B1 — The document says D164 and D165 are open; the register and the document's last paragraph say they were ruled

Four places: the status line ("Two questions the review raised are
decisions, **D164 and D165, open**"), the Depends line's note ("D164 and
D165 are open"), the Supersedes line ("departed from by §C5 and open as
D164"), and the amendment's "Not done" paragraph ("D164 and D165 are open,
and … acceptance … waits on them too"). The register: D164 **RESOLVED**, C;
D165 **RESOLVED**, B; both 2026-10-14. The RFC's own final paragraph,
"Rulings, later the same day", says the same, as does §C5's second note and
the added `WordKind::Async` row.

This is the shape the status paragraph itself names as the thing to carry
away — "A status nothing contradicts is read as authoritative; see F109's
addendum and F146" — and it is in the status line. A reader who stops at the
header is told acceptance is blocked on two open decisions. The fix is four
dated notes, or one sentence in the status line that supersedes the others.

Two rows go with it. The original Preservation rows "`WordKind::Blocking` —
**Defined here for the first time**" and "`WordKind::Sync` — now with a
stated meaning" are withdrawn by D164's C, which §C5's note says in terms;
the note after the table mentions the `Sync` row and not the `Blocking` one.
The open-questions bullet "**What `Async` means** … §C5 declines to invent
it" has no note at all. The register's D164 reads "Blocks: RFC-0007's
acceptance" and is resolved; the document should not read as if it were not.

### B2 — Two figures taken from the third review's text and written as measurements are false

The amendment corrected the third review's S1 figures and its assumption 7
by restating them. Two of them the review had wrong, and the restatement
did not measure:

- **"`HERMETIC.txt` lists 96 programs today"** (criterion 2's note). It
  lists 58. The file is 96 lines: 37 are comments, one is blank. It has not
  changed since 2026-10-01, so the sentence it "corrects" — "`HERMETIC.txt`
  goes 57 → 58, exactly one program" — was still true, and the note turned
  it false. The conformance denominator grew 118 → 146 through probes, not
  corpus programs; the two numbers were conflated.
- **"The host's ceiling of 1024 VMs is 8.4 GiB of reserved address space
  under `jit` … stated here and not changed."** It is 16.25 GiB under `jit`
  and 8.25 GiB without; neither is 8.4. §C8's own arithmetic two paragraphs
  earlier is right ("about a gigabyte" at 64 VMs is 64 × 16.25 MiB), so the
  document now contradicts itself by a factor of two on the one number it
  gives for the backstop. `Host::with_limit`'s doc (`host.rs:233-239`)
  gives the backstop's reason in word-table bytes and says nothing about
  address space, so nothing in the code is wrong; the claim is only here.

This document's history is two numbers "written as though they had been
measured" in the first draft, and the third review's verdict that the code
held and the text did not. These two are the same pattern at a smaller
scale, and they are in the part of the document that exists to say the
review's findings were checked.

## Significant

### S1 — The dropped-handle row cites a `Drop` that does not exist, and the slot comes back before the word table goes

The row: "a `Vm<T>` dropped before it finishes — **Detaches the thread**,
which runs to its end and returns its host slot through the same `Drop`
guard (`crates/bund2-async/src/host.rs`, `Vm`'s `Drop`)." `Vm<T>` has no
`Drop`; the only impl in the file is `Finish<T>`'s (`host.rs:99-121`), which
lives on the VM's thread and fires however the closure ends. The behaviour
the row describes is right; the mechanism named is not.

While there: `Host::spawn`'s thread stores the answer, then `drop(finish)`
— which gives the slot back and wakes the waiter — and only then, at the
scope's end, drops `rt` (`host.rs:354-362`). So the slot is free while the
VM's word table is still allocated, and `Host::live()` undercounts by the
VMs that are tearing down. A waiter woken by that `Drop` can spawn a 65th
VM into a host whose 64th table has not yet been freed. The doc comment
says the opposite — "A VM that has finished has given its word table back,
so the slot is free" (`host.rs:290-294`). It is a window of microseconds and
no program can see it, but D85's bound is on live word tables and criterion
14 says the cap is "on VMs that exist at once". One line fixes it:
`drop(rt)` before `drop(finish)`. Otherwise the comment and the row should
say the slot is released first.

### S2 — The reporter half of the third review's assumption 2 is still unaddressed

The amendment: "2, a host VM's options: D165." D165 covers `HostOptions`,
which is `noio`, `nocolor` and `noeval` (`crates/bund2-stdlib/src/host.rs:42-52`)
and nothing about a reporter. The assumption had two halves, and the other —
"Tens of VMs reporting through tens of `Box<dyn Reporter>` to one stderr is
unaddressed (first review, assumption 8)" — is still true: every spawned VM
is built with the default reporter, so a diagnostic from any of them goes
to the process's stderr with nothing saying which VM. An embedder can
install its own on `rt.interp` inside the closure, since the closure gets
`&mut Runtime`; the RFC does not say so, and the Preservation table has no
row for where a host VM's diagnostics go. That row is the `Reporter` seam's
whole reason for existing, per CLAUDE.md.

## Preservation analysis — rows the table still lacks

Twenty-eight rows now, and the third review's twelve are all present. What
the design touches and no row names:

1. **Where a host VM's diagnostics go** (S2): the default reporter, stderr,
   unlabelled; and that an embedder installs its own inside the closure.
2. **The slot is released before the word table is freed** (S1).
3. **A `Host` dropped with live VMs.** `Host` has no `Drop`; its VMs run on
   through `Vm<T>`'s handles, which the row covers, but a host dropped while
   holding none of its handles is not said to do anything, and it does
   nothing — the threads finish on their own and decrement a counter nobody
   reads.
4. **A received value's `stack` tag** is the receiving push's. The amendment
   says "stated here" under assumption 9; it is a behaviour, and the table
   is where a reader looks for it.
5. **`--nocolor` reaches spawned VMs** with D165, since it is a `HostOptions`
   field. True and unsaid; one word in the D165 row.

## What the RFC assumes but does not state

1. **`Host::live()` is exact.** It is not during teardown (S1).
2. **A host VM's diagnostics have somewhere to go** (S2).
3. **`HostOptions` is the whole of what distinguishes one VM from another.**
   It is `noio`, `nocolor`, `noeval` and the threshold; the reporter, the
   stack size and the stack region are the host's and not the embedder's.
4. **Polling a resolved `Vm<T>` again** returns `Err("a VM thread ended by
   panicking")` (`host.rs:198-205`: the answer is gone and `done` is set).
   An executor that does this is breaking the `Future` contract, so the
   case is theirs; the message is still wrong for it.
5. **Two `Host`s in one process share `PIPES`** — implied by "process-global"
   and by every test using unique channel names; never stated as a property
   an embedder with two hosts will meet.
6. **The oracle's `--noio` run** holds for all eight; the note says so and
   the first review and this one together have re-run five of them.
7. **Criterion 11's two VMs never coexist.** The criterion is about the map,
   not the overlap, and says so; the overlap is criterion 12's and 13's.
