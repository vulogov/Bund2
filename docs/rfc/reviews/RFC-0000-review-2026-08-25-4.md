## Citation defects

### R4-1 — F23 cites the wrong function, the wrong word, and the wrong registration

F23's body: "`stdlib_stacks_right_inline` ends by calling `stdlib_stack_left`
(`reference/rust_multistack/src/stdlib/rotate.rs:88`), so the word registered as
`stacks_right` (`:94`) performs the left rotation."

Line 88 is not in `stdlib_stacks_right_inline`. Reading `rotate.rs`:

- `stdlib_stacks_right_inline` is `:17-19`. It calls `stdlib_stacks_right`
  (`:13-15`), which calls `ts.right()`. Correct.
- `stdlib_stack_right_inline` — different function, singular `stack` — is
  `:83-89`. It pulls a name and calls **`stdlib_stack_left`** at `:88`. That is
  the bug.
- `:94` registers `stacks_right` inline. The buggy function is registered at
  **`:102`**, as `rotate_stack_right`.

F23's *title* — "`rotate_stack_right` rotates left" — is the correct finding.
Every sentence beneath it is about a different word.

Corrected statement: `stdlib_stack_right_inline` (`reference/rust_multistack/src/stdlib/rotate.rs:83-89`)
pulls a stack name and calls `stdlib_stack_left` (`:88`) instead of
`stdlib_stack_right` (`:64`), so the inline registration of `rotate_stack_right`
(`:102`) rotates the named stack left. The function-table registration at `:101`
binds the correct `stdlib_stack_right`, and is unreachable (F19).

### R4-2 — F23's conclusion is false, and contradicts RFC-0000 in the same commit

Following from R4-1: "the `stacks_left` / `stacks_right` pair is broken in both
directions at once … Between them the language has no working stack rotation by
name."

`stacks_right` is not broken. Verified against the oracle:

    $ bund eval --eval '1 2 ->'              → 2
    $ bund eval --eval '1 2 stacks_right'    → 2
    $ bund eval --eval '1 2 <-'              → Inline stacks_left not registered

Only `stacks_left` fails. This is precisely what RFC-0000:307-308 already
states — "Confirmed against the oracle: `1 2 <-` fails …, while `stacks_right`,
which is registered inline, works" — a paragraph this commit did not touch. The
repository now asserts both that `stacks_right` works and that it rotates the
wrong way.

The striking-symmetry paragraph should be deleted rather than repaired. The
real relationship between F22 and F23 is weaker and worth stating plainly: two
neighbouring rotation words are each defective for unrelated reasons.

### R4-3 — F23's evidence for "no golden covers it" is about the wrong words

"No corpus program uses either (`->`, `<-`, `stacks_right`, `stacks_left` are
all in the never-used set)." That set belongs to the word F23 got wrong.

The conclusion survives on different evidence, which I checked: `rotate_stack_right`,
`rotate_stack_left`, `-->` and `<--` have zero occurrences across
`reference/Bund/examples`. No golden constrains the direction. Cite that instead.

### R4-4 — F25 names a divergence that does not exist and misses the one that does

"`apply_in` has **no `$`-prefix arm** and inverts the `autoadd` test relative to
`apply`."

The first half is true. The second is not. Both functions test `if self.autoadd`
in the same position and the same polarity, in all three arms:

| arm | `apply` | `apply_in` |
|---|---|---|
| `CALL` | `:19` `if self.autoadd` | `:15` `if self.autoadd` |
| `CONTEXT` | `:72` | `:45` |
| `_` | `:89` | `:62` |

Nothing is inverted. The real `CALL`-arm divergence is larger than an inversion:
`apply` pulls the top value and appends the name to it, bailing "Autoadd found
no working data on stack" when the stack is empty (`:20-27`); `apply_in` does a
bare `self.stack.push_to_stack(name, value)` (`:16`) — no pull, no append, no
error path. Under `autoadd` the two produce different stacks from the same
input. F25 asserts a difference that isn't there and omits the one that is.

### R4-5 — F25's `execute.rs` citation is off by two

`defects.md:475` cites `reference/rust_multistackvm/src/stdlib/execute.rs:32`
for "`!` goes through `vm.call`". Line 32 is `_ => {`. `return vm.call(fun_name.clone())`
is at `:30`.

RFC-0000:138 cites the same fact as `execute.rs:26-33`, a range that does
contain `:30` — the RFC is fine, the register entry is not. `cargo xtask cite`
passes the wrong one and raises an advisory on the right one; see R4-11(c).

### R4-6 — F25's oracle probe cannot show what F25 says it shows

"Verified against the oracle with `1 2 "$drop" ptr !`, which takes the `$` arm —
the arm `apply_in` does not have."

    $ bund eval --eval '1 2 "$drop" ptr !'   → 1
    $ bund eval --eval '1 2 "drop" ptr !'    → 1

Identical. `drop` has no alias and is a registered inline, so the `$` arm and
the alias-then-inline arm converge on the same call. The program distinguishes
nothing, and a probe that produces the same output down both paths is not
evidence about which path ran.

A discriminating pair exists — and it undercuts F25's framing rather than
supporting it. See R4-7.

### R4-7 — the `$` arm does not skip alias resolution, and this diff builds on the assumption that it does

`apply`'s comment at `multistackvm_apply.rs:29-32` reads "If function name
starts with '$' we are forcing to call internal function **without lambda check
or alias resolution**". Only the first half is true.

`call_internal_word` (`multistackvm_call_internal_word.rs:6-9`) strips the `$`
and calls `self.i(…)`. `VM::i` (`multistackvm_inline.rs:70-79`) tests
`is_alias` and resolves before dispatching. The `$` arm re-enters the alias
table it is documented to bypass.

Both halves verified on the oracle:

    $ bund eval --eval '1 "dup" ptr ! .s'    → 2 values   (alias dup → dup_one)
    $ bund eval --eval '1 "$dup" ptr ! .s'   → 2 values   (same alias, same result)

    $ bund eval --eval ':Hi { "HI" println } register "Hi" ptr !'    → HI
    $ bund eval --eval ':Hi { "HI" println } register "$Hi" ptr !'   → error

`$dup` duplicates: it went through `dup` → `dup_one` (`create_aliases.rs:18`),
which is alias resolution. `$Hi` fails where `Hi` runs the lambda: the lambda
check really is skipped. `$` skips one of the two things the comment claims.

Three consequences:

1. **This is a reference defect with no F-number.** It belongs in `defects.md`
   alongside F6, which already records the double alias resolution — the same
   `i()` behaviour, seen from the other side.
2. **It was already reported and never actioned.** Review pass 1 §4.3 says
   exactly this. RFC-0000:103 still presents the chain as "a `$`-prefixed name
   forcing an internal word (`:33`), then alias (`:39`)", and
   `open-questions.md:62` repeats it. Neither is false as written; both leave a
   reader to conclude that `$` precedes and therefore bypasses aliasing, which
   is what RFC-0002 would then specify.
3. **F25 now rests on it.** F25 treats "takes the `$` arm" as a distinguishing
   property of the live path. The only property that distinguishes it is the
   lambda skip.

### R4-8 — research contradiction with no ERRATA entry

`docs/research/00-jit-feasibility.md:119` — "leading `$` → `call_internal_word`,
bypassing lambdas and aliases" — and `:556` — "**`$name`.** Bypasses lambda and
alias resolution. In IR this is a distinct opcode" — are falsified by R4-7. The
second one proposes an IR opcode built on the false half.

CLAUDE.md: "When an RFC contradicts one, record it in `docs/research/ERRATA.md`."
`ERRATA.md` has six entries and none on this. Note that the same document's
`:675` lists "Second alias resolution in `i()`" as a known cost — the document
contains the mechanism that refutes its own claim, two hundred lines apart.

## The `cargo xtask cite` change

The `agreed` fix itself is correct: the counter now increments only inside
`if vend.is_dir() && sub.is_dir()` after `first_difference` returns `None`
(`xtask/src/cite/mod.rs:309-311`), so a skipped crate no longer counts as
verified. The comment at `:251-253` is accurate. Two problems remain.

### R4-9 — the new message is wrong in exactly the case the check exists for

`agreed < checked` has two causes. The byte tier was skipped, or it **ran and
found a difference** — `:293-307` pushes a hard finding and `continue`s without
incrementing. The new output asserts only the first:

> The remainder were NOT byte-compared: the vendored crate source is absent.
> That is the normal case in CI …

On a real source divergence — a submodule pointing at code the oracle does not
run, the failure this whole tier was built to catch — the tool prints a sentence
saying the opposite of what happened, directly above the hard finding that says
what did. The previous wording was vague; this one is false. Branch the message
on whether a hard provenance finding was recorded, or count skips separately
from disagreements and report both.

This is the same shape as the bug being fixed: a summary line that states a
guarantee the code beneath it did not establish.

### R4-10 — "byte-verified" is narrower than it reads, and the run already shows it

`first_difference` (`:328-359`) walks only files with extension `rs` under
`src/`. Manifests, build scripts, grammars and generated assets are invisible.

This is visible in the current output, which prints `oracle crates byte-verified
5/5` and, in the same run, an advisory that `reference/rust_dynamic` declares
0.50.0 while the oracle links 0.49.0. Both are true only because that version
bump touched `Cargo.toml` — a file the byte tier does not read. "Byte-verified"
here means "every `src/**/*.rs` is identical", which is a real and useful
guarantee, and is not what RFC-0000:235 claims: "The submodule sources and the
linked crate sources are byte-identical today."

Latent rather than live today: no submodule has a non-`.rs` file under `src/`
(checked, all five). It stops being latent the first time
`bund_language_parser` grows a `.pest` grammar under `src/` — the definition of
Bund syntax, silently outside the comparison.

Second, smaller: `dirs_registry()` (`:317-325`) returns the *first* directory
under `~/.cargo/registry/src`. One exists today
(`index.crates.io-1949cf8c6b5b557f`). With two, the byte tier can silently
select the wrong one, find no vendored source, and disable itself — printing the
new "that is the normal case in CI" message on a developer machine where the
oracle was built minutes earlier.

## Acceptance criteria

### R4-11 — criterion 6 is credited with a guarantee it does not state

Criterion 5's new closing sentence: "Criterion 6's provenance check is what
covers the binary."

(a) Criterion 6's text says only that `cargo xtask cite` "reports zero defects:
every `reference/...:N` citation … names a file that exists and a line that
exists." No provenance guarantee appears in it. Criterion 5 points at a promise
criterion 6 does not make.

(b) The same commit establishes, correctly, that the byte tier does not run in
CI. So in CI the "provenance check that covers the binary" is a comparison of
two version strings — which, per the tool's own advisory text, is explicitly
*not* what decides whether citations resolve (`:278-282`: "Gating CI on the
version alone would block on a benign condition"). The paragraph hands the
binary's guarantee to a check the paragraph itself says does not run there.

Either criterion 6 states the provenance property and its CI-versus-local
asymmetry, or criterion 5 stops pointing at it.

(c) Separately, criterion 6 is a resolvability gate, not a correctness gate. The
current run reports `DEFECTS 0` with F25's `execute.rs:32` wrong (R4-5) and 19
advisories, one of which is a false positive on a correct RFC citation
(`RFC-0000:138` → `execute.rs:26`, where `vm.call` is four lines away and the
window is three). The RFC's prose says this — "It cannot check that a line means
what the prose says; that still needs a reader" — the criterion's own wording
does not.

### R4-12 — arithmetic left stale on the line this diff edited

RFC-0000:256: "`docs/registers/defects.md` — **25 entries**. The roadmap's §5
listed eleven; seven more were found by running the oracle rather than reading
it." 11 + 7 = 18. The sentence was already stale at 22 and the edit updated the
count on the same line without touching it.

## Preservation analysis

### R4-16 — two behavioural findings added by this commit are not enumerated

The section carries F22 (`RFC-0000:302-310`). It does not carry either
behavioural finding this commit added.

**F23 as corrected.** `rotate_stack_right` dispatches to a left rotation.
RFC-0002 ports a rotation word and must choose reproduce-or-fix. No golden
constrains the choice — `rotate_stack_*`, `-->`, `<--`: zero corpus occurrences
(R4-3) — which makes it exactly the kind of decision that gets taken silently
during implementation. That is what this section exists to prevent.

**F24's `push`.** `reference/rust_multistack/src/stdlib/push.rs:44` registers
`push` in the function table; `reference/Bund/src/stdlib/functions/values/push.rs:74`
registers a *different* `push` inline, and the inline is what dispatch reaches.
F24 calls this "a third instance of the F1/F20 pattern". F1 and F20 are
shadowing defects with preservation consequences; this one is in `defects.md`
and absent from the enumeration.

F25 needs no entry — a dead cluster changes no behaviour. Its consequence for
RFC-0002 is already stated in the entry.

## Assumed but not stated

**R4-17 — that a clean `git status` in a submodule means the citation targets
are unchanged.** It means no *uncommitted working-tree* edit. A moved submodule
pointer — `git submodule update --remote`, a rebase, a fresh clone at a
different pin — leaves `git status` clean inside the submodule and invalidates
every `path:line` in the repository. The byte tier would catch it locally; in
CI, where that tier does not run, nothing does. Criterion 5's new text is
careful about which binary it guards and silent about which kind of change it
detects.

**R4-18 — that "the oracle" is one object.** `check_oracle_provenance` reads
`reference/Bund/Cargo.lock` (`mod.rs:225`) to learn the resolved versions. The
binary at `target/oracle/release/bund` was built at some earlier moment against
whatever the lockfile then said. Nothing connects them: the check verifies what
the lockfile *would* resolve, not what the binary *did* link. The binary already
volunteers the answer — its own error output names
`…/rust_multistack-0.33.0/…`, `…/rust_multistackvm-0.38.0/…`,
`bundcore-0.7.0` — and the check does not read it.

**R4-19 — that unreachable means out of scope.** F22 and F24 identify four words
dispatch cannot reach. Nothing in the RFC or the registers says whether Bund2
implements them, and the coverage denominator depends on the answer. The owner
has now ruled; see below.

## Owner ruling received during this review

> "Those are good words shall not be dead: dup_in, from_workbench, push_to,
> stacks_left"

This is a deliberate deviation from the oracle — Bund2 would expose four words
the reference cannot dispatch — and per CLAUDE.md it belongs in
`docs/registers/decisions.md` before it reaches an RFC or a work item, with F22
and F24 dispositioned against it. Three facts the decision should record, all
checked:

- **Conformance is unaffected.** No corpus program uses `dup_in`,
  `from_workbench`, `push_to` or `stacks_left`, and neither `←` nor `<-` appears
  in any example. The `conform` denominator does not move.
- **Coverage grows by four**, 497 → 501, and the words arrive untested. Under
  the health metric that is a fall in the completeness number, correctly.
- **Reviving `stacks_left` repairs `<-` and `←`** (`create_aliases.rs:22,23`) as
  a side effect — F22's "two documented words go with it" becomes "two
  documented words come back". `→`/`->` already work (R4-2); the pair ends up
  symmetric for the first time.

The three remaining words have no aliases, so reviving them adds names and
nothing else.
