# Review — RFC-0009: Classes, objects, and method dispatch

- Date: 2026-08-31
- Reviewing: `docs/rfc/RFC-0009-oop.md` (Draft), first pass
- Method: every `path:line` in the RFC opened against the pinned submodules in
  this session; the D14 claim re-checked against the generated
  `docs/core-words.md`; the golden claims re-measured with `cargo xtask
  conform` and by counting `tests/golden/`; every named tool invoked to see
  whether it exists.
- Submodule SHAs match the RFC header exactly and all six are clean: `Bund`
  `21b40b0213a7`, `bund_language_parser` `80377728f45b`, `bundcore`
  `3b0b8ba219a6`, `rust_dynamic` `ceb27c96fa10`, `rust_multistack`
  `9a97675ee5d8`, `rust_multistackvm` `4605832678d4`.
- `cargo xtask cite`: 0 defects over 1410 citations, oracle crates byte-verified
  5/5, 62 advisories (all pre-existing, none in this RFC). `cargo xtask lint`:
  no contradictions over 29 preservation rows. `cargo xtask conform`: 21/69,
  +2 approved deviations.

Most of the citation work holds up. The reading of `m()`, of `#`, of the
slot/method name asymmetry, and of the `oop/` line accounting is accurate, and
S6's correction of the earlier draft is right — I re-derived it from
`object_execute.rs:15-38` and `execute_object.rs:11-20` independently and agree
`#` is `unwrap`-then-apply and not dispatch.

What this pass concentrates on is the other direction. The RFC's central
subject — what `!` does to a CLASS — is described as behaviour to preserve, and
it is behaviour the registers already record as **broken and slated for a
fix**. Everything downstream of that (the preservation row, the F66 plan, the
absent decision list) inherits the error. Ordered by cost.

## 1. Blocking

### B1 — `!` on a CLASS does not construct; it always fails, and F16/D23/D25 already say so

§5 states:

> `!` on a `CLASS` pushes the value and calls `stdlib_object_inline`
> (`execute_class.rs:8-10`) — that is, executing a class **constructs** an
> instance.

and the Preservation table carries the row

> | `!` on a CLASS constructs; on an OBJECT dispatches a named method | preserved exactly (S6) |

The first half of the citation is right: `execute_class.rs:9-10` pushes the
value and delegates. The conclusion is wrong. `stdlib_object_inline` pulls its
operand and immediately `cast_string()`s it to obtain a class **name**
(`reference/rust_multistackvm/src/stdlib/bund_object.rs:119-122`), then looks
that name up with `vm.is_class` (`:123`). A CLASS value is a map, so the cast
fails and the arm errors with `OBJECT returns error: This Dynamic type is not
string` — every time, for the only type that routes to it.

This is not a reading of mine. It is **F16**, verbatim, disposition **FIX**,
with `tests/probes/execute-arm-class.bund` cited as the probe that pins the
failure. Two resolved decisions then say what Bund2 must do instead:

- **D23** — `<class> !` builds from the CLASS **value** it is given, *never* by
  a registry lookup of the class itself; parents still resolve by name through
  the registry.
- **D25** — the object's `.class_name` comes from the class value's own
  `.class_name` slot, and construction **fails at that point** if the class
  carries none.

So the one behaviour in this RFC's territory that Bund2 is required to change
is filed in the Preservation table as "preserved exactly", and the two
decisions that mandate the change appear nowhere in the document. "Decisions
consumed" lists D1 and D2 only. F16 is never mentioned.

Under CLAUDE.md this is the "unplanned deviation" case in reverse: the RFC is
about to implement a *planned* deviation without declaring it, which means no
acceptance criterion covers it and the goldens have no disposition.

What the RFC needs: F16, D23 and D25 in the header; §5 rewritten to say the arm
errors today; a Preservation row reading **changed** with D23/D25 as the
authority; and a criterion that checks both provenances (registered class
resolved back onto the stack, and a class built on the stack and never
registered) plus the anonymous-class failure.

### B2 — the F66 plan for `execute-arm-class` contradicts D25's follow-on

The Open questions section says:

> Two of the four unreproducible goldens are `execute-arm-class` and
> `execute-arm-not-executable`. … Record them once this RFC's implementation
> lands and the output is stable.

`execute-arm-class` is on F66's list *because it errors*, and it errors because
of F16. Once this RFC implements the D23/D25 fix it stops erroring, so there is
no `Location` row and no build path — F66 ceases to apply to it. D25's follow-on
states the correct disposition directly:

> `tests/probes/execute-arm-class.bund` builds a nameless class and must be
> reshaped to set `.class_name`, since it is the probe that will prove F16's
> fix.

Recording it as an F66 deviation "once this RFC's implementation lands" would
pin a hash of exactly the failure the RFC exists to remove. `execute-arm-not-executable`
is unaffected by this and stays on F66's list.

### B3 — S5's cache is invalidated by a counter that never moves for the state it caches

S5:

> A `m()` call site caches `(class identity, method name) → resolved method`,
> invalidated by the same generation counter RFC-0002 gives the word table.

Three separate pieces of mutable state can change the answer, and none of them
is the word table:

1. **The class registry.** `register_class` writes a per-VM class map
   (`reference/rust_multistackvm/src/multistackvm_classes.rs`), reached from
   `register`. Re-registering a class under the same name replaces it.
2. **`methods_fun`.** `register_method` calls `unregister_method` first and then
   inserts (`reference/rust_multistackvm/src/multistackvm_methods.rs:6-13`), so
   method registration is last-write-wins. A slot's PTR can resolve to a
   different function without any class changing.
3. **The object's own field tree** — see B4.

RFC-0003 §S8 uses `(Symbol, generation)` for *word* call sites and that is
sound, because the thing keyed and the thing versioned are the same table. S5
borrows the sentence without the property that made it true.

There is also a second-order problem with the key itself. Under D1 identity is
lazy, and under `set`'s map arm it is re-minted on every write (see B4/§5
below), so keying on "class identity" both **forces a materialisation** D20 does
not list and **misses** after any `set`. This is D35's objection to identity-
keying the compiled cache, which the owner resolved by keying on the payload
`Rc` pointer instead. S5 should say which mechanism it uses and against what it
invalidates.

### B4 — a per-class flattened table is unsound while per-object slot writes exist

S1 resolves the table "once at registration", per **class**. But
`locate_value_in_object` searches the **object**, and objects are writable
through the same tree:

```
reference/Bund/src/stdlib/functions/oop/value_class.rs:31-52
pub fn set_value_in_object(name: String, mut value: Value, n_value: Value) -> Value {
    match value.get(name.clone()) {
        Ok(_) => { value = value.set(name, n_value); return value; }
        Err(_) => {}
    }
    ...
    for s in super_list {
        new_super = new_super.push(set_value_in_object(name.clone(), s, n_value.clone()))
    }
    value = value.set(".super".to_string(), new_super);
```

It walks `.super` exactly as the search does and **rewrites the slot wherever it
finds it**, rebuilding the parent objects on the way out. `wrap` is a caller
(`:104`). So an individual object's slot can differ from its class's, and any
ordinary map-set word reaching an object's map does the same.

`set_value_in_object` appears nowhere in the RFC. Neither does the fact that the
field tree is *writable*, which S2's "the field tree is preserved" reads as
though it were not.

Criterion 2 cannot catch this. It quantifies over "every class and every method
name reachable from it" — the case where the class table and the object search
agree by construction. The differential it needs is over *objects*, after
mutation.

Either the table is per-object (which S1 rejects in Alternatives, on cost), or
the RFC states an invariant that method slots are never written per-object and
proves it against `set_value_in_object` and `wrap`.

## 3. Claims that need a citation and lack one

1. **"`.id` returns a 21-character string"** (Summary implicitly, Preservation
   row, criterion 4). Nothing cites the length. It follows from `id: nanoid!()`
   (`reference/rust_dynamic/src/value.rs:35`) and nanoid's default alphabet
   length — cite both, because criterion 4 turns the number into a test.

2. **Four "confirmed against the oracle" claims with nothing recorded.** §1 "a
   class with `".super" [ :Object ]` answers `.id`"; §3 "two objects of one
   class return different ids"; S6 "`:.id :A object !` returns the instance's
   id"; S6 "a name string is rejected with `# NO LAMBDA or PTR IN #1`". The
   error text I confirmed by reading (`object_execute.rs:19`); the other three
   are behavioural and there is no probe for any of them under
   `tests/probes/`. Criterion 4 says such things are "pinned as probes … per
   D21" — these should be too, and until they are, the RFC is asserting oracle
   results a later reader cannot re-run.

3. **"step 2 writes to the copy immediately, so no payload is ever shared with
   the class"** (§3, step 1) — a claim about *Bund2's* `set`, not the
   reference's, with no citation into `crates/`. It also reads backwards
   against D35: D35's whole resolution is that a `dup`'d value **shares its
   payload** (`crates/bund2-value/src/lib.rs:480`) and that this is what makes
   the cache hit. If construction really unshares immediately, say why that is
   desirable rather than offering it as reassurance.

4. **"the **15** goldens whose first unimplemented word is `class` (11) or
   `object` (4)"** — uncited and, as far as I can measure, wrong; see §5.

5. **"D14 already splits them, and the split runs exactly along this RFC's
   seam"** — contradicted by the generated artefact for `resolve.class`, and
   D14's partition is over *words*, so it cannot answer which side the ten
   classes registered *without* a word fall on (see §6, gap 8).

## 4. What the Preservation analysis does not enumerate

The table has 14 rows. These behaviours are in the code the RFC reimplements
and have no row.

**P1 — `set` on a CLASS/OBJECT is not a field write.** The map arm of `set`
returns `Value::from_dict(m)` (`reference/rust_dynamic/src/set.rs:21-23`), a
brand-new value: fresh `id` and fresh `stamp` (`create_map.rs:31-42`), `q` reset
to `100.0`, and `attr` and `tags` **discarded** — only `dt` is restored (`:22`).
The `res.id = nanoid!()` at `:16` is dead on this path. Construction performs
two of these (`bund_object.rs:36`, `:105`). Four consequences, none stated:

- §3 step 1 attributes the instance's fresh identity to `dup`. It comes from
  the `set` at `:36`; `dup`'s `res.id = nanoid!()` (`dup.rs:11`) is overwritten
  a line later. D1 already lists `set.rs:16,31,43,58,76,91` among the
  fresh-identity sites — the RFC's mechanism is the wrong one, even though its
  conclusion (distinct ids per instance) is right.
- **`.timestamp` on an object is the stamp of the last `set`**, not the class's
  and not `dup`'s. S4 and criterion 4 say only that it "answers". Under D2's
  sampled stamp, *what* it must answer is the open part.
- **An object's `.id` is not stable across mutation.** Every `set` mints a new
  one, so `wrap` changes an object's `.id`. Whether Bund2 preserves that is a
  language question and it is unasked.
- **`q` is reset and `attr`/`tags` are dropped at construction.** D32 says `q`
  propagation is preserved. No row.

**P2 — `.init` can be a PTR, not only a LAMBDA.** Both construction sites branch
`PTR | LAMBDA | _` (`bund_object.rs:57-82` and `:137-162`), and the reference's
own classes use the **PTR** form: `Value` (`value_class.rs:79`), and likewise
`List`, `Floats`, `Intervals`, `Integer`, `Float`, `Bool`. §3 step 4 says
"evaluates each parent's `.init` **lambda**". Two sub-behaviours ride on the
arm split: an unregistered PTR method is **silently skipped** (`:63`, `:143` —
the `if` has no `else`), and a non-PTR/LAMBDA `.init` produces a `log::debug!`
and nothing else (`:81`, `:161`).

**P3 — `.init` may replace the object being constructed.** After each parent's
`.init`, `if_object_of_class_in_stack` (`:6-25`) tests the stack top and, if it
is an object of that class, **pulls it and stores that** into `.super` in place
of the object just built (`:83-94`). The same dance at the top level decides
what `apply` receives (`:163-174`). §3 mentions only the top-level half. This is
the mechanism by which a constructor returns a *different* object, it is why
`.class_name` is load-bearing (D25 says so), and the parent-level half has no
row.

**P4 — `#` swallows errors.** Both applies are `let _ =`
(`object_execute.rs:36,38`), so a failing `unwrap` or a failing `!` inside `#`
produces no error and `#` returns `Ok(vm)`. Under D36 this is precisely the
decision that has to be taken — reproduce the silence, or report. S6 describes
`#` without it.

**P5 — `#.` is counted but never specified.** §6 lists it among the ten words;
the Preservation table has a row for `#` alone. It differs from `#` in two ways
beyond the stack: its depth guard is **1**, not 2 (`:47` vs `:43`), and it takes
the *object* from the workbench while the lambda still comes from the main
stack (`:15-26`) — which is exactly RFC-0003 §S4b's receiver convention and D18's
workbench-form rule, and worth saying so rather than leaving it implied.

**P6 — `make_bund_object` on an OBJECT is the identity** (`:108-110`).
Constructing from an already-constructed value returns it unchanged.

**P7 — the error texts.** Only the non-OBJECT receiver text has a row. Also in
scope: `VM stack is empty` (`multistackvm_object.rs:48`), `VM no method {} has
been registered` (`:53`), `m({}) returned: {}` (`:67`), `VM Method {} not
registered` (`:71`), `VM method name casting error: {}` (`:74`), `Stack is too
shallow for inline EXECUTE.OBJECT` (`execute_object.rs:9`), `Stack is too
shallow for inline object()` (`bund_object.rs:117`), `OBJECT returns: NO DATA`
(`:185`), the four `#`/`#.` texts (`object_execute.rs:19,21,31,33`), and the
`UNWRAP`/`WRAP`/`IS` family (`value_class.rs:85-144`).

Two of those deserve separate attention:

- **`bund_object.rs:99` names the wrong class.** `bail!("OBJECT class {} not
  registered", &name)` interpolates `&name` — the *child's* name — where
  `&class_name`, the parent that is actually missing, is in scope one line up
  at `:98`. A hierarchy `B → A` with `A` unregistered reports `B`. That is a
  defect candidate for `docs/registers/defects.md`, inside the path this RFC
  reimplements.
- **`value_class.rs:97`** bails with the prefix `WRAP:` from inside a function
  whose other messages say `UNWRAP` (`:85,91,93`), and `:85`'s
  "too shallow for inline UNWRAP" is in `stdlib_object_value_wrap`. Cosmetic,
  but goldens capture text.

**P8 — `value_locate` is a second entry point.** `multistackvm_object.rs:29-42`
is a public method running the identical search and returning the value without
dispatching (`rust_multistackvm/tests/vm-test-class.rs:41`). §4 documents `m`
only. It is the same search S1 replaces and it carries its own error texts.

**P9 — `methods_fun` registration is last-write-wins.** `register_method`
unregisters then inserts (`multistackvm_methods.rs:6-13`) — the same shape
RFC-0002 preserves for words as a generation bump (`RFC-0002:603`). Criterion 5
asks only that two `Interp`s can hold different methods; it does not pin
re-registration order.

## 6. Assumed but not stated

1. **That parents are resolvable at registration time.** S1 flattens "once at
   registration". The reference resolves parents at **construction**
   (`bund_object.rs:45-48`), which is why forward references work: `:B class
   ".super" [ :A ] set register` succeeds whether or not `A` exists yet, and
   fails only at `:B object`. Flattening at registration turns that into an
   ordering constraint the language does not have. The RFC needs to say what
   happens — re-flatten when a parent later registers, flatten lazily on first
   construction, or accept the narrowing — and each of the first two needs the
   invalidation B3 shows is missing.

2. **What the flattened table stores.** "Every slot reachable through `.super`,
   resolved once" is ambiguous between the *slot value* (PTR/LAMBDA/other, with
   `m`'s three-arm dispatch still at call time) and the *resolved function*
   (which would delete the LAMBDA and push arms). `m` dispatches on the slot's
   **type** (`multistackvm_object.rs:57-83`), so the difference is observable.

3. **That `.super` is acyclic.** `locate_value_in_object` recurses with no
   visited set (`:18-23`), and `make_bund_object` likewise (`:42-104`), so a
   cyclic `.super` is an infinite recursion today — one that S3's frame push
   converts from a stack overflow into a heap exhaustion or a hang. Flattening
   at registration has to terminate on the same input. Nothing is said. This
   interacts with criterion 3's 60-second wall clock.

4. **That an object's own map is searched before `.super`, and that
   `.class_name` and `.super` are ordinary slots.** Nothing validates a class's
   shape — `Value::make_class()` (`create_map.rs:133-143`) produces an empty
   map with `dt = CLASS` and the three slot kinds are convention. A program can
   `set` a slot named `.super` to a non-LIST, and `locate_value_in_object`
   silently returns `None` at `:19-21`.

5. **That method names match exactly**, with no normalisation of the leading
   dot — the RFC establishes that slot and method names differ but does not say
   the table keys on the raw string.

6. **That "class identity" in S5 is stable enough to key on.** See B3's second
   paragraph; under D1 and `set`'s re-minting it is neither free nor stable.

7. **That construction's `apply` at `:166,169,173` is the ordinary `apply`.**
   §3 step 5 says "`apply`s" without saying what that does to the object — it
   is `vm.apply(<the OBJECT value>)`, which falls to `multistackvm_apply.rs`'s
   push arm for a non-callable. Worth one sentence, because `apply`-on-an-object
   is the only reason the constructed object ends up on the stack at all.

8. **Which classes core registers.** Criterion 4 needs `Object` and `Printable`
   (`base_classes.rs:100,115`); `.str`/`.print`/`.println` need `Display`
   (`display_class.rs:105`); core's `wrap`/`unwrap`/`is` need the `.data`
   convention the `Value` class establishes (`value_class.rs:72-81`). §6 puts
   "the built-in classes" in library and names only the five that also register
   a *word*. Ten classes are registered **without** a word — `Object`,
   `Printable`, `Display`, `Value`, `Integer`, `Float`, `Bool`, plus `List`,
   `Floats`, `Intervals` — and D14's partition, being over words, does not
   place them. This is a real gap: it decides whether a core-only Bund2 can
   answer `.id`.

9. **That RFC-0009 is contingent on three unaccepted RFCs.** RFC-0001 and
   RFC-0002 are **Proposed**; RFC-0003 is **Draft**. S3 depends on RFC-0003 §S4's
   frame loop, S5 on RFC-0002's generation counter, S4 on RFC-0001's heap
   header. The header says "Blocked on: nothing", which is true of *decisions*
   and misleading about RFCs.

## 7. Consistency with accepted RFCs and ERRATA

- **ERRATA** — consistent. The last entry retires the "cannot shrink to 16
  bytes" supersession exactly as the Motivation describes, and cites
  `base_classes.rs:91-92` and `:16` as the RFC does. No conflict.
- **RFC-0000** (Accepted) — §2 calls `methods_fun` "a **fifth** name-keyed
  table" after listing "the inline tables, the lambda table, the alias table and
  the command table". RFC-0000:135 counts **three live tables** plus a dead
  fourth, `functions` (F19), and RFC-0003 §S7 adds `CF`. "Fifth" lines up with
  neither count. The substantive claim — that it is not a *word* table and
  RFC-0002's slot table should not absorb it — is right; the ordinal should go
  or be reconciled.
- **RFC-0003 §S4b** — consistent and well used. `execute_class` and
  `execute_object` taking `_op` is exactly what S4b records, and RFC-0009's
  "which RFC-0003 §S4b confirms is the convention" is accurate.
- **RFC-0003 §S4** — consistent. §S4 names class-hierarchy depth as the third
  axis and defers it here; S3 picks it up. Good.
- **RFC-0003 §S3** — S1's "a cache over the field tree, in exactly the sense
  RFC-0003 §S3 makes BundIR a cache over a lambda body" is a fair analogy, but
  §S3's cache is over an **immutable** body (D5: lambda bodies are write-once).
  The field tree is not immutable (B4). The analogy imports a property the
  subject does not have.
- **RFC-0003 acceptance-criteria preamble** — "Each names the tool that decides
  it. Where no tool exists, that is stated as work rather than assumed."
  RFC-0009's criteria 1, 3 and 5 name tools or measures that do not exist yet
  without saying so.
- **D36** — Open questions says "D36's error presentation is still settling".
  D36's status is **RESOLVED** (frame preserved, location and delivery
  redesigned). What is still in flight is its *implementation*, per F66's
  disposition. Say that; "settling" reads as an open decision, and CLAUDE.md
  makes the difference load-bearing.
- **D35** — see B3 and §3.3. The RFC invokes D35 twice and reads it against
  itself once.

## 8. Smaller notes

- §4 step 2's error text is right, but the **empty-stack** case reaches a
  different message first (`VM stack is empty`, `:48`) and the **not found**
  case a third (`VM no method {} has been registered`, `:53`). §4's three-step
  summary reads as though the OBJECT guard were the only failure.
- S6's "It pulls a method-name *string*" is slightly stronger than the code:
  `execute_object.rs:15` `cast_string()`s whatever it pulled, so a PTR or an
  atom also works. That is D16 territory and probably worth one clause.
- §6 says "nothing dispatches `methods_fun` by name from a program". True as
  far as I can see, and it is the load-bearing sentence for criterion 5 — it
  deserves the same fenced-block treatment criterion 6 asks for elsewhere.
- The oracle caveat is well placed and currently holds: `cargo xtask cite`
  reports oracle crates byte-verified 5/5.
- `set` in the reference calls `self.dup().unwrap()` (`set.rs:15,42,75`). Not a
  Bund2 concern, but it is a panic on the construction path and is worth a line
  in the defects register if it is not already there — a `dup` failure inside
  `set` aborts the interpreter.

## 9. Summary

Four blockers: B1 (the CLASS-execute arm is described as preserved when F16,
D23 and D25 make it a mandated deviation), B2 (the F66 plan for
`execute-arm-class` contradicts D25's follow-on), B3 (S5's cache is invalidated
against the wrong table, and its key forces a materialisation D35 already ruled
out for the compiled cache), B4 (a per-class table is unsound while
`set_value_in_object` can rewrite a slot per-object, and criterion 2 is scoped
so it cannot notice).

Beyond those: one wrong citation of fact (`resolve.class` is library, not core),
two mislocated line numbers (`base_classes.rs:107`, the `make_bund_object`
range), a golden count that does not reproduce against a measure that does not
exist, and nine preservation behaviours with no row — of which P1 (`set` is not
a field write, so `.id` and `.timestamp` and `q` all move at construction), P2
(`.init` is usually a PTR) and P3 (`.init` can replace the object) are the ones
that would change an answer.

The parts I would keep unchanged: §6's line accounting, S2, S6, and the
Alternatives section, which rejects the right three things for the right
reasons.
