## Blocking

### B1 — A world file the reference wrote cannot be opened by Bund2 at all, so the row is false for two of its three words

The row added by the sixth-review amendment (`:691`):

> **Refused at the read, as in the oracle.** A world file or a base64
> string holding a JSON value inside a container, written by the reference,
> fails Bund2's `load`, `load.model` and `decode.base64` with bincode 2's
> reason under each word's prefix, as the oracle's own readers fail. Read
> from the codec, not run.

Run today, release binaries, one value — `dict "k" '{"k": 1}' json set`:

| step | engine | result |
|---|---|---|
| `"cross7" save` | oracle | `after save`; `cross7.world` written, 32 KiB, `file` says `SQLite 3.x database` |
| `"cross7" load` | Bund2 | `Open world operation returns: I/O error: Not a redb database: magic number mismatch` |
| `"cross7" load` | oracle (control) | `Stacks LOAD returns: Extraction of value returns: Bincode does not support the serde::Deserializer::deserialize_any method (…)` |
| `encode.base64 println` | oracle | a base64 string, about 310 characters |
| that string, `decode.base64` | Bund2 | `DECODE.BASE64 unwrapping object returned: Serde(AnyNotSupported)` |
| that string, `decode.base64` | oracle (control) | `DECODE.BASE64 unwrapping object returned: Bincode does not support the serde::Deserializer::deserialize_any method (…)` |

So the base64 third of the row holds exactly as written. The world-file
two thirds cannot: **D27 made Bund2's world file redb**, "replacing the
reference's SQLite" (`decisions.md:1261-1264`), and `open_world` is
`Database::create` (`world.rs:51-54`), which refuses a SQLite file at the
magic number. No codec, no family prefix, no bincode reason. `load.model`
goes through the same `open_world` and necessarily fails the same way.
The row's "as the oracle's own readers fail" is also the wrong comparison
for a file: the oracle reads its own file to the codec and fails there;
Bund2 never reaches the codec.

The RFC lists D27 under "Touched but not consumed" (`:67`) and the sixth
review's own S1 quoted `world.rs:379-381`'s comment that "a world file
moved between the two engines needs a new container, not new bytes" — the
sentence that says why the row is wrong, cited in the review that led to
the row. And the row's last clause, "the `recv` row is the bus's case of
this, and was run", conflates two things: the bus is in-process, so bytes
the oracle wrote can never reach a Bund2 `recv`; what the `recv` row
measured is Bund2's own decode arm on Bund2's own bytes.

What is needed: the row rewritten to what was run — a base64 string the
reference wrote fails `decode.base64` with bincode 2's reason under the
word's prefix; a world file the reference wrote is not readable by Bund2
for any value, by D27, and the oracle's bytes reach Bund2's `load` only if
moved into a redb container by hand, which nothing does. It is the
pattern this document keeps naming: a row labelled "not run" that is wrong
when run.

## Significant

### S1 — `bund2-cli` has an `async` feature that links `bund2-async` to no code, which the document says cannot happen and F124 says should not

§C8's note (`:499-506`): "**And nothing shipped links the crate** … `bund2-cli`
does not depend on it; the façade crate `bund2` declares it behind an
`async` feature, off by default, and its `lib.rs` has no items at all". The
row at `:676`: "No binary links it".

`crates/bund2-cli/Cargo.toml:21` depends on `bund2`, and `:36` declares
`async = ["bund2/async"]`. So:

```
$ cargo tree -p bund2-cli --features async -i bund2-async
bund2-async v0.0.0 (/Users/gandalf/Src/Bund2/crates/bund2-async)
└── bund2 v0.0.0 (/Users/gandalf/Src/Bund2/crates/bund2)
    └── bund2-cli v0.0.0 (/Users/gandalf/Src/Bund2/crates/bund2-cli)
```

and without the feature the package is absent from the tree. A `bund2`
binary built with `--features async` links the host crate, and because the
façade re-exports nothing (`crates/bund2/src/lib.rs`, no items) and the CLI
names no item of it, the feature reaches no code. That is the shape F124
recorded for `jit` — the manifest's own comment two lines above the feature
says so: "the facade re-exports nothing, so a feature routed through it
reached no code (F124)". The `jit` feature was then re-routed through
`bund2-runtime`; `async` was not, and nothing in the RFC, RFC-0000's crate
table or the registers mentions that the feature exists.

The sixth review's "no `bund2-async` in `bund2-cli`'s manifest" was
literally true — the string is not there — and missed the feature. Two
sentences in the RFC are false for that build; and the feature is either a
defect to file against F124's pattern or a stub to remove. Which is the
owner's, as is whether RFC-0000's "what the façade should expose" question
now has a concrete instance.

### S2 — The research's `Value::wrap()` exists and does what the research said; §C3's correction and ERRATA's entry corrected the wrong thing

§C3's note (`:308-317`): "the Bund words `wrap` and `unwrap` serialise
nothing: `wrap` stores a value in an OBJECT's `.data` member …
(`value_class.rs:83-106`, `:108-125`) … So there is **one layer** … and no
Bund program can put an ENVELOPE on the stack." ERRATA `:160-165` records
the research's "`Value::wrap()` produces an `ENVELOPE`… the message-passing
boundary between VMs is a mechanism the language already has a word for"
as "does not hold".

The research wrote `Value::wrap()`, a method, and the method exists:
`reference/rust_dynamic/src/bincode.rs:79-86` is `pub fn wrap(&self)`,
which calls `to_binary()` and returns `Value::make_envelope(res)`; `:87-103`
is `unwrap()`, which requires `dt == ENVELOPE`, calls `from_binary` on the
bytes and mints a fresh id. That is, word for word, "produces an `ENVELOPE`
containing a bincode serialisation, and `unwrap()` reconstructs it". What
does not hold is the sentence after it — "a mechanism the language already
has a word for" — because no Bund word calls `Value::wrap()` or
`Value::unwrap()`; the Bund words of those names are the OOP `.data` words
the note describes, and the grep of all three reference trees finds no
caller of `.wrap()`. The RFC's §C3 is right that the bus does not use it
(`mod.rs:88`) and right that there is one layer on the bus. It is wrong
that the primitive is not there, and ERRATA — the immutable research's
only correction channel — now says the research was wrong about a function
that is exactly as the research described.

And "no Bund program can put an ENVELOPE on the stack" is false of the
reference: the `image` words construct and push ENVELOPE values with
`Value::make_envelope` (`reference/Bund/src/stdlib/functions/image/image_class.rs:36,48,100`,
`image_ops_class.rs:19,42,65,88`, `image_size_class.rs:60`,
`image_face_class.rs:57`) and test for the type (`image_class.rs:218,258,294`).
Those words are deferred (D28, `classify.rs:500-503`), so the sentence is
true of Bund2's in-scope vocabulary and false of the language. The
conclusion §C3 draws — the alternative is moot — survives both
corrections, since `send` on an ENVELOPE would still need a word that makes
one. What is needed: a note at §C3 and an ERRATA entry correcting the §2.3
entry, each saying which half of the research's sentence holds.

### S3 — The lambda refusal text is "held by" a test that does not hold it, and a one-line program reaches it

The write-row note (`:679-685`): "`save`, whose inner texts — `Error
converting data to blob:` for a stack value, `Error compiling lambda body:`
for a lambda — Bund2 dropped until this date; restored, and held by
`a_refused_value_is_refused_in_the_references_words`." D166's note says the
same.

The test (`world.rs`, the uncommitted diff) runs three programs and asserts
three texts: `Stacks SAVE returns: Error converting data to blob:`,
`Aliases SAVE returns: Error converting data to blob:` and `SAVE.MODEL
returns: Error compiling mode:`. The lambda text appears in `world.rs`
exactly once, at the write site (`:397`), and in no test. It is not an
unreachable arm. A lambda holding a list literal 300 deep reaches it
through D114's depth refusal, measured today:

| program | Bund2 | oracle |
|---|---|---|
| `:deep { [ … 300 deep … 1 … ] } register "lam" save.lambdas` | `Lambdas SAVE returns: Error compiling lambda body: the value nests 257 deep, and 256 is the most the wire format can carry` | `after save.lambdas`, 28 KiB written |
| the same, then `save` | `Aliases SAVE returns: Error compiling lambda body: the value nests 257 deep, …` | — |
| the same list on the stack, `save.stacks` (control) | `Stacks SAVE returns: Error converting data to blob: the value nests 257 deep, …` | `after save.stacks`, 36 KiB written |

A nested JSON cannot be put in a lambda body from syntax, which may be why
the test has no lambda case; the depth refusal can. One case in the test,
with the deep lambda, and the sentence becomes true.

### S4 — The depth refusal fires at every writer the D166 row names, and the table's depth row names `send` alone

The Preservation row at `:612`: "A value nested past 256 levels, at
`send` — **Deliberately changed — D114.**" D114's title and body are
`send`'s (`decisions.md:6978-6989`, "Blocks: nothing"). F118's FIX bounded
the codec itself (`defects.md:4014-4016`), so every word that encodes
refuses, and RFC-0001's new note says so: "Both are refused at the write,
by every word that encodes" (`RFC-0001:303`). The D166 write row (`:668`)
enumerates the writers for the JSON case — `send`, `send.quick`, their
workbench forms, `encode.base64`, `save.model`, `save`, `debug.dump`, and
`encode.base64.` by the note. The depth case has no such row, and S3's
table shows three of those writers refusing a 300-deep value the oracle
writes. D167's text mentions it in passing ("D114's for depth, which has
taken the same path since it was built"). The deviation is recorded —
F118's FIX and D114 — but the table that is supposed to enumerate every
behaviour this design changes enumerates one writer of eight for it, and

## Disposition

Not ready to accept, on one finding: B1 is a row added by this amendment,
labelled "not run", that is false for two of its three words when run,
and false for a reason — D27 — the RFC lists among the decisions it
touches. S1 is a false sentence in two places and a feature in the shipped
manifest that reaches no code, F124's shape recurring; S2 is a correction
in the RFC and in ERRATA that corrected a function the research described
accurately; S3 is a test credited with holding a text it does not hold,
for a case a one-line program reaches; S4 is the table naming one writer
of eight for a refusal the register records for all. D167 is built as
ruled and its test holds what it says; every test the criteria name
passes in both builds; conformance is at its ceiling and unmoved; every
citation resolves and, with the two minor exceptions above, says what the
document says it says. Everything the sixth review blocked on is answered
where it stands. The oracle was run on the one new row labelled "not run",
and that is where the blocker came from — the sixth review's closing
point, a third time.
