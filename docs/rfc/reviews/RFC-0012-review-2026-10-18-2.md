## Findings, most serious first

### 1. `graph.maxflow` can answer a wrong flow, and nothing in the RFC says so

S5 (R:194-196) says an arc counts as present only when its residual is
above `1e-12 × max(largest capacity, 1)` (`GA:616`). A consequence S5 does
not state: **a whole capacity below that threshold counts as absent from
the start.** The BFS skips it (`GA:636`), and the shares filter drops any
share under it (`GA:693`).

```
:T :S [ [ :S :T 10000000000000.0 ] [ :S :M 5.0 ] [ :M :T 5.0 ] ] [ :S :M :T ] graph! graph.maxflow println
```

bund2: `{ edges=[ [ S :: T :: 10000000000000.0 :: ] :: ] :: flow=10000000000000.0 :: }`.
The maximum flow is 10000000000005.0. That is below 2⁵³, so an f64 holds
it exactly. Drop the 1e13 edge and the same graph answers `flow=5.0`. A
second path through `M` disappears only because a larger edge exists.

- No criterion can catch this. `max_flow_is_the_min_cut` uses
  `graphs(9, 300, 0)`, whose weights are the integers 0 to 8
  (`GA:1472-1488`). With the largest capacity at most 8, the threshold is
  1e-12, so the tolerance never decides anything.
- **S5's own argument does not need the tolerance.** The bound rests on
  two facts: the bottleneck arc lands at exactly 0.0, and a reverse arc
  gains `b > 0`. Both hold if "present" means `cap > 0.0`. Since `b ≤ cap`,
  `cap - b` never goes negative under IEEE rounding, so no arc off the
  path changes and every reverse arc gains a positive residual. The RFC
  gives no reason for the tolerance. If its reason is to suppress rounding
  noise in `edges`, that is a trade against correct answers like the one
  above, and it needs a ruling.
- It belongs in S1's `graph.maxflow` row or in Open questions, and in
  Preservation. This is the kind of unplanned behaviour CLAUDE.md sends to
  `decisions.md`.

### 2. S4's Bellman–Ford message does not name what S4 says it names

S4 (R:156-157) says `B` is "the smallest-numbered node on a negative cycle
reachable from `A`". The code walks back from the last node relaxed in the
nth pass, collects that one cycle, and takes its minimum (`GA:543-558`).
When two negative cycles are reachable, the cycle it lands on depends on
edge order:

```
:A [ [ :A :B 1.0 ] [ :B :C -5.0 ] [ :C :B 1.0 ] [ :A :D 1.0 ] [ :D :E -5.0 ] [ :E :D 1.0 ] ] [ :A :B :C :D :E ] graph! graph.bellmanford
```

bund2: `GRAPH.BELLMANFORD: A reaches a negative cycle through D`. `B`
(node 1) is on a reachable negative cycle and `D` is node 3. Put the D–E
edges first and the answer is `B`.

- The code comment (`GA:550-551`) and D192 (`decisions.md:3739-3741`)
  say this makes "the message … not depend on which edge the last pass
  relaxed". That holds within one cycle and fails across two.
- Criterion 3's check (`GA:1788-1810`) proves that `u` is the least node
  of *some* negative cycle. That matches the code, not S4's sentence, so
  the criterion passes while the sentence is false.
- Either restate S4 as "the smallest-numbered node on the negative cycle
  the search finds, which depends on edge order", or have the code compute
  the global minimum and test that. Either way the message is
  deterministic (relaxation follows `net.edges`). Only the rule is
  misstated.

### 3. The open question on non-finite weights is answered: a program makes them in both engines

R:304-309 leaves non-finite weights "Unspecified until a program is shown
to make one", and grounds that in an uncited claim about division. Both
engines make them:

```
100…0.0 100…0.0 * println      (two 1e200 literals)   → inf   (oracle and bund2)
-1.0 math.sqrt println                                → NaN   (oracle and bund2)
```

Put into a graph (`-1.0 math.sqrt [ :A :B ] ++ list push [ :A :B ] graph!`),
bund2 gives:

- `:A … graph.bellmanford` → `{ node=B :: path=NaN }`;
- `:A … graph.paths` → `path=NaN` for B. The oracle prints the same row,
  so this is reference behaviour;
- `… graph.mst` → `{ edges=[ [ A :: B :: NaN :: ] :: ] :: weight=NaN :: }`;
- with `1.0e200 1.0e200 *` as the weight, `graph.bellmanford` →
  `path=inf`; negated, `path=-inf`;
- `:B :A … graph.maxflow` with an `inf` weight →
  `a capacity must be a number not below zero: A -> B weighs inf`. That
  message is false for `+inf`, which is not below zero.

The RFC's stated condition is met. The open question now needs an answer:
the behaviour specified and tested, or the question taken to
`decisions.md`. The sentence "whether another word makes one was not
checked" should come out.

### 4. "Current behaviour" misstates `graph.path`'s reader: `fast_paths` drops self-loops and every edge below weight 1

The table at R:68-71 says `graph.path` reads "1.9 as 1, −1.0 as 0" and
keeps "the **lowest** weight" of a repeated edge. That leaves out
`do_add_edge`. It **skips** an edge with `from == to` and one with
`weight < 1`
(`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/fast_paths-1.0.0/src/input_graph.rs:190-203`),
before `freeze` sorts and dedups (`:136-161`). So a weight that truncates
to 0 removes the edge. It does not weigh 0. Both engines agree:

```
:B :A [ [ :A :B 0.5 ] [ :A :C 1.0 ] [ :C :B 1.0 ] ] [ :A :B :C ] graph! graph.path println
```

oracle and bund2: `path=[ A C B ]`, `weight=2.0`. The 0.5 edge is not
there.

```
:B :A [ [ :A :B 0.5 ] [ :A :B 5.0 ] ] [ :A :B ] graph! graph.path println
```

oracle and bund2: `weight=5.0`. "The lowest weight kept" is false here,
because the lower weight was dropped before the dedup ran.

Bund2 matches because it calls the same crate (`G:101-176`). The defect is
in the RFC's text. But "Current behaviour" is the preservation contract,
and Preservation's first bullet (R:225-227) inherits the understatement.
Against `graph.path`, an edge under 1.0 and every self-loop **do not
exist**. Also, R:75-80 cites only `make_graph`'s lines for "both readers".
`make_fast_graph`'s are `make_graph.rs:39`, `:59-69`.

### 5. `graph.path` crashes the oracle and is an internal error in Bund2, and no register records it

`fast_paths` sizes its graph by the largest endpoint of a **kept** edge
(`input_graph.rs:204`). `calc_path` asserts that both nodes are below
that size (`path_calculator.rs:77-82`). A node in `nodes` that no kept
edge reaches, at an index past every kept endpoint, fails the assertion:

```
:C :A [ [ :A :B 1.0 ] ] [ :A :B :C ] graph! graph.path println
```

- oracle: `The application panicked (crashed). invalid end node … path_calculator.rs:81`.
- bund2: `internal error: native graph.path panicked: invalid end node … This is a defect in Bund2, not in the program being run`.
  D49 catches the panic.

That is a valid program. The message tells its author the interpreter is
broken. The same happens for any graph whose kept edges stop short of the
last node: an isolated last node, edges that are all self-loops or under
weight 1 (finding 4), or no edges at all.

This is outside RFC-0012's twelve words. It is inside the RFC's claims,
though: R:89-90 says "Bund2 reproduces all seven words" and R:218-221 says
the seven are "preserved exactly". Under CLAUDE.md, the crash is an
original-implementation defect for `defects.md`. Bund2's disposition then
needs a real error arm rather than `Error::internal` (CLAUDE.md, "Three
ways out", 2). Until that is recorded, "preserved exactly" covers an
unrecorded crash.

### 6. The `.` forms: S1 and S4 describe them wrongly or not at all

S1 (R:96-98) says each word has "a `.` form holding the graph on the
workbench (slot 0)". What `bench_form` does (`wb.rs:91-117`, `:119-160`;
the effect is at `wb.rs:184-188`):

- The graph is **taken** from the workbench and consumed, not held.
- **The answer goes to the workbench**, not the stack (`wb.rs:94-95`,
  `:184-187`). The RFC never says this. `GA:1104-1112` and `GA:1156-1162`
  rely on it.
- **A missing node operand is not `NO DATA #n`.** The pre-check refuses
  first: `Stack is too shallow for inline GRAPH.BFS.` (`wb.rs:133-137`).
  Run: `[ [ :A :B 1.0 ] ] [ :A :B ] graph! . graph.bfs.` answers that.
  An empty workbench gives `Workbench is too shallow …` (`wb.rs:126-131`).
  S4's "a missing one `NO DATA #n`" (R:163-164) is false for all twelve
  `.` forms.
- **What a refusal leaves** goes to the workbench (`wb.rs:113-114`). S4's
  "What a refusal leaves" (R:175-179) covers the plain forms only.

D18 (`decisions.md:888`) and D24 (`:1144`), which set this shape, are not
in "Decisions consumed".

### 7. Criterion 1's test does not check "exactly one answer"

`each_form_holds_the_graph_on_the_workbench` makes three assertions: the
plain form's workbench is empty; the `.` form's stack is `["7"]`; and
`stack[1..]` of the plain form equals the `.` form's workbench
(`GA:1160-1162`). It asserts neither that the plain stack has length 2 nor
that its bottom is `7`. Suppose a word pushed two answers. Both forms
would show two, and the test would pass. "Leaves exactly one answer above
the stack beneath it" (R:251) is therefore unchecked for the plain forms.
The fix is two assertions: `stack.len() == 2`, `stack[0] == "7"`.

### 8. S4's refusal list is incomplete, one unlisted message contradicts S2, and none of the unlisted ones is tested

`read` has refusals S4 does not list, and no test reaches any of them
(grep of `GA:933-1920`):

- `a node name must be a STRING, not N` (`GA:90-95`);
- `an edge must be a LIST of two or three, not N` (`GA:107-112`). "Two
  or three" contradicts the four-or-more rule that "Current behaviour"
  and S2 adopt, and that `each_refusal_section_s4_names` tests
  (`GA:1204-1206`);
- `an edge's node must be a STRING` (`GA:116-121`);
- `the nodes must be a LIST` and `the edges must be a LIST` (`GA:88`,
  `:103`). `graph_operand` checks both first (`G:446-451`), so neither
  can be reached through a word.

In every `, not N`, `N` is `dt()`, a **numeric type code**. Runs printed
`not 9`, `not 4` and `not 3`. In messages written in Bund2's own words,
a reader cannot decode that. S4 quotes the messages without their tails,
so the RFC never shows it.

Also unstated: `graph.maxflow` refuses source = sink (`GA:869-874`)
before it checks capacities (`GA:875` → `:583-590`). A graph with a
negative capacity, given one node for both operands, reports the first
error, not the second.

### 9. S4's "What a refusal leaves" has no test

R:175-179 states the residual stack and calls it observable under
RFC-0004 (`docs/rfc/RFC-0004-stack-effects.md:491-496`, which the RFC
does not cite). Every refusal test goes through `err_of`, which discards
the interpreter (`GA:967-972`). `outcome` is used only on success or for
comparing messages (`GA:1116-1128`, `:1164-1175`). No criterion names a
check for the residual.

### 10. S6: `graph` and `graph.` are promotable, and the sync claim is uncited

R:211-212: "all 24 names are `not reached` … as the reference's graph
words are." That holds for the four reference algorithm words
(`PROMOTABLE.txt:398-399,418-421,428-429`). It is false for `graph` and
`graph.`, which are listed as promotable (`PROMOTABLE.txt:139-140`).
"A compiled body syncs its state before each call to one" (R:213-214) is
grounded in `PROMOTABLE.txt:3-5,13-15`, which the RFC does not cite.
D48 and D55, cited at R:210, are not in "Decisions consumed".

### 11. D37's second half: silent fallbacks where an invariant breaks

S5 says "Nothing panics (D37)" (R:186-187). D37 also asks that "every
unrecoverable internal error [be] handled with a meaningful explanation"
(`decisions.md:2104-2106`). Several arms give a plausible answer instead:

- `toposort` falls back to `.unwrap_or(0)` when `find_cycle` finds
  nothing after a failed sort (`GA:351-354`). A message would then name
  node 0, on no cycle.
- `Net::name` returns `""` for an index out of range (`GA:76-78`), and
  `name_list` drops such indices silently (`GA:66-74`).
- The predecessor walk in `bellman_ford` substitutes `v` for a missing
  predecessor (`GA:548`, `:553`, `:556`).

Each can be reached only by a defect in Bund2. That is exactly where
CLAUDE.md asks for `Error::internal` rather than a wrong answer
(compare `max_flow`, which does this right at `GA:649-668`).

### 12. Smaller points on the criteria

- **Criterion 2**: "it refuses what `build_algos` refuses" is broader
  than `wide()` generates (`GA:1508-1532`). Every node and endpoint is a
  STRING and every edge a LIST, so the non-STRING node, the non-STRING
  endpoint and the non-LIST edge are never compared. Neither is a PAIR,
  which both readers accept (`cast.rs:57-59`; `as_list` takes a PAIR's
  `Payload::List`, `bund2-value/src/lib.rs:1140-1148`).
- **Criterion 6** says "through the interpreter", but
  `a_capacity_that_is_not_finite_is_refused_through_the_word` calls
  `graph_maxflow` directly (`GA:1445`).
- **Criterion 8**: "on a test thread's 2 MiB stack" is the harness
  default, which `RUST_MIN_STACK` can change, and the test does not fix
  it (`GA:1227-1254`). A `std::thread::Builder::stack_size` would make
  the claim structural. The test also calls the algorithms on a
  hand-built `Net`, so `read` and the words are outside it.

## Preservation analysis: what it does not enumerate

1. **`graph.path`'s reader** drops self-loops and weights under 1
   (finding 4). The "reader" bullet (R:225-227) says the new words read a
   fractional or negative weight differently. Against `graph.path`, such
   an edge does not exist.
2. **`graph.path`'s crash** (finding 5), which "preserved exactly"
   carries silently.
3. **Non-finite weights reach `graph.paths`** in both engines, and the
   new words' answers to them are unspecified (finding 3).
4. **`graph.maxflow`'s tolerance** discards small capacities (finding 1).
5. **The `.` forms** answer to the workbench and refuse in other words
   (finding 6).
6. **Title-casing's word splitting.** `node_name` is convert_case's
   Title case (`G:33-43`): `:AB` reads `Ab` and `:my_node` reads
   `My Node`. Under S2, `:ab`, `:AB` and `"Ab"` all find the node listed as
   `:AB`, and `:my_node` finds the node listed as `"My Node"`. S2 says "a
   program names a node the way it wrote it". It can also name the node
   in ways it never wrote.

## What the RFC assumes but does not state

- That capacities span less than 12 orders of magnitude (finding 1).
- That two negative cycles are not both reachable, or that the cycle
  named does not matter (finding 2).
- That weights are finite (finding 3; the open question assumes it).
- Where a `.` form's answer goes (finding 6).
- The order of `graph.maxflow`'s two refusals (finding 8).
- That `graph.neighbors` includes the node itself when it has a self-loop
  (`GA:730` over `out`, built from `net.edges`).
- What the empty graph answers: `graph.toposort`, `graph.components` and
  `graph.scc` give `[ ]`, `graph.mst` gives `edges=[ ]`, `weight=0.0`, and
  every node-operand word refuses `unknown … node`. These follow from
  `GA:319-356`, `:391-403`, `:489-505`, `:201-204`, unstated.

## Disposition

**Not ready for Accepted.** Two places where the design gives a wrong or
misdescribed answer must be resolved first:

- **Finding 1**: `graph.maxflow` answers 1e13 where the flow is 1e13 + 5,
  and S5's own argument does not need the tolerance that causes it.
- **Finding 2**: S4 promises the smallest node on any reachable negative
  cycle and the code names one cycle's minimum.

Three more need register entries:

- **Finding 3**: the open question's stated condition has been met.
- **Finding 4**: "Current behaviour" is wrong about `graph.path`'s reader.
- **Finding 5**: an unrecorded crash in a word the RFC calls preserved
  exactly.

Findings 6–12 are text and test gaps, each with a concrete repair above.
