# RFC-0002 review 4 — 2026-08-26

Adversarial read of `docs/rfc/RFC-0002-symbols-and-words.md` at commit `e49ad04`.
Every `path:line` in the RFC was opened in this session at the pinned SHAs.

**Verdict: do not accept.** Not for D9, D14 or D29 — those are settled and the
RFC uses them correctly — and not for F18, F19 or F25, whose dispositions the
RFC now carries accurately. The blocker is a fourth defect the RFC dispositions
in its own preservation table instead of in the register, and a Preservation
analysis that describes F18's fix as an error-message change when it is also a
stack-state change, and describes the tier merge as free when the two tiers
have different function signatures.

## Blockers

### B1 — F26's disposition is empty, and the RFC takes it in the preservation table

`docs/registers/defects.md` opens: *"Leaving `disposition` empty blocks any work
item that would touch the area."* F26 ends:

> - `reference/rust_multistackvm/src/multistackvm_apply.rs:29-32`,
>   `multistackvm_call_internal_word.rs:7-8`, `multistackvm_inline.rs:71-72`
> - Behavioural, and a wrong source comment. Disposition:

Blank. And F26 carries an explicit consequence clause for this RFC — *"`$` is
not an escape from the name tables"* — exactly like F18, F19 and F25.

RFC-0002's header says **"Nothing gates this RFC"** on the strength of three
dispositions, and its preservation table then rules on the fourth itself:

> | `$` skipping the lambda check but not aliases (F26) | **Preserved exactly**, including the surprise. |

That is a defect disposition taken in an RFC rather than in the register. It is
the same move CLAUDE.md forbids for decisions — *"Never adopt an OPEN decision's
default silently"* — and the reason it matters here is that the RFC's own design
depends on the answer in two places: the `$`-honoured-at-dispatch rule and
criterion 6. It is also not obviously the right answer: F26 says the *source
comment* is wrong, which leaves open whether Bund2 preserves the behaviour and
fixes the comment, or fixes the behaviour to match the comment. The RFC picks
the first without saying a choice was made.

F26 is also the one the RFC leans on hardest: it is cited three times (§"`$`
skips the lambda check", the Slot rationale, and criterion 6's second probe).

**Fix:** record a disposition for F26 in the register, then cite it.

### B2 — F18's fix changes the residual stack, not only the error text

The RFC states the change twice, both times as text only:

> the message becomes the "too shallow" one — a behaviour change on fourteen
> words

> The fourteen words change error text, on inputs that error either way, and no
> golden covers them.

Take `pair` (`artefacts.rs:6-23`). It guards `< 1` at `:7`, pulls `x` at `:10`,
and only then fails at `:19`. So `1 pair` today errors with the stack **empty**
— the one value was consumed. Guarding at 2 fails before the first pull and
leaves the value on the stack.

That difference is observable, because Bund prints the stack with the error.
`print_error_from_str_with_vm` prints "Content of the stack" and dumps it
(`reference/Bund/src/stdlib/helpers/print_error.rs:126-132` and `:155-161`),
and `run_snippet_for_script` routes every eval error through it
(`reference/Bund/src/stdlib/helpers/run_snippet.rs:88`). It is captured in
goldens today —
`tests/golden/probes/execute-arm-not-executable.golden` ends with

```
[BUND]  Content of the stack
╭╮
╰╯
```

So the F18 deviation is: fourteen words, changed message **and** changed
residual stack, both of which appear in error output. The RFC's "only the
message differing" (inherited from F18's disposition text) understates it, and
it is the sentence a future reader would rely on when deciding whether a probe
is worth authoring.

### B3 — the two inline tiers have different signatures, and the merge does not say which one survives

The Design merges them in one sentence:

> The `native` binding is where the VM's `inline_fun` and the stack layer's
> `inline_fun` merge, which is what removes the fallthrough at
> `reference/rust_multistackvm/src/multistackvm_inline.rs:51-67`.

But they are not the same type:

- `pub type VMInlineFn = fn(&mut VM) -> Result<&mut VM, Error>`
  (`reference/rust_multistackvm/src/multistackvm.rs:8`)
- `pub type InlineFn = fn(&mut TS) -> Result<&mut TS, Error>`
  (`reference/rust_multistack/src/ts.rs:9`)

A stack-layer word receives only the `TS`. It is structurally unable to reach
VM state — the word table, the lambdas, `autoadd`, the alias table. Collapsing
both into `native: Option<NativeFn>` either widens 31 words' capability to the
whole VM or requires an adapter the RFC does not describe. And `NativeFn` is
one of the five types `bund2-api` promises stability for, so this is not an
implementation detail to leave open.

The RFC never states `NativeFn`'s signature anywhere.

## Citation defects

**D1. `execute.rs:32` does not contain the call.** RFC line 222:

> The live path is `VM::call` → `apply`
> (`reference/rust_multistackvm/src/multistackvm_call.rs:8`), which is what
> `execute` reaches (`reference/rust_multistackvm/src/stdlib/execute.rs:32`).

`stdlib/execute.rs:30` is `return vm.call(fun_name.clone());`. Line `:32` is
`_ => {`, opening the arm that bails with "not returned a proper function
name". The citation resolves, so `cite` passes it, and it is the eighth
consecutive review finding of that exact class.

Inherited: **F25 cites `execute.rs:32` twice** for the same claim
(`defects.md`, the "live path is unaffected" paragraph and disposition part 1).
D16 cites the range `:26-33`, which does contain `:30` and is fine.

**D2. "110 of those are `init_stdlib` registrations."** Measured: 119 total, of
which 110 sit inside a function named `init_stdlib`. But one of those —
`reference/Bund/src/stdlib/mod.rs:19` — locks and immediately drops
(`let bc = BUND.lock().unwrap(); drop(bc);`) and registers nothing. The count is
of sites in `init_stdlib`, not of registrations. Immaterial to the argument;
the argument (no in-word lock exists) is separately verified and holds.

**D3. RFC-0001 is misquoted in the `Rc`-not-`Arc` argument.** RFC line 482:

> A `Slot` holds a `BundValue` for its `lambda` and `class` bindings, and
> RFC-0001 defines `BundValue` as an `Rc<HeapValue>` whose `id`, `stamp` and
> `curr` are `Cell`s.

RFC-0001 `:233-239` defines `BundValue` as an **enum** — `Int`, `Float`, `Bool`,
`Nodata`, `None`, and `Heap(Rc<HeapValue>)`. The `Cell` fields are on
`HeapValue` (`:257-261`) and the first is named `identity`, not `id`. The
conclusion survives — a lambda or a class is always a heap value, so a `Slot`
that can hold one can never be `Send` — but the premise as written says every
`BundValue` is an `Rc`, which RFC-0001 explicitly denies (`:411`: "A scalar is
`Int(7)` until it acquires anything a header holds"). Since this paragraph is
billed as "the first real collision between RFC-0001 and RFC-0002", it should
quote RFC-0001 correctly.

**D4. `bund.pest:28` is quoted with the load-bearing half removed.** RFC line
408: "`name` is `element ~ nelement*` (`:28`)". The rule is
`name = @{ !("`") ~ element ~ nelement* ~ WHITESPACE+ }`. The negative
lookahead is precisely what D16's closing note calls out as reserving the
backtick for `ptr`. The `$println`-lexes-as-one-name conclusion is unaffected
and correct.

## Preservation analysis — behaviours the design changes that no row covers

The table has thirteen rows and is right about all thirteen. These are the
omissions.

**P1. Interning at dispatch grows the slot table where the reference's tables do
not grow.** The RFC says it plainly and then does not carry it into the table:

> Each interns through the same table, and interning a name not seen before
> **adds a slot** — that is what D16's open world means for this design

In the reference, dispatching a computed name that resolves to nothing adds
nothing: `get_alias`, `is_lambda`, `is_inline` and `TS::get_inline` are pure
reads that bail. Under RFC-0002 the same failed dispatch permanently adds a
`Slot` and a `String` to the interner. A program that builds names in a loop —
which D16 guarantees is legal, and which `execute` over a computed string makes
easy — grows memory monotonically where the reference does not. There is no
row, no bound, and no reclamation policy. This is the design's one genuinely
new failure mode and it is the one thing the Alternatives section's "Keep the
seven tables, index each by `Symbol`" would share, so it is not an argument
against the choice — but it needs stating.

**P2. Merging the tiers changes the error text of a failing or missing
stack-layer word.** `i_direct` returns a VM-layer word's error unwrapped
(`multistackvm_inline.rs:45`), but wraps a stack-layer word's in
`"VM inline function returned error: {}"` (`:59`), and wraps a stack-layer
*miss* in `"i({}) for stack returned: {}"` (`:64`) around `TS::get_inline`'s
`"Inline {} not registered"` (`ts_inline.rs:39`). F26's own probe quotes that
inner string. One slot table has one path and one message, so 31 words' failure
text changes. Not golden-covered today — `grep` over `tests/golden` finds no
occurrence of either wrapper — but observable, and error output is exactly what
the probe goldens capture.

**P3. F18's promised replacement message is wrong for eleven of the fourteen
words.** The RFC and F18's disposition both promise
`"Stack is too shallow for inline <word>()"`.

- `complex` guards with the literal `"Stack is too shallow for inline pair()"` —
  the wrong word name, copy-pasted (`rust_multistackvm/src/stdlib/artefacts.rs:27`
  against `:8`). Recorded in no defect entry; `docs/arity.md:119` lists `complex`
  without noting it.
- The ten string-family words bail with `"Stack is too shallow for inline {}"`,
  no parentheses (`Bund/src/stdlib/functions/string/distance.rs:25`,
  `regex.rs:15`, `regex_matches.rs:15`, `wildmatch.rs:15`).

Only `at`, `head`, `pair` and `tail` produce the form the RFC states — and
`head`/`tail` produce it through `err_prefix` (`values/value_carcdr.rs:17,22`).
If the deviation is worth recording at all, the recorded text should be the
text.

**P4. "Fallthrough … preserved in effect" rests on an unstated measurement.** The
row says "the words keep their names and meanings". That holds only because no
name is registered as an inline in both layers — verified: 31 stack names, 156
VM names, **empty intersection**. It is a property of today's registration set,
not of the design. Once both tiers share one `native` binding, a name in both
resolves by registration order where today the VM tier wins unconditionally
(`multistackvm_inline.rs:42` before `:52`), and D16's open world plus the
registry overlay make that reachable. The RFC should state the measurement and
say which rule governs a future collision.

**P5. Error `Location` rows name the reference's dispatch source.** Golden error
output carries a `Location` row with a `file:line` inside the very code
RFC-0002 replaces — `tests/golden/probes/execute-arm-not-executable.golden`
shows `.../rust_multistackvm-0.38.0/src/stdlib/execute.rs:97:21`. No row says
what becomes of that text, and it is the one part of error output that cannot
be preserved by construction. (It is also machine-specific — the recorded path
is under `/Users/gandalf/.cargo/` — which is a golden-portability problem
beyond this RFC's scope, but the dispatch half of it is squarely inside it.)

**P6. `generation: u32` can wrap.** It bumps on every rewrite of any binding in
a slot; `register`, `unregister`, `alias` and `unalias` are words, so a loop can
reach 2^32. A wrapped generation makes a stale inline cache validate — a silent
wrong-word dispatch. The RFC introduces generations as the thing that "makes
D16's permanently-open world affordable" and gives them no overflow policy.

**P7. `apply_in`'s divergences are enumerated as if exhaustively, and are not.**
The RFC gives two (no `$` arm; `autoadd` pushes the name whole). There are two
more: `apply_in` has **no empty-name check** — `apply` bails at `:13-15`,
`apply_in` goes straight to `is_command` at `:12` — and its catch-all operates
on the named stack via `pull_from_stack`/`push_to_stack` (`:63-72`) where
`apply` uses the current stack (`:90-99`). Immaterial, since nothing can call
it, but the section's claim is "it is **not** the same order" followed by a
two-item list introduced as the differences.

## What the RFC assumes but does not state

1. **`NativeFn`'s signature.** It is one of the five stable `bund2-api` types
   and appears in three `Slot` fields, and the RFC never defines it. See B3.
2. **What "two surfaces" means structurally.** Two crates, two modules, or one
   crate with a feature? Criterion 4 tests `cargo tree -p bund2-api`, naming
   one crate, while the Design says `bund2-api` "is **two surfaces**".
3. **That every dispatch consults the per-VM overlay before the frozen base.**
   The overlay must carry present-or-removed state per slot, so a lookup is an
   index into the base *plus* an overlay probe. The Motivation's "resolution is
   an index" and criterion 3's "0 allocations" are both stated against the base
   alone.
4. **That no name occupies both inline tiers.** True today; measured, not
   stated. See P4.
5. **That the interner is per-run, never reclaimed, and unbounded.** See P1.
6. **That `Symbol(u32)` bounds the word table at 2^32.** Fine on its own; it is
   the only bound in the design, and P1 is what makes it worth naming.
7. **That stack names are a namespace the slot table does not touch.** `TS` keys
   `stack` and `stack_cap` by stack name (`reference/rust_multistack/src/ts.rs:17,19`)
   and `VM` keys `vars`' outer map the same way (`multistackvm.rs:29`). The
   §"Seven name-keyed tables" enumeration counts word-name tables only, without
   saying so, and `CONTEXT` values are interned-looking names that are not word
   names.
8. **That `register_lambda`'s `is_type(LAMBDA)` validation
   (`multistackvm_lambdas.rs:8`) is preserved.** The Slot's
   `lambda: Option<BundValue>` admits any value; nothing says the check
   survives.
9. **That `bund2-syntax`'s parse-time interning and the runtime interning share
   one table across a `bund.eval` boundary that may reparse.** The RFC says
   "through the same table"; it does not say the table is owned by the registry
   the VM holds, which is what makes that true.
