## Should fix

### S1. The library-alone check's label map is named as step 5's, but `prepare_under` checks under the remapped map

**Location.** §P4 step 6, second bullet (lines 2582-2585): "under the same `CheckOptions` as `prepare_under`'s: … the same label map, the batch's labels that step 5 kept (`smysl-ingest/src/stage.rs:226`)".

**Problem.**
- `prepare_under` is given the labels step 5 kept, with the staged, pre-rule-M uids.
  - It remaps them to the uids rule M produced (`smysl-ingest/src/stage.rs:206-211`).
  - Its check runs under that remapped map (`:226`, the line the RFC cites), and `Staged::labels` returns that map (`:259-264`).
- So "the same `CheckOptions` as `prepare_under`'s" and "the batch's labels that step 5 kept" are different maps whenever rule M moves a labelled unit. An implementer who reads the second clause will pass the pre-remap map.
- The closure pass resolves a label to its bound uid without asking whether the store holds it. Its message names that uid: "the body references {o}, which is neither a dep nor a ground" (`smysl-check/src/passes/closure.rs:80,99-106`).
- Take a library unit whose body names `c/x` without declaring it, and a staged `c/x` on a unit `U` that rule M lowers to `U'`.
  - With the pre-remap map, the library-alone report holds an `SMY-E020` naming `U`.
  - The merged report holds an `SMY-E020` naming `U'`.
  - The multiset finds an added error, and the commit is refused. The design meant this label effect to cancel out: it is what r25's N1 asked both checks to share.
- At staging there is no step 5, so "the labels step 5 kept" does not say which map the staging comparison uses either.

**Suggested fix.** Say "the label map `prepare_under` checks under: `Staged::labels`, the labels step 5 kept as rule M remapped them (`smysl-ingest/src/stage.rs:206-211,226`); at staging, the staged value's `labels`". The library-alone check then runs after `prepare_under` returns, which step 6 already implies.

## Notes

**N1. "A message differs only where the batch changed what it reports, and that is an error the batch adds" is slightly too strong. The behaviour it defends is conservative and faithful.**
- `SMY-E030` names the weakest *present* ground: "{status} exceeds the cap of {cap} set by its weakest ground {weakest}". Ties are broken by ascending uid, and absent grounds are skipped (`smysl-check/src/passes/epistemics.rs:38-50,61-68`).
- Take a library unit that already has an `E030` and also a missing ground. A batch that supplies that ground can change the error's wording in two ways:
  - with an equal status and a lower uid, the message names the supplied ground;
  - with a lower status, the message gives a lower cap.
- The library-alone report then holds `(E060, G)` and the old `E030`. The merged report holds the re-worded `E030`. The re-worded error counts as added, so the commit is refused over a library unit's existing defect.
- SMYSL's `stage_or_commit` refuses the same batch, so the outcome is not a deviation. Only the sentence's claim is.
- **Fix:** add a clause: "or where the batch supplies a reference the library lacked, which can re-word an error the library already had (`SMY-E030` names its weakest present ground); that refuses, as SMYSL would".

**N2. "Both stagings check under the library's own granularity profile, as step 6 does" holds only if an answer's staged `granularity` is NODATA.**
- `opts.granularity` is not marked `smysl.ingest` only (line 2394), so `smysl.answer` accepts it.
- `answer` stages under `None` whatever the options say (`smysl-ingest/src/answer.rs:282-283`).
- The staged `granularity` is "the profile `opts.granularity` named" (line 2437). So an answer given `granularity` stages under the library's profile and commits under the named one: the split r25's S2 closed, reopened through the option.
- **Fix:** either make `granularity` `smysl.ingest` only (SM03 for `smysl.answer`, as for the other ingest-only keys), or say that an answer's staged `granularity` is always NODATA.

**N3. §P6's closing paragraph was not updated for the notify on a mark.** Line 2747 still says every writer "is woken at each release to test again". The bullet above it (lines 2733-2736) and the Preservation row (line 3144) both say "at each release and each mark". Align the paragraph.

**N4. Criterion 25's "And two cases that commit:" (line 3727) now heads four bullets, and two of them are refusals.**
- The dangling-ground bullet ends with two refused batches.
- The new `b3:` prefix bullet is a refusal only.
- Move the R47 and R48 refusals, and the `b3:` case, into the refused list above, or reword the lead-in to "And cases that turn on what the library already holds:".

**N5. Step 5's first label pass compares pre-remap uids, so it can drop a binding the library already holds.**
- Take a library that binds `c/x` to `U'`, the unit rule M will make of the staged `U`, while the staged value binds `c/x` to `U`. Step 5 drops the binding with a `Warning` naming two uids. Step 7, after the remap, would have found them equal.
- Nothing is lost, since the library keeps its binding, but the `Warning` reports a collision that is not one.
- The stated residue covers only the other direction: kept at step 5, dropped at step 7.
- **Fix:** a clause in the residue sentence, or step 5 could test against the library's binding with the remap applied. That is not available before step 6, so stating it is enough.
