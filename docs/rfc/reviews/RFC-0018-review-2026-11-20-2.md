## Should fix

### SF1. The logit's clamp is not R's −ln ε

§Current behaviour (`:154`) and the clamp table (`:488`) give the logit's bound as "η at ±`ETA_LIMIT`, R's −ln ε". R's logit is in C, and its behaviour is different (`src/library/stats/src/family.c:31-33`, `:83-84`, `:103`):
- R's threshold is ±30 in η, not ±36.04.
- Beyond ±30, `linkinv` jumps to ε/(1 + ε) or 1/(1 + ε), and `mu.eta` to ε.
- Between ±30 and ±36.04, R computes the logistic exactly, then jumps.

The value R saturates at is the logistic of ±(−ln ε), which is probably where `fit.rs`'s description comes from. But R's bound is not a clamp at ±36.04. `fit.logistic` clamps continuously at ±36.04, and the RFC is right to keep that for K15. The claim that this is R's is wrong.

It matters in one place. `fit.logistic` refuses separation at |η| ≥ 36.04, while R warns once μ is within 10ε of 0 or 1, about |η| ≥ 33.7 by `glm.R:322-325`. So `fit.glm` under logit refuses later than R warns, and under probit it refuses as R warns.

**Fix:** describe the logit row as `fit.logistic`'s continuous clamp at ±(−ln ε), with R's piecewise rule cited beside it as different. State that the separation thresholds therefore differ by link. `fit.rs`'s doc comment on `ETA_LIMIT` makes the same claim; that belongs to RFC-0015, not here, but the RFC should not repeat it.

### SF2. The inverse Gaussian's valid μ is not R's

§S4's family table (`:457`) gives the inverse Gaussian a valid μ > 0. R's `inverse.gaussian` sets `validmu <- function(mu) TRUE` (`family.R:537`). Its deviance (y − μ)²/(yμ²) is finite for a negative μ, so R does not halve when μ ≤ 0 and goes on with V(μ) = μ³ negative.

Requiring μ > 0 is the better rule, since the variance is meaningless otherwise. But it differs from R, and the column carries no citation; the reader takes it for R's. The Gamma's and the binomial's do match R (`family.R:468`, `:354`), as does the Poisson's (`:157`).

**Fix:** cite each family's `validmu`, and mark the inverse Gaussian's as this RFC's choice **[author]**, with the reason.

### SF3. Criterion 3 cannot observe step halving

Criterion 3 (`:790-791`) asks for "a stated model whose second or later step leaves the valid range". But no part of a fit records that a step was halved. §S4's answer has `iterations` and nothing like a count of halvings. So a test can check that the fit is right, but not that halving happened, and an implementation that never halves passes whenever the unhalved path also converges.

The model is also "found when the fixture is written", so no inspection can confirm that one exists.

**Fix:** either add a `halvings` INTEGER to the fit, or say the test reaches a crate-internal counter. Also state the model in the RFC, or name a source for one. The classic case is a Gamma or Poisson fit under `identity` with a fitted value near 0.

### SF4. `stat.lm` "Preserved exactly" has nothing that checks it

The Preservation row (`:694`) says `stat.lm`'s answers are preserved exactly, with "its tests pass unchanged" as the evidence. But `lm_against_the_fixture` compares `coef`, `se`, `t` and `p` at 10⁻⁸ and `r2` at 10⁻¹² (`infer/tests.rs:155-166`). `infer.snapshot`, which pins the plain tests' f64 bits, has no `stat.lm` line. Factoring `stat.lm`'s computation into a shared weighted function (M2) could change its last bits and every test would still pass.

Criterion 2 then compares `fit.lm` with the *refactored* `stat.lm`, so it can't catch the change either. RFC-0016 met the same problem with a snapshot recorded before its first change (its criterion 3; `infer/tests.rs`, the comment above `SNAPSHOT`).

**Fix:** have criterion 9, or M2's first step, record `stat.lm`'s and `fit.logistic`'s answers as f64 bits before any change, and compare after, as RFC-0016 did.

## Notes

- **N1.** `lm.R:673` should be `:673-674`. The default `weights = 1` is on `:674`.
- **N2. R also checks the starting values.** R stops on starting values that are out of range, "cannot find valid starting values: please specify some" (`glm.R:218-219`). For this RFC's families and links each `mustart` is valid, given §S4's response ranges and R's `initialize` rules. The RFC could say so in a sentence, so a reader does not look for a missing refusal.
- **N3. E114's text strains for a leverage of 1.** E114's text is "the answer overflows a FLOAT: <expression>" (`refuse.rs:125-126`). A leverage of 1 divides by zero, which is not quite an overflow. It is the code D250 B12 assigns, so it stays, but the `<expression>` should name the division, for example `Cook's distance at row 3, whose leverage is 1`.
- **N4. The tolerance margin is not a bound.** The 10⁻⁶ tolerance leaves "two orders of margin" over an estimate. That is honest as written. It belongs in the criterion's own text too, so that a failure at 10⁻⁶ is read as a reason to look and not as a bug proven.

## What the RFC assumes and does not state

- **U1. Bit-for-bit equality needs a particular arithmetic.**
  - `stat.lm` computes its RSS as `resid.dot(&resid)` (nalgebra) and its mean as Σy/n (`describe.rs:31-33`).
  - `fit.lm` reaches the same bits only if its RSS is the dot product of the √W-scaled residuals and its weighted mean is Σwy/Σw. With w = 1 both are then exact.
  - A loop summing wᵢrᵢ² can differ in the last bits from nalgebra's `dot`.
  - §S3 says r² "is computed as `stat.lm` computes" it; the same must hold for RSS, σ̂, `se`, `t` and `p`.
- **U2. A refusal while `model.anova` refits.** A submodel's refit can refuse where the full model does not: a first IRLS step out of range, or E110. The RFC doesn't say whether `model.anova` passes the refusal on as it stands, or names the row it was fitting.
- **U3. The null refit's first step.** The null model's refit starts from μ̂, so the first-step refusal (B3) applies to it too. This follows from the text but is not said.
- **U4. The model words' options reader also reads `na`.** It must give `na` the same texts `frame/opts.rs` gives it, since `model.matrix`'s and `model.predict`'s `na` refusals are meant to read as RFC-0017's.
- **U5. Separation and the Poisson zero test are checked once.** Both run once, at convergence, not at each step. A step that passes through μ near 0 and recovers is not refused.
- **U6. `fit.glm`'s answer differs by family.** It has a `t` key or a `z` key depending on the family (§S4), so a program reading one fit word's answer must test which key is present. That is stated for each family, but not as a consequence for programs, and the example (criterion 7) should show it.
