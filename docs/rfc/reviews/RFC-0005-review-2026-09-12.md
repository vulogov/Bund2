  (3,533 lines), as an adversarial reader.
- Date: 2026-09-12. This is the **twentieth** review; the nineteenth is

## What was checked, and how

**Every `path:line` citation was opened and re-read**, not taken from the RFC's
paraphrase. There are 36 distinct ones. All 36 resolve **and say what the RFC
says they say** — see *Citations* below for the itemised result. `cargo xtask
cite` agrees: 3,159 citations checked, 3,159 resolve, and none of its
advisories touches this document.

Beyond the citations, the claims the RFC makes about Bund2's own code by
function name were checked against the source: `Registry::follow`, `resolve`,
`effect_of`, `slot_mut`, `Slot::touch` and its six callers, `Slot`'s fields,
`NativeFn`, `tier0_floor`, `STACK_RESERVE`, `ASSUMED_BUDGET`, `EVAL_STACK`,
`main`'s thread spawn, `Guard::TopAreInt`, `alias`, `exact_int_float_ord`,
`ACTS_ON_HOST`, `PROMOTABLE.txt`'s header, `CONFORMANCE.txt`,
`DEVIATIONS.txt`, and the eighteen tests the RFC names by name. All eighteen
tests exist at the paths given and all pass today
(`cargo test -p bund2-stdlib -p bund2-interp -p bund2-ir -p bund2-value`:
27 + 3 + 169 + 52 passed, 0 failed). Conformance reads **105/113** with eight
approved deviations, so the ceiling of 105/113 is arithmetically right.
The golden counts in criterion 12 — 42 and 46 — reproduce exactly under a
**recursive** `grep` over `tests/golden` (121 files across four
subdirectories); a non-recursive one reads 29 and 33, which is worth knowing
the next time the figure is re-derived.

## Verdict

**Two blockers.** Both are about the same thing this RFC keeps re-learning: a
property asserted structurally in prose, where the code cannot carry the
structure and the set has to be enumerated instead.

**B1** is live and it is a D37 violation the RFC does not name. F118's fix
moved the *encode* ceiling by an order of magnitude and left the **decode**
side as the binding limit at ~6,000 levels, inside a dependency no worklist
reaches. `load.model` aborts there, and so does any SQLite `BLOB` — a third
shipped call site named in no register and in no RFC sentence, whose depth is
not a value the program built but bytes it read. Assumption 35 still describes
the codec as it was before the fix. The disposition F118 leaves to the owner
is open, and the RFC takes neither branch.

**B2** is §S6's generation mirror. The request cell got assumption 33 and a
derivation, `every_writer_of_the_request_cell_is_named`, precisely because the
seventeenth review showed an enumerated mirror-writer set could not be
trusted. The generation cells are the same mirror with a heavier failure —
an inlined fragment running a word's old meaning is a conformance move, not a
late body — and they have neither an assumption nor a scan. Worse, the
sentence that stands in for one, in §S6 and in D43 alike, cannot be
implemented as written.

The rest is in reasonable shape. The eighteenth review's B1 fix (§S4 keying
`$name` on the fixed point) is correct against `Registry::resolve` and
consistent with RFC-0002's criterion 6a as accepted. D33's resolution is now
consumed as RESOLVED in all three places the nineteenth review flagged. The
re-entry prose matches the derived set of 21 exactly. Criterion 28's palette
header now carries its three figures separately, as the seventeenth review's
S3 asked.

One item the nineteenth review raised is **still unfixed** and is recorded
below as S1, because the Status line claims it was fixed.

## B1 — the wire codec still aborts on the decode side, at a depth that comes from a file rather than from a value the program built, and assumption 35 describes code that no longer exists

Assumption 35 (line 2527) reads:

> the **wire codec** (`crates/bund2-value/src/wire.rs`, which recurses and
> aborts `save.model` at 3,400 levels — F118, open)

and the Status line (line 210) reads "the wire codec recursing on the way to
`save.model` (F118, open at 3,400 levels)".

Every clause of that is now wrong, and the clause that is missing is the one
that matters.

**It does not recurse.** `crates/bund2-value/src/wire.rs` is modified in the
working tree. `val_of` is gone — `grep -c val_of` returns 0. `from_value`
(`:135-150`) drives a queue and assembles bottom-up; `into_value` (`:227`)
reads an id-indexed flat node table; `wire_node_of` (`:343`) and
`take_wire_children` (`:413`) are worklist helpers, and `WireValue` has an
iterative `Drop` at `:403`. `wire::conversion_tests::a_deeply_nested_value_survives_the_wire`
passes.

**`save.model` does not abort at 3,400.** F118's own status
(`docs/registers/defects.md:3836-3854`) reads **PARTLY FIXED 2026-09-12** and
records the measurement: encode survives 38,000 and aborts at 40,000.

**The half that still aborts is the one the assumption never names.** The
same table records the decode direction aborting at **6,000** and surviving
5,500 — "bincode's derived `Deserialize` builds the nested `WireValue` before
any Bund2 code runs, at roughly 1.4 KB of stack a level on an 8 MiB thread …
A worklist cannot reach inside the dependency." So the codec is still a D37
violation; the level just moved, and it moved to the direction the RFC does
not mention at all.

**And it has a third shipped call site, which no register names.**
`bund2_value::wire::from_binary` is reached from three places in shipped code:

| site | direction | where the depth comes from |
|---|---|---|
| `crates/bund2-stdlib/src/world.rs:86` | encode | the value the program built |
| `crates/bund2-stdlib/src/world.rs:138` | decode | **a world file on disk** |
| `crates/bund2-stdlib/src/data.rs:326` | decode | **a `BLOB` column in any SQLite database the program opens** |

The third is `sql_cell`, reached through `run_sqlite` — a function
`every_reentering_function_is_named` already names, so it is squarely inside
the RFC's own path set for other purposes. Neither F118, nor D39's dated
notes, nor any sentence in this RFC mentions it. A database a program opens is
third-party input: its nesting depth is not chosen by the Bund program at all.

**That is also why D39's rule does not reach this.** The 2026-09-11 note states
it as "**no Rust recursion may be driven by the depth of a value a program
controls**" (`decisions.md:2221-2223`). A world file written by another
process, or a `BLOB` in someone else's database, is not a value this program
controls, and the rule as phrased exempts it. The 2026-09-12 note narrows the
gap by naming the dependency, but it does not restate the rule.

**The disposition is open and the RFC takes neither branch.** F118
(`defects.md:3867-3871`) leaves the owner a choice: "Either the codec takes a
bound that reports on both directions, as F116's parser does, at a depth under
the measured decode limit; or that limit is recorded as a known ceiling and a
value deeper than it aborts on `load.model`." D39's second note agrees the
choice "is still open". CLAUDE.md: *"Never adopt an OPEN decision's default
silently."* Assumption 35 as written adopts neither — it records a state of the
code that has been superseded, which is worse than recording either branch.

### What would answer it

Assumption 35's wire-codec clause has to say three things it does not: that
the codec is arena-built in both directions since 2026-09-12; that the
**decode** side is the binding limit at ~5,500–6,000 levels and is inside
bincode; and that `load.model` and `sql_cell` are its reachable sites, the
second decoding a `BLOB` whose depth the program does not choose. Then it has
to name F118's open disposition as blocking, rather than assert a state.

If the owner takes F116's branch — a bound that reports — the RFC should say
so and add it to the same Preservation row F116 occupies, since a bound that
refuses a world file is observable where an abort is not. If the owner records
the ceiling instead, D37's "evaluation never aborts" acquires a stated
exception, and that belongs in `decisions.md` before the RFC rests on it.

Either way, the Preservation row that currently reads

> **a value's teardown recursing on its depth** … `Drop for HeapValue` walks
> the levels through a worklist instead (F115); assumption 35

needs a sibling row for the codec, because it is the one member of the six
whose fix did not close it.

## B2 — §S6's generation mirror has no stated property and no derivation, and the sentence standing in for one cannot be implemented as written

§S6, *Addressing* (lines 1465-1467):

> - a **generation cell per name**, mirrored from the registry `Slot`'s counter
>   **by the same `touch()` that bumps it**, and allocated in fixed-size chunks
>   that never move when more are added;

D43 repeats the phrase verbatim (`decisions.md:2549-2552`): "a mirror of each
registry `Slot`'s generation, written by the same `touch()`".

**`Slot::touch` cannot write the mirror.** It is
`fn touch(&mut self)` on `impl Slot` (`crates/bund2-api/src/lib.rs:521-523`),
a private method whose whole body is
`self.generation = self.generation.saturating_add(1);`. It has no `&self`
Registry, no `Symbol`, and no way to reach the cell chunks — which §S6 itself
says belong to `Registry`, "so `Registry` grows an accessor that hands out a
name's cell". A `Slot` does not know its own name. So the mirror write cannot
live in `touch()`. It has to live in each of the `Registry` methods that call
it:

| method | line | field written |
|---|---|---|
| `register_native` | `:894`, touch at `:904` | `native` |
| `register_lambda` | `:911`, touch at `:915` | `lambda` |
| `register_alias` | `:919`, touch at `:924` | `alias` |
| `unregister_alias` | `:929`, touch at `:935` | `alias` |
| `register_command` | `:977`, touch at `:987` | `command` |
| `unregister_lambda` | `:995`, touch at `:999` | `lambda` |

(Those are the only six `touch()` call sites outside tests, and the only six
writes to a `Slot` binding anywhere — verified by grepping every
`.native = / .lambda = / .alias = / .command =` in the workspace. `slot_mut`
is private and no `pub fn` hands out a `&mut Slot`, so the set is closed
today. The §S6 sentence listing those six writers is therefore **correct**;
it is the mechanism sentence that is not.)

**So the property is an enumerated set, which is exactly what the seventeenth
review showed cannot be trusted.** The RFC's own account, at line 199:

> assumption 33 named one writer of the request cell where the code had three,
> so it could not enforce what it was added for

The answer was assumption 33 plus `every_writer_of_the_request_cell_is_named`
(`crates/bund2-interp/src/lib.rs:1713`), which derives the set by scanning and
fails when a fifth appears, and states its own three blind spots. The
generation mirror is the identical pattern:

- it is a cell at a stable address that compiled code reads;
- it shadows state `bund2-api` owns;
- a write that reaches the `Slot` and not the mirror leaves the mirror behind,
  "with nothing to notice" — assumption 33's exact phrasing.

and its failure is **strictly worse**. A stale request cell runs a body late.
A stale generation cell lets an inlined `+` keep adding integers after `+` has
become a lambda, an alias or a command — the failure §S6's meaning guard
exists to prevent, the risk the Preservation table's third row assigns to
criteria 5 and 17, and a movement in `cargo xtask conform` under
`--features jit`, which §S2 forbids outright.

Criterion 5 does not close it. It tests the ways §S4's chain lets a name change
meaning *that the RFC already knows about* — re-registered as a lambda,
aliased, unregistered, registered as a command. A seventh `Registry` method
added later, or a mirror write forgotten in one of the six, is precisely the
case a hand-written criterion cannot reach; that is the argument the RFC makes
for itself in §S8 about the re-entry set ("the set is derived, not listed,
because a list went stale within a day") and in assumption 33.

### What would answer it

Three things, and the first two are edits this RFC can make on its own:

1. **Correct the mechanism sentence** in §S6, *Addressing*, and note that D43's
   matching phrase needs the same correction. Either the mirror write lives in
   the six `Registry` methods beside each `touch()` call, or `touch` moves onto
   `Registry` as `touch(&mut self, s: Symbol)` so that one function does both —
   which is the structural answer, and the one CLAUDE.md's preference order
   asks for ("make the invariant structural … it removes the question").
   If the structural answer is taken, say so, because then no derivation is
   owed and the set stops mattering.
2. **State the property as an assumption**, in the shape assumption 33 uses:
   *no code writes a `Slot`'s generation without writing that name's mirror
   cell*, with its blind spots named.
3. **Derive it**, with a scan beside the other three
   (`every_writer_of_the_request_cell_is_named`,
   `every_reentering_function_is_named`, `no_native_reports_at_error_severity`),
   failing when a seventh writer appears. It can be written **now**, against
   `touch()` call sites, before any cell exists — which is the same thing
   criterion 24's Tier 0 half does.

Alternatively the owner may rule that option 1's structural form is the whole
answer, in which case say which, since D43 is RESOLVED and its text would be
amended rather than reinterpreted.

Carried unfixed from the nineteenth review's S1. Line 211 claims:

> **S1–S4**: F116's status reads FIXED in all three places

Line 2089 still reads:

> and parsing a deep run-time string (F116, **open**), assumptions 34 and 35.

F116's status is `FIXED 2026-09-11` (`defects.md:3755`). The other three places
— lines 189, 2513 and the Preservation row at 2666 — are correct, so the

This matters beyond the word. A Status line that certifies a correction it did
not make is the one sentence a later reader has no reason to re-check, and B1
above is a second instance of the same shape in the same paragraph. Both were

### S2 — the claim that `Slot` holds "six independent bindings" is not what the code holds

Line 668:

> Bund2's registry `Slot` holds six independent bindings
> (`crates/bund2-api/src/lib.rs`, `Slot`), and the `unregister` word clears the
> lambda alone

`Slot` declares six fields — `command`, `alias`, `lambda`, `native`, `class`,
`method` (`:503-508`) — but **`class` and `method` are never written**. There
is no `.class =` or `.method =` anywhere in the workspace. `register_class`
(`:707-710`) writes `self.classes`, a separate map, and bumps
`class_generation`; `register_method` (`:857-860`) writes `self.methods` and
bumps `method_generation`; `oop_generation` (`:871`) hands out that pair. So a
`Slot` carries **four** live bindings, and class and method resolution does not
pass through it at all.

The conclusion §S4 draws from the sentence — that `unregister` clears the
lambda alone, so unregistering a lambda reveals the native — needs only
`lambda` and `native` and survives. But the sentence is load-bearing elsewhere
in a way that is easy to miss: §S6's meaning guard is built on the claim that
each writer of "a binding §S4's chain consults" bumps the slot's generation.
That is true and tight for the four live fields. If a later change made `class`
or `method` real on the `Slot`, the generation would cover them by accident and
the `class_generation`/`method_generation` pair would silently become a second,
uncoordinated counter — which is B2's failure with a different name.

Say four, and say where class and method actually live and what generation
covers them. Two dead fields on a struct the RFC cites by name are also worth
a line in `defects.md`.

### S3 — assumption 33's blind-spot list is missing a fourth, and §S8 invites the reader to assume otherwise

Assumption 33 states three things
`every_writer_of_the_request_cell_is_named` cannot see: it reads one file, it
cuts at the first `#[cfg(test)]` module, and it matches two spellings. There is
a fourth. Its head parser is

```rust crates/bund2-interp/src/lib.rs:1739
                let head_ok = t[..at]
                    .split_whitespace()
                    .all(|w| ["pub", "const", "unsafe", "async", "extern"].contains(&w));
```

`contains(&w)` is an **exact** match, so `pub(crate) fn` or `pub(super) fn`
fails `head_ok`, `current` is not updated, and a `pending_tail` write inside
such a function is attributed to whichever function was parsed last — a silent
misattribution, not a failure.

The sibling scan does not have this problem:
`every_reentering_function_is_named` uses
`QUALIFIERS.iter().any(|q| w.starts_with(q))`
(`crates/bund2-stdlib/src/lib.rs:698-700`), and its comment says so.

§S8 makes the gap easier to fall into, because it credits the *other* scan
explicitly — "reads a function head whatever its qualifiers (`pub(super)`,
`const`, `unsafe`, `async`)" — so a reader carries that property across to
assumption 33's scan, where it does not hold.

Today nothing breaks: `crates/bund2-interp/src/lib.rs` contains only `fn ` and
`pub fn ` heads, verified. But assumption 33 exists to survive the file
changing, and "nothing enforces it" is the standing state of assumption 27 for
the same reason. Either state the fourth blind spot, or make the two scans
share the head parser — which would be the structural answer and would remove
the assumption.

### S4 — `Registry::follow`'s bound is 65 links, not 64, and §S4 now states the number

Line 580:

> `Registry::follow` walks the chain until it runs out of links — **or until 64
> of them**, D39's bound against a cycle `alias` can build, after which it
> answers the last link it reached

The loop increments `guard` after taking a link and breaks on `guard > 64`
(`crates/bund2-api/src/lib.rs:1017-1022`), so it follows **65** links before
stopping. The nineteenth review's S5 asked for the bound to be stated rather
than for `follow` to be called a fixed point, and the RFC did state it — with
the number one short.

It is a single link and no program reaches it, but the sentence is now the
document's statement of where the fixed point stops existing, and §S4 rests a
meaning claim on it ("A chain past 64 links therefore has no fixed point, and
what Tier 0 answers there is part of its meaning"). D39's own note cites
"`follow`'s 64" as one of its thresholds, so both would be adjusted together —
or `follow` changed to `guard >= 64`, which is the cheaper fix and makes the
prose true everywhere.

### S5 — the residual path needs a source-value index per call site, and nothing says so

§S5, *After any call*:

> It syncs every promoted value to **the stack it was taken from** … and then
> applies the rest of the body's values one at a time through the runtime's
> `apply`, exactly as Tier 0 would.

"The rest of the body's values" is a position in the body's
`Vec<BundValue>`. The compiled function's ops are not in bijection with those
values: §S6 inlines fragments, promotion elides pushes, and criterion 10's
spike records Cranelift **folding** `1 2 +` outright and merging the guards'
cell loads between them. So the lowering must carry, for every point at which
the residual path can be entered, the index into the body at which
interpretation resumes.

The design makes that tractable — residual entry is only *after a call*, and
a call is a point at which every promoted value below the callee's arity is
either synced or provably live, so no folded region spans one. But that is an
argument the RFC does not make, and the obligation on the lowering is
never stated. Criterion 21 tests behaviour on six named programs; it would
pass a lowering that resumed at the wrong index on a seventh.

This belongs beside assumption 5 (which already states that the residual
path's `apply` is `Vm::apply`): *a compiled body carries a map from each call
site to the index in its source body at which the residual path resumes, and
no folded or inlined region spans a call site.* Criterion 21 can then assert
the side table rather than only the stacks.

### S6 — the workbench is never said to be outside promotion, and 59 workbench natives are on `PROMOTABLE.txt`

Promotion is described throughout in terms of stacks: values "held in
`Variable`s are synced back to the real stack", "each to the stack it was
taken from", the current-stack epoch, `Stack::push`'s path for the tag. The
workbench appears only as something *audited* — criterion 28's palette runs a
workbench form, `debug.display_workbench` is an observer kept off
`PROMOTABLE.txt`, assumption 7 mentions it.

Meanwhile `tests/golden/PROMOTABLE.txt` lists **59** `.`-suffixed natives —
`+.`, `car.`, `make.call.`, `convert.to_int.` and the rest — every one of which
takes or leaves an operand on the workbench. `+.` declares `eff(1, 0)`
(`crates/bund2-stdlib/src/math.rs:490`), which is honest about the *current
stack* and silent about the workbench, and that is the convention the audits
check.

I believe the design is sound as intended — promotion holds only values the
compiled body would have on the current stack, `Guard::TopAreInt` reads the
stack, and a workbench operand is always synced because it was never in a
register. But the RFC never says it, and the phrase "the stack it was taken
from" reads naturally as including the workbench. A reader implementing §S5
from this text could reasonably promote a value destined for the workbench and
find no epoch, no sync rule and no barrier for it.

One sentence in §S6, and an assumption: *the workbench is never a promotion
source; a `.`-family native's workbench operand is always on the workbench when
it runs.* Then `PROMOTABLE.txt`'s 59 workbench natives are unambiguous.

## Minor

1. **Criterion 11's 2 ns does not decide anything.** The criteria preamble
   lists 11 among those that "carry a number", but the number is used as
   "A check costing more than 2 ns per body entry **should be reconsidered**
   against simply not promoting bodies that can recurse". A criterion whose
   number triggers a reconsideration rather than a failure is the shape the
   RFC itself rejected in criterion 7 ("shows improvement, which nothing can
   fail"). Criterion 17's identical bound is stated as "must stay under 2 ns",
   which is checkable; 11 should borrow that wording or drop the claim to
   carrying a number.

2. **"D39's dated note" is singular where D39 has two.** Line 210-211 credits
   "D39's dated note" with "the rule all six share". The note that *states the
   rule* is dated 2026-09-11 and names three (`decisions.md:2201-2223`); the
   note that covers six is dated 2026-09-12 and restates none of the rule
   (`:2225-2245`). True enough if the second is meant, but the nineteenth
   review's S4 raised this at four and it now reads six, so naming the date
   would settle it.

3. **Criterion 12's re-derivation needs `grep -r`.** Stated above: 42 and 46
   are right, and reproduce only recursively. Putting `-r` in the parenthetical

## Acceptance criteria — is each checkable, and by what

Thirty criteria. Twenty-eight name a tool and a boolean or a number that can
fail. Two do not, fully:

| # | decided by | verdict |
|---|---|---|
| 1 | `cargo bench -- value/push_pull` < 20 ns | checkable; **Met**, 9.47 ns |
| 2 | `cargo xtask conform` ×3, same N/M **and CEILING**, plus a non-zero compiled-body count | checkable; two of three run, 105/113 both ways; the third needs `--jit-threshold`. The compiled-body count is what stops it being vacuous, and it is stated |

## Preservation analysis — completeness

The table is 44 rows and is the most thorough part of the document. Every risk
I could construct from §S4–§S8 has a row, including several I expected to be
missing (`unregister` revealing a shadowed native; a body compiled under one
`Interp` run by another; mint order once a guard widens; the wrapping of
`eval_lambda`'s error by `times`).

Three behaviours the design could change are **not** enumerated:

1. **The codec's decode direction** (B1). The table has a row for teardown
   (F115) and one for rendering (F117), and the row for the parse (F116). The
   codec — the sixth of the six, and the only one whose fix did not close it —
   has no row at all; it appears only inside assumption 35.

2. **The residual path's resume point** (S5). The table's current-stack-switch
   row says "the residual path syncs each value to the stack it came from",
   which is the sync half. Resuming at the wrong *value* is a distinct failure
   with a distinct guard, and nothing names it.

3. **A workbench value held across a call** (S6). If promotion is stack-only
   the row is "cannot arise, and here is why"; if it is not, the row is a
   missing epoch. Either way the table should say which, since it has rows for
   the analogous named-stack case (`swap_in`, `move_from`) and for
   `debug.display_workbench` via criterion 14.

One row I checked and found correct where I expected otherwise: *"a native that
reports with a stack snapshot while values below its arity are promoted"*. The
snapshot really is taken from the interpreter's own current stack and workbench
at `Vm::report` (`crates/bund2-interp/src/lib.rs:1236-1255`), not from the
reporting native, and it really does consult `wants_stack(d.severity)` — so
D45's per-severity answer is what gates it, as the row says.

## Consistency with accepted RFCs and with ERRATA

- **RFC-0002, criterion 6a** — checked at `docs/rfc/RFC-0002-…:698-703`. It
  asserts that a two-deep chain resolves the same way through `$name` as
  through `name`, and records the reference's shallower answer as the
  deviation. §S4's rewritten `$name` rule, its slot rule and the Preservation
  row now all key on the fixed point and cite 6a. The eighteenth review's B1 is
  correctly answered, and `Registry::resolve` (`bund2-api:1034-1051`) does what
  both say: `follow` first, then the sigil selecting only whether `lambda` is
  consulted. No inconsistency.
- **RFC-0003, criterion 2** — cited by number rather than by line, as §S8
  explains, and the reason given (amendments move the lines) is the right one.
- **RFC-0004 §S1** — the amendment of 2026-09-09 withdrawing "a `Fold` or an
  `Opaque` site bails to Tier 0" is consumed correctly, and §S6's 116/21 count

- **ERRATA** — the §2.1 expectation-table supersession is recorded

  §S1's treatment matches the ERRATA entry rather than contradicting it.
- **D12, D16, D9 as amended, D10, D32/Q35, D33, D35/Q32, D37, D39, D41–D49,

## What the RFC assumes but does not state

Thirty-six assumptions are stated, which is more than most documents manage.
These are the ones I could not find:

1. **Every writer of a `Slot`'s generation also writes that name's mirror
   cell.** B2. The counterpart of assumption 33, missing.
2. **The workbench is never a promotion source.** S6.
3. **A compiled body carries a resume index per call site, and no folded or
   inlined region spans one.** S5.
4. **Nothing hands out a `&mut Slot`.** §S4's six-binding claim and §S6's
   generation argument both need the `Slot` write set to be closed. It is
   closed today only because `slot_mut` is private and `slot()` returns `&Slot`
   — but all six fields are `pub`, so one `pub fn slot_mut` added later opens
   it with nothing to notice.
5. **`Registry::follow`'s bound is a Bund2 choice with no oracle behind it.**
   §S4 says a chain past the bound "has no fixed point, and what Tier 0 answers
   there is part of its meaning" — i.e. Bund2's answer at link 65 is meaning
   that no golden pins and no reference behaviour corresponds to. That is a
   defensible position and it is not stated as one.
6. **The decode side of any codec is program-independent input.** B1. D39's
   rule is phrased for "a value a program controls"; nothing states that the
   same hazard exists for depth Bund2 *reads*, which is where F118's live half
   now sits and where `sql_cell` sits with it.
7. **`json`/`json.to_value` recurse on JSON depth, bounded only by
   serde_json's own limit.** `to_value` (`crates/bund2-stdlib/src/json.rs:99-132`)
   recurses per JSON level, on a value built from a run-time string at `:82`.
   It is safe today only because `serde_json`'s deserializer enforces its own
   recursion limit before `to_value` ever sees a deep tree — a property of a
   dependency, unstated here, and exactly the shape F118 shows can move when a
   dependency's behaviour is the bound.
8. **`--raw-values` renders through `render`, not through `Debug`.**
   `Interp::report` uses `v.render(false)` when the reporter wants raw values
   (`crates/bund2-interp/src/lib.rs:1242`), which is F117's iterative renderer,
   so assumption 36's claim holds. But `BundValue`, `Payload` and `HeapValue`
   all `#[derive(Debug)]`, and a derived `Debug` on a recursive payload is an
   eighth walk that assumption 35 does not list. It is unreachable from shipped
   code today — the only `{:?}` on a value in `bund2-stdlib` outside tests is
   `json.rs:61`, which formats a `JsonPathValue` and is **faithful to the
   oracle** (`reference/rust_multistackvm/src/stdlib/json/json_path.rs:37`
   has the identical line). Worth one clause in assumption 35, because "seven"
   is asserted as a closed set and the eighth is one `{v:?}` away.
