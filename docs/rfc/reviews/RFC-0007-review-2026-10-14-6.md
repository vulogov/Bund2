## Significant

### S1 — A host VM's program output goes to the process's one standard output, and no row says so

The Preservation table has a row for where a host VM's *diagnostics* go
(`:694`): `SilentReporter`, unless the embedder installs one. It has a row
for process-global state (`:666`) naming `GENERATORS` as "a second medium
between VMs beside the bus", with `MT`, `CHACHA` and `ARGS`. Nothing in the
table or in §C8 says where a host VM's *output* goes.

It goes to standard output. `println` and every other printing word write
through `bund2_api::outln!`, which is `out::stdout`
(`crates/bund2-api/src/out.rs:29-37`, `:57-60`): `std::io::stdout().lock()`,
then the text and a newline under that lock. The handle is the process's,
not the VM's. So under §C8's host:

- N VMs' `println` lines interleave on one stream, whole lines at a time
  because the lock is held across text and newline, and in whatever order
  the threads reach it. That is a third medium between VMs beside the bus
  and the generators, and the only one a reader of the process sees.
- An embedder cannot route one VM's output anywhere else. The reporter seam
  (D36) is per `Interp`; the output seam is not a seam at all. The row at
  `:694` says "An embedder installs its own on `rt.interp.reporter` inside
  the closure", which is true of diagnostics and has no counterpart for
  output.
- Criterion 13's "an executor driving two VM façades makes progress on
  both" is tested with values, not output, so nothing in the suite has two
  VMs print.

The reference cannot exhibit this — one VM, one process — so it is design,
not preservation, and belongs in the table as §C8's other rows do. The
module doc of `out.rs` says "a word's output is the program's"; under a
host, whose program is the question. One row, and a sentence in the §C8
note on `bund2-async` saying that what the host does not give an embedder
includes a per-VM output stream. Whether it should is RFC-0000's embedding
question, not this RFC's; the row is owed either way.

### S2 — The seventh review's assumptions and lacking rows were not answered, and the one re-measured here is still true

The seventh amendment (`:1329-1363`) answers B1, S1 to S4 and M1 to M7. It
has no paragraph for the review's five "rows the table lacks" or its ten
assumptions, where the third, fourth and fifth amendments each had one.
Three of the five rows arrived by other routes (D27, the depth writers, the
`image` words in the §C3 note) and one is moot (D168 removed the feature).
The remaining row and its assumption are unanswered:

> **A refused `save` under a name no world had**: the oracle's succeeding
> `save` leaves a populated file; Bund2's refused `save` leaves an empty
> redb file, because `open_world` creates before the transaction begins.
> "The world as it was" is the file's tables, not the file's existence.

Measured again today, release builds, `dict "k" '{"k": 1}' json set
"fresh8" save` under a name no file had:

| engine | result | `fresh8.world` afterwards |
|---|---|---|
| Bund2 | `Aliases SAVE returns: Error converting data to blob: the value holds a JSON value …` | **20,480 bytes**, created by `Database::create` (`world.rs:52`) before `begin_write` (`:639-641`) |
| oracle | `after save` | 32,768 bytes, populated |

The file's existence is not visible through the words: `"fresh8" load`
after the refused save answers `Aliases LOAD returns: Error compiling
ALIASES select: … no such table: ALIASES`, the same text as a `load` of a
name never saved, because `load` creates the file too — as the reference's
`Connection::open` does (`world.rs:49-50`). So this is the shape the
reference's own `load` has, and not a new one. But D167's built section
says "the dropped transaction is rolled back … and the file is as it was"
(`decisions.md:3732-3733`), and the row at `:715` says "leaves the world as
it was". For a fresh name the file was absent and is now present. The
sentence is true of the tables and false of the file, which is the
distinction the seventh review drew and nobody recorded. One clause in the
row.

Also unanswered from that list, and stated here so the ninth review need
not: assumption 8, that a redb write transaction over four tables commits
atomically — redb's contract and D27's reason for choosing it ("ACID",
`decisions.md:1262`), relied on and not stated; assumption 9, the `many`
family, which the `dup` row still says "is not measured".

## What the RFC assumes but does not state

1. **A host VM's output belongs on the process's standard output.** It
   goes there; nothing says that is intended (S1).
2. **"The world as it was" means the tables.** For a fresh name the file is
   created before the transaction (S2).
3. **A redb write transaction over four tables commits atomically.**
   redb's contract and D27's reason; relied on by D167 and stated nowhere
   in the RFC (the seventh review's assumption 8, carried).
4. **The `many` family behaves as `dup` on both sides.** Stated as not
   measured; left so (the seventh review's assumption 9, carried).
5. **The reference's `None` arm at `crossbus.rs:19` is reachable.** It is
   not (M3); the row's wording assumes it.
6. **Identities are unique across VMs.** True, because the minter is one
   process-wide atomic (M4); "mints a fresh identity" at `recv` rests on it.
7. **One log threshold per process is acceptable for a host.** `LEVEL` is
   read once from the environment; a host cannot give two VMs two levels
   (M4).
8. **`cast_string` accepts only a STRING on the reference**, so Bund2's
   `as_str()` in `name_of` (`bus.rs:123-127`) matches it. Checked:
   `reference/rust_dynamic/src/cast.rs:33-40` returns the string for
   `Val::String` and errs on everything else. The cast row holds; the
   assumption was not written down.
9. **The `stack` tag of a received value is the receiving push's on the
   reference too.** Checked today: `ts_push.rs:25,51` sets the tag on every
   push, and the oracle reads `"stack": "b"`. The row rested on a golden
   that could not show it.
