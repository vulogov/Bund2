# RFC-0014 review: Draft revision 11, 2026-11-03 (tenth review)

Adversarial review, independent of the nine before it. The RFC and the
sources were read first, and the earlier reviews only afterwards, to drop
findings already raised and answered. Nothing was edited or built, apart
from running `cargo xtask cite`. Read against Bund2's working tree at
ca20110, the `reference/` submodules (whose `git status` is empty), and
SMYSL at 4f5ecb9 ("Merge 1.14.0"), opened file by file. SMYSL citations
are relative to its crate directory, as the RFC writes them. Revision
11's changes were checked hardest: SM07 against SM02 for a held lock;
`smysl.create`'s order; the label MAP and how SMYSL's parser produces
labels; SM08 for an unbound label; the over-cap text with `flag` none;
the empty-marker statements; §S9's steps 6–8; the `--noio` constructor
stub; criteria 15 and 18 and the plan's placement of each case. The label
claims were followed into `parse_surface`'s resolution pass, its record
emission, `WriteContext::from_labels` and `labels.rs`.

**Verdict: Ready once the should-fix items are answered. 0 blocking,
4 should-fix, 9 notes.** D244 and D245 are not re-argued. Revision 11's
answers to the ninth review's S1, S2 and S4 hold against the source. Its
answer to S3 rests partly on the ninth review's own misreading of SMYSL's
parser, and leaves one of S3's requests unanswered. The should-fix items:

- SMYSL's parser emits every label binding twice, as a map and as
  `Record::LabelBinding` records, and the RFC names only the map; whether
  a parsed unit MAP carries `labels` is also unstated, and if it does,
  revision 11's new SM03 refuses criterion 5's own round trip (S1);
- nothing says how `smysl.append` tells a label MAP from a unit or
  relation MAP, or what a MAP that is none of the three is (S2);
- `smysl.parse` has no stated behaviour for SMYSL's error diagnostics,
  its recovered records, or a `ParseError` (S3);
- `bund2 check` can reach the new `"smysl"` arm only if the constructor
  declares `Leaves::Conditional("smysl")` (D181), which the RFC does not
  say, so criterion 18's `bund2 check` case fails as written (S4).

  (`smysl-core/src/surface/mod.rs:12`); its label map's uids are
  `canonical_uid` of the very core it pushes as `Record::Unit`
  (`parse.rs`, `resolve`, about 2871-2873). So for a unit whose MAP form
  is lossless, the uid `smysl.parse` puts in a label MAP is the uid

- **Bund2.** `csv_disabled` and the `noio` arm of `register` in

- **`smysl-core/src/surface/parse.rs:12-14,63`** is cited for "SMYSL's
  parser resolves a document's labels to uids itself and returns them as
  a map beside the records". It does resolve them, and `:63` is the map.
  But the same pass also emits each entry as a record: "Emit the bindings
  as records, so a label reaches the log rather than living only in
  `ParseOutcome`" (`parse.rs:2596-2606`), looping over the map it then
  stores as `out.labels` (`:2793`). The labels are in the records too,
  not only beside them. See S1. The ninth review's S3 said the bindings
  were "off the records" (its `parse.rs:12-13,44,63`), and revision 11
  built on that.
- **`smysl-graph/src/labels.rs:3-8`** is cited at §S4 for "A label bound
  to several units, or to none … is SM08". Those lines are about several
  units only. The "none" half is grounded by the `:20-29` citation in the
  same sentence, so the claim holds; the `(:3-8)` placement reads as if
  it covered both.

## Should fix

### S1. SMYSL's parser gives each label twice, and the RFC does not say which `smysl.parse` uses, nor whether a parsed unit MAP carries `labels`

§S4's `smysl.parse` row says:

> SMYSL's parser resolves a document's labels to uids itself and returns
> them as a map beside the records
> (`smysl-core/src/surface/parse.rs:12-14,63`); each entry becomes a
> label MAP with that uid … Any other record (a view, a schema
> declaration, a thread, a manifest, a commitment, …) has no §S2 form. It
> is skipped, and one `Warning` per record kind names how many were
> skipped.

and §S2 adds, new in revision 11:

> **A unit MAP's `labels` key is read-back only.** On write it is SM03 …

**Evidence.** `ParseOutcome.records` holds a `Record::LabelBinding` for
every entry of `ParseOutcome.labels`: the parser pushes one per entry
after the units (`parse.rs:2596-2606`) and then stores the same map
(`:2793`). §S2's table has a form for that record (the label row, citing
`LabelBinding`). So `smysl.parse`, walking `records` as the row
describes, either maps those records to label MAPs as well as the map's
entries (each label twice), or treats them as "any other record" and
warns that it skipped them (a spurious `Warning` on every labelled
document). Neither is what the row intends.

Second, §S2's unit row lists `labels` (LIST of STRING) "where present",
and `smysl.parse` returns "§S2's MAPs of units". A store reads a unit's
labels back through `labels_of` (`smysl-graph/src/labels.rs:69-79`);
a parse has the same information in its map. If `smysl.parse` fills
`labels` on its unit MAPs, the new rule makes `smysl.append` refuse every
labelled unit with SM03, and criterion 5's step 1 fails on its own
fixtures, which hold labels.

**Needed.** Say that `smysl.parse` takes label MAPs from one source (the
`LabelBinding` records, or the map, which are the same set) and does not
count the other as skipped. Say that a unit MAP from `smysl.parse` has no
`labels` key, since its labels travel as label MAPs. Cite
`parse.rs:2596-2606` beside `:63`.

### S2. How `smysl.append` tells a label MAP from a unit or relation MAP is still unstated

The ninth review's S3 asked for a label row "with its keys and how a
label MAP is told apart from a unit or relation MAP", and for a refusal
for "a MAP in `smysl.append`'s LIST that is none of the three kinds".
Revision 11 added the row (`{ label, uid }`) and answered the rest of S3,
but neither of these. Its answer table does not mention them, and the RFC
has no rule that decides a MAP's kind.

The three shapes do overlap. A unit MAP may not carry `uid` (SM03), but a
label MAP must. A relation MAP has `kind`, `from` and `to`; a unit MAP
has `schema` and `gist`. So a MAP `{ label, uid, gist }`, or a unit MAP
with a stray `uid`, or `{ }`, is classified by whatever order the
implementation tries the shapes in, and the code it answers (SM03 for
"computed, not given", SM03 for a missing key, or a successful label
bind) follows from that order. Criterion 14 cannot assert a text for a
case whose kind is undefined.

**Needed.** State the rule, for example: a MAP with a `label` key is a
label MAP and must have exactly `label` and `uid`; one with `kind` is a
relation MAP; one with `schema` or `gist` is a unit MAP; any other is
SM03 naming the LIST position. Add the unclassifiable MAP to criterion
14.

### S3. `smysl.parse` does not say what happens to SMYSL's error diagnostics, its recovered records, or a `ParseError`

§S4 says `smysl.parse` returns MAPs, skips records with no §S2 form with a
`Warning`, and (§S8) routes `SMY-W054` as a `Warning`. Nothing else about
what the parser reports is stated.

**Evidence.** "The parser never returns `Err` for a malformed record. It
emits a diagnostic with a byte span and recovers to the next record
start. A hard error is returned only for an unparseable `@doc` header"
(`smysl-core/src/surface/parse.rs:3-6`). The outcome counts the records
skipped by recovery (`recovered`, `:66-67`, incremented at `:350-352`)
and carries every diagnostic (`:65`). An unresolved label is `SMY-E060`
and drops the relation that used it (`parse.rs:2553-2560,2608-2614`).
So a document with a malformed unit, or a relation naming a label
nothing declares, parses "successfully" with that record missing and an
error-severity diagnostic in the outcome.

As written, `smysl.parse` answers a LIST that silently lacks those
records. A program that then `smysl.append`s it writes a library that is
not the document, and nothing reports why. A `ParseError` has no stated
code either (SM02 is the obvious one, but the row does not say so).

**Needed.** Say what an error-severity diagnostic does: refuse with SM02
(or a new code) carrying every diagnostic, as SM04 does for a query, or
answer the partial LIST and report each diagnostic and the `recovered`
count as `Warning`s. Name the code for a `ParseError`. Add a criterion
14 or 18 case for a document with one malformed record.

### S4. `bund2 check` reaches the new `"smysl"` arm only through the constructor's `Leaves::Conditional`, which the RFC does not declare

§S9 says:

> `bund2 check`'s per-row conditional arm becomes `"csv" | "sqlite" |
> "query" | "smysl"`.

and criterion 18 says `bund2 check` "reads a program using the `smysl`
conditional … with no unknown-effect diagnostic".

**Evidence.** The checker learns a CONDITIONAL's type only from the
`Leaves` its constructor declares: `Leaves::Conditional(ty) =>
Abs::Cond(Rc::new(ClassModel::kind(ty)))` (`crates/bund2-stdlib/src/check.rs`,
the `Leaves` match, about line 819). That is D181. Every existing
per-row constructor declares it: `csv` and `sqlite` as
`eff(1, 1).leaving(Leaves::Conditional(…))` (`crates/bund2-stdlib/src/data.rs`,
`register`), and `query` as
`StackEffect::fixed(0, 1).leaving(Leaves::Conditional("query"))`
(`crates/bund2-stdlib/src/kb/query.rs:157`). RFC-0013 states the rule:
"A constructor declares its type through `Leaves::Conditional` (D181)".
RFC-0014 gives the constructor `smysl` only as "→ c", never names its
`StackEffect` or `Leaves`, and does not consume D181. A constructor
registered as a plain `eff(0, 1)` leaves an unknown value, `!` on it is
abandoned, the new arm is never reached, and criterion 18's case fails.

**Needed.** State that `smysl` is registered
`StackEffect::fixed(0, 1).leaving(Leaves::Conditional("smysl"))`, as
`query` is, and add D181 to "Decisions consumed". While there, note that
the checker's arm reads an absent `lambda` as an empty body
(`check.rs`, the `"csv" | "sqlite" | "query"` arm, `Slot::Absent`), where
the runner refuses it with SM03 (§S6). That is harmless for a static
walk, but worth one sentence so the arm is not "fixed" to match.

## Notes

- **N1. SM08's "When" column omits the unbound label.** Revision 11 makes
  an unbound label SM08 with `<n>` 0 (§S2, criterion 18), and the text
  column says so, but the "When" column still reads "a label bound to
  several units; or …". Add "or to none".
- **N2. Other caps still name CLI flags.** Only `input_bytes` is
  re-displayed with `flag` none. `Library::add` spends the same `Budget`
  in the reader, `Structure::build` and `part::group`
  (`smysl-text/src/library.rs:1155-1190`), and their `SMY-E440`s carry
  `--max-nodes`, `--max-part`, `--max-fuel` and the rest
  (`smysl-text/src/limits.rs:109-120,136-147`). Either rebuild every
  `Limit` with `flag: None`, or say that only the input cap is rewritten.
- **N3. SM02 is first raised in M2, and SM08 in M3.** `smysl.open` (M2)
  answers SM02 for any `Library::open` failure: an empty marker, an
  undecodable log, a primary shard. `smysl.unit` (M3) resolves labels in
  `grounds` and `deps`, so it raises SM08. The plan lists SM02 under M3
  and SM08 under M4, against its rule that each code is tested where it
  is first raised. (The seventh review's N4 placed SM02 at M3 on
  `smysl.unit` alone.)
- **N4. `--noio` stubs arrive only in M10.** `smysl.open` and the
  research words exist from M2 and M5, the conditional from M7, and every
  one of them reads a library under `--noio` until M10. Nothing is
  released in between, but each milestone "ends with its criteria
  passing" on a tree that does not yet satisfy R11. Registering each
  word's stub with the word would keep every milestone inside the ruling.
- **N5. The command string Bund2 passes to `acquire_all` is unstated.**
  It is what `Lock::holder` reads back, what SM07's text prints after
  `running` (`smysl-graph/src/lock.rs:44-52`), and what `bund2
  smysl-unlock` lists. SMYSL passes its own command (`"text add"`,
  `"lib migrate"`). Name Bund2's, for example `bund2 <word>`.
- **N6. A failed canonicalisation has no code.** "Every word canonicalises
  the root it is given again" (§S2), but `std::fs::canonicalize` fails on
  a root that does not exist, which is the ordinary case for
  `smysl.open` of a wrong path and for a handle whose directory was
  removed. SM01 is the evident answer; say so.
- **N7. A second label on one unit does not survive `smysl.write`.**
  `smysl.label` refuses a label bound to another unit, but not a second
  label for the same unit. SMYSL's writer keeps one name per uid,
  "the first in canonical order" (`smysl-core/src/surface/write.rs:51-61`),
  and its parser drops the rest with `SMY-W054` (`parse.rs:2533-2548`).
  So a library with two labels on one unit loses one through
  `smysl.write`. Say so beside criterion 5, or refuse the second label.
- **N8. The label MAP's `extra` is always empty, which is why it needs no
  `opaque`.** Units and relations set `opaque` for a non-empty `extra`;
  the label row says nothing. It is safe: the only source of label MAPs
  is `smysl.parse`, whose bindings are built by `LabelBinding::new` with
  an empty `extra` (`annex.rs:495-501`; `parse.rs:2603-2606`), and Bund2
  writes them the same way. One sentence would say so.
- **N9. Revision 11's answer table has no row for the ninth review's
  assumptions or Preservation items,** though the header says it answers
  "its assumptions", and every earlier answer table has such a row. The
  ninth review's "a third read of every log, over a torn library" (its
  Preservation list and assumption 7) has no Preservation row or Q54 note
  in revision 11.

  differs from its source document.

  names; `smysl.write` keeps one.
- **A third read of every log over a torn library** (N9), carried over
  from the ninth review and not yet answered.

## Assumptions the RFC makes but does not state

1. **`ParseOutcome.labels` and its `LabelBinding` records are one set, and
   `smysl.parse` reads only one of them** (S1). They are one set
   (`parse.rs:2600-2606,2793`).
2. **A unit MAP from `smysl.parse` has no `labels` key** (S1), without
   which revision 11's SM03 refuses criterion 5's input.
3. **A MAP's kind is decidable from its keys** (S2).
4. **A string in `grounds` or `deps` is a uid when `Uid::parse` accepts
   it and a label otherwise.** It is safe, since a label is
   `<ns>/<name>` in lower case (`smysl-core/src/ids.rs:503-507`, and the
   tests at `:1031-1043`) and a uid begins `b3:`, so the two cannot be
   confused; but the rule is not written down, and a string that is
   neither has no stated code.
5. **SMYSL's parse diagnostics are warnings only** (S3).
6. **The `smysl` constructor carries `Leaves::Conditional("smysl")`**
   (S4).
7. **`smysl.label`'s uid names a unit in the library.** A binding to an
   absent uid is not refused anywhere in the RFC.
8. **A canonicalisation failure is SM01** (N6).
