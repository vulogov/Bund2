## Findings, most serious first

### 1. `graph.allpath` refuses acyclic graphs as "negative cycle detected", and neither the RFC nor F220 says so

R:129-132: "A negative cycle the potentials' Bellman–Ford finds is
refused … only one through `q`'s replaced out-edges goes unseen." That is
true, but the Bellman–Ford does not run over the program's graph. It runs
over `g` (`johnson.rs:40-47`), where `q` has a zero-weight edge **to every
vertex**. So every path that *ends at* `q` with a negative total closes a
negative cycle `q → v ⇝ q` in `g`, whether the program's graph has a cycle
or not. Bellman–Ford reports it (`bellman_ford.rs:91-101`), and Johnson
turns that into `NegativeCycle` (`johnson.rs:50-53`).

Run in both engines today:

```
[ [ :A :C -1.0 ] ] [ :A :B :C ] graph! graph.allpath println
[ [ :A :B 1.0 ] [ :B :C -0.5 ] ] [ :A :B :C ] graph! graph.allpath println
[ [ :C :A 5.0 ] [ :A :C -1.0 ] ] [ :A :B :C ] graph! graph.allpath println
```

- oracle and bund2: `GRAPH.ALLPATH: returned: negative cycle detected in
  graph`, all three times.
- The first two graphs have no cycle at all, and the third's one cycle
  weighs +4.0.
- Listed `[ :C :A :B ]`, the first answers four rows in both engines,
  `A → C` at -1.0.

So the commonest way to meet F220 is not the dropped rows R:111-128
describes. It is a plain error on a DAG with any negative edge into the
last distinct node, and it names a cycle that is not there. This is a
third order-dependence, and it is not stated anywhere:

- not under "Current behaviour" (R:111-132);
- not in the preservation analysis. R:388-391 says "a negative cycle is
  mostly refused", which reads as fewer refusals than the truth, and R:407-409
  says `graph.allpath` "drops rows as F220 says";
- not in F220, whose title and both notes describe only dropped rows and a
  missed cycle;
- not in D200, whose problem statement ("makes Johnson drop that node's
  rows without a word") is narrower than this.

- **No criterion reaches it.**
  `allpath_with_a_negative_edge_out_of_the_last_node_answers_nothing`
  (`GA:1883`) pins F220's one example.
- **Repair:**
  - State the condition under "Current behaviour": the potentials run over
    `g`, so a negative-weight path into `q` from any node is refused as a
    negative cycle. Add one of the programs above, run in both engines.
  - Correct the preservation analysis's `graph.allpath` and
    "negative weights" bullets.
  - Add a dated note to F220.
  - Add a test pinning the refusal of an acyclic graph, in both node
    orders.
  - D200 ruled to preserve F220 **as F220 described it**. This is
    behaviour D200's statement did not show the owner. Preserving it is
    still the conservative choice, and D14 makes the family core. But the
    owner should be told rather than have D200 extended silently. A dated
    note on D200 stating the case, put to the owner, is the minimum.

### 2. "Only an answer that overflows is refused" does not hold: a tiny weight anywhere brings back D199's refusal, with a false message

S4 (R:237-242) says **"only an answer that overflows is refused**
(D202)", and the bellmanford message "nam[es] a node whose distance cannot
be represented". It also says "A negative cycle whose sums would run past
`-1.0e308` is found and reported as the cycle it is". S5 (R:311-313) then
states an exception: "A weight too small to divide without losing bits
keeps the refusal, by the node the first overflowing sum reached." S4 is
absolute, and the exception falsifies all three of its claims.

The code tests exactness over **every** edge (`GA:605-608`, `net.edges.iter().all(…)`).
That includes self-loops and edges the start cannot reach. Run under
bund2:

```
:A [ [ :A :C 1.0 ] [ :A :B 1.0e308 ] [ :B :C 1.0e308 ] [ :D :E 5.0e-324 ] ] [ :A :B :C :D :E ] graph! graph.bellmanford println
:A [ [ :A :C 1.0 ] [ :A :B 1.0e308 ] [ :B :C 1.0e308 ] [ :D :D 5.0e-324 ] ] [ :A :B :C :D ] graph! graph.bellmanford println
:A [ [ :A :B -1.0e308 ] [ :B :A -1.0e308 ] [ :C :C 5.0e-324 ] ] [ :A :B :C ] graph! graph.bellmanford println
```

- The first two answer `GRAPH.BELLMANFORD: the distance to C overflows`.
  C's distance is 1.0. The message names a node whose distance is
  representable, which is the false message the fourth review's finding 1
  objected to, now under a node's name rather than an edge's.
- The third answers `the distance to A overflows` for the `-1.0e308`
  cycle. That is a negative cycle reported as an overflow, which S4 says no
  longer happens.
- Which node is named depends on the order of the edges ("the first
  overflowing sum"). D202's own problem statement rejected that.
- `only_an_answer_that_cannot_be_represented_is_refused` (`GA:1842-1849`)
  **asserts** this message for a graph whose distances are A 0.0,
  B 1e308 and C 1.0. So criterion 11 pins a message S4 says cannot occur.

The trigger is narrow: a weight below about `2^(-1022+k)` with low bits
set, where `k` is about `log2(4 × nodes × edges)`. For small graphs that
is roughly below 1e-306. But the RFC states the rule without the
exception, and the exception is not in D202's option A as ruled ("The
word refuses only when a distance it must answer cannot be represented").
It is only in D202's "Built" paragraph. That is the same shape as the
fourth review's finding 1, a "Built" paragraph going past the ruling.
"Which points are rulings" (R:347-371) does not list it as a build choice
either.

- **Repair**, one of the following:
  - Remove the exception. Track the exponent beside the `f64`, or scale
    only the run's sums rather than the weights. Adding a value whose
    scaled form underflows to one far larger rounds the same as the
    unbounded sum, because the lost bits lie below the larger operand's
    half-ulp.
  - Restrict the exactness test to edges the start can reach and that are
    not self-loops. This narrows the exception but does not remove it.
  - Keep it. Then restate S4 with the exception: "a node whose distance
    cannot be represented, or, when a weight is too small to scale, the
    node the first overflowing sum reached, which need not be either". Add
    it to the preservation analysis's overflow bullet (R:410-416, which
    claims "a graph whose distances are finite is answered, by
    `graph.bellmanford` as by `graph.paths`"). List it among the build
    choices, and take it to the owner as a note on D202.
- The doc comment on `bellman_ford` (`GA:595`) still says "by the first
  *edge* whose sum overflowed". The message names a node.

### 3. D202 is tested by examples only; no criterion checks the scaling argument

S5 (R:308-311) rests on a claim: "Dividing by a power of two is exact, so
the comparisons are the unbounded ones." I checked the argument and it
holds, including for sums that land in the subnormal range. Such a sum is
exact in the scaled run, and the corresponding unscaled sum is exactly
representable. It also depends on `k` covering every walk a run forms. A
run makes `n` passes of `m` edges, so a walk has at most `n × m` terms, and
`2^k ≥ 4nm` (`GA:601-603`). Both hold.

But criterion 3's cross-checks (`bellman_ford_agrees_with_dijkstra`,
`…_with_floyd_warshall`) run small weights that never overflow, so the
scaled run is never entered. Criterion 11 tests five hand-picked graphs.
Nothing checks the claim itself.

- **Repair:** a seeded cross-check. Take the random graphs
  `bellman_ford_agrees_with_floyd_warshall` already makes, multiply every
  weight by `2^1000`, and require each answer to be the unscaled one times
  `2^1000`, to the bit. Where that product is not finite, require a refusal
  by that node. Where the unscaled run finds a cycle, require the same
  cycle node. This checks exactly what S5 asserts, and it would also have
  caught finding 2 had the weights included a subnormal.

### 4. The twelve `.` forms' workbench half is declared `Unknown`, so `bund2 check` cannot see a missing graph; the RFC does not consult D195

S1 (R:175-176): "Its declared effect takes the node operands from the
stack and leaves nothing there." That is the stack half only. Since D195,
an effect has a workbench half (`StackEffect.bench`, RFC-0004 §S1's second
axis, built 2026-10-19), and `check` counts it. Every `.` native that was
not measured is `Unknown` (`decisions.md:4010-4015`, D195 "The declarations"). The twelve forms are
Bund2's own and come from one macro (`bench!`, `wb.rs:176`), so their
workbench half is known by construction (one in, one out). They are still
declared `Unknown`:

```
:A graph.bfs.     →  bund2 check: 0 finding(s)
take              →  bund2 check: `take` needs 1 value(s) on the workbench; 0 can be proven here
```

- RFC-0012 lists RFC-0004 under "Depends on" for "the effects `bund2
  check` reads". D195 is about exactly that, and it is not among the
  decisions consumed or searched (R:28-36). That is the CLAUDE.md failure
  of searching by `Blocks:` rather than by subject.
- **Repair:** declare the twelve forms' workbench half in `bench!` as
  `Fixed { consumes: 1, produces: 1 }`, with a test that `check` finds
  `:A graph.bfs.` on an empty workbench. Alternatively, have the RFC say
  that the half is `Unknown` and why. Either way, cite D195. The reference's
  four `.` forms are D195's to measure, not this RFC's.

### 5. `graph.mst` over a forest of `-0.0` edges now answers `0.0`, an unstated change

`mst_total` folds from `0.0` (`GA:545`) to fix the empty graph's `-0.0`
(the fourth review's finding 3). The fold also changes every non-empty
forest whose weights are all `-0.0`:

```
[ [ :A :B -0.0 ] ] [ :A :B ] graph! graph.mst println
→ { edges=[ [ A :: B :: -0.0 ] ] :: weight=0.0 }
```

Before, `sum()` started from `-0.0` and answered `weight=-0.0`. The IEEE
sum of `-0.0`s is `-0.0`. `mst_total`'s comment says "every total answered
before D202 is answered alike" (`GA:533-534`), and D202's "Built" says
"sums its forest lightest first, as before". Neither holds for this case.
The RFC has made `-0.0` against `0.0` an observable point (S3, R:216-217;
criterion 6's "with its sign").

- **Repair:** state it in S1, as "`weight` is never `-0.0`", or fold from
  the first weight. Add the case to a test either way.

- **R:281-282**, "the residual F18 calls the observable part of a word's

  `RFC-0004-stack-effects.md:544-546` ("That residual is what F18 calls the
  observable part"). The fourth review's finding 6 replaced a drifted

- **R:339-340**, "The palette cannot build a graph", is still uncited after
  three reviews. The palette is `crates/bund2-stdlib/src/lib.rs:566-570`:
  its `dict` has no `type`, so every word that checks `type` refuses it.
- **R:303-304**: "In `graph.maxflow` only the total can overflow." D202's
  principle (refuse only the answer) holds there for an unstated reason:
  the running flow only grows, so a partial total that overflows means the
  answer does. One sentence would make S4's "only an answer that overflows
  is refused" cover all three words explicitly.
- **R:313-315**: the `graph.mst` fallback's total is a sum in a different
  order from lightest-first, so its last bits can differ from any
  "canonical" total. No earlier answer exists to compare it with, but S5's
  "each word's ordinary answer is unchanged by how" should say it means the
  answers that do not reach the fallback.
- **R:28-36**: the "Registers searched" list predates D199–D202 and the
  F220 note. D195 is missing (finding 4).

## Preservation analysis: what it does not enumerate

1. **`graph.allpath` refuses acyclic graphs** with a negative path into the
   last distinct node, as "negative cycle detected" (finding 1). This is a
   preserved behaviour of a core word. The "negative weights" bullet
   (R:407-409) and the F220 bullet (R:386-393) both miss it. For a program
   moving to `graph.bellmanford`, the change is from an error to an answer,
   not from missing rows to full ones.
2. **`graph.bellmanford` refuses graphs `graph.paths` answers** when a
   weight is too small to scale (finding 2). The overflow bullet
   (R:410-416) says it does not.
3. **A `-1.0e308` negative cycle is still reported as an overflow** when a
   tiny weight is present anywhere (finding 2).
4. **`graph.mst` answers `0.0` where it answered `-0.0`** for an all-`-0.0`
   forest (finding 5).
5. **`bund2 check` is blind to the twelve `.` forms' workbench**, where it
   counts `take` (finding 4). This is not a runtime behaviour, but it is
   what the RFC's dependency on RFC-0004 promises.

## What the RFC assumes but does not state

- That Johnson's potentials expose only the program's own negative cycles
  (finding 1).
- That a weight small enough to break the scaling is not worth an answer.
  Equivalently, that S4's "only" admits an exception S5 states and S4 does
  not (finding 2).
- That a proof sketch in S5 needs no test (finding 3).
- That a `.` form's declared effect is its stack half alone (finding 4).
- That a total folded from `0.0` equals the old `sum()` wherever the old
  one was finite (finding 5).
- Carried from the fourth review, unchanged: that `graph.maxflow`'s `flow`
  and its `edges` shares agree to the bit. `r.cap += b` on a reverse arc
  far larger than `b` can absorb `b`. Neither review constructed a case.

## Disposition

**Not ready for Accepted.**

- **Finding 1** is a preserved behaviour of a core word, wider than its
  defect entry, its ruling and the RFC all say: an acyclic graph refused
  as a negative cycle, depending on node order. It needs the text, F220
  and a test. The owner should be told that D200's ruling now covers it.
- **Finding 2** is S4's central D202 claim falsified by an exception that
  S5 states and the ruling did not grant. Either the exception goes, or it
  is stated in S4, in the preservation analysis and among the build
  choices, with a note on D202 for the owner.
- **Finding 3** is a missing cross-check for the one new numerical
  argument.
- **Findings 4 and 5** are smaller repairs: a declaration or a sentence
  plus D195, and one sentence plus a test.
- The rest is citation and wording.
