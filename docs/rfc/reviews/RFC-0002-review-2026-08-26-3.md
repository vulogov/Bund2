# RFC-0002 review — third pass, 2026-08-26

Reviewing `docs/rfc/RFC-0002-symbols-and-words.md` at commit `f62be91`, revised
after reviews 1 (`RFC-0002-review-2026-08-26.md`) and 2
(`RFC-0002-review-2026-08-26-2.md`).

Method: every `reference/...:N` citation was opened and read in this session —
30 distinct long-form citations plus the 13 short-form rows of the allocation
table and the 12 short-form line refs in §Resolution order. Every count was
re-derived (`BUND` lock sites, `init_stdlib` share, inline names per layer,
alias chains, `dt: 6`/`dt: 7` renderings). `cargo xtask coverage`, `cargo tree
-p bund2-api` and `cargo xtask cite` were run. Five claims were put to the
oracle directly.

Verdict: **do not accept.**

Review 2's blocker — the duplicated `## Design` section — is gone, and the
document now says one thing throughout. Review 1's structural blocker is
properly repaired: the slot is a set of independent `Option` bindings, and I
confirmed on the oracle that a name really is a lambda and a native at once.
Every citation this pass resolves, and the allocation table is exactly right,
all thirteen rows.

What blocks acceptance is that the two mechanisms the RFC *moves* — `$`
handling and alias resolution — are each specified against `VM::apply` alone,
and each breaks in a case the reference reaches. Both are oracle-verified
below. Separately, the RFC consumes D16 and addresses only half of it, and
three register entries name RFC-0002 as the consumer of their consequence
while the RFC cites none of them.

## A. Claims the reference contradicts

### A1. `$` is stripped at dispatch, on names the parser never sees

RFC:326 heads a section **"The `$` sigil is stripped at intern time, not at
dispatch"**, and RFC:341-345 puts the strip in `bund2-syntax`:

> So `bund2-syntax` strips the sigil when it interns: `$println` interns to the
> `Symbol` for `println` … which is exactly what `call_internal_word` does with
> `&name[1..]`, **moved from run time to parse time**.

That move is only sound if every `$`-name passes through the parser as a name.
It does not. D16 — which this RFC consumes — makes a call target nameable by a
string that exists only at run time, and `execute` takes `PTR | STRING | CALL`
and hands the name to `vm.call` (`reference/rust_multistackvm/src/stdlib/execute.rs:27-30`),
which wraps it in a fresh `Value::call(...)` and re-enters `apply`
(`reference/rust_multistackvm/src/multistackvm_call.rs:8`). `apply` then does
the sigil test at `:33` on a string the parser lexed as a **string literal**,
not as a name.

Run on the oracle this session, both forms:

    "hello-from-native" "$println" ptr !    ->  hello-from-native
    "hello-bare"        "$println" !        ->  hello-bare

Both work. Under a design that strips only in `bund2-syntax`, `"$println"`
interns as the literal name `$println`, no slot carries it, and both lines
fail.

The RFC's one sentence about runtime interning (RFC:323-324) names `bund.eval`
and nothing else:

> A `CALL` built at run time by `bund.eval` interns through the same table.

Same *table* is not the same as *same stripping rule*, and `bund.eval` is not
the main source. Per ERRATA, `!` is one of the five most-used words in the
corpus — 69 invocations across 39 of 132 programs — and D16 item 4 makes the
bare-`STRING` form part of the contract explicitly
(`reference/rust_multistackvm/src/stdlib/execute.rs:27`).

The fix is small — strip at *intern* time wherever interning happens, parser
and runtime alike — but the section's title asserts the opposite of the
reference's mechanism, and the preservation table has no row for moving it.

### A2. The alias-chain deviation is wrong for `$name`: it bites at two links, not three

RFC:440:

> | Alias resolved twice | **Preserved for one level, deliberately changed for
>   chains.** Resolving to a fixed point differs from resolving exactly twice
>   only for an alias chain **three deep or more**. |

True for the plain spelling. False for `$`, and the RFC has the premise two
sections earlier without drawing the conclusion.

`apply` resolves one link at `:39` and `i` resolves a second at `:71-74` — two
links for a plain name. But `$name` goes to `call_internal_word`, which calls
`self.i` directly (`multistackvm_call_internal_word.rs:7-8`), so it gets **one**
link only. RFC:191-198 states exactly this mechanism (F26) and then RFC:440
counts as though both spellings resolved twice.

So on a **two**-deep chain the two spellings already diverge. Built and run on
the oracle this session:

    "println" "b2" alias
    "b2" "a2" alias
    "plain a2 (two links):" a2   ->  printed
    "now dollar a2:"        $a2  ->  ERROR: i(b2) for stack returned:
                                     Inline b2 not registered

Fixed-point resolution turns that error into a successful call. That is a
change at two links, on the `$` path, and it is not what the row says.

Two further gaps in the same row:

- **Chains are constructible.** `alias` is a registered word
  (`reference/rust_multistackvm/src/stdlib/alias.rs:72`); the four lines above
  build a chain. The row says "none is constructible **in the corpus**", which
  is true and is a weaker statement than it reads next to a permanently-open
  world (D16). Worth one clause.
- The row is uncited. `multistackvm_apply.rs:39` and `multistackvm_inline.rs:71-74`
  are cited in §"Alias resolution happens twice" but not where the deviation is
  claimed.

### A3. "Methods are reached … not by name" contradicts the RFC's own Motivation

RFC:130-133:

> A `$`-prefixed name forces the internal word (`…apply.rs:33`); **methods are
> reached through object dispatch, not by name**; and the stack layer's dead
> `functions` table is consulted by nothing.

Object dispatch locates a method *value*; if that value is a `PTR`, `VM::m`
casts it to a string and looks the string up in `methods_fun` by name —
`is_method(method_name)` then `get_method(method_name)`
(`reference/rust_multistackvm/src/multistackvm_object.rs:57-71`). It is a
by-name lookup into a `HashMap<String, _>`, which is why RFC:86 cites
`get_method` (`multistackvm_methods.rs:32-33`) as one of the four
`contains_key`-then-`get` tables in Motivation.

The sentence is doing real work — it justifies keeping `method` a separate
binding — and the justification survives. The claim as written does not: the
method namespace *is* name-keyed and *is* reached by name, just not from
`apply`. Say "not reached from `apply`", which is what is true and what the
design needs.

### A4. The open questions re-open a table the Summary, Design and `Slot` all settle

RFC:528-530:

> Whether `methods_fun` and `vars` become slot-table discriminants or stay
> separate tables is left to the implementation; both preserve the namespaces.
> Recorded here so it is not read as settled.

But the Summary (RFC:40-44) says **six** of the seven collapse; the Design
(RFC:257-271) says six collapse and names `vars` as the one that stays; and
`Slot` (RFC:225-233) carries `method: Option<NativeFn>` as a binding. Those
three agree — six is `inline_fun`, `command_fun`, `methods_fun`, `lambdas`,
`classes`, `name_mapping`, and the six `Slot` fields map onto them one for one.

If `methods_fun` might stay separate, the number is five, not six, and
`Slot.method` is provisional. Review 2 rejected this RFC partly for giving
"three different answers on which tables collapse"; this is a fourth, and it is
in the same document as the three that now agree. Either drop `methods_fun`
from the open question or drop `method` from `Slot`.

## B. Citation precision

### B1. `Library_introduction.typ:15-19` says the standard library is in `rust_multistack` too

RFC:415-420, justifying D14's partition line:

> It is `docs/core-words.md`, generated by `cargo xtask scope --write`, and it
> follows the reference author's own three-layer split — **`rust_multistack`
> and `rust_multistackvm` are the language, the Bund runtime is where the
> standard library lives**
> (`…/Library_introduction.typ:15-19`).

The cited lines are the three bullets, and the first one says:

> The Rust crate _rust_multistack_ encompasses all the logic associated with
> stack operations. **Additionally, it incorporates elements of the standard
> library that pertain specifically to these operations.**

Two lines above the citation (`:13`) the author writes "The BUND standard
library is situated across multiple locations." The passage establishes a
three-*location* split and explicitly denies the clean language/library
assignment the RFC draws from it.

The three-layer *axis* is the author's; the *cut* is D14's. RFC-0000 is careful
about exactly this distinction — "which is D14's axis confirmed from an
independent source (**the axis, not the cut**)" (`RFC-0000-architecture.md:507-508`)
— and `docs/core-words.md`'s own generated preamble is careful too, using the
three-layer split only as a file-closure rule for `vm/` and `stack/`. RFC-0002
collapses the distinction that the accepted RFC and the generated artefact both
preserve. This is a citation that resolves and misleads, which is the class
criterion 8 warns about.

### B2. `dup.rs:87` registers `dup_one`, and `dup` is registered into the dead table

RFC:55-58:

> Take `dup`, an alias for `dup_one` (`create_aliases.rs:18`), which is
> registered in the **stack** layer (`reference/rust_multistack/src/stdlib/dup.rs:87`).

`dup.rs:87` is `ts.register_inline("dup_one".to_string(), …)`. If "which"
refers to `dup_one`, the citation is right and it is the line the trace needs.
If it refers to `dup` — the nearer reading for most readers, and the subject of
the sentence — it is wrong: `dup` is registered at `:85`, by
**`register_function`**, into the `functions` table F19 records as dead.

That is worth a clause rather than a rewrite, because the dead registration is
substantive: it is where `dup_in` also lives (`:88`), which is why D29 exists
at all. As written a reader cannot tell that `dup`-the-name has two
registrations in the same file with only one of them reachable.

### B3. "The rest matter more" describes one of nine

RFC:106-108. Nine `BUND.lock` sites are outside `init_stdlib` and the RFC names
one. The other eight are `run_snippet_for_cmd` (`:16`),
`run_snippet_and_return_value` (`:101`), `run_snippet` (`:142`),
`run_snippet_as_actor` (`:163`), and four in `cmd/`. The argument is unaffected
— none is word-reachable, which I verified — but `run_snippet_as_actor` in
particular is worth a mention in an RFC that discusses what RFC-0007 inherits.

## D. Behaviours the preservation analysis does not enumerate

The table has thirteen rows. These are missing.

### D1. D29's word-set deviation — three words dropped, one revived

RFC:422-424 records D29's outcome and then says "That is a deliberate deviation
in both directions and is recorded **there**." The preservation analysis is
where this RFC's deviations are enumerated, and it has no row for either
direction:

- `dup_in`, `from_workbench` and `push_to` are registered by the reference
  (into the dead `functions` table) and Bund2 will not have them.
- `stacks_left` gains a slot it never had, and `<-` / `←` change from
  **resolving to an error** to **resolving to a working word**. That is an
  observable change from failure to success, on two names that are already
  registered aliases.

D29 records the decision; the RFC is where its behavioural consequence belongs.

### D2. F25's dead `apply_in` cluster — a second resolution order

`VM::apply_in` (`reference/rust_multistackvm/src/multistackvm_apply_in.rs:7`)
is a near-copy of `apply` with three divergences, and the RFC never mentions it:

- **No empty-name check.** `apply` bails at `:13-15`; `apply_in` goes straight
  to `is_command` at `:12`.
- **No `$` arm at all.** `apply_in` goes from the `autoadd` test straight to
  `get_alias` (`:15-20`). `apply` checks the sigil at `:33`.
- **A different `autoadd`.** `apply` pulls the value beneath and appends
  (`:20-27`); `apply_in` does `push_to_stack(name, value)` (`:16`). Its
  `CONTEXT` arm pushes to the named stack (`:45`) and its catch-all uses
  `pull_from_stack`/`push_to_stack` (`:62-70`).

So §"`autoadd` has three branches, not one" (RFC:167-180) is really six across
two functions, and the preservation row promising `autoadd` "**Preserved
exactly**, including … `:72`" covers one of the two.

This is **already dispositioned** — F25 records the cluster, names both
divergences, and says: "Consequence for RFC-0002: the dispatch contract has one
resolution order to specify, not two, and porting this cluster would import a
second." The RFC does not cite F25 and has no row for dropping the cluster. It
should, because "one resolution order, not two" is a deliberate omission of
reachable-looking code, and a work item reading only the RFC would have to
rediscover it.

(I verified the cluster is closed: `apply_in` ← `lambda_eval_in:14` and
`call_in:12`; `lambda_eval_in` ← `apply_in:25`; `call_in` has no caller
anywhere in the six crates.)

### D3. F19's dead `functions` table

Same shape. F19 says "Consequence for RFC-0002: **bund2 does not need a fourth
`WordEntry` variant.** The slot table absorbs three tiers, not four." The RFC
alludes to the table once (RFC:133) and gives it no row, no citation and no
mention of F19 — even though the table is where `dup_in`, `from_workbench` and
`push_to` live, which is the entire subject of D29.

### D4. `StackEffect` at registration collides with F18, and has no row

RFC:363-366 is the RFC's one semantic addition to a word:

> `StackEffect` is declared at registration for natives. `cargo xtask arity`
> already extracts the reference's guards mechanically and found 14
> under-declared ones (F18), so the initial declarations are **derived rather
> than hand-written**.

Derived from *which column*? F18 is explicit that they differ and that the
difference is observable:

> **The error message differs from every other arity failure**, so a program
> catching or printing it sees `NO DATA #2` where it would elsewhere see "Stack
> is too shallow". That is observable behaviour, which is why this is a defect
> and not a tidy-up.
> … RFC-0004 must take the **probed** column of `docs/arity.md`, not the
> declared one, wherever the two disagree.

If Bund2 declares the probed arity, `1 pair` reports "Stack is too shallow for
inline pair()" where the reference reports `NO DATA #2` — an error-text change
on 14 words. If it declares the guard's arity, it reproduces the defect. Either
way it is a preservation decision, and the table has no row, no criterion names
it, and the RFC does not say which column feeds the declaration.

### D5. `WordKind` has no semantics, no row and no criterion

`pub enum WordKind { Sync, Blocking, Async }` (RFC:360) appears in the Summary
and the Design and nowhere else. Nothing says what declaring a word `Blocking`
or `Async` *does*, nothing preserves or changes, and no criterion checks it.
It is a stable-surface type (RFC:401) with no stated contract — which is the
one place a missing contract costs the most.

### D6. `PTR` is used as evidence and left out of the design

RFC:216 says "A **`CALL`** value carries a `Symbol`, not a `String`". Nothing
in the RFC says what a `PTR` carries. But:

- RFC:312 cites "**30 `dt: 7`** renderings" — the PTR count — as part of the
  evidence for the string-at-every-boundary rule.
- A `PTR` *is* a name that executes: `execute` treats `PTR | STRING | CALL`
  identically (`execute.rs:27-30`), and D16 makes `` `name `` and
  `<string> ptr !` first-class.
- RFC-0001 rests its whole "independent axes" thesis on `PTR` versus `STRING`
  over one `Val::String` payload.

If PTR carries a Symbol, the RFC should say so and the same boundary rule
applies. If it does not, then one `Val::String` payload arm has two internal
representations chosen by `dt` — which is a fact RFC-0001's undefined `Payload`
would have to express, and neither RFC says it.

### D7. Runtime interning is unbounded, and D16 is why

`Symbol(u32)` indexes a `Vec<String>` that only grows (RFC:315-316). Under D16
the world is permanently open and a call target may be "named by a string that
exists only at run time" — so a loop that assembles names and executes them
interns forever. D3 exists precisely because `bund.eval` is "a whole class of
unbounded code-memory growth"; the interner is a second, smaller one that the
RFC introduces and does not bound.

Nothing here demands a solution. It demands a sentence, in the RFC that adds
the table.

### D8. The `$` flag has no home in RFC-0001

RFC:342-343 puts the sigil "on the `CALL` as a flag rather than as part of the
name", and RFC:347-348 requires it to render and serialise as `$println`.
RFC-0001's `HeapValue` has `identity`, `stamp`, `dt`, `curr`, `tags`, `attr`
and `payload` — no flag — and its `Payload` type is declared and never defined
(carried in RFC-0001's own review as an unstated assumption). So RFC-0002
requires a field of a struct that RFC-0001 measured at 80 bytes without it.

The RFC is admirably explicit about the *other* RFC-0001 collision it found
(`Arc` versus `Rc`, RFC:377-390). This is a second one, in the same direction,
and it is unrecorded.

## E. Acceptance criteria, one at a time

The "each below names the tool" discipline is a real improvement and holds up
throughout. Criteria 3, 4 and 5 are labelled honestly about what cannot run
today, which is exactly what review 1 asked for.

1. **`conform` does not fall below the mark** — checkable; `cargo xtask conform`
   exists and `CONFORMANCE.txt` reads `0/66`. Note the RFC quotes no figure,
   which is right for a criterion that must not pin a moving number.
2. **CORE COVERAGE 121/286** — checkable and reproduces exactly: `cargo xtask
   coverage` prints `CORE COVERAGE 121/286 (42.3%)` beside `COVERAGE 121/497`.
   Worth noting what the tool also shows and the RFC does not: the two share
   the numerator, so **every covered word is core** and the library 211 has
   zero coverage.
3. **Dispatch allocates 0 times** — correctly labelled "no tool exists yet",
   with the harness named and deferred to RFC-0003. Good.
4. **`cargo tree -p bund2-api`** — checkable, near-vacuous, labelled. Verified.
5. **`resolve` succeeds for `dup_one` and the 31 stack-layer words** — checkable
   as a Bund2 unit test, and the reasoning for why it cannot be a golden is
   correct: the oracle fails it, so capture would pin the failure. Good
   criterion.
6. **`name` and `$name` reach the same slot** — checkable, and the grammar
   argument is verified: `element` admits `SYMBOL` (`bund.pest:36`), `$` is
   Unicode category Sc, and `name = !("`") ~ element ~ nelement*` (`:28`), so
   `$println` lexes as one name. But A1 shows the criterion tests only the
   lexical case. A `"$println" ptr !` line — which the oracle passes — would
   catch the gap this criterion currently leaves open, and it belongs in the
   same probe.
7. **A lambda saved in one process reloads and runs in another** — checkable as
   an integration test, and it is the right criterion for the boundary rule.
   Note the RFC has no criterion for the *other* boundary it names: that
   `Debug` renders `data: String("println")` unchanged. That is checkable today
   by `conform` over the 29 goldens carrying `Value {` text, and criterion 1
   covers it only implicitly.
8. **`cite` reports zero defects** — passes, with the caveat the criterion
   itself states, which this pass vindicates again: B1 and B2 are citations
   `cite` accepts.

**Missing criteria.** Nothing checks: the `autoadd` behaviour any of its
branches (a `conform` run covers it only if a golden exercises `:`/`;`); the
`generation` counter invalidating an inline cache; `StackEffect` (D4); anything
about `WordKind` (D5); D29's revived `stacks_left` and the `<-`/`←` repair,
which is a stated deviation with no test named.

**D-1's reassignment.** RFC:513-518 hands RFC-0000's deferred D-1 to RFC-0003.
The reasoning is right and stating it is the correct instinct. But RFC-0000 is
**Accepted** and its text still reads "D28 is a commitment until RFC-0002
declares the feature set" (`RFC-0000-architecture.md:429`). RFC-0002 lists
"Supersedes: nothing". A reader of RFC-0000 has no way to learn the target
moved. ERRATA covers `docs/research/` only, so the right place is probably a
note on D28 — but somewhere.

## F. Register and cross-RFC consistency

**F18, F19 and F25 all have empty `Disposition:` lines.** Each ends
`- Behavioural. Disposition:` or `- Dead code. Disposition:` with nothing after
the colon. All three name RFC-0002 as the consumer of their consequence, and
this RFC depends on all three: F19 for not adding a fourth binding, F25 for
having one resolution order rather than two, F18 for where `StackEffect`'s
numbers come from. There is nothing for a work item to cite. (Fourteen entries
in `defects.md` share this shape; these three are the ones RFC-0002 rests on.)

**D16 is consumed and half-addressed.** The RFC reduces D16 to table mutability
— "`register`, `unregister`, `alias` and `unalias` are words, so the table is
mutable at runtime" (RFC:204-206), and a preservation row reading "Open world —
`register` / `alias` at runtime". D16's actual subject is **dispatch by
computed name**: `<string> ptr !` and `` `<name> ! ``, with five numbered
consequences, of which item 5 is addressed to this RFC by name:

> **`bund2-api` cannot assume a compile-time-fixed word set** (RFC-0002). The
> table stays queryable by computed name at run time, in every tier.

That is the half the RFC omits, and it is the half that stresses the `Symbol`
design (A1, D7). D16 item 3 also declares the resolution order "observable in
full and its order is contract" **including the VM-to-stack fall-through** —
against which the RFC's "Preserved in effect" row is a slightly weaker promise
than the decision grants.

On that fall-through: I checked, and the merge is safe today. 156 VM inline
names, 31 stack inline names, **zero overlap**. But the design never says which
wins on collision, and D14's second surface — out-of-tree word packages — is
exactly where a collision would first arrive.

**ERRATA is satisfied but uncited.** The entry superseding
`00-jit-feasibility.md` §2 ends "RFC-0002's slot table has to absorb all three
[tiers]". It does — six VM tables plus the stack layer's inline table covers
every registration source. The RFC never says so, and a reader checking ERRATA
against the RFC has to reconstruct the mapping.

**RFC-0000 is stale on D29** (`:488-490`, "D29 is OPEN"). That is RFC-0000's
defect, not this one — RFC-0002 reports D29 correctly — but RFC-0002 cites
RFC-0000's B2 at RFC:522-524, and B2's own text ("it moves whenever D14 or D29
rules on another word", `RFC-0000:399-400`) is the part that is still accurate.

**The `Arc` → `Rc` collision is handled well.** RFC:377-390 is the model for how
a cross-RFC collision should be recorded, and it is worth saying so. The
sentence "and RFC-0001 says it is not [`Send`]" is the one flaw: RFC-0001 does
not mention `Send` or `Sync` anywhere. The conclusion is correct — `Rc` plus
`Cell` is neither — but it is derived here, not stated there. I raised the
matching gap in RFC-0001's third review; whichever RFC states it, only one
should claim the other already did.

## G. Assumed but not stated

1. **That every `$`-name reaches `bund2-syntax`.** A1. The largest one.
2. **That runtime interning applies the same sigil rule as parse-time
   interning.** RFC:323-324 says "the same table" and stops.
3. **What a `PTR` carries.** D6.
4. **That the interner grows without bound.** D7.
5. **Which arity column feeds `StackEffect`.** D4.
6. **What `WordKind` means.** D5.
7. **That the VM/stack `native` merge is collision-free.** True today (0 of
   156 × 31); unstated, and the second `bund2-api` surface is where it stops
   being true.
8. **That stack names are not interned.** `apply`'s `CONTEXT` arm resolves a
   *stack* name (`apply.rs:75`), and `TS` keys stacks by `String`. The RFC says
   "Names become interned `Symbol`s" without scoping which names, and stack
   names are an eighth string-keyed namespace it never mentions.
9. **That `register` writes two namespaces.** `stdlib_lambda_register`
   dispatches on the value's type and calls `register_lambda` or
   `register_class` (`reference/rust_multistackvm/src/stdlib/lambdas/registry.rs:15-22`).
   The slot design handles it correctly; the RFC never says the word is
   type-dispatched.
10. **That `Symbol` is `u32` and the interner is a `Vec<String>`** makes reverse
    lookup O(1) — stated (RFC:315-316) — but nothing says what happens on
    overflow or whether symbols are ever freed. With D16 open, they are not.
11. **That the generation counter is per-slot and monotonic**, and that
    wrapping a `u32` generation cannot alias a stale cache entry.
12. **That `bund2-syntax` re-implements `bund.pest`** rather than reusing the
    pest grammar — stated as premise (RFC:320-322), never as a decision.

## What would make this acceptable

1. **Fix A1.** Strip the sigil wherever interning happens, not only in
   `bund2-syntax`; retitle the section; add a preservation row for moving the
   strip; and extend criterion 6 with `"$println" ptr !`, which the oracle
   passes today.
2. **Fix A2's row.** `$name` resolves one link and plain resolves two, so the
   fixed-point deviation bites at two links on the `$` path. Cite the
   mechanism, and soften "none is constructible" to "none in the corpus" —
   `alias` is a word.
3. **Fix A3's sentence** to "not reached from `apply`", and resolve A4 by
   removing `methods_fun` from either the open question or `Slot`.
4. **Add the missing preservation rows**: D29's word set in both directions,
   F25's dropped cluster, F19's dropped table, `StackEffect` against F18, and
   `WordKind`. Cite F18, F19 and F25 where they are relied on.
5. **Address D16's actual subject** — dispatch by computed name — in one
   paragraph, and bound or acknowledge the interner's growth.
6. **Say what a `PTR` carries**, and record the `$`-flag's need for a field
   RFC-0001 does not have, the way the `Arc`/`Rc` collision is recorded.
7. **Qualify B1** — the cited passage says the standard library is spread
   across all three crates, including `rust_multistack`; borrow RFC-0000's
   "the axis, not the cut". Add a clause to B2 so `dup.rs:85` versus `:87` is
   legible.
8. **Add criteria** for `autoadd`, the generation counter, `StackEffect`, and
   D29's `<-`/`←` repair; and record D-1's reassignment somewhere a reader of
   RFC-0000 or D28 will find it.

## Defects this pass found that are not in the register

Recommended, not written — the register is the owner's to append.

- **F18, F19 and F25 have empty dispositions**, and all three name RFC-0002 as
  the consumer of their consequence. Eleven further entries in `defects.md`
  share the shape; these three block a work item.
- **`$name` and `name` resolve alias chains to different depths** — one link
  versus two — so on a two-deep chain the plain spelling succeeds and the `$`
  spelling fails. Oracle-confirmed this session with `"println" "b2" alias`,
  `"b2" "a2" alias`. This is a sibling of F26 and is not recorded in it: F26
  covers *that* `$` resolves aliases, not *how far*.
- **`VM::apply_in` has no empty-name check**, where `apply` bails at
  `multistackvm_apply.rs:13-15`. F25 records the missing `$` arm and the
  `autoadd` divergence and not this third one.
