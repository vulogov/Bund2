# Review — RFC-0003: Surface syntax, BundIR, and the Tier 0 interpreter

- Date: 2026-08-29
- Reviewing: `docs/rfc/RFC-0003-syntax-ir-and-tier0.md` (Draft)
- Method: every `path:line` opened against the pinned submodules; oracle
  probed at `target/oracle/release/bund` where a claim was empirical.
- Submodule SHAs match the RFC header exactly, and every submodule is clean:
  `Bund` `21b40b0213a7`, `bund_language_parser` `80377728f45b`, `bundcore`
  `3b0b8ba219a6`, `rust_dynamic` `ceb27c96fa10`, `rust_multistack`
  `9a97675ee5d8`, `rust_multistackvm` `4605832678d4`.

This is a strong RFC. The grounding is real, the trailing-whitespace section
argues against an earlier draft of itself and wins, and D3's "a representation
Bund code cannot construct is not a representation of this language" is the
right argument. The findings below are what an adversarial reader found anyway,
ordered by how much they cost.

---

## 1. Blocking

### B1 — D5 is RESOLVED, blocks RFC-0003, contradicts D3, and is not cited

`docs/registers/decisions.md` D5 ("lambda body mutability", `Blocks: RFC-0003`)
resolves **write-once**, and states the consequence for this RFC in the
register itself:

> **Consequence for RFC-0003: the compiled cache needs no invalidation
> machinery.** Every mutating path returns a new value with a regenerated
> identity … so a cache keyed on **identity** simply does not contain the
> replacement. The default would have built a guard against something the value
> model makes impossible.

RFC-0003's D3 keys the cache on a **content hash** and specifies
**invalidation** — "invalidated when the body changes". Different key, plus
machinery D5 says is unnecessary. D5 appears nowhere in the RFC: not in
"Decisions consumed", not in D3's text, not in the alternatives.

The two register entries themselves pull apart — decisions-D3's resolution says
"content-hash compiled cache", D5's says identity — and this RFC is the
document that has to notice. Content hashing is defensible (decisions-D3's REPL
argument needs it, since eval'd snippets have no stable identity), but adopting
it silently is adopting a language decision on the owner's behalf. Cite D5,
say which key wins, and say what happens to D5's "no invalidation machinery".

### B2 — D2's preservation claim is false for `( … )` nested in `{ … }` or `[ … ]`

The Preservation table records `ctx` flattening as "preserved in the emitted
stream; **representation changed**", and D2 says lowering "emits the same
three-part stream the reference produces … so the runtime sees what it sees
today."

That holds at top level only. `lambda.rs:11` and `list.rs:11` pass the **outer**
`state` vector into `parse_pair`, and `ctx.rs:9,13` pushes into whatever vector
it is handed. So a `( … )` inside a lambda hoists its CONTEXT marker **and its
inner terms** out into the enclosing top-level stream, and the lambda body
receives only the `endcontext` CALL. Confirmed on the oracle:

    :F { 7 9 } register "ok" println        ->  ok
    :F { ( 7 ) 9 } register "ok" println    ->  REGISTER expecting lambda name
                                                to be string

The second fails because the hoisted `7` ran at top level, before `register`,
displacing the atom `:F`. A `ctx` AST node lowered *in place* — which is what
D2 describes — makes that program work, which is a deviation, not a
representation change. Either the table carries it as a deviation, or D2 states
that lowering hoists out of enclosing block nodes and reproduces the defect
structurally.

(The corpus appears not to contain a `(…)` inside a block, so this is probably
cheap to decide — which is what Q21 should have been asking.)

### B3 — "No Rust recursion, anywhere on the evaluation path" is unsupported for the `?`-family

D4 names three recursion sites: `lambda_eval`, and `execute`'s LIST and MAP
arms. Those are the easy ones — each is a tail position that becomes a frame
push. The hard ones are not listed, and they are the corpus's control flow:

- `conditional_ifthenelse::conditional_run` evaluates `if` (`:27`), then
  **pulls and casts the result** (`:31-38`), then evaluates `then` or `else`
  (`:40`, `:45`).
- `conditional_tryexcept::conditional_run` evaluates `try` (`:30`), **catches
  the Rust `Err`**, builds a value from `err.ctx` (`:34-37`), then evaluates
  two more lambdas (`:40`, `:44`).
- `conditional_ctx::conditional_run` evaluates three lambdas in sequence
  (`:62`, `:66`, `:70`).
- `execute_class` and `execute_object` (`execute.rs:88`, `:91`) — unread, and
  the RFC's closing note does not list them among its acknowledged gaps.

A native word that evaluates a lambda **and then inspects the stack** cannot be
expressed as "push a frame and return". It needs to suspend and resume. Exit
actions run on unwind; that is a different mechanism and it does not cover the
resumption point. D4 buys four things and this is the cost of all four — it
needs a paragraph saying how a `ConditionalFn` becomes re-entrant, or the
`?`-family stays recursive and the criterion in §Acceptance 2 is scoped to
lambda call depth.

### B4 — "`{` and `}` appear in 42 of the 69 captured goldens" is uncited and wrong

Measured over all 69 golden sources (45 under `reference/Bund/examples`, 12
under `reference/Bund/tests`, 12 under `tests/probes`): **49** contain a brace,
20 do not. Not 42, on any reading I could construct — the count is the same
whether or not comment lines are stripped.

The figure appears twice, and the second occurrence is inside acceptance
criterion 1, where it is load-bearing. Fix it and cite how it was measured.

## 3. Claims that need a citation and lack one

1. **The `STDLIB` mutex.** D7 says "The `STDLIB` mutex went the same way in
   RFC-0002 and for the same reason." No citation for `STDLIB` — it is
   `reference/bundcore/src/lib.rs:22`. And RFC-0002 does not remove `STDLIB`;
   it removes the **`BUND`** global mutex (RFC-0002:89, 152-161, 537), which is
   a different global in a different crate. The analogy is asserted and the
   cross-RFC half of it is not true as written.
2. **"42 of the 69 captured goldens."** See B4.
3. **The D1 oracle probes.** "Confirmed against the oracle — `{ 1 println}`
   parse error, `[1 2] println` accepted" has no capture and no probe file. I
   re-ran both and both hold, as do F49's `1_000` error and F51's `{}` error.
   But **F21 applies to all of them**: the built oracle links
   `bund_language_parser-0.14.0`, `bundcore-0.7.0` and
   `rust_multistackvm-0.38.0` **from crates.io**, not the pinned submodules —
   its own error output prints the `~/.cargo/registry/...` paths. Every
   "confirmed against the oracle" line in this RFC inherits that gap, and the
   RFC does not mention it. D21 says authored probes belong in `tests/probes/`;
   these are the probes the RFC's design turns on and they are not there.
4. **"RFC-0000's 'three live tables' counted word registration only."** It is
   RFC-0000:135; no pointer given.
5. **"`{` and `}` … the single largest blocker to conformance."** No analysis
   showing braces are the *binding* constraint rather than one of several
   co-occurring ones. Acceptance criterion 1 depends on the difference.
6. **`element` "…which is why `←`, `Σ` and `$` are ordinary name characters."**
   The count of seventeen punctuation characters at `bund.pest:36` is exact,
   but not one of the three examples is among them: `Σ` matches `LETTER`, and
   `←` and `$` match `SYMBOL`. The sentence credits the wrong alternative for
   the effect it describes.

## 4. Acceptance criteria

**1 — not checkable, and internally contradictory.** It asserts three different
things in four sentences: "conformance strictly increases", then "must pass
every golden it passes at 4/69 today, plus the goldens gated only on block
syntax", then retreats to "no golden that passes before this lands fails after
it, and every golden whose only unimplemented construct was `{ }`, `[ ]` or
`( )` parses without error". The retreat permits zero increase, contradicting
"strictly increases". And nothing named in the RFC computes the set "whose only
unimplemented construct was" — `cargo xtask conform` compares captured bytes
(`xtask/src/conform/mod.rs`, per F48) and has no parse-only mode to report
"parses without error" separately from passing. Name the tool that decides this
or drop the clause. *(4/69 is confirmed against `tests/golden/CONFORMANCE.txt`.)*

**2 — checkable.** Names the test and the depth. Two gaps: "completes or
reports a Bund-level error" admits an infinite loop or an OOM kill as a pass,
so bound the wall clock; and it silently scopes to *call* depth, not *nesting*
depth — see §6.5.

**3 — checkable, and the best criterion here**, because it names a mechanism and
forbids a permitted difference. Three gaps. The differential harness does not
exist and is not assigned to a work item. "Compares the emitted value streams
element by element, with no permitted difference" cannot hold literally: every
`Value` carries a fresh `id` and `stamp` (D1, D2, and F14 on exactly this), so
the criterion needs a stated normalisation or it is unsatisfiable. And the
corpus is 132 programs while only 69 have goldens, so the other 63 need a live
oracle run — which lands back on F21.

**4 — checkable**, and the only criterion that says the right thing about where
truth lives ("against the oracle's behaviour, not merely against this
document"). Should name `tests/probes/` per D21.

**5 — checkable for F53**; the F57 half is not, as written. "A `context` whose
lambda raises inside a `?try` leaves the interpreter on the stack it started
from" needs the observable named — no word the RFC cites prints the current
stack name, so the test needs to say what it asserts on.

**6 — half checkable.** "No second copy of the eval loop exists in the
workspace … Checkable by grep" — grep for what? A duplicated loop has no
literal to match. The second half ("a test that a fix to one is visible from
the other") is real and sufficient; drop the grep.

**7 — very nearly vacuous for this document.** `cargo xtask cite`'s hard checks
are: file exists, line exists, and **exact match of fenced blocks whose info
string carries a citation** (`xtask/src/cite/mod.rs`, header). RFC-0003 contains
**no fenced block with a citation info string**. So all four defects in §2 pass
it — including C1, which is the same class of error (`execute.rs:28` should be
`:27`) that motivated writing the tool. If this RFC wants criterion 7 to mean
something, quote the four or five load-bearing lines as cited fenced blocks.

## 5. Preservation analysis — behaviours it does not enumerate

Beyond B2 and B3:

**P1 — fixing F53 widens `execute.` into arms that are wrong for the workbench,
and the table calls the fix "widening only".** With the `:117` guard removed,
`execute.` on a LIST reaches `execute.rs:40-48`, which pushes each element onto
the **main** stack (`:41`) and then recurses with `op` still `FromWorkBench`
(`:42`) — pulling from the workbench, not from what it just pushed. The MAP arm
pulls its key from the **main** stack (`:56`) regardless of `op`. Today those
paths are unreachable through `execute.` whenever the main stack is empty;
after the fix they are reachable. "`execute`'s eight arms and their errors |
preserved exactly" and "F53 — widening only" cannot both survive that. The RFC
has to say what `execute.` does on a LIST.

**P2 — how `?try` catches, in a loop with no Rust stack to unwind.** D5 says
error text is preserved and `?try`'s `context` slot is unchanged. But
`conditional_tryexcept.rs:37` stores `err.ctx`, and today `err.ctx` is a
concatenation assembled by `bail!` at every level it passed through
(`lambda_eval.rs:17`, `execute.rs:45`, and the eval loop's wrapper at
`bundcore_eval.rs:33`). Preserving that string means preserving that nesting in
a design that replaces the nesting with a frame stack. Nothing states how frames
pushed by the failing lambda are discarded, or which frame the unwinder stops
at.

**P3 — `through` is a ninth conditional type, registered from another crate.**
`execute_types/mod.rs:36` inserts `"through" → conditional_through::conditional_run`
into `CF` from `rust_multistackvm`; the other eight come from `Bund`
(`conditional/mod.rs:20-27`). §5's enumeration and D7's "populated at
construction" both miss the cross-crate half, which is the part that makes
"a field on the registry RFC-0002 already owns" non-trivial. `raise`
(`conditional/mod.rs:44`) is a ninth registered word in the same family and is
also unmentioned.

**P4 — D8 changes `$name`.** F26 and ERRATA both record that `$` does **not**
bypass alias resolution: `apply` skips the alias step at `:39`, but
`call_internal_word` strips the sigil and calls `i()`
(`multistackvm_call_internal_word.rs:7-8`), and `i()` resolves aliases
(`multistackvm_inline.rs:71-72`). D8's "stops being paid twice per call" is
removing the *only* resolution `$name` gets. Not in the table, and F26 is not
referenced anywhere in the RFC.

**P5 — D8 must preserve the three-tier inline fall-through.** ERRATA records
`i_direct` trying the VM's table (`multistackvm_inline.rs:42`) then the stack
layer's (`:52`), and D16 point 3 makes the order contract. A monomorphic
`(Symbol, generation) → resolution` cache has to say what a "resolution" is
across three tables and which generation invalidates it. RFC-0002's generation
is **per slot** (RFC-0002:375), and RFC-0002:945 records its overflow policy as
still missing — so D8 depends on an unfinished part of RFC-0002.

**P6 — `autoadd`'s disable side.** §3 states the enable guards
(`autoadd.rs:6-8`, `:9-11`). The disable path bails with the *same* message,
"You can not nest autocollection", when autocollection is already off
(`:17-18`), and also requires a non-empty stack (`:20-22`). "Preserved exactly"
is the right disposition; the enumeration is incomplete, and the duplicated
message is the sort of thing a faithful port reproduces only if it is written
down.

**P7 — `cmd` is `cmd+`.** `bund.pest:30, 44` means `::`, `;;` and `:;` are
single command tokens, and `command.rs:8` turns them into `Value::call("::")`,
which resolves to nothing. The handler table shows only `Value::call(":")` and
`(";")`.

**P8 — `atom`'s byte-index slice.** `atom.rs:8` slices `[1..t.len()-1]` by byte
and is safe today only because the grammar guarantees a trailing ASCII
whitespace character. D1 widens the terminator set to include end-of-input. One
line, but it is exactly the arithmetic a faithful port copies without noticing
the guarantee moved.

**P9 — the error-text preservation in D5 collides with F14.** The eval loop
interpolates the offending word with `{:?}` (`bundcore_eval.rs:33`), and F14
records that this text embeds `id` and `stamp` and therefore cannot reproduce.
D5's "the reference's error text is preserved verbatim where a golden captures
it" should say the *wrapping shape* is preserved and the interpolated value is
not, or cite F14 and defer.

**P10 — `Bund::run` is a third caller shape D6 does not name.** `bundcore_run.rs:6-22`
wraps `eval` and pulls from the **workbench first, then the stack** (`:9-14`);
`run_snippet_for_cmd` uses it and prints the result (`run_snippet.rs:38-47`)
while `run_snippet_for_script` uses `eval` and does not (`:85`). Collapsing to
one evaluator is right; "`bund.eval` and the top-level script path both use it"
omits the CLI `eval` subcommand's return-value behaviour, which is observable.

## 6. Consistency with the registers, the accepted RFCs, and ERRATA

**6.1 — D5 not consumed.** See B1.

**6.2 — D11 is RESOLVED, `Blocks: RFC-0003`, and is not consumed.** "Version the
IR format freshly." RFC-0003 defines BundIR and says nothing about a format or a
version. Under D3 the IR may never be serialised at all — in which case say so
and discharge D11 explicitly. Leaving a resolved blocking decision unaddressed
is how it gets adopted by default later.

**6.3 — Q21 and Q22 do not exist.** `docs/registers/open-questions.md` runs to
Q20. The RFC mints Q21 and Q22 in its own Open questions section without adding
them to the register, so no other session can see them. The closing "the read is
partial for the word vocabulary" note has the same problem and is exactly what
that register is for.

**6.4 — the "Supersedes" header supersedes nothing.** `05-rfc-roadmap.md` §1.1
already says what the RFC's alternatives section says, nearly word for word:
"`?ifthenelse` is not a control-flow construct the compiler can see … BundIR
needs CONDITIONAL as a first-class value with a helper-call execution path …
Literal `if`/`times`/`while`/`loop` remain statically analysable; the `?`-family
does not." Nothing is refined. A "Supersedes" header pointed at an immutable
research document, with no ERRATA entry and no actual contradiction, invites the
precise confusion the immutability rule exists to prevent. Drop the line.

**6.5 — RFC-0000 assigns BundIR a crate and a pipeline this RFC quietly
redraws.** RFC-0000:180 gives `bund2-ir` as "AST to BundIR; the only crate that
defines the instruction set". RFC-0003's pipeline is AST → `Vec<BundValue>` →
*optional* BundIR cache. `bund2-ir` is never named; nothing says which crate
owns the cache, or that "AST to BundIR" is no longer the path. This is a real
architectural change and it belongs stated against RFC-0000 rather than left for
a reader to infer. (`bund2-syntax` and `bund2-interp` do match RFC-0000:179,181.)

**6.6 — three documents now cite three ranges for `execute`'s arms.** ERRATA
says `execute.rs:26-97`; D16 says `:26-33` / `:36-48` / `:53+`; RFC-0003 says
`:26-98` / `:40-48` / `:56-72`. All resolve; the MAP arm actually begins at
`:55`. Cosmetic, and `cite` cannot see it, but it is drift.

**6.7 — F56's count, adopted by this RFC's disposition.** F56 says "Bund2
registers 45 aliases from this table minus this one." `create_aliases.rs:4-45`
holds **42**. RFC-0003 wisely does not repeat the number but does adopt the
disposition; fix the register before an implementation copies it.

**6.8 — `tests/golden/CONFORMANCE.txt`'s own comment says "59 goldens"** while
the number below it is `4/69` and there are 69. Stale, not this RFC's doing, but
criterion 1 is measured against that file.

**Consistent, checked:** decisions-D3 and D16 are both RESOLVED and the RFC's
use of them is faithful — including D16's "the world is permanently open" as the
justification for a call target computed at runtime. The ERRATA entry on `!` is
paraphrased correctly (69 invocations across 39 of 132 programs; `execute` never
spelled). F48's caveat under Open questions is correctly stated and correctly
scoped. The RFC's §3 resolution order is *more* accurate than D16 point 3's,
which omits `autoadd`.

## 7. Assumed but not stated

1. **That lowering the AST to `Vec<BundValue>` is total and information-
   preserving.** Criterion 3 depends on it; D2 introduces an AST node with no
   value counterpart; nothing states lowering is even a function.
2. **That identity is normalised out of criterion 3's comparison.** See §4.3.
3. **That the content hash excludes per-value identity.** Every `BundValue`
   carries a fresh `id` and `stamp` (D1, D2). A literal hash of the body never
   repeats, the cache never hits, and D3's resolution of decisions-D3 quietly
   fails. This needs one sentence and currently has none.
4. **That native words can call back into evaluation without Rust recursion.**
   See B3.
5. **That "no Rust recursion on the evaluation path" excludes the parser.**
   `parse_pair` recurses through `lambda.rs:11`, `list.rs:11` and `ctx.rs:11`,
   so deeply nested brackets overflow at parse time. Criterion 2 tests call
   depth. If the exclusion is deliberate, say so.
6. **That the frame loop reproduces the nested `bail!` concatenation** that
   `?try` files into its `context` slot. See P2.
7. **That RFC-0002's generation counter is finished enough for D8.** RFC-0002:945
   lists its overflow policy as unresolved.
8. **That removing the `\n` append is neutral.** It is applied *twice* on the
   CLI paths (`run_snippet.rs:15,62,100,138,162`, then `bundcore_eval.rs:8`).
   The argument in D1 covers the single-append case only; it does happen to hold
   for the double, but the RFC should say so rather than not notice.
9. **That the oracle behind "confirmed against the oracle" is built from the
   pins.** It is not — F21, verified again today from the binary's own output.
10. **That `curry`'s generated body is stable under D8.** It ends in
    `Value::call("!")` (`conditional_curry.rs:51`) — an alias — so every curried
    word's last instruction is a call site whose cache D8 must invalidate on an
    alias-table generation bump.
11. **That "the goldens gated only on block syntax" is a computable set.**
    See §4.1.
12. **That `{ }` is only ever a lambda literal.** §7's corpus idiom shows
    `?try :try { … } set`, where the lambda is a *value filed into a MAP*, and
    D5's register entry counts 45 such sites (`:.init { ... } set`). The RFC
    describes `{ }` as "a lambda-valued argument", which is true, but the
    implication that a block is a call target is what BundIR would want and is
    exactly what D5 and §5 say it is not.

## 8. Smaller notes

  `execute.rs:42,67` — both correct, and both are the recursive call rather than
  the arm. Good.

  additionally records that the *base* function's own workbench guard at

  clause in D-space rather than only in the register.

  named in the closing note all exist at
  `reference/Bund/src/stdlib/functions/values/`. The self-declared grounding gap

  it (see B3).
- `registry.rs:88-90` registers `unregister` twice, so `stdlib_class_unregister`
  is unreachable — already F1/F32, no action here, noted only because §6 cites
  that file and a reader may trip on it.
