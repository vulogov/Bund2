## Should fix

### S1. R25's stamp does not show that nothing reached a log whole

§S9 under R20, and R25 as ruled, say:

> A shard log's length grows only once a write and its `sync_data` have
> succeeded (`smysl-text/src/shards.rs:380-382`), and the stamp is a
> function of those lengths. … An unchanged stamp means no record reached
> any log whole. At most one log holds a torn tail.

`ShardLog::append` does this (`smysl-text/src/shards.rs:371-384`):

1. opens the file for append;
2. cuts a torn tail;
3. calls `f.write_all(bytes)`;
4. calls `f.sync_data()`;
5. only then runs `self.len += bytes.len()` and updates the hasher.

`Library::stamp` is computed over these in-memory `len` and hash fields
(`smysl-text/src/library.rs:993-995`; `smysl-text/src/shards.rs:395-416`).
It is not computed over the files. So the stamp does not move in two cases
where whole records of the failing shard's batch are already in its file:

- **`write_all` fails part way**, for example on `ENOSPC`. `bytes` is
  every record routed to that shard, concatenated
  (`smysl-text/src/shards.rs:523-524`). A short write followed by an error
  leaves the records before the cut whole in the file and the next one
  torn.
- **`write_all` succeeds and `sync_data` fails** (`EIO`). The whole
  shard's batch is in the file and visible to the next open, and `len`
  has not moved.

In both cases R25 drops the locks, and the word answers SM02 "with
SMYSL's reason". Yet the next open reads some of the batch. For example,
it may read a unit without its attestation, or a relation whose
endpoint's own shard was the one that failed. That is the partly written
library that R20 keeps the locks to flag. When the failing shard is the
first in the batch, no earlier shard has grown, so this is not a rare
corner of a rare corner. It is the whole of the single-shard case,
`smysl.unit`'s usual one.

**Needed.** Correct the claim in §Current, §S9 and Q51. The owner should
know that R25's stated reason does not hold. Whether R25 stands is the
owner's to decide, not this review's. One rule that does have the claimed
property: compare each shard log's **on-disk length**
(`std::fs::metadata(root.join(shards::log_path(name)))`, where `log_path`
is public, `smysl-text/src/shards.rs:65`) before and after the failed
call. Keep the locks if any file grew. That over-approximates a torn
tail, which the RFC already treats as harmless, but it never
under-approximates a whole record. Criterion 15 has no case for this
path. A test can reach it on Linux by appending to a library on a
small filesystem that fills up.

### S2. R22's list of SMYSL's unlocked writers names a flag that does not exist and misses `ingest --text`

§Current's table, §S9, U9, the Preservation row, R22, and D245's ruled
text all name "`measure --save`".

- **`measure` has no `--save`.** Its arguments are defined from
  `smysl:src/main.rs:1082`. The only write flag is `--dry-run`, "Print
  the values and refusals and write nothing" (`:1163-1167`). Without it
  the command appends (`:7536-7539` returns early only for `dry_run`, and
  `:7579` appends). So plain `smysl measure` is an unlocked writer. The
  documentation R22 A requires would tell a user that only
  `measure --save` is unsafe, and that flag cannot be typed. `assess`
  works the same way (`--dry-run` at `:1245-1249`), and the RFC already
  names it without a flag.
- **`smysl ingest --text` also appends to a library without locks.** It
  opens the library with `Library::open` (`smysl:src/main.rs:10803`),
  builds a `TextIngest` over it (`:10947-10948`), and the ingest crate
  commits each window with `t.lib.append_records`
  (`smysl-ingest/src/text/run.rs:546,635`). Nothing in `smysl-ingest/src`
  or in `cmd_ingest_text` calls `acquire_all`. Of the six, this is the
  longest-running writer: it commits window after window across a model
  run. It is a Phase 2 command for Bund2, but a SMYSL user can run it
  today against a library a Bund program writes.

A search of every `append_records`, `add`, `append` and `redact` call in
`src/main.rs` and the pure and ingest crates finds no other unlocked
writer. `smysl-lib/src/access.rs:193` is reached through the locked
`with_library`.

**Needed.** In §Current, §S9, §S11 U9, the Preservation row and R22's
row, say `measure` (unless `--dry-run`) and add `ingest --text`. D245's
ruled sentence names `measure --save` and lists five commands. It needs
a dated note, since the documentation it orders would be wrong as ruled.

### S3. M3 claims criterion 15's re-open case, which uses `smysl.append`, a word M4 builds

Revision 8 states the plan's rule: "Each criterion is claimed by the
first milestone at which every word it uses exists." M3 claims "15's …
re-open cases". The re-open case reads: "With the probe armed to `pause`,
a `smysl.append` of two new units stops after its first open." M3 builds
`smysl.create` and `smysl.unit`. The plan's table adds `smysl.append` in
M4. This is the class of error the sixth review's B2 raised, reintroduced
in the reordering.

**Needed.** Move the re-open case to M4. Or restate it with `smysl.unit`:
pause a `smysl.unit` of unit 2 after the test has queued unit 1 through
SMYSL's API. That loses the "appends neither that unit" half, which needs
both units in one batch, so moving the case is the better fix.

### S4. No CI step builds the probe, so criterion 15's panic and pause cases never run in CI, and the unlock step has no home

§S9 puts `pause`, `panic` and their tests behind `smysl-panic-probe`, "on
no default and in no shipped build". §S1's five CI steps run
`--features smysl` only:

- `cargo nextest run -p bund2-stdlib --features smysl --profile ci`;
- `cargo nextest run -p bund2-cli --features smysl --test smysl_demo`;
- clippy, the feature matrix and `cargo deny`, all with `--features smysl`.

None of them turns on `smysl-panic-probe`. So the panic case, the re-open
case and everything that depends on them never runs in CI. Clippy never
sees the probe's code either, and that code holds a `panic!` the
workspace lints deny.

The panic case also ends with "After `bund2 smysl-unlock <root>` lists
every one of those locks … and `--yes` breaks them all, a write
succeeds". `smysl-unlock` is a `bund2-cli` subcommand (§S9), while the
probe is a `bund2-stdlib` feature armed by "the crate's own tests". A
`bund2-stdlib` test cannot run a `bund2-cli` subcommand. A `bund2-cli`
test needs the probe forwarded, as `panic-probe` is forwarded
(`crates/bund2-cli/Cargo.toml:53`, `crates/bund2-runtime/Cargo.toml:33`).
The RFC declares neither.

**Needed.** Add to §S1 and M3:

- a CI step that runs the probe-gated tests:
  `cargo nextest run -p bund2-stdlib --features smysl,smysl-panic-probe --profile ci`;
- the probe in the clippy run;
- `bund2-cli`'s forwarding feature, or a statement that the unlock half
  calls the subcommand's function directly from a `bund2-stdlib` test,
  and where that function lives.

D220's step for `test.panic` (`.github/workflows/ci.yml`, "a panic under
the tier, reported") is the precedent.

### S5. `--noio` does not reach the `smysl` conditional's handler, which D119 requires

R11 A, §S8's SM06, the Preservation row and criterion 18 stub "every
`smysl.` word that touches disk". The `smysl` conditional is not a
`smysl.` word, and its runner opens the library and runs a query (§S6).

D119 (`docs/registers/decisions.md`, "`--noio` gates `csv` and
`sqlite`") ruled that under `--noio` "so are the two conditional
handlers". `crates/bund2-stdlib/src/data.rs:476-494` gives the reason:
"`conditional` builds a CONDITIONAL of any type, so a program can make a
`csv` one without calling `csv`; stubbing the word alone would leave the
read reachable". The same holds for `Conditional("smysl")`. As written,
a `--noio` program can still read any library it can name.

**Needed.** Under `--noio`, stub the constructor `smysl` and its
conditional handler, as D119 does for `csv` and `sqlite`. Add D119 to
"Decisions consumed". Extend criterion 18's `--noio` case to the
conditional, and the Preservation row to it.

### S6. §S5's environment still leaves out the measure's `Input`, so criterion 10's T1 has no defined direct call

Revision 8 names the scope, the `Env`, `PlanOptions::default()` and the
base `Recipe`. A measure also takes an `Input`
(`smysl-measure/src/lib.rs:246`), and a text measure such as T1, which
criterion 10 uses, reads text only through it. SMYSL's `measure` builds
it like this (`smysl:src/main.rs:7366-7438`):

1. the scope is resolved with `ms::resolve(scope_text, &env, &PlanOptions::default())`
   (`smysl-measure/src/scope.rs:100`);
2. when any requested id `needs()` `TEXT`, the text is read with
   `texts(scope_text, &library)` and
   `Corpus::load(&library, &found, level, analyzer)`
   (`smysl-measure/src/text/mod.rs:160,436-440`);
3. `Input::new(library.store(), &resolved).with_library(&library)` is
   built, then `.with_text(&corpus)` when there is a corpus.

The level and analyzer come from flags. Under "the base Recipe" they
would be `Level::default()` and `None` (`smysl-measure/src/recipe.rs:202,206`),
but the RFC does not say so. It also does not say that a text measure's
scope must be a text scope (`from texts …`), which a unit measure's
filtering scope is not (`smysl:src/main.rs:7385-7387`).

**Needed.** State the three steps in §S5, with the level and analyzer
taken from the base `Recipe`. Criterion 10's direct calls should name
them. If `Corpus::load` or `texts` turn out not to compose from outside
SMYSL, that is Q55's spike, and the spike should include a text measure.

  "Each refusal code is tested in the milestone that first raises it."
  SM11 is raised by every word from M2, but it is listed under M10. SM02
  is first raised in M3 (`smysl.unit` with a gist of spaces; the guard's

- **N5. Criterion 12's libraries with views.** No `smysl.` word writes a
  view, and `smysl.parse` skips views (§S4). So all four view libraries,
  not only the `smysl/content/1` one, are built through SMYSL's API. Say
  so.
- **N6. Re-binding a label.** `smysl.label` on a label already bound to
  another unit writes a second `LabelBinding`. From then on the label is
  ambiguous, and every later use is SM08 (`smysl-graph/src/labels.rs:3-8`).
  Nothing removes a binding. The RFC should say whether `smysl.label`
  refuses a label bound to a different unit (SM08 at bind time), or

- **N7. Criterion 17's demo must start from an empty library.** Run a
  second time against the same root, `smysl.retract` answers NODATA, no

  manifest. So `expected.txt` holds only for a fresh library. Say where
  the demo's library lives, and who empties or creates it for each run:
  the test's temporary directory as the working directory, for example.
- **N8. SM02 with `SMY-E440` is Bund2's own refusal.** Bund2 refuses an
  oversized `path` before SMYSL is called (§S4), so SMYSL never raised
  it. The SM02 text, "SMYSL refused it: <code> <message>", attributes the

  the stamp grows by that writer's bytes. A failure later in the batch
  then keeps the locks although Bund2 wrote nothing. This is conservative
  and rare, and it falls inside R22's hazard. Mention it beside R25.

## Preservation: what is missing

- **`--noio` and the `smysl` conditional** (S5). As written, a `--noio`
  program reaches a library through `Conditional("smysl")`.
- **Concurrent use with SMYSL** (S2). The row names `measure --save`
  instead of `measure`, and leaves out `ingest --text`.
- **A failed write that leaves part of its batch whole on disk, with the
  locks released** (S1). The R20 row says the locks are kept whenever a
  log has grown. Under the in-memory stamp that is true of `len`, not of
  the file.
- **The wall clock enters the library.** Attestation clocks
  (`Hlc::now`) and the dossier's clock make two runs of the same program
  write different attestation records. Uids do not change, since
  attestations are outside identity (`smysl-core/src/types/unit.rs:20-22`).
  This bears on N7. A row saying so would make it explicit.
- **The process-wide mutex table only grows.** An entry per canonical
  root is never removed. That is harmless at the sizes intended, but it
  is state that outlives every VM.

## Consistency

- **RFC-0013.** §S7's node table matches RFC-0013 §S15 and D230. §S6's
  runner matches §S11 except where N11 of the sixth review asked for the
  difference to be stated, which revision 8 did. §S11 says `query`'s
  `lambda` runs on the current stack and nothing restores it. RFC-0014
  does not say whether the `smysl` runner does the same (assumption 5).
- **D119** is not consumed, and S5 conflicts with it.
- **D245.** Its R22 text names `measure --save` and five commands (S2).
  Its R25 text rests on the stamp claim S1 corrects. Both need dated
  notes. Neither ruling is re-argued here.
- **ERRATA.** `docs/research/ERRATA.md` does not mention SMYSL or
  RFC-0014, and nothing here contradicts a research document.
- **Registers.** Q57's revision-8 note repeats the five names (S2). Q51's
  revision-8 narrowing repeats the stamp-free claim that "shards written
  before a failure keep their records". That holds, but the failing shard
  can also keep whole records (S1).

## Assumptions the RFC makes but does not state

1. **A failed `write_all` or `sync_data` leaves no whole record in the
   file** (S1).
2. **No SMYSL command beyond the five named writes a library unlocked,
   and `measure` writes only with a flag** (S2).
3. **The probe-gated tests run somewhere** (S4).
4. **`--noio` cannot reach a library except through a `smysl.` word**
   (S5).
5. **The `smysl` conditional's `lambda` runs on the current stack with
   nothing restored, as `query`'s does (RFC-0013 §S11), over an answer
   computed in full before the first run.** A lambda that writes to the
   same library therefore does not change the units the conditional
   still has to visit. That is safe, since the runner holds no lock, but
   it should be said.
6. **The demo starts from an empty library** (N7).
7. **A label is bound once** (N6).
