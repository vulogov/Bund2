## Blocking

### B1 — Step-into does not work for most bodies, because most bodies do not run in the flat loop

§D1: "**Step-into works for words, lambdas and `bund.eval`'d code alike**,
because all three are bodies in frames. … it is not new work here — it is what
RFC-0003's loop already did."

Not in the code as built. A driven `Interp::step()` can return to the caller
only between two iterations of `run_to`. Whenever a *native* runs a body, that
body runs in a **nested `run_to` inside the native's Rust frame**:

- `eval_lambda` pushes a frame and calls `self.run_to(floor)` before returning
  to the native (`crates/bund2-interp/src/lib.rs:1507-1530`);
- `Interp::apply` does the same (`:964-985`);
- `bund.eval` is `eval_source`, which loops over the compiled string and
  calls `vm.apply(word)` on each value (`crates/bund2-stdlib/src/singles.rs:327-340`).
  **So `bund.eval`'d code is the worst case the RFC names as working**, not the
  best.

RFC-0003's third amendment names the natives that do this: "`times`, `loop`,
`map`, `while`, the conditionals, `?try`, the method paths — still spends a
Rust frame per level" (`docs/rfc/RFC-0003-syntax-ir-and-tier0.md:1042-1045`).
There are 23 `eval_lambda(` call sites in `crates/bund2-stdlib/src/`. §S4's
design — "Re-entrant natives are resumable, not recursive … a small state
machine" (`RFC-0003:521-535`) — is not what was built for them.

To stop inside a `times` body, `step()` must suspend a native mid-call and
resume it later. That is precisely **D6**: "Is fine-grained suspension inside
a word required, or is VM-per-task enough?" — **Status: OPEN**, default
VM-per-task (`docs/registers/decisions.md:324-328`). RFC-0003 already said so:
"**The `--debugger` path is now in D6's scope.** … the observer's interface is
not designed here" (`RFC-0003:944-946`). RFC-0008 mentions D6 only as a
blocker of RFC-0007 (§D6), and lists it neither as consumed nor touched.

This is the failure CLAUDE.md names: a required deviation (or an unmade
decision) filed as "not new work". The RFC must either:

1. take D6 to the owner, since stepping inside a loop or conditional needs
   resumable natives; or
2. state that step granularity stops at any native that runs a body
   synchronously — that `step` over `10 { … } times` is atomic, as the
   reference's top-level `vm.apply` is — and list it as a limit that survives
   into Bund2 in the Motivation table (the "Granularity" row).

Either way, research §3.3(a)'s "all IR bodies in frames" is contradicted by
Bund2 as built and needs an ERRATA entry. Criterion 5 would not catch this: a
stepper whose unit is the top-level value passes it (see S10).

### B2 — The reference's command-line debugger surface is missing from "Current behaviour"

The RFC's contract is thirteen words. The reference also has four CLI flags
that are this RFC's subject:

| flag | behaviour | citation |
|---|---|---|
| `--debugger` | "Run BUND code inside debugger": `script`, `eval` and `shell` hand the **whole program** to `bund_debugger` instead of `bc.eval` / `bc.run` | `reference/Bund/src/cmd/mod.rs:124-125`; `reference/Bund/src/stdlib/helpers/run_snippet.rs:23-35,70-82` |
| `--debug-shell` | "Drop to DEBUG shell if error occurs": after an uncaught error, run `debug_shell` on the failed VM | `mod.rs:127-128`; `run_snippet.rs:31-33,51-53,78-80,89-91` |
| `-d` / `--debug` (count) | Log verbosity: 0 → `BUND_LOG_LEVEL` or `error`, 1 → `bund=info`, 2 → `bund=debug`, 3+ → `bund=trace` | `mod.rs:121-122`; `reference/Bund/src/cmd/setloglevel.rs:6-31` |
| `--profile` | Prints `time_graph`'s full graph as a table after the command | `mod.rs:106-110,136-137` |

F52 — which the RFC quotes twice — ends "and **`--debugger` uses the
third**" (`docs/registers/defects.md:1674`).

Three consequences:

- **The open question "Whether the debugger is a word, a flag, or both" is
  mis-framed.** "The reference has the word `debug`; the research assumes
  `bund2 run --debug`." The reference has both already. "Both" is not a
  proposal; it is preservation.
- **`--debug` is taken.** In the reference it raises the log level. Naming the
  debugger flag `--debug` would give a reference flag a different meaning, in
  a CLI that otherwise cites the reference flag by flag
  (`crates/bund2-cli/src/main.rs:309-312`). And Bund2 has no `run` subcommand:
  the shape is `script --file` (`main.rs:276-277`). `--debug-values` already
  exists as an alias of `--raw-values` (`main.rs:293`), which is a third near
  collision.
- **`--profile` is a user-visible behaviour F7's FIX removes the source of.**
  §D7 says "Nothing in Bund2 carries a `time_graph`-style attribute, so there
  is nothing to remove". True of attributes, but the flag's output is
  something a user runs. Preservation needs a row for it.

Each flag needs a row in Current behaviour and a disposition in Preservation.

## Significant

### S1 — `debug.dump` is described from the research, not the code

"`debug.dump` hexdumps `bytemuck::bytes_of` of the *scalar* for INT, FLOAT and
BOOL — so eight little-endian bytes, reproducible — and `to_binary()` for
everything else (`debug_dump.rs:20-55`)."

The cited range says otherwise:

- **STRING has its own arm.** It `conv(STRING)`s, `cast_string`s, and dumps
  `str_raw.as_bytes()` (`debug_dump.rs:40-50`) — the UTF-8 bytes, no id, no
  stamp. **Reproducible.** It does not go to `to_binary`. Research §3.1's
  table has the same omission, word for word, which is how it reached the RFC.
- **BOOL is one byte, not eight.** `cast_bool` returns `bool`
  (`reference/rust_dynamic/src/cast.rs:25-28`), and `bytes_of(&bool)` is one
  byte (`debug_dump.rs:34-38`).
- **"Little-endian" is native-endian.** `bytes_of` is a memory view. On every
  host Bund2 targets today they coincide. Say that rather than rely on it.
- **`dump` peeks, it does not pull** (`:14`). The value stays on the stack;
  the RFC does not say so, and an implementation that pulls would break every
  program using it.
- **Seven error texts** (`:16,22,29,36,43,47,57`), starting `DUMP: NO DATA #1`,
  are absent from Preservation. They are as checkable as `log.*`'s.
- **The output format belongs to a crate outside `reference/`.**
  `hexdump::hexdump` prints through `println!` in `hexdump` 0.1.3
  (`reference/Bund/Cargo.lock:3650-3652`). Criterion 2's "byte-identical" is
  a promise to reproduce that crate's line layout. The format cannot be cited
  into `reference/`. It needs an `[UNGROUNDED]` marker and an entry in
  `open-questions.md`, or a golden captured first to stand as its ground.
- "the encoding carries the id and the stamp" has no citation. It should point
  at `rust_dynamic`'s `to_binary`.

Criterion 2 should add a STRING row. The Preservation row "`to_binary` path"
covers fewer types than it says.

### S2 — Where `log.*` output goes is answerable from source, and the answer breaks criterion 1's hermeticity

The first open question says the destination is "the binary's logging
configuration", undecided, and "Not a language question". The reference
decides it: `env_logger`, which writes to stderr, with a default filter of
`error` unless `BUND_LOG_LEVEL` is set, raised by `-d`
(`reference/Bund/src/cmd/setloglevel.rs:7-31`).

The registers already carry the consequence. `open-questions.md`'s *Hermetic
partition* (`docs/registers/open-questions.md:585-589`) classifies `log.*` as
hermetic **because "the golden format records stdout, not stderr. If goldens
ever capture stderr, its default timestamped format makes these words
non-hermetic."** Goldens now capture stderr. `drain` appends it to stdout
(`xtask/src/golden/mod.rs:419-446`). So:

- a probe where `log.error` **succeeds** captures an `env_logger` line with a
  timestamp, which no normaliser handles;
- `log.info`/`warning`/`debug`/`trace` emit nothing at the default filter, so
  a probe of them checks nothing but the absence of a line;
- the capture inherits the caller's environment (`run_once` sets no env,
  `:364-373`), so `BUND_LOG_LEVEL` in the reviewer's shell changes a golden.

Criterion 1 as written (empty stack, uncastable value) still checks: both are
errors and go through the report, not the logger. But the RFC must cite the
Hermetic-partition note and say that its premise has failed. It must also
decide what Bund2's `log.*` write at which level before any positive-path
probe exists. That is a disposition, not an open question.

### S3 — `debug.display_hostinfo` is an approved deviation, not "Preserved"

The Preservation row says "**Preserved**, built". D53 records the opposite:
"the six version rows name Bund2's own crates and versions … recorded as an
approved deviation" (`docs/registers/decisions.md:3209-3237`). This is the
subject-search miss CLAUDE.md warns about: D53 says `Blocks: nothing`.

### S4 — `debug.display_distributed_info` already has an "absence" behaviour, and neither option in the open question is it

Without `--distributed`, the reference logs
`BUND must be in distributed mode. You shall pass --distributed to CLI` at
`error` level and returns `Ok`, printing **nothing** to stdout
(`debug_display_distributed_info.rs:21-25,71-75`). Bund2 has no distributed
mode, so every Bund2 run is that branch. Reproducing it is the preserving
answer. Both of the RFC's options, "reports its absence" (in some new form)
and "the reference's table with empty fields", are deviations from it. The
Preservation row ("Preserved in shape … reports its absence rather than
inventing state") needs to name the reference's own absence text. That text
goes through `log::error!`, so S2 applies to it too.

### S5 — §D2 understates the span work. Nested values have no span at all

"`lower_with_spans` produces `Lowered` with a span per value … Threading one
through is the substance of §D2."

`lower_with_spans`'s own doc: "**Top level only.** A value inside a lambda
body carries no span … positions for nested values need the IR RFC-0003 §S5
describes, which does not exist yet"
(`crates/bund2-syntax/src/lib.rs:702-707`). There is nothing to thread for a
body: the spans must first be *produced*, which is RFC-0003 §S5's unbuilt
work. And `bund.eval` lowers with `compile`, not `lower_with_spans`
(`singles.rs:328`), so "`bund.eval`'d text has spans only into a string" is
wrong as well. It has none.

So location breakpoints (§D3's second form) and a named `bt` depend on
unbuilt RFC-0003 work. §D2 should say so, and name it as a dependency in the
header.

Also: "a body is an `Rc<[BundValue]>`" is inaccurate. It is
`Payload::Lambda(Vec<BundValue>)` behind the value's heap `Rc`
(`crates/bund2-value/src/lib.rs:213`).

### S6 — "The symbol it was pushed for" is not available where a frame is pushed

`push_frame(body, exit)` (`crates/bund2-interp/src/lib.rs:1159`) and
`request_tail(body)` (`:1133`) take a body and nothing else. The RFC does not
say how the symbol reaches them, or which symbol wins through an alias, a
`PTR`/`execute`, a D16 computed name, or a method. It also leaves out frames
that have no symbol: `scoped_call`'s per-call LIST (`:1488-1505`) and `( … )`
contexts.

§D3's first form — "break when a frame for that symbol is pushed … one
comparison" — never fires for a **native** word, because natives push no
frame. `println` cannot be breakpointed this way. That is a limit the RFC
needs to state.

### S7 — Conditional breakpoints: a silent departure from the research, and an exit that cannot be absorbed

Research §3.3(c): the condition is "evaluated **in a child VM context** at the
breakpoint". §D3 drops that clause but says "Research §3.3(c), unchanged", and
the header says the RFC "departs nowhere". Run in the debuggee's `Interp`, a
condition can push, pull, switch the current stack, toggle `autoadd`, or
register words. So a breakpoint changes what it observes, which §D6 calls
"worse than a slow one".

"A lambda that errors, **exits**, or leaves no value … treated as 'do not
stop'". An exit cannot be undone today. `request_exit` is
`self.exit_code.get_or_insert(code)` (`crates/bund2-interp/src/lib.rs:1692`),
every later step is refused by `exit_gate`, and `Vm` has no call that clears
the request (`crates/bund2-api/src/lib.rs:598-600`). Absorbing an exit widens
the API the same way D52 did. That is a decision, and D52 is listed as
"consumed" without mentioning it.

Criterion 7 tests only the error case. It needs the exit and no-value cases,
and a check that the debuggee's stacks are unchanged by a condition that does
not stop.

### S8 — Watchpoints do not hook "one place", and D41 is not the reason they would

"Every push already writes the stack tag (D41), so the push path is the one
place this hooks." D41 is about *where a scalar's tag is stored*, not about
push being a single path. The paths:

- **the workbench push is separate and untagged**: `push_workbench`, "As it
  arrives, untagged — F90" (`crates/bund2-interp/src/lib.rs:1768-1776`). So
  "every push writes the stack tag" is false for exactly the stack `watch
  workbench` names;
- `push_to` writes a named, non-current stack (`:1399-1403`);
- a capped stack drops its newest value before pushing (`:118-150`);
- `autoadd` appends by pull-then-push (`:1030-1036`). Should a watch on the
  collector's stack fire on every collected item?

`watch depth > 100` is not keyed on pushes at all. A pull or a clear moves
depth as well.

Criterion 8's "and on no other" needs these cases named, or it can pass on a
hook at `Stack::push` that misses the workbench.

### S9 — §D7: `eval_observed` cannot drive the trace, and the counters cannot drive a profiler

**The observer sees top-level values only.** `eval_observed` calls
`observe(v)` for each value of the *stream*, then `drain_frames()` runs every
nested body without calling it again (`crates/bund2-interp/src/lib.rs:1087-1117`).
It has no depth, no symbol and no stack effect. §D7's
`(depth, symbol, value, stack effect)` per step needs an observer inside
`run_to`, and then inside every synchronous native's nested `run_to` (B1). The
Summary's "per-word observer" repeats the doc comment's phrase, and the
behaviour does not match it.

That also contradicts an accepted RFC. RFC-0003's Preservation row reads "The
debugger's third eval loop, which prints and steps | preserved via S6's
observer" (`RFC-0003:709`). RFC-0008 §D1 says the observer "can *watch* but
cannot *stop*" and so is not the debugger. Both cannot hold. RFC-0003 needs an
amendment note, or RFC-0008 needs to say which row it supersedes.

**The counters are aggregates on a tier the debugger removes.** The public
figures are totals: `compiled_bodies`, `counted_bodies` (a count of bodies,
not of entries), `crossed_calls`, `compiled_entries`
(`crates/bund2-runtime/src/tier.rs:127-153`,
`crates/bund2-runtime/src/lib.rs:225-242`). The per-body count §S7 compares
is keyed by body pointer, not by symbol, and it exists only under
`--features jit` with a tier installed. §D6 does not install one. So "the
profiler comes from the counters that already exist" has nothing to read in a
debug session or in a non-`jit` build. The research's "for free" was written
before either fact.

### S11 — `"…" debug` inside a normally-run program

§D6 keeps the tier out of a *session started with the flag*. The word `debug`
can be reached from any program, run under `script` with the tier installed.
It can also be reached from a `bund2 build` bundle (RFC-0006). Stepping into a
body the tier has compiled is impossible, because compiled code keeps no frame
(`crates/bund2-interp/src/lib.rs:1182-1189`). The RFC needs a rule for this
case: disable the tier from the word onward, refuse, or step at top-level
granularity. Criterion 9 needs a case to match.

  lists.
- **M8.** "F139 measured that no corpus program compiles a body at the
  default threshold". F139 measured at 64. The default is now 1024 (D74), so
  the claim holds more strongly, but the RFC should say that.
- **M9.** Preservation for `debug` says "Preserved, and extended", but "a
  breakpoint on entry" stops once. The reference prints a type/value/`{:?}`
  table and pauses after **every** top-level term (`debug_debug.rs:17-37,73-108`).
  The RFC should say whether the per-term table and the per-term pause
  survive, and give the word's own error texts (`:125,130,138`, and the two
  `bail!`s at `:66,69`). It should also cover the case where the
  `DefaultEditor` fails: the snippet is consumed and the word returns `Ok`
  silently (`:40-46`).
- **M10.** §D9's obligation, "keep the frame state serialisable", is not
  checked by any criterion. `Frame` holds the body by `Rc` identity because
  D42 keys the cache on it, and serialisation loses that identity. State what
  "serialisable" has to preserve.
- **M11.** "Adding two words to `Frame`": a symbol plus a `Span`
  (`start`, `end`) is three words, or more if optional.
- **M12.** "`Runtime::with_options_and_threshold` installs the tier in one
  place". `Runtime::install_tier` (`crates/bund2-runtime/src/lib.rs:244-248`)
  is a second, public one.

## Preservation analysis — what is missing

Beyond the rows S1–S4 correct, the design can change these behaviours and
the table does not list them:

1. `--debugger`: the whole program run under the debugger (B2).
2. `--debug-shell`: the REPL after an uncaught error (B2).
3. `-d`/`--debug` as log verbosity, and `BUND_LOG_LEVEL` (B2, S2).
4. `--profile`'s table (B2, S9).
5. `debug.dump` peeks. Its STRING arm, its BOOL width, its seven error texts
   (S1).
6. `debug`'s per-term table, per-term pause, error texts, and silent
   `DefaultEditor` failure (M9).
7. `debug.shell`'s history file (M5). Every line, empty ones included, is
   evaluated (`debug_shell.rs:27-34`). Ctrl-C and Ctrl-D end it (`:36-43`).
8. `display_distributed_info`'s logged refusal (S4).
9. `display_memstat`'s fallback line (M4).
10. `display_hostinfo`: approved deviation D53 (S3).
11. **The debuggee's state under a conditional breakpoint** (S7). This is the
    one row where the design itself could change program meaning.
12. **Step granularity inside synchronous natives** (B1). Whichever way D6
    goes, the row must say what a user sees.
13. The cost of `Frame`'s growth falls on **every** run, not only debug
    sessions. The row has "Changed", but should say who pays.

## Consistency with accepted RFCs and ERRATA

- **RFC-0003 §S6 / Preservation row `:709`** says the debugger is preserved
  "via S6's observer". RFC-0008 §D1 rejects the observer as the debugger.
  RFC-0003 is Accepted, so this needs an amendment to RFC-0003, or an explicit
  supersession here (S9).
- **RFC-0003 `:944-946`** puts `--debugger` in D6's scope. RFC-0008 does not
  engage with that (B1).
- **RFC-0003 §S4's resumable natives** (`:521-535`) are what §D1 assumes. The
  third amendment (`:1036-1060`) records that they run synchronously instead
  (B1).
- **ERRATA.** The header says the RFC "departs nowhere" from research §3. It
  departs, or the research is contradicted by the code, in four places, and
  none has an ERRATA entry:
  1. §3.3(a): `bund.eval`'d code "in frames". False in Bund2 (B1).
  2. §3.3(c): "evaluated in a child VM context". Dropped (S7).
  3. §3.3(h): trace "at IR-op granularity". §D7 routes it through a
     top-level observer (S9).
  4. §3.1's `debug.dump` row omits the STRING arm (S1). The research is
     wrong here, and the RFC inherited it.

  §3.3(f)'s `bund2 run --debug` also names a subcommand Bund2 does not have
  (B2).

## What the RFC assumes but does not state

1. **Every body runs under the flat loop**, so a driven step can suspend
   anywhere (B1). False for every synchronous native and for `bund.eval`.
2. **A frame knows its symbol at push time** (S6).
3. **A condition may run in the debuggee's VM without changing it** (S7).
4. **Goldens capture stdout only.** The *Hermetic-partition* note assumed
   this, and the capture no longer does (S2).
5. **Nested values have spans to thread** (S5).
6. **Third-party output formats are reproducible**: `hexdump` 0.1.3's line
   layout, `env_logger`'s line format, `comfy_table`'s box (F46 shows the last
   one reacting to content width).
7. **The debugger's input side has a seam.** The Summary says the
   `Diagnostic`/`Reporter` split "was built for this". `Reporter` is
   output-only, one method (D36). A debugger front end, a TUI included, also
   needs a way to *send* commands. Nothing names it.
8. **How the debugger's own messages are delivered.** "The debugger reports
   the condition's failure" gives no severity. Under D36 a `Warning` is one
   stderr line and an `Error` stops the program. Which one is it, and does it
   go through `Vm::report`?
9. **Readline runs on the evaluation thread.** Evaluation runs on a thread
   whose stack Bund2 sizes (RFC-0003 third amendment). That is probably fine,
   but a TUI front end on another thread changes it.
10. **The profiler and trace exist outside `--features jit`** (S9).

## Disposition

**Not ready to propose.** The RFC calls itself a Draft for §D2's cost and
§D6. Those are real, but they are not the two blocking issues. B1 is a
language-level decision, D6, that the RFC treats as already made. B2 is a
preservation contract missing four CLI flags that F52 names outright. Of the
significant findings, S1–S4 are errors in the Current-behaviour and
Preservation tables that the cited files contradict, and S7 is the one place
the design could change a running program's meaning.
