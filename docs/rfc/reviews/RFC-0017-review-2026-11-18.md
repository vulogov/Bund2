## Should fix

### S1. The bounding rule names a renderer that does not escape, and two rows sit outside it

**The RFC says** (RFC:677-682): "Every value a text interpolates from the program … is rendered as `summary(WIDTH)` renders a STRING (`biomath/operand.rs`, `WIDTH`, 40): in double quotes, escaped, and truncated with `…`, so no refusal is unbounded and none breaks across lines". Criterion 5 asks for a 200-character key holding a `"` and a line break to show "bounded and escaped, on one line" (RFC:839-840).

**What `summary` does.** For a STRING it pushes `"`, then `truncate(s, width − 2)`, then `"` (`bund2-value/src/lib.rs`, `summarise`, the `_ =>` arm of `Payload::Str`). `truncate` cuts by characters and adds `…` (`:170-176`). Nothing escapes. Probed: `[ 1.0 2.0 ] '"a\"b\ncd"' json json.to_value vec.scale` reports

```
VEC.SCALE: E101 k is outside vec.scale's domain: "a"b
cd"
```

The quote is unescaped and the line break is printed. Read literally, the rule makes criterion 5's last case fail. An implementer who follows the rule's words instead has to invent an escape, its form (`\"`, `\n`, `\u{…}`), and its order against truncation. Escaping after truncating to 38 characters can exceed 40.

**The house has two renderers, each with half of the property:**
- `summary(WIDTH)` is bounded but not escaped. RFC-0015's operand readers use it (`operand.rs:56`, `:120`).
- `format!("{k:?}")` is escaped but not bounded. RFC-0016's options reader uses it for an unknown key (`biomath/infer/opts.rs:79`, `:85`), and `ode.rk45` does the same (`dynamics.rs:235`). Probed: a 70-character key holding `"` and `\n` in a `stat.cor.test.pearson.opts` options MAP is reported as `an unknown key "k\"ey\nxxxx…xxx"`, in full, escaped.

**Two rows the preamble does not reach:**
- RFC:709, E114: `the answer overflows a FLOAT: x.mean of group [ "a" ]`. `x` is a column name, which the preamble lists, but here it is printed unquoted and unbounded. RFC:711 quotes the same result name (`result name "x.mean"`).
- RFC:721 and RFC:723: `sep` and options refusals "as RFC-0016 §S1". That text interpolates a key with `{:?}` and no bound, so "no refusal is unbounded" does not hold for an options MAP with a long unknown key.

**Do not change `summary`.** Changing it would change every existing E101/E103 text that holds a STRING, which the Preservation table says are unchanged (RFC:736). So the fix belongs to the frame words.

**Suggested fix.** Replace "as `summary(WIDTH)` renders a STRING" with a stated rule. For example: "truncated to 38 characters with `…`, as `summary(WIDTH)` truncates, then written as Rust's `{:?}` writes a `str` (quoted, `"` and control characters escaped)". Say that the escape can lengthen the text past `WIDTH`, which is still bounded. Then:
- quote `x.mean` at RFC:709;
- either bound the options keys too (a frame-local reader, not RFC-0016's) or exempt RFC:721 and RFC:723 by name;
- add `summary`'s non-escaping to §Current behaviour, so the reason for the new helper is grounded.

### S2. S5's grouping leans on a FLOAT comparison that `frame.sort` never states

**The RFC says.**
- S5 (RFC:454-458): "Two rows are in one group when `frame.sort` compares each of their `by` cells equal: numbers by value, so INTEGER `1` and FLOAT `1.0` are one group, and so are `0.0` and `-0.0`, as `frame.join` matches them."
- S4 (RFC:369-372): `frame.sort` "compares numbers as numbers (an INTEGER with an INTEGER exactly, and with a FLOAT by exact value, as D33 compares them)". FLOAT against FLOAT is not mentioned, and neither is signed zero.
- `frame.join` (RFC:479-481) says "1 matches 1.0, as `frame.sort` compares" and is silent on `±0`.

So the chain S5 → `frame.join` → `frame.sort` ends in a rule that does not cover the case S5 names.

**Why it matters.**
- The crate's own float ordering is `f64::total_cmp`, which `describe.rs`'s `sorted` uses for `stat.median` (`describe.rs:56-60`). It puts `-0.0` before `0.0`.
- A `frame.sort` built that way is stable on its own terms. Rows `0.0, -0.0` come out `-0.0, 0.0`, where an equal-comparing sort keeps them in row order. `frame_eq` tells the two answers apart (RFC:291-293).
- Under `total_cmp`, `frame.aggregate` would make two groups, against S5.
- D33 does give the answer, "by the mathematical values they denote" (`decisions.md:1755-1757`), and Bund's `==` agrees (probed: `-0.0 0.0 ==` prints `true`). But S4 cites D33 only for INTEGER against FLOAT.
- No criterion pins it. Criterion 4's sort case has no signed zero (RFC:814-816). Criterion 5 has a signed-zero tie for `"min"` (RFC:835-836), but none for grouping.

**Suggested fix.**
- In S4, add: "FLOATs compare by value, so `-0.0` equals `0.0` and a stable sort keeps them in row order; not by `total_cmp`".
- Add a signed-zero case to criterion 4's `.sort`, and a `by` column of `0.0` then `-0.0` to criterion 5, answering one group whose cell is `0.0`.

## Notes

**N1. S2's factor-column sentence overlaps S8 rows 8 and 9.** RFC:265-267 says that in a column in `levels`, "any non-NONE cell that is not one of its levels, a number or a BOOL included", is `not one of its levels`. But:
- RFC:257-259 makes a LIST or MAP cell "E101 in any column" (row 8's `is a LIST`);
- row 9 (`is NaN`) runs before row 11 (RFC:682-683).

So a NaN or a LIST in a factor column gets row 8's or row 9's text, not row 11's. The S8 order decides each case, so nothing is ambiguous. But S2's "any" is wrong for two kinds of cell. Write "any finite scalar cell", or "after rows 8 and 9". Criterion 2 tests one rule at a time and does not reach this.

**N2. Which operand a frame-check text names when no operand is a frame.** Every frame-check text starts `frame is outside <w>'s domain` (RFC:687-697). But some words build the frame they check from other operands:
- `frame.new` (`names columns`) checks the frame it builds (RFC:224-226): repeated names, a LIST cell, a NaN cell;
- `frame.with`'s new column "passes the column rules" (RFC:359-360), and its `name` can be empty or a non-STRING, which only row 3 catches.

For these words the text would name an operand the word does not have. Say that such a text names `names`, `columns`, `name` or `list` as the word takes them, or that `frame` stands for the frame being built.

**N3. Preservation does not list a program that calls a new name without defining it.** Probed today:
- `na println` is `i(na) for stack returned: Inline na not registered`;
- `bund2 check` abandons a program at `` `frame.nrow`, which declares no effect ``.

After this RFC the first pushes NONE and the second analyses past it. RFC:742-744 covers a program that defines a name, `?stdlib`/`?word`, and the listings. It does not cover the error that becomes an answer, nor `check`/`infer`. RFC-0016 has the same gap (`RFC-0016:655` covers `?stdlib` only), so this is precedent, not a regression. One row would close it.

**N4. The order of `frame.aggregate`'s own refusals is unstated.** "The checks come first" (RFC:421-423) puts size checks before computation. It does not say:
- whether every group is size-checked before any statistic is computed;
- which group is named first: the answer's order or row order;
- which `stats` entry is named first.

A frame with group `a` overflowing `"mean"` (E114) and group `b` having one value for `"var"` (E101) can be refused either way, with different codes. Criterion 5 tests each fault alone, so the tests pass either way, and two implementations would report different texts. One sentence fixes it: "groups in answer order, statistics in `stats` order, all size checks before any computation".

**N5. Criterion 6 does not reach some of S6's stated rules:**
- empty text is a frame of no columns and no rows (RFC:544-545);
- text that is only a byte-order mark (RFC:541-543);
- `"\n"` under `header` true (E101) and false (`column_1`) (RFC:538-540);
- a `sep` of two bytes or a non-ASCII character (RFC:511-514; only `"\""` is listed, RFC:872-873).

Each is a line in the parse test.

**N6. Q64 says "with two differences"** (`open-questions.md:14`). §Differences from R now lists four: P6, P7, blank lines and `fill` (RFC:1023-1049). The two extra are not about P6, P7 or P11's defaults, which is what Q64 asked, so the answer is not wrong. A reader comparing the two will still trip on it. The register is append-only, so this is for the entry's next touch.

**N7. "The bytes after a closing quote"** (RFC:679) against "the first character after it" (RFC:717). The row is the precise one. Make the preamble say "the character after a closing quote".

**N8. NONE is spelled two ways in one family's refusals.** Frame refusals show `NONE` (RFC:682, **[author]**, listed at RFC:995-996). `stat.cov`'s E103, which the Preservation table keeps, shows `none` (`summary`'s spelling; RFC:155-156, :736). This is deliberate and listed, but no criterion pins it. Add a NONE `by` key to criterion 5's group-refusal case: a group `[ NONE ]` with one value for `"var"`.

## What the RFC assumes and does not state

- **That `summary` is left as it is.** S1's fix needs a frame-local renderer. A change to `summary` would move existing texts (RFC:736).
- **What E112 says when `frame.filter`'s lambda leaves nothing.** `ask` answers `None` for an empty scratch stack (`bridge.rs:104-118`), and `call` reports `left nothing` for it (`dynamics.rs:82-84`). RFC:362-365 says only "a result other than a BOOL", so it is presumably the same.
- **The order of refusals across checks** (carried, and widened by N4):
  - the frame check against other operand checks;
  - inside `frame.csv.parse`, tokenising faults against inference faults against the frame check's E103;
  - inside `frame.aggregate`, across groups and statistics.
- **That an `na` string matches by exact bytes**, case-sensitive and untrimmed (carried).
- **That a final line without a terminator is a record** (carried). RFC:530-531 still states only terminated lines.
- **That `frame.text` of a frame with columns and no rows prints its header row alone** (carried).
- **That `file`'s path is absolute, and that `file` may fetch over HTTP** (carried).
- **That a row MAP per row in `frame.filter` and `frame.rows` is affordable at Tier 0** (carried).
