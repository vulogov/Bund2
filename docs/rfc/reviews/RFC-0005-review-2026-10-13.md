## Blocking

**B1 — Criterion 11's cost clause is held by an instrument the criterion
does not name and contradicted by the one it does. Read L6731–6740, L9255–
9270, D149.** D149 as ruled, and the criterion's note of the same date
(L6731–6734), word the clause as: fewer than 20 instructions an entry, "read
by `floor_count` … over 10,000,000 entries at each of four body lengths …
each the median of five runs under `/usr/bin/time -l` (D117)". The Linux
amendment then reports (L9262–9268) that `/usr/bin/time -l` on macOS,
"repeated three times at 64 sites on this date, put the checked arm anywhere
from 68 instructions an entry below the unchecked arm to 21 above it", and
concludes "the Linux figure is the one that says what it is". So: by the
named instrument on the named host, one of three repetitions read **+21,
over the bound of 20**; the readings that hold the clause (3.04 to 3.06) are
callgrind's over **one million** entries on Linux, which the criterion,
D149 and D117 never name — D117 says Linux reads "the same counter with
`perf stat`", and the workflow's own comment says a hosted runner exposes
none. This is the twenty-fourth review's B4 again, one criterion over: the
named check does not decide, an unnamed one does. The status block (L105–
110) lists 11 under "holds for the criterion as re-worded". Either the
clause names the instrument that decides it — an exact count, with the host
and the entry count — and records `/usr/bin/time -l` as a reading, or 11
returns to "held by less than its text". D149's note of 2026-10-12 says the
macOS spread "is larger than they are" and does not say a reading crossed
the bound; D117 carries no note that its Linux sentence is not what was
done. Also stale in the same note: L6740 "No CI step runs it; it is a
command run by hand" — `linux-reading`'s `floor-count` job runs it.

## What the RFC assumes and does not state

1. Callgrind's instruction count and `/usr/bin/time -l`'s `instructions
   retired` are one quantity for criterion 11's clause (B1, S3).
2. Cranelift's aarch64 backend set up a frame record for every function the
   tier emits before F204, so the flag changed nothing on the host every
   figure was taken on (B3). Stated as a code comment; cited nowhere.
3. The `ci` workflow will run on the next push to this branch and pass.
   It has run once, on `main`, and failed (B2).
4. The three Linux variants are the oracle's answers on Linux and not
   Bund2's. D150 says the `capture` job builds the oracle there and the
   variants are its output; the job's log is the evidence, and the RFC
   cites the run number only.
5. Every shared golden was captured on macOS arm64 (`hosts::SHARED`,
   uncommitted). D150 says so; nothing in `tests/golden/` records the
   capturing host of a shared golden.
6. `JITBuilder::with_isa(cranelift_native::builder()…)` builds the module
   `with_flags` built. True by reading `backend.rs`; stated in F205 as
   shown by the suite and `conform`, which is a consequence and not a
   comparison.
7. A hosted Linux runner's kernel, allocator and `ulimit -s` are
   representative of a Linux host a user runs `bund2` on. The amendment
   names the kernel and compiler and says "x86-64" and "glibc"; it does not
   say what `ulimit -s` printed, and the `loop` floor level it reports
   (7,858) depends on it.
