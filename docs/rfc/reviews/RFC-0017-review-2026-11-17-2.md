## Blocking

### B1. `frame.csv.parse` of `frame.csv.text` is not the frame, for five reasons; one is ruled (D254) and not consumed

**The RFC says** (§S6): "`frame.csv.parse` of `frame.csv.text` of a frame is that frame, factors aside (criterion 6)". It also says "Parsing reuses `csv`'s inference (`data.rs`, `infer`, `column_kind`)" and that writing "quotes a field holding the delimiter, a quote or a line break". Criterion 6 asks for equality "of a frame of every kind with NONE", "each FLOAT bit for bit".

**What the source and probes show.** The inference reads the text, not the frame, and over a window:
1. **STRING cells that look like something else.** The `csv` crate removes quotes before the inference sees a field (`data.rs:24-25`). A STRING cell `""` is written as an empty field and read back as NONE; `"NA"` is read back as NONE; `"007"` or `"true"` is read back as INTEGER or BOOL. D254 (`decisions.md:17376`, RESOLVED 2026-11-17, "Blocks: RFC-0017's revision") rules that a quoted field is text and that `frame.csv.text` quotes every STRING cell. The RFC does not list D254 in "Decisions consumed" and §S6 still quotes only fields with a delimiter, quote or line break.
2. **A numeric column mixing INTEGER and FLOAT** (S2 allows it) reads back all FLOAT, since `column_kind` merges the two (`data.rs:119-125`). D254 says this "is not settled by this ruling" and is to be put to the owner.
3. **The 100-row window fails outright past row 100.** A numeric column whose first 100 cells are INTEGERs and whose 101st is a FLOAT is typed `Int` from the window, and `cell` then refuses the FLOAT. Probed with `csv` on a file of 100 integer rows and then `2.5`: `CONTEXT.RUN: Error finishing dataframe: could not parse `2.5` as dtype `i64` at column 'x'`. Reusing `infer`/`column_kind`/`cell` makes `frame.csv.parse` refuse the text `frame.csv.text` wrote, with a text that is not an E1nn, which criterion 9 also forbids.
4. **The window misreads a column with 100 leading NONEs.** `read_frame` skips empty fields when collecting kinds (`data.rs:184-191`); a column empty for its first 100 rows has no evidence, `column_kind` of the empty set is `Str` (`data.rs:122-124`, and the test at `:555`), and every later number is read as a STRING. Probed: a file with 100 empty `y` cells and then `7`, `:column "y"`, `car type println` prints `String`. A numeric frame column whose first 100 cells are NONE comes back as a string column.
5. **Ordinary numbers are not the only FLOAT forms.** `is_float` accepts `inf`, `NaN`, `-inf` (`data.rs:81-83`): `csv` on a column `NaN, inf, -inf` answers `[ NaN ::  inf ::  -inf :: ]` (probed). This is a parse problem rather than a round-trip one (a frame cannot hold them), but the RFC does not say what `frame.csv.parse` does with such a field: refuse (E101, B12), treat it as missing, or read it as a STRING. Without a rule it builds a frame that `frame.check` refuses.

**Why it matters.** Criterion 6 cannot pass as written. Items 3 and 4 also break a file the user wrote themselves, with no frame involved, and item 3 does it with a text that is not one of the family's refusals.

**Suggested fix.** Consume D254 (quote every STRING; a quoted field is text). For 2–4, either judge a column's kind over all rows, not 100 (the frame reader is not bound to polars' window: D51 binds `csv`, not this word), or narrow the round-trip claim and criterion 6 explicitly, and take the INTEGER/FLOAT question to the owner as D254 says. Make every parse failure an E1nn with its row and column. State what a `NaN`/`inf` field becomes, as a ruling.

### B2. "Equal" is never defined, and neither of the equalities that exist can check criteria 4–7

**The RFC says** that answers "are frames equal to ones written out in the test" (criterion 4), that `frame.csv.parse` of `frame.csv.text` "is equal to it, each FLOAT bit for bit" (criterion 6), that a frame through JSON and base64 "is equal to itself" (criterion 7), and that `stat.lm` on `frame.matrix`'s answer "equals `stat.lm` on the same columns written by hand" (criterion 5).

**What the source and probes show.**
- Bund's `==` refuses containers: `'[1,2]' json json.to_value '[1,2]' json json.to_value ==` and `dict dict ==` are both `== returns error: COMPARE: unsupported operand #1` (probed). It refuses NONE too (probed, and the RFC says so).
- `BundValue`'s `PartialEq` compares a LIST or MAP **by identity** (`crates/bund2-value/src/lib.rs:2001-2048`, the last arm, `a.identity() == b.identity()`), so two separately built frames are never equal under it.
- Its scalar arms are loose in exactly the ways the round trip can fail: `Int(a) == Float(b)` when they denote the same number (`int_eq_float`, `lib.rs:2013`; `1 1.0 == println` prints `true`, probed), and floats compare by `float_key` (`:2010`), which folds `-0.0` to `0.0` and every NaN to one (`lib.rs:1974-1982`). A structural comparison written over these arms would pass B1's INTEGER→FLOAT change and a sign-of-zero change.

**Why it matters.** Four criteria rest on a relation the RFC does not name. The obvious implementations are either always false (identity) or blind to the failures the criteria exist to catch.

**Suggested fix.** Define frame equality in §S2: same `columns` in order; same `levels` keys and LISTs in order; per cell, same type (INTEGER ≠ FLOAT), INTEGERs equal, FLOATs by `to_bits`, STRINGs and BOOLs by content, NONE equal to NONE. Say whether `q` counts (see N5). Name the test helper that implements it, and use it in criteria 4–7. For criterion 5, say which keys of `stat.lm`'s MAP are compared, and how.

### B3. Q63 is answerable, and the answer is the opposite of the RFC's: Bund's LIST index counts from 1

**The RFC says** (§S4): "**Indices are 0-based INTEGERs**, as Bund's own LIST words count from 0 [UNGROUNDED; Q63]".

**What the source and probes show.** The reference's `at` (`reference/rust_multistackvm/src/stdlib/values/value_carcdr.rs:121-148`, registered as `at` at `:203`) pulls the LIST and then the index and calls `Value::at(n)`, which returns `raw_list[(n-1) as usize]` (`reference/rust_dynamic/src/carcdr.rs:57-60`). Bund2 agrees: `1 [ 10 20 30 ] at println` prints `10`, `3 [ 10 20 30 ] at println` prints `30`, and `0 [ 10 20 30 ] at println` is `AT returned: NO DATA` (probed). The open question asked is answered: Bund's LIST word is 1-based.

**Why it matters.** The stated reason for the choice is false, and the choice is a language-level convention that D253 does not rule: none of P1–P12 is about indices. CLAUDE.md asks that such a choice go to the owner rather than be adopted silently. As written, `frame.take` would be the first index-taking word in the language to count from 0, and a program mixing `at` and `frame.take` would be off by one.

**Suggested fix.** Close Q63 with the citation above. Raise the index base as a decision (1-based, like `at`, or 0-based, as a deliberate break), with the result and its reason in §S4. Also state what a FLOAT index and a negative index are (B15 converts INTEGERs to FLOAT for `math.` words; the reverse is not covered).

## Should fix

### S1. The refusal codes are not assigned per rule, and E103's text does not fit most of the uses

**The RFC says** (§S1): "Refusals are RFC-0015 §S11's codes and texts; no new code **[P9]**. A malformed frame is E101 …, columns of unequal length E102, a cell of the wrong kind E103". §S2's table says NaN is "refused (B12)", and then "Any other mixture, or any other type of cell, is a malformed frame (E103, naming the column and the cell's row)". Criterion 2 asks that a frame breaking each rule is "refused with its code and text".

**What the source shows.** RFC-0015 §S11's E103 template is `<operand> is not a MATRIX (or LIST) of numbers: <cell or row>` (`RFC-0015-biomathematics.md:842`); E102's is `<what> do not agree: <n> and <m>` (`:841`), with no slot for a row; E112's is `the model lambda left <what>, where <expected> was required` (`:851`). B12 makes a NaN or ±∞ operand E101 (`:861-862`; D250's B12 row).

**Why it matters.** A STRING cell in a logical column, a factor cell outside its levels, or two `by` columns of different kinds are not "not a LIST of numbers", so either the text is wrong or it is not §S11's. Whether a NaN cell is E101 (B12) or E103 (S2's "any other type of cell") is not decided, and criterion 2 lists eleven rules but gives a code for only two. "Naming the row" for a ragged CSV row (§S6, E102) does not fit E102's template either.

**Suggested fix.** A table, one row per rule of the check and per refusal of §S4–§S6, with its code and the exact text, including the E103 wording for a non-numeric kind error. If §S11's templates cannot carry them, say how the text extends them (D253 P9 rules the codes, not the texts).

### S2. Two words take options their declared effects do not have, and the read example drops a required operand

**The RFC says**: `frame.sort` has effect `frame names -- frame`, and "options give `descending` **[P11]**" (§S4). `frame.csv.parse` has effect `text opts -- frame`, and "Reading is `"path" file frame.csv.parse`" (§S6). §S3 says "The words that only move cells (S4) carry NONE and take no `na` option", without saying whether `frame.sort` takes an options MAP for anything else.

**What the source shows.** RFC-0016 rejected a trailing optional options MAP because "a word whose arity depends on its top operand cannot declare a fixed effect" (`RFC-0016-statistical-inference.md:670-672`), and made `.opts` words instead.

**Why it matters.** `frame.sort`'s `descending` has nowhere to go. The read example, taken literally, pulls the file's text as `opts` (E101) and whatever lies below as the text. A reader copying the example gets a refusal.

**Suggested fix.** Give `frame.sort` an `opts` operand (`frame names opts -- frame`) or a separate `frame.sort.opts`, and say whether NONE sorts last when a column is descending. Write the read example as `"path" file dict frame.csv.parse`. State, once, that every `opts` operand is required, and inherit RFC-0016 §S1's options rules (an unknown key, or a value of the wrong type, is E101 naming the key) by citation.

### S3. The `na` option contradicts itself on `by` columns, and `count` and `frame.join` are left out

**The RFC says** (§S3): "Under `"refuse"` a NONE in a cell it reads is E101 naming the column and row. Under `"omit"` it drops each case with a NONE in a column it reads". (§S5): "NONE in a `by` column is a group of its own, last"; groups are "in order of first appearance".

**Why it matters.**
- `frame.aggregate` reads its `by` columns. Under `"refuse"` a NONE there is E101 by §S3 and a group by §S5; under `"omit"` the case is dropped by §S3 and grouped by §S5. Each reading gives a different answer.
- Which columns a statistic "reads" is not said: if a row has NONE in `x` only, is it dropped from `y.mean` as well (complete cases over all `stats` columns, which a single `.dropped` per group implies) or only from `x`'s statistics?
- `"count"`: of rows, or of non-NONE cells?
- `frame.join` compares cells in its `by` columns and takes `opts`, but §S5 gives the `na` option to `frame.aggregate` and `frame.matrix` only. Whether a NONE key matches a NONE key, matches nothing, or is refused is not said.

**Suggested fix.** One rule for `by` columns (for example: never subject to `na`, NONE always a group of its own, last), stated in §S3 and §S5 alike; "reads" defined as the union of the `stats` columns, with `.dropped` counting those rows; `"count"` defined; a rule for NONE keys in `frame.join`, with criterion 5 extended to cover it.

### S4. Under `"omit"`, `frame.matrix` and `na.omit` let a program misalign X and y silently

**The RFC says**: `frame.matrix` is "the numeric columns as a MATRIX, rows by rows, for `stat.lm`"; under `"omit"` it drops each case with a NONE and answers `{ matrix, dropped }` (§S5). `na.omit` "is how a program hands a frame's column to an RFC-0015 word" (§S3).

**What the source shows.** `stat.lm` takes `X y -- MAP`, X a MATRIX and y a series read by `whole`, and refuses only when their lengths differ (`crates/bund2-stdlib/src/biomath/infer.rs:836-849`).

**Why it matters.** y does not come from `frame.matrix`; the RFC's way to get a NONE-free y is `frame.column na.omit`. If X has a NONE in row 2 and y one in row 5, both lose one row, the lengths agree, and `stat.lm` fits rows that do not belong together, with no refusal. The same holds for `stat.cov` on two `na.omit`ed columns. This is the failure D252's ruling was meant to prevent ("drops incomplete cases"), reintroduced across two words.

**Suggested fix.** Provide complete cases at the frame level: a `frame.omit` (`frame names -- frame`, dropping each row with a NONE in any named column), so that X and y are taken from one already-complete frame; or have `frame.matrix` take the response column and answer y beside X. Add a criterion that builds exactly the case above and shows the supported route aligns.

### S5. The named statistics cite the wrong file and leave their types and edge cases open

**The RFC says** (§S5): the statistics are "computed as RFC-0015's words compute them (`describe.rs`), so a group's `"mean"` is what `stat.mean.arithmetic` answers on its cells". A `"var"` of one value is E101.

**What the source shows.** `describe.rs` registers `stat.var`, `stat.sd`, `stat.median` and the rest of §S6's descriptive words (`describe.rs:269-282`), and has no mean, sum, min, max or count word. `stat.mean.arithmetic`, `math.min`, `math.max` and `stat.count` are the reference's words, built in `series.rs` (`:498-501`), not RFC-0015's. `amean` refuses an empty series with `… Missing or insufficient data: amean: empty self vec` (`series.rs:280-283`), which is not an E1nn. `math.min` and `math.max` fold from NaN, so an empty series answers NaN, and an INTEGER series answers a FLOAT (`series.rs:219-251`). `"sum"` matches no word cited.

**Why it matters.** A group whose cells are all dropped under `"omit"` is empty: copying `extreme` answers NaN, against B12; copying `amean` refuses with a non-E1nn text, against criterion 9. Whether `"sum"`, `"min"` and `"max"` of an INTEGER column are INTEGER or FLOAT is unstated. So is what a statistic other than `"count"` does on a logical, string or factor column. A result column named `<column>.<statistic>` can collide with an existing column or with another pair, and `.dropped` with a `by` column of that name, which gives a frame with duplicate names, which the check refuses.

**Suggested fix.** Cite `series.rs` for the four reference statistics and `describe.rs` for `var`, `sd` and `median`; give each statistic's answer type; make an empty group E101 naming the group; refuse a non-numeric column for any statistic but `"count"` (E103 per S1's table); refuse a result name that collides (E101).

### S6. `frame.join` is underspecified

**The RFC says** (§S5): "the rows of `left` with the matching rows of `right` on the `by` columns, `"inner"` or `"left"`"; "a `by` column must have one kind in both frames (E103)".

**Why it matters.** Criterion 5 asks for answers "written out in the test", and the test author must invent each of these: the output's column order (`left`'s, then `right`'s non-key columns, presumably); the row order when a left row matches several right rows; whether INTEGER 1 matches FLOAT 1.0 in a numeric key (both are "numeric" by S2, and `BundValue`'s equality says yes, `lib.rs:2013`); whether a factor key and a string key are "one kind", and whose levels the output carries; whether `right`'s factor columns keep their levels; NONE keys (S3 above); and how E111's 10⁸ is counted before allocating.

**Suggested fix.** State each of these in §S5, and make criterion 5's join case exercise duplicate matches and a factor key.

### S7. The `UNVARIED` list is wrong by the audit's own rule, and its reason is not the audit's

**The RFC says** (§S7): `UNVARIED` lists "`frame.with`, `frame.factor.levels`, `frame.aggregate`, `frame.join`, `frame.matrix`, `na.fill` and their forms, their deepest operand a frame or LIST the palette does not build".

**What the source shows.** The audit lists a fixed-effect native exactly when it consumes more than the palette varies: two operands for a plain word, one for a `.` or `,` form (`crates/bund2-stdlib/src/lib.rs:934-946`), and asserts the list equal to `UNVARIED` (`:948-952`). A `.` form declares its stack operands only, `consumes − 1` (`wb.rs:188`). So `na.fill` (2) and `na.fill.` (1) are **not** unvaried, and listing them fails the assertion. The palette does build LISTs and a MAP (`[ 1 2 ] list dict`, `lib.rs:604-605`); the criterion is operand depth, not type. If S2 gives `frame.sort` an `opts` operand, it and its form join the list.

**Suggested fix.** Derive the list from the declared effects: the plain words consuming 3 or more and the `.` forms of every word consuming 3 or more. Give each its reason as the audit's comment block does (`lib.rs:823-856`), and add `PROMOTABLE.txt` and `UNVARIED`'s length to the Preservation table as lines that move.

### S8. "`+` … unlike NODATA" is false; D252's finding is wrong, not just narrow

**The RFC says** (§Current behaviour): "`+` appends it to a LIST (… probed), unlike NODATA (D252's findings)". D252's finding is "`+` will not append one to a LIST" (`decisions.md:17304-17305`).

**What the probe shows.** `[ 1 2 ] nodata + println` and `nodata [ 1 2 ] + println` both print `[ 1 ::  2 ::  NODATA :: ]` (probed).

**Why it matters.** The RFC repeats a register finding that does not hold. D252's ruling rests mainly on the drain sentinel, which stands, so the ruling is not in question; the record is.

**Suggested fix.** Drop "unlike NODATA" from the RFC, and add a dated note to D252 beside the existing one, as was done for "no word produces it". Separately, the RFC says "D253 records the correction" of the NONE finding; the correction is D252's dated note (`decisions.md:17339-17349`), not D253.

### S9. `frame.text`'s layout is unspecified, so criterion 8 pins whatever is written first

**The RFC says** (§S6): right-align numeric columns, left-align the rest, NONE as `NA`, at most 20 rows and `… <n> more rows`. Criterion 8: "equals a string written out in the test".

**Why it matters.** The header line, the separator between columns, the padding, how a FLOAT is shown (the `dtoa` form, or fixed places), how a BOOL and a factor are shown, whether a long STRING is truncated (D36 asks for bounded rendering in reports; a table with a 10⁶-byte cell is not bounded), and whether the ellipsis is `…` or `...` are all the implementer's. A criterion that compares with a string the implementer writes checks nothing the RFC decided.

**Suggested fix.** Give the layout as a worked example in §S6, a three-column frame with a NONE, a FLOAT, a factor and a long STRING, and the exact text it prints. Then criterion 8 compares with that.

### S10. `frame.csv.parse` can build frames its own check refuses, and its header handling is unstated

**The RFC says** (§S6): options `header` (default `true`), `na`, `factors`; a ragged row is E102.

**What the source shows.** `read_frame` takes the header row as the names verbatim and, without a header, names columns `column_1`, `column_2`, … from the first row's width (`data.rs:162-183`). The `csv` conditional's key is `is_header` (`data.rs:225`, and `conditional_csv.rs:44`).

**Why it matters.** A header with a repeated or empty name gives a frame S2 refuses; the RFC does not say whether that is the check's refusal or the parser's. The names under `header false` are not stated. NaN and ±∞ fields: B1, item 5. A `factors` name that is not a column, or names a numeric column, has no rule. `header` beside `csv`'s `is_header` gives the same option two names in one language. There is no delimiter option, so a TSV or a `;`-separated file (common where `,` is the decimal mark) cannot be read.

**Suggested fix.** State each rule and its code; name the header option `is_header`, or say why it differs; state the `header false` names; either add a `delimiter` option or record its absence under Alternatives.

## What the RFC assumes and does not state

- **An equality** on frames, and that it distinguishes INTEGER from FLOAT and FLOAT bit patterns (B2).
- **That D254 is to be consumed**, and that consuming it means the frame reader needs to know whether a field was quoted. The `csv` crate's `StringRecord` does not say, so `read_frame`'s reader cannot be reused unchanged: `csv-core`, a record-level quote flag, or a parser of its own (`data.rs:24-25`).
- **That `infer` and `column_kind` can be shared.** Both are private to `data.rs`; sharing them is a visibility change in the module whose tests criterion 10 keeps "unchanged".
- **That every word checks its own answer.** Criterion 4 requires each answer to pass `frame.check`, but §S2 states the check only on entry.
- **What carries `levels`**: `frame.select` says so; `frame.take`, `frame.head`, `frame.filter`, `frame.sort`, `frame.aggregate` (on its `by` columns) and `frame.join` do not.
- **Types are preserved through moves**: an INTEGER cell stays INTEGER through `frame.take`, `frame.sort` and `frame.join`, and a numeric sort compares INTEGER with FLOAT by value.
- **STRING order is by UTF-8 bytes** (§S4 says "bytes"; D253 P7 says "sorted (bytes)"), and so is the default level order, which is not R's locale order. Q64 asks only whether R sorts.
- **The options MAP rules are RFC-0016 §S1's** (unknown key E101, and so on): the header names RFC-0016 as a dependency, but the design never says so.
- **No cap on the per-row work** of `frame.rows` and `frame.filter` (one MAP per row), beyond the input's size; D39 asks for caps on work a program's operands choose.
- **Input is UTF-8 text from `file`**, the delimiter is a comma, and line endings are whatever the `csv` crate accepts; output ends lines with `\n`. A byte-order mark on the first header name is not addressed. Not checked whether the `csv` crate strips one.
- **`frame.matrix`'s answer type depends on an option value** (a MATRIX, or a MAP under `"omit"`). The effect is still 1-for-1, but a program cannot write one sequence for both settings. P8 rules this; the RFC could say why the variation is acceptable.

## Verdict

**Not ready. 3 blocking, 10 should-fix, 13 notes.** The reference and Bund2 citations hold, the health numbers are right, and D253's rulings are transcribed faithfully. Blocking: the CSV round trip the RFC promises fails in five ways, one already ruled by D254 and not consumed (B1); the equality that criteria 4–7 depend on is undefined, and the two that exist cannot check them (B2); and the 0-based index convention rests on a premise the reference contradicts, a language choice no ruling covers (B3). The should-fix items are mostly unstated rules (codes, options, `na` on `by` columns, joins, statistics, the text layout, the header) and one real hazard: misaligned X and y under `"omit"` (S4). B3 needs an owner decision. B1 needs the INTEGER/FLOAT question D254 left open. Everything else is drafting.
