## Blocking

### B1. argmin's Gauss–Newton cannot run on the argmin-math the build links, so S16 and "Phase 4 adds no crate" are ungrounded

**Location.** §Current behaviour, "What is linked", the `argmin` row (line 153); S16 (lines 505-510); B1's and B8's recommendations (lines 705, 712); D250's "What is linked already".

**Evidence.**
- `GaussNewton`'s `Solver` impl requires `J: … + ArgminInv<J> + ArgminDot<J, J> + …` (`argmin-0.10.0/src/solver/gaussnewton/gaussnewton_method.rs:112-122`).
- In `argmin-math-0.4.0`, `ArgminInv` is implemented only in `src/nalgebra_m/inv.rs` and `src/ndarray_m/inv.rs`. `src/vec/` has no `inv.rs`.
- The crate's default features are `primitives` and `vec` (`argmin-math-0.4.0/Cargo.toml`, `[features]`).
- The lockfile's `argmin-math` 0.4.0 depends on neither nalgebra nor ndarray (`Cargo.lock:201-213`). So only the `vec` backend is compiled, and it cannot satisfy `ArgminInv`.
- The newest nalgebra backend argmin-math 0.4.0 offers is `nalgebra_latest = ["nalgebra_v0_32"]`, nalgebra **0.32**, not the 0.33.3 the RFC proposes to use. 0.32.6 is in the lock only through `statrs` 0.17.1 under `distimate` (`cargo tree -i nalgebra@0.32.6`).
- `ndarray_latest` is ndarray 0.15 plus `ndarray-linalg`, which links LAPACK.

**Problem.** "Nelder–Mead and Gauss–Newton (`argmin-0.10.0/src/solver/neldermead`, `…/gaussnewton`)" is cited to a directory, with no line. The call was not followed into the trait bounds. Gauss–Newton through argmin needs one of these:
- a backend feature that changes argmin-math's build: nalgebra 0.32 matrices beside the 0.33 ones the RFC uses elsewhere, so every Jacobian is converted between two nalgebra versions;
- Bund2's own parameter and Jacobian types implementing argmin-math's traits, which means making `argmin-math` a direct dependency (M1 does not name it);
- Bund2's own Gauss–Newton.

B1's and B8's recommendations rest on "Phases 1, 3 and 4 add no crate". D250 repeats that, so the owner would rule on a premise that is not established.

S16 also leaves unsaid where the Jacobian comes from. `f` is a Bund lambda, so it has to be finite differences, and the RFC does not state the step or the method. It also leaves unsaid how argmin's `Operator::apply(&self, …)` reaches `&mut dyn Vm` to call `eval_lambda`.

Research 06 §2 makes the same claim ("`argmin` 0.10.0 … Nelder–Mead, BFGS, L-BFGS, Gauss–Newton"). Once this is settled it belongs in `docs/research/ERRATA.md`.

**Suggested fix.**
1. Name the route: own types with argmin-math as a direct `=0.4.0` dependency, a backend feature with its version, or Bund2's own Gauss–Newton.
2. State the Jacobian's method.
3. Re-derive B1's and B8's rationale and D250's "What is linked already" from it.
4. Add an ERRATA line for research 06 §2.

### B2. Several entry points the RFC names panic or iterate without bound (D37, D39), and S11 has no code for the outcome

**Location.** S4's Source column (lines 257-263), the `nalgebra` row (line 152), S7 (lines 337-354), S9 (lines 380-389), S11 (lines 414-434); criterion 4 ("no panic path").

**Evidence.**

*nalgebra:*
- `symmetric_eigen` (`decomposition.rs:321`, cited) calls `SymmetricEigen::new`, which is `Self::try_new(m, T::RealField::default_epsilon(), 0).unwrap()` (`nalgebra-0.33.3/src/linalg/symmetric_eigen.rs:59-64`).
- `Schur::new`, which `schur()` calls and whose `eigenvalues` and `complex_eigenvalues` the RFC cites at `schur.rs:393,404`, is the same: `Self::try_new(m, …, 0).unwrap()` (`schur.rs:59-60`).
- `max_niter` 0 means "the algorithm continues indefinitely until convergence" (`decomposition.rs:302-306`, and the same text at `symmetric_eigen.rs:75-78`). So the cited entry points are an internal loop bounded by nothing (D39) followed by an `unwrap` (D37).
- The bounded forms are `try_symmetric_eigen` and `try_schur` (`decomposition.rs:307,341`), which return `None` at the cap.

*statrs, functions:*
- `beta`, `ln_beta` and `beta_reg`, the three S4 names (`beta.rs:44,75,124`, cited), are each `checked_*(…).unwrap()` and document "# Panics" (`beta.rs:40-46,71-77,120-126`).
- `gamma_lr`, S4's source for `math.gammainc`, is `checked_gamma_lr(a, x).unwrap()` and panics unless a and x are in (0, +∞) (`gamma.rs:255-266`).

*statrs, distributions:*
- The default `DiscreteCDF::inverse_cdf` does `panic!("p must be on [0, 1]")`, and a NaN p reaches it, because `!(0..=1).contains(&NaN)` is true (`distribution/mod.rs:198-210`).
- `Gamma`, `Beta`, `FisherSnedecor` and `StudentsT` panic or `assert!` on p outside [0,1] in their own `inverse_cdf` (`gamma.rs:184-187`, `beta.rs:187-189`, `fisher_snedecor.rs:202-204`, `students_t.rs:227-229`).
- The `Continuous` trait is documented "unchecked, meaning they can panic if in an invalid state or encountering invalid input" (`distribution/mod.rs:224-231`).

**Problem.**
- S4's table is the specification an implementer will follow, and it names the panicking functions.
- S9 needs a refusal for "did not converge within its cap" on eigen-decomposition. E110 is defined as "an integration or optimisation that did not converge", which does not cover it, and S9 lists no such refusal.
- The RFC states "No word answers NaN or ±∞ from finite operands" and "A NaN operand is E101". It never says that every statrs call is guarded before it is made. That guard is what keeps the panics out, and criterion 4 cannot be met without it.

**Suggested fix.**
1. Name the `checked_*` functions in S4.
2. Name `try_symmetric_eigen` and `try_schur` with a stated `max_niter`, and give their `None` a code: E110 widened, or a new one.
3. State that every `inverse_cdf` and `pdf` call is preceded by Bund2's own check of p ∈ [0,1], x in the support, and not NaN.
4. Add a criterion per family that feeds NaN, p = −0.1 and p = 1.1, and requires a refusal rather than an abort. A `#[test]` that does not abort is the check.

### B3. Worked example 5 is refused by S9's own E108, so criterion 11 cannot pass as written

**Location.** S9, `linalg.eigenvalues` (line 387); worked example 5 (lines 552-555); criterion 11 (line 662); the Motivation's "a growth rate from a Leslie matrix" (line 72).

**Evidence.**
- The example's matrix has rows `[0 1.5 0.8] [0.5 0 0] [0 0.7 0]`.
- Its characteristic polynomial is λ³ − 0.75λ − 0.28 = 0. That is λ³ = f₂s₁λ + f₃s₁s₂, with f₂ = 1.5, f₃ = 0.8, s₁ = 0.5 and s₂ = 0.7.
- Solved numerically, its roots are 1.0131 and −0.50655 ± 0.14066i.
- ‖A‖ is about 1.9, so 1e-12·‖A‖ is about 2e-12. The imaginary part, 0.14, exceeds it by eleven orders.
- S9 says `linalg.eigenvalues` answers "real parts, with E108 if any imaginary part exceeds 1e-12·‖A‖". So `linalg.eigenvalues math.max` is refused.
- nalgebra's `Schur::eigenvalues` likewise answers `None` here ("Return `None` if some eigenvalues are complex", `schur.rs:391-399`).

**Problem.** Leslie and other population-projection matrices generically have complex subdominant eigenvalues. The quantity a biologist wants is the dominant (Perron) eigenvalue and its eigenvector, the stable age distribution. S9 offers no word for it. The RFC's own motivating case is therefore unreachable, and criterion 11's "against a published value" names neither the value nor its source.

**Suggested fix.**
1. Add a word, for example `linalg.dominant` (`A -- MAP` of `value` and `vector`), or let `linalg.eigenvalues` answer complex values as pairs.
2. Rewrite example 5 and criterion 11 against it, with the expected λ = 1.01310… and the eigenvalue's source named.

### S1. B12 promises "never ±∞ from finite operands" but S11 has no refusal for overflow, and several domains are mis-stated

**Location.** S4's domain paragraph (lines 271-273); S11 (lines 419, 433-434); criterion 6.

**Problem.** Each case below gives ±∞, NaN or a refusal from finite operands, and none is covered:

| Case | What happens | Evidence |
|---|---|---|
| Γ(172) | overflows f64 | |
| `math.expm1` at 710 | overflows | |
| `vec.prod` and `vec.cumprod` | can overflow | |
| `linalg.power` | can overflow | |
| `dist.pdf` near a degenerate point | can overflow | |
| `math.choose` at large n | `binomial` takes `exp` of a log difference | `factorial.rs:42-48` |
| `math.erfinv` at ±1 | returns ±∞ | `erf.rs:24-31` |
| `math.lgamma` at 0 | `ln_gamma` takes `ln(sin(πx))`, so 0 gives +∞ | `gamma.rs:54-66` |

Criterion 6's "ln Γ(171.5) finite" is trivially true: about 706. The useful pins are "Γ(171.5) is refused" and "ln Γ(171.5) equals its published value".

### S2. The new `math.*` words differ from their neighbours twice over, and the operand-order claim is wrong

**Location.** S4 (lines 252, 265-269); §Current behaviour, "Scalar functions" (lines 111-116).

**Evidence.**
- *INTEGER operands.* Every reference unary `math.*` word refuses an INTEGER: `cast_float` accepts only `Val::F64` (`reference/rust_dynamic/src/cast.rs:9-16`). In Bund2, `4 math.sqrt` answers "FLOAT_OP returns error: This Dynamic type is not float: 2". S4's new words take one ("an INTEGER converts").
- *Domain errors.* `-1.0 math.ln` and `-1.0 math.sqrt` answer `NaN` in Bund2. S4's new words refuse under B12.
- *Operand order.* S4 says the reversed order "is a reference property of the arithmetic operators alone".
  - `math.nroot` passes the **top** operand as the radicand: `math::nrt(fvalue, nvalue)`, with `fvalue` pulled first (`reference/Bund/src/stdlib/functions/math/math.rs:57-82`). In Bund2, `8.0 3.0 math.nroot` answers 1.1472 (3^(1/8)), not 2.
  - `math.perimeter` also takes the top first (`math.rs:94-99`). `math.power` takes the deepest as the base (`math.rs:111-116`).
  - `math.interpolation` reads `x` from the top series and `y` from the one beneath (`reference/Bund/src/stdlib/functions/math/interp.rs:15-26`).
  - So the reference's own two-operand `math.` words disagree with each other, and the claim of "alone" is false.

**Problem.** Programs will mix old and new words under one prefix. An owner ruling B12 should see that `math.log2` will refuse where `math.ln` answers NaN, and that `math.lgamma` will take an INTEGER that `math.ln` refuses.

**Suggested fix.** Correct the operand-order sentence, citing `math.rs:57-82,111-116`, and state both inconsistencies as accepted under B12. Alternatively, make the INTEGER rule match the neighbours.

### S3. Words with a series and further operands, or two series, are not defined against `get_data`'s drain and forms

**Location.** S5 (lines 279-287); S6 (lines 291-324); S3 (lines 244-245).

**Evidence.**
- `get_data` drains the stack to a NODATA, or to the bottom, when the top is neither a LIST nor a METRICS (`get_data.rs:213-216`, `:24-41`).
- The reference's two-series words call it twice, and the first call takes the **top** series (`forecast/outliers.rs:24-31`, `math/interp.rs:15-26`).

**Problem.** The RFC does not say, for any of these words:
- **The read order.** For `stat.quantile` (`series p`), `stat.test.t1` (`series μ₀`), `stat.cov`, the `stat.cor.*` words and every two-sample test, it does not say whether the scalar is pulled before the reader runs. Nor does it say which series is read first, or whether either may be a drain. A drained first series consumes the second.
- **The `.` form.** It does not say which operand comes from the workbench. D111's dated note of 2026-10-07 answers this for fixed-arity words, "the operand the plain word has on top" (`decisions.md`, D111, the family table). The RFC does not cite it, and it does not apply to a drain.
- **Operand order for non-commutative words.** It is unstated for `vec.sub`, `vec.div`, `stat.test.t2`, `stat.test.welch`, `stat.test.paired`, `stat.test.mannwhitney` and `stat.test.ks2`, where the statistic's sign depends on which sample is `a`. It is also unstated for `linalg.mul`, `linalg.solve` and `bio.align`. S4's deepest-first rule is stated for S4 alone.

**Suggested fix.**
1. Add a paragraph to S2 or S3. Scalars are pulled first. Two-series words take LISTs or METRICS only and refuse a drain. The deepest operand is the first parameter for every word in the RFC.
2. State that the reference's `interp`/`outliers` precedent runs the other way, and that this is a choice.
3. Give each multi-operand series word's `.` form.

### S4. "Opaque" is redefined, against the term's meaning in Bund2, and the promotion mechanism for `rng.seed` is missing

**Location.** S3 (line 248); S17 (lines 517-522).

**Evidence.**
- In Bund2, "opaque" is a declared effect, `StackEffect::opaque`: "runs a body, or variadic" (D111's table, `decisions.md` line 11849).
- **Every series word is already opaque.** `math.normalize`, `math.smoothing`, `math.max`/`min`, `stat.count` and `stat.mean.*` register `StackEffect::opaque(1)` and `opaque(0)` "for the drain's sake" (`crates/bund2-stdlib/src/series.rs`, the comment and registrations from line 405). `bund2 effects` prints `stat.count 1 0 opaque`.
- So S3's "words that read a series have the four forms" and "opaque words have none" contradict each other in the house's terms.
- S17 then calls "the multi-result tests" opaque, but each test answers one MAP. It also calls `rng.seed` opaque, though it is fixed `1 → 0`.
- **Promotion.** Tier 1 crosses natives listed in `tests/golden/PROMOTABLE.txt`. `math.random.int` and `math.securerandom.int` are listed (`PROMOTABLE.txt:222,225`), so "has a side effect" is not by itself what keeps a native out. The hand-kept list that does is `ACTS_ON_HOST` (`crates/bund2-stdlib/src/lib.rs:647`).
- **Forms.** D24, as D111 applies it, gives producers ("consumes nothing") no `.` form. `rng.uniform` (`-- x`) is one, and S3 says "every other fixed-arity word has its `.` form".

**Suggested fix.**
1. Use the house's meaning: a word is opaque if it is declared `StackEffect::opaque`, which covers the lambda-calling words and every drain-reading form.
2. Say whether `rng.seed` goes into `ACTS_ON_HOST`, or is promotable as `math.random.int` is, and why.
3. Exempt producers from S3's `.` rule, citing D24 and D111.

### S5. A tree as a GRAPH has its names rewritten by `graph.*`, so "So `graph.*` walks it" holds only for some names

**Location.** S14, "A tree [B7]" (lines 477-478); B7; criterion 16's Newick round trip.

**Evidence.**
- "Node names are **Title-cased before anything looks them up** … `:my_node` becomes `My Node` and `:AB` becomes `Ab`" (`crates/bund2-stdlib/src/graph.rs:34-43`).
- "Title case splits at digits too, so `:N1` lists a node `N 1`" (`graph_algorithms.rs:1356`).
- A node *operand* is looked up as given (F218, D211; `graph_algorithms.rs:13-24`).
- RFC-0012 is cited for the representation, but no line or symbol is given for it.

**Problem.**
- The root `"root"` reads as `Root` to every algorithm, and `:root` as an operand finds nothing.
- Taxon names such as `Homo_sapiens`, `HLA-B27` or `seq1` change, and two names can merge (`AB` and `Ab`).
- The tree that `phylo.*` writes can round-trip through Newick, but what `graph.*` answers about it will name different nodes. B7's recommendation is argued from "So `graph.*` walks it", and the owner should see this cost.

**Suggested fix.**
1. State that `phylo.*` writes names verbatim and that `graph.*` Title-cases them on reading.
2. Choose a root name that Title-casing leaves alone (`Root`), or reconsider B7.
3. Add a criterion running one `graph.*` word over a `phylo.upgma` tree with mixed-case names.

### S6. The worked examples, and S2's distribution literal, are not Bund as Bund2 reads it

**Location.** S2 (line 230); worked examples 3 and 4 (lines 541-550); criterion 20, which runs each.

**Evidence.** Each item was run on `target/debug/bund2` at 948bd78.
- **S2's literal.** `{ dist=normal :: mean=0.0 :: sd=1.0 } println` prints `lambda[ F(dist=normal) ::  F(::) ::  F(mean=0.0) … ]`. `{ }` is a LAMBDA literal, not a MAP. A MAP is built as `dict "dist" "normal" set …` (`tests/probes/conv-string-words.bund:21,34-36`).
- **Example 4.**
  - `:sir lambda` pushes the STRING `"sir"` and then an empty LAMBDA. `:rep { 1 2 + } register :rep lambda println` prints `lambda[]`, because `lambda` builds an empty LAMBDA and does not fetch a word's body. So `ode.rk45` receives an empty `f`, and a stray STRING is left beneath.
  - The body's `,` is an alias of `set` (D111's dated note: "`,`, the other alias of `set`").
- **Example 3.**
  - `list 1 swap push println` prints `[ [ 1 :: ] :: ]`. `push` appends its second operand whole (`tests/probes/list-push-and-unfold.bund:4-7`). So the child receives a LIST on its stack, and `rng.seed` gets a LIST, not an INTEGER.
  - `:rep` is registered in the parent, and "a LAMBDA that calls the parent's own words fails in the child" (`crates/bund2-runtime/src/vms.rs:164-169`). The program must be the lambda itself.
- **Example 1.** It reads `:p` from `popgen.hwe`'s answer, but S13 does not name that answer's keys. `popgen.hwe` is not among S6's tests, which use S2's `statistic`/`p`/`df`/`method`.

**Suggested fix.**
1. Rewrite the examples in runnable Bund: inline `{ … }` lambdas, `[ 1 ]` for the start-up LIST, a MAP built with `dict … set`, and no `,` or `−` in a body.
2. Name `popgen.hwe`'s keys.
3. "Illustrative until Phase acceptance" does not excuse S2's literal, which is in the Design.

### S7. `statrs`'s binomial sampler is O(n), so `popgen.wf` and `dist.sample` on a binomial are an operand-driven loop D39's cap does not reach

**Location.** S13, `popgen.wf` and `popgen.wf.selection` (lines 464-465); S7, `dist.sample`.

**Evidence.** `Binomial::sample` folds `0..self.n`, drawing one uniform per trial (`statrs-0.18.0/src/distribution/binomial.rs:115-124`).

**Problem.** One Wright–Fisher generation at N = 10⁹ is 2·10⁹ draws inside one native call. The RFC caps `generations` (E111) but not N, so the work is N × generations. `rand_distr` 0.4.3 is already in the lock (`Cargo.lock:3651`, through nalgebra's `rand` feature) and has an O(1) BTPE binomial. But its stream differs from statrs's, which matters to S8's reproducibility statement.

**Suggested fix.** Choose the sampler, cap N, or both, and state it in S8 as part of what "repeats exactly" means.

### S8. Several criteria will fail, or cannot be reproduced, against the references they name

**Location.** §Acceptance criteria (lines 624-699).

**Problem.** Criteria that will fail as written:
- **Geometric.** statrs's Geometric counts trials, with support from 1 and pmf(0) = 0 (`statrs-0.18.0/src/distribution/geometric.rs:166-168,273-279`). R's `dgeom` counts failures, with support from 0. Criterion 9's "against R's `d`/`p`/`q`" fails for `dist.geometric` unless S7 states the support and the shift.
- **Hypergeometric.** `dist.hypergeometric (N K n)` and R's `dhyper(x, m, n, k)` differ in parameters. The mapping should be written down.
- **Inverse cdf.** Gamma and χ² (`ChiSquared` delegates to `Gamma`, `chi_squared.rs:153-155`) run 8 bisection steps and at most 4 Newton steps (`gamma.rs:194-222`). Criterion 9's "`dist.quantile` inverts `dist.cdf` to 1e-10" is not assured for them.
- **R base.** It has no skewness, kurtosis or mode, so criterion 8's "descriptive answers … against R 4.x" names no reference for `stat.skewness`, `stat.kurtosis` (which of g₂, G₂ or b₂?) or `stat.mode`.
- **R's defaults.** `chisq.test` applies Yates's correction to a 2×2 table by default. `ks.test` uses the exact p for small samples without ties. `fisher.test` and `binom.test` use a specific two-sided rule. S6 states none of these, so the fixtures cannot be regenerated.
- **A&S table 7.1.** It gives erf to 10 digits. Criterion 6 applies "1e-12 for closed forms" to it.

Reference values the criteria do not identify:
- "R 4.x" (give the exact release);
- "R's `pbeta` at stated points", and "three points" for each family in criterion 9 (no points are stated);
- "a published value" (criterion 11);
- "a fixture from GenBank" (give the accession);
- "a fixture with known answers" (criterion 15);
- "the textbook five-taxon example" (give the text and page);
- "a published data set" with "its published confidence interval" (criterion 19);
- "Wigginton et al.'s published examples" (give the table).

Criteria that cannot be checked as worded:
- Criterion 3, "a test by its text": S11 gives each code's reason, not its text. RFC-0013 renders `<WORD>: <text>` (`crates/bund2-stdlib/src/kb/words.rs:26-28`), and the RFC should give each code's text or its template.
- Criterion 10's third bullet, "`math.random.int` is unaffected by `rng.seed`": an unseeded source cannot be shown unaffected. The checkable form is the converse: a seeded `dist.sample*` stream is unchanged when `math.random.int` and `generator.sample` calls are interleaved with it.

### S9. Most words have no criterion

**Location.** §Acceptance criteria.

**Problem.** These words, from the S-tables, appear in no criterion:
- S9: `linalg.t`, `identity`, `det`, `solve`, `eigen.sym`, `power` and `mulv`. Criterion 11 covers "products and inverses".
- S7: `dist.mean`, `dist.var` and `dist.lpdf`; the multivariate families' `dist.pdf`; their E105 for each refused word.
- S10: `bio.valid?`, `complement`, `transcribe`, `backtranscribe`, `gc`, `kmers`, `count`, `hamming`, `consensus`, `pwm`, `pwm.scan` and `mw`. `bio.mw` names no weight table at all.
- S12: `semiglobal`, `bio.align.score`, and the `pam250` and MAP matrices.
- S13: `popgen.freq`, `het`, `fst`, `ld` and `wf.selection`.
- S15: `ode.rk4`. Criterion 17 names no integrator for logistic growth.

Criterion 2 says only S-table words are added. The four forms add more, so criterion 2 should count them.

### S10. "A generator per thread, so per VM" is not true of Bund2's API

**Location.** S8 (lines 358-360); B4.

**Evidence.**
- `Host` and `vm.spawn` give each VM its own thread (D249; `vms.rs` module doc).
- An embedder may still build several `Interp`s on one thread. The stdlib's own palette audit does: `Interp::new()` many times in one test thread (`crates/bund2-stdlib/src/lib.rs:852,888,1004`).

**Problem.** `rng.seed` in one VM then changes another's draws on the same thread. B4 A is argued as "per VM".

**Suggested fix.** Either keep the generator in the VM (`Interp` state reachable through `dyn Vm`), or say "per thread" and state the consequence for embedders.

### S11. The model lambda's stack discipline is unspecified

**Location.** S15 (lines 484-499); S16 (lines 507-508).

**Problem.** S15 says "Each call into `f` is a `Vm::eval_lambda`", and E112 refuses "a model lambda that left the wrong number of values". The RFC does not say:
- which stack the lambda runs on;
- whether the caller's values beneath `t y` are visible to it;
- how "wrong number" is measured when the lambda consumes below its operands;
- what the stack holds after a mid-integration refusal.

RFC-0013's bridge is cited as precedent (`kb/bridge.rs`, which calls `Vm::eval_lambda` at line 463), and its discipline should be named or reused.

Nested integration, an `ode.rk45` whose `f` calls `ode.rk45`, is Rust recursion per level. It is bounded by `eval_lambda`'s stack floor (`crates/bund2-interp/src/lib.rs:2830-2835`, F85, RFC-0005 §S8). Cite that floor as the D39 answer. The RFC's "no Rust recursion is driven by a value a program controls" otherwise reads as violated.

### S12. Phase 2 and Phase 3 inputs are not specified well enough to implement or test

**Location.** S12 (lines 438-449); S13 (lines 453-465); S10, `bio.translate` (line 398).

**Problem.**
- **Alignment gaps.** Gotoh's affine-gap convention is unstated: is the first gap residue charged `open` or `open + extend`? End-gap handling in `global` is unstated too. EMBOSS `needle`, criterion 14's reference, does not penalise end gaps by default and charges `gapopen` for the first position. The fixtures depend on both.
- **Population-genetics shapes.**
  - `popgen.fst`'s `populations` has no stated shape.
  - `popgen.ld`'s four counts have no stated order.
  - S13 accepts "a LIST of MAPs or of genotype STRINGs", while B13 and D250 say "genotype STRINGs or counts". The MAP form has no stated keys.
  - Allele encoding is case-based and biallelic (`"Aa"`), and the RFC does not say so or say what a multi-allelic locus does.
- **Genetic code tables.** "NCBI table number" does not say which tables exist. NCBI numbers 1-6, 9-16 and 21-33, with gaps. Criterion 13's "each genetic code table" needs the list.

## What the RFC assumes and does not state

- That statrs's Normal, Uniform and LogNormal parameterisations match R's: they do, but nothing says so. Gamma is (shape, rate) in both. Geometric and Hypergeometric do not match (S8).
- That each statrs `sample` algorithm is stable within one pinned version, as `rand`'s `StdRng` is. That is true while `statrs` is pinned exactly, which it is (`=0.18.0`).
- That making `nalgebra` a direct dependency at `=0.33.3` unifies with `augurs-ets`'s features. Enabling statrs's `nalgebra` feature with `rand` also enables `nalgebra?/rand` (`statrs-0.18.0/Cargo.toml`, `[features]`). That is already on through augurs, since the lock shows nalgebra 0.33.3 depending on `rand` and `rand_distr` (`Cargo.lock:2808-2820`). So no crate is added. The RFC asserts the conclusion, and this is the reason.
- That generated artefacts beyond `PROMOTABLE.txt` move with the new words. `bund2 effects` output and `docs/arity.md` (`cargo xtask arity`) do, and the Preservation table does not list them.
- That the palette audit, which runs every fixed-effect native over `7 2.5 … { 1 } { drop } …` (`crates/bund2-stdlib/src/lib.rs:601-602`), is harmless for these words. It is, at those magnitudes, but only because the palette's INTEGER is 7.

## Verdict

**Not ready.** Three things block:
- **B1.** The Gauss–Newton route through argmin is not buildable from the linked argmin-math. "Phase 4 adds no crate", on which B1 and B8 rest, needs re-deriving.
- **B2.** The named nalgebra and statrs entry points panic or loop without bound. The specification must name the checked or bounded forms and give non-convergence a code.
- **B3.** The Leslie-matrix example and criterion 11 are refused by S9's own E108. A dominant-eigenvalue word, or complex answers, is needed.

After those, the largest should-fix items are:
- S3: operand order and drain behaviour for multi-operand series words;
- S4: "opaque" used against its house meaning;
- S6: worked examples that do not parse as intended;
- S8: criteria whose references are unnamed, or will disagree with statrs (Geometric).
