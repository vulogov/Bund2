## 1. Blocking

### B1 — §S1's diagnosis does not describe the line it cites

§S1 (lines 111–118) is the passage the RFC says "is what the gate turned on",
and it is kept deliberately. It reads:

> `with_tag` (`crates/bund2-value/src/lib.rs`) boxes the scalar,
> materialises its identity, clones the entire `HeapValue` including its
> `BTreeMap` of tags, inserts two freshly allocated `String`s, and wraps the
> result in a new `Rc`. Four allocations and a map clone, per value, per push.

`crates/bund2-value/src/lib.rs` today is:

```
pub fn with_tag(self, key: Rc<str>, value: Rc<str>) -> Self {
    let mut h = self.into_heap();
    match Rc::get_mut(&mut h) {
        Some(only) => { only.tags.insert(key, value); }
        None => { let _ = h.identity(); let mut next = (*h).clone(); … }
```

Three of the four claims are false of that line:

- **"inserts two freshly allocated `String`s"** — the parameters are `Rc<str>`,
  interned. `crates/bund2-bench/benches/interpret.rs` says so in its own
  words: "Interned once, as `Stack` caches them — measuring `Rc::from` here would
  measure the allocation the interning exists to remove."
- **"materialises its identity"** and **"clones the entire `HeapValue`"** — both
  live on the `None` arm, taken only when the `Rc` is shared. The bench's comment
  at `:141-143` names the production case as the *other* arm: "a literal off the
  stream is a scalar, so boxing it yields a fresh `Rc` with one holder and
  `with_tag` takes its in-place branch."

So the sentence describes the **shared** path and attributes it to **every
push**, and "four allocations and a map clone, per value, per push" does not
follow from the cited code.

This is not cosmetic. §S1's whole standing is "the diagnosis is kept because it
is what the gate turned on". If the diagnosis is not what the cited line says,
the RFC cannot claim to have grounded the reason the gate moved. Either cite the
pre-D41 revision explicitly (D41's own entry has the decomposition: of 52 ns,
43.7 was `with_tag` and 25.1 of that was `promote/scalar` — boxing with no tag
written, `decisions.md:2127-2135`) or restate the claim against line 2018 as it
now stands. The same wrong sentence has propagated to two other places and
should move with it: `crates/bund2-bench/benches/interpret.rs` and
`docs/registers/open-questions.md:13` (Q25).

### B2 — the header, the Summary and §S1 give three different answers to "does the gate pass", and two different numbers

- **Header, line 11**: "The gate is met and §S2-§S11 are live." Line 10: "push/pull
  126.9 -> **10.1** ns, dispatch now the dominant term."
- **Summary, line 43**: "**The measurement in §S1 says it should not be built
  yet.**"
- **§S1, line 149**: "**So the gate's answer is: not yet.**"
- **§S1 update, line 184**: "**Prerequisite 2 is not settled, and this update no
  longer claims it is.**" And line 198: "'at most' is the honest quantifier".
- **§S1 update table, line 179 and criterion 1, line 665**: `push_pull/balanced`
  is **9.8 ns**.

Three problems, all fixable by editing, none by a reader:

1. Line 43 and lines 149–164 are pre-update text left in the present tense. Line
   120 announces that §S1 "is written in the past tense deliberately" and then
   lines 149–164 are not. `[carried — prior review S2, S3]`
2. **The header asserts "dispatch now the dominant term" while §S1 explicitly
   withdraws that claim.** The header is the load-bearing sentence — it is what
   makes §S2–§S11 live — and it states the one thing the body says cannot be
   shown with these benchmarks. Q29 (`open-questions.md:17`) carries the same
   over-claim ("so dispatch is the dominant term"), so the register does not
   rescue it.
3. **10.1 ns and 9.8 ns are both given for `value/push_pull/balanced`.** D41 and
   Q29 say 10.1. §S1's table and criterion 1 say 9.8. The gate passes on either,
   but the RFC quotes two figures for one benchmark and marks one of them "Met".
   Pick one and say what the other was (a re-run? a different machine state?).

The honest header is: prerequisite 1 is met, prerequisite 2 is bounded from
above and not settled, and §S2–§S11 are live because criterion 10 will settle it
rather than because it is settled. That is what §S1 argues; the header should say
it.

### B3 — "Cranelift … is not yet a dependency of anything" is false

Current behaviour, line 61. The tree says otherwise:

- `crates/bund2-jit/Cargo.toml:13-17` — all five cranelift crates, `workspace =
  true, optional = true`.
- `:23-24` — features `aot` and `jit` already declared, each naming its `dep:`
  set.
- `crates/bund2-runtime/Cargo.toml:16` — `bund2-jit = { workspace = true,
  optional = true }`; `:21-22` — `aot = ["dep:bund2-jit", "bund2-jit/aot"]`,
  `jit = ["dep:bund2-jit", "bund2-jit/jit"]`.

This matters beyond accuracy. §S10 argues that "Tier 1 must be a `cargo` feature
that compiles out cleanly, exactly as `string.grok` is (D40)" as though it were
prescribing something. Half of it exists. The RFC should state what is already
wired and specify only the gap — chiefly the one §S10 never states: **is `jit`
in any crate's `default` list, and what does `cargo xtask conform` build?**
Criterion 2 requires conform to read the same N/M "with the `jit` feature on and
off" and there is no stated route from an xtask invocation to that feature.
`[carried — prior review S10]`

### B4 — criterion 7's command cannot be run as written

    cargo bench -p bund2-bench -- --save-baseline off
    cargo bench -p bund2-bench --features jit -- --baseline off

`crates/bund2-bench/Cargo.toml` declares no `[features]` table at all, and its
dev-dependencies are `bund2-value`, `bund2-api`, `bund2-syntax`, `bund2-stdlib`,
`bund2-interp` — no `bund2-runtime`, no `bund2-jit`. The second command fails
with "Package `bund2-bench` does not have feature `jit`", and even with the
feature added there is no path from a bench to compiled code.

A criterion whose command does not run is the same failure mode the RFC's own
preamble diagnoses for criteria 4, 6 and 7 ("names no tool"). Criterion 7 names a
tool that does not accept it. The criterion should say what has to be built:
`bund2-bench` gains a `jit` feature forwarding to `bund2-runtime/jit`, and the
benches take their `Interp` through whatever entry point the tier hangs off.
Criterion 9 and criterion 10 depend on the same missing wiring and inherit the
defect.

### B5 — §S6's claim about the study's table is false, and the RFC contradicts it four pages later

§S6, line 393: "§2.1's only row promising more than ~1.5× is 'stack-slot
promotion + type guards — ~2–5×'."

`docs/research/00-jit-feasibility.md:248-254` has five rows. Three promise more
than ~1.5×:

| row | expectation |
|---|---|
| Value representation rework | large multiple |
| Symbol interning + slot table | large multiple |
| IR + threaded interpreter | ~2× |
| Cranelift tier: naive lowering | ~1.2–1.5× |
| Cranelift tier: stack-slot promotion + type guards | ~2–5× |

The RFC's own Alternatives section says so: "**A threaded interpreter instead of
a JIT.** §2.1 rates this ~2×" (line 638). §S6 and Alternatives cannot both be
right. The defensible sentence is "the only *Cranelift* row promising more than
~1.5×", which is what §S6 needs and is true. As written the RFC overstates the
uniqueness of the win it is arguing for, in the section that argues for it.
`[carried — prior review S6]`

### B6 — ERRATA's live conclusion still contradicts the RFC, and the RFC's Supersedes bullet claims otherwise

The header (line 32) says the substitution of §2.1's table is "Recorded in
`docs/research/ERRATA.md`". It is, at `ERRATA.md:89-106` — and that entry's last
sentence is:

> **Boxing is the bottleneck; dispatch is not.**

The entry does carry the 2026-09-09 withdrawal of the Amdahl bound (`:95-100`),
which matches §S1. It does **not** carry D41, and it still concludes in the
present tense that §2.2's gate "does not pass". Its evidence line (`:102-103`)
quotes the pre-D41 figures — 73.1 / 4.1 / 126.9 ns — as current.

Research documents are immutable and ERRATA is the amendment log, so the fix is
an *appended* line recording D41 and the gate's reversal. Until it exists, the
RFC's header claim "Recorded in ERRATA" is true of the table substitution and
false of the status change the header actually turns on, and a reader who
follows the pointer finds the opposite conclusion. `[carried — prior review S5]`

### B7 — compiled non-tail calls reintroduce Rust-stack growth that RFC-0003 exists to remove, and no criterion catches it

§S8 states the property and provides no mechanism:

> RFC-0003's frame loop already makes Bund-level call depth cost heap rather
> than Rust stack, and `Vm::tail_call` exists for exactly these positions; a
> compiled body must preserve that property rather than reintroduce stack
> growth Tier 0 does not have. (lines 551–554)

`Vm::tail_call` is real — `crates/bund2-api/src/lib.rs`,
`crates/bund2-interp/src/lib.rs`, called from `control.rs:56`, `:149`,
`values.rs:299`. But §S8 claims tail-call lowering for **the last word of a body
only**, and explicitly disclaims threaded code. Every *other* inter-word call in
a compiled body is an ordinary `call_indirect` and consumes a machine frame. Tier
0 consumes none: the frame loop is flat.

So a recursion that Tier 0 runs to arbitrary depth on the heap overflows the
machine stack once its body is promoted. That is:

- a **conformance-visible behaviour change** — the same program succeeds
  interpreted and dies compiled — which §S2's "exactly zero" invariant forbids;
- an **abort**, which D37 forbids absolutely and which no `Result` arm can catch;
- **not in the Preservation analysis table**, and not covered by any criterion.
  Criterion 2 would only catch it if a golden recurses deeply enough, and the
  goldens are 86 corpus programs, not a depth probe.

The RFC must either (a) require every inter-word call in tail position within a
compiled body — not just the last — to lower as `return_call_indirect`, and say
what happens on s390x where §S8 says it degrades to an ordinary call, or (b)
carry a depth guard at compiled-body entry that declines to run beyond a bound,
or (c) state the deviation. Whichever it is, it needs a Preservation row and a
criterion of the form "a body Tier 0 recurses N deep in, promoted, still
recurses N deep".

Note the interaction with Q28: if the answer to "does s390x matter" is yes, then
on s390x option (a) is unavailable and the design has no answer at all.

## 2. Significant

### S1 — §S7's `Weak` argument undercuts D35's stated rationale for the cache's strong reference, and the RFC does not say so

§S7 (lines 481–486) establishes a property and leans on it:

> **the backing allocation is freed only when the strong *and* weak counts reach
> zero.** So a live `Weak` keeps the allocation — and therefore the address
> `Rc::as_ptr` returns — out of circulation.

That is correct about `Rc`. But D35's entire justification for the *cache*
holding a **strong** reference is address reuse:

> If an entry outlives its body, the allocator may reuse the address and a stale
> entry becomes a *false hit* — wrong code executed
> (`docs/registers/decisions.md:1758-1760`).

If a `Weak` suffices to keep the address out of circulation — and §S7 says it
does — then a `Weak`-held cache would be equally safe from false hits *and*
would not pin ≤1024 bodies alive. §S7's own comparison table (lines 491–494)
asserts a stale cache entry means "wrong code executed"; under the argument §S7
introduces four lines earlier, a stale entry is an entry whose `Weak` fails to
upgrade, which is a miss.

This may still resolve in favour of strong (the compiled code may need the body
reachable for reasons the RFC has not stated — deopt-free reporting, D36
diagnostics naming the body, re-entry after demotion). But the RFC has discovered
an argument against a resolved decision and files it as support for that
decision. Say which: either state the reason the cache needs the body's
*contents* and not merely its address, or record that D35's rationale is
narrower than stated and take it back to `decisions.md`. Adopting the pinning
cost silently is the thing CLAUDE.md forbids.

### S2 — §S7's D3 argument is off by one, in the sentence that makes D3 true

Line 454: "eval'd bodies are fresh `Rc`s per call, so their count never reaches
1, let alone 64."

An eval'd body evaluated once takes its count to **1**. The claim is "never
exceeds 1" or "never reaches 2". As written the sentence is false, and it is the
sentence the RFC offers as making "D3 true *by construction* rather than by
rule".

### S3 — §S6's `graph!` row is wrong and uncited

§S6's table (line 414): "`graph!` | 5 | consumes 0 or 2 depending on the tags it
is handed".

`crates/bund2-stdlib/src/graph.rs`: it pulls `nodes`; if the value is not
a `LIST` it **pushes it back** and substitutes an empty list; then does the same
for `edges`. So the discriminator is the **type**, not tags, and the consumption
is **0, 1 or 2** — a LIST on top of a non-LIST consumes exactly one. The
function's own doc comment (`:40-44`) states this and cites
`reference/Bund/src/stdlib/functions/graph/mod.rs:71-76`. §S6 cites nothing.

### S4 — §S6 uses three unreconciled denominators

- §S6 line 405: "over the **160** corpus programs and probes"
- §S6 line 417: "81 of the **132** corpus programs"; "88 contain a lambda body"
- RFC-0004 line 525: "Across the **157** programs: 770 sites analysed"
- ERRATA line 22: "zero uses across all **132** programs"

132 is the corpus; 160 presumably adds `tests/probes/`; 157 is RFC-0004's own
run of the same tool. None of that is stated, and 157 vs 160 is unexplained
between two documents dated one day apart. Say what each population is once.

### S5 — §S6 enumerates two of D33's three options, and the missing one changes §S6's rule

§S6 (lines 437–441) requires mixed-kind comparison to take the generic path and
notes "if D33 resolves to option 2 the lowering becomes available". D33
(`decisions.md:1527-1533`) has a third option: **reject mixed kinds** — bail as
the gate already does for a string operand.

Under option 3 the "generic path" is not a comparison at all; it is an error
return, and a compiled site must lower to a diagnostic rather than to a branch.
That is a different lowering, not the same one deferred. §S6 should say so, or
say why option 3 need not be planned for.

Two smaller notes on the same paragraph: the RFC says it "does not take D33's
default", but D33 records a **Recommendation** (option 2) and a separate "What is
implemented meanwhile" (**option 1**). Requiring the generic path *is* what
option 1 produces. The RFC is withholding the recommendation, not the default,
and it is worth naming which. And F47 is cited by number without a `path:line`;
`defects.md:1479` is the entry.

### S6 — §S4 discharges §3.2d for inter-word calls and leaves helper calls unaddressed

§S4 (lines 326–333) says the indirect-slot rule "*is* that indirection table",
so §3.2d is "met by a decision already taken".

`00-jit-feasibility.md:344-347` says: "route **runtime-helper** calls through an
indirection table so helper addresses are never a relocation-range problem".
Runtime helpers are not inter-word calls — they are the calls compiled code makes
into Bund2's own Rust (boxing, `Vm::push`, `Vm::report`, the sync in §S5's second
rule, the generic arms in §S5's first). §S4's slot rule is derived from D16 and
covers only targets a Bund program can name. Nothing in the RFC says helper calls
go through a table, and criterion 4 — "the module's relocation records contain
no entry targeting a function" — would *fail* on a design that emitted helpers as
direct relocations, which means criterion 4 and §S4 are currently stricter than
the RFC's prose. Say explicitly that helpers are slots too, and that criterion 4
covers them.

### S10 — D3's recorded status names a cache key D35 replaced

§S3 (line 240) says D3's "amended resolution rests on exactly this" — that
eval'd code cannot hit the cache. D3's status line
(`decisions.md:130-131`) reads:

> **RESOLVED — no eval-specific tier rule. Eligibility falls out of the
> **content-hash** compiled cache, bounded by that cache's cap.**

D35 chose **option 4, the `Rc` pointer**, and explicitly rejected content
hashing for now. D35's Consequences note the compatibility (`:1770-1773`), so the
conclusion survives — but D3's status still names a mechanism that does not
exist. RFC-0005 is the document that consumes both. It should say, in §S3, that
D3's conclusion holds under pointer keying and that D3's status text needs the
same one-line amendment D35 anticipated. Registers are append-only; amending a
status is permitted and is the point of this note.

sentence is at `00-jit-feasibility.md:257-258`, in **§2.1**, not §2.2. Both §2.2

### S12 — §S4's code quotation is not verbatim

## 4. Acceptance criteria — is each checkable, and by what

| # | checkable? | what actually decides it |
|---|---|---|
| 1 | **yes** | `cargo bench -p bund2-bench -- value/push_pull`, threshold 20 ns. Runs today. The withdrawal of its second half is the right call and is well argued. Number disagrees with the header — B2 |
| 2 | **not yet** | `cargo xtask conform` "with the `jit` feature on and off" — no stated route from xtask to a feature (B3). Threshold is exact equality, which is right |
| 3 | **yes** | `Rc::strong_count ≥ 1` while the entry lives, falls on eviction. Concrete, and a real improvement on "force an allocation at the same address". Note it tests D35's *mechanism*, not the false-hit *property* — which is fine, and worth the RFC saying so given S1 |
| 4 | **yes, and sharper than the prose** | "the module's relocation records contain no entry targeting a function". Executable against `cranelift-module`. See S6: as written it also forbids direct helper calls, which the prose does not |
| 5 | **yes** | register / promote / re-register / assert the result changes. Boolean |
| 6 | **yes** | four sub-tests, each with a number, plus the no-pinning assertion. The strongest criterion in the set. One gap: it tests the caps at *reduced* settings (4, 2, 8) and never that the shipped defaults (1024, 4, 4096) are the ones in force — a config regression would pass |
| 7 | **no — command does not run** | B4. The 5% band and its noise justification are sound; the `startup`/`value`/`dispatch`/`arith`/`corpus` groups all exist (`interpret.rs:66,109,140,196,228`). `lambda` (`:207`) and `rendering` (`:261`) are unassigned by the table — `lambda` is call overhead and is exactly what §S8 changes, so its omission is odd |
| 8 | **yes, and no longer vacuous** | `cargo xtask cite` covers `crates/` since F79 (`xtask/src/cite/mod.rs`). Verified green on RFC-0005 this session. `lint` is named but no invocation is given (`cargo xtask lint`) |
| 9 | **yes in form, not runnable** | lengths 1/4/16/64, 5% band, crossover recorded, and a stated consequence if nothing passes. This is the best-constructed criterion in the RFC. It needs B4's wiring |
| 10 | **yes in form, not runnable** | "below 1.2× on `1 2 + drop`" fails. Genuinely falsifiable, which the RFC says and means. Needs B4's wiring. It also needs a stated *which* body — "one compiled body" is not a fixture |

Missing criteria, given the design:

- **No criterion checks §S4's `autoadd` entry guard.** It is a named guard in the
  Preservation table and nothing tests it. The test exists: set `autoadd`, call a
  promoted word, assert the CALL is collected exactly as Tier 0 collects it.
- **No criterion checks B7** — that a compiled body does not grow the machine
  stack where Tier 0 does not.
- **No criterion checks §S9's pin mechanism.** §S9 specifies "ineligible for
  promotion, and demoted if already promoted" and nothing decides it.
- **No criterion checks D37 for the tier.** Compilation itself can fail —
  Cranelift returns errors, the module can be exhausted, a lowering can be
  unimplemented — and every one of those paths must fall back to Tier 0 rather
  than `unwrap`. `crates/bund2-jit/src/lib.rs` already denies the panic lints; a
  criterion should say the fallback is exercised, not merely that it compiles.

## 5. Preservation analysis — what the table does not enumerate

The nine rows present are accurate and each names a real guard. These are the
behaviours the design can change that no row covers:

1. **Machine-stack depth on recursion.** B7. The most serious omission: it
   converts a working program into an abort, and D37 forbids aborts.
2. **`unregister` against a live slot.** §S4 names `unregister` as a reason calls
   must be indirect, and then never says what a slot holds after it. If it holds
   the old pointer, a compiled caller calls an unregistered word — which Tier 0
   would report as an error. If it holds null, the check is a branch nothing
   specifies. Neither is stated; no row.
3. **`alias` retargeted after compilation.** §S4 concludes "a slot must name the
   *resolved* target, not the spelling" (line 276) — which is correct for the
   double resolution at `multistackvm_apply.rs:39-40` and
   `multistackvm_inline.rs:71-74`. But resolution is a run-time property: if
   `alias a b` is later replaced by `alias a c`, a slot keyed on the resolved
   name `b` is stale in exactly the way §S4 forbids for `register`. The
   Preservation row ("slots key on the resolved name") is the *cause* of this
   hazard, filed as its guard.
4. **The `$` bypass.** Step 4 of §S4's own chain: `$name` skips the lambda check
   *and* alias resolution. A compiled call site that resolved through the normal
   path and one spelled `$name` must reach different targets. §S4 lists step 4 as
   something a call site "cannot assume" and no row follows it.
5. **Diagnostic fidelity.** D36 requires a structured `Diagnostic` with a Bund
   source location and an optional stack snapshot; goldens capture error text.
   §S5 orders guards by RFC-0004's `StackEffect`, so a compiled body may detect a
   depth violation at *entry* where Tier 0 detects it mid-body — a different
   location, a different snapshot, possibly a different message. CLAUDE.md's own
   example of the right behaviour is the reference guarding depth *and* writing
   `SET returns: NO DATA #1` for the pull that follows. No row.
6. **The stack symbol on a synced value (D41).** After D41 a scalar carries an
   interned `StackSym` written by `push_as` (`crates/bund2-interp/src/lib.rs`).
   A value promoted into a Cranelift `Variable` never went through `push_as`; on
   the sync §S5 requires, it must acquire the symbol for whichever stack is
   *current at sync time* — and the current stack can change mid-body
   (`context`, `endcontext`, stack-switch words). The tag is observable: goldens
   capture `tags: {"stack": "main"}`, as §S1 line 127 and Q25 both say. This is a
   conformance-visible field that promotion routes around, and there is no row.
7. **Identity and `stamp` (D13, D20).** A promoted region that never materialises
   a `BundValue` never mints an identity. D20 enumerates materialisation points
   and D35's whole argument for pointer keying is that executing a lambda is not
   one. Promotion goes further: it can *elide* a value that Tier 0 would create.
   If a later materialisation point is reached, do the ids agree with Tier 0's?
   The RFC does not ask.
8. **Warnings and notices.** D36 makes `Warning`/`Notice` a one-line stderr
   emission through `Vm::report`. A promoted region that skips a word's slow path
   may skip its report. Not conformance-visible if goldens capture stdout only —
   but the RFC should say that is why, rather than not raise it.
9. **`Fold` at run time.** §S6 says D12's barrier "still has to be *represented*,
   because D16 means one may appear at run time" and §S5 says D12 "no longer
   kills the body it appears in". What a compiled body *does* on reaching a
   `*`-family word is never stated: promotion stops (like `Opaque`), or the guard
   declines (like `autoadd`)? The Preservation row says "represented not assumed"
   and represents nothing. `[carried — prior review S7]`
10. **Counter thrash under repeated `bund.eval`.** §S7 evicts the coldest entries
    at 4096. Every eval'd body has count 1, so all 4096 are equally cold and
    eviction has no signal. Combined with §S7's own `Weak`-keeps-the-address
    property, a loop calling `bund.eval` holds 4096 `RcBox` headers and 4096
    addresses out of circulation. Not a correctness bug; it is the REPL profile
    Q27 asks about, and §S7 says its caps are chosen for exactly that profile.
11. **Cranelift's own compilation failure.** See §4 above. A failed compile must
    leave the program running on Tier 0 with no observable difference. That is a
    preservation claim and it has no row.

## 7. What the RFC assumes and does not state

1. **That `jit` is not a default feature.** Criterion 2's "on and off" presumes
   an off. Nothing says which is which, and `bund2-runtime`'s manifest is where
   the answer lives.
2. **That the counter's `Weak` is over the same `Rc` the cache keys on** — the
   `Rc<Payload>` inside `BundValue::Heap`, per D35 option 4. §S7 says "the body's
   `Rc`" throughout. A `Weak<HeapValue>` and a `Weak<Payload>` have different
   lifetimes and only one of them keeps `Rc::as_ptr(&payload)` out of circulation.
3. **That runtime helper calls also go through the indirection table.** S6.
4. **That compiled code never reads the body.** This is what would make S1's
   objection to the cache's strong reference bite. If compiled code *does* hold a
   reference into the body — a literal pool, a span table for D36 diagnostics —
   the strong reference is justified and the RFC should say that instead.
5. **That the `autoadd` entry guard is cheap and correct to check once.** §S4
   says "an entry guard, not a mid-body one". `autoadd` is VM-wide and mutable
   (`autoadd.rs:12`, `:23`), and `:` and `;` are reachable by computed name
   through `!` — which the RFC states. So a compiled body containing an `!` can
   have `autoadd` toggled *inside* it. §S4 covers this by making `:`/`;` opaque
   sites, but opacity stops *promotion*, not execution, and the entry guard has
   already been passed. The unstated assumption is that an opaque site's runtime
   helpers re-check the flag.
6. **That `StackEffect` is available for every compiled body.** §S5 says
   "RFC-0004 orders the guards" via the declared or inferred effect. RFC-0004
   reports `Opaque` for 128 of 770 sites; an `Opaque` effect gives no arity, so
   the guard §S5 describes has nothing to order. What happens then is unstated.
7. **That a demoted body stays demoted across `unregister`/`register` of the same
   name.** §S7 says demotion is "permanent, per body" — and a re-registered body
   is a new `Rc`, hence a new body with a fresh count. So the recompile cap is
   evaded by any REPL loop that re-parses, which is every REPL loop. That may be
   fine (each redefinition orphans one function and the *compiled-function* cap
   still bounds it) but the recompile cap's stated purpose — "a word redefined in
   a REPL loop would otherwise orphan a function per redefinition" — is not
   achieved by a per-body cap. This deserves a paragraph.
8. **That benchmark medians in §S1 are reproducible.** No machine, no date, no
   saved Criterion baseline, no commit. §S1 is the section on which the RFC's
   status turns and it is the least reproducible section in the document.
9. **That `cargo xtask conform`'s 86 goldens exercise a promoted body at all.**
   Criterion 2 requires conform to read the same number with the tier on. If no
   golden runs a body 64 times, the criterion passes with the tier never engaged
   and proves nothing. The threshold of 64 makes this likely. State how conform
   forces promotion — a threshold override for the conformance run is the obvious
   answer and is not written down.
10. **That the AOT path shares this design.** `crates/bund2-jit/Cargo.toml:21-24`
    declares `aot` alongside `jit`, and its comment says "Build this before the
    JIT". RFC-0006 is named nowhere in RFC-0005 except through D10. Whether the
    indirect-slot rule, the caps and the guard-and-branch rule apply to a
    `cranelift-object` build — where there is no runtime to own a slot — is
    unaddressed.

## 8. Recommendation

**Revise before Proposed.**

The design is sound and better grounded than it was on 2026-09-08: the
resolution chain in §S4 is now followed all the way and reads correctly against
the reference; §S5's split between the type rule and the opacity rule is right
and RFC-0004 has been amended to match; §S7's `Weak`-versus-strong reasoning is
the best argument in the document; criteria 9 and 10 are genuinely falsifiable
and say so.

What blocks it is that the RFC's *status* — the claim that makes §S2–§S11 live —
rests on a §S1 whose diagnosis does not match the line it cites (B1), whose
headline contradicts its own body (B2), and whose ERRATA record still concludes
the opposite (B6). Those three are one problem seen from three sides, and they
are editorial rather than architectural: the measurements are real, D41 is real,
and the gate does pass on prerequisite 1.

The one substantive design gap is **B7** — non-tail compiled calls grow the
machine stack where RFC-0003's frame loop does not, which is a conformance
change and a D37 violation, with no row and no criterion. That needs an answer
before the design is complete, and Q28 makes it worse rather than better.

Everything in §2 is fixable in place. B3 and B4 are the ones that would otherwise
be discovered by the implementer on the first afternoon.
