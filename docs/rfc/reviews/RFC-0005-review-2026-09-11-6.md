## 1. Blocking

### B1 — `execute_value`'s LIST arm still files a tail request, and still loses one of two, through its MAP arm

**What the RFC claims.** Three places, all added or rewritten in the answer to
the fifteenth review:

- §S5, *A call may leave a body to run*, line 977: "When the fifteenth review
  found this, `execute_value`'s LIST arm reached it from `bund2-stdlib`.
  **F113's fix has that arm run a lambda item at once, as the reference does,
  so the case is an embedder's native again**, as F96 has it."
- Assumption 29, line 2313: "**A native that files two tail requests loses the
  first.** `Interp::request_tail` assigns. **No `bund2-stdlib` native does that
  now**: the one that did, `execute_value`'s LIST arm, runs a lambda item at
  once since F113."
- Criterion 26, line 3137: "F113 has that arm run a lambda at once, **so it no
  longer files**, and the case is an embedder's native again."

The Status line (line 144) says the same.

**What the code does.** The F113 guard tests the *item*, not what executing the
item reaches (`execute_value`, `crates/bund2-stdlib/src/values.rs`):

    if top.dt() == LAMBDA { vm.eval_lambda(&top)?; } else { execute_value(vm, top)?; }

A **MAP** item takes the `else`. The MAP arm of the same function pulls a key
off the stack and calls `execute_value(vm, inner)` on the value it finds. If
that value is a LAMBDA, it reaches the LAMBDA arm — which is still
`vm.tail_lambda(body); Ok(())`. So a list holding a dict whose key holds a
lambda files a request from inside the LIST loop, and the loop then keeps
going: a second such item files again and overwrites the first, and a
non-executable item after it fails with the request still set.

**Reproduced, both halves.** Two probes appended to
`crates/bund2-stdlib/src/host.rs` in a `git archive` copy of `HEAD`, built
under a separate `CARGO_TARGET_DIR`, values constructed through the public API
(`BundValue::map(…).set("k", BundValue::lambda([int(n)]))`,
`BundValue::list([…])`, `Interp::apply(BundValue::call("!"))`), with `"k"`
pushed once per MAP item:

| program | Bund2 at `cdac5d9` | the reference |
|---|---|---|
| `[ D(k→{10}) D(k→{20}) ] !` | `Ok`, stack `[20]` | `10` beneath `20` |
| `[ D(k→{10}) 5 ] !` | `Err("Received value is not of executable type")`, stack `[]` | the same error, with `10` left behind |

The reference's behaviour is the chain F113's own entry cites and I read this
session: the LIST loop pushes each item and recurses
(`reference/rust_multistackvm/src/stdlib/execute.rs:37-54`), the MAP arm pulls
a key, pushes the value it finds and recurses (`:55-83`), and the LAMBDA arm is
`return vm.lambda_eval(ptr_value)` — **at once** (`:93-95`). Every lambda a
list reaches runs, in order, synchronously, whichever arm reached it.

**Three consequences, and only the third is about the tier's design.**

1. **F113's disposition is wrong.** Its table row says `[ { 10 } { 20 } ] !`
   gave `20` where the reference gives `10` beneath `20`; the MAP form of the
   same row still does. Its "Status: FIXED 2026-09-11" and its closing "A
   consequence for F96" paragraph both overstate what the one-line guard
   reaches. So does F96's second dated note of 2026-09-11, which says "no
   `bund2-stdlib` native files a tail request and then fails."

2. **Assumption 29 is false as stated.** It is stated as a property of shipped
   code, not of the corpus. The precedent is F94: `drop_stack` declared `1 -> 0`
   while emptying the stack and no program called it, and the RFC built
   criterion 28 precisely because corpus reach is not the standard. The same
   standard applies here. I could not build `List([MAP, …])` from Bund source
   with the words registered today — `push` converts both operands through
   `conv(LIST)`, so a MAP cannot become an element (`push_base`,
   `crates/bund2-stdlib/src/singles.rs`), and `[ … ]` does not evaluate its
   items (assumption 28, re-checked 2026-09-11) — but the arm is
   `bund2-stdlib`'s, it is reachable through the `Vm` trait, and the first word
   that returns a list of dicts makes it reachable from source without touching
   `values.rs`.

3. **The design rule is unaffected, and this strengthens it.** "`status_of`
   clears the request cell whenever it answers an error" already covers a
   `bund2-stdlib` native as well as an embedder's, and it is the right rule
   either way. What changes is the evidence the RFC offers for it: criterion 26
   demoted its only real program to a synthetic embedder native
   (`a_failed_native_leaves_no_tail_request`) on the strength of a fix that is
   not finished. A criterion whose only case is a native the test registers for
   itself is weaker than one with a shipped word behind it.

**Two ways out, and the choice is the owner's.**

- **Finish F113.** Make the LIST arm run *whatever the item executes to* at
  once — the reference's shape is recursion into a function whose LAMBDA arm
  calls `lambda_eval`, not a `dt()` test at the loop. Then all three sentences
  become true, and criterion 26 keeps its embedder-native case. This is a Tier 0
  fix against the oracle, and it should carry the two rows above as its
  evidence.
- **Reopen F113 and correct the three sentences and assumption 29**, keeping the
  `bund2-stdlib` case live and giving criterion 26 back a real program:
  `?try` over `[ D(k→{10}) 5 ] !`, which under the adapter would run `{ 10 }`
  inside `?try`'s handler and under Tier 0 does not.

Either way, F96's and F113's register entries need the correction, since both
now assert the same false thing.

## 2. Significant

### S1 — §S8 says the scan finds 21 re-entering functions, then names 19

Lines 2069–2077 introduce the derived set with "On 2026-09-11 the scan finds
21:" and enumerate it in three bullets. Counting what the bullets name: seven
loop words, four conditional runners, two method paths, `conditional_move`,
`context`, `eval_source`, `execute_value`, `apply` and `text` — **19**.

The set the test holds is 21 (`REENTERING`, `crates/bund2-stdlib/src/lib.rs`;
`every_reentering_function_is_named` passes). The two the prose omits are
`data.rs: run_csv` and `data.rs: run_sqlite`, both of which reach
`vm.eval_lambda` (`crates/bund2-stdlib/src/data.rs`).

This matters beyond bookkeeping. Criterion 11 must "report `c_p` and `δ_p` for
each", and `m ≥ 8 MiB × max_p(δ_p / c_p)` is a maximum over the whole set. A
reader building that measurement from §S8's prose measures 19 paths. The RFC is
right that the set is derived rather than listed — that is what keeps it from
going stale — but the prose beside it is what an implementer reads, and it is
two short on the day it was written.

### S2 — §S8 groups `execute_value` under `Vm::apply`; since F113 it also re-enters through `Vm::eval_lambda`

Line 2076 puts `execute_value` in the `Vm::apply` bullet, and lines 2079–2081
say "`eval_source` and `execute_value` are paths of their own. Each adds its own
frame … to `Vm::apply`'s, so their `c_p` is not `Vm::apply`'s alone."

F113 added `vm.eval_lambda(&top)?` to the LIST arm (`execute_value`,
`crates/bund2-stdlib/src/values.rs`). `execute_value` now re-enters evaluation
two different ways, with two different per-level costs, and the LIST arm
recurses into itself for a nested list — so a level of `[[[…]]] !` is Rust
recursion in `execute_value` with **no floor check between two frames**, where a
level of `[ {…} ] !` is an `eval_lambda` that does check. The path's `c_p` is
not one number.

F113's register entry notices the frame cost ("That spends a Rust frame per
lambda inside a list, bounded by the Tier 0 floor"); §S8 has not absorbed it.

### S3 — assumption 28 enumerates `execute_value`'s arms and omits the one B1 turns on

Assumption 28 reads: "`[ 1 2 + ]` keeps `+` as a CALL value (run 2026-09-11), so
`execute_value`'s arms that do Rust work before re-entering evaluation — CLASS,
OBJECT, CONDITIONAL — are not reachable from a literal."

`execute_value` has a **MAP** arm too, and a **LIST** arm, and the MAP arm is
the one that still files a tail request (B1). The assumption's conclusion about
literals happens to hold for MAP as well, but the enumeration is what a later
reader will trust when asking "which arms matter?", and it is the second place
in the document where `execute_value`'s arms are listed incompletely. The first
is S2's.

### S4 — `execute.rs:93-95` is a citation `cite` cannot see, and it is ambiguous

Line 2316, added in the answer to the fifteenth review:

> runs a lambda item at once, as the reference does (`execute.rs:93-95`).

`cargo xtask cite` matches a citation only when it begins with one of
`reference/`, `crates/`, `xtask/`, `docs/`, `tests/golden/` or `tests/probes/`
(`CITE_PREFIXES`, `xtask/src/cite/mod.rs`). A bare filename starts no citation
at all, so this one is neither resolved nor corroborated — it is invisible, and
criterion 8's own words apply: "A citation `cite` cannot see is one it cannot
fail."

It is also ambiguous: two files named `execute.rs` exist under `reference/`
(`reference/rust_multistackvm/src/stdlib/execute.rs` and
`reference/Bund/src/stdlib/functions/internaldb/execute.rs`). The intended one
resolves and says what the prose says — I opened it — but nothing in the
document or the tooling says which.

This is the exact failure §S4's parenthetical records ("thirteen citations the
tool could not check") and criterion 8 carries forward, reintroduced one
revision after it was last corrected. The same line inside `values.rs` spells
the path in full; the RFC does not.

## 3. Minor

- **§S8, line 2007:** "Tier 0's part is `EVAL_STACK`'s 8 MiB
  (`crates/bund2-cli/src/main.rs`)." `EVAL_STACK` is `8 * 1024 * 1024 +
  bund2_interp::STACK_RESERVE`. The document gets this right two paragraphs
  later ("spawns its evaluation thread at 8 MiB plus the 256 KiB reserve"); this

  (`crates/bund2-ir/Cargo.toml`, `crates/bund2-interp/Cargo.toml`), so the
  claim holds — but naming the feature would let a reader check it.
- **Criterion 29** asserts a panicking native gives "`Error::internal` naming

  their body returns, including that one (`object_execute_base`,
  `crates/bund2-stdlib/src/oop.rs`). Both tiers agree, so nothing diverges, but
  the criterion's program must not route the panicking native through a native
  that discards, or it passes without exercising the adapter.

## 4. What the RFC assumes and does not state

Five, beyond the twenty-nine it lists.

1. **That a native re-entering evaluation does not recurse in Rust *between*
   two floor checks.** Assumption 4 scopes its claim to "a leaf native";
   `execute_value` is not a leaf, and its LIST and MAP arms recurse into
   `execute_value` on the depth of the value, with `stack_ok()` consulted only
   when an arm reaches `Vm::apply` or `Vm::eval_lambda`. A list nested `n` deep
   spends `n` Rust frames before any floor is asked. The reserve carries them.
   §S8 should say so, or assumption 4 should drop "leaf".
2. **That the entry trampoline needs no `status_of`.** §S5 lists four helpers
   that make their status through one function and treats the entry separately
   ("refuses to start a body once an exit is recorded"). The unstated premise is
   that the entry only converts a *body's* status, never makes one of its own,
   so there is nothing for `status_of` to substitute. If a later entry path
   grows a step after the body returns, the twelfth review's B1 returns at the
   entry.
3. **That `#` and `#.` discarding an error is the whole of the "discards"
   family.** Assumption 25 names them as the `Ok` path; it does not say the
   scan or audit that would catch a third. `let _ =` around a re-entering call
   is the spelling, and nothing looks for it.
4. **That the request-cell mirror can only be written by `request_tail` and
   `take_pending`.** §S6's *Addressing* says it is; nothing enforces it, and a
   future assignment to `pending_tail` that bypassed both would desynchronise
   compiled code from Tier 0 silently. `Interp::request_tail` is the only
   writer today (checked).
5. **That a list literal is the only way a program builds a LIST, so
   assumption 28's conclusion covers every list `!` can be handed.** B1 is what
   happens when it does not.

## 5. Preservation analysis

The table is thorough and I found no risk in the design it fails to name. Two
observations rather than gaps:

- The row "**a stale tail request** left by a native that failed after filing
  it" is **correct as written** — it names the adapter, `status_of` and the
  refused drain. Only the prose around it (B1) misstates who can trigger it.
  The row needs no change; the sentences do.
- No row names a **native that discards the error its body returned** (`#`,
  `#.`). It is covered obliquely by assumption 25 and 26 — the `Ok` path — but a
  reader scanning the table for "what a callee can do to a compiled body" will
  not find it, and it is the one shape where the two tiers make the same
  refusal from different places.
