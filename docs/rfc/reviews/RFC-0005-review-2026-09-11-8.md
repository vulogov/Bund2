## B1 — §S4's `$name` slot rule contradicts RFC-0002, which is Accepted, and would move conformance

§S4, line 556:

> A slot keyed on "the resolved target" therefore needs to say which
> resolution, and a compiled `$name` call must key on the **one-level answer**.

and the Preservation table, line 2544:

> slots key on the resolved name (§S4), **except for `$`**, which is resolved
> one level shallower and keys on that one-level answer.

**The premise about the reference is correct.** I confirmed it on the oracle,
with a chain that ends at a real inline word rather than at another alias
(`dup` is itself an alias in the reference, F24, so a chain ending there proves
nothing):

    "dup_one" :b alias
    "b" :a alias
    1 a            # oracle: two values — a → b → dup_one, two resolutions
    1 "$a" ptr !   # oracle: error — $a resolves one link to b, which is not
                   #   an inline word

built out-of-tree at `target/oracle`, 2026-09-11.

**The premise about Bund2 is false, and the RFC never states it.**
`Registry::follow` walks the alias chain to a fixed point and `Registry::resolve`
calls it for both spellings — the sigil selects only whether `lambda` is
consulted (`crates/bund2-api/src/lib.rs`, `follow` and `resolve`). The same two
programs under `./target/release/bund2`: **both leave two values.** Bund2's
`$a` reaches `dup_one` through two links.

That is not a Bund2 defect. It is a **deliberate, accepted deviation**:

- RFC-0002 (**Accepted** 2026-09-04), *Alias resolution*: "Resolved once, at
  the point of dispatch, following `Alias(Symbol)` links… See Preservation
  analysis for the one case where 'twice' and 'to a fixed point' differ."
- RFC-0002's Preservation row: "Alias resolved twice, and once under `$` —
  **Deliberately changed, and the divergence starts at two links, not three.**"
- RFC-0002 criterion **6a**: "A two-deep alias chain resolves the same way
  through `$name` as through `name`… This is the deviation the preservation
  table records, and it is asserted rather than left implicit."
- `docs/registers/defects.md`, F26's consequence paragraph, records the same
  thing.

So a compiled `$name` call keyed on "the one-level answer" would reach `b`
where Tier 0 reaches `dup_one`. That is a **meaning** difference between the
tiers, which §S2 forbids outright and criterion 2 measures. It would also
un-meet RFC-0002's accepted criterion 6a under `--features jit` — the exact
shape §S8 names as this RFC's most serious historical defect ("it silently
un-meets an accepted criterion of another RFC").

This is CLAUDE.md's recurring failure in its second form: the RFC grounded a
claim in `reference/` and did not check what Bund2 does one step further. It is
also the register failure — RFC-0002's deviation is directly about this RFC's
subject and declares no `Blocks:` line.

**What has to change is one sentence and one Preservation row**, not the
design: slots key on the fixed point for every spelling, because that is what
Tier 0 does, and §S4's paragraph should record the reference's one-level
behaviour as RFC-0002's approved deviation rather than as a rule Tier 1 must
reproduce. If the owner instead wants Tier 1 to be faithful to the reference
here, that is a change to Tier 0 and to RFC-0002's criterion 6a, and it belongs
in `docs/registers/decisions.md` before either is edited.

## B2 — assumption 36 is no longer "unmeasured": rendering a deep value aborts the process

Assumption 36:

> **`debug.display_stack` and `--raw-values` render a deep value without a
> bound.** A report's values go through `BundValue::summary`, which is bounded
> by design (D36), and these two do not. 20,000 levels rendered here, so this
> is **unmeasured rather than known false**.

It is now known false. Measured 2026-09-11, release binary, the same shape
F114 and F115 were filed for:

    list
    30000 { drop list push } times
    "built" println
    debug.display_stack
    "rendered" println

prints `built` and then

    thread 'bund2' has overflowed its stack
    fatal runtime error: stack overflow, aborting

exit **134**. Bisected: 20,000 exits 0, **24,000 aborts**, 26,000 aborts. The
recursion is `BundValue::render_into` / `render_payload`
(`crates/bund2-value/src/lib.rs`), which descend per level with no bound;
`summary` is bounded at `MAX_DEPTH = 2` (`crates/bund2-value/src/lib.rs`,
`summarise`), which is why D36's path is safe and this one is not.

This is a D37 violation of exactly the class F114, F115 and F116 were each
filed and fixed for, on a path the RFC names and then leaves standing on an
explicit "unmeasured". `debug.display_stack` is on the conformance path —
criterion 14 says so, because the golden capture epilogue calls it — so this is
not a corner an embedder alone can reach.

It needs a defect entry and a disposition, as F114–F116 got. The RFC's own
assumption 30 states the general rule that now applies to it: "a new one must
not recurse on data a program controls." Until it is filed, assumption 36
asserts a property the binary contradicts.

## Significant

### S1 — F116's status is given three different ways in one document

`docs/registers/defects.md` records F116 as **FIXED 2026-09-11**
(`crates/bund2-syntax/src/lib.rs`, `MAX_NESTING = 1024`), and the fix is in the
tree at `67c687a` with two tests passing. The RFC says:

- Status line 186–189: "and F116, parsing a deep run-time string, **which
  stays open**. Assumptions 34 and 35 record both." — stale;
- Preservation table, line 2587: "nothing in this design: the floor
  `eval_source` checks comes after the parse (**F116, OPEN**; assumption 34)"
  — stale, and the guard column is now wrong on the substance as well: the
  guard is `MAX_NESTING`, refused before the frame is spent;
- assumption 34: states the fix correctly ✓.

A Preservation row whose guard reads "nothing in this design" for a risk that
has since been closed understates the design and overstates the risk; the
register is the authority and two of the three places disagree with it.

### S2 — assumption 35's list of "walks that still recurse on depth" is wrong on two of its three members

Assumption 35 closes with:

> Other walks over a value's members — `render`, `PartialEq`, `Hash`, the wire
> format — still recurse on depth, and assumption 36 covers the rendering half.

Opened in this session (`crates/bund2-value/src/lib.rs`):

- `impl PartialEq for BundValue` (line 1276) — a container compares by
  `a.identity() == b.identity()`. It descends **one** level, into a
  `Payload::Scalar`, and never into a list's members. It does not recurse on
  depth.
- `impl Hash for BundValue` (line 1318) — "mirrors `PartialEq` arm for arm";
  a container hashes `h.identity()`. Same answer.
- **the wire format** — the crate's header names "the bincode wire format
  (D4)"; there is no `Serialize`, no `to_wire`, no encoder in `bund2-value` or
  `bund2-stdlib` today. It names something that does not exist to recurse.
- `render` — real, and B2 above shows it aborts.

So one of four is true, and it is the one assumption 36 already carries. This
is a claim about existing behaviour with no citation, which CLAUDE.md requires
be grounded; here the grounding falsifies three-quarters of it. The direction
of the error is safe, but it misdirects the next reader to audit two paths that
are already flat and to leave the one that aborts as the "covered" half.

### S3 — §S8's derived re-entry set and §S5's request-filer list both name a function that is no longer on the path

§S8 line 2138 puts **`execute_reached`** in the set of 21 re-entering paths,
and line 2145 says "**`execute_reached` has two costs, not one**". §S5's
request-filer list names **`execute_value`** for `!` on a lambda.

Since F114, neither calls `Vm::apply`, `Vm::eval_lambda` or `Vm::scoped_call`.
`execute_value` delegates in one line; `execute_reached` runs the worklist and
the push/pull tag write; **`execute_one`** holds every arm, and so holds both
re-entries and the `tail_lambda` (`crates/bund2-stdlib/src/values.rs`). The
derived set agrees with the code and not with the prose — `REENTERING` reads
`"values.rs: execute_one"`, with a comment saying so.

The RFC's own reason for deriving the set was that "a list went stale within a
day". The list is derived; the *prose* that reads it is not, and it has gone
stale again. Two consequences beyond the name:

- criterion 11 reports `c_p` per path. On this path a re-entry now costs
  `execute_reached`'s frame **plus** `execute_one`'s, not one frame. §S8 says
  "Each adds its own frame" for `eval_source` and `execute_reached`; for this
  path it is two, and the larger `c_p` is the one `m` is set from.
- §S5's "`!` on a lambda (`execute_value`, …)" is now only true through
  delegation, and only for `Reach::Top`. The distinction is load-bearing —
  assumption 29 and criterion 26 both turn on it — so the file-plus-symbol
  citation should name the function that does it.

### S4 — assumption 33 states a derived property without stating what the derivation cannot see

Every sibling scan in this RFC states its own blind spots: criterion 25 says
"the scan checks spellings, and knows it"; §S8 lists three things the re-entry
scan cannot see; assumptions 24 and 27 carry two of them. Assumption 33 states
none, although `every_writer_of_the_request_cell_is_named`
(`crates/bund2-interp/src/lib.rs`) has the same three shapes of gap, read from
the test:

- **One file.** It reads `crates/bund2-interp/src/lib.rs` only. `pending_tail`
  is a private field of `Interp`, and `bund2-interp` has a second module,
  `frag.rs`, which as a descendant module may write it. A fifth writer added
  there passes the test.
- **Cut at the first `#[cfg(test)]`.** Shipped code after an inline test module
  goes unscanned — assumption 27 states exactly this for the `bund2-stdlib`
  scan and nothing states it here.
- **Two spellings.** It matches `pending_tail =` and `pending_tail.take()`.
  `self.pending_tail.replace(v)`, `.get_or_insert_with(…)`,
  `std::mem::swap(&mut self.pending_tail, …)`, or a `&mut` to the field handed
  to a helper are all writes it does not see.

The property the assumption exists to hold — that Tier 1's mirror cell cannot
fall behind `pending_tail` "with nothing to notice" — is exactly the kind that
fails silently, and the seventeenth review's B1 was that this assumption could
not catch what it was added for. It can now; the RFC should say how far.

1. **Criterion 1's second figure is unverified here.** "re-run at **9.47 ns**
   on 2026-09-11, after F115 put a `Drop` impl on `HeapValue`" — the bench
   crate is not under version control (§S1 says so), so nothing in the tree
   records the run. Same for §S6's *Measured* tables and criterion 10's spike
   numbers, although the spike itself checks out: `spike/lowering-1` exists and
   `3138d3c` is "Spike: a throwaway lowering for RFC-0005 criterion 10", whose
   message carries the same three figures the RFC quotes.
2. **`MAX_NESTING`'s "512× the deepest nesting anywhere in the corpus"**
   (assumption 34) rests on a measurement recorded only in F116's table
   (deepest = 2). §S6's *Where promotion stops* sets the standard for this —
   "a count with no derivation beside it rots" — and this one has no command.
3. **The six `cranelift-codegen` citations are invisible to `cite`**, since the
   crate is not in the tree. I opened all six in
   `~/.cargo/registry/…/cranelift-codegen-0.135.0` and every one says what the
   RFC claims: `supports_tail_calls` is true for `Tail` alone
   (`src/isa/call_conv.rs:88-93`); `typecheck_tail_call` requires a matching
   calling convention and matching return types and says nothing about
   parameters (`src/verifier/mod.rs:1710-1735`); `gen_stack_lower_bound_trap`
   emits a compare and a `TrapIf` with `TrapCode::STACK_OVERFLOW` on all four
   ISAs, against the stack pointer from below; `generate_gv`
   (`src/machinst/abi.rs:1428`) is where the limit comes from; and
   `get_stack_pointer` is lowered in x64, aarch64, s390x and riscv64's
   `lower.isle` plus riscv64's `inst.isle`. Criterion 8 already says a citation
   `cite` cannot see is one it cannot fail; these are seven more of them, and
   they are the load-bearing ones for §S8.
4. **`CallConv` "has no Rust ABI"** is right but is stated as though the enum
   were checked for a `Rust` variant. What the file shows is `Fast`, documented
   "Best performance, **not ABI-stable**" — which is the stronger reason, and
   the one a reader should be given.

## What the RFC assumes and does not state

- **That Bund2's Tier 0 resolves aliases the way the reference does.** It does
  not, by RFC-0002's decision. B1.
- **That `render`, unlike `Drop` and the parser and `execute_reached`, is far
  enough from a program's reach not to need a bound.** It is not: 24,000
  levels through `debug.display_stack` aborts. B2.
- **That the re-entry and request-cell scans see every shipped file of their
  crate.** Both cut at the first inline test module and the request-cell scan
  reads one file of two. S4, and assumption 27 for the other half.
- **That a two-frame re-entry path is one frame for `c_p`.** S3.
- **That `bund2-jit`'s `status_of` and drain helper, which live outside
  `bund2-interp`, will keep the mirror cell and `pending_tail` in step through
  `Vm::clear_tail_request` alone.** D56 gives them the door; nothing derives
  that they walk through it, and no scan can, because the crate does not exist.
  That is fair for a design not yet built, but it is the one half of assumption
  33 that no test will ever cover, and the assumption reads as though the
  scan covered the whole property.

## Preservation analysis — completeness

The table is 47 rows and covers, as far as I can find, every behaviour the
design can change. Two gaps, both from the findings above:

- the F116 row is stale (S1) and should read as a closed risk with `MAX_NESTING`
  as its guard;
- there is no row for **a deep value rendered by a word on the conformance
  path**. The teardown row exists because F115 was measured; its sibling has
  now been measured too (B2) and has no row.

One row I checked especially, because it is where B1 lands: "a slot naming a
spelling rather than the resolved target, when `i` resolves aliases twice". Its
guard is the sentence B1 contradicts. Rewriting it is part of B1's answer.
