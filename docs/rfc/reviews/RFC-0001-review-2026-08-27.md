## B. Blocking findings

### B1. The two-bucket classification is false for `attr_add`, and the oracle says so

§"One policy…" states:

> - **Minting mutations** — `set`, `push`, `attr_add` — rebuild the header. The
>   result gets a fresh identity and an empty `attr`/`curr`/`tags`, per F34.

`attr_add` does not rebuild the header. It is
`self.dup().expect(…).regen_id()` followed by `res.attr.push(value)`
(`reference/rust_dynamic/src/attr.rs:19-21`), and `dup` is
`to_binary`/`from_binary` over the whole struct
(`reference/rust_dynamic/src/bincode.rs:30`), so `attr`, `tags`, `curr` and
`q` all survive verbatim. F34 never claimed otherwise — it is about `set` on a
container rebuilding through `from_dict`/`from_list`/`from_valuemap`
(`docs/registers/defects.md:907-926`), and `attr_add` reaches none of them.

Confirmed against the oracle this pass:

```
1 2 attribute 3 attribute
debug.display_stack
```

renders

```
Value { … dt: 2, q: 100.0, data: I64(1),
        attr: [Value { … I64(2) … }, Value { … I64(3) … }],
        curr: -1, tags: {"stack": "main"} }
```

Two entries in `attr`, and `tags` still populated. If `attr_add` emptied the
header, the second `attribute` would have discarded the first — and the
rendering the RFC itself cites two sections earlier (`1 2 attribute` giving a
populated `attr`) would be the *only* thing `attribute` could ever produce.

This is the same shape as the contradiction review 5 closed (`set` classified
as both a split and a rebuild): the buckets are stated as a partition, and one
member is in the wrong one. `attr_add` mints *and* preserves the header — a
third case the two-bucket rule has no room for.

`regen_id` also **resets `stamp`** (`reference/rust_dynamic/src/id.rs:7`),
which neither bucket mentions. See B4.

### B2. `set_tag` is not the only reachable minting-free mutation, and the RFC says so itself

§"One policy…" and §"Value semantics" both assert:

> **Minting-free mutations** — `set_tag` alone, among the reachable ones — …

> Mutations that mint nothing, of which `set_tag` is the only one reachable, …

An exhaustive scan of in-place `self.<field> =` writes across `rust_dynamic`
returns three, not one:

- `reference/rust_dynamic/src/tags.rs:5` — `set_tag`.
- `reference/rust_dynamic/src/iter.rs:11,27,37,53,63,86,93,96` — `next`
  writing `curr`. The RFC knows this (§"`curr` is the iteration cursor"
  documents the six `for … in` callers) and handles it by moving the cursor
  out of the shared header — but then does not remove `curr` from the
  minting-free set, or reconcile with §"The heap object", which says the
  opposite: "`Iterator::next` takes `&mut self` …, so `curr` is reached
  through `make_mut` and splits with it."
- `reference/rust_dynamic/src/q.rs:5,9` — `calc_q` and `set_q`. **The RFC
  establishes their reachability four pages earlier**: "both are reached from
  the arithmetic operators — `impl Add` … calls `set_q` on the result
  (`reference/rust_dynamic/src/math.rs:416-420`) … So every arithmetic
  operation writes `q`." Verified: `math.rs:416` computes the average and
  `:419` is `return res.set_q(q).clone();`.

There is at least a fourth outside `rust_dynamic`:
`reference/Bund/src/stdlib/functions/values/merge.rs:83` is
`op_val1.dt = o_type;` — an in-place `dt` write on a value pulled from the
stack, minting nothing. It only escapes being a split when the preceding loop
(`:79-82`) has rebuilt `op_val1`, which it does not for an empty map.

The likely repair for `set_q` is "it only ever writes a freshly constructed
result, so the receiver is never shared" — but that is an argument the RFC has
to make, not one a reader should have to reconstruct. As written, the policy
declares a singleton and the document contains three counterexamples, one of
them on the arithmetic path.

The scan scope also is not stated. F39 records that habit costing this RFC
four false negatives; the singleton claim is exactly the kind that needs its
search scope written down.

### B3. `Payload::ValueMap` is a `BTreeMap`, so D30's mechanism has no consumer

`Payload` declares `ValueMap(BTreeMap<BundValue, BundValue>)`, justified by
F15. Two problems.

**F15 did not ask for this.** Its disposition is "Bund2 uses a deterministic
map for **dict members and tags**, so printing is stable"
(`docs/registers/defects.md:209-210`), and its two rendering surfaces are the
dict display form and the `Debug` of a `Val::Map`
(`:225-233`). `Val::ValueMap` is not named, and F29 says it has no read path
to render through anyway.

**It contradicts D30.** D30 decides *hash by content*, and states the
mechanism explicitly: "This is what makes `valuemap "k" 42 set "k" get`
return `42`: the fresh `"k"` **hashes into the same bucket**"
(`docs/registers/decisions.md:1190-1191`). A `BTreeMap` does not hash. So:

- §"Hashing mirrors equality (D30)", its `-0.0`/`NaN` rules, and criteria D6
  and D8's hashing clauses describe a `Hash` impl that nothing in the design
  calls.
- The structure the RFC actually chose needs a **total `Ord` on `BundValue`**,
  and the RFC never defines one. Worse, it removes the reference's: F12's
  disposition is FIX, and the preservation row "Ordering falling back to
  `id.cmp` — **Deliberately fixed**" deletes the only total order
  `rust_dynamic` has.
- The order must be consistent with the equality the RFC specifies, and the
  RFC's own float rules make that impossible: `Float(f64)` is not `Ord`, and
  "`NaN` is never equal to anything, including itself" is incompatible with a
  total order, which requires reflexivity. A `NaN` key in a `HashMap` is
  merely unfindable — which is what §"Hashing" describes and accepts. In a
  `BTreeMap` it corrupts the tree's invariant.
- D30's stated win — "a scalar-keyed lookup mints nothing" — survives, but the
  composite-key cost changes character and is not restated: a tree descent
  compares against O(log n) stored keys, materialising an identity at each,
  where a hash lookup materialises one.

Either `ValueMap` keeps a hash map and F15's citation is dropped from that
line, or the RFC takes the `BTreeMap` and must define `Ord`, say what it does
with `NaN`, record the departure from D30's mechanism, and rewrite §"Hashing"
and criteria D6/D8 accordingly. Silently substituting an ordering contract for
the hashing contract an accepted decision names is the thing CLAUDE.md's
register rule exists to prevent.

### B4. The header-rebuild rule omits `q` and `stamp`, and `q` is now a field

Review 5 made `q` a field. The rebuild rule was not updated for it.

`from_list` (`reference/rust_dynamic/src/create_list.rs:19-28`), `from_dict`
(`create_map.rs:31-41`) and `from_valuemap` (`:43-51`) all write
**`q: 100.0`** alongside `attr: Vec::new()`, `curr: -1`,
`tags: HashMap::new()`. So a container mutation resets `q` to the fixpoint —
and the *fallback* arms of the same words do the opposite, explicitly copying
it: `res.q = self.q` at `set.rs:33,60,93` and `push.rs:164`.

With `q` a carried field and `Value::none` starting at `0.0`, that is a live
divergence: a container whose `q` has been driven off 100.0, mutated, must
come back at 100.0 — while a scalar `set` must carry the receiver's `q` onto
the *pushed value*. Neither is stated. §"Mutation resets the header" lists
only `attr`, `curr` and `tags`, and the preservation row repeats the same
three.

`stamp` has the same gap on the other side: the rebuilding constructors write
`timestamp_ms()` and the RFC has a row for that, but `regen_id`
(`id.rs:6-7`) resets `stamp` too, and `attr_add` reaches it — so the
minting-mutation bucket resets a stamp it does not mention while preserving an
`attr` it claims to clear.

### B5. Boxed scalars have an identity slot, so two arguments that rest on "scalars have no identity" no longer hold

The boxed form arrived in review 3. Two places written before it still argue
from the pre-boxing structure:

- Preservation row: "Equality by identity for `Bool`, `Nodata`, `None` —
  **Deliberately changed** — *scalars have no identity to compare*."
- Criterion D2: "**Not for a bool**: *scalars carry no identity*, so
  `true == true.dup()` is true in Bund2 and false in the reference."

But §"Scalars have no header at all" establishes that any scalar reaching a
stack **is** `Heap(Rc<HeapValue>)` with a full header — identity slot
included — because `TS::push` tags unconditionally. So a bool that a Bund
program can put its hands on always has an identity to compare. Content
equality for scalars is now a **choice**, not a structural consequence, and
`true == true.dup()` is true only because the design elects to read content
through both forms.

That does not make the deviation wrong — the reachability argument
(`logic_compare_fun.rs:67-69`, no `BOOL` arm) still carries it. It makes the
stated *reason* false, in the same way review 3's "the scalar repair had been
applied to one field of six" was false. The row and the criterion need the
reachability argument, not the no-slot one.

There is a live consequence, not just a wording one: because a boxed scalar
has an identity, `dup` on it clears that slot (§"`dup` is an identity reset")
— so the design has a scalar that carries an identity, a `dup` that resets it,
and an equality that refuses to read it. Nothing says which of the three is
load-bearing if a later RFC gives scalars an identity reader.

### B6. `.id` and `.timestamp` on an unadorned scalar are unstable, and unadorned scalars are reachable

§"Scalars have no header" closes with: "equality, ordering and hashing read
through both forms identically, so boxing is invisible to the language." Those
are three of the five readers D1 names. The other two are `.id` and
serialisation, and `.timestamp` is D2's.

`.id` is `Value::from_string(value.id)` off a `peek()`
(`reference/Bund/src/stdlib/functions/oop/base_classes.rs:12-16`), and
`.timestamp` the same at `:20-25`. For a heap value under this design both are
stable: `peek` clones the `BundValue`, the clone is an `Rc` bump, the `Cell`
is shared, and a second call sees the minted value. **For an unadorned scalar
there is no shared cell** — observing it produces a box that is discarded
when the observation ends, so a second observation mints a different id and
samples a different stamp. The reference's ids and stamps are stored, so both
calls return the same string.

The RFC's boxing trigger list — "an observed identity, a stamp, a tag, an
attribute, a moved cursor" — makes "an observed identity" a trigger without
saying where the resulting box is written back to. For a value held inside a
container there is nowhere: `get` hands out a copy.

Unadorned scalars are reachable. Oracle probe this pass:

```
"[1,2]" json json.to_value
debug.display_stack
```

renders the two elements as `data: I64(1) … attr: [], curr: -1, tags: {}` and
`I64(2)` likewise — no tag, no attribute, no cursor, and yet each carries a
stable `id` and `stamp`. Under this design both are `Int(_)` with no header.
So `l 0 get .id  l 0 get .id` returns the same string on the oracle and two
different ones in Bund2.

The goldens cannot catch this (F14 normalises `id` and `stamp` away), which is
precisely why it needs to be a preservation row rather than a discovery.

### B7. `dup`'s handling of `stamp`, `tags`, `attr` and `curr` is unspecified

§"`dup` is an identity reset" specifies exactly one field: "`dup` allocates a
fresh `HeapValue` with a **cleared** identity slot, sharing the payload by
`Rc`". The reference's `dup` is a whole-struct bincode round trip that mints
only the id, so `stamp`, `tags`, `attr`, `curr` and `q` all survive unchanged
— and the layout row `D: dup a list  4  649` is only meaningful if the fresh
header copies `tags` and `attr` by value, which is what makes it four
allocations rather than one.

The gap bites hardest on `stamp`. The D13 rule — "a CoW split materialises the
identity before it copies … `stamp` follows the same rule" — is stated for
`make_mut`. `dup` is not a `make_mut` split; it is an explicit header
construction, and the rule is not applied to it. Under the naive reading, an
unobserved value and its `dup` each carry an unminted `stamp` cell and sample
independently on first observation — **different** stamps, where the reference
guarantees the same one. That is a second D2 deviation, distinct from the one
the RFC does state, and it is observable through `.timestamp` in a way the
stated one is not.

F34 exists because header handling on mutation was left implicit. `dup` is now
in the same position.

### B8. Three sections still assert what reviews 4 and 5 corrected

`cargo xtask lint` passes, and this is the shape it cannot see: a corrected
claim that survives elsewhere in the same document.

- §"Iteration" (line 665): "`impl Iterator for Value` has no caller in the
  reference, so `curr` never advances in a running Bund." §"`curr` is the
  iteration cursor" says the opposite, with six citations: "**It has six
  callers**, and two earlier drafts said it had none."
- Preservation row `curr`: "**Preserved as a field.** *Nothing advances it
  today*; RFC-0003 decides whether Bund2's iteration does." Same stale claim,
  and it also leaves the RFC's own decision — that Bund2 iterates on a local
  cursor — recorded nowhere in the table.
- §"Rendering" (line 673): "`q` is rendered as the constant `100.0` rather
  than carried." Review 5 established `q` is a field averaged by every
  arithmetic operation and escapable to `0.0` through `json.to_value`; the
  preservation row says "**Preserved exactly**, as a field. Two earlier drafts
  rendered it as the constant `100.0`". §"Rendering" *is* one of those drafts,
  unedited.
- **Q18's state is given twice, both ways.** The header and §"Open questions"
  say closed; §"`q` is a field too" (line 244) and the `q` preservation row
  both say "**Q18 is reopened**". The register is unambiguous —
  `docs/registers/open-questions.md:39`, "closed — `q` is a field". Two of
  four statements in the RFC disagree with it.

## C. Acceptance criteria — is each checkable, and what checks it

**Binding.**

- **B1** (unadorned scalar 0 allocations, boxed scalar 5/721). Checkable;
  `cargo xtask layout` rows `D: construct a scalar`, `D: clone a scalar`,
  `D: box a scalar (what push forces)`. Reproduced. Good criterion — the
  qualifier is paired with the row that prices it.
- **B2** (`dup` 4 allocations / 649 bytes, list and boxed scalar). Checkable;
  `layout` rows `D: dup a list` and `D: dup a boxed scalar`. Both reproduce.
  Note it constrains only allocation count, not which fields `dup` copies —
  see B7.
- **B3** (`cite` zero defects). Checkable, and it runs clean. **The stated
  count is wrong**: 1265, not 1266.
- **B4** (`lint` no contradictions). Checkable, runs clean, and the criterion's
  own caveat is correct — findings B1, B2, B5, B7 and B8 are all invisible to
  it.

**Vacuous but real.** V1 (`0/68`) and V2 (`cargo tree`) are correctly labelled
and correctly described.

**Deferred.** Each names what makes it checkable, which is the improvement the
partition bought. Four have defects:

- **D2** — the bool clause rests on "scalars carry no identity", which B5 shows
  is false for any bool a program can reach. The assertion is still the right
  one; its stated justification is not.
- **D3** — written against `258 renderings across 29 goldens`, `255`/`3` and
  `34`/`29`, all of which have drifted (B9). It is also unsatisfiable as a
  *stable* check for the unadorned-scalar renderings, which mint a fresh `id`
  per render (B6) — it passes only because F14 normalises them away, and the
  criterion should say that is why.
- **D6 / D8** — assert hashing behaviour (`42` and `42.0` hash alike, `-0.0`
  and `0.0` hash alike, a scalar-keyed lookup finds its entry) for a
  `Payload::ValueMap` that is a `BTreeMap` and hashes nothing (B3). D8's
  equality half is checkable and well specified; its hashing half has no
  implementation to check.
- **D7** — "two independently constructed values have non-decreasing stamps
  once observed" is **not guaranteed by the design**. Under sampling at first
  observation, the stamps order by observation, not by construction: build A,
  build B, observe B, observe A, and A's stamp is the later one. The criterion
  asserts a property lazy sampling deliberately gives up. Either it constrains
  observation order or it is testing the reference's behaviour, not Bund2's.

**D5** ("`.id` returns a 21-character string … and two values minted in one VM
never collide") is checkable but does not assert the property B6 breaks:
*that `.id` on the same value returns the same string twice.*

## D. Preservation analysis — behaviours that could change and are not enumerated

The table is thorough on everything reviews 1–5 named. These are not in it:

1. **`q` reset to 100.0 by every container mutation**, and copied from the
   receiver by the scalar fallback arms (B4). There is a row for `q` as a
   field and a row for `stamp`'s reset; the `q` reset has neither.
2. **`attr_add` preserving the header while minting** (B1). The table has
   `attr` "Preserved exactly, as a field" and F34's reset row; the case where
   both apply to the same word is in neither.
3. **`dup` preserving `stamp`, `tags`, `attr`, `curr` and `q`** (B7). The
   `dup` row speaks only of "an equal payload with a fresh identity".
4. **`.id` and `.timestamp` stability across two observations of one
   unadorned scalar** (B6). The `.id` row asserts format preservation and says
   nothing about stability.
5. **The stamp of an unobserved value and its `dup`** (B7) — the D2 row covers
   two *independently constructed* values, not a value and its copy.
6. **`Ord` on `BundValue`** (B3). The ordering row disposes of the `id.cmp`
   fallback as "deliberately fixed" without saying what replaces it, while
   `Payload::ValueMap` now requires a total order.
7. **`Payload::Scalar(BundValue)` admits nesting.** Nothing in the RFC forbids
   `Payload::Scalar(BundValue::Heap(_))`, so the type permits an unbounded box
   chain that `dup`, `make_mut` and equality would each have to handle. The
   invariant "`Payload::Scalar` holds only an unadorned arm" is assumed
   everywhere and stated nowhere.
8. **`BundValue` is neither `Send` nor `Sync`.** `Rc` plus `Cell` decides it,
   and RFC-0002 depends on the conclusion — see §E.
9. **Identity ordering becomes observation order, not creation order.** D1's
   secondary consequence (`decisions.md:54-56`) anticipates counter-derived
   ids ordering by *creation*; under materialise-on-first-need they order by
   first need, and a split can mint out of creation order. D1 calls this low
   risk given F12 and it probably is, but the RFC consumes D1 and does not
   record that it lands somewhere D1 did not predict.

## E. Consistency with accepted RFCs and ERRATA

**ERRATA** — consistent. The `05-rfc-roadmap.md` §6 supersession matches the
RFC's header, and the retirement of the `00-jit-feasibility.md` §4.1 entry
matches §"Identity: lazy, but a nanoid-shaped string when observed",
including `base_classes.rs:16`.

**RFC-0002 cites RFC-0001 for a claim RFC-0001 does not make.** Lines 527-538:

> an `Rc` is neither `Send` nor `Sync` and a `Cell` is not `Sync` … making a
> registry *shareable across threads* is a separate problem that starts with
> whether `BundValue` is `Send`, **and RFC-0001 says it is not**.

RFC-0001 never mentions `Send`, `Sync`, or threads. The inference is correct —
it follows from `Heap(Rc<HeapValue>)` and the `Cell` fields — but RFC-0002 is
resting an architectural conclusion, and RFC-0007's inheritance of the
question, on a statement that is not in the document it names. RFC-0001 should
state it, in the section that chooses `Rc` and `Cell`.

**RFC-0002 and RFC-0001 disagree on why `curr` is a plain field.** RFC-0002
lines 524-526: "`curr`, which is a plain field precisely so clones do not
share a cursor." RFC-0001 §"The heap object" says the same — and then §"`curr`
is the iteration cursor" says Bund2's `next` "operates on a locally owned
cursor rather than mutating through the value", so clones do not share a
cursor because nothing writes the field at all. Both documents are describing
a field that, as specified, is written once to `-1` and never again. That is
the design an earlier draft proposed and review 5 rejected; if it is now the
intended design, it should be said outright rather than reached by two
sections cancelling.

**D13** is quoted verbatim and correctly (`decisions.md:384-388`), and the
one-rule answer does discharge the clone/`make_mut` half it was written for.
**D1**'s reset-site list (`decisions.md:45-46`) includes `bincode.rs:95`
(`unwrap`) and `id.rs:6` (`regen_id`), which the RFC's two-bucket taxonomy
does not classify — a smaller instance of B1.

**D30** — see B3. **D4, D20** — consistent. **F12, F14, F15, F29, F30, F33,
F34, F35, F36, F38, F41, F42** — dispositions match the rows that cite them,
which is what `lint` confirms.

## F. Assumed but not stated

1. That `Payload::Scalar` never nests (D §7).
2. That `set_q` and `calc_q` only ever write a freshly constructed, unshared
   value — the only thing that saves the "`set_tag` alone" claim (B2).
3. That `BundValue` has a total `Ord` consistent with the equality this RFC
   specifies, including a decision about `NaN` (B3).
4. That the `dup` header copies `stamp`, `tags`, `attr`, `curr` and `q`
   verbatim, and that a cleared `stamp` cell is not among them (B7).
5. That `HeapValue` is `Clone` — required by `Rc::make_mut` and by the split
   policy, and true of the declared fields, but never stated.
6. That the split policy governs **one** `Rc`, when the design has two:
   `Rc<HeapValue>` and `HeapValue.payload: Rc<Payload>`. D13 asks for "one
   policy governing both" the pointer and the slot; the second pointer arrived
   with `dup` and the policy was not restated over it. (A payload split
   plausibly needs no materialisation, since identity lives above it — but
   that is the argument, and it is absent.)
7. That `identity == 0` is a reserved sentinel the minting counter never
   produces.
8. That the boxing of an unadorned scalar is *not* written back to wherever the
   scalar came from (B6) — the entire stability question turns on this and it
   is never said either way.
9. That `BundValue` is single-threaded (E).
10. That the golden normaliser's `id: "` prefix match is satisfied by a
    quoted 21-character string — asserted in §"Identity: lazy…" as a
    constraint on the design, but no citation into the normaliser is given.

## G. What is right, and should not be relitigated

- The one-rule statement — *a CoW split materialises the identity before it
  copies* — does discharge D13's condition for the `Clone`/`make_mut` pair,
  and the reasoning (the reference's derived `Clone` deep-copies the `id`
  string, so both halves hold it, and `set_tag` leaves it alone) is exactly
  right and correctly cited.
- `dup` as a cleared-identity header over a shared payload is the correct
  reading of D1's clone-equal/dup-unequal contract, and the second `Rc` is the
  right structure for it.
- The scalar-boxing analysis is correct and the cost is stated rather than
  elided; handing the stack-slot optimisation to RFC-0003 is the right
  division.
- The `==`-reachability argument for scalar content equality holds
  (`logic_compare_fun.rs:67-69`), including the narrowing review 3 forced.
- The criteria partition is a real improvement: four binding criteria that can
  fail, two vacuous ones labelled as such, and eight deferred ones that each
  name their check.
