## Verdict

**Not ready for Accepted**, on one finding. It is a false statement
about a core word, and it is not an unruled deviation. Everything else is
bookkeeping or a claim that needs restating.

1. **A weight that saturates at `usize::MAX` *is* used by `graph.path`.**
   The RFC (R:147-149, R:600-602), F227 and the new test's doc comment
   all say a weight of 2^64 or more is "never used" and "no path through
   it is chosen". `MAX + w` wraps to `w − 1` like any other `usize` sum,
   so a saturated edge after a non-zero prefix makes the path *lighter*.
   `graph.path` then picks it over a real path, in the oracle and in both
   Bund2 builds. Bund2 matches the reference, so no golden or conformance
   figure is at stake. What is at stake is that the preservation analysis
   tells a program the opposite of what happens, and that D210 was put to
   the owner on that description.

Then, smaller:

2. "Bund2's `HashMap` is a different build, and the rates differ" (R:564-566):
   both binaries use std's `HashMap` from the same compiler. Over 1,000 runs
   each, the rates are 9.3% and 8.5%.
3. "Seeded afresh for each graph" (R:213-214) is cited to lines that say
   nothing about seeding.
4. `allpath_answers_f225s_programs_alike_on_every_run` checks less than its
   name, and less than R:224 says.
5. "Preserved in every build" holds only for builds whose root is this
   workspace.

## Findings, most serious first

### 1. A saturated weight is used: `usize::MAX + w` wraps to `w − 1`

`make_graph.rs:64` casts `w as usize`, which saturates: 1.0e300 becomes
`usize::MAX`, which is `WEIGHT_MAX` (`constants.rs:26`). The RFC
concludes the edge is dead:

- **R:147-149:** "A single weight at or above 2^64 saturates at
  `usize::MAX`, which is `WEIGHT_MAX` (`src/constants.rs:22,26`), so no
  path through it is chosen."
- **R:600-602:** "a weight of 2^64 or more saturates at `WEIGHT_MAX` and is
  never used".

That holds only when the saturated edge is the first edge searched from a
node at weight 0. `fast_paths` treats `WEIGHT_MAX` as an ordinary
`usize`. Both contraction (`node_contractor.rs:75`) and the query
(`path_calculator.rs:145`) add it unchecked, so a prefix of weight `d > 0`
followed by it sums to `d − 1`. That passes every `<` test
(`path_calculator.rs:146`), and the path wins.

```
:A :C [ [ :B :A 1.0e300 ] [ :C :B 2.0 ] [ :C :A 7.0 ] [ :A :D 1.0 ] ] [ :A :B :C :D ] graph! graph.path println
```

| build | answer |
|---|---|
| oracle | `{ found=true :: path=[ C :: B :: A :: ] :: weight=1.0 }` |
| `target/release/bund2` | the same |
| `target/debug/bund2` | the same |

- **The path is wrong.** It runs through a 1.0e300 edge, and the direct
  edge `C → A` weighs 7.0.
- **The weight is wrong.** It is `2 + (2^64 − 1)` mod 2^64 = 1.
- **It is stable.** It answered the same on 40 runs in each build.

Whether `fast_paths` reaches the wrap depends on its contraction order:

- Without the `[ :A :D 1.0 ]` edge, the graph answers `can not calculate
  path` in all three builds.
- The ninth review's `[ [ :A :B 1.0e300 ] ]` answers `can not calculate
  path` because the saturated edge is first.

A seeded search over 400 random graphs found 17 answering `found=true`
along a saturated edge. Two more, from that search:

- `:C :A [ [ :A :B 1.0 ] [ :B :A 3.0e19 ] [ :A :B 1.0 ] [ :C :A 1.0 ] [ :B
  :A 1.0e300 ] [ :A :B 1.0e300 ] [ :B :C 1.0e300 ] ] [ :A :B :C ]` answers
  `path=[ A B C ]` at `weight=0.0`. The repeated `A → B` keeps 1.0
  (`input_graph.rs:149-161`), so `B → C` (1.0e300) is the saturated edge,
  and `1 + (2^64 − 1)` wraps to 0. Oracle and both Bund2 builds agree.
- Two saturated edges in a row, `[ [ :A :B 1.0e300 ] [ :B :C 1.0e300 ] ]`,
  sum to `2^64 − 2`, which is below `WEIGHT_MAX`. With or without a fourth
  node beside them, each variant tried answered `can not calculate path`
  in all three builds. So R:601-603's 1.0e300 program does answer as the
  RFC says, but not for the reason it gives.

Consequences:

- **R:147-149 and R:600-602 are false**, and they are in the preservation
  analysis's "what a program moving between old and new words sees"
  list. A program reading the RFC would take 1.0e300 as a safe "no edge"
  weight for `graph.path`. It is the opposite: such an edge can become
  the cheapest step in the graph.
- **F227 (`defects.md:4251-4253`) says the same** ("so no path through it
  is ever chosen … for that reason, not because a sum was refused"). So
  does the test's doc comment (GA:2456-2457). The test itself asserts the
  one graph where it holds. It pins the claim as if it were general.
- **D210 was put to the owner as "a sum past 2^64 wraps".** The saturated
  case is the same arithmetic, and Bund2 already matches the reference, so
  the presumption is that D210 covers it. But its premise, quoted from
  F227, says a saturated weight cannot be used. D203 and D208's two notes
  set the precedent: a new face of a preserved defect goes back to the
  owner as a dated note rather than being assumed.
- **The new words differ more than the RFC says.** R:605-606 says that
  where the new words "refuse or answer exactly, `graph.path` answers a
  wrong weight as found". That is true, and it is also a wrong *path*:
  here `graph.bellmanford` from `:C` answers `A` at 7.0.

**Repair:**
- R:147-149 and R:600-602 restated: a saturated weight wraps like any
  other sum, so it can make a path lighter and be chosen, and whether it
  is depends on `fast_paths`' contraction.
- A dated note on F227 with this program, and one on D210 for the owner to
  confirm it covers this face.
- The doc comment at GA:2456-2457 corrected, and this program added to
  `path_wraps_a_sum_past_2_to_the_64`, asserting `path=[ C B A ]` at
  `weight=1.0` beside the direct 7.0 edge.

### 2. "Bund2's `HashMap` is a different build, and the rates differ" is not so

R:564-566: "Bund2 keeps the variation, not the oracle's answer on any
given run: its `HashMap` is a different build, and the rates differ (6 in
150 against 17 in 150 on F226's program)." F226 (`defects.md:4289-4290`)
says the same.

- **It is the same build.** `algos` uses `std::collections::HashMap`
  (`algos/src/cs/graph.rs:29`). The oracle and `target/release/bund2` were
  both compiled by `rustc` `59807616e` (1.95.0), so both link the same std
  table and the same SipHash. Both run the same `algos` revision.
- **The rates do not differ measurably.** Over 1,000 runs each, the oracle
  refused 93 and Bund2 85. A two-proportion test gives z ≈ 0.6. The ninth
  review's 17/150 against 6/150 (z ≈ 2.4) was a small sample. The test's
  own doc comment (GA:2440) says "about 1 map in 12", which is 8.3%.
- **The conclusion still holds**, for a different reason. Bund2 does not
  reproduce the oracle's answer on a given run because each process draws
  its own random keys, not because the table differs.

**Repair:** R:564-566 to say both engines vary at the same rate within
sampling, for the reason above. Drop "a different build". A dated note on
F226 to the same effect.

### 3. "Seeded afresh for each graph" is cited to lines that do not say it

R:213-214: "`algos` keeps its edges in a `HashMap` seeded afresh for each
graph (`algos/…/4c08437/src/cs/graph.rs:64-66`, `:150-154`)".

- **The cited lines** show the field's type and `edges()` iterating it.
  `:89` and `:97` show `HashMap::new()`. None of them says anything about
  seeding.
- **The seeding is std's `RandomState`**, which neither the RFC nor F226
  cites. No toolchain source is installed here (`rust-src` is absent), so
  this review cannot ground how it seeds. As this reviewer understands
  std, each thread draws random keys once and each new `RandomState` then
  increments one of them. That is "afresh per process, distinct per map",
  not independent per map.
- **That matters for `allpath_answers_vary_between_runs`** (GA:2444). The
  test runs 2,000 maps in one process and states "the chance of one never
  occurring is below 10^-30" (GA:2441-2442). That bound assumes the maps'
  orders are independent draws.

**Repair:** cite std for the seeding, or mark the claim `[UNGROUNDED]` and
add it to open questions. Say in the test what the bound assumes.

### 4. `allpath_answers_f225s_programs_alike_on_every_run` checks only whether each run refuses

R:224 says "The first three programs answer alike on every run", and
criterion 11 names this test for it. The test (GA:2416-2437) counts
`run_src(…).is_err()` through `allpath_refusals` (GA:2402-2406):

- for the refused program, 200 of 200 must refuse;
- for the four answered programs, 0 of 200 may refuse.

It never compares the rows of one run with another's. So "alike" is
checked as "never refuses", and the answered programs' faces are pinned
once, by the earlier tests, not over 200 maps. Those faces are `B → C` at
`0.0` and the missed cycle's eight rows.

The rows are in fact stable: F225's misstated-distance program gave one
row set over 150 runs in each engine, and F226's gave one over 1,000. So
this is a gap in the check, not in the behaviour. The RFC's argument for
it, the gfp of a monotone relaxation, is not stated in the RFC either.

**Repair:** have the helper return the rows of each answered run and
assert they are equal across the 200. Or say in criterion 11 that the test
checks refusal only.

### 5. "In every build" means every build rooted in this workspace

D210, R:149-150 and R:567-570 say `graph.path` answers the wrap "in every
build profile". That rests on `[profile.dev.package.fast_paths]` in the
workspace `Cargo.toml`. Cargo reads profile settings only from the root
of the build. So a crate that depends on `bund2-stdlib`, built in its own
dev profile, checks overflow in `fast_paths` again. There, F227's program
is a panic that D49 reports as a Bund2 defect: the state D210 removed.
RFC-0012 S6 and `PROMOTABLE.txt:5` both speak of embedders' natives, so
such builds are contemplated.

This is not a reason to change D210's answer. It is a scope the RFC
should state. A test in a downstream crate cannot see it, which leaves
documentation. The other route is to do D210's arithmetic in Bund2: a
`u128` pre-pass that *reproduces* the wrap, rather than refusing it as
option B would, so no profile is involved.

**Repair:** state the scope in R:149-150 and in D210's note, or remove
the dependence on the profile.

## What the RFC assumes but does not state

- **That `WEIGHT_MAX` is a sentinel `fast_paths` respects.** It is only
  the initial value of a `<` test, and unchecked addition passes through
  it (finding 1).
- **That a `Cargo.toml` profile override reaches every build of
  Bund2** (finding 5).
- **That the maps in one process are independent draws.**
  `allpath_answers_vary_between_runs`' bound needs this (finding 3).
- **That a settled floating-point relaxation reaches the same potentials
  in any order.** This is what makes "only the refusal varies" true: it
  is the greatest fixed point of a monotone map, so any order that stops
  stops there. The RFC states the conclusion without the reason, and no
  test checks it (finding 4).
