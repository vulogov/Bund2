## 1. Blocking

### B1 — the per-native adapter bypasses `Interp::invoke`, so a failed native's tail request survives into `?try`

**What §S5 claims.** "**A request is never lost.** […] Tier 0 cannot reach
that state since F96, because `Interp::invoke` clears a request when the
native that filed it fails. Before F96 an embedder's native could leave one
behind, and Tier 0 ran it late (the tenth review's S3.2). **Under these rules
compiled code cannot reach it either**" (lines 944–950).

**What the rules actually cover.** Three of the four helpers inherit the fix,
because each reaches a native through `dispatch`:

- the resolving trampoline runs the chain through `dispatch`, which calls
  `Interp::call_native` and then `Interp::invoke` (`crates/bund2-interp/src/lib.rs`,
  `dispatch`, `call_native`, `invoke`);
- the residual path's `apply` is `Interp::apply` → `apply_step` → `dispatch`,
  the same way;
- the drain helper clears the cell when the floor refuses it (lines 962–965).

**The adapter does not.** §S8 specifies it as "a per-native adapter in Rust
[…] It rebuilds `&mut dyn Vm` from the context and calls the native's
`NativeFn` through `bund2_api::catch_panic` (D49). It parks an `Err` in the
error slot and returns the status" (lines 1742–1746). `Interp::invoke` is a
private method of `Interp`, reachable only from `call_native`, so a compiled
call to a native is precisely the path on which nothing clears `pending_tail`.
`status_of` clears the cell **only when it answers an exit** (lines 822–823
and 966–971). A native that files a request and then fails without an exit
keeps it.

**It is reachable from `bund2-stdlib`, not only from an embedder.**
`execute_value`'s LIST arm pushes and executes each item in a loop
(`crates/bund2-stdlib/src/values.rs`, `execute_value`), so a LAMBDA item files
a request through `Vm::tail_lambda` and a *later* item can fail. Run at Tier 0
today:

    [ { 10 } 5 ] !
    → Received value is not of executable type; the stack is empty

and under `?try`:

    ?try :try { [ { 10 } 5 ] ! } set :except { "EXCEPT" println } set \
         :recovery { "RECOVERY" println } set !

prints `EXCEPT`, `RECOVERY` and leaves **only** the `error` CONDITIONAL, whose
`context` is `Lambda content evaluation returned error: Received value is not
of executable type`. No `10`. That is `Interp::invoke`'s clearing doing its
work.

**With the `try` body compiled**, the `!` adapter parks that `Err` and returns
the error status. The request cell stays set, `run_tryexcept` catches, pushes
its CONDITIONAL and runs its `except` body through `Vm::eval_lambda`, and the
first `take_pending` inside that body pushes `{ 10 }`. The final stack then
carries a `10` Tier 0 does not leave — and D52's dated note has just made that
stack meaning.

**Why no criterion stops it.** Criterion 26 names the case — "a native that
files a request and then fails, under `?try`, must leave no body to run
afterwards (F96)" (lines 3057–3062) — so a built tier would fail it. But the
criterion names no program, and the design text says the state is unreachable,
so the mechanism that would make it unreachable is the thing missing.

**F96's own entry understates the reach.** It says "No `bund2-stdlib` native
does this: all four request sites return `Ok` straight after filing"
(`docs/registers/defects.md`, F96). The LIST arm above is a fifth site, with a
loop after it, and the program above is the proof. The register is append-only,
so this needs a dated note.

**Required.** This is the RFC's own mechanism and needs no owner decision:
- **`status_of` clears the request cell whenever it answers an error**, not
  only when it answers an exit — exactly what `Interp::invoke` does for a
  native that fails. §S5 already made `status_of` the single status-maker so
  that "a helper added later cannot forget it"; this is the same argument
  applied to the same function.
- Correct lines 944–950: name the adapter as the path that does not inherit
  F96, and say what closes it.
- Correct Preservation row 2380, which credits `Interp::invoke` and the refused
  drain and so reads as complete.
- Give criterion 26's F96 case the program above, with its Tier 0 result.
- Add a dated note to F96 recording that `execute_value`'s LIST arm is a
  `bund2-stdlib` native that files and then fails.

## 2. Significant

### S1 — "`?try` is the only native that catches" is false: `#` discards a refusal

Four places now say it:
- line 802, "Every other native passes the refusal up, wrapped in its own
  context";
- assumption 25, "In `bund2-stdlib`, `?try` is the only such native" (line 2244);
- D52's second dated note, "That holds for every native that passes the
  refusal up, which in `bund2-stdlib` is all of them but `?try`";
- the Status line, "`?try` is named as the only native that catches" (line 137).

`#` and `#.` do neither. `object_execute_base` ends

    vm.push(body);
    let _ = crate::values::execute_top(vm);
    Ok(())

(`crates/bund2-stdlib/src/oop.rs`, `object_execute_base`), and the doc comment
above it says so in as many words: "**Both of those calls discard their
result** — `let _ = vm.apply(…)` — so a failing `unwrap` does not stop `#`".
Through `execute_value`'s `PTR | STRING | CALL` arm that discarded result is
`Vm::apply`'s, which since F112 carries the refusal. So `#` swallows it and
answers `Ok`.

**No tier divergence follows, and that is worth stating rather than left for a
reader to re-derive.** A swallowed refusal is the `Ok` path, where `status_of`
substitutes `exit_gate`'s refusal and assumption 26 covers the wrappers; `#`
does no Rust work after the discard, it returns `Ok` immediately. What is wrong
is the scope of the claim, in all four places.

**Required:** say "the only native that catches the refusal **and then does
work**", and name `#`/`#.` as the ones that catch and do none. D52's note is in
an append-only register and needs a further dated note. Assumption 25's last
three sentences, about an embedder's native, are then the general rule and `#`
is the `bund2-stdlib` instance of the harmless half.

### S2 — criterion 30's two new cases name no program and no Tier 0 half

The `?try` and `input*` bullets are now checkable and have Tier 0 halves. The
bullet between them is not:

> a drained body and a residual-path value that reach `exit` through a native,
> compared the same way (lines 3145–3146)

Every other case in criterion 30 names its program. This one names neither the
program nor what "the same way" compares when the value left behind is not a
`?try` CONDITIONAL — and unlike the bullets above it, it has no Tier 0 half,
although both halves are runnable: a drained body is what `{ … } !` leaves for
the loop, and a residual-path value is what follows a stack switch.

Also worth stating: the Tier 0 test that now backs the `?try` case compares
*less* than the criterion asks of the compiled half. It asserts that the
`context` slot ends with the refusal and contains each native's wrapper; it
does not compare whole final stacks. That is enough to pin the gates — I
mutation-checked both — and the criterion should say which half the test covers
so the compiled half is not taken as already specified.

**Required:** give the drained-body and residual-path cases a program each and
say what they compare; add their Tier 0 halves; say what
`try_keeps_the_error_its_body_returned_after_an_exit` covers and what remains
for the tier.

### S3 — smaller items

- **F112's new note gives the wrong reason.** It says the two gates "change no
  native's behaviour: `eval_source`, `execute_value`, `apply`, `text` and
  `run_context` return straight after the call". Two of the five do not.
  `eval_source` loops over the parsed stream, applying each value
  (`crates/bund2-stdlib/src/singles.rs`, `eval_source`), and `execute_value`'s
  LIST and MAP arms loop and recurse (`crates/bund2-stdlib/src/values.rs`,
  `execute_value`). Before F112, an `exit` that was not the last value of a
  `bund.eval` source was refused at the *next* value's `apply_step`, so the
  wrapper named that value rather than the `exit`; and in a LIST the loop went
  on to push and execute the next item. The note's conclusion survives for
  reachable programs — the arms that do Rust work before re-entering
  evaluation (CLASS, OBJECT, CONDITIONAL) cannot appear in a list literal,
  since `[ 1 2 + ]` keeps `+` as a CALL value rather than evaluating it (run
  this session) — but the reason given is not the reason. The same sentence is
  in criterion 30, "whose only visible effect is the text" (line 3158).
- **Assumption 26's reason is incomplete.** It says Tier 0's next step after a
  helper's `Ok` "runs inside the same `run_to`, under the same
  `Vm::eval_lambda` wrapper". When the `Ok`-returning call is the body's last
  word there is no next step: `run_to` pops the frame and returns `Ok`, and the
  refusal comes from the gate *after* `run_to`. The two texts agree only
  because `eval_lambda` applies its wrapper to both —
  `self.run_to(floor).and_then(|()| self.exit_gate()).map_err(|e| e.context("Lambda content evaluation returned error: "))`
  (`crates/bund2-interp/src/lib.rs`, `eval_lambda`). That chain is what
  criterion 30's `map` rows and the `?try` control row rest on, and if the
  post-`run_to` gate ever moved outside the `map_err` the tiers would part
  while every stated reason still held. State it.
- **A Tier 0 defect, unfiled, found while checking the request model.** The
  reference's LIST arm runs each lambda item immediately — `return
  vm.lambda_eval(ptr_value)`
  (`reference/rust_multistackvm/src/stdlib/execute.rs:93-95`, reached from the
  list loop at `:40-48`). Bund2 files each through `Vm::tail_lambda`, and
  `Interp::request_tail` **assigns**, so a second request overwrites the first:
  `[ { 10 } { 20 } ] !` leaves only `20` at Tier 0 today (run this session),
  where the reference leaves `10` beneath `20`. I did not build the oracle, so
  the reference half is from reading those lines. No golden covers it, and
  `conform` is at its ceiling. This is **not** a tier divergence — compiled
  code calls the same native — but §S5's "A request is never lost" reads as a
  property of the system and is false of Tier 0 today; the rule it states is
  about compiled call sites only. Say so, and file the defect.

## 7. What the RFC assumes and does not state

1. **Every helper that returns to compiled code inherits `Interp::invoke`'s
   clearing of a failed native's request.** Three do, by going through
   `dispatch`. The adapter does not (B1).
2. **`Vm::eval_lambda` wraps its post-`run_to` refusal in the same context as
   `run_to`'s error.** This is what makes the two tiers' error *text* agree when
   an exit is the body's last action, and it is not assumption 26's stated
   reason (S3).
3. **A native that swallows a refusal does no further work.** True of `#`
   today, because it returns `Ok` at once — which is why B1's fix leaves the
   `Ok` path alone and why S1 is prose rather than a second blocker.
4. **A list literal does not evaluate its items**, so `execute_value`'s arms
   that do Rust work before re-entering evaluation (CLASS, OBJECT,
   CONDITIONAL) are unreachable from one. F112's "no golden moves" rests on
   this (S3).
5. **A second request filed inside one native overwrites the first**, which
   Tier 0 does today and the reference does not (S3). §S5's "A request is never
   lost" is a rule about compiled call sites, not a property of the system.
