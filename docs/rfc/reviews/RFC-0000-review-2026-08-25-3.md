## 1. Citation defects

### 1.1 `">=0.33.*"` does not bound the minor series — and so *twelve* of twelve pins are unbounded

RFC lines 48-51:

> All are `">=0.*.*"` except `reference/rust_multistackvm/Cargo.toml:21`,
> pinned `">=0.33.*"`, **which bounds the minor series but not the patch**. So
> a `Value` layout change propagates to every dependent without a version bump
> **on all but one edge**.

Both emphasised clauses are false. A `>=` requirement in Cargo has no upper
bound; the wildcard in the patch position does not introduce one. `>=0.33.*`
means "0.33.0 or later", forever.

The proof is on disk, in the oracle's own lockfile:

- `reference/rust_multistackvm/Cargo.toml:21` — `rust_dynamic = ">=0.33.*"`
- `reference/Bund/Cargo.lock:8713-8714` — `rust_dynamic`, version **0.49.0**,
  and it is the only `rust_dynamic` entry in the lock.
- `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rust_multistackvm-0.38.0/Cargo.toml:178-179`
  — the *published* manifest carries the same `">=0.33.*"`, so this is not an
  artefact of submodule/registry skew.

If the pin bounded the minor series, resolution would have produced a
0.33.x `rust_dynamic`, or two versions. It produced one, at 0.49.0 — sixteen
minor releases past the floor.

This matters beyond arithmetic:

- The count in the heading is wrong. Eleven of twelve unbounded should be
  **twelve of twelve**. The exception the RFC constructs does not exist.
- "on all but one edge" should be "on every edge". The error runs against F8,
  understating the defect the RFC uses to justify the monorepo in Alternatives
  ("Unbounded `">=0.*.*"` pins between separately released crates mean a
  `Value` layout change reaches four dependents without a version bump").
  `rust_multistackvm` is not the safe edge; there is no safe edge.
- This is the paragraph the diff rewrote. The previous pass corrected the
  count from six-of-seven to eleven-of-twelve; the rewrite kept an unexamined
  clause from the superseded text and re-asserted it.

Minor, same sentence: "All are `">=0.*.*"`" is a verbatim claim, and two of
the twelve are written with a space — `rust_multistack/Cargo.toml:14` and
`rust_multistackvm/Cargo.toml:22` both read `">= 0.*.*"`.

### 3.2 And the closing paragraph is the one that is right, for clause one

Ran both:

That is the entire output. `bund2-value` has no dependencies at all, so

The diagnosis of the *previous* draft is correct and worth keeping — writing

Separately, both clauses check only the default feature set. The rule
criterion 4 encodes for `bund2-jit` is that Tier 1 stays optional, which is a
statement about *every* feature combination; a `jit`-gated dependency inside
`bund2-stdlib` would satisfy the criterion as written. `--all-features`, or an
explicit enumeration, would make it say what it means.

### 3.3 Criterion 5's rationale is false by the RFC's own new definition of "Oracle"

Line 400-401:

> Criterion 5 catches an accidental edit to **the oracle**, which would
> invalidate every citation in every RFC.

The Terminology section, rewritten by this diff (lines 222-231), now defines
Oracle as "the `bund` binary in `target/oracle`", built from crates.io. An
empty `git status` inside `reference/<crate>` does not observe that binary,
does not observe its inputs, and cannot be invalidated by editing it.

What criterion 5 actually catches is an accidental edit to the *submodules* —
which is the thing that invalidates citations, and which is worth catching.
The sentence was true under the old definition of Oracle and became false when
the definition moved. The previous pass asked for exactly this ("Correct the
Terminology definition of Oracle, and correct what criterion 5 is claimed to
catch", §3.5); half of it was done.

### 3.4 The provenance check reports 5/5 when it has compared no bytes

This is the sharpest of the new findings, because it is F21's own shape
reproduced inside F21's mitigation.

`xtask/src/cite/mod.rs` runs two tiers. Tier 1 compares each submodule's
declared version against the lockfile and emits a **non-blocking advisory**.
Tier 2 byte-compares the source trees and is **hard**. Tier 2 is guarded:

```rust xtask/src/cite/mod.rs:287-289
        if let Some(reg) = &registry {
            let vend = reg.join(format!("{c}-{want}/src"));
            let sub = repo.join(format!("reference/{c}/src"));
```

and `agreed += 1` at `:307` runs at the end of the loop body regardless of
whether Tier 2 executed. The summary at `:527-531` then prints
`prov_agreed/prov_checked` under the label **"oracle crates byte-verified"**.

So when the vendored registry source is absent, the run prints
`oracle crates byte-verified 5/5` having compared zero bytes.

That is not hypothetical for CI. `.github/workflows/ci.yml:31` runs
`cargo xtask cite` in the `check` job. The five crates are dependencies of
`reference/Bund`, not of the Bund2 workspace, so nothing in that job — `cargo
fmt`, `clippy`, `test`, `check` — populates
`~/.cargo/registry/src/*/rust_dynamic-0.49.0`. Tier 2 will be skipped on every
CI run, and the summary will report full byte verification anyway.

The code's own doc comment states the design plainly — "Two tiers, so the
weaker one still runs in CI where no registry source exists" (`:219-220`) — so
the implementer knew Tier 2 does not run there. The RFC's Terminology does not:

> The submodule sources and the linked crate sources are byte-identical today,
> which `cargo xtask cite` verifies **on every run and in CI**

It verifies on every run *where the vendored crate happens to be present*, and
in CI it does not verify at all. On this machine the check is real — I confirmed
all three vendored crates exist and the run reports 5/5 legitimately. The defect
is that the two cases are indistinguishable in the output.

Fix shape, for whoever takes it: count `agreed` only when Tier 2 ran, print
`byte-verified n/5 (m skipped: no vendored source)`, and decide whether a
skip should be an advisory. The label is the load-bearing part — "5/5" is
read as evidence, and right now it is sometimes an assumption.

Two smaller gaps in the same check:

- `first_difference` (`:322-352`) walks only files with extension `rs`. No
  non-`.rs` file exists under any of the five `src/` trees today, so this is
  latent rather than live — but an `include_str!`ed data file would diverge
  unnoticed.
- Nothing compares `Cargo.toml`. That is the file all twelve F8 edge
  citations point into, and the file whose contents determine what the oracle
  links. The provenance guard's coverage excludes the citation class most
  exposed to the provenance problem. (I checked the one that matters:
  `rust_multistackvm-0.38.0`'s published manifest matches the submodule at
  `:178-179`.)

## 4. Preservation analysis — what it still does not enumerate

The four new items added by this diff are all correct as far as they go. Three
of them do not go far enough, and the section still omits two behaviours in
the same files it now cites.

### 4.1 The dead table strands four words, not one

The RFC (lines 293-301) says "*Some* names exist only in the dead table, and
two aliases point into it", and names `stacks_left`. The previous pass said
six names. The complete set, computed by differencing `register_function`
names against `register_inline` names across `reference/rust_multistack/src/stdlib/`
and then searching all six crates for any other registration:

| name | registered where else | reachable? |
|---|---|---|
| `dup` | alias → `dup_one` (`create_aliases.rs:18`) | yes |
| `push` | **different function**, inline, in `Bund` (`Bund/src/stdlib/functions/values/push.rs:74`) | yes, but not this one |
| `dup_in` | nowhere | **no** |
| `from_workbench` | nowhere | **no** |
| `push_to` | nowhere | **no** |
| `stacks_left` | nowhere (F22) | **no** |

Verified against the oracle — each of `1 2 dup_in`, `1 2 from_workbench`,
`1 2 push_to`, `1 2 stacks_left` fails with `i(<name>) for stack returned:
Inline <name> not registered`.

So F22 records one instance of a four-instance defect. `<-` and `←` are the
only *aliased* casualties, which is why they were noticed, but three more
documented word names are equally dead.

`push` is a second F20: `rust_multistack/src/stdlib/push.rs:44` registers
`stdlib_push_value_to_current` under `push` in the dead table, while
`Bund/src/stdlib/functions/values/push.rs:74` registers a different function,
`stdlib_push_list_stack`, under the same name in the live VM table. The alias
`+++` (`Bund/src/stdlib/functions/create_aliases.rs:34`) reaches the latter.
Same shape as F1 and F20, third instance.

Consequence for the RFC's sentence "dropping it is not purely subtractive —
two documented words go with it": the true statement is that the table names
six words, of which four are already unreachable and one is shadowed by a
different implementation. Dropping the table changes nothing observable; what
is at stake is whether Bund2 *implements* `stacks_left`, `dup_in`,
`from_workbench` and `push_to` (four fixes) or preserves their absence (four
preservation decisions). Neither the RFC nor F19/F22 puts that choice to the
owner.

### 4.2 `rotate_stack_right` rotates left — unrecorded, in the file this diff just cited

`reference/rust_multistack/src/stdlib/rotate.rs:83-89`:

```rust
pub fn stdlib_stack_right_inline(ts: &mut TS) -> Result<&mut TS, Error> {
    if ts.current_stack_len() < 1 {
        bail!("Stack is too shallow for inline rotate_stack_right()");
    }
    let name = ts.pull();
    stdlib_stack_left(ts, name, None)      // <- :88
}
```

The inline wrapper for `rotate_stack_right` calls `stdlib_stack_left`. The
correct implementation, `stdlib_stack_right` (`:64-81`, which calls
`ts.rotate_stack_right` → `curr.right()` at `ts_rotate_stack.rs:50-58`), is
registered **only into the dead function table** (`:101`). The reachable word
is the wrong one.

Verified against the oracle, `@s 1 2 3 4` then rotate, printing four values:

| program | output |
|---|---|
| no rotate | 4 3 2 1 |
| `:s rotate_stack_left` | 1 4 3 2 |
| `:s rotate_stack_right` | **1 4 3 2** |
| `rotate_current_left` | 1 4 3 2 |
| `rotate_current_right` | 3 2 1 4 |

`rotate_current_*` behaves correctly and asymmetrically; `rotate_stack_*` does
not. This is a behavioural defect with no register entry, in `rotate.rs`'s
`init_stdlib` — the same function the diff cites at `:93` for F22. It needs an
F-number, and it needs a disposition before RFC-0002, because "preserve the
reference exactly" and "implement `rotate_stack_right`" are different programs.

### 4.3 A second, divergent, unreachable copy of the resolution order

`multistackvm_apply_in.rs` is a near-copy of `apply` that differs from it in
two observable ways and is reachable from nothing:

- **No `$`-prefix arm.** `apply_in:12-18` goes `is_command` → `autoadd` →
  `get_alias` directly. `apply` interposes the `$`-forces-internal-word check
  at `:33`.
- **Different `autoadd` semantics.** Under `autoadd`, `apply_in` *pushes* the
  value to the named stack (`:16` for CALL, `:46` for CONTEXT, `:65` for the
  default arm), where `apply` appends it to the top-of-stack value
  (`apply.rs:22`, `:92`).

Reachability, grepped across all six crates' `src/`:

- `call_in` (`multistackvm_call.rs:11-13`) — **zero callers**.
- `apply_in` — called only from `call_in` and from `lambda_eval_in`
  (`multistackvm_lambda_eval_in.rs:14`).
- `lambda_eval_in` — called only from `apply_in` (`:25`).

A closed cycle whose only entry point has no callers. The whole cluster is
dead, exactly like F19's function table, and unlike F19 it is a dead *copy of
the dispatch contract*.

Why this belongs in Preservation and not merely in the defect register: RFC-0002
is instructed to reproduce the resolution order, and there are two of them in
the source, differing in the `$` arm — which is one of the five elements the
RFC's own ordered list names. An implementer who reads `apply_in` (the file
name suggests the in-stack forms, which do exist as words) will write a
different contract. The RFC should say which file is normative and that the
other is dead.

To be explicit about what this does *not* affect, since it is easy to
misread: `!` is safe. `vm.call` uses `apply`, not `apply_in`
(`multistackvm_call.rs:8`), so the resolution order the RFC documents is the
one dynamic dispatch takes. Verified against the oracle: `1 2 "$drop" ptr !`
leaves `1`, so `$`-forcing works through `ptr !` exactly as through direct
evaluation.

### 4.4 The JSON item understates the loss, and `to_binary` is not deterministic

The RFC (lines 303-309) says a JSON round trip "discards identity". Reading
the constructors it round-trips through:

```
reference/rust_dynamic/src/create_special.rs:241-252   json_wrap
reference/rust_dynamic/src/create_special.rs:205-216   json
```

Both mint `id: nanoid!()` and `stamp: timestamp_ms()`, and both set `q: 100.0`
with `attr: Vec::new()` and `tags: HashMap::new()`. So the round trip discards
`id`, `stamp`, `q`, `attr` **and `tags`** — everything except the JSON payload.
Tags are observable; F15 exists because they print.

And the wrapping happens on the way *out*, at `bincode.rs:22`
(`Value::json_wrap(str_data)`), before `bincode2::serialize`. So serialising
the same JSON value twice produces **different bytes**, because the wrapper
carries a fresh `nanoid!()` each time. `to_binary` is not a pure function for
JSON values. That has consequences the RFC does not reach: content-hashing or
diffing a world file that contains a JSON value cannot work, and any golden
that ever printed serialised bytes would be caught by `cargo xtask golden`'s
run-it-twice check for reasons unrelated to F14.

### 4.5 Carried, unaddressed: `autoadd` is still described wrongly in Current behaviour

The previous pass's blocking item was "Move `autoadd` into Preservation and
complete it: the command check precedes it, `apply` has three arms, `apply_in`
differs, it cannot nest". The diff added the `ptr` paragraph and stopped.
Line 102 still reads:

> `apply` **first** tests `self.autoadd` (`multistackvm_apply.rs:19`)

It does not. `is_command` is tested at `:16`, three lines earlier, and returns
at `:17`. So commands dispatch under `autoadd` just as they do without it, and
the first element of the RFC's own five-element resolution chain is **not** in
the `else` arm the RFC says the chain is. The very next sentence — "The chain
above is the `else` arm" — is therefore wrong about its first element.

Still missing, from the same reading:

- `apply` has three `autoadd` tests, not one: `:19` (CALL), `:72` (CONTEXT),
  `:89` (everything else).
- The CONTEXT arm **inverts**: with `autoadd` set it pushes the value
  (`:73`); without it, it switches stacks (`:75`). The RFC's blanket
  qualifier — "Every statement in this RFC about what a word 'pushes' carries
  that qualifier" — is the wrong qualifier for CONTEXT, where `autoadd` is
  what makes it push.

## 5. Consistency with accepted decisions and with ERRATA

### 5.1 The new JSON item contradicts D20, which is RESOLVED

D20 (`docs/registers/decisions.md:554-589`) states:

> `to_binary` writes concrete values, so the bincode wire format stays
> byte-identical to the reference (`reference/rust_dynamic/src/bincode.rs:30`)
> and `from_binary` restores them verbatim (`:71`).

and again:

> round-tripping is self-consistent whatever is written (`bincode.rs:71`
> restores exactly what `:30` wrote)

Both cited lines are inside the **non-JSON** branches — `:30` is
`bincode2::serialize(self)` in the `else` of `if self.dt == JSON`, and `:71`
is `return Ok(value)` in the `else` of `if value.dt == JSON_WRAPPED`. For a
JSON value the path is `:9-28` out and `:54-69` back, and round-tripping is
*not* self-consistent: it mints new identity in both directions (§4.4).

D20 is RESOLVED, and its correctness argument depends on that

> they remain bincode-serialised `Value`s, and **D20's rule that serialisation

### 5.3 Carried, unaddressed: "three live tables"

RFC line 122: "Three dispatch tiers, three live tables."

The VM struct holds seven name-keyed maps
(`reference/rust_multistackvm/src/multistackvm.rs:24-30`): `inline_fun`,
`command_fun`, `methods_fun`, `lambdas`, `classes`, `vars`, `name_mapping`.
`TS` adds its inline table and the dead function table. The RFC's own
resolution order traverses commands, aliases, lambdas and two inline tables —
five. `methods_fun` the RFC never mentions at all.

The payload of the sentence is an instruction to RFC-0002 ("the slot table
absorbs three, not four"), so the ambiguity is load-bearing: an RFC-0002 that
absorbs three has not been told where commands, lambdas and methods go.

New, and cutting the other way — worth stating because it changes what the
preservation claim is doing. The RFC warns (line 265-267) that collapsing the
two inline tables "would be invisible until a word registered in two tiers
resolved to the wrong one". I checked whether that hazard is live: **it is
not**. Differencing every `register_inline` name in `rust_multistackvm/src` +
`Bund/src` (513 names) against every one in `rust_multistack/src` (31 names)
gives an **empty intersection**. No name is in both inline tables, so the
fallthrough order at `multistackvm_inline.rs:42,52` is currently unobservable,
and collapsing them today would change nothing.

The precaution is still right — it is cheap and the hazard is real for future
registrations. But the RFC states it in the present tense, as a property being
preserved, when what it is preserving is headroom.

## 6. Assumed but not stated

New this pass. The previous pass's list (§6.2-§6.8: where AOT lives,
`bund2-runtime`'s async invariant, whether the twelve-member list is closed,

**6.1 That "byte-verified" in `cite`'s output means bytes were compared.**
§3.4. The RFC's Terminology rests on this and the output cannot distinguish
verified from skipped.

**6.2 That the four registration tables are the whole namespace.** The RFC
counts three live plus one dead. `methods_fun` and `classes`
(`multistackvm.rs:26,28`) are neither, and OOP method dispatch is a
name-keyed lookup the RFC does not account for. RFC-0002 inherits the gap.

**6.3 That a word name resolves to one implementation.** Three counter-examples
are now known — F1 (`unregister`), F20 (`swap`), and `push` (§4.1) — and the
RFC's response is a caveat on one table row. The general statement the RFC
does not make: **a name may be registered in more than one table, and the
tables are ordered, so the registration a reader finds by grepping is not
necessarily the one that runs.** That is the rule RFC-0002 needs; the three
instances are evidence for it.

**6.4 That the dead code is one table.** §4.3. There are two dead
subsystems: the function table (F19) and the `apply_in`/`call_in`/
`lambda_eval_in` cluster. The second is dead *dispatch logic*, which is more
dangerous to port than a dead map.

**6.5 That `cargo xtask cite`'s coverage extends to the files the RFC cites.**
It walks `.rs` under `src/` only. `Cargo.toml` (twelve edge citations),
`bund.pest` (the twelve-alternatives claim) and `Cargo.lock` (F21's own
evidence) are all outside it.
