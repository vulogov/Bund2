# Review — RFC-0005: Tier 1, the Cranelift backend

- Reviewed: `docs/rfc/RFC-0005-cranelift-tier.md` at 1183 lines, Status **Draft**
  (2026-09-08, revised 2026-09-09).
- Reviewer stance: adversarial. Every `path:line` in the document was opened in
  this session at the pinned SHAs (`git status` clean in all six `reference/`
  submodules). Every number the RFC says can be re-derived was re-derived with
  the tool it names.
- Fifth review. `-09-08`, `-09-09`, `-09-09-2` and `-09-09-3` precede it.
  Findings they already made are marked **[carried]** and are only confirmed
  as still open, not re-argued.
- Environment note: `RUSTUP_TOOLCHAIN=1.94.1` was again set in this shell, and
  every `cargo xtask` invocation refused to run under it (F80's guard, still
  working). All numbers below were produced with it unset, under the pinned
  1.95.0.

## Verdict

**Stay Draft.** The revision since `-3` fixed real things: `conform` now takes
`--features` and prints what it measured (`-3` B1); §S6 now has a mechanism —
BundIR fragments — for how a promoted value reaches a word (`-3` B2); the
arity-overreach hazard is recorded as Q34 and criterion 14 (`-3` B3); the
workspace MSRV is 1.95.0 (`-3` S3); and `bund2-bench` has an `aot` feature
(`-3` S2). Every `reference/` citation still resolves and still says what the
RFC claims.

The revision also introduced the RFC's new centre of gravity — **inline first,
promote second** — and that is where this review's blockers are:

- **B1** — inlining a fragment removes the slot indirection that §S4 exists
  to guarantee. A redefined, aliased or lambda-shadowed `+` is not seen by an
  inlined caller. The RFC calls inlining the risk-free half.
- **B2** — the measurement that decided the staging does not measure a
  fragment. `int_add/inlined` constant-folds the literal the fragment would
  have to push, and nothing in the benchmark calls `frag::run` or
  `fragments::int_add`.
- **B3** — the §S6 site-count table was deleted but is still cited in five
  places, including by the justification of an accepted RFC's amendment. The
  numbers it carried are stale (113/63/50 today, not 116/61/55), and the
  conformance figure is stale too: **79/86**, not 73/86.

Under those sits a register conflict no one has recorded (**S1**): D32 says
arithmetic averages `q`, shipped code says it does not, and the reference
agrees with the code. RFC-0005 cites D32 for the one field its differential
test is built around.

## 1. Blocking

### B1 — an inlined fragment is a direct call in everything but name

§S4 builds the whole call architecture on one rule, derived from §3.2a:

> - **No compiled call is a direct relocation to a `FuncId`.** Every inter-word
>   call loads a pointer from a runtime-owned slot and calls it indirectly.
> - **Redefining a word writes a new pointer into its slot.**

Criterion 5 tests it: "`register` it again with different behaviour, and
assert the caller's next result changes."

§S6's mechanism then does the thing the rule forbids, by a different route. An
inlined fragment is not called through any slot — its ops are the body. The
guard set is closed and has two members:

```rust crates/bund2-ir/src/fragment.rs:49
pub enum Guard {
```

`TopAreInt(u8)` and `Depth(u8)`, nothing else. **Nothing guards on what the
name currently means.** Once `+`'s `Int + Int` arm is inlined, the compiled
body adds two ints for as long as it lives, whatever `+` has since become.

And `+` can become several things, all of them run-time properties this RFC
already enumerated in §S4's chain:

- **A lambda.** `apply` tests `is_lambda(real_name)` before it reaches `i`
  (`reference/rust_multistackvm/src/multistackvm_apply.rs:46-49`), so a lambda
  registered as `+` shadows the native.
- **An alias** to something else (`:39-40`).
- **A command** (`:16-17`), which outranks everything.
- **Collected, not called**, under `autoadd` (`:19-27`).

§S6 says the opposite of this, twice:

> Inlining alone is 3.8–5.4×, and it applies *everywhere*. [...] it keeps
> working across an opaque site.

> **And every risky part of this design belongs to promotion, not inlining.**
> [...] Inlining moves no value anywhere.

It moves no value. It freezes a name, and freezing names is the risk §S4 was
written to remove. "Keeps working across an opaque site" is the sharpest form
of the problem: §S4 itself says that after `:` or `;` "the meaning of every
following call has changed", and `!` can reach `register`, `alias` or `:` by
computed name. After an opaque site, an inlined `+` is exactly the stale code
the slot rule prevents.

**It is worse than opaque sites, because the table mutators are not opaque.**
Bund2 declares them with fixed effects:

- `register` — `eff(2, 0)`, `crates/bund2-stdlib/src/values.rs`
- `unregister` — `eff(1, 0)`, same file
- `alias` — `eff(2, 0)`, `crates/bund2-stdlib/src/singles.rs`

So under §S5's rules a body can run `register` straight through, with
promotion and inlining both still live, and then execute an inlined `+` whose
meaning the previous word just changed. RFC-0004's `Opaque` classifies *stack
depth*; it says nothing about *name meaning*, and nothing else in this RFC
does either. Q34 is the stack-observation instance of the same shape — a
`Fixed` effect understating what a word does — and this is the name-table
instance.

**Where the fragment for a name comes from is also unstated.** §S6 says "a word
may carry an optional BundIR fragment". Nothing does: the fragments are free
functions (`int_add`, `dup`, `drop_top` in
`crates/bund2-stdlib/src/fragments.rs`), no registry slot has a field for one,
and `bund2-api` depends on `bund2-value` alone. So either the slot grows an
`Option<Fragment>` — which puts a `bund2-ir` type on `bund2-api`'s stable
surface, and D9's amendment says external packages get "`Native` with a
declared effect and no more" — or `bund2-jit` keeps a name → fragment table,
which reopens §S4's "which resolution?" question for every inlined site.

**Required:**

1. A **meaning guard** on every inlined fragment. Check that the name still
   resolves to the native whose arm was inlined — one load and compare
   against the slot, which is already guard-and-branch shaped (§S5), with the
   slot call as the generic branch. Re-check after any site that can change
   meaning: opaque sites **and** `register`/`unregister`/`alias` and command
   registration.
2. Say where the name → fragment association lives, and whether `bund2-api`
   carries a `Fragment` type.
3. Extend **criterion 5** to inlined words, not only called ones, and add a
   Preservation row. As written, criterion 5 would pass on a called word while
   failing on every inlined one.
4. Withdraw "every risky part belongs to promotion". Inlining carries the
   redefinition risk; promotion carries the stack-visibility risk. Both are
   real, and the staging argument must weigh both.

### B2 — the measurement that set the staging does not measure a fragment

§S6's staging decision — "fragments that inline first, promotion second" — and
criterion 10's stop rule — "If the inlining half comes in under 2× … a reason
to stop" — both rest on the `inlined` column:

| | `tier0` | `inlined` | `promoted` |
|---|---|---|---|
| `Int + Int` | 68.2 ns | **16.3 ns** | **6.6 ns** |

The `tier0` program is `0 1 + 1 + 1 + …` — each step pushes the literal `1`,
dispatches `+`, pulls two and pushes one. The `inlined` shape is this
(`crates/bund2-bench/benches/fragment.rs`, `int_add/inlined`):

```rust
let a = i.pull().and_then(|v| v.as_int());
if let Some(a) = a {
    i.push(BundValue::int(a + 1));
}
```

One pull and one push. **The literal `1` is never pushed and never pulled — it
has been folded into the arm as a constant.** That is not what the fragment
does. `fragments::int_add()` is `PopInt, PopInt, AddInt, PushInt` behind
`Guard::TopAreInt(2)`, and `Op` has **no immediate operand**, so a fragment
*cannot* fold a constant. The column reports a shape the representation built
in the same revision cannot express.

The cost of what was removed is on record in this RFC. §S1's update prices a
literal push, with no dispatch, at **13.2 ns** (`dispatch/literal_only`) —
about a fifth of the `tier0` figure, and most of the `inlined` one. The guard
is also absent: the benchmark tests `as_int()` on the pulled value, where
`frag::run` peeks, snapshots the stack and calls `admits` before touching
anything.

The `dup_drop/inlined` shape is faithful — peek, `push(top.dup())`, pull —
and its 4.8× is the better evidence. But it is the arm with no operand work
at all, which is the case least like the rest of the language.

**`frag::run` exists to answer exactly this, and is not used.** Its module
doc:

> Its purpose is to make the representation testable and to measure the
> consumer's half of §S6's ceiling before a lowering is written.

Nothing in `crates/bund2-bench/benches/fragment.rs` calls `frag::run` or any
function in `bund2_stdlib::fragments`.

**The quoted ranges also disagree with the table they summarise.** §S6's prose
(the "Inlining alone is 3.8–5.4×" and "Promotion adds 2.6–2.7×" bullets),
criterion 10, `crates/bund2-ir/src/fragment.rs`'s module doc and Q33 all quote
**3.8–5.4× / 2.6–2.7×**. The table beside the prose reads **4.2× / 4.8×** and
**2.5× / 2.7×**. The RFC's own footnote withdraws 5.4× as a measurement of
`push(clone)`, and then quotes it three more times. Q33's register row carries
a third set of raw numbers (`Int + Int` 59.5 → 15.5 → 6.1, `dup drop`
86.0 → 15.9 → 5.9) that match neither. (Re-derived from the table: 68.2/16.3
= 4.18, 92.0/19.0 = 4.84, 16.3/6.6 = 2.47, 19.0/6.9 = 2.75 — the last rounds
to 2.8, not 2.7.)

**Required:** re-measure `inlined` by running `frag::run(&mut i,
&fragments::int_add())` over a stack the literal was pushed onto, so the
column is the fragment rather than a hand-optimised stand-in. Then restate
§S6's staging and criterion 10's 2× threshold against that number. If
constant folding is wanted, it is a separate `Op` and a separate claim. Quote
one set of numbers everywhere, with the command and date that produced it.

### B3 — §S6's measurements were deleted, and five places still cite them

The `-3` review re-derived a §S6 table: 116 call sites, 61 whose effect is not
a fixed pair, 55 with no effect, and ten rows from `!` 32 down. **That table,
the re-derivation command, and the sentence "What is promotable is the
straight-line run before the first opaque site" are gone from the current
text.** The references to them are not:

| RFC text | points at |
|---|---|
| §S5: whole-body exclusion "is measured to be ruinous (§S6)" | nothing in §S6 |
| §S6: "§S6 measures **61** such sites in the corpus, with `!` at 32" | itself; no table |
| §S6: "**`Opaque` effects**, per the table above" | no table above |
| criterion 9: "(RFC-0004's original reading, §S6 measures what that costs)" | nothing |
| criterion 13: "§S6 measures **55 sites** whose word declares no effect" | nothing |
| criterion 14: "§S6's second hole" | no first or second hole in §S6 |

(The line numbers are omitted deliberately. The same phrases can be found with
`grep -n` against the file.)

**The numbers are also stale.** Re-run with the command `-3` used, against
today's `bund2 check`:

```
$ for f in $(find reference/Bund/examples reference/Bund/tests tests/probes \
                  -name '*.bund' -not -path '*/features/*'); do
    ./target/debug/bund2 check --file "$PWD/$f" | grep -E '^ +[0-9]+ +`'
  done
```

gives **113** sites, **63** not a fixed pair, and **50** therefore without an
effect. The opaque list is `!` 32, `times` 7, **`if` 7**, `loop` 5, `graph!`
5, `?true*` 2, `pull.` 1, `map` 1, **`#` 1**, `?true` 1, `?.` 1. `if` moved
from 6 to 7, and `#` is new. That is expected — words landed, effects were
declared — and it is why a number with no derivation beside it rots.

**Why this is blocking rather than editorial:** RFC-0004 is **Accepted**, and
its 2026-09-09 amendment withdrew an accepted sentence on the strength of this
measurement ("measured to be ruinous" in
`docs/rfc/RFC-0004-stack-effects.md`'s amendment). The measurement that
licensed amending an accepted RFC now exists in neither document. RFC-0004's
amendment also carries **its own, third, set of figures** — "abandons at 55
opaque sites, and 18 of them are ordinary control flow: `times` 7, `if` 6,
`loop` 5" and "the 160 corpus programs and probes" — which contradicts
RFC-0005's 61-opaque / 55-absent split. It names the tool `cargo xtask check`,
which is `bund2 check`. And it locates "§S6's win" in "the straight-line
region before the site", which RFC-0005 §S6 has since reversed in favour of
inlining.

**Conformance is stale too.** The RFC says **73/86, ceiling 79/86** in the §S1
update ("Conformance did not move — 73/86"), in §S10 ("Criterion 2 has run:
73/86 with the feature on"), in the criteria preamble, and in criterion 2

  CEILING      79/86   (0 golden(s) still to reach it)

Criterion 2's invariant — both builds agree, N/M and CEILING — **holds**, and
now demonstrably, which is `-3` B1 resolved. But every quoted value is wrong,
and `conform` also reports "above baseline (73); record it with `cargo xtask
conform --accept`": the baseline file itself lags.

**Required:** restore §S6's measurement with its command, or remove every
reference to it. Restate conformance at 79/86. Raise RFC-0004's stale figures
with the owner, because an accepted RFC's amendment is not this RFC's to edit.

## 2. Significant

### S1 — D32 says arithmetic averages `q`; the code and the reference say it does not; no register records the conflict

§S6 describes `numeric_op` as handling "int, float, mixed kinds, LIST append,
string concatenation, division by zero **and `q` averaging**", and describes
the `+` fragment as covering "`Int + Int → Int` **plus D32's `q` average**".
Criterion 16 makes `q` the headline of the differential test.

D32 (RESOLVED) states:

> Arithmetic averages it: `q(a ⊕ b) = (q(a) + q(b)) / 2`, matching `calc_q`.

and grounds it on `calc_q` "reached from `impl Add` at
`reference/rust_dynamic/src/math.rs:416-420`".

The shipped code states the opposite, at the head of
`crates/bund2-stdlib/src/math.rs`:

> `q` is **not** averaged by arithmetic. `numeric_op` builds a fresh value and
> `calc_q` (`reference/rust_dynamic/src/q.rs:4`) is never called from
> `math.rs`, so a result carries the default 100.0. Confirmed by probe

**The reference sides with the code.** I followed the call:

- `+` is `stdlib_add_inline` → `stdlib_math_op_inline(…, Ops::Add, …)`
  (`reference/rust_multistackvm/src/stdlib/math/add.rs:6-8`).
- `math_op` calls `Value::numeric_op(mop, value1, value2)` directly and
  pushes the result
  (`reference/rust_multistackvm/src/stdlib/math/math_op.rs:7-19`).
- The averaging lives in `impl Add for Value`
  (`reference/rust_dynamic/src/math.rs:413-424`), a Rust operator overload
  that wraps `numeric_op` and sets `q` on the result. The word does not go
  through it.
- `calc_q` (`reference/rust_dynamic/src/q.rs:4-7`) has **no caller** in
  `rust_dynamic`.

So D32's premise — "`calc_q` averages it on every arithmetic operation" — is
grounded on a path the language's `+` does not take. The only mention of
averaging in any register is D32's own. This is the "claim about what a
function does, not grounded until its callees are read" failure CLAUDE.md
names, in a resolved decision rather than in this RFC.

It matters here for three reasons:

1. The RFC's sentence about `numeric_op` is **false** as written, by the
   code's own statement.
2. `fragments.rs` concludes "`Int + Int` needs no `q` arithmetic" for a
   different reason: the guard admits only unboxed scalars, whose `q` is the
   100.0 fixpoint. That reasoning is sound, but it makes **`TopAreInt`
   excluding boxed values** load-bearing for `q` correctness, and the RFC does
   not say so. A later guard widened to boxed ints (to cover a value with an
   `attr`, say) would silently need averaging — if D32 is right.
3. Criterion 16's `q` assertion, on this arm, **cannot fail**: both sides
   produce unboxed ints at 100.0.

**Required:** do not resolve it here — it is the owner's. Record the conflict
as an open question (or as a D32 amendment for the owner), and have §S6 state
the guard-excludes-boxed invariant as what currently makes `q` free.

### S2 — criterion 16's test is not the test criterion 16 describes

Criterion 16:

> So the test is **generated over the arm's declared domain** rather than
> written by hand, and the arm's domain is what the guard in §S5 admits.

The test (`the_int_add_arm_agrees_with_the_word` in
`crates/bund2-stdlib/src/fragments.rs`) is an eleven-element hand-picked
array — `0, 1, -1, 2, -2, 7, 42, -42, 1000, i32::MAX, i32::MIN` — crossed
with itself. Its doc comment says "Generated over the arm's domain, not
hand-picked". It is hand-picked.

**It omits the one boundary that matters for this arm.** `Op::AddInt` is
documented as "wrapping — the reference's `i64` arithmetic (D4)". `i64::MAX`
and `i64::MIN` are absent, so the test never exercises wrap-around — the
place where a lowering using `iadd` with an overflow trap, or a checked add,
would part company with the word.

**The `dup` half cannot detect what the RFC says it caught.** The RFC's
footnote says the differential test caught a benchmark doing `push(clone)`
instead of `dup`, which is F13's fresh-identity property. The current test,
`the_dup_and_drop_arms_agree_with_their_words`, compares renders after
`norm()`, and `norm()` replaces every `id: "…"` with `<id>`. Two values
sharing one identity and two values with distinct identities normalise to the
same text. Whatever caught the defect, **this test as it stands asserts
nothing about identity.** It should assert that the two ids differ, or that
they are not the same `Rc`.

**And the thing criterion 16 needs to test does not exist yet.** The test
compares the word against `frag::run`, the interpreter of the fragment. The
code that will run is the CLIF lowering. Nothing requires the lowering to
agree with `frag::run` or with the word, so criterion 16 as implemented
certifies the model and not the compiled code. It needs a third leg — lowered
code against `frag::run` over the same domain — added once a lowering exists.

### S3 — `frag::run` returns `false` for two different things, and one of them has already moved the stack

`frag::run`'s contract:

> Returns `false` **without touching the stack** if the guard does not admit
> it, so the caller can fall through to the word.

Its op loop also returns `false` *after* the guard has admitted and ops have
already pulled: `PopInt` on a `None` or non-int, and `PushInt`, `AddInt` or
`SubInt` with an out-of-range register. By then `PopInt` has consumed
operands. A caller honouring the contract — fall through to the word — runs
`+` on a stack missing the values it was about to add.

The comments call these unreachable ("an `Op` list and a `Guard` are separate
data and nothing structurally ties them"). That is exactly the case D37 and
CLAUDE.md route to `Error::internal`, not to a return value that means "fine,
run the word instead". The RFC's asserted property — "A declined guard leaves
the stack untouched" — is tested only for declines at the guard
(`a_declined_guard_does_not_disturb_the_stack`).

For the RFC, the question is general: **what does compiled code do when an op
after the guard fails?** §S5 answers for the guard and is silent after it.
Either make it structural (validate `ops` against `guard` and `registers` when
a `Fragment` is built, so a malformed one cannot exist), or specify that a
post-guard failure is an internal error with a Bund location.

### S4 — the `autoadd` guard has no criterion and, today, no trigger

§S4 requires compiled code to "guard on `autoadd` at entry and decline to run
when it is set", and the Preservation table lists that guard as the answer to
a row. No acceptance criterion checks it. Criteria 3–16 cover the cache,
indirection, redefinition, caps, benchmarks, cite, sync, dispatch share,
depth, stack tag, absent effect, overreach, dependency direction and
fragments — not `autoadd`.

It is also not currently testable end to end. `bund2 words` lists neither `:`
nor `;`. `Interp` carries an `autoadd` field
(`crates/bund2-interp/src/lib.rs`) and the parser recognises `:` as a
`Term::Command`, but no word sets the flag. The RFC should say that the guard
covers a mode no Bund2 program can yet enter, and name the criterion that
activates when `:` and `;` are bound. Otherwise the guard will be built,
never exercised, and assumed.

### S5 — criterion 8 is still vacuous for §S4's thirteen citations **[carried]**

`-3` S1 found that §S4's table and prose cite `multistackvm_apply.rs:13-14`,
`:16-17` … `:59`, `multistackvm_inline.rs:69-75`, `:41-67` and `:29` without a
recognised prefix, so `cargo xtask cite` cannot see them. The tool has since
learned bare `:N` continuations. **It does not help here**, for two reasons
visible in `xtask/src/cite/mod.rs`:

- **A blank line ends the scope** (the comment on `last_path`). §S4's table
  follows a blank line, so no path is in scope when it begins.
- **An unprefixed filename never enters scope**, so
  `multistackvm_apply.rs:13-14` cannot seed the `:16-17` that follows. The
  tool's own comment on the bare-citation branch concedes this: "the
  documents use a *second* shorthand the extractor cannot see either — a bare
  filename".

`cargo xtask cite` exits 0 and names RFC-0005 nowhere in its output. I opened
all thirteen by hand, and all thirteen are correct (§3). Criterion 8's "was
vacuous as first written and is not now" still overstates it. The fix is
still the five-minute one: spell the `reference/rust_multistackvm/src/`
prefix.

### S6 — criterion 2's "all five subcommands share one builder" is not so

Criterion 2:

> All five subcommands that measure the binary now share one builder
> (`xtask/src/buildcli/mod.rs`)

Four do: `conform`, `bench`, `corpus`/`coverage` and `effects` call
`crate::buildcli::bund2`. **`depth` does not** — it keeps its own
`build_bund2` in `xtask/src/depth/mod.rs`, which builds `--release` where
`buildcli` builds dev for `conform`. `buildcli`'s module doc makes the same
five-way claim, and names `depth` among the five.

This matters for the criteria because criterion 11 is `depth`, and a separate
builder is where `-3` found the drift that became a false claim. It also
means criterion 2 and criterion 11 measure **different profiles** of the
tier: dev for conformance, release for depth. Nothing in the RFC says so, and
a compiled tier whose Rust helpers behave differently under debug assertions
is exactly what that split would hide.

### S7 — header and §S10 restate the reading of D9 that D9's amendment withdrew

The header lists "**D9** (no third-party CLIF lowerings; `Intrinsic` stays
internal)", and §S10 closes with "**D9 applies**: no third-party CLIF
lowerings; `Intrinsic` stays internal to `bund2-stdlib`".

D9's amendment of 2026-09-09 says that sentence "has been read as deciding
**where Bund2's own lowerings may live**. It does not", and that the binding
constraint is "**no Cranelift type may appear in `bund2-stdlib` or
`bund2-api`**". §S6 of this RFC says the same, and says `Intrinsic` "appears
nowhere in `crates/`". The document now carries both readings. The header
and §S10 should quote the amended constraint.

### S8 — Preservation rows cite mechanisms their sections do not contain

- The sync row: "the sync writes through the same path `Stack::push` uses,
  not a bare `push_back` (§S5)". §S5 says values "are synced back to the real
  stack" and nothing about the path. Same shape as the `unregister`-stub row
  **[carried, `-3` S5]**, which is also still unaddressed: §S4 contains no
  stub.
- The alias row: "slots key on the resolved name (§S4), **except for `$`** —
  see below". Nothing below in the table addresses `$`.

### S9 — register rows that contradict the RFC **[mostly carried]**

- **Q29** still closes "so dispatch is the dominant term", and D41's
  "Implemented" section says the same, with 10.1 ns against the RFC's 9.8
  **[carried, `-3` S4 and `-2` S2]**. §S1 retracts that sentence.
- **Q31** still says "`--features jit`/`aot` build in all four crates"
  **[carried, `-3` S2]**. The feature is now declared in five: `bund2-jit`,
  `bund2-runtime`, `bund2`, `bund2-cli` and `bund2-bench`. I built
  `cargo check -p bund2-bench --features aot` clean. §S10's list omits the
  umbrella `bund2` crate.
- **Q33**'s numbers differ from the RFC's table (B2).
- The RFC's **Open questions** section still presents Q25 as blocking
  ("this RFC is blocked on it") **[carried, `-2` B4]**, while §S1 and the
  register say D41 answered it.

### S10 — three statements of the gate's status

The Status line says "Half the gate is met and half is not". §S1's heading
still reads "**The gate, measured — and it does not pass**". §S1's update is
headed "**the gate is met**" and then says prerequisite 2 "is not settled".
Each is defensible in context, but a reader skimming headings gets "does not
pass" and then "is met". The heading should say what the Status line says.

The Status line also names "**§S8's frame consumption**" as "the outstanding
blocker". §S8 now specifies a headroom guard and criterion 11. If the guard
resolves the blocker, the Status line should say so. If it does not, because
the check's mechanism is unspecified (see §7.8), the Status line should say
that instead.

## 7. What the RFC assumes and does not state

1. **That a name's meaning at compile time is its meaning for the life of the
   compiled code.** B1. It is the assumption §S4 was written to refuse, and
   §S6 reintroduces it.
2. **Where the name → fragment association lives**, and whether `bund2-api`
   exposes a `Fragment` (B1).
3. **That `TopAreInt` excluding boxed values is what makes `q` free** (S1).
4. **That `frag::run`'s pull order is the semantics a lowering must match.**
   `fragments.rs` says "the *pulls* must still happen in the word's order or a
   failure mid-arm would leave a different stack". That is a lowering
   obligation stated only in a code comment.
5. **That a fragment's register numbering is obvious.** `PopInt` does
   `rotate_right` and writes slot 0, so after two pops slot 0 holds the
   *second* value and slot 1 the top. `numeric_op` takes the top as the left
   operand (`crates/bund2-stdlib/src/math.rs`'s header: "`3 5 -` asks for
   `5 - 3`"). `Op::SubInt` exists with no fragment using it — against
   `Op`'s own rule that "an operation with no fragment using it is a lowering
   nobody has tested" — and a `-` fragment written as
   `SubInt { dst: 0, a: 0, b: 1 }` by analogy with `int_add` would compute the
   reverse of the word. Commutativity is what hides this in `+`.
6. **That Tier 0 is flat for every path a compiled body will call back
   through.** §S8's "the interpreter is flat, so declining recovers the
   RFC-0003 guarantee" holds for direct calls. But `eval_body`, which natives
   such as `times`, `loop` and `map` use, pushes a frame and calls `run_to` —
   one Rust frame per nesting (`crates/bund2-interp/src/lib.rs`, `eval_body`).
   A compiled body calling such a word, whose lambda calls a compiled body,
   alternates Rust frames. The headroom guard's threshold has to cover that,
   and criterion 11's self-recursive word does not exercise it.
7. **That dispatch costs the same for every word** **[carried, `-3` §7.1]**.
8. **That a stack-headroom check is expressible** without a crate D10 or D38
   would have to rule on **[carried, `-3` §7.9]**.
9. **That AOT conformance is RFC-0006's** **[carried, `-3` §7.7]**. It still
   needs one sentence.

## 8. Recommendation

**Stay Draft.** The prototype was the right move, and it found something
true: operand-free arms like `dup drop` gain a lot from inlining alone. But
the revision drew two conclusions the prototype does not support — that
inlining is the risk-free half (B1), and that it is a 4× win on arithmetic
(B2) — and it lost the measurement its own amendments rest on (B3).

In order:

1. **B1** — add a meaning guard for inlined fragments, say where fragments
   attach to names, and extend criterion 5. This is design, and the rest
   depends on it.
2. **B2** — re-measure `inlined` through `frag::run` and
   `fragments::int_add()`, then restate the staging and criterion 10 against
   that number. One set of figures, with a command.
3. **B3** — restore or remove §S6's site table, restate conformance at
   79/86, and take RFC-0004's divergent figures to the owner.
4. **S1** — record the D32 / `math.rs` contradiction for the owner before any
   fragment for a float or boxed arm is written.
5. **S2–S4** — cheap, and each is a place where a check exists in name only.

§S4's chain, §S7's counter argument and §S8's guard remain sound. Criterion
2 and criterion 15 now demonstrably hold. Nothing in this review challenges
them.
