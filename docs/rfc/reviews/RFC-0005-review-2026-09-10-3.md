Two blockers remain, **both in text new this revision**:

- **B1.** §S8 promises that Tier 0's nesting capacity is *never less* with the

  moves only the second.

## 1. Blocking

### B1 — §S8's two floors: "never less" and "the same" cannot both hold

§S8, *How the guard reads the stack*:

> The thread is spawned at that plus Tier 1's share, so **Tier 0's nesting
> capacity with the tier on is never less than it is with the tier off**.

Criterion 11:

> It also reports the depth at which Tier 0's floor fires, and **that depth
> must be the same with the feature on and off**: the tier's share of the stack
> sits above Tier 0's, never inside it.

Here is what the code does today. `EVAL_STACK` is 8 MiB plus `STACK_RESERVE`
(`crates/bund2-cli/src/main.rs`). `tier0_floor` computes
`top - size + STACK_RESERVE`, so the floor sits 8 MiB below the declared top
(`crates/bund2-interp/src/lib.rs`). §S8 enlarges `size` by Tier 1's share when
the feature is on, and **that moves the Tier 0 floor down by the same amount**.

1. **"The same" fails on a correct implementation.** Take a program that runs
   entirely at Tier 0 under a `--features jit` binary. That covers every body
   below the 64-entry threshold, and every run in which nothing compiles. It
   nests roughly twice as deep before `Vm::eval_lambda` refuses as the same
   program under the default binary does.
2. **Pinning the floor makes "never less" fail.** The alternative keeps the Tier
   0 floor at `top − 8 MiB` whatever the feature. Then compiled frames come out
   of Tier 0's 8 MiB.
3. **"The top part is Tier 1's" describes a permission, not an occupancy.** The
   stack is LIFO. Its outermost frames are Tier 0's: `run_cli`, `Interp::eval`
   and the frame loop. Tier 0 frames sit in the top part whenever compiled
   bodies call natives that re-enter evaluation. The Tier 1 floor says where
   compiled frames may *start*. It does not reserve a region for them. "Sits
   above Tier 0's, never inside it" is therefore not true of any layout. To
   have both properties, the floor would have to move by the bytes that live
   compiled frames hold, and no fixed floor does that.

**Why this blocks and is not wording.** Whether a program reports
`machine stack exhausted`, and how many levels of side effects it performs
first, becomes a property of the feature. `conform` cannot catch it, and no
golden could exist: the oracle aborts (F85). CLAUDE.md's invariant is that the
tier changes speed and not meaning. Either this *is* meaning, and the design
must meet "the same", or it is not, and that is a decision about what a Bund2
program's observable behaviour includes. Taking that decision is the owner's
job, not the RFC's.

The evidence leans towards "not meaning". The exhaustion depth already differs
between Bund2's own builds: `conform` measures the dev profile and `depth` the
release profile, and frame sizes differ between them, as criterion 2 itself
records. Leaning is not deciding, though.

**Not checkable as written, either.** `cargo xtask depth` prints one label per
axis: `Outcome::label` returns `completed`, `reported a Bund-level error`,
`ABORTED`, `TIMED OUT` or `unsupported` (`xtask/src/depth/mod.rs`).
`loop_program` counts down silently. **Nothing reports the depth at which the
floor fires**, although criterion 11 says the tool "also reports" it.

**Required:**
- Take the question to the registers: is the depth at which evaluation reports
  stack exhaustion part of a program's meaning across builds and tiers?
- If it is not, record that decision, restate criterion 11 as "never aborts,
  and Tier 0's capacity is never less", and delete "never inside it".
- If it is, §S8 needs a mechanism that meets "the same", and a fixed floor is
  not one.
- In either case, make `depth`'s `loop` axis print the level it reached, so a
  depth comparison has something to compare.

### B2 — the pre-call generation check reads one slot, and an aliased call resolves through two

§S5, *A fold, or any change of effect, arriving at run time*:

> So before every call **across which any value stays promoted**, compiled code
> compares the call slot's generation cell (§S6, *Addressing*) against the one
> it was compiled with.

§S4, *Two structures*: "A name whose resolution passes through another `Slot` —
an alias — has its call slot point at a resolving trampoline". Generation cells
are per name and mirror that name's `Slot`. Each writer touches only the slot
it writes: `register_alias` touches the alias's slot, and `register_lambda` the
name it binds (`crates/bund2-api/src/lib.rs`, `Registry::register_alias`,
`Registry::register_lambda`).

The stdlib's own aliases make this concrete. `stack.rs` registers `<-` and `←`
for `stacks_left`, and `->` and `→` for `stacks_right`. `conditional.rs`
registers `?` for `conditional`. Now take a compiled body that promotes values
and then calls `<-`, which is `eff(0, 0)`, so every promoted value stays in a
register across it. Before that call, `:stacks_left { … } register` binds a
lambda that consumes two values. Dispatch now resolves `<-` → `stacks_left` →
the lambda, because the lambda outranks the native at step 6 of §S4's chain.
**`<-`'s generation did not move**, so the check passes, and the lambda runs
against a stack with the promoted values missing from it. Tier 0 would have
handed it those values.

§S6 already refuses this shape for *inlining*, with three rules: a direct
resolution only, never against a saturated slot, and the registration
recognised. The pre-call check needs all three and states none:

- **Alias.** Either keep nothing promoted across a call that does not resolve
  through its own slot, or check the generation of every slot on the path.
- **Saturation.** A slot at `u32::MAX` never changes again, so a check compiled
  against it can never fail (`Slot::touch`).
- **`$name`.** It resolves one level shallower (§S4, *The chain*). Say which
  slot's generation its check reads.

This is CLAUDE.md's "follow the call one level further": the check reads the
call slot and stops, while dispatch continues to the target.

**Required:** apply §S6's rules to the pre-call check, add the alias case to
criterion 22, and add a Preservation row.

## 2. Significant

### S1 — the reporter rule rests on a false premise, and in the default configuration it turns off promotion across calls

§S5: "**while the reporter wants stacks, no value stays promoted across a
call.** The reporter is fixed when the `Interp` is built, so this is known at
entry, and costs nothing per call."

- **It is not fixed at build.** `Interp::new` installs `SilentReporter`. The CLI
  replaces it afterwards with `vm.reporter = Box::new(reporter)`
  (`crates/bund2-cli/src/main.rs`, `run`), and the field is `pub`.
  `Reporter::wants_stack` is a trait method, and nothing requires it to be
  constant (`crates/bund2-api/src/diag.rs`). The claim that holds is narrower:
  no `Vm` method reaches the reporter, so it cannot change *while a compiled
  body runs*. State that, and read it at each entry.
- **The default configuration wants stacks.** `TextReporter::wants_stack`
  returns `dump_stack` (`crates/bund2-stdlib/src/report.rs`), which the CLI
  defaults to `true` and turns off only with `--no-dump-stack`. So in every
  `bund2 script` run, which includes every `cargo xtask conform` run, **no value
  is ever promoted across a call.** The consequences go unstated:
  - Criterion 2 with a tier never exercises promotion across a call.
  - Criteria 9 and 10 measure promotion only under a reporter that does not
    want stacks, and neither says which reporter it uses.
  - §S6's promotion ceilings (4.3–4.4×) are figures for `--no-dump-stack` or a
    silent embedder. The default is a straight-line fragment run between two
    calls.
  - `report.rs` anticipates a TUI that "renders the stack in its own pane",
    which suggests the planned front end wants stacks too.

**Required:** correct the premise; state what promotion is in the default
configuration; name the reporter in criteria 9 and 10. If the owner wants
promotion in the default configuration, the design needs another answer, for
example a sync before any call to a native that can report. That would be a
different cost, and criterion 9 would have to measure it.

### S3 — the `:`/`;` count does not say what the RFC says

§S4: "The corpus barely exercises this — one program uses `:` or `;` as a
word, `reference/Bund/examples/code_snippets/textexpression_demo.bund`, found by
`grep -lE …`".

Run today, the command matches **two** files, and **neither uses the word**:

- `textexpression_demo.bund`, lines 7, 12, 17 and 22. Every match is inside a

- `tests/probes/workbench-variants.bund:76`, which is a comment: `// ---
  make.call. and merge. / ++. : plain mirrors, …`.

**No corpus program uses `:` or `;` as a word**, which agrees with Bund2 binding
neither and `conform` sitting at its ceiling. The sentence should say "never",
and the grep should not be offered as evidence for a word count: it cannot tell

### S4 — CONTEXT under `autoadd` is pushed, not collected

§S4 says the reference "collects every value it applies under the mode — calls,
CONTEXT values and literals alike", citing `:19-27`, `:72-73` and `:89-97`.
Criterion 18 asserts that "the calls, **literals** and CONTEXT values after it
are collected rather than dispatched, pushed or switched to".

The three branches do not do the same thing:

- A **CALL** and **any other value** are appended *into* the value beneath:
  `self.stack.push(val.push(value))`
  (`reference/rust_multistackvm/src/multistackvm_apply.rs:22`, `:92`).
- A **CONTEXT** value is pushed as a separate value, `self.stack.push(value)`
  (`reference/rust_multistackvm/src/multistackvm_apply.rs:73`). It is not
  collected.

F84 says this correctly ("A CONTEXT value is pushed instead of switching
stacks"). The RFC and its criterion contradict F84. A probe written to
criterion 18's wording would assert the wrong shape for CONTEXT.

### S5 — the reserve: RFC and code disagree on its purpose, and a Preservation row claims more than a floor can give

- The RFC says "a reserve beneath that floor is kept for reporting the error".
  `STACK_RESERVE`'s doc comment says the reverse: "for the frames between one
  check and the next. **Reporting the error needs none of it**: by the time it
  is reported, the stack has unwound" (`crates/bund2-interp/src/lib.rs`). The
  code gives the right reason.
- That reason implies a bound the RFC never states: **everything a leaf native
  does between two checks fits in 256 KiB.** A native that recurses in Rust on
  the depth of its *data*, rather than on evaluation, is not bounded by the
  floor at all. I have not built a failing program for this, so it is an
  unverified assumption, not a demonstrated defect. Rendering a deeply nested
  value is the kind of case in question. But the Preservation row's "below it a
  Bund-level error, **never an abort**" claims more than a floor on evaluation
  nesting can deliver. Narrow it to "never an abort from evaluation nesting".
- The declared top is `stack_marker()` called inside the spawned closure
  (`crates/bund2-cli/src/main.rs`, `main`). That sits below the true top by the
  thread-entry frames, and on some platforms the requested size includes a
  guard page. Both come out of the reserve. It is small, but the budget should
  say so.

### S6 — the costing no longer adds up

- §S6, *Addressing*, says "**two per call** (epoch, `autoadd`), as costed". §S5's
  new pre-call check adds the callee's generation. That makes **three** for any
  call across which a value stays promoted, and generation cells are now read
  at call sites as well as at inlined sites.
- §S5's "one load and compare per call for each of the two cells" has the same
  gap.
- Criterion 17's 2 ns bound covers inlined sites only. Nothing bounds the
  per-call checks, although a call is far more common than an inlined site in a
  body that promotes.

### S7 — "minted at the same program point as in Tier 0" holds for scalars only

§S5: "A promoted value is observed only after it has been synced, so it is
minted and sampled at the same program point as in Tier 0."

Tier 0 mints identities where nothing observes them. `Stack::push_as` tags a
heap value through `with_tag` (`crates/bund2-interp/src/lib.rs`), and
`with_tag`'s shared arm mints before it splits: `let _ = h.identity();`
(`crates/bund2-value/src/lib.rs`). `mint()` is a process-wide counter (same
file). So Tier 0 mints when it pushes a shared heap value. A promoted heap value
skips that push and is minted later, in a different order relative to other
values.

Today this is unreachable, because `Guard::TopAreInt` admits unboxed scalars
only. Once a guard widens, the argument that survives is the one `with_tag`'s
own doc comment makes: ids are opaque, and F14 normalises them, so mint order is
not meaning. Rest the rule on that, not on "the same program point", which will
stop being true.

### S8 — smaller items

- **There is no REPL.** §S8 says "`bund2 script` and the REPL both do this". The
  CLI's module doc says "no REPL, no `--emit`, no subcommands beyond
  `script --file`" (`crates/bund2-cli/src/main.rs`).
- **D42 does not reach every entry.** §S3 says "D42 carries the key to every
  point where a body starts running", and the Preservation row credits D42 for
  "a conditional". D42 itself keeps `Vm::scoped_call`'s `Vec`, wrapped as a LIST
  built per call. So `context` bodies never have a key and never reach the tier.
  That is not a meaning risk, but the text should say it.
- **Criterion 22 is partly uncheckable.** "Promotes and then fails — once
  through its own op": criterion 19 makes a post-guard op failure impossible to
  construct, so name the op that fails. "Assert nothing is held across a call"
  names no seam that could observe it; criterion 20 has `entry_log`, and this
  needs its equivalent.
- **A `cite` false positive.** The tool flags the RFC's line 329, saying
  `autoadd` is not within three lines of `multistackvm_apply.rs:27`. The cited
  range is `:19-27`, and `autoadd` is at `:19`, so the tool measures from the
  end of a range. That is a tool defect, not an RFC defect.

## 7. What the RFC assumes and does not state

1. **One compiled cache, one `JITModule` and one set of cells per `Interp`.**
   *Addressing* embeds each cell's address as an immediate, "safe … because the
   cells outlive every compiled function: both die with the runtime". That
   holds only if "the runtime" is the `Interp` and the cache belongs to it.
   Values are `Rc` and `!Send`, but two `Interp`s on one thread share them
   freely, as the tests and embedders both do. A thread-wide cache would run
   code that reads another `Interp`'s cells, or freed ones after that `Interp`
   drops. Registration ids are already per `Registry` (§S6), so the fragment
   table is per `Interp` too.
2. **`Reporter::wants_stack` is constant for a run** (S1).
3. **The depth at which exhaustion is reported is not part of a program's
   meaning**, or it is, and §S8 must preserve it (B1).
4. **256 KiB covers a leaf native between two floor checks** (S5).
5. **The residual path's `apply` is `Vm::apply`**, which is synchronous. Each
   value that runs a body costs a Rust frame, so recursion through a residual
   path is bounded by the Tier 1 floor's decline, not by the heap. §S8's
   argument covers this, but the RFC never connects the two sections.
6. **Every call crossed by promotion resolves through one slot** (B2).
