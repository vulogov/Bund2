## Should fix

### S1. `frame.aggregate` does not say when two numeric `by` values are one group

**The RFC says.**
- `frame.aggregate` answers "one row per distinct combination of the `by` columns" (RFC:384).
- Groups are "ordered by the `by` columns as `frame.sort` orders them" (RFC:442-445). `frame.sort` compares "an INTEGER with an INTEGER exactly, and with a FLOAT by exact value" (RFC:361-363).
- A numeric column may mix INTEGER and FLOAT (RFC:248).
- `frame.join` says outright that "numbers match by value (1 matches 1.0)" (RFC:464-465).

**What is left open.** "Distinct" has no stated equality. A `by` column holding INTEGER `1` and FLOAT `1.0`, or `0.0` and `-0.0`, can be:
- one group, as `frame.sort`'s comparison and `frame.join`'s matching suggest, and as Bund's `==` agrees (probed: `1 1.0 == println` and `-0.0 0.0 == println` both print `true`); or
- two groups, as `frame_eq` would tell them apart (RFC:287-289).

If it is one group, the answer's `by` cell can be `1` or `1.0`, and `0.0` or `-0.0`. The same choice decides the group's text in S8 (RFC:688), whose number is shown "as Bund prints" it. `frame_eq` compares that cell by type and by `to_bits`, so criterion 5's test has to know.

**Why it matters.** An implementer must invent the equality and the representative. Two implementers would produce frames that `frame_eq` tells apart. No criterion covers it: criterion 5 groups by a factor and a string column only (RFC:798).

**Suggested fix.** One sentence in S5, marked **[author]**: "Two `by` values are one group when `frame.sort` compares them equal; the group's cell in the answer, and in its text, is the first of them in row order." Add one case to criterion 5: a `by` column holding `1` and `1.0`, answering one group with INTEGER `1`. If two groups are wanted instead, say that.

### S2. The group text is unbounded, against `CLAUDE.md:89`

**The RFC says** (RFC:688): a group is `group [ <k1> <k2> … ]`, "a STRING or factor level in double quotes, … every key shown".

**The rule.** "Values in a report use `BundValue::summary`, which is bounded" (`CLAUDE.md:89`, citing D36). `summary` truncates a STRING to the width it is given (`bund2-value/src/lib.rs:1667`). RFC-0015's family passes `WIDTH`, 40 (`operand.rs:21`, `:56`). As written, a `by` column of free text yields a refusal as long as the text. A STRING key holding `"` or a line break is printed raw, so the refusal can break across lines and its quoting becomes ambiguous.

The sixth review's suggestion praised not capping the *number* of keys at four, which is a different bound. Showing every key is fine if each key is bounded.

**The same gap in three other texts.**
- `field "…"` in the non-finite and beyond-i64 rows (RFC:696-697). An unquoted run of digits of any length matches `is_int` (`data.rs:101-103`).
- `"b"` after a closing quote (RFC:695).
- Column and header names quoted in many rows.

These interpolate program text with no stated bound.

**Suggested fix.** In S8's preamble (RFC:659-661), say that every interpolated cell, field or name is rendered as `summary(WIDTH)` renders a STRING: quoted, and truncated with `…`. If `NONE` is kept in place of `summary`'s `none`, say so. The group row can then keep "every key shown".

## Notes

**N1. The group row points at the wrong rows.** "How a group is named, in this row and the one above" (RFC:688) is itself row 688. So "this row and the one above" means 688 and 687. The texts that name a group are 686 (too few cells) and 687 (E114). Write "in the two rows above". Separately, row 686 shows `has 1 value`. The emptied group of RFC:432-434 would read `has 0 values` or `has 0 value`. Say that the noun agrees with the count.

**N2. S2's new sentence and the frame check's mixture texts disagree.** RFC:254-256 makes a column in `levels` a factor "whatever its cells". The check's texts still read a column's kind from "its first non-NONE cell's" (RFC:263), and row 10 (RFC:674) fires on any number beside a STRING. Two cases follow:
- A column in `levels` holding `1` and a valid level `"a"` is refused by row 10 as `column "g" is not a LIST of numbers: "a" at row 2`. That blames the valid cell and calls a factor numeric.
- A column in `levels` whose first cell is `true` reads `the column is logical`.

Say that, for a column in `levels`, any cell that is not one of its levels is row 11's `not one of its levels`, and that rows 10 and 11's mixture rules apply only outside `levels`. Criterion 2 tests one rule at a time, so it does not reach this. A malformed factor column is exactly what a hand-built frame produces.

**N3. Three criterion cases the sixth review asked for are still absent.**
- Criterion 5: a zero-row frame with a factor column under `"mean"`. This is the case S2 of that review decided. RFC:810 tests only "a frame of no rows".
- Criterion 4: `frame.factor` on a factor with a custom level order, keeping that order (RFC:792).
- Criterion 8: two trailing empty cells (RFC:860-861).

Each is a sentence.

**N4. The author list is stale in two places.**
- RFC:924-925 lists a repeated name as E101 in `frame.select`, `frame.sort`, and a `by` of `frame.aggregate` or `frame.join`. S4 now extends that to `frame.complete`, `frame.matrix`, `factors` and `descending` (RFC:349-353).
- RFC:927 still says "`frame.factor` recomputes a factor's levels". RFC:960-961 and S4 (RFC:368-372) say it keeps their order and drops the unused ones. "Recomputes" was the reading the sixth review's N11 flagged.

Update RFC:924-925 and drop "recomputes" from RFC:927.

**N5. Q64 still reads "RFC-0017 RFC-0017 recommends"** (`open-questions.md:14`). The entry was edited in this revision (the N1 ranges), so this was its next touch. The register is append-only, but a doubled word in an entry's own text is a typo, not a deletion.

**N6. §Differences from R omits `fill`.** `read.csv` defaults to `fill = TRUE` (`readtable.R:299`): "If TRUE then in case the rows have unequal length, blank fields are implicitly added" (`read.table.Rd:159-160`). The RFC refuses a ragged row with E102 **[author]** (RFC:520-521). A reader coming from R meets this beside the blank-line difference the section already lists (RFC:1003-1008). One bullet would cover it.

**N7. `frame.factor`'s R claim cites Q64, which does not make it.** RFC:370-371 says a factor's `order` follows its levels, citing "Q64". Q64 cites `sort.Rd:61-63` (character collation) only. The sentence that says it is `sort.Rd:64-65`: "The sort order for factors is the order of their levels". Cite that line, which the sixth review's N11 quoted.

**N8. An overflowing literal is a non-finite field too.** `1e400` matches `is_float`'s exponent arm and parses to +∞. Probed: a column `1.5`, `1e400` through `csv` answers `[ 1.5 ::  inf :: ]`. D255 ("parses to NaN or ±∞", `decisions.md:17459`) and RFC:567 ("a field that parses to") cover it. RFC:568's examples (`NaN`, `inf`, `-inf`, `+inf`) and criterion 6 do not, and the refusal's advice to list the field in `na` reads oddly for it. Add `1e400` to the examples and to criterion 6.

**N9. `describe.rs`'s module doc becomes wrong by construction.** Once `amean` calls `mean` (RFC:414-417), the doc's "the two may differ in the last bit" (`describe.rs:5-6`) contradicts the code that the RFC's own Preservation row describes (RFC:709). Say in S5 that the sentence is corrected in the same change.

**N10. S4's list of words that refuse an absent name is partial.** RFC:348-350 names `frame.column`, `.select`, `.complete`, `.sort` and `.factor`. It omits:
- `frame.factor.levels`'s `name`;
- `frame.matrix`'s `names`;
- `frame.aggregate`'s `by` and the columns in `stats`;
- `frame.join`'s `by`, where the text should also say which frame lacks the key.

S8's generic row (RFC:679) covers the code. Extend the list, and give `frame.join`'s text a frame, for example `no column "id" in right`.

**N11. "A byte after a closing quote" shows `"b"` without saying which bytes.** For `"a"bcd,` the text could show `b`, `bcd`, or the rest of the line. For a non-ASCII byte, the RFC does not say whether the whole character or the byte is shown (RFC:695). Say "the first character after it".

## What the RFC assumes and does not state

- **That `file`'s path is absolute.** RFC:488 writes `"path" file` (carried from the fourth review).
- **That `file` reaches only the file system.** It also fetches over HTTP (`host.rs:1455-1456`, the `Target::Http` arm). "No new I/O" holds, but `frame.csv.parse` can parse fetched text (carried).
- **How `frame.filter` reaches the bridge.** This sharpens the carried point. `dynamics.rs`'s `call` is `pub(super)` (`dynamics.rs:53`). It also reads back "a LIST of `n` finite numbers" (`:64-79`), so it cannot serve a BOOL predicate even if made visible. `frame.filter` has to call `crate::kb::bridge::ask` directly (`kb/bridge.rs:104`, `pub`) and do its own E112 check. "As `ode.rk4` runs its model" (RFC:355-356) is true of the bridge, not of `call`.
- **The order of refusals across checks** (carried):
  - the frame check against other operand checks;
  - inside `frame.csv.parse`, tokenising faults (quotes, width) against inference faults (NaN, beyond i64), and both against the frame check's E103 for a quoted number in a numeric column.
- **How an `na` string is matched**: exact bytes, case-sensitive, with no whitespace trimmed. This is natural, but unstated. R trims only when `strip.white` is set, and its default is `FALSE` (`readtable.R:71`).
- **That a final line without a terminator is a record.** It follows from "it ends at … the end of the text" for a quoted field (RFC:508-509), but RFC:515-516 states only terminated lines.
- **That `frame.text` of a frame with columns and no rows prints its header row alone** (carried).
- **That a row MAP per row in `frame.filter` and `frame.rows` is affordable at Tier 0** (carried; RFC:377-378 says only "bounded").
