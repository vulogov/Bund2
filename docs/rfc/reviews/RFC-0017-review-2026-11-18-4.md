## Should fix

### SF1. "Keys are checked in sorted order" cannot hold for `frame.csv.parse`'s `factors`

**What the RFC says.** S1 says "keys are checked in the MAP's sorted order and the first bad one is the refusal" (RFC:223-225). For `frame.csv.parse`, `factors` sorts before `header`, `na` and `sep`.

**Where it fails.** Some of `factors`' faults can only be found after the text is parsed:
- a name that is not a column (row 764 with `opts`, RFC:538);
- a numeric or logical column (row 766 with `opts`).

Parsing needs `header`, `na` and `sep` already read and valid. So for `{ factors: [ "z" ] sep: ";;" }` the rule as written says `factors` wins, but no implementation can know that `"z"` is not a column without a valid `sep`. An implementation has to read `factors`' type first and check it against the columns later.

**Where implementers would differ.** The rule does not say which of `factors`' checks run in key order. For `{ factors: [ 1 ] header: 1 }` or `{ factors: [ "x" "x" ] sep: ";;" }`:
- one implementer checks every option's shape in sorted order and refuses for `factors`;
- another checks all of `factors` after the parse and refuses for `header` or `sep`.

Criterion 6's "two bad keys refused for the first in sorted order" (RFC:952) does not name the pair, so a test author can pick a pair the rule cannot satisfy.

**Fix.** One sentence in S1: the sorted order covers each key's type, range and repeats within a LIST. The checks against the frame (`factors` naming a missing, numeric or logical column) come after the text is parsed and checked. Name criterion 6's pair, for example `{ header: 1 sep: ";;" }` refused for `header`.

### SF2. Row 762's operand list stops short of three operands

Row 762 lists `names`, `by`, `rows`, `stats`, `levels`, `columns` and `name`. Three operand faults still have no row or two candidate texts:
- **`frame.filter`'s `lambda` not a LAMBDA.** No row covers it. `ask` takes a body slice (`kb/bridge.rs`, `ask`), so the word must refuse a non-lambda itself. `dynamics.rs`'s `lambda` helper refuses with `domain(word, operand, v.summary(WIDTH))`, which is row 762's text, but the row does not name the operand.
- **`frame.with`'s `list` not a LIST.** Row 762 omits `list`. The preamble maps `frame.with`'s cell faults to `list` (RFC:707-708), which leads to row 753: `list is outside frame.with's domain: column "dose" is 7`. Row 762's form would give `list is outside frame.with's domain: 7`. Two implementers can write either.
- **A `names` or `by` LIST holding a non-STRING** (`[ 1 ] frame.select`). Row 762 covers only "not a LIST". Row 764's `no column …` with the renderer gives `no column 1`, and row 762 applied to the whole operand gives `[ 1 :: ]`. Either is plausible, and only criterion 9's code-only palette reaches the case. `factors` and `descending` entries already fall under row 786's wrong value, and `levels` entries under row 767.

**Fix.** Add `lambda` not a LAMBDA, `list` not a LIST, and "a `names` or `by` entry not a STRING" to row 762's parenthesis.

## Notes

**N1. Row 786's "any other value as `summary` shows it" breaks RFC:732-733's guarantee.** RFC:731-733 renders only numbers, BOOLs and NONE through `summary`, and concludes "so no interpolated value is unbounded or breaks a line". Row 786 now sends any non-STRING option value through `summary`. `summarise` recurses into a LIST and emits a STRING item quoted and truncated but not escaped (`bund2-value/src/lib.rs`, `summarise`, the `Str` arm). So `{ factors: [ 1 "a<LF>b" ] }` or `{ how: [ "a<LF>b" ] }` prints a line break inside the refusal. This is the residue of `-3.md`'s N2. Either:
- say the option value is `<summary>` in RFC:737-742's sense, bounded and not escaped, and narrow RFC:732-733 to "no value the renderer interpolates"; or
- render a LIST value's STRING items with the renderer.

**N2. Two leftovers from row 762.**
- The preamble's "for `frame.with`, `name` for the new name" (RFC:707) now maps to no reachable row. Every fault of the new name is row 762, and criterion 4 pins that. Dropping the clause stops an implementer from looking for the numbered form.
- Row 762 is a choice no ruling names: the wrong-type template, and `frame.with`'s empty name checked as an operand fault, not by the frame check. It has no `[author]` mark and no entry in the list at RFC:1019-1102.

**N3. The not-taken text differs from `opts.rs` in its wording too, not only in where the key sits.** `opts.rs` writes `the key "k", which this word does not take`; row 786 writes `a key "k" <w> does not take`. The `[author]` entry (RFC:1078-1080) records only "the key leading the wrong-value text". Either reuse `opts.rs`'s phrase or widen the entry.

## What the RFC assumes and does not state

- **Which option checks the sorted order covers**, and that `factors`' column checks come after parsing (SF1).
- **That an empty `na`, `factors` or `descending` LIST is valid.** `na: []` would mean nothing is missing. This is natural, but unstated.
- **What E112 says when `frame.filter`'s lambda leaves nothing** (carried). `ask` answers `None` for an empty scratch stack, and `call` writes `left nothing`.
- **That a final line without a terminator is a record** (carried).
- **That an `na` string matches by exact bytes**, case-sensitive and untrimmed (carried).
- **That `frame.text` of a frame with columns and no rows prints its header row alone** (carried).
- **That a row MAP per row in `frame.filter` and `frame.rows` is affordable at Tier 0** (carried).
