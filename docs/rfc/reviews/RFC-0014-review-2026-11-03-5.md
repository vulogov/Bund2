# RFC-0014 review: Draft revision 13, 2026-11-03 (twelfth review)

Adversarial review, independent of the eleven before it. The RFC and the
sources were read first, and the earlier reviews only afterwards, to drop
findings already raised and answered. Nothing was edited or built, apart
from running `cargo xtask cite`. Read against Bund2's working tree at
d33e7ef, the `reference/` submodules (whose `git status` is empty), and
SMYSL at 4f5ecb9 ("Merge 1.14.0"), opened file by file. SMYSL citations
are relative to its crate directory, as the RFC writes them.

Revisions 12 and 13 were checked hardest:

- `smysl.write`'s omissions, its counting predicate, and its rule for a
  label bound to several units;
- `smysl.parse`'s refusal, its warnings for comments and salience, and
  its label source;
- `smysl.agent`'s narrowed canonicalisation;
- the record-kind rule and SM03's new cases;
- SM01's `cannot reach` text and SM02's parse text.

`smysl.write`'s claims were followed past `write_surface` into
`WriteContext::reference`, `write_relation`, `refs` and
`has_surface_form`, and into the CLI's `merge`, which builds the context
the RFC cites as precedent. The retraction sequence was followed into
`EffectiveStatus::is_retracted`. The relation claims were followed into
`Relation::uid` and the store's `absorb_hot`.

**Verdict: Ready once the should-fix items are answered. 0 blocking,
3 should-fix, 8 notes.** D244 and D245 are not re-argued. Revision 13's
answers to the eleventh review's S1 and S2 hold against the source, with
one gap in S1's answer (S2 below). The should-fix items:

- A relation's rid is its kind and endpoints only. Re-writing an edge
  with another weight or note appends a record that no read sees and no
  attestation covers, and the RFC does not say so (S1).
- `smysl.write`'s label context is not specified. Built the way SMYSL's
  own `merge` builds it, an omitted unit's label still spells every
  reference to that unit. The text then fails to re-parse, rather than
  coming back "short a unit" as the RFC says (S2).
- "Already retracted" in SMYSL's `retract` means *directly* retracted.
  The RFC's wording also admits a unit that is `unfounded` only by
  cascade, and no criterion tells the two apart (S3).

## Should fix

### S1. A relation's identity is its kind and endpoints, so re-writing an edge with another weight or note is silent

§Current, "Relations", says a relation carries "a kind, two uids, an
optional weight and an optional note". §S2 gives a relation MAP a
computed `rid`. §S4 says what happens when a **unit** is re-written
("Re-writing a unit SMYSL already holds"), and that "a program that
re-proves or re-appends adds nothing to the log". Nothing says what
happens when a **relation** is.

**Evidence.**

- **The rid leaves out weight, note and `extra`.** `Relation::uid` hashes
  the envelope code, the kind, `from` and `to`, and nothing else
  (`smysl-core/src/types/relation.rs:231-238`). The doc comment on `key`
  calls `(kind, from, to)` "the identity tuple" (`:219-224`).
- **The log de-duplicates by bytes, not by rid.** `encode_by_shard`
  skips a record only when its encoding is already present
  (`smysl-text/src/shards.rs:516-522`). So `{ kind: "supports", from: A,
  to: B, weight: 0.2 }`, appended where the library already holds the
  same edge at weight 0.9, is a new record on the log.
- **The store keeps the first.** `absorb_hot` files a relation under
  `rel_key`, which is `(kind, from, to)`
  (`smysl-graph/src/store/interp.rs:38-40`). When the key is already
  held, it unions the attestations and keeps the existing record
  (`:47-58`). `relation_by_id` reads that one (`smysl-graph/src/store/mod.rs:1521-1526`).
- **Bund2 then writes no attestation.** Under R15 an attestation is
  skipped when "this agent has already attested that uid", and the rid
  is the uid an edge's attestation names. So the second record goes on
  the log unattested, under a rid this agent already vouches for, and
  the word answers that rid as if it had been written.

A program that re-weights an edge therefore gets the old rid back, and
the change is invisible to every read. Yet the library has grown. If
`smysl.write` feeds `write_surface` the store's records, as SMYSL's
`merge` does (`store.iter()`, `main.rs:4327`), it writes two `@rel`
lines for one rid with different weights (`write.rs:781-799`).

**Needed.**

- State in §Current that a rid is `(kind, from, to)` alone.
- In §S4, beside "Re-writing a unit", say what `smysl.rel` and
  `smysl.append` do with an edge whose rid the library holds with a
  different weight or note. Either refuse it (SM03 or SM08, "rid <rid>
  is held with another weight"), or append it and report a `Warning`
  that the stored edge is unchanged.
- Say which relation records `smysl.write` passes: one per key, as the
  store resolves it, or every record.
- Add a Preservation row and a criterion 18 case.

### S2. `smysl.write`'s label context is unspecified, and the precedent the RFC cites keeps an omitted unit's label

Revision 13's `smysl.write` row makes three claims:

- the omitted unit's labels "go with it";
- "a relation naming an omitted unit is still written, by uid";
- what is left out is counted "with SMYSL's own predicate,
  `has_surface_form`".

The Preservation row adds that the round trip can "copy a library short
a unit and its labels, said by that `Warning`".

**Evidence.** All three claims depend on what goes into
`WriteContext.labels`, and the RFC says only that a label bound to
several units is left out of it.

- Every reference the writer emits goes through `ctx.reference`
  (`write.rs:104-110`). That covers a relation's endpoints
  (`write_relation`, `:781-787`), its `note` (`:792-794`), and other
  units' `grounds` and `deps` (`refs`, `:823-828`). A uid the context
  labels is spelled by its label.
- The natural way to build the context is `WriteContext::from_labels`
  over the library's bindings. That is what the RFC's own precedent does:
  SMYSL's `merge` folds every label first-wins and calls `from_labels`
  (`main.rs:4320-4326`). Built that way, the context keeps the label of
  a unit `unit_has_surface_form` then omits.
- The text then spells that unit's label in the relation and in other
  units' `grounds`, and never declares it, because the unit's header is
  not written. Re-parsing it is `SMY-E060`: `resolve` drops a ground and
  keeps the unit under another uid (`parse.rs:2836-2846`), and `lookup`
  drops the relation (`:2553-2562,2608-2614`). Revision 12 made
  `smysl.parse` refuse any error diagnostic. So the round trip ends in
  SM02, not in a library "short a unit".
- **The count is wrong too.** `has_surface_form` admits a `LabelBinding`
  when `ctx.labels.get(&b.uid) == Some(&b.label)` (`write.rs:217`). It
  does not ask whether the unit itself is written. So the omitted unit's
  label is counted as written.

The RFC's statements hold only if `ctx.labels` holds, per uid, the first
label in canonical order among those that bind only that unit, and only
for uids whose unit has a surface form.

**Needed.**

- State that construction in `smysl.write`'s row. It also settles which
  label is written for a unit with two labels when one of them is bound
  elsewhere.
- Extend criterion 18's omission case: give the omitted unit a label, a
  relation naming it and a unit grounded on it. Then parse and append
  the written text, which must succeed with that unit and its label
  missing and every other uid present.

### S3. "Already retracted" is SMYSL's `is_retracted`, which excludes units `unfounded` only by cascade

§S4's retraction step 1 says:

> If the effective status under the strict policy already reads the
> target as retracted, nothing is written and the word answers NODATA.

The RFC says the sequence follows SMYSL's `retract` "step for step".

**Evidence.**

- SMYSL's check is `effective_status(&store, policy).is_retracted(&target)`
  (`smysl:src/main.rs:4484`).
- `is_retracted` is "whether this unit was retracted **directly**". It
  tests the `retracted` set, the targets of `retracts` edges
  (`smysl-graph/src/merge/retraction.rs:42-45,83-88`).
- A unit whose grounds were all retracted is in `orphaned`, not
  `retracted` (`:47-50,109-117`). Its status in the map is still
  `Unfounded`. So SMYSL plans an orphaned target, and writes its
  self-edge when authorised.
- `smysl.status` gives both kinds of unit as `"unfounded"` (§S5).
  "Reads the target as retracted" can therefore be implemented as a
  status test, which answers NODATA for an orphan where SMYSL writes.
- Criterion 8's "already read as retracted" case does not separate the
  two. Its two-step cascade fixture produces exactly such an orphan, but
  the test never retracts it.

**Needed.** Cite `is_retracted` in step 1 and say "retracted directly,
not orphaned". Add a criterion 8 case: retracting a unit that is
`unfounded` only by cascade, through a handle authorised for it, writes
the self-edge and answers its rid.

## Notes

- **N1. `warn_surface_omissions` counts a total, and the RFC does not
  say which records are counted.** The function prints one count
  (`main.rs:5709-5719`), and its message names "attestations". Per-type
  counting is `SMY-W428`'s. Cite W428 for "per kind", or say Bund2
  departs from the CLI. Also state which records `smysl.write` hands to
  `write_surface` and to the predicate. If it is the library's every
  record, every attestation Bund2 writes is counted (`write.rs:218-220`),
  and the `Warning` fires on every call. Criterion 18's "a `Warning`
  counting them" should name the counts it expects. A multi-bound
  label's bindings, and a unit's second label, are each counted by the
  predicate as well as named.
- **N2. A relation's `extra` is lost through `smysl.write` without a
  word, and no word reads a relation back from a library.**
  `has_surface_form` admits every relation (`write.rs:208`), and
  `write_relation` writes no `extra` (`:781-799`). The rid is unchanged
  (S1), so the round trip keeps the rid and drops the keys. The same is
  true of a `LabelBinding`'s `extra`. Separately, no Phase 1 word answers
  a relation MAP read from a library: `smysl.get` answers units, and
  `smysl.parse` reads text, which carries no `extra`. So §S2's relation
  `opaque` and criterion 18's relation case are reached only through the
  mapping function. Say so, or add a word that reads relations.
- **N3. An empty payload MAP writes no payload.** `object_to_payload`
  returns `None` for an empty object (`smysl-core/src/surface/payload.rs:33-36`).
  So `payload: {}` gives the unit and uid of one written without
  `payload`, and it reads back without the key. State it beside "drops
  an empty body or detail".
- **N4. A measure's `value` is the whole gist, and may be cut.** The
  result unit's gist is `<id> <label> <v> <unit>, over <scope>`
  (`smysl-measure/src/outcome.rs:268-292`). `fit` cuts it to the default
  profile with `…`, and the scope is what is cut (`lib.rs:461-475`).
  `fit` is `pub(crate)`. For an `Unwritable` or `NoBasis` result there is
  no unit gist. Define `value` as the public `outcome::gist`
  (`lib.rs:81`), uncut, or as the headline alone. Criterion 10's
  comparison depends on which.
- **N5. M2's primary marker path.** It is `log/catalog.primary` for the
  catalog, or `log/shards/<stem>.primary` for any other shard
  (`shards.rs:65-71,88-99,115-119`). `log/<stem>.primary` for a
  non-catalog stem is read by nothing.
- **N6. Criterion 14's `smysl.text.add` cases have no milestone.** The
  sparse file over the input cap (SM02 with `SMY-E440`) and the spec with
  no `lang` (SM03) need `smysl.text.add`, which is M4's. M4's row names
  criterion 18's `smysl.text.add` reporting cases, but not these two.
  Criterion 14 is "complete at M10", so the rule "each criterion is
  claimed by the first milestone at which every word it uses exists"
  leaves them unplaced. Name them in M4.
- **N7. The CLI's `merge` gives a multi-bound label to one unit, and
  `smysl.write` gives it to none.** `main.rs:4320-4326` folds labels
  first-wins. That is a deliberate departure, and the reason the RFC
  gives (`parse.rs:2500-2507`) is right. Say it departs, so the
  Preservation row "A label bound to several units" does not read as
  SMYSL's behaviour.
- **N8. `smysl.agent` and R3.** R3 and §S2 describe a handle's `root` as
  "a canonical path". Since revision 13, `smysl.agent` answers a
  hand-built handle's root unchanged, so a handle may hold a root that
  is not canonical until a word that opens it re-canonicalises. That is
  harmless. The handle's description should say "canonical when built by
  `smysl.create` or `smysl.open`".

## Assumptions the RFC makes but does not state

1. **A relation's rid covers its weight and note** (S1). It covers kind,
   `from` and `to` only.
2. **`smysl.write`'s context leaves out the labels of units it omits**
   (S2). SMYSL's own `merge` does not.
3. **"Already retracted" is a status test** (S3), or `is_retracted`. The
   two differ on an orphan.
4. **`smysl.write` passes only units, relations and label bindings to
   the writer and to its count** (N1). If it passes the library's every
   record, every attestation is counted.
5. **An empty payload MAP is a payload** (N3). It is none.
6. **Relations are read back from a library by some word** (N2). None
   does in Phase 1.
7. **`value` is the headline alone** (N4). SMYSL's gist carries the id
   and the scope, and is cut.
