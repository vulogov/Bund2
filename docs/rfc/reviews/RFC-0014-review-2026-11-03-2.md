### R25, tested

The question was whether revision 10's snapshot is now exact outside
R22's hazard. It is.

- **The files.** The open reads exactly `shards::list`'s pairs
  (`library.rs:332-333`). `list` maps every stem back through
  `log_path`, so a stray `log/shards/catalog.cbor` is measured at the
  catalog's own path, and a stem that does not round-trip is measured at
  the path the open read (and found absent). Revision 9's directory
  listing differed from `list` in exactly those cases (the eighth
  review's N1). Using `list` closes them. A `.primary` shard fails the
  open without `store-redb` (`shards.rs:307-321`), so no snapshot is
  taken over one.
- **The cheap test.** For each log the open read, the bytes on disk are
  `len + torn` (`shards.rs:234-251`). `stamp`'s length is the sum of `len`
  over the catalog and the logs with `len > 0`, and with one live log it
  is that log's `len`, which is the same sum (`shards.rs:395-416`). So
  under the locks, with no unlocked writer, the total on disk exceeds the
  stamp's length exactly when some log is torn. Nothing between the second
  open and the snapshot writes a log. The open's own writes are
  `enforce_z`'s unlinks (`library.rs:676-698`), and `complete_index`
  writes nothing.
- **"A log opened for append without a cut can only grow."** It holds.
  `ShardLog::append` opens with `create(true).append(true)`
  (`shards.rs:371-375`). The only shortening call is `set_len`, made only
  when the in-memory `torn > 0` (`:376-379`), and that `torn` comes from
  the same second open. A log the batch creates (`library.rs:1366-1368`)
  was absent at the snapshot and counts as 0. If the call fails after
  `create(true)` with nothing written, the log is still 0 and unchanged,
  which is right.
- **Torn logs.** After a cut, the bytes from the decoded length onward
  are new, so a same-length rewrite differs from the snapshot's tail
  unless it is byte-identical. The one byte-identical case is a retry
  whose short write stopped exactly at the old tail's length. That leaves
  the file as it was before the call, so dropping the locks is correct.
  A cut followed by no write shortens the log and keeps the locks. That
  is a real change, since the torn bytes are gone.
- **The marker.** It is rewritten only by `append_records` raising
  layout 1 (`library.rs:1357-1362`), and only to a different string, so a
  content comparison catches a whole rewrite and a partial one.

What the RFC does not state is in the notes. The snapshot is not one of
§S9's numbered steps (N9). And "every refusal that writes no log leaves
no lock" holds for a word's first call only (N5).

## Should fix

### S1. A held lock is SM02 in criterion 15 and §S8's SM02 row, and SM07 everywhere else

Revision 10's SM02 row says:

> `SMYSL refused it: <message>`, where `<message>` is SMYSL's error as
> its `Display` writes it. That begins with the code when the error has
> one (`SMY-E445: …`, `smysl-core/src/error.rs:905-926`) …

and criterion 15's new "SM02's text" case says:

> … a held lock's is the same prefix followed by `SMY-E445: …`, once.

But §S8's SM07 row maps "a lock is held (`SMY-E445`)" to `the library is
locked: <holder as SMYSL names it>`. Criterion 15's first case says "a
write is SM07 naming the holder". §S9 says "A lock held by another
process is SM07". The `SMY-E445` error is `LibError::Locked`, which only
`Lock::acquire` returns (`smysl-graph/src/lock.rs:165-176`). It reaches
Bund2 only from `acquire_all`, which is exactly the SM07 path. So no
input makes a held lock SM02, and a test asserting "`SMYSL refused it:
SMY-E445: …`" contradicts the test two bullets above it.

**Needed.** Choose one mapping. If SM07 stands, drop the held-lock
clause from criterion 15's "SM02's text" case, and give SM02's row an
example that is actually SM02. For instance, `SMY-E440` from the
over-cap refusal: `SMYSL refused it: SMY-E440: input_bytes limit …`.
Then say whether SM07's `<holder as SMYSL names it>` is `Display` of
`Locked` (`SMY-E445: library is locked by …`) or only the holder.
`Display` would put the code in SM07's text, and criterion 14 asserts
that text.

### S2. `smysl.create` holds "the process mutex for the root", which is keyed by a canonical root it cannot have yet

§S4's new `smysl.create` row says:

> It holds the process mutex for the root (§S9) and takes no SMYSL lock …

The plan relies on it:

> `smysl.create` takes no SMYSL lock, but it takes the process mutex,
> which M3 builds, and so waits for M3 rather than joining `smysl.open`
> in M2.

But §S9 keys the mutex table "by the canonical root". §S2 says:

> **Every word canonicalises the root it is given again**, before it
> takes §S9's mutex …
> `smysl.create` creates the library first and canonicalises after,
> because a path that does not exist yet has no canonical form.

So as written, `smysl.create` can take the mutex in only two ways. It
can take it after `Library::create` has run, in which case it does not
"hold" it while creating. Or it can key the mutex by the uncanonicalised
spelling, which is a different key from every other word's, so it
serialises nothing. Either way, the claim the plan depends on cannot be
built as written. The mutex is also what keeps two in-process creates of
a new root from racing the non-atomic marker write
(`smysl-text/src/library.rs:290-293`), which criterion 18's create/open
case exercises.

The fix is cheap. `Library::create` itself starts with
`create_dir_all(root)` (`library.rs:289`), and a directory that exists
can be canonicalised.

**Needed.** State `smysl.create`'s order:
1. `create_dir_all`;
2. canonicalise;
3. take the mutex for that key;
4. `Library::create`;
5. release.

Correct §S2's "creates the library first and canonicalises after" to
match. If the RFC prefers not to take the mutex, drop the claim and the
plan's M3 rationale.

### S3. The label MAP has no defined shape, and the one shape the RFC implies is refused by its own rule

§S4 says `smysl.append` takes "a LIST of unit, relation and label MAPs",
`smysl.parse` produces them, and §S2's new order rule resolves `grounds`
and `deps` against "the label MAPs earlier in the same `smysl.append`
LIST". Criteria 5 and 18 depend on them. But §S2's table has rows for a
unit, a source, a relation, a diagnostic, a subject and a payload, and
none for a label. Four things follow:

- **The key for the bound unit is unnamed.** SMYSL's record is
  `LabelBinding { label, uid, extra }`
  (`smysl-core/src/types/annex.rs:488-493`). The obvious MAP is
  `{ label, uid }`. But §S2 says "A MAP carrying `uid`, `rid` or `opaque`
  is refused (SM03, 'computed, not given')". As written, that rule
  refuses such a label MAP.
- **`smysl.parse` output cannot name its units by uid.** It returns MAPs
  "without their ids". SMYSL's parser resolves labels to uids and keeps
  the bindings in a separate `labels` map, off the records
  (`smysl-core/src/surface/parse.rs:12-13,44,63`). A label MAP emitted
  "without ids" therefore cannot say which unit it binds, unless it
  carries that unit's uid. A program can get that uid only by appending
  the unit first.
- **A unit MAP's `labels` key is defined on read-back only.** §S2's unit
  row lists `labels` (LIST of STRING). `UnitCore` has no such field
  (`smysl-core/src/types/unit.rs:25-58`), so on write it means either
  "bind these" or nothing. The RFC does not say which. If it binds, the
  new order rule should name it beside "label MAPs earlier in the same
  LIST".
- **Some cases have no refusal.** A label in `grounds` that nothing
  binds is `LabelError::Unbound` (`smysl-graph/src/labels.rs:24-29`),
  and no SM code is named for it. A MAP in `smysl.append`'s LIST that is
  none of the three kinds also has no refusal, since the MAPs carry no
  discriminating key.

**Needed.** Add a label row to §S2's table, with its keys and how a
label MAP is told apart from a unit or relation MAP. Say whether a unit
MAP's `labels` binds on write. Exempt the label MAP's unit key from the
"computed, not given" rule, or name it otherwise. Say what `smysl.parse`
puts in a label MAP and in a relation's `from` and `to`: uids, which
SMYSL's parse already computed, or labels. Then name the code for an
unbound label (SM08, or SM03).

## Notes

- **N1. ShapeError's `Display`.** Cite `smysl-core/src/error.rs:179-192`
  for "A `ShapeError` displays the same way, with its code"; `:143-150`
  is `code()`.
- **N2. The over-cap SM02 text tells a Bund program to use a CLI flag.**
  `Budget::new` builds `LibError::Limit` with
  `flag: Some("--max-input")` (`smysl-text/src/limits.rs:109-111,136-147,169-171`).
  Its `Display` then ends "(raise it with --max-input)"
  (`smysl-core/src/error.rs:911-915`). Bund2 has no such flag, and Phase 1
  fixes `Caps::default()`. Either say so beside SM02, or strip the
  suffix.
- **N3. An interrupted create leaves an empty marker for good, and
  "a retry succeeds" does not hold then.** `Library::create` writes the
  marker only `if !marker.is_file()` (`library.rs:291-293`). A process
  killed between `std::fs::write`'s truncate and its write, or a write
  that fails with a full disk, leaves an empty `LIBRARY`. Every later
  `create` skips it, and every open fails with "layout `` is not …"
  (`:304-319`). That is SM02 on every word, with no Bund2 or SMYSL
  repair. Across processes, two creates can also make one create's own
  open (`:298`) read the marker the other has just truncated, so a
  `smysl.create` can itself be SM02. "Two creates at once write the same
  bytes" says only half of that. The "Creating a library" Preservation
  row and U10 should name both.
- **N4. The `Unwritable` arm has no test, and its severity is
  re-labelled.** §S5 maps `NotPersisted::Unwritable` to `uid` NODATA,
  with its diagnostic in `diagnostics` and reported as a `Warning`.
  Criterion 10 does not reach it, since T1 and A4 over a fixture do not
  overflow a payload integer, and criterion 18 does not name it. The
  diagnostic is `SMY-E489`, error severity (`smysl-measure/src/lib.rs:454-456`).
  Reporting it as a D36 `Warning` is defensible, because the program has
  not stopped. Say so, since criterion 18's "a diagnostic of each
  severity" would otherwise read as one `Warning` per warning only.
- **N5. "Every refusal that writes no log leaves no lock" holds only for
  a word's first call.** The snapshot is taken once per acquisition, so
  a word whose first call wrote and whose second was refused keeps the
  locks. §S9 says so ("a word that wrote one batch and then failed on a
  second still keeps the locks"). The next sub-bullet's "So every
  refusal that writes no log leaves no lock" then over-states. Either say
  "every refusal of a word's first call", or state that each word makes
  one `append_records` or `Library::add` call. SMYSL's own `measure`
  appends its basis, units and attestations as one batch
  (`smysl:src/main.rs:7560-7579`), which suggests the second.
- **N6. Ground "exactly the logs the open reads" in the open.** Cite
  `smysl-text/src/library.rs:332` beside `shards.rs:84-113`.
- **N7. The `smysl` constructor under `--noio`.** The Preservation row
  implies the constructor is stubbed as well as the handler ("stubbing
  the constructor alone would leave a library readable"). Criterion 18
  tests "every other `smysl.` word" and a hand-built CONDITIONAL. The
  constructor `smysl` is neither of those. D119 stubs `csv` itself. Say
  whether `smysl` is SM06 under `--noio`, and test it.
- **N8. Criterion 18's `redacted` case needs a redaction that no word
  makes.** "A text with a part the library has redacted" requires
  `Library::redact`, through SMYSL's API and under the locks, on Bund2's
  library as well as the twin. Say so, as criterion 12 does for views.
- **N9. The snapshot is not in §S9's numbered steps.** Steps 1–7 go
  from "validate, decide and write" (6) to "drop the locks" (7). The
  snapshot falls between 5 and 6. A failure comparison falls inside 6,
  and step 7 becomes "drop or forget". Put them in the list, since an
  implementer reads the steps.

## Preservation: what is missing

- **A library made unopenable by an interrupted create** (N3). The
  "Creating a library" row says an open that races a create is SM02, and
  that a retry succeeds. An empty marker left by a killed or failed
  create is permanent.
- **A third read of every log, over a torn library.** When the cheap
  test is true, the guard reads and decodes every log before every
  write. That is on top of the two opens §S9 already makes (Q54). It
  costs speed, not meaning, but it applies to every library a crash has
  touched, until some write cuts the tail.
- **SMYSL's CLI advice in Bund's refusals** (N2). SM02's over-cap text
  names `--max-input`.
- **A measure error reported as a warning** (N4). An `SMY-E489` from
  `to_unit_on` becomes a D36 `Warning`.

## Assumptions the RFC makes but does not state

1. **A held lock can reach Bund2 through a path other than
   `acquire_all`**, which S1's SM02 example implies. At 4f5ecb9 it
   cannot: without `store-redb`, nothing else returns `Locked`.
2. **A root can be canonicalised before `Library::create` runs** (S2).
   It can, once `create_dir_all` has run, but the RFC says the opposite.
3. **A label MAP can name its unit without a uid, or a uid is not a
   "computed" key on a label MAP** (S3).
4. **An empty `LIBRARY` marker is transient** (N3).
5. **Each word makes one `append_records` or `Library::add` call per
   acquisition**, which "every refusal that writes no log leaves no lock"
   needs (N5).
6. **`Library::stamp()` and the snapshot describe the same set of logs.**
   They do, because the open iterates `shards::list`
   (`library.rs:332`), but the RFC cites only `list` (N6).
7. **Reading every log again over a torn library is affordable** (see
   "Preservation: what is missing"; Q54).
