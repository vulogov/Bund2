## Verdict

**Nothing here needs a ruling, and no citation is wrong.** Every
`path:line` in the RFC says what the RFC claims; every test and symbol
named exists, and the ones I read check what the criteria say they
check; each of the eleventh review's findings is answered where the RFC's
table says it is. I would move the RFC to Accepted once finding 1 is
written in, because the preservation analysis promises to list what a
program moving between old and new words sees, and it omits one face.

1. **`graph.path`'s third answer to a weight that is not finite is
   unstated.** `make_graph.rs:64` casts `w as usize`. Rust's cast sends
   NaN and every negative value, −inf included, to 0, and anything at or
   above 2^64, +inf included, to `usize::MAX` (checked by running
   `rustc 1.95.0` today). So under `graph.path` a NaN edge **does not
   exist**: it reads as 0 and `fast_paths` skips it
   (`input_graph.rs:197-203`). Run today in both engines, over `A → B`
   weighing NaN and `B → A` weighing 1.0:

   | word | oracle | `bund2` |
   |---|---|---|
   | `:B :A … graph.path` | `GRAPH.PATH: can not calculate path` | the same |
   | `:A … graph.paths` | a row `node=B :: path=NaN` | the same, in node order |
   | `:B :A … graph.bellmanford` | — | `an edge's weight must be finite: A -> B weighs NaN` |

   The "non-finite weights" bullet of the preservation analysis
   (R:647-648) names two of these three. The "Current behaviour" table's
   row "weight below 1 after the cast: skipped" covers NaN only for a
   reader who knows the cast's rule, which the RFC never states; it states
   the truncation ("1.9 reads as 1") and the saturation ("at or above
   2^64") and cites `make_graph.rs:64` for both, but that line is the
   cast, and the rule is the language's. Nothing pins NaN → 0: the tests
   pin 0.5 (`graph_path_drops_an_edge_under_one_before_the_lowest_is_kept`)
   and 1.0e300 (`path_wraps_a_sum_past_2_to_the_64`). One sentence under
   "Current behaviour" and one in the bullet would close it; a NaN case in
   either test would pin it.

Then, smaller:

2. The claim that Bund2 Title-cases as the reference does, which S2 makes
   for digit and inner-capital splits "in both engines", rests on both
   resolving the same `convert_case`. They do today, and the RFC does not
   say so.
3. Smaller points: `graph!` "checks nothing"; `graph` and `graph.` "only
   check a MAP"; three behaviours S1's rules determine but do not name;
   a tolerance in one max-flow test; and "fits in memory".

## Findings, most serious first

### 1. What `graph.path` does with a weight that is not finite

See the verdict. The programs:

    :B :A -1.0 math.sqrt [ :A :B ] ++ list push [ :B :A 1.0 ] swap push [ :A :B ] graph! graph.path
    :A  -1.0 math.sqrt [ :A :B ] ++ list push [ :B :A 1.0 ] swap push [ :A :B ] graph! graph.paths
    :B :A 1.0e200 1.0e200 * [ :A :B ] ++ list push [ :B :A 1.0 ] swap push [ :A :B ] graph! graph.path

The first answers `GRAPH.PATH: can not calculate path` in both engines:
the NaN edge read as 0 and was skipped, and `B → A` sizes the graph so
F219's crash is not what happens. The second answers `path=NaN` for `B`
in both. The third answers `can not calculate path` in both, for F227's
reason: +inf saturates to `WEIGHT_MAX`, and alone as the first edge
searched it is no path. So a NaN or −inf weight is a **silent absence**
under `graph.path`, a NaN row under `graph.paths`, a wrapping weight
under `graph.path` when +inf, and a refusal under the twelve. The
preservation analysis's "non-finite weights" bullet (R:647-648) should
say all four, since it is the list a program author reads when swapping
`graph.path` for `graph.bellmanford` and finding a refusal where there was
a quiet no-path.

The cast's rule is a claim about Rust and carries no citation. The RFC
uses three of its four parts (truncation at R:145, saturation at
R:166, and "below 1 after the cast" at R:147) and cites
`make_graph.rs:64` for each; that line shows the cast and not the rule.
A citation to the Rust reference's numeric-cast section, or the one-line
statement "NaN and negatives read as 0; 2^64 and above, +inf included,
as `usize::MAX`; others truncate toward zero", is what grounds it.

### 2. "In both engines" for Title case rests on a shared crate version

S2 (R:344-347) says Title case splits at digits and inner capitals "in
both engines", and cites `make_graph.rs:9-11`, which is
`name.trim().to_case(Case::Title)`. The splitting rule is
`convert_case`'s, not those lines'. It is the same in both engines
because both resolve the same version: `reference/Bund/Cargo.toml:85`
pins `convert_case = "0.7.1"` (`reference/Bund/Cargo.lock:1900-1901`),
and `crates/bund2-stdlib/Cargo.toml:50` pins `"0.7"`, which `Cargo.lock:
803-804` resolves to 0.7.1. Bund2's lock also carries 0.6.0 and 0.10.0
for other crates, as the reference's does; the graph code uses neither.

That parity is what makes the claim hold for every name and not only for
`:N1` and `:my_node`, which were run. A `cargo update` within `0.7.x`
cannot move it, but the RFC should state the dependency, since S2 now
tells a program author what spelling to write and the answer is a
third-party crate's word-boundary rule. One sentence in S2 or in the
"Current behaviour" bullet that cites `make_graph.rs:9-11`.

### 3. Smaller points

- **"`graph!` checks nothing (`mod.rs:68-93`)"** (S4, R:416). The lines
  test each pulled value's `dt` and, for one that is not a LIST, push it
  back and use an empty list (`:70-76`, `:79-85`). Run today, `[ :A ] 7
  graph! println println println` prints the empty graph, then `7`, then
  `[ A ]`, in both engines. "Refuses nothing" is what the lines say, and
  Bund2's own doc comment says it exactly (`graph.rs:48-52`). The first
  review's citation table recorded the same. The sentence's point, that
  `graph!` neither checks nor defaults `type`, is right.
- **"`graph` and `graph.`, which only check a MAP"** (S6, R:562). They
  also refuse `nodes` or `edges` that is not a LIST (`mod.rs:50-55`); the
  palette's `dict` passes because a missing key defaults to an empty list
  (`:42-49`). The conclusion, promotable, stands.
- **Three behaviours S1's rules determine but do not name**, each run
  today under `bund2`:
  - an isolated node is a group of one in `graph.components` and
    `graph.scc`: `[ [ :A :B 1.0 ] ] [ :A :B :C ] graph! graph.components`
    answers `[ [ A B ] [ C ] ]`. S1 says "LIST of LISTs" and S3 how groups
    are ordered; neither says every node appears. The test
    `structure_words_answer_lists_of_lists` pins `[ F ]` (GA:1394).
  - `A → B` and `B → A` are two candidates for `graph.mst`, since S2's
    "repeated edge" is an ordered pair; Kruskal takes the lighter and
    reports it in its own direction: `[ [ :A :B 5.0 ] [ :B :A 1.0 ] ] [ :A
    :B ] graph! graph.mst` answers `edges=[ [ B A 1.0 ] ] weight=1.0`.
    "Edges read both ways" implies it; a clause would state it.
  - `-0.0` is a capacity of zero `graph.maxflow` accepts, since `-0.0 <
    0.0` is false (GA:893): `:B :A [ [ :A :B -0.0 ] ] [ :A :B ] graph!
    graph.maxflow` answers `flow=0.0`, `edges=[]`. Consistent with S3's
    `==` rule for `graph.mst`; unstated for `graph.maxflow`.
- **`max_flow_is_the_min_cut` compares within `1e-9`** (GA:3225, :3232)
  over whole capacities, where `…_across_magnitudes` asserts equality
  (GA:3188). The tolerance hides nothing today, since every sum is exact,
  but the two tests make different claims about the same arithmetic.
  Criterion 3 says nothing false; `assert_eq!` in both would let it say
  "exactly" for both.
- **"which no graph that fits in memory is"** (S4, R:401; S5, R:484).
  `nodes × (edges + 1) ≥ 2^76` is least at about 2^38 of each, and a
  `Net` of that size is tens of terabytes before the MAP that holds the
  literal. Machines of that size exist; a literal of that size does not
  get parsed. The guard is an ordinary error either way, so nothing turns
  on the phrase.
- The oracle's `graph.allpath` names its unknown-node errors
  `GRAPH.TRANSITIVECLOSURE:` (`allshortpath.rs:65,69`). Both arms are
  unreachable, since `t_res` holds every index `make_graph` numbered, so
  there is nothing to preserve and the RFC rightly says nothing.

## What the RFC assumes but does not state

- **Rust's float-to-integer cast rule**, used three ways and never
  stated or cited; the NaN → 0 part is what finding 1 turns on.
- **That both engines resolve `convert_case` 0.7.1** (finding 2), which
  is what makes S2's "in both engines" general.
- **That an isolated node is its own group**, that antiparallel edges
  are two candidates for `graph.mst`, and that `-0.0` is an acceptable
  capacity of zero (finding 3). Each follows from a stated rule; none is
  written.
- **That `Exact` makes the walk back safe.** S5 classes "Bellman–Ford's
  walk back reaching a node no edge relaxed" as an internal error, which
  is right, and the reason it can never happen is exact comparison
  (D207): in `f64` the chain argument above fails by rounding. The RFC
  does not connect the two, and a future reader who relaxes the exactness
  would reopen a reachable internal error without a test saying so.
- **That "fits in memory" means commodity sizes** (finding 3). Harmless.
