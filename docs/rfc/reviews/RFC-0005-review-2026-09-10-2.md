That is a good revision. The new design text is also largely well grounded: the
generation counter exists, it saturates, and every writer bumps it.

Two blockers remain, and both are assumptions no earlier review stated. Each
sits one call past the file the RFC read:

- **B1.** The cache key is the body's `Rc`, and **no `Rc` survives to the point
  where a body starts running.** `Vm::eval_body` takes `&[BundValue]` and
  `Vm::tail_call` takes `Vec<BundValue>`. `times` copies the body out with
  `.to_vec()` before it calls either. The loop words that §S5 relies on to avoid
  OSR ("rely on loop bodies being separately compilable lambdas") therefore give
  Tier 1 nothing it can key, count or compile.
- **B2.** The meaning guard re-checks what a *name* means. Nothing re-checks
  *which stack* compiled code is addressing. `to_stack` and `to_current` declare
  `eff(1, 0)` and switch the current stack. A CONTEXT value switches it with no
  word involved at all. Promotion runs straight through both. The RFC does not
  mention the workbench, the current stack or CONTEXT once (a `grep` count of
  0). This has been carried as "the multi-stack" since `-3` §5.5, and it now has
  a concrete failing program.

## 1. Blocking

### B1 — the `Rc` key does not reach the entry point, so loop bodies cannot be compiled

§S3: "**D35 resolves the key: the body's `Rc` pointer**, with the cache holding
a strong clone." §S7: "The counter holds a `Weak`." Both need the body's `Rc` in
hand at the moment the body is entered, because that is where a count is taken
and where compiled code would be chosen instead of the interpreter.

Here is what Bund2's entry points actually receive:

| entry | signature or code | `Rc` present? |
|---|---|---|
| `Vm::eval_body` (`crates/bund2-api/src/lib.rs`) | `fn eval_body(&mut self, body: &[BundValue])` | **no**: a borrowed slice |
| `Vm::tail_call` (same file) | `fn tail_call(&mut self, body: Vec<BundValue>)` | **no**: an owned copy |
| `Interp::dispatch`, `Resolved::Lambda` arm (`crates/bund2-interp/src/lib.rs`) | `body.as_lambda()…to_vec()`, then `request_tail(items)` | only before the `.to_vec()` |
| `Interp::eval_body` (same file) | `self.frames.push(Frame { body: body.to_vec(), … })` | **no** |
| `times_base` (`crates/bund2-stdlib/src/seq.rs`) | `let body = lambda_val.as_lambda()…to_vec();` then `vm.eval_body(&body)` | **no**: a fresh `Vec` per call to `times` |

`eval_body` has fourteen call sites in `bund2-stdlib`, and `tail_call` has three.
Between them they cover `times`, `loop`, `map`, `if` and its family, `try`,
`while`-shaped control, and the OOP method paths (`control.rs`, `seq.rs`,
`conditional.rs`, `oop.rs`, `singles.rs`, `values.rs`). Only the named-lambda
arm of `dispatch` ever holds the `Rc`, and it discards it one line before the
body runs.

This removes more than a detail:

1. **§S5's no-OSR argument cannot be implemented as written.** It says to
   "compile at word granularity and rely on loop bodies being separately
   compilable lambdas", and then grounds that in `times`, `loop`, `map` and
   `while` testing `is_type(LAMBDA)`. The reference's `times` passes
   `lambda_val.clone()` to `lambda_eval` on every iteration
   (`reference/rust_multistackvm/src/stdlib/logic/times_fun.rs:20`), so the
   same `Rc` arrives each time. Bund2's `times` passes a slice of a copy.
2. **§S7's counter cannot hold a `Weak` of something it was never given.** A
   slice pointer is not a key either: `times` rebuilds the `Vec` on every call,
   so the pointer changes and the count restarts every time.
3. **What is left eligible is exactly the named-lambda path.** That is the case
   least likely to be hot inside a loop.

Fixing this changes `Vm`, which is `bund2-api`'s stable surface (RFC-0002,
Accepted). It also changes RFC-0003's frame, which holds `Vec<BundValue>` where
the cache wants an `Rc`. RFC-0003 §S3 "states the shape" of the `Rc` key and
says nothing about how it survives into a frame. **Neither RFC is this one to
amend.**

**Required:**
1. State the assumption: every body entry passes through a point that holds the
   lambda's `Rc`.
2. Name the change that makes it true, for example `eval_lambda(&BundValue)` in
   place of `eval_body(&[BundValue])`, and take it to the owner as an RFC-0002
   and RFC-0003 amendment.
3. Add a criterion: a body run by `times` N ≥ 64 times reaches the counter under
   one key.

### B2 — a fixed-effect word can change which stack every later op addresses

The meaning guard re-reads two things at each inlined site: the slot's
generation and `autoadd`. The fifth review's B1 was "a fixed-effect word
changes what a later *name* means". This is the same shape one step further
along: **a fixed-effect word changes which *stack* a later op means.**

- `to_stack` and `to_current` are registered `eff(1, 0)` in
  `crates/bund2-stdlib/src/stack.rs` (the `w(r, "to_stack", to_stack, eff(1, 0))`
  line and its neighbour). Both pull a name and call `vm.to_stack(&name)`.
  Under RFC-0004 they are ordinary fixed pairs, not `Opaque`, so §S5 promotes
  straight through them.
- **A CONTEXT value switches stacks with no word at all.** `Interp::apply_step`'s
  `CONTEXT` arm calls `push_context` and then `to_stack`. That matches
  `reference/rust_multistackvm/src/multistackvm_apply.rs:69-87`. RFC-0004's
  effects classify *calls*; a CONTEXT literal is not a call, and nothing
  classifies it.
- `rotate_stack_left` and `rotate_stack_right` are `eff(1, 0)` and reorder a
  *named* stack. When the name is the current stack's, they reorder values that
  promotion is holding in registers. That is Q34's shape (a word observing past
  its arity), and Q34's register row does not list it.

The failing program is short: `1 2 "s" to_stack +`.

- **Tier 0:** switches to `s`, then runs `+` there, which fails with a depth
  error or adds whatever `s` holds.
- **Compiled with promotion:** `1` and `2` sit in `Variable`s. `to_stack` is a
  fixed pair, so promotion continues, and the inlined `+` adds them and pushes
  `3` onto `s`.

Different stack contents, and possibly an error on only one side. `conform`
would catch it only if a golden happened to exercise it.

Inlining alone has the same exposure if the lowering resolves the current stack
once at entry. `frag::run` does not — it goes through `Interp::pull`, which
reads `stacks.current_mut()` every time — but nothing in the RFC obliges a
lowering to match. §S5's sync rule also names no target stack. "Synced back to
the real stack" means *which* stack, if the body switched stacks before the
opaque site?

**Required:**
- Treat a current-stack switch as a promotion barrier: every word that calls
  `Vm::to_stack` or equivalent, plus every CONTEXT value. Either classify them,
  or guard on the current stack's identity the way the meaning guard guards on
  a generation.
- State that a lowered op addresses the current stack *as of that op*.
- Say which stack a sync writes to.
- Add a Preservation row and a criterion.
- Raise `rotate_stack_*` under Q34.

## 2. Significant

### S1 — the `autoadd` design covers calls, but the reference collects every applied value, and Bund2's Tier 0 is the wrong oracle

**The reference.** `apply` consults `autoadd` in **three** places, not one:

- CALL: `reference/rust_multistackvm/src/multistackvm_apply.rs:19-27`
- CONTEXT: the value is pushed instead of switching stacks (`:72-73`)
- **every other value**, literals included: appended to the value beneath (`:89-97`)

**The RFC.** It frames `autoadd` entirely as a property of calls: "every
inter-word call it contains would be wrong". It guards at two places, body
entry and each inlined site.

**What is left out:**
1. **Literal pushes after a mid-body `:`.** In the reference they are collected.
   In compiled code they are pushed, promoted or not.
2. **Slot calls after a callee has enabled the mode.** Suppose a compiled body
   calls a lambda through its slot, and that lambda runs `:`. The caller passed
   its entry guard long ago, and its next slot call carries no check. §S4 never
   says whether a slot call re-enters `dispatch`, which does check `autoadd`
   (`Interp::dispatch`'s `_ if self.autoadd` arm), or jumps to the native
   directly, which would not.

**Bund2's Tier 0 diverges from the reference here.** The doc comment on
`Interp::apply` says "`autoadd` is not implemented, so the branches at `:19` and
`:89` are absent". And `dispatch`'s `autoadd` arm pulls the value beneath,
pushes it back, and pushes the CALL **as a separate value**. The reference
appends *into* it — `self.stack.push(val.push(value))`
(`reference/rust_multistackvm/src/multistackvm_apply.rs:22`) — and leaves one
value. The test `autoadd_appends_the_name_instead_of_running_it` asserts two
values ("the value is left beneath"), so it encodes the divergence rather than
catching it. None of this is observable today, because nothing binds `:`.

Criterion 18 then asks compiled code to behave "exactly as in Tier 0". That
certifies agreement with a Tier 0 that is known to be incomplete.

**Required:**
- Cover literal and CONTEXT application under `autoadd`, and slot calls made
  after any call, not only entry and inlined sites. Or state that every slot
  call goes through `dispatch`.
- Make criterion 18's oracle a golden captured from the reference, not Tier 0.
- **For the owner, not this RFC:** Tier 0's `autoadd` arm and its test look like
  a Bund2 defect worth an `F` entry before `:` is bound.

### S2 — the meaning guard's "two loads" has no addressing mechanism, which is the gap the Status line already admits for §S8

The Status line says §S8's headroom check "has no mechanism: how a compiled body
reads its remaining machine-stack headroom is still unstated". **The meaning
guard has the same gap.** The RFC costs it as "two loads and two compares per
inlined site", and does not say how compiled code reaches either value:

- **`Slot` has no stable address.** `Registry` stores `slots: Vec<Slot>`, and
  `slot_mut` grows it with `resize_with` whenever a new symbol's index is past
  the end. That happens at run time too, whenever `register` or `alias`
  introduces a name. A compiled body therefore cannot hold a pointer to `+`'s
  generation. It has to reload the vector's buffer every time: registry → buffer
  → `slots[i].generation`. That is at least three loads, plus the load for
  `Interp::autoadd`.
- **Compiled code receives `&mut dyn Vm`.** That is the `NativeFn` signature
  §S8 relies on (`crates/bund2-api/src/lib.rs:61`, quoted in the RFC's fenced
  block). `Vm` exposes no registry and no generation, and `Slot::generation` is
  a private field behind a getter. What remains is either a helper call per
  site, which is not "two predictable loads", or raw reads into `Interp`'s
  layout from `bund2-jit`. Today `bund2-jit` depends only on `bund2-value` and
  `bund2-ir` (`crates/bund2-jit/Cargo.toml`).
- **"`Slot` already carries this counter for inline caches"** is true of the
  field and its doc comment. **No inline cache exists.** Searching `crates/` and
  `xtask/` for `generation()` finds nothing outside `bund2-api`'s own tests
  (`rewriting_a_binding_bumps_the_generation`, `the_generation_saturates`). The
  meaning guard would be the counter's first reader.

**Required:**
- State how compiled code reads the generation and the flag, and count the loads
  that implies.
- If the answer involves `unsafe` in `bund2-jit`, say so: it is the first
  `unsafe` this design needs.
- Give criterion 17's cost measurement a threshold, as criterion 11 gives the
  headroom check (2 ns).

### S3 — `Fragment::validate` is not "at construction", and it misses two post-guard failures

§S6's table says `Fragment::validate` "refuses, at construction, a fragment
whose ops outrun its guard or its register file". Criterion 19 says the same
and reports it **Met at the model level**. Neither holds.

**It is not at construction.** `Fragment`'s three fields are `pub`, there is no
constructor, and `fragments::int_add`, `dup` and `drop_top` build struct
literals. Nothing on a non-test path calls `validate`: `frag::run` does not, and
only the bench and the tests do. A malformed fragment is refused only by a
caller who remembers to ask. That is the "make it structural" option `-09-10` S3
offered, not taken.

**It counts only `PopInt`.** The consumption check (`pops > regs`,
`pops > n`) filters on `Op::PopInt`. So:

- **`DropTop` is never counted against the guard.** `Fragment { guard:
  Depth(1), ops: [DropTop, DropTop], registers: 0 }` passes `validate`. On a
  one-deep stack `frag::run` drops one value and then runs `let _ = i.pull()`
  on an empty stack, which silently does nothing and returns `Ok(true)`. The
  words `drop drop` would fail "too shallow". The result is **neither refused
  nor an internal error**: a silent success where Tier 0 errors.
- **A register that was never written reads as zero.** `Fragment { guard:
  TopAreInt(1), ops: [PopInt, PushInt(1)], registers: 2 }` passes `validate`
  (one pop, register 1 inside a file of 2) and pushes `0`.

Both fragments are hand-built and none ships. But criterion 19's claim covers
the whole model — "anything that escapes is `Error::internal`" — and these
escape as success.

**Required:**
- Private fields and `Fragment::new(…) -> Result<Fragment, String>`.
- Count every stack-consuming op against the guard.
- Track written registers.
- `DropTop` on an empty stack becomes `Error::internal`, like `DupTop` already is.
- Add a test for each.

### S4 — §S7's threshold does not make D3 true, and "never reaches 1" is wrong

The §S7 table says the threshold "is what makes D3 true *by construction*
rather than by rule: eval'd bodies are fresh `Rc`s per call, so their count
never reaches 1, let alone 64".

1. **An eval'd token stream is not a body.** D3 records that
   `bund_compile_and_eval` "parses the string and `apply`s each token straight
   into the VM, retaining nothing". There is no `Rc` to count, so the count is
   not "below 1": the stream is never a compilation unit at all. *That* is what
   D3's amendment rests on ("structurally incapable of hitting"). It is not a
   threshold.
2. **A lambda *inside* eval'd code is a body, and it can cross 64 inside one
   eval.** `1000 { … } times` evaluates the inner body 1000 times under one
   `Rc` (once B1 is fixed). It compiles. Every re-evaluation of the same string
   mints a new body and compiles it again, and each orphans its code, which
   §S4 says is never reclaimed. In a REPL, **the 1024-body cap bounds this and
   the threshold does not.** Once 1024 such lines have run, Tier 1 is off for
   the rest of the process. That is Q27's REPL profile, arriving through D3's
   door.
3. As arithmetic, a fresh body evaluated once *does* reach 1.

**Required:**
- Restate the D3 argument as "the token stream is never a compilation unit".
- State that inner lambdas of eval'd code are ordinary bodies, bounded only by
  the cap.
- Say whether that is acceptable, or whether content-hash keying (D35's "strict
  upgrade", rejected for now) is what the REPL case eventually needs. Link Q27.

### S5 — criterion 10's stop rule is applied to a number it was not written for

As originally worded, criterion 10 said inlining "under 2×" would mean "the
lowering, not the ceiling, was the constraint". The RFC now applies that rule
to the **ceiling**: "inlining alone on arithmetic sits at 2.0× before any
compiled-code overhead — so by this rule it is already not worth building".

- The ceiling is **2.03×** by the RFC's own table (59.2 / 29.2), and **2.04×**
  on today's re-run (60.8 / 29.8). That is not under 2×.
- The conclusion — overhead will push the real figure below 2× — is probably
  right, but it is a prediction, and the rule as written governs the measured
  lowering.

I agree with the RFC's substance. The rule needs rewording so it says what it
is applied to. As it stands, a reader cannot tell whether the lowering result
will be judged against 2× or has already been judged.

Re-run today, one run, `cargo bench -p bund2-bench --bench fragment`, point
estimates per 1000 operations:

| | `tier0` | `inlined` | `lowered` | `promoted` |
|---|---|---|---|---|
| `Int + Int` | 60.8 µs | 46.3 µs | 29.8 µs | 6.99 µs |
| `dup drop` | 89.0 µs | 46.3 µs | 30.5 µs | 7.05 µs |

The ratios agree with the RFC's table to within about 3%: 2.04× / 2.92×
inlining, and 4.26× / 4.33× promotion. **The table stands.** The two `inlined`
cells coincide in both the RFC's run and mine. That is plausible, since
`frag::run`'s fixed cost dominates both, but it is the kind of coincidence
worth a sentence.

### S6 — §S4's unregister stub contradicts Bund2's slot model, and "slot" means two things

§S4: "**Unregistering a word writes a failing stub into its slot** … a compiled
body that still calls the name reports the same `not registered` error Tier 0
would."

Bund2's `Slot` holds **six independent bindings** — command, alias, lambda,
native, class, method — "because the namespaces are independent in the
reference … writing a lambda must not disturb the native that `$name` reaches"
(`Slot`'s doc comment, `crates/bund2-api/src/lib.rs`). The `unregister` word
calls `vm.unregister_lambda` (`crates/bund2-stdlib/src/values.rs`), which
clears the lambda alone. So:

- **Unregistering a lambda that shadowed a native reveals the native.** Tier 0
  then runs the native. It does not say "not registered". A failing stub would
  diverge.
- **A program cannot unregister a native at all.** Criterion 5's "unregistered"
  case against a native `+` is therefore a no-op in Tier 0. That is fine as a
  test, but it exercises nothing the stub rule describes.

Separately, **the RFC uses "slot" for two different structures without saying
so.** §S4's slot is a runtime-owned *code pointer* that compiled code calls
through. §S6's slot is the registry's `Slot` record with a generation. The
Preservation row on `alias` ("retargeting must rewrite every slot that resolved
*through* the alias") assumes one call slot per resolved target, updated by
fan-out. §S6's rule "a name reached through an alias … is called, not inlined"
assumes one generation per name, never fanned out. These are two models.

**Required:**
- One statement of what a call slot is, whether it is the registry's `Slot`,
  and what writes it.
- Restate the unregister rule as "rewrite to whatever the name now resolves to;
  a failing stub only when nothing does".
- Add a Preservation row for a revealed binding.

## 5. Preservation analysis — what the table does not enumerate

New in this review, in rough order of how late each would be found:

1. **A body entered through `eval_body` or `tail_call`** never reaches the tier
   (B1). Not a meaning risk today, but the fix changes `Vm`, a stable surface,
   and every native that runs a body.
2. **A current-stack switch mid-body** — `to_stack`, `to_current`, a CONTEXT
   value, `endcontext` — while values are promoted or while a lowering has
   cached the stack (B2).
3. **A named-stack reorder that targets the current stack** under promotion:
   `rotate_stack_left` and `rotate_stack_right` (B2, Q34).
4. **`autoadd` collecting literals and CONTEXT values**, and slot calls made
   after a callee enables it (S1).
5. **Unregistering a lambda that shadows a native** — the native reappears; a
   stub would be wrong (S6).
6. **Error wrapping on the `eval_body` path.** `Interp::eval_body` wraps every
   failure as `Lambda content evaluation returned error: …`, and `times_base`
   wraps again as `TIMES: lambda execution returns error: …`. A compiled body
   substituted at that entry must reproduce both prefixes byte for byte, or an
   error-bearing golden moves. This is the concrete form of `-3` §5.10's
   "tier-dependent error wrapping".
7. **A fragment that validates but is wrong after its guard** (S3).
8. **Eval'd inner lambdas recompiled on every eval** until the cap (S4).

Still absent **[carried from `-3` §5]**:
- the `Diagnostic` stack snapshot under promotion (§5.4)
- `.id` / `.timestamp` under promotion via D20 (§5.6)
- `Warning` / `Notice` from compiled code (§5.7)
- run-time `Fold` detection (§5.8)

The table now carries the `$` resolution depth, the stub, the sync path, the
meaning guard, post-guard failure, and widened-guard `q` — all ✓, with S6's
caveat on the stub.

## 7. What the RFC assumes and does not state

1. **The body's `Rc` is in hand wherever a body starts running** (B1). It is
   not, anywhere but in `dispatch`'s lambda arm, just before it is discarded.
2. **The current stack is fixed for the life of a compiled region** (B2).
3. **Compiled code can read registry state and `autoadd` from `&mut dyn Vm`**
   (S2). `Vm` exposes neither.
4. **A `Slot` has a stable address** (S2). `Vec<Slot>` reallocates on intern.
5. **§S4's call slot is §S6's registry `Slot`**, or has some stated relation to
   it (S6).
6. **Registration ids are per `Registry`.** Each `register_all` on a fresh
   `Interp` mints new ids, and F32's replay means a re-registration gets a
   fresh one (`register_native`'s doc comment: "registrations are replayed
   rather than deduped"). So the `(registration id, Fragment)` table cannot be
   a static in `bund2-stdlib`; it has to be built per registry, at registration
   time. Unstated.
7. **Fragments are validated before use** (S3).
8. **Tier 0 is a correct oracle for `autoadd`** (S1).
9. **A compiled body reproduces the error wrapping of the entry it replaces**
   (§5.6 above).
10. **Tier 0 is flat on every path a compiled body calls back through**
    **[carried, `-09-10` §7.6]**.
11. **A stack-headroom check is expressible** without a crate D10 or D38 must
    rule on **[carried, `-3` §7.9]**.
12. **AOT conformance is RFC-0006's** **[carried, `-3` §7.7]**.

## 8. Recommendation

**Stay Draft.** The fifth review's findings were answered properly and I
confirmed every answer I could run. The meaning guard is the right shape, and
the registry already does its half. The re-measured table holds within 3%.

What is left is below the level the RFC has been reviewed at. Each item is a
place where the design is described at the reference's shape and not yet at
Bund2's. In order:

1. **B1.** Get the `Rc` to the entry point. That is an `api` and frame change,
   so it goes to the owner as RFC-0002 and RFC-0003 amendments. Until it lands,
   §S3, §S5's loop argument and §S7's counter rest on a key Tier 0 never
   supplies.
2. **B2.** Make a current-stack switch a barrier, name the sync target, and add
   `rotate_stack_*` to Q34.
3. **S1–S3.** Cover `autoadd` beyond calls, with a reference-captured oracle and
   an `F` entry for Tier 0's divergence; give the meaning guard an addressing
   mechanism and criterion 17 a threshold; make `Fragment` impossible to build
   invalid.
4. **S4–S7.** Restate D3's argument, reword criterion 10's stop rule, unify the
   two meanings of "slot", fix the `times_fun.rs:37` citation and the stale text.

§S4's chain, §S5's two rules, §S7's `Weak` argument and §S8's analysis still
stand. Criteria 2, 15 and 16 demonstrably hold. Nothing here challenges them.
