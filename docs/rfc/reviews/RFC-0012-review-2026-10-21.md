## Findings, most serious first

### 1. `graph.bellmanford` refuses a graph whose every distance is finite, and says "a distance overflows"

S4 (R:215-220): "`GRAPH.BELLMANFORD: a distance overflows: A -> C`, naming
the edge whose sum first stopped being finite … Every weight is finite, so
a sum that is not overflowed." The code checks **every** candidate sum,
not only the ones that would become a distance. `relax` returns `Err`
before it asks whether the sum is an improvement (`GA:567-570`, before the comparison at `:571-574`).

```
:A [ [ :A :C 1.0 ] [ :A :B 1.0e308 ] [ :B :C 1.0e308 ] ] [ :A :B :C ] graph! graph.bellmanford println
```

- bund2: `GRAPH.BELLMANFORD: a distance overflows: B -> C`.
- The shortest distances are A = 0.0, B = 1e308 and C = 1.0, all finite.
  The sum B → C is a path that is not shortest, and its overflow is
  irrelevant to the answer.
- `graph.paths` over the same graph, in the oracle and in Bund2, answers
  all three rows, `C path=1.0`.

So the word refuses a question that has an answer, and its message names
a distance that did not overflow. S1's row for `graph.bellmanford` (R:143)
offers it as `graph.paths`' drop-in, and here the swap fails with
non-negative weights. That is a case outside both D199's problem statement
and its options. D199 was raised over answers of `inf`, and here there is
none. Only D199's "Built" paragraph ("checks each relaxation's sum") covers
it, and nothing ruled on that.

- No criterion reaches it. Every case in `a_sum_that_overflows_is_refused`
  (`GA:1637-1669`) has a true distance that is not finite.
- Checking only sums that improve a distance does not fix it on its own.
  With the edges listed `[ :A :B … ] [ :B :C … ] [ :A :C 1.0 ]`, the first
  pass meets B → C while C has no distance yet, so the infinite sum *is*
  an improvement at that moment. Which graphs are refused would then
  depend on the order of the edges.
- **Repair:** this needs a ruling in `decisions.md`, not a text fix. One
  option is to refuse only when a distance left after the passes is not
  finite, and to report a distance that reached `-inf` as the negative
  cycle it is. The other is to keep the build and restate S4 as "a path's
  sum overflows", adding this case to the preservation analysis.

### 2. `graph.mst` refuses a total that is exactly representable, because it sums lightest first

`graph_mst` sums the chosen edges in their sorted order (`GA:906`), so
every negative weight is added before any positive one. The intermediate
sum can overflow when the total does not.

```
[ [ :A :B -1.0e308 ] [ :B :C -1.0e308 ] [ :C :D 1.0e308 ] [ :D :E 1.0e308 ] ] [ :A :B :C :D :E ] graph! graph.mst println
```

- bund2: `GRAPH.MST: the total weight overflows`.
- The graph is a path, so all four edges are the tree, and its weight is
  exactly 0.0.

S4 and S5 (R:217-218, R:274-276) say "a sum that overflows is … the
program's numbers". Here what overflows is the order Bund2 adds them in.
This is smaller than finding 1, since it needs weights near `f64::MAX` of
both signs. It belongs with finding 1's ruling, or the text should say the
refusal is of the running sum.

### 3. `graph.mst` answers `weight=-0.0`, not `0.0`, over the empty graph and over a graph with only self-loops

R:146-148: "Over the empty graph, … `graph.mst` answers `edges=[ ]` and
`weight=0.0`". It does not:

```
list list graph! graph.mst println          → { edges=[] :: weight=-0.0 }
[ [ :A :A 1.0 ] ] [ :A ] graph! graph.mst println → { edges=[] :: weight=-0.0 }
```

`total` is `chosen.iter().map(|e| e.2).sum()` (`GA:906`). On the pinned
toolchain (1.95.0), the sum of an empty `f64` iterator is `-0.0`. `println`
shows the sign, so a program sees it, and the third review's finding 5
made `-0.0` against `0.0` a point the RFC states exactly (S3, R:196-197).
`-0.0 == 0.0` holds, so an equality test would not catch this. In any case
**no test covers R:146-148 at all**: nothing in `GA` runs a word over the
empty graph (`grep` finds no `list list graph!`), and criterion 6 does not
name that paragraph. **Repair:** start the fold at `0.0`, or state `-0.0`.
Either way, add a test for the paragraph covering all five of its claims.

### 4. F220 is stated more broadly than it holds, and one consequence is false

R:105-113 and R:347-352 describe Johnson's failure. Three parts of that
text do not match `johnson.rs` or the engines:

- **"with a negative cycle it answers `[]` rather than refusing"**
  (R:350-351). That holds only when the cycle runs through the extra
  source's out-edges, which Johnson replaced. Every other negative cycle
  is found by the Bellman–Ford pass Johnson runs first
  (`johnson.rs:50-53` → `bellman_ford.rs:91-101`), and the word refuses:

  ```
  [ [ :A :B 1.0 ] [ :B :A -5.0 ] ] [ :A :B :C ] graph! graph.allpath println
  ```

  oracle and bund2 both answer: `GRAPH.ALLPATH: returned: negative cycle
  detected in graph`.
- **"which happens when the node listed last has a negative out-edge"**
  (R:348-349) is not sufficient. Johnson reweighs `q → v` as
  `w + h_q - h_v` with `h_q = 0` (`johnson.rs:61-65`). That is below zero
  only when `w < h_v`, and `h_v` can itself be negative:

  ```
  [ [ :B :A -2.0 ] [ :C :A -1.0 ] ] [ :A :B :C ] graph! graph.allpath println
  ```

  `C` is listed last and has a negative out-edge. Both engines answer all
  five rows, `C → A` at -1.0. Also, the rows dropped are those of every
  source whose Dijkstra meets the failing edge, not "that source's rows"
  (R:110-111). With `[ :D :A -0.5 ] [ :A :B 1.0 ]` over `[ :A :B :C :D ]`,
  both engines drop only D's rows and keep the other four.
- **"the node listed last"** should be the last *distinct* name.
  `q = vertices.max()` (`johnson.rs:41-44`), and nodes are numbered at
  first appearance after Title-casing (`make_graph.rs:92-97`). With F220's
  graph listed `[ :C :A :B :C ]`, the last name listed is `C`, but
  `q = B`, and both engines answer all nine rows.

F220 (`defects.md:4302`) has the same wording in its title, though its
"still `[]`" sentence is about its own example. **Repair:** state the
condition as `johnson.rs` computes it, and drop or narrow the negative-cycle
clause. Add a dated note to F220. D200's ruling (preserve) is unaffected.

### 5. "the `graph_operand` the seven share" is not so

R:227-230: "The **shape** of the graph is checked first, in the
reference's words, by the `graph_operand` the seven share". `graph_operand`
(`G:444-447`, whose own comment says "The prologue the three `algos` words
share") is called by `graph.paths`, `graph.allpath` and
`graph.transitiveclosure`, and by the twelve through `operand` (`GA:187-190`).
The other four reference words do not call it:

- `graph.path` repeats the same checks inline (`G:195-227`; reference
  `getpath.rs:14-43`).
- `graph` and `graph.` **do not check `type` at all**. They default it to
  `"graph"` (`mod.rs:38-41`, `G:329-332`), so `MISSED TYPE` and `unknown
  data type` are not their words.
- `graph!` checks nothing (`mod.rs:68-93`).

The claim about the twelve stands. Only "the seven" is wrong, and it is a
claim about code with no citation. **Repair:** "the `graph_operand` that
`graph.paths`, `graph.allpath` and `graph.transitiveclosure` use
(`graph.rs`)".

## What the RFC assumes but does not state

- That a relaxation's sum that is not finite means some distance is not
  finite (finding 1).
- That the running sum's overflow implies the exact total's
  (finding 2).
- That an empty `f64` sum is `0.0` (finding 3).
- That Johnson's extra source is the last node *listed*, and that a
  negative out-edge on it always fails the reweighting (finding 4).
- That every reference graph word shares one prologue (finding 5).
- That a program distinguishing a negative cycle from an overflow does
  not need to (finding 7).
- That `graph.maxflow`'s `flow` and its `edges` shares agree. In floating
  point, `r.cap += b` on a reverse arc that already holds much more than
  `b` can absorb `b` unchanged, so the shares out of the source need not
  add up to `flow`. The bound is unaffected, since the arc is present
  either way. This review did not construct a case, and it is listed as an
  unstated assumption, not a finding. R:288-289 covers the related "share
  of rounding size" point.

## Disposition

**Not ready for Accepted.**

- **Finding 1** is a wrong refusal in a new word, with a false message,
  over weights well inside the range D199 was about. It needs a ruling in
  `decisions.md`, which cannot be fixed in the text alone. Finding 2 belongs
  with it.
- **Finding 3** is a stated answer the word does not give, in a paragraph
  no test covers. It is a one-line code or text repair, plus a test.
- **Finding 4** restates a defect in a core word more broadly than the
  code behaves, and one consequence of it is false. It needs the text
  corrected and a dated note on F220. D200 stands.
- Findings 5–7 are small repairs to text, citations and the register.
