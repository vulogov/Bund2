## Verdict

**Not ready for Accepted.** One finding is again a statement the owner
ruled on. F225, and so D208, describe `graph.allpath`'s rounding defect
more narrowly than it holds. The defect needs no cycle: on an acyclic
graph with a negative weight, `graph.allpath` can answer an edge's
distance as `0.0` where the edge weighs `1.0`. The rest are small.

## Findings, most serious first

### 1. `graph.allpath` loses distances to rounding with no cycle at all; F225 and D208 cover only the missed cycle

F225's title, D208's question and R:167-175 all describe a *negative
cycle* that the potentials round away. But the rounding is in Johnson's
reweighting and un-reweighting, and these lose a distance whether or not
a cycle exists:

- `reweighted = weight + *h_u - *h_v` (`johnson.rs:63`);
- `d + (*h_target - *h_source)` (`johnson.rs:86-87`).

Run today:

```
[ [ :A :B -1.0e20 ] [ :B :C 1.0 ] ] [ :A :B :C :Z ] graph! graph.allpath println
:B [ [ :A :B -1.0e20 ] [ :B :C 1.0 ] ] [ :A :B :C :Z ] graph! graph.paths println
:B [ [ :A :B -1.0e20 ] [ :B :C 1.0 ] ] [ :A :B :C :Z ] graph! graph.bellmanford println
```

- **`graph.allpath`**: `{ from=B to=C weight=0.0 }` in both engines. The
  graph has no cycle. The only path from B to C is the one edge, of
  weight `1.0`.
- **`graph.paths` from `:B`**: `C` at `1.0` in both engines.
  **`graph.bellmanford`** from `:B` also answers `1.0`.
- **How:** `h_B` and `h_C` are both −1e20, since `fl(−1e20 + 1.0)` is
  −1e20. The edge reweighs to `fl(fl(1.0 − 1e20) + 1e20) = 0.0`, Dijkstra
  answers 0.0, and adding back `h_C − h_B = 0.0` leaves 0.0.
- **Which graphs it can affect:** any graph with a negative weight, once
  the potentials grow large against the other weights. A graph with no
  negative weight has every potential at 0.0, because `q`'s edges weigh
  zero (`johnson.rs:45-47`), so the defect cannot occur there.
- **No error is raised.** The distance is simply wrong.

Consequences:

- **F225 is narrower than the defect, which is the pattern D203 was
  raised for.** In F225's own graph, `B → C` answers 0.0 because of this
  rounding, cycle or no cycle. Deleting the `C → B` edge still leaves
  `B → C` at 0.0. F225 says the rows "treat the cycle as free", and its
  test's doc comment (`GA`,
  `allpath_misses_a_negative_cycle_its_potentials_round_away`) says
  "neither edge of the −2⁻⁵² cycle `B ↔ C` relaxes, and both reweigh to
  0.0". Both attribute to the cycle a value that does not need it.
- **D208 was put as "misses a negative cycle".** Whether its ruling
  covers a wrong finite distance on an acyclic graph is the owner's
  question, as D203 put F220's third face to D200. The presumption is
  that it does, since the cause and the crate are the same, but no ruling
  says so.
- **The preservation analysis is incomplete.**
  - R:510-515 lists what a swap to `graph.bellmanford` changes: "an
    answer where `graph.allpath` refused or dropped rows, or an error
    where it answered rows". It omits **a different distance where both
    answer**, as in the graph above.
  - "Negative weights" lists `graph.allpath`'s faces, and this one
    belongs there too.
- **"Current behaviour" (R:167-175) states only the cycle.** A reader
  would conclude that `graph.allpath`'s finite rows are right whenever it
  refuses no cycle.

**Repair:**
- A dated note on F225, and D208's question widened, or a new decision,
  for the owner.
- R:167-175 restated: the potentials' rounding can drop a negative cycle
  *and* misstate a distance with no cycle.
- R:510-515 to add "a different distance".
- A test pinning the acyclic program's `B → C` at `0.0` beside
  `graph.paths`' `1.0`.

### 2. F225's "the other way" claim was unrun when written; it holds

F225 says "a cycle of weight exactly zero far down the potentials can
relax by rounding and be refused as negative". The commit ran no program
for it. Run today, it holds:

```
[ [ :S :A -1000.0 ] [ :A :B 3.700101551766398 ] [ :B :C 0.699993338763802 ] [ :C :A -4.4000948905302 ] ] [ :S :A :B :C :Z ] graph! graph.allpath
```

- **Both engines** answer `GRAPH.ALLPATH: returned: negative cycle
  detected in graph`. The cycle weighs exactly 0.
- **`graph.bellmanford` from `:S`** answers distances, with `A` at
  `-1000.0`.
- **Size matters:** with `1000.0` in place of `-1000.0`, or with
  `-1.0e6`, `graph.allpath` answers 14 rows. Whether the cycle is
  refused depends on the size of the lead edge, not only on how far the
  cycle lies.

**Repair:**
- F225 should carry this program.
- The preservation analysis's "an answer where `graph.allpath` refused"
  can cite it.
- A test would pin it.

### 3. S4 does not list the new refusal

R:276-300, S4's list of `graph.bellmanford`'s errors, does not include
the guard's message, `GRAPH.BELLMANFORD: the graph could need N
relaxations, past the 2^76 its exact sums hold`. It is reachable by no
graph that fits in memory, but S4 is the list of what the words refuse,
and S5 (R:376-378) now calls it an ordinary error. One bullet would fix
it.

### 4. Smaller points

- **R:396, the cost's `f64` side cannot be re-taken.** The figure
  compares ~100 ms with "about 7 ms in `f64`". The program is now
  recorded, but the `f64` relaxation it was compared against was removed
  by `5b8db1a`. Only the exact side can be re-measured. The RFC should
  say that the 7 ms figure comes from `1a587db`.
- **The seventh-review answers table, last row.** It answers the
  assumption "that an `Exact` relaxation's cost stays a constant factor"
  with "scales as `f64`'s did, by about ×14". It does not say whether the
  resulting quadratic worst case is acceptable. Measured today, a
  6,000-node chain listed backwards takes 0.97 s. Extrapolated, 20,000
  nodes would take about 11 s. This is not a criterion, but the RFC
  should state the figure and the owner's acceptance of it, or leave it
  as an open question.
- **Two rounding rules within one family.** `graph.bellmanford` rounds
  each distance once (D207), and `graph.mst` folds its total in `f64`
  lightest first (S5). The RFC states each rule, but nowhere says the
  family has no single rounding rule. A reader comparing the two words'
  sums over the same edges can see different last bits.

## What the RFC assumes but does not state

- **That `graph.allpath`'s finite rows are right when it answers.** They
  are not, once a negative weight makes the potentials large (finding 1).
- **That the 2,000-node cost is representative of acceptable cost**
  (finding 4).
- **That only `graph.paths` sums left to right in `f64` among the words
  compared.** `graph.allpath` rounds three times per edge: in the
  potentials, the reweighting and the un-reweighting. The RFC's
  comparisons of `graph.bellmanford` with `graph.paths` do not extend to
  `graph.allpath` by analogy.
