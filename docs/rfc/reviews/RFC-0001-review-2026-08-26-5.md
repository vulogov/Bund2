# RFC-0001 review 5 — 2026-08-26

Adversarial read of `docs/rfc/RFC-0001-value.md` at commit `e49ad04`. Every
`path:line` in the RFC was opened in this session at the pinned SHAs, and every
figure was re-derived from the tools or from the goldens.

**Verdict: do not accept.** Reviews 1–4 have driven the citations to a state
where I found no citation that resolves to a line saying something other than
what the prose claims — that is new for this document. What blocks it now is a
different class: **two load-bearing negative claims are false, and both fail
inside the crates the RFC itself names as the search scope.** The RFC records
**F39** — "a caller search that stops at four crates finds phantom dead code" —
in its own review history, and then commits the same error twice.

- `impl Iterator for Value` has **six callers** in `reference/Bund/src/cmd/`.
- `q` has **two writers** (`q.rs:5,9`), reached from `impl Add/Sub/Mul/Div`
  (`math.rs:416-453`), reached from `Value::push` (`push.rs:75`) — and a
  registered word produces a value whose `q` is `0.0`.

Beyond those, `Payload` is still used and never defined, though review 4's own
history entry says it was defined; the identity policy contradicts the F34
header-reset rule; and preservation row 1 contradicts rows 12 and 18 on the
`dt` count.

## Blockers

### B1 — `impl Iterator for Value` has six callers, in a crate the RFC says it searched

RFC line 193:

> What makes the disposition tractable is a separate fact: **`impl Iterator for
> Value` has no caller.** Nothing in `rust_dynamic`, `rust_multistackvm`,
> `rust_multistack` or the Bund runtime consumes a `Value` as an iterator, and
> `.curr` is written nowhere outside `iter.rs`. That, not "iteration resets", is
> why every rendering shows `-1`.

And line 571: "`impl Iterator for Value` has no caller in the reference, so
`curr` never advances in a running Bund."

Both are false. `Value` is consumed as an iterator at six sites, all in the
Bund runtime:

| site | iterated expression |
|---|---|
| `reference/Bund/src/cmd/bund_cluster.rs:35` | `for n in value`, `value: Value` from `zenoh_get_internal` |
| `reference/Bund/src/cmd/bund_cluster.rs:40` | `for snippet in val`, `val` from `n.at(2)` |
| `reference/Bund/src/cmd/bund_cluster.rs:305` | `for n in value`, from `zenoh_get` |
| `reference/Bund/src/cmd/bund_cluster.rs:310` | `for v in val` |
| `reference/Bund/src/cmd/bund_bbus.rs:172` | `for n in value`, from `zenoh_get` |
| `reference/Bund/src/cmd/bund_bbus.rs:177-178` | `n.at(1)` / `n.at(2)`, then iterated |

`zenoh_get` and `zenoh_get_internal` both return `Result<Value, Error>`
(`reference/Bund/src/stdlib/helpers/zenoh/putget.rs:80` and `:119`). Both
modules are declared and compiled (`reference/Bund/src/cmd/mod.rs:20,21`).

**Why this is a blocker and not a citation nit.** Three things in the design
rest on it:

1. **The preservation row.** "`curr` as the iteration cursor | Preserved as a
   field. **Nothing advances it today**" — it does advance, on the cluster and
   bus paths.
2. **The CoW policy has never been applied to iteration.** Review 4 moved
   `curr` out of a `Cell` and made it "a plain field now, split by `make_mut`
   like any other". The reference's `next()` takes `&mut self` and writes
   `self.curr` **in place** (`reference/rust_dynamic/src/iter.rs:11,24,27`) —
   a minting-free mutation, structurally identical to `set_tag`. Under
   `Rc::make_mut` on a shared value that write splits, so the original's cursor
   does not advance and the loop does not terminate the way the reference's
   does. Under this RFC's own rule — "a CoW split materialises the identity
   before it copies" — it also mints an identity **per iteration step**.
   None of that is discussed, because the RFC believes the path is dead.
3. **`.curr` written nowhere outside `iter.rs`** is the narrower claim and is
   true; it is the *reads* through `Iterator::next` that were missed. The RFC
   uses the false claim to explain why every golden shows `-1`. The true
   explanation is narrower and still available: no *corpus* program reaches
   `bund cluster` or `bund bbus`.

This is F39's failure mode exactly, in the document whose review history
records F39. The RFC even names its search scope ("the Bund runtime"), and
`Bund/src/cmd/` is inside it.

### B2 — `q` has writers, and a registered word produces `q: 0.0`

RFC line 199:

> **`q` is the only one that is genuinely constant in reach.** `set` copies it
> (`set.rs:33`) and `push` copies it (`push.rs:164`); neither changes it, **and
> no word writes it**. `Value::new` sets `q: 0.0`
> (`reference/rust_dynamic/src/value.rs:38`) **but nothing reaches it** — the
> `nodata` word yields `dt: 97` with `q: 100.0`, confirmed by probe. Q18 closes
> on this, grounded.

The design turns that into "`q` is not a field: it is rendered", and the
preservation table into "`q` rendered as `100.0` | **Preserved as text.** Not
carried. Grounded by Q18: no word writes it."

Two separate things are wrong.

**(a) `q` has two writers, and neither is cited anywhere in the RFC or in
Q18.** `reference/rust_dynamic/src/q.rs` — a file the RFC never mentions —
contains:

```
 4:    pub fn calc_q(&mut self, other: Value) -> &mut Self {
 5:        self.q = (self.get_q() + other.get_q())/2.0;
 8:    pub fn set_q(&mut self, q: f64) -> &mut Self {
 9:        self.q = q;
```

`set_q` is called from `impl Add`, `impl Sub`, `impl Mul` and `impl Div` for
`Value`, each of which averages the operands' `q` and writes it onto the
result: `reference/rust_dynamic/src/math.rs:416,419` (Add), `:429,431` (Sub),
`:440,442` (Mul), `:451,453` (Div).

So `q` is not a constant. It is an **averaged, propagated** field — which is
also the only reading under which `set.rs:33`'s and `push.rs:164`'s
`res.q = self.q` make sense as design rather than as copying dead weight.
(The RFC cites only `set.rs:33`; the same copy is at `set.rs:60` and `:93`.)

The arithmetic **words** do not reach `impl Add`: `stdlib_math_op_inline` calls
`Value::numeric_op` directly
(`reference/rust_multistackvm/src/stdlib/math/math_op.rs:103`). But
`Value::push` does — `res = res + value` in the `TEXTBUFFER` arm
(`reference/rust_dynamic/src/push.rs:75`) — so a `push` onto a text buffer
averages `q`. `push` and `text` and `convert.to_textbuffer` are all registered
words in scope.

**(b) A registered word produces a value whose `q` is `0.0`.** `Value::none()`
is `Value::new()` (`reference/rust_dynamic/src/create_special.rs:19-20`), which
writes `q: 0.0` (`value.rs:38`). It is reached from Bund:

`json.to_value` is a registered inline word
(`reference/rust_multistackvm/src/stdlib/json/conversion.rs:60`); it calls
`cast_json_to_value` (`:38`); and for a JSON **null** that returns
`Value::none()` (`reference/rust_dynamic/src/cast_json_to_value.rs:38-39`, and
the same at `wrap_json.rs:38-39`). `json.to_value` is in scope —
`docs/core-words.md:66`, library side. `conv.rs:68` compounds it: converting a
`NONE` to a `LIST` wraps another `Value::none()`.

So `<json null> json.to_value` leaves a value that the reference renders with
`q: 0.0`, and RFC-0001 would render `q: 100.0`. Criterion 6 asks the `Debug`
rendering to reproduce the reference's text "including `q: 100.0` as a
constant"; on that value it does not.

**What is true** is narrower and worth having: every rendering in the current
corpus shows `q: 100.0`, because the only non-`100.0` constructor is
`Value::new` and no corpus program reaches it. That is a fact about the corpus.
The RFC states it as a fact about the language, and Q18 is marked "grounded"
on a scan that never opened `q.rs` or `math.rs`.

Three things need to change: cite the writers, restate the claim as
corpus-scoped, and say what Bund2 does when a `q` other than `100.0` is
producible — carry the field, or take the divergence explicitly with a
preservation row.

*(Checked and ruled out, so the report stays honest: `Value::curry`,
`ptr_curry`, `lambda_curry` and `Value::maybe` — the other `Value::none()`
users — have zero callers across all six crates, and the `curry` word builds a
`CONDITIONAL` through `Value::conditional()` instead
(`reference/Bund/src/stdlib/functions/conditional/conditional_curry.rs:18`).)*

### B3 — `Payload` is used, referenced as defined, and is not defined

`HeapValue` declares `payload: Rc<Payload>` (line 264). Two preservation rows
point at a definition: "`Payload` uses `BTreeMap`, so both rendering paths are
ordered" (line 598) and "Recorded in the `Payload` definition" (line 599). The
review-4 history entry says (line 887):

> **`Payload` was used and never defined** … It is defined now, with `BTreeMap`
> for both map kinds — F15's actual request — and with the arms F36 and F38
> rule out omitted.

There is no `Payload` definition in the document. `grep -n Payload` returns
lines 264, 598, 599 and 887 and nothing else. This is review 2's failure mode
inverted: there, an edit inserted instead of replacing; here, the history
records a change that did not land.

What is unanswered as a result:

- **F15's actual request** — "choosing a deterministic map for the value
  representation, which is RFC-0001 territory". `tags: BTreeMap` is specified;
  the *dict payload* is not, and F15's second surface is the `Map({...})`
  `Debug` rendering of an OBJECT, which is the payload.
- **F36's request** — "Record the omission in RFC-0001's tag table". See B4.
- **Which of the twenty `Val` arms survive.** `Val::Exit` in particular: F39
  establishes that every parsed program ends with an `EXIT` value and that
  three evaluation loops break on it, so it is one of the most-executed arms in
  the language and the design does not say it exists.

### B5 — the identity policy and the F34 header-reset rule disagree, and both fire on `set`

Three statements, in three sections:

1. §"One policy for the `Rc` and the identity slot" (line 346): "**a CoW split
   materialises the identity before it copies** … Both halves then carry the
   same concrete id."
2. §"Value semantics" (line 368): "**every mutating operation that the
   reference gives a fresh id to is a CoW split point** (`set.rs:16,31,43,58,76,91`,
   `push.rs:165`, `attr.rs:7,13,19`)."
3. §"Mutation resets the header" (line 457): "a container mutation in Bund2
   **clears** `attr`, `curr` and `tags` … matching the constructors rather than
   matching `make_mut`."

`set` on a map is in class 2 and in class 3 simultaneously. Under rule 1 the
receiver and the result end up carrying the *same* concrete id; the reference
gives them **different** ones — `set.rs:15` dups, `:16` mints, and the returned
value comes from `Value::from_dict` at `:21`, which mints again
(`create_map.rs:33`). Under rule 3 the result's header is rebuilt, which under
laziness means an **unminted** slot — the opposite of "materialise before it
copies".

Rule 1 is correct for the minting-free class, of which the RFC says `set_tag`
is the only reachable member, and it is justified in the text only from
`Clone` + `set_tag`. It is wrong as stated for `set`, `push` and `attr_add`.
D13 asks for "one policy governing both"; what the RFC has is one policy that
covers one of the two classes it enumerates. The preservation rows "Fresh id
per mutation | Preserved exactly" and "`set_tag` … | Preserved exactly" are
each individually satisfiable and not jointly satisfiable by the stated rule.

## Citation defects and imprecisions

No citation resolves to a line that says something other than what the prose
claims — the first pass on this RFC where that is true. What remains:

**C1. The split-point enumeration is presented as exhaustive and is not.** RFC
line 368 says "**every** mutating operation that the reference gives a fresh id
to", and lists ten sites. D1's own list — which the RFC consumes — adds two
more: `bincode.rs:95` and `id.rs:6`. The reference adds more still, all through
`regen_id` (`id.rs:5-6`, which mints the id *and* resamples the stamp):
`pull.rs:53`, `map.rs:55,69`, `func.rs:13,15`, `applicative.rs:10`,
`ctxapplicative.rs:10`. `pull` is not an obscure path. Either the enumeration
is closed and should be complete, or it should say it is representative.

**C2. `push.rs:165` is the least representative arm of `push`.** It is the
catch-all (`push.rs:162-168`), which *replaces* the receiver with the pushed
value rather than mutating a container. The container arm returns
`Value::from_list(data)` (`push.rs:48`) and mints through the constructor — the
F34 shape, not the mint-in-place shape the citation is offered for. Both D1 and
D13 inherit this citation, so it is not this RFC's error alone.

**C3. `eq.rs:59-62` for `impl Eq`.** The impl is `:60-62`; `:59` is blank.
Trivial, but the RFC and D30's amendment both use the range.

**C4. `q` copying is cited at two of four sites.** `set.rs:33` and
`push.rs:164` are cited; `set.rs:60` and `:93` do the same and are not.

## Preservation analysis — behaviours the design changes that no row covers

The table has 26 rows and every one I checked against its cited defect matches
that defect's disposition. These are the omissions.

**P1. `Value::has_key` on a `VALUEMAP` has no row.** `has_key` omits `VALUEMAP`
from its arm and its catch-all answers false
(`reference/rust_dynamic/src/has_key.rs:7,19-20`) — a **value-layer** defect,
squarely RFC-0001's territory, and half of what `?key` needs. The RFC points at
Q19 in Open questions and specifies nothing. `Value::get`'s `VALUEMAP` gap gets
a row (F29); its sibling does not.

**P2. `stamp`'s reset by `set` and `push` has no row.** D2 states it
explicitly: "`set` and `push` continue to reset it (`set.rs:32,59,92`,
`push.rs:166`), which under deferred sampling means **resetting it back to
unobserved**." The RFC cites none of those four lines, and F34's row names only
`attr`, `curr` and `tags` — but `from_dict` also mints a fresh `id`
(`create_map.rs:33`) and a fresh `stamp` (`:34`). The identity and stamp halves
of the header reset are exactly where B5's contradiction bites, and neither
appears in the table.

**P3. `set` on a `LIST`/`RESULT` discards the container and drops the `dt`.**
`set.rs:8-10` returns `Value::from_list(vec![value])` — the key is ignored, the
existing elements are thrown away, and a `RESULT` becomes a `LIST`. That is
F35's defect in the `set` word rather than the `push` word, and F35's
disposition explicitly contrasts the two: *"the way `set` already does for
maps … The asymmetry between `set` restoring the tag and `push` not is the
defect."* `set` restores the `dt` for **maps** (`:22`) and not for lists. No
row, no defect entry, and the F35 row's justification reads as though `set`
preserved `dt` generally.

**P4. `Ord::cmp`'s `id.cmp` fallback survives F12's fix, and the row says it is
"deliberately fixed".** F12's disposition is narrow: *"Bund2 implements
`Ord::cmp` with a proper `Val::F64` arm, consistent with `partial_cmp`."* The
`id.cmp` fallback for the fifteen identity-compared arms
(`ord.rs:199`) is untouched by that. The row titled "Ordering falling back to
`id.cmp` | **Deliberately fixed**" claims the whole fallback goes. It does not,
and it must not — it is one of D1's three internal id readers and the RFC's own
§Equality says so at line 147.

**P5. `Value::context()` mints a nanoid into the *payload*.**
`reference/rust_dynamic/src/create_special.rs:28` writes
`data: Val::String(nanoid!())` — a second, payload-level identity distinct from
`id`. Under lazy identity a CONTEXT value must still mint that one eagerly at
construction, which is the single exception to "nothing is computed at
construction". No row, no mention.

**P6. The `Debug` rendering must be hand-written, and the RFC never says so.**
A derived `Debug` on `BundValue` prints `Heap(HeapValue { … })` with
`HeapValue`'s own field order — `identity, stamp, dt, curr, tags, attr,
payload` as declared at lines 257-265. The reference prints
`Value { id, stamp, dt, q, data, attr, curr, tags }` — a different type name, a
different field order, and a `q` that is not a field at all. Criterion 6 rests
entirely on this and §Rendering says only that "the rendering must reproduce
the reference's text exactly". That it is an explicit `impl Debug` rather than
`#[derive]`, and that the field order is part of the contract, are unstated.

**P7. `dt` is a plain immutable field, and the reference assigns it after
construction.** `dt: u16` in `HeapValue` sits behind an `Rc`. The reference
writes `dt` post-construction in at least three places the RFC itself cites —
`create.rs:166` (`PAIR`), `:186` (`MESSAGE`), `set.rs:22` (restoring the
container tag). Each of those becomes a `make_mut` under this design, hence a
CoW split, hence (under B5's rule) an identity materialisation — on the
construction of every pair and every message. No row.

## Consistency with accepted RFCs, decisions and ERRATA

- **D14 is stated as OPEN and is RESOLVED.** RFC line 749: "**D14** is OPEN and
  governs which words exist". D14 has been RESOLVED — method B″, core 286 —
  since commit `f62be91`, and RFC-0002 consumes it. The header's "**No OPEN
  decision or question gates this RFC**" is right; the Open-questions bullet is
  stale.
- **Q19 is OPEN, and the header sentence should acknowledge which side of it
  RFC-0001 sits on.** Q19's value-layer half is `has_key` (P1), which is this
  RFC's to specify. As written the RFC lists Q19 as a residue of D30 without
  saying that a `Value` method's behaviour is left undefined by it.
- **RFC-0002 depends on a property RFC-0001 never states.** RFC-0002's registry
  is `Rc<Registry>` rather than `Arc` because `BundValue` is neither `Send` nor
  `Sync` — `Rc<HeapValue>` plus `Cell` fields. RFC-0001 defines both and never
  draws the thread-affinity consequence, so the collision was found in
  RFC-0002's fourth review rather than declared here. Worth a sentence in
  §"The heap object": this type is single-threaded by construction, and every
  later RFC inherits that.
- **ERRATA is consistent** with everything in the RFC that touches it.
- **RFC-0000's B1/B4/B5 are unaffected**; B5's `cite` figure (1059 at
  acceptance) has since grown to 1238 with the register work, which is
  expected.

## What the RFC assumes but does not state

1. **`Payload`'s definition** — arms, map types, and whether `Val::Exit`
   survives (B3).
2. **That `Debug` is hand-written and field-ordered to match the reference**
   (P6).
3. **That `q` is renderable as a constant** — which requires that no reachable
   constructor writes anything else (B2).
4. **That `impl Iterator` is not a live path** — which requires the six sites in
   `Bund/src/cmd/` not to exist (B1).
5. **Which rule fires when a mutation is both a mint site and a header rebuild**
   (B5).
6. **What the identity counter's scope is.** Criterion 8 says "two values minted
   in **one VM** never collide", and D1 says "counter plus VM seed". Nothing
   says what happens across VMs — and `bund.eval`, the actor path
   (`run_snippet_as_actor`) and `bundcore` each construct one
   (`reference/bundcore/src/bundcore.rs:18`, `bundvm.rs:26`,
   `reference/rust_multistackvm/src/multistackvm.rs:36`). A nanoid collides with
   probability zero; a per-VM counter formatted into nanoid shape does not,
   unless the seed makes it so. The RFC says "preserving the format" and leaves
   the uniqueness argument to the seed without stating it.
7. **That `set_tag` is the only reachable minting-free mutation.** Stated as
   fact at line 372 ("of which `set_tag` is the only one reachable") with no
   citation and no enumeration of what was searched. Given B1 and B2, this
   claim now needs the same six-crate treatment before it can be relied on —
   and `Iterator::next`'s in-place `self.curr` write is a second one.
8. **That the boxing predicate is exactly "acquires anything a header holds".**
   Line 409 lists five triggers; `dt` is a sixth — a `Bool` is `dt: BOOL` and a
   `Nodata` is `dt: NODATA`, but `Val::String`'s six tags mean a scalar arm
   cannot carry an arbitrary `dt`. The enum has five scalar arms against 38
   live tags; which tags are representable unboxed is never stated.

## Summary of what must change before acceptance

1. Withdraw the "`impl Iterator for Value` has no caller" claim, cite the six
   sites, and say what `make_mut` plus the identity policy do to an iteration
   step (B1).
2. Cite `q.rs:5,9` and `math.rs:416-453`, restate "no word writes it" as the
   corpus-scoped claim it is, and decide whether `q` is carried or the
   `json.to_value` divergence is taken with a row (B2).
3. Define `Payload` — F15's map choice, F36/F38's omissions, and `Val::Exit`
   (B3).
4. Reconcile row 1's "42 constants" with rows 12 and 18, and record F36's "38
   live of 42" in the tag table (B4).
5. Split the identity policy into the minting class and the minting-free class,
   or state which wins at `set`/`push`/`attr_add` (B5).
6. Fix "65 goldens" → 66, the leftover "24" → 29, and "dup-family" → `dup`
   (N1–N3).
7. Label criterion 5 as vacuous and criterion 7 as having no runner yet;
   restate criterion 6 against the *normalised* golden text (A1–A3).
8. Add rows for `has_key`/`?key`, the `stamp` reset, `set` on a

   consequence of `Rc` + `Cell` that RFC-0002 already relies on.
