## Should fix

### SF1. The bounding guarantee is false for S8's `<summary>` rows

**The RFC says** (RFC:695-712): every value a text interpolates from the program is rendered by the frame words' renderer, "So no refusal is unbounded and none breaks across lines". The list of such values is "a cell, a CSV field, a column, header, level or result name, a group's key, the first character after a closing quote".

**But seven rows interpolate `<summary>`.** Each is a whole operand or a non-STRING part of one, rendered by `summary`, which the preamble itself says does not escape:
- RFC:724: `frame is outside <w>'s domain: <summary>`, a non-MAP frame operand;
- RFC:726: `column name 3 is <summary>`;
- RFC:728: `column "x" is <summary>`;
- RFC:730: `levels is <summary>` / `hold <summary>`;
- RFC:741: `levels is outside <w>'s domain: <summary>`;
- RFC:742: `list is outside <w>'s domain: <summary>`;
- RFC:752: `text is outside <w>'s domain: <summary>`.

Any of these operands can be a STRING holding a line break. A LIST holding one does the same: `summarise`'s `List` arm recurses into each item (`lib.rs:1686-1700`), so a nested STRING is printed unescaped. Probed with an existing E101 that uses the same `summary(WIDTH)`: `'"x\ny"' json json.to_value [ 1.0 2.0 ] swap vec.scale` reports `k is outside vec.scale's domain: "x`, and then `y"` on the next line. So `'"a\nb"' json json.to_value frame.nrow` would break row 724's text the same way, and `"a\nb" na.count` would break row 742's.

**Suggested fix.** Either of these:
- Make `<summary>` mean the renderer for a STRING operand and `summary(WIDTH)` otherwise. Then say that a container's nested STRINGs are shown as `summary` shows them, so the one-line guarantee covers top-level values only.
- Narrow RFC:711-712 to the listed values. Say that `<summary>` rows inherit RFC-0015's texts, line breaks included.

Either way, criterion 9's palette could add a STRING with a line break as a non-frame operand.

### SF2. The options exemption rests on a reader the frame words cannot call

**The RFC says** (RFC:713-717, listed RFC:1043-1044): "the options rows' texts are RFC-0016 §S1's shared reader's (`biomath/infer/opts.rs`), which escapes an unknown key but does not truncate it; bounding that is a change to RFC-0016's words, outside this RFC". Rows RFC:758 and :760 give their text as "as RFC-0016 §S1".

**What the code holds:**
- **The reader is not shared.** `opts::read` is `pub(super)` (`opts.rs:67`), visible only inside `biomath::infer`. It recognises a fixed `KEYS = ["alternative", "conf", "mu"]` (`:62`) and answers an `Opts { alternative, conf, mu }` (`:55-59`).
- **The only other options reader is private too.** `ode.rk45`'s `rk45_opts` (`dynamics.rs:223`) is private, with its own four keys.

None of `header`, `na`, `factors`, `sep`, `descending` or `how` can pass through either reader. So the frame words must write their own options reader, and its texts are this RFC's to set. Bounding them changes no RFC-0016 word.

**The inheritance is also wider than stated.** A wrong-typed or out-of-range value is rendered with `x.summary(WIDTH)` (`opts.rs:92`, `:98`, `:105`), which does not escape. Probed: `[ 1.0 2.0 3.0 ] '{"alternative": "two\nsided"}' json json.to_value stat.test.t1.opts` reports `alternative is outside stat.test.t1.opts's domain: "two`, and then `sided"` on the next line.

**And "as RFC-0016 §S1" names no text.** RFC-0016 §S1 states the rules (`RFC-0016-statistical-inference.md:198-204`: unknown key, key not taken, wrong type or range, each E101 naming the key), not a text. The texts exist only in `opts.rs`'s code (`an unknown key "k"`, `the key "k", which this word does not take`). So rows RFC:758 and :760 fall short of D256 S3's "every refusal listed with its text".

**Suggested fix.**
- Give the frame words' options reader its texts in S8, in `opts.rs`'s words for familiarity, with keys and values passed through the renderer: `opts is outside <w>'s domain: an unknown key "k"`, `… the key "k", which this word does not take`, `<key> is outside <w>'s domain: <rendered value>`.
- Drop the exception at RFC:713-717 and its list entry.
- Optionally say that a later change could move RFC-0016's reader onto the same renderer.

### SF3. The operand-naming sentence names the wrong operand for two words, and contradicts S1 and S6 for a third

**The RFC says** (RFC:689-693): "In the frame check's rows, `frame` stands for the operand the check reads: `left` or `right` for `frame.join`, `columns` for the frame `frame.new` builds, `list` for the column `frame.with` adds **[author]**. `frame.csv.parse`'s answer is built valid and not checked."

1. **`frame.new` (`names columns -- frame`).** Row 726's faults are faults of `names`: a name that is not a STRING, empty, or repeated. Read literally, the sentence makes them `columns is outside frame.new's domain: a repeated name "x"`. Only rows 728, 729 and 731-734 (columns, lengths, cells) are about `columns`.
2. **`frame.with` (`frame name list -- frame`).** Row 726 is also the only rule that catches an empty or non-STRING `name` (the ninth review's N2). The sentence makes that `list is outside frame.with's domain: …`, naming the wrong operand.
3. **`frame.csv.parse`.** "Built valid and not checked" contradicts two passages:
   - S1 (RFC:225-227): "the cells it takes from outside a frame (`frame.new`, `frame.with`, `frame.csv.parse`) are checked as part of it";
   - S6 (RFC:576-578): a quoted number among unquoted numbers "is therefore a STRING in a numeric column, which the frame check refuses with E103".

   Under D254 the reader cannot build a valid frame from such text. Nor can it from a quoted `"x"` in a column whose unquoted fields are BOOLs (row 734's mixture). So the sentence is wrong, not merely redundant. If the answer is checked, the texts need an operand: the E101 mixture text would otherwise read `frame is outside frame.csv.parse's domain`, an operand that word does not have. The sentence is new since revision 5 (`git diff 625edb2`) and carries no **[author]** mark. No criterion pins either reading: criterion 6 has no quoted number among unquoted numbers (RFC:898-921).

**Suggested fix.**
- Map row 726 to `names` for `frame.new` and to `name` for `frame.with`, and the other rows to `columns` and `list`.
- Replace the `frame.csv.parse` sentence with "`frame.csv.parse`'s answer is checked, its texts naming `text`".
- Add to criterion 6: `x\n1\n"2"\n` is E103 naming `"2"` at row 2.

## Notes

**N1. S5's refusal order leaves out the frame check.** S2 says every `frame.` word checks its frame "on entry" (RFC:275). The order paragraph (RFC:453-458) begins "the operand and option checks first …, then the frame's cells under `na`". The phrase "the frame's cells" can be read as the frame check running second. Also, the `by` and `stats` name checks (S8 rows RFC:738, :744) need a valid frame to resolve a name's kind. Say "the frame check first (S8's first eleven rows), then the operand and option checks, then …". The ninth review's assumptions carried the general question (frame check against other operand checks); this paragraph was the place to settle it for one word.

**N2. Criterion 5's order case cannot fail the obvious alternative.** RFC:881-883 tests "a group failing E101 for `"var"` before another failing E114 for `"mean"`". An implementation that size-checks every group before computing anything also answers E101 there, against S5's interleaved order. Add the reverse case: the E114 group first in the answer's order and the E101 group later, answering E114.

**N3. Truncating after escaping can split an escape.** Step 2 cuts the escaped text at 37 characters plus `…` (RFC:705-707). If character 37 is the `\` of `\"` or `\n`, the text ends `\…`, which reads as an escaped `…`. Say that a cut never splits an escape: drop a partial escape before the `…`. Also, step 1's `\u{…}` uses the truncation glyph as a placeholder; write `\u{hex}`.

**N4. The `[author]` list says "truncated to `WIDTH`"** (RFC:1041-1042). The body truncates to `WIDTH` − 2, then quotes (RFC:705-708). Make the list match.

**N5. Row RFC:743 spells `NONE`:** `column "x" row 3 is NONE (na "refuse")`. The preamble says NONE prints as `none` (RFC:710-711). If `NONE` here is a kind word, like row 731's `a LIST`, say so. Otherwise write `none`.

**N6. The q of a NONE the frame words make is unpinned.**
- S1 (RFC:232-233) says cells a word makes "carry q as their constructor gives it". S3 pins `na` at q 0.0, criterion 3 checks it, and JSON's `null` is the same (`json.rs:112`).
- But Bund2's bare constructor `BundValue::none()` is an unboxed scalar (`lib.rs:636-638`), and an unboxed scalar's `q()` is 100.0 (`:1792-1796`).
- So the NONEs that `frame.csv.parse` reads from an `na` string, and that `frame.join` puts in `"left"`'s unmatched rows, could carry q 100.0 beside `na`'s 0.0 in one frame.
- `frame_eq` ignores q (RFC:297), so no criterion would notice.

Say that every NONE a frame word makes is `na`'s, q 0.0.

**N7. S4's FLOAT-by-value rule is already D108's.** D108 orders "integers and floats, together … by the value they denote (D33)" (`decisions.md:12112`). That makes `-0.0` equal to `0.0` for `sort`. RFC:372-377 marks the rule **[author]**, and RFC:1046-1047 lists it as unruled. Citing D108's rank 1 grounds it and shortens the owner's list. The stability half, keeping row order, remains the RFC's own: D108's quicksort is not stable (`:12119-12121`).

**N8. A group text is bounded per key, not in total.** Row RFC:747 shows "every key shown, each bounded". A `by` of k columns gives a text of up to about 41·k characters. RFC:711's "no refusal is unbounded" is true of each value, not of each text. Either say "bounded per value", or cap the keys shown (for example, the first 8 and then `…`).

## What the RFC assumes and does not state

- **That the frame words write their own options reader** (SF2). RFC:713-717 assumes they can reuse RFC-0016's.
- **Where the frame check runs** against the other operand checks in every word, not only `frame.aggregate` (N1; carried, and widened).
- **That every NONE a frame word makes has `na`'s q** (N6).
- **What E112 says when `frame.filter`'s lambda leaves nothing.** `ask` answers `None` for an empty scratch stack (`bridge.rs:114`, `pull_from`), and `call` reports `left nothing` (`dynamics.rs:82-84`). RFC:364-368 says only "a result other than a BOOL" (carried).
- **That a final line without a terminator is a record** (carried; RFC:543-544 states terminated lines only).
- **That an `na` string matches by exact bytes**, case-sensitive and untrimmed (carried).
- **That `frame.text` of a frame with columns and no rows prints its header row alone** (carried).
- **That a group text's length grows with `by`** (N8).
- **That `file`'s path is absolute, and that `file` may fetch over HTTP** (carried; `host.rs:1455-1470` shows the HTTP arm).
- **That a row MAP per row in `frame.filter` and `frame.rows` is affordable at Tier 0** (carried).
