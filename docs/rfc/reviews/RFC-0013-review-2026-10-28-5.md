## Should-fix

### S1. Criterion 4 fails under the JIT for a reason that is not recursion

The probe compares the address of a local in a test native, sampled at the
10th answer and at the 1,000,000th. `lambda` runs once per answer, so it
is hot long before the millionth. A body is compiled "within the first few
thousand rounds" (the comment on `a_running_program_is_stopped_at_its_next_call`,
`oom_guard.rs`).

From then on, the probe native is called from compiled code, through a
different chain of Rust frames than the interpreter's `run_to`. Under
`--features jit`, which the suite runs, the two addresses can differ with
no recursion in the engine. *PLAUSIBLE: not measured, since the engine
does not exist yet.*

**Fix:** take both samples after the compile point (say the 100,000th and
the 1,000,000th answer), or run the criterion at Tier 0 only and say so.

### S2. The choicepoint preamble's distinguishing sentence is wrong for `Not`

It says that where the table names "the continuation", that kind "resumes
with a goal list other than the one current when it was pushed". `Not` is
pushed after the loop pops the `not` goal, when the current goal list is
`rest`, and it resumes with `rest`: the same list.

The sentence explains nothing that the "On backtrack" column doesn't
already say. **Fix:** drop it, or state per kind what it resumes with.

### S3. Criterion 12a's last clause names no test

"A file placed in `src/kb/` with an `Error`-severity report fails it"
describes a mutation, done by hand. No named test checks it.

`nothing_shipped_follows_a_test_module` already counts the files it reads
(`files += 1`). The same shape would do here: assert that the scan read a
file under `kb/`. That catches a scan that stops recursing.

### S4. Criterion 20 still has no program for two of its E54 cases

Revision 6 wrote out the `p`/`q` program. "An `if` whose condition calls
an evaluating table, and a `findall` over one" still have no KB.

Two lines would do: tabled `p/0` and `q/0`, with `[ [ q ] ← [ p ] ]` and
either:
- `[ [ p ] ← [ if [ [ q ] ] [ true ] [ fail ] ] ]`, or
- `[ [ p ] ← [ findall X [ [ q ] ] L ] ]`.

## Notes

- **N1. `debug.display_stack` does not show a stack's name.** It renders
  the current stack's values (`vm.snapshot()`). While λ runs, that is the
  scratch stack's contents, unnamed. Only `stack_names` and `save.stacks`
  expose the id. S5's "What λ can see" overstates `debug.display_stack`'s
  part.
- **N2. Criterion 20's second KB is argued, not shown, to discriminate.**
  Traced by hand, the correct join rule answers `h`. Whether a *wrong* one
  (merging from V's entry instead of V's SCC root) loses `h` depends on
  what that implementation records for a non-root merge, which the RFC
  can't know. A unit test on the completion stack's merge, over the same
  call sequence, would pin the rule directly.
- **N3. Q44's register row is broader than the RFC now is.** The RFC's
  worked-examples preamble says the operand orders were re-read and hold,
  and that only the run itself is open. The row in
  `docs/registers/open-questions.md` still says the examples are unchecked
  in general.
