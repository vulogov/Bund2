## Blocking

### B1. An absent interval key does not answer NODATA: `get` fails, and A3's ruling was explained on that premise

**Location.** S2 "Infinite ends [A3]" (lines 303-308): "A program asks `"upper" get` and meets NODATA, as for any absent key." D251 A2's amendment (`decisions.md:17236-17238`): "an absent `lower` or `upper` means only an infinite end (A3)".

**Evidence.**
- **The reference.** `get` on a MAP without the key is an error:
  - `Value::get` returns `Err("Key not found: …")` (`reference/rust_dynamic/src/get.rs:10-12`);
  - the word bails with `GET returns error: {}` (`reference/rust_multistackvm/src/stdlib/values/value_dict.rs:62-67`).
- **Bund2** mirrors it (`crates/bund2-stdlib/src/values.rs:156-161`).
- **Probed.** `dict "a" 1 set "upper" get println` stops the program with `GET returns error: Key not found: upper`.
- **The word that tests presence** is `?key` (`value_dict.rs:122`; in `bund2 words`).

**Problem.**
- The RFC states a behaviour of an existing word with no citation, and it is false.
- Under A3's option A, every one-sided `.opts` call has an absent `upper` or `lower`. The same holds for Fisher at the support's maximum and for Pearson's `statistic` at |r| = 1. A program written as the RFC describes, `"upper" get`, is stopped with an error rather than handed a NODATA it can test.
- The option the owner ruled against, C, is literally "NODATA in a two-element LIST". So the difference between A and C as presented rested on this misstatement. Under CLAUDE.md, a ruling made on a wrong premise is the owner's to confirm, not the RFC's to keep.

**Suggested fix.**
- Replace the sentence: "a program tests `"upper" ?key` before `get`; `get` on an absent key is an error (`reference/rust_dynamic/src/get.rs:12`)".
- Add criterion text checking that `?key` answers false for the absent end.
- Take A3 back to the owner as a confirmation, with the corrected consequence, as a dated note on D251 (A3 confirmed or re-ruled). This is the same kind of step as A7's confirmation.

## Should fix

### S1. The floor is not conservative where it applies: n = 2, m ≥ 50 at 90% covers below conf

**Location.** S2 "Mann–Whitney [A9]", the normal branch (lines 290-293): "The floor is Bund2's choice and is conservative". D251's A9 amendment (`decisions.md:17261`): "A's floor where the exact distribution does not apply, conservative".

**Evidence (`rev4_levels.py`).**
- **Inside the floor branch.** The floor is used with no ties whenever n or m ≥ 50. For n = 2…5 and m = 50…200, at 90% two-sided, the floor's k exceeds the exact k in **217 of 604** size pairs. Its interval then covers below conf. For example, at n = 2, m = 52, exact k = 15, floor k = 16, and coverage is 1 − 2·P(U ≤ 15) = **0.89937**.
- **Inside n, m < 50,** at levels not in D251's table, the floor is above the exact k:
  - 19 pairs at 90% one-sided (worst n = 2, m = 23);
  - 19 pairs at 80% two-sided;
  - 34 pairs at 70% two-sided;
  - 1 pair at 90% two-sided (n = 2, m = 49).
- **Inside the measured range** (2 ≤ n ≤ m ≤ 20), the claim holds at 0.80, 0.90, 0.95 and 0.99, one- and two-sided.

**Problem.** "Conservative" is stated without its range. It fails precisely in the regime where the floor is used for untied data: a small sample against one of 50 or more. The exact branch's condition, "n, m < 50", bounds each size. But what u128 needs is C(n + m, n) < 2¹²⁸, and for n = 2 that holds for any practical m.

**Suggested fix.**
- Restate the property as measured: "never above the exact k for 2 ≤ n ≤ m ≤ 20 at 0.80–0.99; not conservative in general (n = 2, m = 52 at 90%: 0.8994)".
- Better, take to the owner a widening of C's condition to "no ties and C(n + m, n) < 2¹²⁸" (u128 still exact; n·m capped at 10⁷ anyway). That removes the anti-conservative unbalanced case for n ≤ 15 or so. It changes the condition D251's C ruled, so it needs a dated note on D251.

### S2. The exact k's f64 comparison disagrees with the definition on exact-rational boundaries; n = m = 3 at 90% flips an interval into E101

**Location.** S2, exact branch (lines 283-289): "the largest k with P(U ≤ k − 1) ≤ α/2 … the ratio to C(n + m, n) is compared in f64". Criteria preamble: fixtures "computed from the definitions with mpmath at 50 digits".

**Evidence (`kexact_tie.py`).**
- **At conf 0.9:** (1 − 0.9)/2 in f64 is 0.04999999999999999, below 1/20. For n = m = 3, P(U ≤ 0) = 1/20 exactly.
  - Read with decimal conf, the definition gives **k = 1**, the interval [D₍₁₎, D₍₉₎] with coverage exactly 0.90.
  - The f64 comparison gives **k = 0**, which is E101.
- **Over all n ≤ m < 50**, the two readings disagree in 45 (conf, sides, n, m) cases:
  - at 0.9: 5 two-sided and 12 one-sided;
  - at 0.8: 12 two-sided and 16 one-sided;
  - at 0.95 and 0.99: none.

  Examples within n, m ≤ 20: (3, 3), (2, 14) and (3, 9) at 90% two-sided; (2, 3), (3, 3) and (4, 4) at 90% one-sided.
- **The binary value.** f64 0.9 is slightly above 9/10, so the f64 result is the right answer for conf's binary value. A 50-digit fixture fed "0.9" as a decimal gives the other answer.
- **D251's own table** (`kcmp.py`) has 186 pairs at 0.90, which is the f64 reading: the exact-rational reading admits (3, 3) and gives 187.

**Problem.** The definition and its fixture are ambiguous at exactly the small, round cases a test is likely to use. Criterion 6's "k < 1 at a level too high for n = m = 2" is safe; a sibling case at n = m = 3 and 90% is not.

**Suggested fix.** State that α is (1 − conf)/2, or 1 − conf one-sided, evaluated in f64 from conf's binary value, with the comparison cum as f64 / C(n + m, n) as f64 ≤ α. Require the fixture to use `mpf(float(conf))`, not the decimal. Alternatively, adopt a stated fuzz, as `REL_ERR` does for Fisher (`infer.rs:42-44`). Either way, add n = m = 3 at 0.9 to criterion 6 as the boundary case.

### S3. `math.signif` answers +∞ from a finite operand (B12)

**Location.** S6, Implementation (lines 461-463); S1 "Refusals … B12 holds" (lines 160-161).

**Evidence (rustc 1.95.0, `rev4rs/f.rs`).** `format!("{:.*e}", n − 1, f64::MAX)` gives:
- `2e308` for n = 1;
- `1.798e308` for n = 4;
- `1.797693134862316e308` for n = 16.

Each parses to **inf**. Only n = 17 reads back finite. Likewise, 1.79e308 at n = 4 stays finite, but anything that rounds up past `f64::MAX` does not.

**Problem.** "Parses the formatter's string" overflows near the top of the range, and S6 lists only E101 and E103. Without a check, the word answers ∞, which B12 forbids. `math.round.places` cannot overflow, since places ≥ 0 never round past an integer that f64 already holds.

**Suggested fix.** Add: "a result that is not finite is E114 (`the answer overflows a FLOAT`), as `finite` refuses (`operand.rs`, `finite`)". Add `1.7976931348623157e308 1 math.signif` → E114 to criterion 2 or 10.

### S4. Kendall's exact counts overflow u128 from n = 36, and their number type is unstated

**Location.** S3 "Kendall", exact branch (lines 340-345).

**Evidence (`rev4_mah.py`).**
- The largest Mahonian number max_t I(n, t) first reaches 2¹²⁸ at **n = 36**.
- n! does so at n = 35.
- At n = 49, max I is about 4.2·10⁶⁰ and 49! is about 6.1·10⁶².

**Problem.** S2 states u128 for the Mann–Whitney counts, and an implementer will reach for the same width here. An unchecked u128 overflows in the range the RFC defines (n < 50): it panics in a debug build and wraps in release. Checked arithmetic would need an error arm the RFC does not give. The fixture's tolerance (1e-12) also depends on the representation.

**Suggested fix.** State the representation, for example the recurrence over probabilities in f64, dividing by n at each step, as R's `ckendall` does in doubles [UNGROUNDED as R's]. Or use u128 counts up to n = 33 and f64 above. Give the tolerance criterion 7 applies to the exact p.

### S7. The risk ratio's zero-cell refusal is broader than its stated reason

**Location.** S5, the `riskratio` row (line 405) and "Refusals" (lines 410-411): "The ratios refuse a zero cell, which makes them 0 or infinite".

**Problem.**
- For the risk ratio, (a/(a + b))/(c/(c + d)) is 0 or infinite only when a = 0 or c = 0.
- With b = 0 or d = 0, every exposed or unexposed subject had the event. The estimate is finite, and Katz's se is finite: 1/a − 1/(a + 0) = 0. If both b and d are 0, the interval is the single point [estimate, estimate].
- Refusing such a table rejects real, legitimate data, for example an exposure in which every exposed subject fell ill, on a reason that does not apply.
- For the odds ratio, every zero cell does make it 0 or infinite.

**Suggested fix.** "`oddsratio` refuses any zero cell; `riskratio` refuses a = 0 or c = 0 (E101 naming the cell) and answers b = 0 or d = 0." Adjust criterion 9's "a zero cell in either refused" to name the cell.

## Notes

**N1. The lgamma figure is one point of an erratic error.**
- "1.2e-10 relative at df 4·10⁵" reproduces at df = 400 000 (1.17e-10).
- Criterion 9's own case, n_a = n_b = 2·10⁵, has df 399 998, where the lgamma path is 4.6e-10 (Bund2's `math.lgamma` and libm agree).
- The argument stands, since the series is used there. Say "up to about 5e-10 near df 4·10⁵".

**N2. Criterion 9 does not straddle the switch.** df 398 and 399 998 both use the series, and no case tests the lgamma path near its limit. Add n_a = n_b = 101 (df 200) and n_a = 101, n_b = 102 (df 201).

**N3. "At |r| = 1" needs r = 1.0 in f64.**
- `[0.1 0.2 0.3 0.7] [1.0 2.0 3.0 7.0] stat.cor.pearson` answers 0.9999999999999999 (probed). For that data t is about 9.5·10⁷, finite, and the special case does not fire.
- `b = 2a` on integers answers exactly 1.0.
- Criterion 7's "[1, 1] at r = 1" must use such data. Say that the rule is "at r = ±1.0 in f64", and that near-1 values take the ordinary path.

**N4. Negative zero, for all four words.**
- `{:.2e}` of −0.0 is `-0.00e0`, and `math.signif` of −0.0 parses to −0.0. S6's "Negative zero is normalised" reads as general, but its examples cover two words. Say all four.
- Criterion 10's `-0.4 0 math.round.places` 0.0 must compare the sign bit, since −0.0 == 0.0 in f64.

**N5. `whole` converts a STRING cell.** `[ "2.5" 1.0 3.0 ] stat.var` answers 1.0833 (probed): `whole` reads cells through `conv_value(…, FLOAT)` (`operand.rs:113`). S6 says a LIST cell that is "not a number is E103 … as `whole` refuses them". Say whether S6 accepts what `whole` accepts, so `["2.5"]` is 2.5, or refuses non-numeric cells outright. S6 already refuses a STRING scalar x.

**N6. An INTEGER `mu`.** The options table says "`mu` a finite number". S1 says "B15's INTEGER conversion does not apply to an option". Read together, `"mu" 1 set` is E101. Say so, or let `mu` convert.

**N7. The exact branch's tie test under `mu`.** Is "no ties in the pooled n + m values" tested on a and b, or on a − μ and b? The interval is over a − b, so a and b is the natural reading. State it.

**N8. One-sided tails.** "The normal tail of z" (Mann–Whitney) and "the asymptotic tail" (KS) do not say which. Say: the upper tail of z for "greater" and the lower for "less"; KS's exp(−2·nm/(n + m)·D²) at D⁺ or D⁻.

**N9. Work bounds.**
- Each Fisher root also evaluates its two starting ends, so the bound is about 3 × (2 + 64 + 200) = 798 sums, not 792.
- At the 10⁸ support cap that is about 8·10¹⁰ terms: bounded (D39), but minutes of Tier 0 time. The second review's suggestion of a lower cap for `.opts` was not taken up, nor rejected in §Alternatives.
- The exact-k recurrence's table is at most 50·50·2402 ≈ 6.0·10⁶ cells, not 49·49·2402.

**N10. `weights` whose sum overflows.** Two finite weights of 10³⁰⁸ give Σw = ∞, so u = ∞ and every cumᵢ is ∞. S7's fallback then answers "the last positive weight" every time. Refuse a non-finite sum (E114), or scale by the largest weight.

**N11. Line 107 is an unmarked R claim:** "R's `sign(z)·½`, which is 0 there". Q62's revision-3 extension covers "the p of 1 at W = n·m/2 being R's". Mark the sentence [UNGROUNDED; Q62], as Preservation row 4 is.

**N12. D251's Status line is stale.** It reads "A2 re-ruled C and A9 raised and ruled A the same day" (`decisions.md:17211-17213`), and does not mention A9's re-ruling as C or A7's confirmation. The register allows a status to be changed; bring the line up to date.

**N13. `s_pooled` is undefined** in S5's `cohend` row. Say √(((n_a − 1)s_a² + (n_b − 1)s_b²)/df), the same as `t2`'s pooled variance (`infer.rs:112`).

**N14. Decisions consumed but never used.** The header lists B3, B4, B11, D24, D36, D37 and D38, and the body never names any of them. B11 in particular rules "R 4.4.1 fixtures" for RFC-0015 (`decisions.md:17185`). Say that A7 governs this RFC's reference values instead.

**N15. Criterion 11 does not pin the streams.** S7 fixes each algorithm "which fix the streams", but criterion 11 only checks that a reseed repeats a draw. An implementation that used `SliceRandom::shuffle` would pass. Pin the first answers after `7 rng.seed` in a unit test, as within-version regression values.

**N16. Preservation could add that a program's own word still wins.** `:math.abs { 42 } register -2.5 math.abs` answers 42 (probed). So a program that already defines `rng.shuffle` or `string.fixed` keeps its meaning, and no existing program changes by the new names.
