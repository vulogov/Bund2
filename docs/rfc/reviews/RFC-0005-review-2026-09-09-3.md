# Review — RFC-0005: Tier 1, the Cranelift backend

- Reviewed: `docs/rfc/RFC-0005-cranelift-tier.md` at 1046 lines, Status **Draft**
  (2026-09-08, revised 2026-09-09).
- Reviewer stance: adversarial. Every `path:line` in the document was opened in
  this session. Every number the RFC says can be re-derived was re-derived.
- Third review of the day. `RFC-0005-review-2026-09-09.md` and `-2.md` precede
  it; findings those already made are marked **[carried]** and are not
  re-argued, only confirmed as still open.
- Environment note: `RUSTUP_TOOLCHAIN=1.94.1` was set in this shell and
  `cargo xtask` correctly refused to run under it (F80's guard, working). Every
  number below was produced with that variable unset, i.e. under the pinned
  1.95.0.

## Verdict

The RFC's grounding is in much better shape than the review history suggests:
**every citation that names a file resolves and says what the RFC claims** —
sixteen of sixteen, including the whole `apply` chain, which is the section the
RFC was most recently corrected on. §S6's site counts re-derive exactly
(116 / 61 / 55, and the ten-row `Opaque` table row for row). §S8's correctness
argument is real and correctly attributed.

Three things block it, and all three are new to this review:

- **B1** — criterion 2 cannot be run by the tool it names, and the RFC states
  it *has* run. `cargo xtask conform` accepts no `--features`.
- **B2** — promotion, the RFC's entire stated win, has no mechanism, and §S8's
  argument against §3.2f is the thing that removes it.
- **B3** — a `Fixed` effect does not mean a word touches only its arity.
  `debug.display_stack` is `eff(0, 0)` and reads the whole stack.

Below those, criterion 8 is still substantially vacuous for this document
(**S1**), and §S10's build claims are wrong in two places that a single `cargo`
invocation refutes (**S2**, **S3**).

## 1. Blocking

### B1 — criterion 2 names a tool that cannot express its own condition, and the RFC records it as having run

Criterion 2 reads:

> **Conformance moves by exactly zero.** `cargo xtask conform` reads the same
> N/M **and the same CEILING** with the `jit` feature on and off.

and §S10 and the criteria preamble both assert it has been executed:

> **Criterion 2 has run**: 73/86 with the feature on and 73/86 with it off,
> ceiling 79/86 in both.

`cargo xtask conform` has no feature flag and rejects one:

```
$ cargo xtask conform --features jit
xtask conform: unknown argument `--features`
```

The argument loop in `xtask/src/conform/mod.rs` (`run`, the `while let Some(a)
= it.next()` match) accepts exactly `--accept-deviation`, `--reason`,
`--accept`, `-v`, `--verbose`, `--parse-only`, `--blocked-on`, and returns
`unknown argument` for anything else. The binary it measures is produced by
`bund2_binary`, which runs `cargo build -q -p bund2-cli` with **no features**
and then reads `target/debug/bund2`. There is no path by which a feature
reaches the measured binary — and because it rebuilds unconditionally, a
`bund2` a developer had previously built with `--features jit` is *overwritten*
by a featureless one before the goldens run.

So the sentence "73/86 with the feature on" was not produced by
`cargo xtask conform`, and the RFC does not say what produced it.

Two things make this worse than a stale claim:

1. **It is the invariant CLAUDE.md singles out for this milestone** — "the JIT
   and AOT milestones must move it by exactly zero". Criterion 2 is the only
   check of that invariant in the document.
2. **The RFC diagnoses this exact defect elsewhere and fixes only the other
   instance.** Criterion 11 says, of `xtask depth`:

   > **`--features` did not exist when this criterion was written**, and
   > `xtask depth` shelled out to whichever `bund2` happened to be sitting in
   > `target/`, so the command could not have measured a tier even in
   > principle.

   `xtask depth` was repaired — `build_bund2(repo, features)` in
   `xtask/src/depth/mod.rs` forwards `--features` to `cargo build` — and it is
   the *only* xtask subcommand that does. `grep '"--features"' xtask/src`
   returns two hits, both in `depth`. F80's lesson was applied to the criterion
   that was reviewed and not to the criterion beside it.

I verified the featureless number stands: `cargo xtask conform` reports
`CONFORMANCE 73/86 (+7 approved deviation(s))`, `CEILING 79/86`. That half is
correct. The other half is not measurable today.

**Required:** either `conform` grows `--features` as `depth` did, or criterion 2
names the command that actually produced both numbers. Until then the criteria
preamble's "Criterion 2 has since **run and passed**" should read "cannot be
run", which is the honest form and the one the RFC already uses for the
withdrawn half of criterion 1.

### B2 — promotion has no mechanism, and §S8's own argument is what forecloses it

§S6 is the RFC's stated payoff:

> a compiled body's intermediate values live in Cranelift `Variable`s rather
> than round-tripping through the `Stack`, so a sequence like `1 2 +` never
> materialises a `BundValue` at all.

§S8 rebuts the study's §3.2f like this:

> §3.2f is about passing *arguments*. A concatenative language passes none: a
> word's operands are already on the VM's stack, which the callee shares. So a
> compiled word's signature is not variadic and never becomes `argc/argv` — it
> is one pointer to the VM and one status, uniformly

with the fenced citation `crates/bund2-api/src/lib.rs:61`, which I opened and
which reads exactly `pub type NativeFn = fn(&mut dyn Vm) -> Result<(), Error>;`.
The citation is correct. The consequence is the problem.

**If a word's operands reach it only through the shared VM stack, then a value
living in a Cranelift `Variable` is invisible to every word.** `+` is a
`NativeFn`; it takes `&mut dyn Vm` and pulls. It cannot see a `Variable`. So
`1 2 +` can avoid materialising a `BundValue` only if `+` is **not called** —
if it is lowered inline, as machine code emitted into the body.

The RFC never says this. It never uses the word "inline" or "lowering" for a
stdlib word; it says only that D9 keeps `Intrinsic` "internal to
`bund2-stdlib`" (§S10). And `Intrinsic` **does not exist**: `grep -rn Intrinsic
crates/ --include='*.rs'` returns nothing. There is no type, no variant, no
registration path, and no statement in this RFC of which words have one.

The consequences are load-bearing, not editorial:

- **§S6's promotable set is wrong as stated.** "What is promotable is the
  straight-line run before the first opaque site in each body" is only true if
  every word in that run has an inline lowering. The actual promotable set is
  the straight-line run of *intrinsic-lowered* words before the first opaque
  site — a strictly smaller and currently *empty* set.
- **Criterion 9 measures something undefined.** It benchmarks "straight-line
  run lengths of **1, 4, 16 and 64 words** before the site". Which 64 words?
  If they are `NativeFn`s, every one of them syncs and the criterion measures
  the sync cost against itself.
- **The ~2–5× figure §S6 inherits from §2.1 is for a strategy the RFC has not
  specified.** §S6 already discounts it correctly for D41; it should also say
  it is contingent on an intrinsic set that does not exist.

There is a second-order consistency problem underneath. D9's resolution places
`Intrinsic` "internal to `bund2-stdlib`", and D9's own text explains that a
`LowerFn` signature "contains `cranelift_frontend::FunctionBuilder`". But
RFC-0000's **B3** is `cargo tree -p bund2-stdlib` does not list `bund2-jit`
(`docs/rfc/RFC-0000-architecture.md:453`), and `crates/bund2-stdlib/Cargo.toml`
today has no cranelift dependency and no `jit` feature — though its `[package]
description` already reads "The standard library: native words, effects, **and
JIT lowerings**". So the place D9 assigns lowerings to is the place RFC-0000
forbids them from reaching Cranelift. RFC-0005 §S10 restates D9's sentence
without noticing that it has nowhere to put the code its own §S6 depends on.

**Required:** §S6 must state how a promoted value reaches a word — the
intrinsic set, where the lowerings live under B3, and what happens when a word
in an otherwise-promotable run has only a `NativeFn`. As written, §S6 and §S8
cannot both be true.

### B3 — a `Fixed` effect does not mean the word touches only its arity, and promotion assumes it does

§S5:

> **RFC-0004 orders the guards.** A word's declared or inferred `StackEffect`
> gives the arity a guard must check before entry.

§S6 and criterion 13 then partition every call site into `Opaque` (stop
promoting), absent effect (treat as `Opaque` — criterion 13), and everything
else (keep promoting). The third bucket is unsafe, and the counterexample is in
the standard library:

```rust
    r.register_native(
        "debug.display_stack",
        display_stack,
        eff(0, 0),
        WordKind::Sync,
    );
```

`crates/bund2-stdlib/src/console.rs`, and `display_stack` itself is

```rust
fn display_stack(vm: &mut dyn Vm) -> Result<(), Error> {
    let rows: Vec<String> = vm.snapshot().iter().map(|v| v.render(false)).collect();
```

An effect of `Fixed(0, 0)` — consumes nothing, produces nothing — and it reads
the **entire stack** through `vm.snapshot()`. Under §S5's rule this is not an
opaque site, so promotion runs straight through it, and the box it prints is
missing every value still held in a `Variable`. That output is compared
byte-for-byte: `crates/bund2-stdlib/src/console.rs` says `debug.display_stack`
"is here because the golden capture epilogue calls it", and 39 of 86 goldens
carry rendered stack rows (`grep -rl 'tags: {"stack"' tests/golden | wc -l` →
39, which is also where criterion 12's number comes from).

`debug.display_workbench` is the same shape via `snapshot_workbench`. And the
weaker form is everywhere: most natives open with `if vm.depth() < N`, the
underflow guard CLAUDE.md's disposition 2 requires them to keep. `depth()`
reads the real stack, which under promotion is short by exactly the promoted
values — so a promoted region followed by an ordinary arithmetic word makes
that word bail with the reference's "Stack is too shallow" text where the
interpreter succeeds.

This is a different failure from criterion 13's. Criterion 13 catches an
**absent** effect. This is a **present, correct, declared** effect that
understates what the word observes, and no criterion, no §S6 bound and no
Preservation row covers it.

**Required:** the promotion rule needs a third stop condition — a word that
observes stack state beyond its declared arity — and `StackEffect` needs a way
to say so, or the effect table needs an "observes the stack" bit. Note this is
also a hazard for the *interpreter's own* invariants under D37: a depth guard
computed against a stack that is deliberately short is exactly the kind of
"cannot happen" that becomes an abort.

### S2 — §S10 says `--features aot` builds in `bund2-bench`; it does not exist there

§S10:

> `--features jit` and `--features aot` build in `bund2-jit`, `bund2-runtime`,
> `bund2-cli` and `bund2-bench`.

```
$ cargo build -q -p bund2-bench --features aot
error: the package 'bund2-bench' does not contain this feature: aot
help: packages with the missing feature: bund2-jit, bund2-runtime, bund2, bund2-cli
```

`crates/bund2-bench/Cargo.toml`'s `[features]` block declares `jit` and nothing
else, deliberately and with a comment explaining that it exists for criterion 7.
So the sentence is wrong in two directions at once: `aot` is not in
`bund2-bench`, and the umbrella `bund2` crate — which does have both — is not in
the list. The list should be four crates for `jit` (plus `bund2`) and four for
`aot`, and they are different four.

Q31's register entry carries the same error ("`--features jit`/`aot` build in
all four crates"), so this is worth correcting in both places.

### S3 — the toolchain migration §S10 declares "paid" left the declared MSRV behind

§S10:

> **The migration was owed and has now been paid — F80.**
> `cranelift-codegen@0.135.0` requires rustc **1.95.0** while
> `rust-toolchain.toml` pinned **1.90.0** […] The toolchain pin is now
> **1.95.0**

`rust-toolchain.toml:2` is `channel = "1.95.0"` — correct. But `Cargo.toml:32`
is still `rust-version = "1.90.0"`, workspace-wide, and every crate inherits it
via `rust-version.workspace = true` (verified in `bund2-jit`, `bund2-stdlib`).

So the workspace advertises an MSRV of 1.90 for crates that cannot build with
`--features jit` below 1.95. Cargo will not catch it — `rust-version` only
errors when the *toolchain* is older than the declaration, never the reverse —
which is precisely why it stays wrong silently. F80's finding was that a pinned
dependency and a pinned toolchain disagreed; half the pin was raised.

This does not block the RFC, but §S10's claim that the migration is paid is
what makes it a review finding rather than a chore: the sentence is the
document's only statement about the pin's consistency, and it is incomplete.

### S4 — Q29's register entry still asserts the claim §S1 withdraws

§S1's whole revision is that prerequisite 2 is **not** settled:

> **Prerequisite 2 is not settled, and this update no longer claims it is.**

`docs/registers/open-questions.md`, the Q29 row, closes:

> `BundValue` still measures **16 bytes**, and conformance held at 73/86
> throughout. RFC-0005 SS1's 20 ns gate is met for the first time, and the
> value layer is now ~10 ns of a ~25 ns word, **so dispatch is the dominant
> term**

That is the sentence §S1 retracts, resting on the "~25 ns word" figure §S1
identifies as the unit error. ERRATA was updated on 2026-09-09 to withdraw the
same claim; Q29 was not. The registers are append-only but statuses and entries
are amendable, and this one is a live contradiction between the RFC and the
register it cites.

(The 10.1 vs 9.8 ns discrepancy in the same row is **[carried]** from review -2
§S2 and is unresolved.)

### S5 — the Preservation table's `unregister` row cites a mechanism §S4 does not contain

The table's row:

| `unregister` against a slot a compiled body still calls | the slot is the indirection point; **unregistering writes a failing stub** rather than freeing it (§S4) |

§S4 says nothing about `unregister` beyond naming it as one of three mutators.
It states only "Redefining a word writes a new pointer into its slot." There is
no stub, no failing stub, and no statement of what the stub must *say*. Under
D37 and D36 that second part matters: the reference's answer for an
unregistered word is `i(<name>) returned: VM Inline <name> not registered`,
assembled across `multistackvm_inline.rs`'s `get_inline` bail and `i_direct`'s
wrap. A stub that reports anything else is a golden difference, not just a
missing design note.

This row was added in response to review -2's finding 1. The row exists; the
design it cites does not.

The `alias` row beside it has the same problem and one more (see §5.2).

## 4. Acceptance criteria — checkable, and by what

The criteria are the strongest part of the document. The preamble's own rule
— each names a tool **and** either a threshold or a boolean outcome — is met by
every one of the thirteen, and the withdrawals (criterion 1's second half,
criterion 7's "shows improvement", criterion 9's renameable failure) are real
improvements that removed real vacuity.

| 9 | a new `bund2-bench` benchmark | ≤ 5% slower at 1, 4, 16, 64; crossover length reported | needs a tier — **and B2: "64 words" is undefined until the intrinsic set is** |
| 10 | A/B, one compiled body vs interpreted | **< 1.2× on `1 2 + drop` fails** | needs a tier; correctly the one that can fail |
| 11 | `cargo xtask depth --features jit` | reads the same 100,000; guard threshold and per-entry cost reported, > 2 ns reconsidered | ✓ the command exists and forwards features |
| 12 | a probe + `cargo xtask conform` | green — boolean | needs a tier |
| 13 | register nothing, compile a caller | promotion stops as for `!` — boolean | needs a tier |

Two notes beyond B1:

- **Criterion 10's stated bound is not what the named benchmark bounds.** It
  says "`dispatch/literal_only` bounds dispatch at **≤ 33.7 ns**".
  `literal_only` measures 13.2 ns; the 33.7 comes from `literal_push` −
  `literal_only`. The named benchmark alone bounds nothing. §S1's update states
  the subtraction correctly; the criterion compresses it into something false.
- **Criterion 7 lists a `corpus` group as "free to improve", and criterion 7's
  own closing paragraph says a corpus figure is not an acceptance criterion.**
  These are two different things with the same name — the in-process
  `corpus` benchmark group in `bund2-bench` and `cargo xtask bench`'s
  subprocess harness — and the paragraph does not say so. A reader who takes
  the disclaimer at face value will delete the row.
- **The benchmark IDs in §S1's tables are still not benchmark IDs**
  **[carried]**. `dispatch/literal_push` is `dispatch/literal_push/w2000`;
  `value/with_tag/scalar` is `value/with_tag/scalar_unique` (there is also a
  `heap_shared` arm, and the 73.1 ns belongs to one of them). ERRATA inherits
  the same non-existent name.

## 5. Preservation analysis — what the table still does not enumerate

The table now has fifteen rows and has absorbed most of review -2's findings —
`unregister`, `alias`, the diagnostic location, the D41 stack symbol, the
machine stack. What remains missing, in descending order of how much it would
cost to find later:

1. **A `Fixed`-effect word that reads the whole stack.** B3. No row, no
   criterion, and the offending word runs in the golden capture epilogue.

2. **A *new* alias introduced for an already-compiled name.** The table's row
   handles an alias being *retargeted*: "the slot names the resolved target, so
   retargeting must rewrite every slot that resolved *through* the alias". It
   does not handle `register_alias` creating an alias where there was none.
   `apply` consults `get_alias` **before** dispatch (`:39-40`), so aliasing an
   existing word redirects it — and a slot that was populated at compile time
   with a resolved target that *was not an alias* has no record linking it to
   the new alias, so there is nothing to rewrite. The mechanism the table
   describes ("rewrite every slot that resolved through the alias") cannot fire.
   Keying slots on the resolved target is what creates this; keying them on the
   spelling and resolving in the stub would not.

3. **A name that *becomes* a command.** Step 2 of §S4's chain outranks
   everything, and `register_command` is a runtime operation — `:` and `;` are
   registered that way at `autoadd.rs:28-29`. Same class as 2, same absence.

4. **The `Diagnostic`'s stack snapshot under promotion.** D36's `Diagnostic`
   carries an "optional stack snapshot" and CLAUDE.md makes it part of the
   structured form. A guard or a helper failing inside a promoted region
   snapshots a stack short by the promoted values. Review -2's finding 4 covers
   the **location** field; the **snapshot** field is a separate row and a louder
   failure, because the tryexcept goldens compare error output.

5. **The multi-stack, which the RFC never mentions.** §S5 says values are
   "synced back to **the real stack**", singular. Bund is a multi-stack language
   with a workbench — `pull.` is in §S6's own `Opaque` table,
   `debug.display_workbench` reads `snapshot_workbench`, and context words move
   the current stack. Nothing in the RFC says which stack a `Variable` belongs
   to, what happens if the current stack changes inside a promoted run, or
   whether workbench values can be promoted at all. For the language's headline
   feature that is a conspicuous silence.

6. **`.id` and `.timestamp` under promotion (D1, D2, D13, D20)** **[carried]**,
   review -2 finding 5, and worth restating because D20 is in this RFC's
   "Decisions consumed" list and appears nowhere in its body except through
   D35's argument. A value that lived only in a `Variable` and was then synced
   has not passed through the paths D13's CoW policy fires on. Criterion 12
   covers the stack symbol only.

7. **`Warning` / `Notice` to stderr from compiled code** **[carried]**,
   review -2 finding 6.

8. **`Fold` arriving at run time** **[carried]**, review -2 finding 7 — what
   *detects* it is still unspecified.

9. **The `autoadd` guard's granularity** **[carried]**, review -2 finding 9.
   Still unanswered, and B2 sharpens it: if "everything after an opaque site
   runs through runtime helpers" means the helper re-enters the full `apply`
   chain (steps 1–7), the mid-body flip is handled and the RFC should say so in
   one sentence. If a helper only performs step 7, it is not handled at all.
   The RFC never says what a runtime helper does.

10. **Errors wrapped at a different tier.** `i_direct` wraps a VM-tier failure
    as `i({name}) returned: {err}` and a stack-tier failure as `VM inline
    function returned error: {err}` (`multistackvm_inline.rs:41-67`) —
    `crates/bund2-api/src/lib.rs`'s own doc comment calls out "the stack tier's
    distinct error wrapping" as a stated RFC-0002 deviation. A compiled call
    that reaches a word directly, bypassing the tier that wraps it, changes
    error text. Conformance compares that text.

## 7. What the RFC assumes and does not state

1. **That dispatch costs the same for every word.** §S1 derives 33.7 ns from
   `drop` and then says "dispatch is **at most** 33.7 ns" as a general bound.
   The same subtractions give `dup` 48.9 and `+` 45.1 — both larger — so the
   bound generalises only if dispatch is uniform and the excess is all work.
   That may well be true; it is assumed, not said, and criterion 10 is written
   as though it were established.
2. **That a "runtime helper" re-enters the interpreter's dispatch.** §S5's
   second rule says "everything after it runs through runtime helpers" and the
   RFC never says what a helper *is* or how much of `apply`'s chain it
   reproduces. §S4's autoadd hole, §S4's `is_command` hole, and §S8's
   correctness argument all depend on the answer.
3. **That the promoted words are inlined rather than called.** B2.
4. **That `bund2 check`'s `Opaque` verdict and Tier 1's promotion barrier are
   the same predicate.** §S6 uses one to count the other. B3 is the counterexample.
5. **That the compiled-function cap (1024) and the counter cap (4096) are
   reached in a bounded time.** §S7's sweep is bounded per D39, correctly. But
   §S7 does not say when a sweep runs, and D3's own workload — a loop calling
   `bund.eval` — inserts a fresh counter entry per iteration. **[carried]**,
   review -2 finding 8.
6. **That the goldens' epilogue runs outside any compiled body.** B3's severity
   depends on it. Nothing states it.
7. **That `--features aot` is out of scope for criterion 2.** §S10 discusses
   both features; criterion 2 tests only `jit`. CLAUDE.md's invariant names
   "the JIT **and AOT** milestones". RFC-0006 presumably owns AOT conformance,
   and the RFC should say so rather than leave the reader to assume it.
8. **That `Rc`'s strong-and-weak-counts-to-zero property is a guarantee and not
   an implementation detail.** §S7 leans on it hard — it is what makes the
   `Weak` counter safe and what cuts at D35's rationale (Q32). It is in fact
   documented `std` behaviour, and the RFC cites nothing for it.
9. **That a stack-headroom check is expressible portably.** §S8 requires "every
   compiled body checks machine-stack headroom on entry"; there is no portable
   stable-Rust API for remaining stack, and the usual answer is a crate
   (`stacker`) or a platform call. D10 permits neither below `bund2 build`
   without saying so, and D38 governs pinning third-party crates. Criterion 11
   measures the cost of the check but nothing names its mechanism.

## 8. Recommendation

**Stay Draft.** The RFC is right that its status question has moved from
"should this be built" to "is the design right", and §S8's self-correction is
the strongest piece of work in the document. But two of the three blockers are
about the design rather than the gate:

- **B1** must be fixed before the RFC's own summary can say what it says.
  It is a small change to `xtask/src/conform/mod.rs` — `depth` shows the shape.
- **B2** is the substantive one. §S6 promises the win, §S8 argues the calling
  convention away, and the two are in direct tension. The RFC needs a paragraph
  on the intrinsic set and where its lowerings live under RFC-0000's B3, or §S6
  needs to say that promotion is bounded by an intrinsic set that does not yet
  exist and that criterion 9 and criterion 10 are contingent on it.
- **B3** needs a third stop condition in §S5 and a row in the Preservation
  table. It is cheap to fix and expensive to find later, because it fails as a
  wrong rendered stack in a golden rather than as a crash.

**S1** is worth fixing in the same pass, because it is the difference between
criterion 8 being a check and being a comment — and §S4 is the section this RFC
has already been corrected on twice.

§S4, §S6's measurements, §S7's counter argument, and §S8's guard are all sound
and re-derived. Nothing in this review challenges them.
