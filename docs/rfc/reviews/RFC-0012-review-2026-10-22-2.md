## Verdict

**Not ready for Accepted. Close.** The sixth review's findings are answered
as ruled, and nothing here asks for a change of design. Two findings,
though, are statements the owner ruled on or must rule on:

- **Finding 1.** D207's option C told the owner that answers over whole
  weights would not change, and that answers over fractional weights
  could change only in the last bit. Neither is true. The ruling's
  direction is unaffected; its stated consequence is wrong, and the RFC
  repeats it in two places.
- **Finding 2.** The reference's `graph.allpath` has the same rounding
  defect D207 removed from `graph.bellmanford`. It is unrecorded, so it
  has no disposition. It also falsifies the preservation analysis's "a
  swap works one way".

## Findings, most serious first

### 1. "Over whole weights that is the sum `f64` forms … can differ in the last bit" is false, and D207 was ruled on it

R:361-363 (S5) says:

> Over whole weights that is the sum `f64` forms; over fractional ones it
> can differ in the last bit from a left-to-right `f64` sum

R:487-489 (the preservation analysis, "negative weights") says
`graph.bellmanford`'s distances "over fractional weights … can differ in
the last bit from `graph.paths`' left-to-right sum". D207's option C,
which the owner chose, says the same: "Answers over whole weights do not
change. Answers over fractional weights can change in the last bit."

Both halves fail, because a left-to-right `f64` sum loses one rounding per
term, and the losses add up. Run today, rebuilt binary; `graph.paths`'
answer is the same in the oracle:

```
:A [ [ :A :B 9007199254740992.0 ] [ :B :C 1.0 ] [ :C :D 1.0 ] ] [ :A :B :C :D ] graph! graph.bellmanford println
:A [ [ :A :B 9007199254740992.0 ] [ :B :C 1.0 ] [ :C :D 1.0 ] ] [ :A :B :C :D ] graph! graph.paths println
```

- **Whole weights.** D's distance is `9007199254740994.0` under
  `graph.bellmanford` and `9007199254740992.0` under `graph.paths`, in both
  engines. `2^53 + 1` rounds to `2^53` (ties to even) twice in `f64`. The
  exact sum, `2^53 + 2`, is representable.
- **Fractional weights, far more than the last bit.** One edge of `1.0`
  followed by ten edges of `1.0e-16`:
  - `graph.bellmanford` answers `1.000000000000001` for the eleventh node;
  - `graph.paths` answers `1.0` in both engines.

  That is five ulps apart. Each `1.0e-16` is below half an ulp of `1.0`, so
  `f64` drops every one. Ten thousand such edges would put the exact
  answer near `1.000000000001`, against `graph.paths`' `1.0`. The gap grows
  with path length and has no fixed bound in ulps.

The correctly rounded answer is the better one, and D207's choice of it
is not in question. But "the last bit" undersells the change as a
migration hazard. A program that compares `graph.paths` and
`graph.bellmanford` answers on a non-negative graph can see differences of
any size relative to the ulp. That is the swap R:485-487 recommends.

- **No criterion reaches it.** `bellman_ford_agrees_with_dijkstra` draws
  whole weights below 2^53, where both are exact.
- **Repair:**
  - Restate R:361-363 and R:487-489 as: whole weights whose partial sums
    stay below 2^53 answer as `f64` does; otherwise `graph.paths`' sum can
    be off by one rounding per edge, and `graph.bellmanford`'s is the
    correctly rounded one.
  - Add a dated note to D207 correcting option C's sentence, as D200's
    note did for a ruling made on a narrower statement.
  - Add a test pairing the two words on the `2^53` program.

### 2. The reference's `graph.allpath` misses a negative cycle by rounding: unrecorded, and "a swap works one way" is false

D207 says "Not checked: whether the reference's `graph.allpath`
(Johnson's, over `f64` Bellman–Ford) behaves the same way." It does.
Johnson's potentials come from `algos`' `f64` Bellman–Ford
(`johnson.rs:50-53`), whose cycle test is `new_dist < *dist_v`
(`bellman_ford.rs:91-101`). That is the test D207 found deciding by
rounding. Run today:

```
[ [ :A :B -1.0e20 ] [ :B :C 1.0 ] [ :C :B -1.0000000000000002 ] ] [ :A :B :C :Z ] graph! graph.allpath len println
:A [ [ :A :B -1.0e20 ] [ :B :C 1.0 ] [ :C :B -1.0000000000000002 ] ] [ :A :B :C :Z ] graph! graph.bellmanford println
```

- `graph.allpath`: **8 rows in both engines**. Among them, `B → C`
  weighs `0.0` and `C → B` weighs `0.0`, though the cycle `B ↔ C` weighs
  −2⁻⁵² and both distances are unbounded.
- `graph.bellmanford` (`bund2`):
  `A reaches a negative cycle through B`.
- `q` is `Z` here (F220 has nothing to do with it). The potential
  `h_B = −1e20` swallows the cycle: `fl(−1e20 + 1.0) = −1e20` and
  `fl(−1e20 − 1.0000000000000002) = −1e20`. No pass relaxes and nothing is
  reported. The reweighted cycle edges then come to exactly 0.0
  (`johnson.rs:63`), so Dijkstra accepts them.

Three consequences:

- **An original-implementation defect with no register entry.** It is
  distinct from F220, which concerns the last node. It sits in a core word
  (D14). Under CLAUDE.md it goes to `defects.md`. Whether to preserve it,
  as D200 did F220, is the owner's call. Preserving is the presumption,
  but no ruling yet covers it.
- **The preservation analysis is wrong in direction.** R:485-487: "a swap
  to it works one way: from an error or missing rows to an answer". Here
  the swap goes from rows, wrong ones, to an error. The opposite direction
  is just as available: a zero-weight cycle far down the potentials can be
  refused by `graph.allpath` and answered by `graph.bellmanford`, the
  shape of the sixth review's first program. A swap now moves to the
  exact answer, whichever way that is.
- **"Current behaviour"** (R:128-156) states every face of F220 but not
  this one. It reads as if `graph.allpath` refuses every negative cycle
  except one through `q`'s replaced out-edges (R:146-149). That is untrue
  whenever the distances dwarf the cycle.

**Repair:**
- Record the defect, and take its disposition to the owner (preserve, by
  D200's reasoning, is the obvious default).
- State it under "Current behaviour".
- Restate R:485-487 as "a swap gives the exact answer, which can be an
  error where `graph.allpath` answered".
- Pin it with a test of both words over this graph.

### 3. Smaller points

- **R:355-358 and `GA:604-609`, the 2^76 guard**, is an `Error::internal`.
  D37's internal error says the defect is in Bund2. A graph too large for
  `Exact` is not a Bund2 defect, and the RFC itself says no graph that fits
  in memory reaches the guard. Harmless as unreachable code. But if it is
  meant as a real limit, it is an ordinary error (CLAUDE.md, "Three ways
  out", 2). If it is meant as unreachable, the message should say so.
- **R:371-374, the cost**, quotes measured times (~100 ms against ~7 ms).
  D207 says how they were taken: medians of `bund2 script` rounds. No
  command or program is recorded, so the figure cannot be re-taken. It is
  not an acceptance criterion and need not be one; the program should
  still be named, as RFC-0005's criteria name theirs.
- **R:164-171, the `:201-208` citation**, ends at `nodes,`. The
  constructor closes at `:209`.
- **`Exact`'s rounding near the range edges is checked only by hand-picked
  cases.** `exact_sums_round_once_to_the_nearest_f64` covers the
  subnormal boundary, `f64::MAX` and the overflow tie, all by hand. The
  random cross-checks stay within 2^-60 to 2^~110 units. The hand checks
  are sound (verified above); a randomized check against an exact model
  near 2^-1074 and 2^1024 would make criterion 11 say what it claims for
  the whole range.

## What the RFC assumes but does not state

- **That `graph.paths`' answer is within an ulp of the exact one.** It is
  not (finding 1). The RFC's comparisons between the two words lean on
  this.
- **That the reference's `graph.allpath` finds every negative cycle not
  through `q`.** It does not (finding 2).
- **That an `Exact` relaxation's cost stays a constant factor.** The
  factor is about 34 limbs per add or compare, so roughly ×14 on the
  measured worst case. The RFC gives the figure for 2,000 nodes only. A
  program running `graph.bellmanford` on a 20,000-node adversarial chain
  pays about 100× the 2,000-node time either way, quadratic in nodes, and
  the RFC does not say whether that is acceptable.
