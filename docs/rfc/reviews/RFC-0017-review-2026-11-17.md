## Blocking

### B1. Criterion 6's round trip is false for four kinds of frame the design allows

S6 states: "`frame.csv.parse` of `frame.csv.text` of a frame is that frame, factors aside". Criterion 6 asks for this "of a frame of every kind with NONE … each FLOAT bit for bit". Under S6's own rules (writing quotes only a field holding a delimiter, a quote or a line break; parsing reuses `csv`'s inference, which sees the field after the `csv` crate has removed any quotes, per `data.rs`'s module doc) the round trip fails in four cases:

1. **A numeric column mixing INTEGER and FLOAT**, which S2 allows ("mixed INTEGER and FLOAT allowed").
   - It is written `1` and `2.5`, and read back as a FLOAT column, so the INTEGER 1 returns as FLOAT 1.0.
   - Probed: a file `x\n1\n2.5\n` through `csv` answers `[ 1.0 :: 2.5 :: ]`.
2. **A STRING cell equal to an `na` string.** `""` or `"NA"` is written bare and read back as NONE.
3. **A string column whose cells all look like numbers or BOOLs** (`"007"`, `"12"`, `"true"`). It is written bare and read back as INTEGER or BOOL.
   - Probed: `007` stays a STRING only because the same column holds `true`.
   - A column of `"007"` and `"012"` infers as an integer column.
4. **A factor whose levels look like numbers.** Criterion 6 sets factors aside, but the cells still change kind.

Either narrow the claim and the criterion to frames where the cases above cannot occur, or change the format.
- **One option for the format:** write every STRING cell quoted and have `frame.csv.parse` treat a quoted field as a string.
- That would be *closer* to polars than `csv` is: `data.rs`'s module doc records that "polars treats a field written in quotes as a string whatever it holds".
- It would need the `csv` crate's raw-field position, or a reader of the RFC's own.
- Either way, the INTEGER/FLOAT mix needs a rule: keep the kinds apart in text (for example, write an INTEGER without `.0`, which it already is, and stop inferring a mixed column as FLOAT), or state that such a column comes back all FLOAT.

### B2. `NaN` and `inf` in a CSV infer as FLOAT, which S2 forbids, and S6 says nothing about them

- `data.rs`'s `is_float` accepts `inf` and `NaN` with an optional sign (polars' `FLOAT_RE`).
- Probed: a column `1.5`, `NaN`, `inf` through `csv` answers `[ 1.5 :: NaN :: inf :: ]`.
- S2 makes a non-finite numeric cell a malformed frame (B12).
- S6 reuses the inference with only two stated differences: NONE in place, and the `na` strings checked before inference.

So `frame.csv.parse` on such a file either builds a frame its own check refuses or must refuse; neither is stated. Criterion 9's palette includes NaN but only as a frame operand. State one of these and add it to criterion 6:
- E101 naming the row and column;
- read as NONE;
- or an opt to choose between them.

## Should fix

### S1. The statistics are attributed to `describe.rs`, but `mean` is not there and `sum`, `min`, `max` have no word

S5 says the statistics are "computed as RFC-0015's words compute them (`describe.rs`), so a group's `"mean"` is what `stat.mean.arithmetic` answers". This does not hold:
- **`stat.mean.arithmetic` lives elsewhere.** It is the reference's word, ported in `series.rs` (`amean`, registered at `:501`, with `stat.mean` aliased to it at `:528`). It reads through `get_data`.
- **The two files' means can differ.** `describe.rs`'s module doc says `stat.var`'s mean "is a sum over a count, as `stat.mean.arithmetic`'s is, but the two may differ in the last bit".
- **Criterion 5's bit-for-bit claim therefore depends on which code `frame.aggregate` calls,** and the RFC does not say.
- **Three statistics have no word.** `bund2 words` lists `stat.count` and `stat.mean`, but no `stat.sum`, `stat.min` or `stat.max`, so those three are defined by nothing.

For each of the eight statistics, state the function it shares (the file and symbol), and fix criterion 5 to name the same one.

### S2. `"omit"` in `frame.matrix` drops rows that `y` still holds, so `stat.lm` refuses it

`stat.lm` is `X y -- …` and refuses unequal lengths with E102 (`infer.rs`, `stat_lm`). Under `"omit"`, `frame.matrix` drops each row with a NONE in its columns. But the program gets `y` from `"y" frame.column`, which carries NONE and drops nothing. The lengths then disagree, or, when `y` has NONE of its own, `stat.lm` refuses the NONE.
- No word of the RFC answers the complete cases of a frame.
- Criterion 5 tests `frame.matrix` only on a frame with no NONE.

Add one of these:
- a `frame.complete` word (`frame names -- frame`, the rows with no NONE in those columns);
- the kept row indices in `frame.matrix`'s `{ matrix, dropped }` answer;
- a `y` operand.

Then test the path a model actually takes.

### S3. E103's text says "of numbers", but S2 and S5 use it for non-numeric kinds

E103's template is "`<operand>` is not a MATRIX (or LIST) of numbers: `<cell or row>`" (`RFC-0015-biomathematics.md:842`). The RFC sends these to E103:
- a logical column holding a STRING;
- a factor cell not among its levels (criterion 2);
- a `by` column whose kind differs between the two frames of a join (S5);
- `frame.factor.levels`'s refusal.

None of these is about numbers, and with P9 ruled "no new code", the texts must be stated. D252 asks for "an S11-style refusal naming what is wrong". Give the text for each S2 rule; criterion 2 already asks for "its code and text".

### S4. What `frame.csv.parse` does past the inference window is unstated, and today's answer is not an E1nn

- **The window:** `read_frame` infers each column from the first 100 rows (`data.rs`, `take(100)`).
- **A later cell that does not parse** is `CONTEXT.RUN: Error finishing dataframe: could not parse … as dtype …` (`data.rs`, `cell`), which is not an S11 code. For example: an integer column with `2.5` at row 101, or a BOOL column with `yes`.
- **Two conflicts:** criterion 9 requires every word to answer, refuse with an E1nn, or give a shallow-stack or bridge error. S6 says the parser "reuses `csv`'s inference", which brings this refusal with it.

State:
- whether `frame.csv.parse` keeps the 100-row window (polars' and `csv`'s) or reads every row (which would avoid the error entirely);
- the refusal for a late mismatch, with its code;
- a test.

### S5. Headers: `header false`, duplicate or empty names, and whether text writes one

- **Without a header,** `read_frame` names the columns `column_1`, `column_2`, … from the first row's width. The RFC does not say `frame.csv.parse` does the same.
- **Duplicate or empty header names:** a CSV file may have them, and the frame check refuses them. The RFC should state what happens: E101 at parse, naming the name (R's `read.csv` makes names unique [UNGROUNDED; would extend Q64]).
- **Writing a header:** S6 does not say whether `frame.csv.text` writes one, nor whether it takes an opts MAP.
- **Option name:** S6's option is `header`, but the reference's conditional calls its key `is_header` (`conditional_csv.rs:44`). Either name is fine; the difference should be deliberate and stated.

### S6. `frame.matrix` is defined for numeric columns only, and the rest is unstated

S5 says "the numeric columns as a MATRIX". It does not say what a named column of another kind does:
- a logical column (0/1, or refused?);
- a string column;
- a factor column, whose coding (treatment contrasts, research 07 §3.1) is Phase C's.

It also leaves unstated `names` empty, zero rows, and whether an INTEGER cell becomes a FLOAT (`table` converts). Criterion 5 covers none of these.

### S7. `frame.aggregate`'s groups and statistics have unstated cases, and one rule contradicts another

- **The NONE contradiction:**
  - S3 says the `na` option governs "a NONE in a cell it reads", and `"refuse"` is the default.
  - S5 says "NONE in a `by` column is a group of its own, last".
  - Under the default, which rule applies to a `by` column? Say which.
- **`"count"`:** does it count rows, or cells that are not NONE? Under `"omit"`, with which columns?
- **A statistic on a non-numeric column** (`"mean"` of a string column): which code? See S3.
- **Name collisions:**
  - A result column `<column>.<statistic>` can collide with a `by` column, or with `.dropped`.
  - The frame check would then refuse the answer as a duplicate name, an E101 that names nothing the program wrote.
  - State a refusal at entry instead.
- **Group order:**
  - "In order of first appearance" makes the answer's row order depend on the input's row order.
  - That is the property P7's ruling rejected for factor levels ("stable under row order").
  - It also ignores a factor `by` column's level order.
  - Either order by the `by` columns (levels for a factor, as `frame.sort`) or state why first appearance is preferred.

### S8. The Preservation analysis misses three changes

- **Existing refusals of NONE.** A program that runs `json.to_value` on data with `null` and hands a column to `stat.mean` is refused with the reference's text today. Nothing in this RFC changes that, but its examples recommend `na.omit` before `stat.`. Worth one row saying the existing refusal texts (`STAT.VAR … Can not convert NONE`, `E103 … none`) are unchanged.
- **`csv`'s `is_header` and the new `header` option** (S5 above) are two spellings of one setting in the same family of words.
- **`bund2 words`'s output grows by the new names and forms.** The `?stdlib` row covers the answer to one name, not the listing, which a tool or test may compare. The UNVARIED audit's list grows as S7 says; the list is a fixed-size array, `UNVARIED: [&str; 63]` in `lib.rs`'s tests (`:857`), compared with the audit's findings (`:950`), so that test changes and should be listed.

## Notes

- **N1. Two NONEs may differ.** `json.to_value`'s NONE is `BundValue::none().with_q(0.0)` (`json.rs:112`). S3 does not say whether `na` makes the same value. If equality in tests or in `frame.check` compares q, criteria 3 and 7 depend on it. State that `na` answers what JSON's `null` does.
- **N2. Large integers.** "Sorting compares numbers as numbers": an INTEGER above 2⁵³ against a FLOAT, or two such INTEGERs, should compare exactly, not through f64. State it.
- **N3.** `frame.factor` on a numeric or logical column is unstated (R allows a numeric factor [UNGROUNDED]); presumably E101 or E103.
- **N4. Q63.** 0-based indices remain [UNGROUNDED; Q63]. It can be grounded before acceptance by reading one reference LIST word that takes an index; that is a lookup, not an owner question.
- **N5.** `frame.column` with an absent name is unstated: E101, or `get`'s `Key not found` (which §Current behaviour cites and nothing then uses)? The same applies to `frame.with` with a LIST of the wrong length (presumably E102) and `frame.select` with an absent name.
- **N6.** `frame.text`'s FLOAT format, column width, long-string handling and the non-ASCII `…` are left to criterion 8's fixed string. That is acceptable, but a sentence on the float format (Bund's `float_text`?) would make it reviewable.
- **N7.** `frame.join` with a key column holding NONE: does NONE match NONE? R's `merge` matches NA to NA by default [UNGROUNDED]; SQL does not. Unstated.
- **N8.** `frame.rows` and `frame.filter` give a row MAP whose keys sort (MAP order, §Motivation). That is fine for a lambda that reads by name, but say it, so nobody expects `columns` order from `frame.rows`.
- **N9.** S1 says a lambda-running word "has the plain form only". `frame.filter` is the only such word. State that `frame.aggregate`, `frame.join` and `frame.matrix` (fixed effects) have both forms, and which operand the `.` form takes from the workbench; RFC-0016's review S9 found the same gap.

## What the RFC assumes and does not state

- That `frame.csv.parse` shares `read_frame`'s `flexible(true)` reader, but refuses ragged rows (E102) where `csv` pads them with empty fields.
- That the `csv` crate's quote handling is the one wanted, though it is the stated difference from polars (B1).
- That `na`'s NONE and JSON's are equal values (N1).
- Which operand each `.` form takes (N9).
- That no frame word reads a MAP key order. True by S2's design, but `frame.rows` exposes sorted keys (N8).
- That the 100-row inference window carries over (S4).
- That a frame is small enough for O(cells) checks on every word. S2 says so, but the cost a chain of ten words pays (ten full checks) is not discussed; a `frame.check`-once alternative is not considered.
- That `stat.count`, the existing word, is not what `"count"` means (S7).

## Verdict

**Not ready.**
- **The blocking pair:** B1 and B2 are both in S6's CSV path, and both are defects in criterion 6. The fix is a decision about the text format (quote-aware parsing, or a narrower round-trip claim) and a rule for non-finite fields.
- **The should-fixes** are mostly unstated cases with one-line answers. S2 is the exception: as drafted, `"omit"` cannot feed `stat.lm`, which is the reason `frame.matrix` exists.
